## Terms

- **The author** is the person who owns this project and took the decisions of this spec. **A person** owns a machine that runs wizardingcode-mem. **The operator** is whoever has a shell on the host that runs the server (through `docker compose exec` or `docker compose run`): the operator installs, upgrades, restores and purges; the operator is often an admin too, but the two are different powers. **The gate machine** is the author's development machine, an Apple Silicon laptop, where the crew's gates and this part's tests run; every timing in this spec is measured there. **A member** is a person the team server knows, with a `name` (part 1's author rule, `authorNameProblem`: 1 to 80 characters, no line break, not starting with `agent:`) and a role. **A device** is one of a member's machines, holding one **device token**; it has an **id** (admins see it) and an **alias** (members see it in memory uids). **An admin** is a member who may invite, list, revoke, disable, enable, withdraw and reinstate.
- **The sync client** is part 6's code on a device: it pushes items and pulls changes. **An item** is one knowledge entry or one memory as part 4's payload types shape it (`OutgoingEntry`, `OutgoingMemory`).
- **A scope** is where an entry lives on the client (ADR 0024): `workspace` (one person's cross-project entries), `shared` (the repository written for the team) or `project`. **A remote alias** is how a team matches projects across machines: part 4's `remoteAlias`, the string `remote:` followed by the project's normalized git remote, host first, in lower case, as `remoteAliasOf` in `src/core/project.ts` builds it and `isHostLedAlias` in `src/sharing/levels.ts` accepts it (for example `remote:github.com/acme/site`; a remote that is a local path never names a project to a team). An alias holds colons and slashes and never a comma; a member reads a project's alias in `wizardingcode-mem share status`.
- **An entry's uid** is part 4's `entryUid`: `workspace:<uuid>`, `shared:<uuid>` or `project:<remote alias>:<uuid>`, where the UUID is the last 36 characters and, for a project, the alias is the text between `project:` and the last colon. The UUID is the entry's identity (ADR 0024 D-8); the scope and the alias are where it lives now. **A memory's uid** is part 4's `memoryUid`, `<generation>:<row id>`, where the **generation** is a random value the client store mints when it is created or restored, so a copied or restored store is another generation.
- **A revision** is the server's counter of an item's applied versions, starting at 1; a withdraw is a revision too. The client's frontmatter `version` is another number, local to one machine, and stays in the file bytes.
- **The epoch** is part 4's policy epoch, a counter the client bumps at every change of its sharing policy; the server stores it with each applied item for the audit and never acts on it.
- **The feed** is the server's ordered log of changes (`changes`), one row per applied, withdrawn, moved or purged item, which a device pulls from by a **cursor** (the last `seq` it saw). **The high-water file** is `<data>/feed.seq`, the record of how far the feed and the audit had got, kept beside the database so a restored copy can be told from the live one. **The mirror** is the set of git repositories under the data directory, an export of the entries written from the database. **The runbook** is part 7's document for operating a VPS.
- **The legacy migration** is the client's one-time move of its data from the old brand's home (`migrateLegacyData` in `src/cli/main.ts`), which `serve` never runs; the renaming of old environment variables (`applyLegacyEnv`) still runs for every command. **The lazy command table** is `COMMANDS` in `src/cli/main.ts`, where each command is an `await import()`.

## Problem

A small team wants the knowledge and the memories its members chose to share to reach every member's machine within seconds, with every change kept and nothing overwritten in silence; the WizardingCode team is the first to use it. Part 4 lets a person say what may leave their machine, and part 6 will move it. Nothing receives it yet. The team needs one place that holds what members share, tells who may read and write it, keeps every revision so an agent's or a person's change never silently overwrites another's, and gives each machine what changed since it last looked, for the projects it works on, within seconds while both machines are online. Today nothing in the product listens on a network: the viewer's server answers only the local machine. The release builds five binaries and no image, so a server deploy has nothing to run.

Success is visible when:

- `wizardingcode-mem serve` starts over an empty data directory, prints one admin invitation, and refuses every request but health and join without a valid device token;
- an admin invites by name, a member joins from two machines as one member, and an admin can list, revoke, disable and enable;
- a device pushes entries and memories shaped by part 4's types, a stale base is answered with the server's current revision and hash, a retry of an applied item or an applied withdraw is idempotent whatever else is going on, a payload whose hash does not match its bytes or that carries a recognisable secret is refused, a move of an entry or a memory with the same bytes is a change the others learn of, and a withdraw becomes a tombstone the others pull;
- a device pulls the changes since its cursor for the projects it names, a pull that finds nothing waits for the next change, a new project on a machine is fetched with one small snapshot, an item that moves out of a machine's projects is announced to it, and a restored database is detected and announced through a new instance id;
- the repositories on the volume hold one commit per applied revision, by the member, written by `serve mirror` and rebuilt by `serve mirror --rebuild` while the server keeps serving;
- the image runs as a non-root user behind Caddy from one compose file, and the release publishes it.

## Goals

- The command `serve` with its subcommands, its own database (`team.db`) with its own migrations behind one store module, and the repositories under one data directory (D-1, D-10, D-17, D-26).
- Members, devices, invitations, roles, bootstrap, single-phase rotation, revocation, disabling and enabling as D-2, D-3, D-4, D-5, D-9, D-14, D-19 and D-23 rule, with these refinements: admin-only invitations that carry the member's name; a device alias members see; the bootstrap admin named at join.
- The sync API under `/v1/`: `health`, `me`, `join`, `rotate`, `push`, `pull`, the admin routes; revisions decide conflicts; the server recomputes every hash and refuses recognisable secrets (D-6, D-7, D-8, D-11, D-12, D-13, D-18, D-20).
- One server is one destination, with a stable id, knowing nothing of other servers a device joins (D-21); a pull may wait for the next change, so a change reaches the other machines within seconds (D-22).
- Every revision kept (`entry_revisions`), so the mirror can be rebuilt with its history and a future item can reinstate an earlier revision; `serve purge` for the one thing a withdraw cannot do, durable against a re-send (D-24).
- The limits and rate limits this slice keeps (D-15 as narrowed by D-25); JSON logs with a request id that record the pull's cursor and filter and the push's refused uids and reasons, enough to trace a missing item from the cursor, the filter and the refusals; `serve status`, `serve audit`, the audit table (D-17).
- The Dockerfile, the compose file with Caddy, the release and CI steps (D-16).
- A `redact` rule for device tokens and invitation codes (D-14).
- `docs/adr/0026-team-server.md`.

## Non-goals

- The sync client: join, status and leave on a machine, push on write, the open pull, conflicts kept for a person, the full pull after a new instance, the list of servers and the binding of a project to one (part 6; its obligations are gathered in "What part 6 must do").
- The runbook and the README section (part 7). Until part 6 ships, nothing in the product joins a server or pushes to it: the image this part releases is tested over HTTP by this part's tests, and a person can only exercise it with `curl` as the runbook will show; the ADR says so.
- Deferred by D-25 to named follow-up items: the stored daily and per-member quotas; the feed's pruning and the horizon (the feed keeps every row in this part); the two-phase rotation; reinstating an earlier revision (reinstate unlocks only); `serve backup` (the runbook snapshots the volume with the server stopped).
- A second destination per server, teams within a server, a web page on the server, e-mail invitations, SSO, a server-side taxonomy, another database engine (D-1 keeps the one boundary that would admit it, and the ADR says what else would have to change).
- Any change to the hook path or to a client's store (part 6 owns the ledger's change, named below).

## Sizing

Measured by this part's tests on the gate machine: a pull of one alias from a seeded feed of 100,000 rows answers in under 50 ms (AC-50 pins it); a push of 200 items, a pull page of 500 rows and the propagation of a change to a held pull are measured and recorded, not pinned ("Non-functional requirements"). Estimated, not measured: the pilot is one team of at most 10 members and 25 devices, 20,000 entries and 200,000 memory rows; an export commits about ten revisions a second (a git spawn per commit), so a rebuild of 20,000 revisions takes about 35 minutes beside the running server and an hourly incremental run seconds; storage grows without bound in this part, since every revision is kept and no quota is stored: at most 25 devices × 64 MiB an hour of applied payload, so the runbook sizes the volume at 50 GiB and watches `serve status`'s free-disk figure. The figures above rest on the feed's indexes (a pull costs its page), on one connection (a push is 200 small transactions) and on the mirror running in another process. One process and one connection are the design (the ADR says so): the change signal, the leases, the rate limiter and the high-water file all assume it.

## Critical user journeys

1. **First start.** Given an empty data directory, when `wizardingcode-mem serve --data <dir>` starts, then it logs one JSON line `{ event: "bootstrap", code: "wci1_…", validHours: 24 }`, `GET /v1/health` answers `{ ok: true }` without a token, and `GET /v1/me` answers 401 without one; when `POST /v1/join` is called with that code, a device label and `name: "André"`, then it answers a device token beginning `wcm1_` once, the member is an admin named `André`, and the code is spent. Given the container was recreated and the log is gone, when the operator runs `docker compose exec server wizardingcode-mem serve invite --role admin --name André`, then a new code is printed.
2. **Two machines, one member.** Given an admin's device, when it calls `POST /v1/invitations { role: "member", name: "Ana Lopes" }`, then it gets a code; when a person joins with it and a label, then a member `Ana Lopes` and a device exist; when the admin calls `POST /v1/invitations { forMember: <Ana's id> }` and Ana joins from a second machine with the code, then the second device belongs to the same member and `GET /v1/me` on both shows one member id.
3. **A push that applies, a retry, a push that is stale.** Given an entry uid `shared:<uuid>` unknown to the server, when device A pushes it with `baseRevision` 0 and the payload, then the answer is `applied` with `revision` 1 and the hash of the payload bytes; when device B pushes a new version with `baseRevision` 1 and the current hash, then `applied` with `revision` 2; when A retries its first push, its answer lost, with `baseRevision` 0 and the same payload, then `stale` with `current: { revision: 2, hash }` and `appliedAs: 1`, so A records revision 1 as its own applied push and takes revision 2 as received; when A pushes a third version with `baseRevision` 1, then `stale` with `current` and no `appliedAs`; when B retries its own second push, then `applied` with `revision` 2 and nothing changes; when B pushes the same bytes under `project:remote:github.com/acme/site:<uuid>` on base 2, then `applied` with `revision` 3, and the feed holds an `upsert` under the alias and a `tombstone` with `movedTo` under `shared`.
4. **A memory and its owner.** Given a device pushing a memory uid `<generation>:<row id>` with a payload whose hash the server recomputes, when it pushes again with a later `updatedAt`, then `applied` with `revision` 2; with an older `updatedAt`, then `stale` with `current { revision, hash, updatedAt }`; when another device pushes the same uid, then a second row exists and both pull as `remote:<alias>:<uid>` with each device's alias; when the owning device pushes `op: "withdraw"` with `baseRevision` 2, then `withdrawn`, and the feed carries a tombstone the others pull; when it retries that withdraw, then `withdrawn` again with nothing changed.
5. **A pull for one machine's projects, a new project, a move.** Given shared entries, a member's workspace entries, and project entries and memories for two remote aliases, when a device pulls with `since` 0 and `projects` naming one alias, then it gets the shared and workspace entries and only that alias's project items, `snapshot: true`, `next` and `more`; when it pulls again with `since` set to `next` and `wait` 25, then the request is held and answers within a second of the next push with that change; when the machine takes up the second project, then one pull with `since` 0, `scope=project` and `projects` naming the new alias answers that alias's current items and nothing else; when a teammate moves an entry from the first alias to a third, then the device's next pull carries a tombstone for it with `movedTo` naming the new uid.
6. **Revocation, disabling, the last admin.** Given two admins, when one revokes the other's device, then that device's requests are 401 with `error: "device revoked"` and its unused invitations are cancelled; when the remaining admin tries to disable themself, then 409 `the last admin stays` with the way out in the body; when an admin disables a member with `withdraw: true`, then the member's workspace entries and their devices' memories are tombstoned in the feed without a lock and their devices revoked, the team's shared and project entries stay, and the member's device answers 403 `member disabled`; when the admin enables the member and invites a device for them, then the member joins again under the same id and writes their workspace entries again.
7. **Stop, restart, restore, mirror.** Given a push applied a moment ago, when the server receives SIGTERM, then it answers every held pull with an empty page, stops accepting, finishes the item in flight, signals a running mirror child and waits for it, releases its lease and exits 0; when it starts again, then `/v1/health` answers ok and `serve status` shows the lease held by the new process; when `docker compose exec server wizardingcode-mem serve mirror` runs, then the repositories hold one commit per applied revision with the member as author and a `Revision:` trailer, and `serve status` prints the last run; when an older `team.db` is put in place of the current one and the server starts, then it sees the high-water file ahead of the database, renews the instance id, advances the feed's sequence, rewrites the file, logs and audits it, and every answer carries the new id.
8. **Deploy.** Given the compose file with a domain in `.env`, when `docker compose up -d` runs, then Caddy obtains a certificate and proxies to the server, the server runs as user 10001 on the named volume behind Docker's init, `docker compose logs server` shows the bootstrap line, and `docker compose exec server wizardingcode-mem serve status` prints the state; when the operator needs `serve instance renew`, the one subcommand that needs the server stopped, then `docker compose stop server && docker compose run --rm server serve instance renew && docker compose start server` is the form.

## Proposed architecture

### The command and the data directory

`wizardingcode-mem serve [--data <dir>] [--host <addr>] [--port <n>] [--trust-proxy]` is a long-running process.

- `--data` defaults to `WIZARDINGCODE_MEM_TEAM_DATA` or, absent, `<data dir>/team` under the product's data directory; the image sets `/data`.
- `--host` defaults to `WIZARDINGCODE_MEM_TEAM_HOST` or, absent, `127.0.0.1`; the image sets `0.0.0.0`; `Bun.serve` always receives the hostname explicitly. A host outside loopback (`127.0.0.0/8`, `::1`, `localhost`) without trust-proxy logs one `warn` line at start (`event: "plain-http"`): tokens would travel in clear.
- `--port` defaults to `WIZARDINGCODE_MEM_TEAM_PORT` or 8787.
- `--trust-proxy` (or `WIZARDINGCODE_MEM_TEAM_TRUST_PROXY=on`, set by the compose file, not by the image) makes the server read the client address from the last hop of `X-Forwarded-For` for the join rate limit and the audit, and refuse every request but `/v1/health` whose `X-Forwarded-Proto` is not `https` with 400 `https required` (join included, since its answer carries the token; health stays exempt because Docker's probe sends no proxy headers); without it, the socket's address is used and the headers ignored.
- `serve` joins the lazy command table; `main.ts` skips the legacy data migration for it and its subcommands. `run` resolves on a signal, after `stop()` has cleared every timer, so the process ends on its own.
- The data directory holds `team.db` (plus `-wal` and `-shm`), `feed.seq` (the high-water file), `repos/` (the mirror) and `backups/` (the migration runner's upgrade copies, `team-<ms>-v<n>-<pid>.db`; the runner takes the backups folder itself as an option and prunes per folder as today, so the client's copies stay in its own `backups/`).

**One server per data directory (D-17).**

- At start the server claims the lease `serve.lease` in the team's `meta` with the client store's lease functions reused from `src/store/meta.ts` (`claimLease`, `releaseLease`, `leaseActive`, wrapped by `store.ts`): a holder `serve-<16 hex>` (never a pid: a container's pids repeat across restarts and namespaces, and the non-numeric prefix keeps the reused function from reading one) and a 30-second expiry, renewed every 10 seconds by a timer `stop()` clears.
- A fresh lease held by another holder makes the start exit 1 with `another serve holds <dir> (lease until <time>)`; a stale lease is replaced. A renewal that finds another holder (the event loop stalled past the expiry and another process took the directory) answers the held pulls and exits 1. `stop()` releases the lease.
- After a crash the old lease stays fresh for up to 30 seconds, so under `restart: unless-stopped` the restarted server exits repeatedly for up to 30 seconds before it runs ("Risks and mitigations").
- Subcommands that read (`status`, `members`, `invitations`, `audit`, `health`) run beside a server and write nothing. Writers of a short transaction (`invite`, `invitation revoke`, `revoke`, `disable`, `enable`, `role`, `withdraw`, `reinstate`, `purge`) run beside it through SQLite's lock, write an audit row and update the high-water file, and never migrate a database whose `user_version` is below the binary's while the serve lease is fresh ("the server runs an older schema; upgrade the image first"). `mirror`, with or without `--rebuild`, and purge's repository rebuild run beside the server under their own lease (`mirror.lease`, 120 seconds, renewed before every git call; a second run refuses "a mirror run is in progress"). `instance renew` alone refuses while the serve lease is fresh, with `stop the server first: docker compose stop server && docker compose run --rm server serve instance renew`; every other subcommand runs as `docker compose exec server wizardingcode-mem serve <sub>`.

The subcommands (the plan's subcommand table gives each one's flags, output lines and exit codes; every subcommand sends the JSON log to standard error, so standard output carries its own output alone):

- `serve invite --role admin|member --name <name> [--expires <hours>]` (a new member; the name validated by `authorNameProblem`) or `serve invite --for <member id> [--expires <hours>]` (a device for an existing member): prints the code alone, once.
- `serve invitations`: the unused ones (id, role, name or member, creator, expiry). `serve invitation revoke <id>`.
- `serve members`: one line per member (id, name, role, state, devices, last seen) and one indented line per device (id, alias, label, created, last seen, revoked).
- `serve revoke <device id>`; `serve disable <member id> [--withdraw]`; `serve enable <member id>`; `serve role <member id> admin|member`.
- `serve withdraw entry <uid> | memory remote:<alias>:<uid>` (an admin's withdraw: tombstone and lock; on an item already withdrawn, the lock alone); `serve reinstate entry <uid> | memory remote:<alias>:<uid>` (clears the lock; the item stays withdrawn until its owner re-sends).
- `serve status [--json]`: the binary's version, the team schema version, `serverId`, `instance`, members and devices (active and revoked), a pending first admin, the last feed `seq`, the high-water file's marks, the mirror's last run (time, commits, error) and its pending count (entries with `mirror_revision < revision`), the heads of the repositories, free disk at the data directory, the serve lease's owner and expiry. Exit 0; 1 when the database cannot be opened.
- `serve audit [--limit <n>]`: the last audit rows, newest first.
- `serve mirror [--rebuild]`: the export ("The mirror"); `--rebuild` rewrites every repository, beside the running server.
- `serve purge entry <uid> | memory remote:<alias>:<uid> --yes`: in one transaction removes the item's row (and an entry's revisions), blanks the payload reference of its feed rows and marks them `op: purge`, writes one feed row with op `purge`, and records the key in `purged`, so a later send of it is `refused purged`; then rebuilds every repository the entry's revisions touched without it, under the mirror's lease; the audit records it; without `--yes` it exits 64.
- `serve instance renew`: a new instance id and the feed's sequence advanced (the runbook's step after a restore of the whole volume, when the high-water file came back too); the server stopped.
- `serve health [--url <origin>]`: fetches `/v1/health` (default `http://127.0.0.1:<port>`), exits 0 on `ok: true` within 3 seconds, 1 otherwise; the image's `HEALTHCHECK`.

### The team database (D-1, D-17)

`src/team/db.ts` opens `team.db` over the core runner, which gains a file name, a backups folder and a migration list (`openFile`, `migrateFile`, `openExistingFile` in `src/store/db.ts`; `openDb` calls them with its own file, prefix, folder and `MIGRATIONS`, runs the module schemas inside the same guarded step, and restricts the files after both, so its behaviour and the place of its upgrade copies are unchanged). Before migrating, every opener reads the file by hand: a file whose `user_version` is above 0 and whose `meta` table is missing or has no `team.schema = 'team'` row is refused with `NotATeamDatabaseError` ("not a team database"), so a client store copied to `team.db` is named for what it is instead of being reported as a newer schema (`openTeamExisting` and `openTeamForWrite` run that check before the version check too); a file at a newer team version is `SchemaTooNewError`, which `serve` turns into exit 3 and the log line `team.db was written by a newer wizardingcode-mem; upgrade the image`. `src/team/errors.ts` holds `HttpError`, `NotATeamDatabaseError`, `SchemaBehindError`, `ServerRunningError`, `LeaseHeldError` and the exit code of a too-new file; `src/team/db.ts` re-exports the `Db` type for the rest of the folder. Migration 1, `team_init`, creates the tables below and mints `team.schema`, `server.id` (16 hex, never renewed), `server.instance` (16 hex, renewed by a detected restore and by `serve instance renew`) and `server.created_at`.

The entities (the DDL is the plan's; the invariants are this spec's):

- `meta` (key, value): `team.schema`, `server.id`, `server.instance`, `server.created_at`, `serve.lease` and `mirror.lease` (the JSON `src/store/meta.ts` writes: `owner`, `until`), `mirror.last` (JSON: `at`, `commits`, `error`).
- `members` (id: 12 base32 characters, random; name; role `admin|member`; created_at; disabled_at). `devices` (id: 12 base32; alias: 8 base32, unique; member_id; token_hash: SHA-256 hex, unique; label ≤ 80; created_at; last_seen_at; revoked_at). `invitations` (id; code_hash unique; role; name or null; for_member or null; created_by_device or null; created_at; expires_at; used_at; used_by_device; revoked_at). The bootstrap invitation is the one with role admin and null `name`, `for_member` and `created_by_device`.
- `entries` keyed by the UUID (`uuid` primary key; `scope`, `remote_alias`, `slug` as attributes of the current revision; `created_by_member`; `revision`; `hash`; `size`; `writer_member`; `writer_device`; `updated_at`; `withdrawn_at`; `locked_by_admin`; `mirror_revision`, the last revision the mirror exported). The client's uid is derived from the attributes; a push that moves an entry (the same UUID under another scope or alias) or renames it is a new revision of the same item, so a renamed remote or a moved entry never splits one history in two. A partial index names the entries pending the mirror.
- `entry_revisions` (uuid, revision, seq (the feed row's), op `send|withdraw`, scope, remote_alias, slug, frontmatter, body, hash, writer_member, writer_device, client_epoch, at; primary key (uuid, revision)): every revision, verbatim bytes; a withdraw revision keeps the withdrawn revision's hash and empty texts. An ordinary rowid table, since a row may hold 256 KiB (SQLite's advice for rows far above a page); so is `memories`.
- `memories` (device_id, uid, remote_alias, payload as JSON verbatim, hash, size, revision, updated_at, member_id, received_at, withdrawn_at, locked_by_admin; primary key (device_id, uid)).
- `changes` (seq `AUTOINCREMENT`; kind `entry|memory`; uid in the client's form, a memory's as `remote:<device alias>:<uid>`; key: the UUID or `<device id>:<uid>`, with `@<revision>` appended on the row a move leaves behind; op `upsert|tombstone|purge`; scope (`project` for a memory); remote_alias; revision; hash; moved_to (the new uid, on the row a move leaves behind); member_id and device_id (the actor: `operator` and `cli` for a CLI write); client_epoch; at; `current`: 1 on the newest row of a key, set to 0 on the older one in the same transaction that writes the newer). Indexes on `(key, seq)` and `(scope, remote_alias, current, seq)`: a pull is one indexed range per scope it reads (`shared`, `workspace`, and `project` with each named alias), each `current = 1 AND seq > ?` through the second index, merged by `seq` and cut at the limit, so it costs the page and never the feed; the plan's `team-pull` test pins it with `EXPLAIN QUERY PLAN` (no `SCAN` of `changes`) and with a seeded feed of 100,000 rows holding three rows for the named alias, answered in under 50 ms.
- `purged` (key, at): the keys `serve purge` erased; a send of one is `refused purged`.
- `audit` (id `AUTOINCREMENT`, at, source `api|cli|bootstrap|system`, device_id, address, action, target, detail).

**One store boundary (D-1).** Every SQL statement the server runs lives in `src/team/store.ts`: one exported function per query or write, taking the `Db` and plain values and returning plain rows, plus one `transaction(db, fn)` that wraps the core `withWrite`, the only way a caller outside `store.ts` opens a transaction (push applies an item's read-decide-write inside one), and the lease functions wrapped from `src/store/meta.ts`. `members.ts`, `auth.ts`, `audit.ts`, `push.ts`, `feed.ts`, `instance.ts`, `mirror.ts`, `status.ts` and the routes call those functions and hold no SQL: the plan's `team-store-boundary` test reads every file under `src/team/` but `store.ts` and `db.ts` and fails on an import from `src/store/` or on `.query(`, `.run(`, `.prepare(` or `withWrite(`. The schema and the migration stay in `db.ts`. Another engine would be a second `store.ts` behind the same signatures and a different `transaction`; the ADR records that the change signal, the leases, the rate limiter and the high-water file also assume one process, so the boundary keeps the SQL in one place and does not by itself make the store swappable.

### Members, devices, invitations, roles (D-2, D-3, D-4, D-5, D-9, D-14, D-19, D-23)

- **Bootstrap.** At start, when `members` is empty and no unexpired, unused admin invitation exists, the server mints one (`wci1_` plus 26 base32 characters of 130 random bits, hashed at rest, role admin, no name, expiry 24 hours), logs `{ event: "bootstrap", code, validHours: 24 }` once (the only secret the server's log ever carries; the runbook says to rotate the first admin's token after joining and how to rotate Docker's logs), and audits `bootstrap`; a restart within the 24 hours prints nothing and keeps the pending one; a lost code waits for the expiry or `serve invite --role admin --name <name>`. Until a member exists, every route but `/v1/health` and `/v1/join` is 401.
- **Invitations are admin-only.** `POST /v1/invitations { role, name, expiresInHours? }` makes a new-member code (the name validated by `authorNameProblem`, 400 `name` otherwise; `expiresInHours` 1 to 720, default 72, 400 otherwise); `POST /v1/invitations { forMember, expiresInHours? }` makes a device code for an existing member; both answer the code once. `GET /v1/invitations` lists the unused ones; `POST /v1/invitations/<id>/revoke`. Revoking a device revokes every unused invitation it created. A member cannot mint invitations: a stolen member token cannot add devices.
- **Join.** `POST /v1/join { code, label, name? }` (no token; 10 a minute per source address; a failure audited with the address and never the code, and only while the address is not rate-limited, so at most ten rows a minute per address): the code's hash must match an unused, unexpired, unrevoked invitation; a device invitation adds a device to its member; a member invitation creates the member with the invitation's name and role; the bootstrap invitation creates the admin with `name` from the body (`authorNameProblem`; absent, `admin`); `name` is ignored for any other invitation. The device gets an `id`, an `alias` and `wcm1_` plus 43 base64url characters of 32 random bytes, stored as its SHA-256 hex; the answer is `{ token, deviceId, deviceAlias, memberId, name, role, contract: 1, serverId, instance }`, the token's only appearance; `used_at` and `used_by_device` are set in the same transaction. Errors: 400 for a malformed body, a label over 80 characters or a bad name; 404 `invitation unknown`; 410 `invitation expired`, `invitation used` or `invitation revoked`; 429 over the limit.
- **Authentication.** Every other route reads `Authorization: Bearer <token>`, hashes it and loads the device by `token_hash` (the digest is the lookup key; the stored and the computed digests are then compared with `timingSafeEqual`, which adds no security after an exact lookup by digest and is kept as a convention). The checks run in this order: no device for the digest → 401 `missing or wrong token`; the device's member has `disabled_at` → 403 `member disabled`; the device has `revoked_at` → 401 `device revoked`. Every 401 and 403 body carries `serverId` and `instance`, so a client whose device a restored server has forgotten can tell it from a wrong token and re-join; `last_seen_at` is written at most once a minute per device. The header `X-WCM-Contract` names the client's contract ("Compatibility").
- **Roles.** A member calls `me`, `push`, `pull`, `rotate`; an admin also calls the invitation and admin routes (403 `admin only` for a member). The last active admin (the only admin with `disabled_at` null and an unrevoked device) cannot be disabled, have its last device revoked, or be demoted (the check runs inside the write's transaction, so a CLI writer beside the server cannot race it): 409 `{ error: "the last admin stays", hint: "promote another member, or invite a device for this admin with serve invite --for <id>, then retry" }`; a lost laptop is recovered that way.
- **Rotation (single-phase).** `POST /v1/devices/me/rotate`: a new token for the calling device, answered once; the old token is invalid from that transaction on; the id and the alias are unchanged. A client that loses the answer is 401 `missing or wrong token` with `serverId` and `instance`, and re-joins with a device invitation; the runbook says so.
- **Admin routes.** `GET /v1/members`, `GET /v1/devices` (ids, aliases, labels, times), `POST /v1/devices/<id>/revoke`, `POST /v1/members/<id>/disable { withdraw?: boolean }` (revokes every device of the member; with `withdraw` true, tombstones the member's workspace entries and their devices' memories in one transaction, one feed row each, without a lock, and never a shared or project entry), `POST /v1/members/<id>/enable` (clears `disabled_at`; the devices stay revoked and a device invitation brings the member back under the same id), `POST /v1/members/<id>/role { role }`, `POST /v1/items/<kind>/<uid>/withdraw` (the uid URL-encoded as one path segment: an entry's uid, or a memory's feed form `remote:<alias>:<uid>`; sets `withdrawn_at` and `locked_by_admin`, the lock alone when the item is already withdrawn: the admin routes and `serve withdraw` are the only writes that lock), `POST /v1/items/<kind>/<uid>/reinstate` (clears the lock; the item stays withdrawn until its owner re-sends), `GET /v1/audit?limit=`. The plan's route table gives every request and answer shape.
- **`GET /v1/me`**: `{ member: { id, name, role }, device: { id, alias, label }, serverId, instance, contract: 1, now, limits: { bodyBytes, itemsPerPush, itemBytes, pullItems, pullBytes, pullWaitSeconds, requestsPerMinute, payloadBytesPerHour, joinsPerMinute, minFreeBytes } }`.

### Compatibility (D-18, D-21)

`X-WCM-Contract` absent or `1` is accepted on every route but health and join; another value is 409 `{ error: "contract", accepted: [1] }`. The client speaks the highest contract the server accepts, read from `/v1/me` or from the 409, so a newer client against an older server keeps working at the older contract (part 6's rule, named here, since client binaries reach machines through plugin updates the operator does not control); and from the first bump on, the server accepts the contract before the current one for one release, so a member who has not updated keeps pushing and pulling until the next release. A contract is the key lists `OUTGOING_ENTRY_KEYS` and `OUTGOING_MEMORY_KEYS`, the result shapes and the push reason codes: the plan's `team-contract` test pins `CONTRACT_FINGERPRINT`, the SHA-256 of those lists and shapes, beside `CONTRACT`, and fails when they change without the contract changing. The redaction rules are not part of the contract: a server with a rule a client lacks refuses that client's entry with `secret` and the rule's name, which the client's log shows, and the remedy is the client's upgrade; a new rule ships in the client release first ("Risks and mitigations"). The server publishes `serverId` (`server.id`, minted once and never renewed) in `join`, `me`, every pull and every 401, 403, 409 and 410, so the client's ledger and policy are keyed by it, not by the URL (which moves) or the instance (which a restore renews).

### Push (D-6, D-7, D-8, D-12, D-15, D-20)

`POST /v1/push { epoch, items: [ { op: "send" | "withdraw", kind: "entry" | "memory", uid, baseRevision?, baseHash?, payload? } ] }`, at most 200 items; the plan's `parsePushBody` says which fields are required, their types, the defaults (`baseRevision` 0 and `baseHash` empty when absent on a send) and the 400 texts. The published body cap is 1,048,576 bytes: the handler refuses a `Content-Length` above it with 413 and the request id, and counts the bytes it reads so a chunked body past the cap is 413 too; `Bun.serve`'s own `maxRequestBodySize` is set at 2 MiB, above the handler's check, so Bun's 413 without a request id or a log line happens only for a body above that (behind the proxy, Caddy's `max_size 1MiB` refuses first). Items are applied one by one in the order given, each in its own `transaction`, and the answer lists one result per item in the same order: `{ uid, result, revision?, hash?, current?: { revision, hash, updatedAt? }, appliedAs?, reason?, rule? }`. After the last item the server fires the change signal once when a feed row was written ("Pull, the feed, the wait, the instance"), writes the high-water file ("Pull, the feed, the wait, the instance", the paragraph "Restore detection"), arms the mirror timer and logs the request line with the counts and the refused uids and reasons.

For an entry `send`, in this order:

1. **Shape.** The payload must be an `OutgoingEntry` by `OUTGOING_ENTRY_KEYS` and by type (`kind` the literal `entry`; `uid`, `scope`, `slug`, `frontmatter`, `body` and `hash` strings; `remoteAlias` a string or null; `version` a finite number; a wrong type is `refused shape`, never a 500), with `uid` equal to the item's and matching `entryUid`'s grammar (the UUID by part 1's `UUID`; a project's alias by `isHostLedAlias`), `scope` agreeing with the uid's prefix and `remoteAlias` with its alias (null outside a project), and `slug` passing `checkSlug` (else `refused slug`); else `refused shape`.
2. **Size.** The bytes are the UTF-8 of `payload.frontmatter + payload.body`, where the client fills `frontmatter` with the file's frontmatter block including its closing `---` line and newline and `body` with the rest of the file as on disk, so the concatenation is the file's text; over 256 KiB (`ENTRY_MAX_BYTES`), `refused size`.
3. **Hash.** `hashOf(bytes)` (`src/modules/knowledge/repo.ts`: the first 16 hex characters of the SHA-256) is recomputed; a `payload.hash` that differs is `refused hash`. The server's hash is of the bytes received, after the client's redaction.
4. **Entry.** `parseEntry(frontmatter + body, payload.slug, null)` must read the entry without a problem (the frontmatter has no slug: the slug is the file name, `payload.slug`); its `id` must equal the uid's UUID and its `area` must match `AREA_ID` within `AREA_MAX`; else `refused shape`. `author` is informational.
5. **Secrets.** `findSecrets(text, { env: {} })` over the bytes; a match is `refused secret` with `rule` naming the pattern (defence in depth: the client redacts at its edge, the server refuses what still looks like a credential).
6. **Purged.** A UUID in `purged` is `refused purged`: erasure is durable.
7. **Idempotency.** When a row exists for the UUID, is not withdrawn, and its `hash`, `scope`, `remote_alias` and `slug` all equal the payload's, the answer is `applied` with the current revision and hash and nothing changes, whatever the item's base, the lock, the bucket or the disk: a retry of an applied item always succeeds. The hash covers the file bytes alone, which carry no scope, alias or slug, so a move or a rename with the same bytes is a change, not a retry.
8. **Ownership.** The stored row decides, never the uid alone: a row whose current scope is `workspace` takes a send of any scope only from its `created_by_member` (another member's push is `refused not-owner`); a send that would move a row into `workspace` is taken only from its creator; a row whose current scope is `shared` or `project` is the team's, and a move between those two is any member's on the current base. With no row, a `workspace:` uid makes its sender the creator.
9. **The lock.** An item locked by an admin is `refused withdrawn-by-admin` until reinstated.
10. **Stale.** With no row, `baseRevision` must be 0 and `baseHash` empty, else `stale` with `current: { revision: 0, hash: "" }`; with a row, `baseRevision` must equal `revision` and `baseHash` must equal `hash`, else `stale` with the current ones and, when an earlier revision of this UUID written by the same device has the payload's hash, scope, alias and slug, `appliedAs: <that revision>`, so the client learns its earlier push applied; a deliberate revert on an old base is `stale` without it. A withdrawn row is current at its tombstone's revision and keeps the withdrawn revision's hash, so a re-send on that base, with that revision and that hash, reinstates the entry as a new revision.
11. **Rate.** The device's bytes bucket (64 MiB of applied payload an hour) must take the payload's size, else `refused rate`; an idempotent retry (step 7) was never charged.
12. **Storage.** Free space at the data directory under 200 MiB is `refused storage` (one check per push, before the first item that would write).
13. **Write.** The row (`revision + 1`, the attributes of the payload, the hash, the size, the writer, `withdrawn_at` null), the revision row with the bytes, the feed row's `seq` and `client_epoch`, a `changes` row `upsert` under the UUID's key (the older row of the key set to `current = 0`), and, when the scope or the alias changed, a second `changes` row `tombstone` in the scope and alias the entry left, keyed `<uuid>@<new revision>` and carrying `moved_to` (the new uid), so a device reading the old range learns the entry left; then `applied` with the new revision and hash.

For a memory `send`, in this order:

1. **Shape.** An `OutgoingMemory` by `OUTGOING_MEMORY_KEYS` and by type (`kind` the literal `memory`; `uid`, `remoteAlias`, `title`, `body`, `memoryKind`, `status` and `hash` strings; `importance`, `createdAt`, `updatedAt` and `version` finite numbers; `memoryKind` and `status` matching `^[a-z][a-z0-9_-]{0,31}$`), with `uid` equal to the item's and `remoteAlias` passing `isHostLedAlias`; else `refused shape`.
2. **Size.** The payload's JSON at most 256 KiB, else `refused size`.
3. **Hash.** `memoryHash` over `MEMORY_HASH_FIELDS` recomputed; a differing `payload.hash` is `refused hash`.
4. **Secrets.** `findSecrets` over title and body; a match is `refused secret` with `rule`.
5. **Purged.** A key `<device id>:<uid>` in `purged` is `refused purged`.
6. **Idempotency.** The device's own row with the same hash and the same `remoteAlias`, not withdrawn, is `applied` with its revision and nothing changes. Another device's row with the same uid is another row, never this one.
7. **The lock.** The device's own row locked by an admin is `refused withdrawn-by-admin`.
8. **Rate.** The bytes bucket must take the size, else `refused rate`.
9. **Storage.** Free space under 200 MiB is `refused storage`.
10. **Order.** The payload's `updatedAt` must not be older than the stored one, else `stale` with `current: { revision, hash, updatedAt }`.
11. **Write.** The row replaced (`revision + 1`), a `changes` row `upsert` with the uid `remote:<device alias>:<uid>`, the key `<device id>:<uid>`, scope `project` and the memory's alias, and, when the alias changed, a second `changes` row `tombstone` under the old alias, keyed `<device id>:<uid>@<revision>` with `moved_to`; then `applied`.

For a `withdraw`, in this order:

1. **The item.** An entry withdraw names the entry's uid; a memory withdraw names the caller's own row by its `<generation>:<row id>` uid, or another device's row by the feed form `remote:<alias>:<uid>`. An unknown item is `refused unknown`.
2. **The base.** An entry withdraw carries `baseRevision` and `baseHash` like a send; a memory withdraw carries `baseRevision` equal to the row's revision and no hash. One retry rule, for both kinds: when the item is already withdrawn, a withdraw whose `baseRevision` is the revision just before the tombstone, from the device or the member that wrote the tombstone, answers `withdrawn` with nothing changed; any other base on a withdrawn item, and any base that is not the current one on a live item, is `stale` with `current`, so a creator who has not seen a teammate's revision never tombstones text they have not read.
3. **Ownership.** An entry is withdrawn by its `created_by_member`'s devices or by an admin; a memory by its own device, by another device of the same member, or by an admin; anyone else is `refused not-owner`.
4. **Write.** The tombstone: `withdrawn_at`, for an entry a revision row `withdraw` keeping the hash and incrementing the revision, for a memory the revision incremented, a `changes` row `tombstone`, no lock; then `withdrawn`.

The push reason codes, a fixed list: `shape`, `size`, `hash`, `slug`, `secret`, `purged`, `not-owner`, `withdrawn-by-admin`, `unknown`, `rate`, `storage`. The server never calls `decide`; `epoch` is stored with the revision and feed rows for the audit.

### Pull, the feed, the wait, the instance (D-11, D-13, D-22)

`GET /v1/pull?since=<seq>&limit=<n>&projects=<comma list of URL-encoded remote aliases>&wait=<seconds>&scope=project`: the `changes` rows with `current = 1` and `seq` greater than `since`, read as one indexed range per scope (`shared`; `workspace`, every member's; `project` for each alias in `projects`, none when it is empty) merged by `seq`, at most `limit` (default and maximum 500) items or 2 MiB of payload (a page stops before the item that would cross it), as `{ serverId, instance, next, more, snapshot, items: [ { seq, kind, uid, op, scope, remoteAlias, revision, hash, movedTo?, payload?, member: { id, name }, device?, at } ] }`; an `upsert` carries the current payload (`frontmatter` and `body`, or the memory's JSON), a `tombstone` or `purge` none; a member's view carries the writer's member (`{ id: "operator", name: "operator" }` for a CLI write) and no device id (the memory uid's alias is opaque); an admin's view adds `device`. The alias filter keeps a machine small; it is not a permission: any member may name any alias, and the ADR says so. An alias is URL-encoded in the query like any value and holds no comma.

**Snapshots.** A pull with `since` 0 opens a snapshot: `snapshot: true` on that page; the client pages on with `since` set to `next` until `more` is false, and the set of items the pages answer is the current state of the scopes and aliases it asked for; "a uid absent from the snapshot is gone" applies to that set, after the last page, and to those scopes and aliases only. With `scope=project` and one alias in `projects`, a snapshot answers that alias's current items alone: the pull a machine makes when it takes up a project it did not name before, so adding a project costs one small snapshot and not a full one.

**Moves.** An entry or a memory that leaves a scope or an alias leaves a `tombstone` row with `movedTo` in the range it left (its key with `@<revision>` appended stays current there), so a device that reads only the old range drops its copy, and a device that reads both ranges sees the tombstone and the `upsert` and keeps one.

**Cursors and restores.** `next` is the last `seq` served, `more` says whether rows follow. A `since` above the server's current sequence (the `AUTOINCREMENT` high-water, `sqlite_sequence`) is 410 `{ error: "cursor ahead of this server", fullPull: true, serverId, instance }`. `serverId` is `server.id`; `instance` is `server.instance`; a client that sees a new instance pulls from zero and reconciles its ledger (part 6's rule, named below).

**Waiting for the next change (D-22).** `wait=<seconds>` (0 to 25; absent is 0; above 25 is clamped) makes an otherwise empty answer wait: when no row visible to the caller has `seq` greater than `since`, the handler subscribes to the server's change signal (`ChangeSignal`, fired once per push that wrote a feed row and once per API call that writes one) and re-reads the feed (the same indexed ranges, limit one) when it fires or every 5 seconds (so a change made by a CLI subcommand in another process is seen within 5 seconds), answering as soon as a row the caller can see exists, or with `{ serverId, instance, items: [], next: since, more: false, snapshot: false }` when the wait ends. A pull that finds rows answers at once, `wait` or not. A held request counts once for the device's rate limit; the server's `idleTimeout` (120 s) is above the longest wait; `stop()` answers every held pull with the empty page before anything else, so a deploy never leaves a client waiting; Caddy's `reverse_proxy` sets no response timeout by default and the 25-second answer is one complete response, not a stream, which the runbook's smoke test checks (this part's tests run without the proxy). `GET /v1/me` publishes `pullWaitSeconds: 25`.

**Restore detection (D-13).** After every write that adds a feed row or an audit row (a push, a join, a rotation, an API or CLI admin act, a tombstone), the writer updates `<data>/feed.seq` (an atomic write, through part 1's `writeFileAtomic`, of the two `AUTOINCREMENT` high-waters read from `sqlite_sequence`, as JSON `{ changes, audit }`, each 0 while its table has no row yet; every join and every admin act writes an audit row, so a copy taken before a revoke, a disable or a join is detected even when no push came between). At start the server compares the file with `sqlite_sequence`: either number ahead of the database means the database was restored from an older copy; the server renews `server.instance`, advances the `changes` sequence to 1,000,000 above the greater of the file's and the database's marks (an upsert of the `sqlite_sequence` row, which may not exist yet, never lowering it, so rows written from now on never reuse a number a client passed before the restore), rewrites the file with the database's marks in the same step (so the next restart detects nothing), logs and audits `restore detected` with the four numbers, and carries on; a database ahead of the file (the file lost) rewrites the file. `serve instance renew` does the same renewal and advance by hand: the runbook's step after a restore of the whole volume, when the file came back too, run before the server starts; that case no file on the volume can detect, and the ADR names it as the one undetected restore: a client that pulls between such a restore and the renewal reads rows under reused numbers and misses the rows the restore lost until the renewal makes it pull from zero.

### The mirror (D-10, D-26)

`serve mirror` (`src/team/mirror.ts`) exports the entries to git repositories under `repos/`:

- The folders: `repos/shared/`; `repos/projects/<slug>-<hash>/`, the slug part 1's `slugify` of the alias without its `remote:` prefix (`project` when nothing is left) and the hash the first 8 hex of part 1's `projectFolderName(alias)`; `repos/members/<member id>-<slug>/`, the slug `slugify` of the name (`member` when nothing is left). A folder is built from the id or the hash and the slug and never from the raw name or alias, so a name such as `../x` or an alias with slashes stays directly under its parent. `knowledge.json` in each holds `{ format: 1, scope, remoteAlias | memberId, memberName, mirror: true, createdAt }`.
- A repository is created on first use with `git init -q --template=` (as part 1's `createRepository` does), `knowledge.json`, `entries/` and one commit `team: init <scope>` by the server; a repository found with `.git` and no HEAD (a run cut after `init`) is completed the same way; an `index.lock` left in a repository by a run whose lease is gone is removed before the first git call.
- A run holds `mirror.lease` (120 seconds, renewed before every git call; a renewal that finds another holder aborts the run and records the error), reads the entries with `mirror_revision < revision`, and, in the order of their revisions' `seq`, writes each revision as one commit: the file `entries/<slug>--<first 8 hex of the UUID>.md` (a fixed name, so two entries with one slug never collide and a slug change is a rename of the same file), the payload bytes verbatim; a `withdraw` revision removes the file; a revision whose repository differs from the previous revision's (a move) removes the file from the previous repository in a commit there and writes it in the new one; the message `team: <send|withdraw|move> <uid>` with the trailers `Revision: <n>`, `Uid: <uid>` and `Hash: <hash>`; the author is the member (`<name> <<member id>@members.wizardingcode.invalid>`), the committer the server (`wizardingcode-mem serve <server@team.wizardingcode.invalid>`); then `mirror_revision` is set.
- A run that fails on one repository records the error in `meta.mirror.last` and goes on with the others; the next run retries. `--rebuild` removes every repository folder and replays `entry_revisions` from the start, each revision into the repository its scope and alias name, beside the running server under the same lease (the sync never reads the mirror); a database restored without the mirror is followed by `serve mirror --rebuild`, which the runbook says. `serve purge` of an entry rebuilds every repository its revisions touched, the same way.
- The server runs `serve mirror` as a child process (its own command line through `src/util/self.ts`'s `selfCommand`, which tells a compiled binary from a run under bun, with the data directory) every hour and one minute after the last push of a quiet period, never while its previous child is alive; it never runs on a request and never blocks the event loop; the child's JSON lines are forwarded to the server's log; `stop()` signals a running child and waits for it for up to 20 seconds within the compose file's grace; `serve status` reads `meta.mirror.last` and the pending count from the database, so another process sees them.
- Git runs through part 1's runner, synchronously in the child: `gitEnv` and `runGit` take a `GitHost` (the data directory, the environment the runner reads `PATH` from, the git timeout, an optional root and extra configuration), which `KnowledgeStore` satisfies as it is; `GIT_CEILING_DIRECTORIES` is the host's root (the store's `knowledge/` as today, the mirror's `repos/`); `gitEnv` and `commitPaths` take a `committer` apart from the author; the staging and commit helpers take a repository path; the mirror's host sets a 60-second timeout and the extra configuration `safe.directory=*` for a volume owned by another user; `gc.auto` stays git's default, so git compacts loose objects in the child, under its timeout, and no weekly job exists. Every other isolation rule of the runner (no user configuration, no hooks, no signing, no templates) applies as it stands.

### Limits, rate limits, logs, health (D-15, D-17)

- The rate limiter is in memory per process: a token bucket per device id for requests (600 a minute, 429 `{ error: "rate limited" }` with `Retry-After` in seconds), one per device id for applied payload bytes (64 MiB an hour, checked per item before its write, `refused rate`), and one per source address for joins (10 a minute, 429); the buckets are swept by the hourly interval and reset on restart; `/v1/health` is not limited. The limits are constants in `src/team/server.ts` (`LIMITS`), published in `/v1/me`; the stored daily and per-member quotas are a follow-up (D-25).
- `GET /v1/health` answers 200 `{ ok: true }` without a token and carries no version; it answers 503 `{ ok: false, error: "low disk" }` when free disk at the data directory is under 100 MiB. Its consumer is the image's `HEALTHCHECK` (`serve health`), which `docker ps` and the runbook's checks read; nothing restarts the container on it.
- Logs are JSON lines on standard output: `{ at, level, event: "request", requestId, deviceId?, memberId?, route, status, ms, address?, held?: ms, pull?: { since, next, projects: n, items, snapshot }, push?: { applied, stale, refused, withdrawn, refusals: [ { uid, reason, rule? } ] } }`, enough to trace a missing item from the cursor, the filter and the refusals, without a payload; `src/util/log.ts` gains `setLogSink(fn)`, which every `serve` subcommand sets (the server to standard output, a subcommand to standard error) so every `logError` in the process (the runner's included) becomes a line `{ at, level: "error", event: "error", scope, name, message, requestId? }` instead of a file write; the bootstrap line is the only secret the server's log ever carries; tokens, codes and payloads never appear; a 500 answers `{ error: "internal error", requestId }` and the log line carries the message; every answer the handler gives carries `X-Request-Id` (a client's own `X-Request-Id` of at most 64 safe characters is echoed, else one is minted), and every 401, 403, 409 and 410 body carries `serverId` and `instance`.
- `Bun.serve` runs with `idleTimeout: 120` and `maxRequestBodySize: 2_097_152`.
- SIGTERM and SIGINT: every held pull answered, `server.stop()` without force (no new requests, the item in flight finishes), the lease renewal, the mirror and the hourly interval cleared, a running mirror child signalled and awaited for up to 20 seconds, the lease released, the database closed, exit 0 within the compose file's 30-second grace.

## What part 6 must do

Gathered here so part 6's author reads one section; the ADR records them as obligations.

- Hold a list of servers, each with its `https://` URL, its `serverId`, its device token and its contract; bind a project to one server at most; choose roots and areas per server; key the ledger and the policy by `serverId` (D-21), which asks part 6 for a migration of part 4's `sharing_ledger` (`destination` from the one value `team` to a `serverId`, `version` meaning the server's revision), named here and owned by part 6.
- Speak the highest contract the server accepts, read from `/v1/me` or a 409 (D-18).
- Fill `OutgoingEntry.frontmatter` and `body` by splitting the file's text at the end of the frontmatter block, not from a parsed and trimmed body, redact both, recompute `hash` with `hashOf` over the redacted bytes before sending, and record in the ledger the local hash `decide` compares beside the hash the server answered, which is the `baseHash` of the next push.
- Treat `applied` with an unchanged revision as success, `stale` with `appliedAs` as an earlier success to record, `refused` as final for that item and that content (a `secret` refusal names the rule: an older client's remedy is its upgrade; a `purged` refusal means the item is gone for good: drop the copy and its ledger row), `rate` and `storage` as "try later", `stale` on a withdraw as a revision to read first, and a memory's `current.updatedAt` as the clock to compare.
- Keep one pull open per server with `wait` while a session or the viewer is active; push right after each local change the policy allows, never on a hook path; open a snapshot (`since` 0, paged with `since` set to `next`) at the first pull, after a new `instance`, after a 410, and for one alias with `scope=project` when a machine takes up a project; drop the local copy of an item whose tombstone carries `movedTo` to a range it does not read; on a `purge` row, drop the copy and its ledger row and never re-send it.
- Use the feed's memory uid (`remote:<alias>:<uid>`) as the item's uid as it stands, without a second prefix; dedupe copied stores by content, since a restored client store is another generation and another device.
- Re-join with a device invitation when a 401 carries a `serverId` it knows and an `instance` it does not, or after a lost rotate answer.

## Alternatives considered

- **Git repositories as the server's source of truth.** Rejected: three stores cannot share one transaction, and the feed cannot be rebuilt from files (D-10).
- **A live mirror written by an in-process queue after each applied item.** Rejected after the brainstorm's second round: it cost a queue, crash recovery from commit trailers, a backoff ladder, a second asynchronous copy of part 1's git runner and a high-water file inside the derived tree, and four of the round's blockers came from it (the mark lagged the database and never moved for memories; revisions reused after a restore defeated the trailer check; the runner's fail path misnamed the command; `gc` ran under a 15-second timeout); an export from the database gives the same repositories, rebuildable, with a child process run hourly (D-26).
- **No git on the server.** Rejected: the mission names repositories on volumes; the export runs hourly in a child process and gives the team a readable history (D-26).
- **Last write wins for entries.** Rejected: the mission says versions decide, never a silent overwrite (D-7). **A withdraw without a base.** Rejected for the same reason: it tombstoned a revision the withdrawing member had never seen (D-7, D-12).
- **The payload's `version` as the server's.** Rejected: part 1's counter is local to one machine; the server owns a revision and keeps the payload bytes verbatim so the client's hash stays the judge (D-7).
- **Entries keyed by the client's uid.** Rejected: the uid carries the scope and the alias, so a renamed remote or a moved entry would split one history in two; the UUID is the identity (ADR 0024 D-8, this spec's D-8) and the scope and alias are attributes.
- **Idempotency by hash alone.** Rejected in the second review: the hash covers the file bytes, which carry no scope, alias or slug, so a move or a rename with the same bytes would be swallowed as a retry; the stored attributes are compared too (D-7).
- **Trusting the client's hash.** Rejected: a wrong hash would make every other client's `decide` (part 4's predicate, which compares an item's hash with the ledger's) answer `received-same` and never fetch the change; the server recomputes with the same functions (D-8).
- **Only the current payload kept.** Rejected: a retry whose answer was lost could not be recognised, the mirror could not be rebuilt with its history, and a later item could not reinstate an earlier revision.
- **Memories keyed by the client's uid alone.** Rejected: a copied store would be refused forever; the device scopes it (D-12).
- **A member per join; a member minting their own device invitations.** Rejected: one person has several machines, and a stolen member token must not add devices; admins invite, by name (D-9).
- **Every device pulls everything; a full pull when a machine takes up a project.** Rejected: ADR 0018's rule (a machine holds only the projects it works on) carried across people; a device names the projects it works on, and a new project is one snapshot of that alias (D-11).
- **A password hash for device tokens.** Rejected: 256-bit random secrets need no slow hash; the digest is the lookup key (D-2).
- **The first admin's code in a file on the volume.** Rejected: a second copy of a secret where backups go; the log is enough (D-3).
- **A lock file with a pid.** Rejected: a container's pids repeat across restarts and namespaces, so a crash left a lock that looped the restart; a lease in the database with an expiry needs no pid (D-17).
- **A manual instance renewal as the only restore signal.** Rejected: a forgotten step makes every client miss changes; the high-water file written by every writer and compared with the sequences detects a restored database, and the margin added at renewal keeps new rows from reusing numbers (D-13).
- **Restore detection written by the mirror.** Rejected: the mirror handles entries only and could lag; the writers of the feed and the audit write the mark (D-13).
- **Purge as a deletion alone.** Rejected in the second review: a device that still held the item would re-create it on base 0; the server remembers the key and refuses it (D-24).
- **A rebuild and a purge with the server stopped.** Rejected in the second review: a rebuild of the pilot's 20,000 revisions takes about 35 minutes, and the sync never reads the mirror, so both run beside the server under the mirror's lease (D-26).
- **Only one direction of contract skew.** Rejected: client binaries reach machines through plugin updates the operator does not control, and the operator upgrades the server when they can, so the client adapts downward and the server keeps the previous contract for one release (D-18).
- **Postgres.** Rejected for this part: a second service with its secret, its backups and a CI service, for 60 pushes a minute on one process; the store boundary keeps the SQL in one place (D-1).
- **Polling on a timer as the only way to learn of a change.** Rejected: the author asked that a change reach the other machines within seconds; a pull that waits costs one idle connection per device (D-22).
- **One server for everything a person shares.** Rejected: a person works for several teams; each server is a destination of its own (D-21).
- **Health through curl in the image; tini in the image.** Rejected: the binary probes itself; Docker's init is one line in the compose file (D-16).
- **`0.0.0.0` and trust-proxy as the binary's or the image's default.** Rejected: loopback by default, the compose file sets the host and the proxy trust, and a public host without the proxy warns (D-16).

## Risks and mitigations

- **Withdrawn text stays in `entry_revisions` and in the mirror's history; a tombstone keeps a memory's bytes.** `serve purge` is the erasure path (D-24), durable against a re-send, and the ADR and the runbook say when to use it; a purge of a shared entry rebuilds `repos/shared`, about 35 minutes at the pilot's size, beside the running server; clones of the volume are the operator's.
- **A leaked device token.** It is `wcm1_`-prefixed, so `redact` catches a pasted one; a device rotates it; an admin revokes it, and revocation cancels the invitations it made. A leaked admin token before revocation can mint members: the audit shows them and an admin disables them.
- **The first admin's code is in the container's log.** It is single-use and expires in 24 hours; the runbook says to rotate the first admin's token after joining and how to rotate Docker's logs; a recreated container loses the line, and `serve invite --role admin` mints another.
- **A copied store sends twice.** Two machines with the same generation are two devices on the server; their memories are two rows; a teammate's agent sees duplicates until part 6 dedupes by content. Named in the ADR.
- **A device looping on edits.** Within its request limit a device could write 600 MiB of revisions a minute; the bytes bucket caps it at 64 MiB an hour (`refused rate` per item), `serve status` shows free disk, and the operator's remedy is `serve revoke` of the device; the storage floor refuses new writes at 200 MiB free for everyone, and the runbook sizes the volume at 50 GiB and says so.
- **Join spam.** A failed join writes an audit row only while its address is under the limit, and the address buckets are swept hourly; many addresses still grow the audit table and the address buckets; named in the runbook with the proxy's own limits as the remedy.
- **A redaction rule a client lacks.** A newer server refuses that client's entry with `secret` and the rule's name; the client's log shows it and the upgrade is the remedy; a new rule ships in the client release first. Named in the ADR.
- **Clock skew.** Memories use the client's `updatedAt` to order a device's own replaces only; the feed uses the server's `seq`; expiries and leases use the server's clock.
- **A full disk.** Pushes are `refused storage` under 200 MiB free, health fails under 100 MiB, `serve status` prints the figure; a migration that fails leaves one upgrade copy per attempt under `backups/`, so the runbook says to free space before restarting a looping container.
- **A restore.** A restored database is detected by the high-water file, the instance renewed, the sequence advanced and the file rewritten; a restore of the whole volume needs `serve instance renew` before the server starts, the one case nothing on the volume can detect, and a client that pulls before that step misses the rows the restore lost until the renewal makes it pull from zero; after a new instance every client pulls from zero and reconciles (part 6); devices joined after the copy are gone and their 401 carries the ids they need to re-join; a database restored without the mirror is followed by `serve mirror --rebuild`, beside the server.
- **A crash and the lease.** After a kill the old lease stays fresh for up to 30 seconds, so under `restart: unless-stopped` the restarted server exits repeatedly for up to 30 seconds and `instance renew` refuses for that long; the runbook says so.
- **A killed mirror child.** `stop()` signals the child and waits for it within the grace; a run that still dies mid-commit leaves `index.lock`, which the next run removes once the dead run's lease is gone.
- **A held pull and a restart.** `stop()` answers every held pull before anything else, so a deploy never leaves a client waiting; a client whose connection drops retries from the same cursor.
- **The alias filter is not a permission.** Any member may read any item of the server; the Sharing page already says a shared item reaches the team. Named in the ADR.
- **One process.** The change signal, the leases, the rate limiter and the high-water file assume one server process per data directory; a second process is refused by the lease, and a server that loses its lease exits. Named in the ADR beside the store boundary.
- **Rollback.** The server is new code behind a new command; a client without part 6 never calls it. Across a schema bump, a previous image exits 3 against the newer `team.db` and `restart: unless-stopped` would loop: the procedure, in the compose form the ADR and the runbook carry, is `docker compose stop server`, then `docker compose run --rm --entrypoint sh server -c 'cp /data/backups/team-<ms>-v<n>-<pid>.db /data/team.db && rm -f /data/team.db-wal /data/team.db-shm'` (the WAL and SHM files go with the replaced file, or a stale write-ahead log replays frames of the newer schema over the older copy), then `WIZARDINGCODE_MEM_VERSION` set to the previous tag in `.env` and `docker compose up -d server`; `feed.seq` stays as it is, ahead of the copy, so the restore detection renews the instance and every client pulls from zero and re-pushes what the copy lacks; the plan's `team-db` test walks that path (AC-44). A writer subcommand of a newer binary refuses to migrate a database a running older server holds.

## Non-functional requirements

- **Hook path.** Untouched: no hook imports `src/team/`; the runner's split, the HTTP helpers' move, the log sink and the `GitHost` seam change no behaviour (the pinned snapshots, part 1's tests and the perf budgets hold).
- **Latency.** A push of 200 items applies in under 2 s on the gate machine (no git on the request path; one `findSecrets` pass per item); a pull page of 500 rows in under 500 ms from a feed of 100,000 rows; a change pushed by one device is in another device's held pull within 1 s; measured by the gate and recorded, not pinned, except the 50 ms of the seeded single-alias pull, which AC-50 pins.
- **Security and privacy.** Every route but health and join authenticated; tokens hashed at rest; invitations admin-only; roles enforced on the server; the last admin protected; bodies capped, by header and by bytes read; hashes recomputed; recognisable secrets refused; no version on the unauthenticated route; the binary loopback by default and a public host without the proxy warned; the image non-root with a read-only root, no capabilities and no new privileges; TLS at the proxy with HSTS and `https` required behind it; tokens and codes recognised by `src/core/redact.ts`, which the client's store applies; the database holds part 4's payload types plus member, device, invitation and audit rows, the revision, the hash and the times (D-8) and nothing else; the pull feed shows members' names and times to members, and the device id to admins only.
- **Operability.** JSON logs with request ids that name the pull's cursor and the push's refusals; `serve status` with the mirror's last run, the pending count and the lease; `serve audit`; `serve mirror` and `serve purge` beside the running server; `serve instance renew` with the compose form in its refusal; the server id and the instance in every answer; restore detected.
- **Rollout and rollback.** The release publishes the image with the version tag and `publish` waits for it; the runbook (part 7) names the three files to copy and the commands to run; the client adapts to the server's contract and the server keeps the previous one for a release; the rollback across a schema bump is the procedure under "Risks and mitigations".
