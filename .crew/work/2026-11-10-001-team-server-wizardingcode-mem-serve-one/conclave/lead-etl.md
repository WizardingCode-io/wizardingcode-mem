## Returns
- R-1 · .crew/work/2026-11-10-001-team-server-wizardingcode-mem-serve-one/plan.md:170 (and spec.md:267, AC-22) · The feed's "O(page)" claim has no plan and no check. The general pull (spec.md:184) filters `scope IN (shared, workspace) OR (project AND remote_alias IN (...))`, `current = 1 AND seq > ?`, ordered by `seq`. The index `changes_current(current, seq)` serves the order but not the OR. A device that names few aliases therefore walks every current row after its cursor, so the cost is O(feed), not O(page). The held pull repeats the same query every 5 s (spec.md:190). Only the single-alias snapshot fits `changes_scope`. Task 12 and AC-22 must add one of two things. Either (a) the pull is one indexed range per scope, `(shared)`, `(workspace)` and `(project, alias)` for each named alias, merged by `seq` and cut at `limit`. Or (b) the spec states the scan and its bound. Either way, task 12 needs a test that reads `EXPLAIN QUERY PLAN` for the pull, the snapshot and the wait's emptiness check, and fails on a scan of `changes` without an index. It also needs a seeded 100,000-row feed with a sparse alias, asserting the rows read are bounded. The NFR at spec.md:293 says "measured, not pinned", so nothing would fail if the pull degraded.
- R-2 · .crew/work/2026-11-10-001-team-server-wizardingcode-mem-serve-one/spec.md:288 (and spec.md:268, AC-23; plan.md:159, task 7) · The rollback procedure across a schema bump is stated but unsafe and unproven. "Put the upgrade copy in place of `team.db`" does not say to delete `team.db-wal` and `team.db-shm`. The runner sets WAL (`src/store/db.ts:177`, `enableWal`). A stale WAL left beside a replaced main file can corrupt the restored database or replay frames from the newer schema. Two changes. First, the procedure must name the removal of both files, with the server stopped. Second, a criterion and a test must prove it. The test fakes a 1→2 migration list and checks that `openFile` leaves `backups/team-<ms>-v1-<pid>.db`. It then opens with the version-1 list and gets `SchemaTooNewError`, so `serve` exits 3 (AC-23 covers only the exit). It then replaces the file with the copy, removes the WAL and SHM files, and reopens with the version-1 list. Finally it checks that the restore detection renews `server.instance` when `feed.seq` is ahead. Today AC-16 and AC-23 prove only the refusal, never the way back.
- R-3 · .crew/work/2026-11-10-001-team-server-wizardingcode-mem-serve-one/spec.md:192 (and AC-22, spec.md:267) · The restore detection watches only the `changes` sequence, so restoring an older copy goes undetected when only non-feed rows changed since the copy was taken. Such rows are joins, device revocations, disables, role changes and invitations, and the tables involved have no feed row. `fileSeq` equals `dbSeq`, so the instance is not renewed. A revoked device's token then silently works again. Two changes. First, extend the mark to cover the `audit` table's `AUTOINCREMENT` id, since every join and admin act writes an audit row. `feed.seq` would hold both numbers, `checkRestore` would compare both, and the CLI and API writers would update the mark after their audit write. Or second, state the limit in the spec, the ADR and the runbook, with the operator step (`serve instance renew` plus a review of revocations). Add a test in task 12 for either choice: restore a copy taken before a revoke, with no push in between.

## Notes
- The scope holds: the data change is a new `team.db` with its own migration list. Nothing is copied or dropped in a client store (spec.md:57, D-1; plan.md:39 "Delete: nothing"). The first migration needs no down step.
- Checked in `src/store/db.ts`: `migrate`, `backup` and `openDb` do split as plan.md:45 says. `migrate(db, path, dir, migrations, busyTimeoutMs)` already takes the list. `backup` hard-codes the `wizardingcode-mem-` prefix and `BACKUPS_DIR` (lines 70-74), which the plan parameterises. `openDb`'s order is busy_timeout, foreign_keys, synchronous, migrate, then `migrateModules`, then `restrict`. The plan's `openFile` keeps that order and adds only the `before` hook. The "no behaviour change" claim is credible and has tests (task 4, AC-16, AC-27).
- Backups go to the team's own `backups/` folder with the `team` prefix. The pruning at `db.ts:77-81` (it keeps `BACKUPS_KEPT` files) then cannot touch the client's copies. Backups are taken only when the old version is above 0 (`backupVersion`), so rollback copies exist for every bump from 1 up.
- The revision lookups by `(uuid, hash)` are planned: `entry_revisions_hash(uuid, hash)` (plan.md:114), step 9 and `appliedAs` (spec.md:172).
- The tombstones and `current` flag design is sound for the per-key writes. `changes_key(key, seq)` serves "set the older row's `current` to 0" and `markPurged`. `AUTOINCREMENT` keeps `seq` from reusing numbers, and 410 catches a cursor ahead.
- Minor, not a return. `entry_revisions` and `memories` are `WITHOUT ROWID` and hold up to 256 KiB per row. SQLite advises ordinary rowid tables for rows well above about 1/20 of a page, because the primary-key tree carries the whole row. Revisit if the 100,000-row measurement from R-1 shows it.
- Minor, not a return. `purgeItem` deletes `entries` and `entry_revisions` with `foreign_keys = ON` (set in `openFile`). The revisions must be deleted before the entry. Task 13 should name this order.
- The criteria for the restore itself (AC-22: `feed.seq` ahead of `sqlite_sequence`, the instance renewed, a lost file rewritten, the 410) are observable and tested in task 12, apart from the gap in R-3.
