# devops lead's validation of 2026-11-10-001-team-server-wizardingcode-mem-serve-one: spec
verdict: returned
## Returns
- R-1 · .crew/work/2026-11-10-001-team-server-wizardingcode-mem-serve-one/spec.md:208 (and plan.md:189) · The `docker` job lists `download-artifact` of `binaries` into `dist` but no `actions/checkout` and no `context: .` on `build-push-action`. Without them the action builds from its default Git context, which is the repository at the ref. That context has no `dist/` (the downloaded artefacts are not in it), no usable `.dockerignore` result and no `COPY` source, so the build fails or builds the wrong tree. Add `actions/checkout@v7` before the download, `context: .` on the build step, and `file: Dockerfile`. `ci.yml` cannot catch this, because its image step builds locally, so the spec must state it and `deploy-files.test.ts` must assert it. Evidence: `.github/workflows/release.yml:63-68` shows `publish` does the same checkout plus download pair.
- R-2 · .crew/work/2026-11-10-001-team-server-wizardingcode-mem-serve-one/spec.md:208 and :271 (AC-26), plan.md:189 · AC-26 (observed) claims "uid 10001 with a read-only root filesystem and no init of its own", but the CI step as written does a plain `docker run -d --name wcm -v wcm-data:/data …`. It never sets `--read-only --tmpfs /tmp --cap-drop ALL --security-opt no-new-privileges:true`, so the read-only claim is never exercised. A write outside `/data` or `/tmp` (for example Bun's extraction, git, or the mirror child) would only show up in production. Make the CI run use the compose file's flags, and add `docker stop -t 30` to mirror the grace period. Replace the fixed `sleep 3` with a retry loop on `serve health` (up to about 30 s), since a slow runner makes it flaky.
- R-3 · .crew/work/2026-11-10-001-team-server-wizardingcode-mem-serve-one/spec.md:207 · The `caddy` service is listed without `environment`. `{$SERVER_DOMAIN}` in the Caddyfile is read from the Caddy container's environment. Compose's `.env` only interpolates compose values and does not pass them into containers, so the site address would be empty and no certificate would be issued. Add `environment: [SERVER_DOMAIN=${SERVER_DOMAIN:?set SERVER_DOMAIN in .env}]` to `caddy`, and `${WIZARDINGCODE_MEM_VERSION:?}` to the server image reference. Have `deploy-files.test.ts` assert both.
- R-4 · .crew/work/2026-11-10-001-team-server-wizardingcode-mem-serve-one/spec.md:288 · The rollback procedure ("put `backups/team-<time>-v<n>.db` in place of `team.db`") is incomplete and has no compose form. (a) `team.db-wal` and `team.db-shm` must be deleted, or removed with the copy. A stale WAL replayed over an older base file corrupts or confuses the restore. (b) The previous image crash-loops with exit 3 under `restart: unless-stopped`, so the steps must be given in compose form: `docker compose stop server`, then `docker compose run --rm --entrypoint sh server -c 'ls /data/backups; cp … /data/team.db; rm -f /data/team.db-wal /data/team.db-shm'`, then set `WIZARDINGCODE_MEM_VERSION` to the old tag and `docker compose up -d server`. (c) Say that `feed.seq` stays as it is (ahead of the copy), so restore detection renews the instance. The spec delegates the spelling-out to part 7. Put the exact forms in the spec and the ADR (AC-28), and add a test in `team-serve-cli` or a doc check that exercises the copy-plus-start path with WAL files present.
## Notes
- The pipeline as it is today matches the spec's premises. `release.yml:39-58` has `sign` uploading `binaries`, and `publish` at `:60` currently needs only `sign`, so the `needs: [sign, docker]` change is clean. `ci.yml:32-45` `build` runs on `ubuntu-latest` (x64) and uploads `dist/`, so the image step belongs there. `.github/workflows/release.yml:72` restores the executable bit by hand, which supports `COPY --chmod=0755`. `linux-x64` and `linux-arm64` are both built, per `ci.yml:57-58`.
- Dockerfile design holds: user 10001, no init, trust-proxy only in compose, `HEALTHCHECK` through the binary's own probe (default host loopback, port 8787, reachable with `HOST=0.0.0.0`), and `WIZARDINGCODE_HOME=/data/home` on the volume. A named volume copies the ownership of `/data` (chowned to 10001) on first use. `docker compose run --rm server serve mirror --rebuild` works because the entrypoint is the binary. The `serve` lease also guards against a second container on the same volume.
- The metadata-action tags work out. `type=semver,pattern={{version}}` strips the `v`, which matches the `.env.example` form `0.7.0`. `latest` is enabled only for tags without `-`. The lower-case `ghcr.io/wizardingcode-io/…` name is fixed in the workflow, and `docker` has its own `packages: write` against the workflow-level `contents: write`.
- Non-blocking, for the runbook or ADR. (1) CI proves only the amd64 image. The arm64 image first builds, under qemu, on a tag, and the `docker` job pushes before `publish` creates the release. Consider an unpushed two-platform `build-push-action` in `ci.yml`. (2) The volume must be a local Docker volume, not NFS, because SQLite WAL uses shared memory across `exec` and `run` containers. (3) After SIGKILL or OOM the lease stays for up to 30 s, so the restart loop may refuse once or twice before it recovers. Say so in the runbook. (4) The digest pins on `debian` and `caddy` need a renewal habit. (5) Add `443/udp` if HTTP/3 is wanted.
- AC-26 is mostly checkable in CI. The Dockerfile, compose, Caddyfile and workflow text are checked by `deploy-files.test.ts` (plan.md:189). The image behaviour is checked by the CI step once R-2 is fixed. The `docker` job's dependency and permissions are text-asserted only, since they are exercised for real only on a tag. The "package made public" step is a manual runbook step named in the ADR, which is acceptable as stated.
