## Findings
- F-1 · defect · tests/integration/team-push.test.ts:211 · AC-47 says a retry of the same payload is `applied` with revision 1 "when the item is locked by an admin", but the test withdraws and then reinstates (lines 212-227) before any retry, so no retry is ever sent while the lock holds. Reverting the idempotency check to run after the lock check would leave every test green (rubric Q1).
- F-2 · defect · tests/unit/team-contract.test.ts:15 · AC-57 says the contract test "fails when they change without `CONTRACT`", but the test compares `contractFingerprint()` with `CONTRACT_FINGERPRINT`, a constant that lives in `src/team/contract.ts`. Someone can repin that constant without bumping `CONTRACT` and the test still passes (it only checks `CONTRACT` is 1). Also, `RESULT_SHAPES` is a hand-written list that no test checks against what the server actually answers. The pin should be a `{ CONTRACT → fingerprint }` pair written in the test (rubric Q1).
- F-3 · defect · tests/integration/team-mirror.test.ts:508 · AC-49 says the mirror run "renews the lease before every git call" (the clause that replaced AC-35's "after every commit"), but the only assertion is `reads > 3` on the clock. Plus the stolen-lease abort, that would still pass if renewal happened once per commit or once per repository. Nothing ties a renewal to each git call (rubric Q1).
- F-4 · defect · tests/integration/team-mirror.test.ts:546 · AC-49 says the server "forwards its [child's] lines to the log", but every test injects `mirrorChild` (here and in `tests/helpers/team.ts:123`). The real default, `spawnMirror` and `forwardLine` in `src/team/mirror.ts:615-644`, which launches `serve mirror` and forwards its stdout and stderr, runs in no test, so breaking the forwarding or the command it launches fails nothing (rubric Q1).
- F-5 · defect · tests/integration/team-process.test.ts:171 · AC-51 says the logs never contain "a code (after the bootstrap line) or a payload". The test only checks that the token is absent, and that run pushes nothing. No test anywhere checks that the bootstrap code appears only once or that a pushed frontmatter or body stays out of `t.lines` (rubric Q1).
- F-6 · defect · tests/integration/team-process.test.ts:235 · AC-51 says "`serve` and `serve health` skip the legacy data migration", but the seeded legacy home is only exercised by `serve health`. Every `serve` process in this file starts with an empty `HOME`, so if `serve` itself stopped skipping the migration, no test would fail (rubric Q1).
- F-7 · defect · tests/integration/team-auth.test.ts:441 · AC-51 says a server whose lease renewal finds another owner "exits 1 after answering its held pulls". The test checks exit code 1 and the `lease-lost` line, but no pull is held during the renewal, so the "answers held pulls first" part is never exercised (rubric Q1).
- F-8 · defect · tests/integration/team-auth.test.ts:94 · AC-45 says "the token itself [is] nowhere in the database", but the check only reads `group_concat(token_hash) FROM devices`. A token written into `audit.detail`, `meta`, a device label or an invitation row would pass. The positive half (that `token_hash` equals `hashSecret(token)`) is not asserted either (rubric Q1).
- F-9 · defect · tests/unit/deploy-files.test.ts:50 · AC-54's recorded reason is not true for the file half of the criterion. Building the image and running the container on CI legitimately cannot have a red run, but the Dockerfile `pick` stage, the compose `:?` variables, `SERVER_DOMAIN`, Caddy's `max_size`/HSTS, `.env.example` and the release `docker` job are all asserted by `deploy-files.test.ts`. That test could have been run and seen failing before those files were written (rubric Q4).
- F-10 · advisory · tests/unit/team-db.test.ts:109 · AC-44 says `openDb` "closes its handle when a module migration fails". The comment "The handle was closed: the file opens again" claims more than the check shows: SQLite reopens a file whether or not an earlier handle was left open, so this would pass if the close were removed.
- F-11 · advisory · tests/integration/team-push.test.ts:722 · AC-47's storage floor is "under 200 MiB", but the test injects exactly 100 MiB, which is also the health floor. A push guard that reused the 100 MiB floor with `<=` would pass. A value such as 199 MiB, plus one above 200 MiB, would pin the boundary.
- F-12 · advisory · tests/integration/team-push.test.ts:731 · AC-45/AC-47 say "an idempotent retry is not charged". The test only shows the retry is `applied` once the bytes bucket is empty. It does not show that a retry leaves the bucket's level unchanged.
- F-13 · advisory · tests/integration/team-auth.test.ts:237 · AC-46 says "a member calling any invitation or admin route is 403", but only `POST /v1/invitations`, `GET /v1/members` and `GET /v1/audit` are tried as a member. The other admin routes (revoke, disable, enable, role, items withdraw/reinstate, devices, invitations list/revoke) are not covered as a member, except the item withdraw at team-push.test.ts:611.
- F-14 · advisory · tests/integration/team-serve-cli.test.ts:314 · AC-52 names `serve audit --limit 5`, but the test uses `--limit 2`. It also checks "every writer updates `feed.seq` and writes one audit row" only for `invite` (line 78-79): the other writers are checked through `lastAudit`, not through the count or the marks file.
- F-15 · advisory · tests/unit/deploy-files.test.ts:165 · AC-54 says `latest` is tagged "only for a tag without `-`", but the regex accepts any `enable=` expression containing `contains(github.ref_name, '-')`, so an `enable` that tags only prereleases (no `!`) would pass.
- F-16 · advisory · tests/integration/team-pull.test.ts:537 · `expect(newUuid()).toMatch(...)` asserts the test helper's own output, not the server's, and does not belong to the alias test it sits in (rubric Q2).
- F-17 · advisory · tests/unit/team-store-boundary.test.ts:12 · AC-57: `importsOf` only matches `from "…"`, so a dynamic `import("../store/db.ts")` or a `require` in `src/team/` would get past the boundary test.
- F-18 · advisory · tests/integration/team-mirror.test.ts:464 · AC-49 says "no hooks, no signing": the stub's environment dump confirms the global and system config are off and the ceiling is set, but no assertion looks for `core.hooksPath` or `commit.gpgsign=false` (or an equivalent) on the recorded arguments.
