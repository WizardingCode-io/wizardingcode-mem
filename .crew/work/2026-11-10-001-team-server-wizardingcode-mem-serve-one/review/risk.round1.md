# risk findings for 2026-11-10-001-team-server-wizardingcode-mem-serve-one
reviewer: review-risk
read: spec, plan, 9 files

## Findings
- F-1 · defect · src/team/mirror.ts:626 · In production the server never exports anything to the mirror. The server starts its hourly and quiet-minute child as `serve mirror --data <dir>`, but the `mirror` subcommand accepts only `--rebuild` (src/cli/commands/serve.ts:479 calls `parseFlags(argv, { rebuild: "flag" })`, and plan.md:112 lists only `--rebuild`), so every child exits 64 on "unknown flag --data". Because of that, `meta.mirror.last` is never written, `serve status` shows no run and no error while its pending count only grows, and the one trace is a `mirror-exit` warn line per attempt. Every test swaps in its own `mirrorChild` (src/team/server.ts:116), so nothing ever ran the real child. Nothing is lost, since the database is the authority, but D-26's export and its promise that "a failed run is recorded in meta for serve status" both fail without anyone seeing it.
- F-2 · defect · src/team/mirror.ts:552 · `serve purge entry` commits its erasure transaction first: it deletes the row and its revisions, marks the feed rows as purged and records the key in `purged`. Only after that does `replayFolders` (mirror.ts:606) take `mirror.lease`. If a mirror run holds the lease (for example a `--rebuild`, which the spec puts at about 35 minutes), `holdLease` throws `LeaseHeldError` and the CLI prints "a mirror run is in progress" and exits 1. At that point nothing undoes or completes the purge: the erasure has already committed, so no audit row is written (serve.ts:510-513 is skipped), the list of repositories to rebuild is thrown away, and a second `purge` answers "unknown". A rebuild already running may also have loaded the purged revisions before the delete and write them into the new history. The result is an irreversible deletion whose audit trail is missing and whose text can stay in the mirror, behind a message that says nothing happened. Fix: check the lease before the transaction, or write the audit row and the pending rebuild before the replay.
- F-3 · advisory · .github/workflows/release.yml:99 · `publish` now waits on `docker`, so every client release (the binaries the plugins fetch) depends on a QEMU arm64 build and a push to ghcr.io. CI never runs either one: it builds a single architecture and pushes nothing (ci.yml:32). The first time they run is the first tag, and any failure there blocks the whole release. The failure is visible as a red job and is undone by re-running the job or dropping `docker` from `needs`. Plugin marketplace bumps should wait until the release is out.
- F-4 · advisory · src/team/server.ts:81 · `openTeamDb` migrates `team.db` before `holdLease` (server.ts:89) checks for a running server. If a newer image is started beside a live older server (`docker compose run --rm server` with a bumped tag, or a restart inside the 30-second window after a tag change), it migrates the database under the running process and only then exits on the lease. The spec's guard ("never migrate while the serve lease is fresh", spec.md:132) covers the subcommands only. This cannot bite at team schema 1, but it will at the first schema bump.
- F-5 · advisory · .env.example:4 · `WIZARDINGCODE_MEM_VERSION=0.7.0` while package.json is at 0.6.0. If the release carrying this change gets any other tag, a copied `.env` points at an image that does not exist. The failure is visible at `docker compose pull`.
- F-6 · advisory · .crew/work/2026-11-10-001-team-server-wizardingcode-mem-serve-one/spec.md:350 · The rollback across a schema bump is manual, and it restores the copy taken before the migration. Members, devices and pushes written since the upgrade are lost on the server, and the spec relies on part 6 clients to re-push what the copy lacks, but part 6 is not built. The procedure is written down (ADR 0026 "Rollback"), so this is advisory.
- F-7 · advisory · .crew/work/2026-11-10-001-team-server-wizardingcode-mem-serve-one/spec.md:251 · The HEALTHCHECK has no consumer: nothing restarts the container or alerts on it. So the 503 at low disk, and in general an unhealthy server, is visible only to someone who runs `docker ps` or `serve status`. The spec says so, but an alert or the runbook's monitoring would make the first hour safer.
