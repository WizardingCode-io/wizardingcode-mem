# data findings for 2026-11-10-001-team-server-wizardingcode-mem-serve-one
reviewer: review-data
read: 16 files, the schema and migrations read (src/team/migrations/0001_team_init.sql, src/team/db.ts, the runner split in src/store/db.ts, docs/adr/0026-team-server.md), risk areas: data-migration, personal-data

## Findings
- F-1 · defect · src/team/mirror.ts:605 · A purge commits its erasure transaction first and then calls `replayFolders`, which takes `mirror.lease` through `holdLease` and throws `LeaseHeldError` while the hourly or after-push mirror child holds it (`serve purge` runs beside a live server, and `openTeamForWrite` checks only the schema). The purged entry's text then stays in the `repos/` git history. Nothing durable records that a replay is owed: the revisions are gone, so no later mirror run touches those folders, and a second `serve purge` answers 404 `unknown`. A mirror child that loaded its pending revisions before the purge can also commit them afterwards. This breaks D-24 ("covering … the mirror's files", "must not come back from a copy") and answers rubric question 5 (erasure as the project states it). Only `serve mirror --rebuild` recovers, and nothing says to run it.
- F-2 · defect · src/team/migrations/0001_team_init.sql:66 · `audit.address` stores the source IP address of joins, failed joins included. Neither the spec nor ADR 0026 states its retention or erasure: Follow-ups and Risks only name the table's growth, and no prune or purge path reaches `audit`. Rubric question 5 asks for exactly this: personal data in a new column without its retention.
- F-3 · advisory · src/cli/commands/serve.ts:510 · The `purged` audit row is written in its own statement after `purgeItem` returns, so it is outside the erasure transaction and after the replay. When the replay throws (F-1), an erasure that has already committed has no audit row and `feed.seq` is not rewritten, against D-24's "audited". The audit insert belongs inside the transaction at mirror.ts:552 (rubric question 3).
- F-4 · advisory · src/team/store.ts:838 · `markPurged` uses `key = ? OR substr(key, 1, length(?)+1) = ? || '@'`. The OR and the `substr` keep the planner off `changes_key`, so every purge scans the whole `changes` table, which only grows (no pruning, D-25) and has 100,000 rows in the test, and holds the write lock while it does. A range (`key = ? OR (key > ?||'@' AND key < ?||'A')`) would use the index (rubric question 2).
- F-5 · advisory · src/team/push.ts:367 · A memory's key is `<device id>:<uid>` and the server accepts any string as the uid (validate.ts:105). Its move tombstone uses the key `<key>@<revision>`, which can equal another memory's key on the same device (a uid such as `abc@3`). In that case `insertChange` retires that memory's current feed row, and `markPurged`'s prefix match (store.ts:838) rewrites its rows as `purge`. Honest clients send `<generation>:<id>`, so only a device's own items are exposed. Refusing `@` in a memory uid, or using a separator a uid cannot hold, closes it (rubric question 4).
- F-6 · advisory · src/team/feed.ts:151 · `pull` reads the page with `changesSince` and then each row's payload with `revisionAt` or `memoryByKey`, one statement at a time and outside any read transaction. A CLI withdraw or purge from another process can land between the two reads and produce an `upsert` item with a hash but no payload. Wrapping the page in one deferred read transaction gives it one snapshot. The per-row lookups (up to 500 primary-key reads a page) are an N+1 that a join on `entry_revisions` and `memories` would avoid (rubric questions 2 and 3).
- F-7 · advisory · src/team/store.ts:800 · `feedSql` adds one `UNION ALL` range for every alias in `projects`, which `parsePullQuery` (feed.ts:74) neither deduplicates nor caps. An alias named twice returns every one of its rows twice on the page, and more than about 498 aliases exceeds SQLite's compound-select limit, so the pull fails with an internal error instead of a 400 (rubric question 2).
- F-8 · advisory · src/team/store.ts:546 · `workspaceEntriesOf` filters `entries` on `scope` and `created_by_member`, and no index covers them. Disabling a member therefore scans the whole entries table inside its write transaction (push.ts:559). The path is a rare admin act, not a list path (rubric question 2).
- F-9 · advisory · src/team/store.ts:584 · `allRevisions` orders `entry_revisions` by `seq`, which has no index, and loads every revision's frontmatter and body into memory at once with `.all()`. The purge replay (mirror.ts:478) and `pendingRevisions` after `--rebuild` (mirror.ts:356, one `revisionsOf` per entry) therefore hold the whole history in memory, which at the ADR's 20,000 revisions can be large. Iterating the rows or reading them in batches avoids that (rubric question 6).
- F-10 · advisory · src/team/mirror.ts:409 · `--rebuild` removes `repos/` and then resets `mirror_revision` in a separate step. A crash between the two leaves every revision marked as exported with no repositories, and later normal runs export nothing until `--rebuild` is run again. Resetting first, or recording the rebuild in `meta`, keeps the state recoverable (rubric question 1).
- F-11 · advisory · src/store/db.ts:80 · The split runner now gives each file a prefix, but the pruning step still keeps the two newest `.db` files of the whole folder, whatever their prefix. Sorting by name is also no longer sorting by age, as the comment on line 76 claims. A team data directory that shares its `backups/` with a client store (`serve --data <store dir>`) would delete the `team-…` copy it has just written, because `team-` sorts before `wizardingcode-mem-`. The default `<data dir>/team` keeps the two apart (rubric question 1).
- F-12 · advisory · src/team/db.ts:87 · A purge deletes rows without `PRAGMA secure_delete`. The erased text stays in free pages of `team.db` and its WAL until they are reused, and it stays in every upgrade copy in `backups/`. ADR 0026's rollback procedure restores from those copies, and a copy taken before the purge has no `purged` row, so a later re-send is accepted again. The gap is latent while TEAM_LATEST is 1 and no upgrade copy exists yet (rubric question 5).
- F-13 · advisory · src/team/instance.ts:54 · `renewInstance` writes the new instance, the sequence advance and the audit row in three separate transactions. A crash between them leaves a new instance without the 1,000,000 margin, or without its audit row. The next start detects the file still ahead and renews again, so this heals itself. One transaction would make the step atomic (rubric question 3).
