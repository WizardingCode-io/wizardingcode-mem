## Findings
- F-1 · defect · src/team/mirror.ts:653 · `setMeta(db, REPLAY_MARK, JSON.stringify([...touched]))` replaces any replay an earlier purge still owes instead of merging with it, and `purgeItem` never runs `owedReplay` first. Take this sequence: purge A commits its erasure, then dies or is interrupted before `replayFolders` removes its folders at line 501. That can happen during the up-to-5 s checkpoint wait at line 664, or when `rmSync` throws. Purge B then runs before any mirror run. B overwrites A's note with its own folders, replays them and clears the mark (line 553). A's folders keep the purged text in their git history under `repos/`, and nothing records the debt any more. This is the crash window round 2's F-1 asked to close, reopened by a second purge (rubric questions 1 and 5: erased personal data left with no record). Merging with the existing note, or replaying the owed folders before erasing, closes it.
- F-2 · advisory · src/team/store.ts:580 · The pending query is correct under concurrent writes. `entry_revisions.seq` comes from `changes.seq` AUTOINCREMENT, which is unique and assigned in commit order under SQLite's single writer, so `seq > ?` neither skips nor repeats a row between batches. Purge, the only deleter, is held off by the mirror lease. Its memory is now bounded: the LIMIT keeps the sorter at 200 rows. The plan, though, is the `entries_pending` partial index as the outer loop, a primary-key range on `(uuid, revision)`, then a temp B-tree for `ORDER BY r.seq`. Every batch therefore reads and sorts every pending revision, frontmatter and body included. After `--rebuild` (line 433), when the whole history is pending, the export reads about P²/200 rows instead of P. This is a slower query with an index present (rubric questions 2 and 6). Driving from `entry_revisions_seq` when the pending set is large, or starting `after` at the smallest pending seq, would keep each batch at its own size.
- F-3 · advisory · src/team/mirror.ts:681 · `wal` is "truncated" only when both checkpoints succeed. Either successful TRUNCATE checkpoint copies every frame into the file and cuts the log, the purged frames included. So a busy first checkpoint followed by a truncated second, or the reverse, reports `busy` although the purged frames are gone. The report errs on the safe side but is wrong. `first || second` is the fact to report (rubric question 5).
- F-4 · advisory · docs/adr/0026-team-server.md:78 · "in which case the next checkpoint cuts it" is not true of the server's own checkpoints. Nothing sets `journal_size_limit`, and the automatic checkpoint is PASSIVE. It lets the log restart from its head but does not shrink the file, so after a `busy` purge the original frames past whatever is rewritten can stay on disk. Only another TRUNCATE checkpoint removes them, and in this change only a purge runs one. Either state that the operator re-runs a purge-time checkpoint, or set `journal_size_limit` on writer connections (rubric question 5).
- F-5 · advisory · src/team/store.ts:633 · The TRUNCATE checkpoint takes the WAL writer lock and holds it while it waits, up to the purge connection's `busy_timeout` (5 s by default, src/team/db.ts:91), for readers to finish. It does this twice per purge. The server's pushes are blocked for that time, but its readers are short: pull's `readTransaction` (feed.ts:147) does not span the wait (feed.ts:207). The stall is therefore bounded and only on the operator's command. It is worth one sentence in the ADR's Purge section (rubric question 6).

## Round 2
- F-1 (no durable record of an owed replay): mostly answered. `mirror.replay` is written inside the erasure transaction (mirror.ts:653), cleared only after a whole replay (mirror.ts:553), finished by the next run before any export (mirror.ts:437-438), and cleared by `--rebuild` (mirror.ts:434). The test at team-mirror.test.ts:615 proves the failure path. The remaining hole, a second purge overwriting the note, is F-1 above.
- F-2 (WAL frames outlive `secure_delete`): answered. `checkpointWal` runs after the transaction (mirror.ts:664) and again after the lease is released (mirror.ts:681), the test checks that the `-wal` file is 0 bytes (team-mirror.test.ts:408), and the ADR now states what `secure_delete` covers. What remains: the reported result (F-3), the "next checkpoint" claim (F-4) and the writer stall (F-5).
- F-3 (`forEachRevision` pins one snapshot): answered. Batches of 200 by `seq` use `entry_revisions_seq` (store.ts:613-627), and `.all()` leaves no open statement across the git calls, so no read snapshot survives between batches. The walk is correct while the server writes, because seq is unique and monotonic. The cached `mirrorRevision` per uuid (mirror.ts:503-512) is safe under the lease, and a new entry is at 0 and is skipped.
- F-4 (`--rebuild` loads the history): answered for memory. `pendingRevisions` is a generator over `pendingRevisionsAfter` (mirror.ts:355-365), and `entriesPendingMirror` and `allRevisions` are gone. The new query's cost per batch is F-2 above.
- F-5 (a member's name has no stated erasure): answered. ADR 0026 line 94 states where the name lives and that it is erased by the operator with a shell plus `serve mirror --rebuild`, and line 114 names `serve forget <member id>` as a follow-up.
