## Findings
- F-1 · defect · src/team/mirror.ts:626 (with src/cli/commands/serve.ts:479) · The Design (D-26, "The mirror") says the server runs `serve mirror` as a child process, using its own command line through `selfCommand` and passing the data directory. `spawnMirror` launches `selfCommand("serve", "mirror", "--data", dataDir)`. But the `mirror` subcommand parses its arguments with `parseFlags(argv, { rebuild: "flag" })`, so `--data` is an `unknown flag` and the child exits 64. The parent only logs that as a `mirror-exit` warn. None of the subcommands reads `--data` at all: `run()` takes the directory from `resolveTeamDir(process.env)` only, even though the USAGE text says "The data directory is --data, WIZARDINGCODE_MEM_TEAM_DATA, or <data dir>/team". As a result, the hourly and after-push export the Design puts in a child process never runs from a live server. Even if the flag were dropped, a server started with `--data <dir>` would point its child at a different directory. The tests miss this because `startTeamServer` takes an injected `mirrorChild` (server.ts:116) and nothing calls `spawnMirror`. This is the contract between the server and its own child, built differently from the way the subcommand reads it (rubric questions 3 and 5). Fix: make the subcommands accept `--data` (the plan's table already gives it to `serve`) and resolve `shell.dir` from it before the environment. Add a test that runs the real `spawnMirror` command line, or one that runs `serve mirror --data <dir>` through `runCliWith`/`spawnCli` and expects exit 0.
- F-2 · advisory · src/team/db.ts:58 · The ADR and the CLAUDE.md bullet say every SQL statement lives in `store.ts` and `db.ts` is "the schema and the three opens". But `db.ts` also holds runtime reads that are not part of opening: `teamSchemaVersion` (`PRAGMA user_version`), which `status.ts` calls, and the `requireTeamSchema` queries. A second engine would have to reimplement `db.ts` as well. Either move `teamSchemaVersion` behind `store.ts`, or have the ADR's boundary sentence name the reads `db.ts` keeps.
- F-3 · advisory · src/team/push.ts:8 · `push.ts` and `feed.ts` (feed.ts:7) import `Context`, `Limits` and `Meta` from `routes.ts`, the HTTP edge, while `routes.ts` imports them. The domain modules depend on the route layer's types, which reverses the direction the rest of `src/team/` follows (the edge calls the domain). Move those types to a leaf such as `src/team/types.ts`.
- F-4 · advisory · src/team/mirror.ts:153 · The mirror's git calls pass `operation: "mirror"` to part 1's `runGit`. On failure the runner logs them under the scope `knowledge.mirror` (repo.ts `logError(\`knowledge.${options.operation}\`…)`), so the team server's log names its failures as the knowledge module's. Let the `GitHost` carry a log prefix, or name the operation so the scope reads correctly.
- F-5 · advisory · src/store/db.ts:172 · `migrateFile` (and `migrateModules` at db.ts:275) are now exported, but nothing outside `db.ts` calls them. The split the Design asks for is `openFile` and `openExistingFile`, so these two exports widen the core store's surface without a consumer. Keep them module-private.
