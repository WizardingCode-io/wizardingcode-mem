## Findings
- F-1 · advisory · src/team/server.ts:217 · The hourly `checkpointWal(db)` runs synchronously on the server's only connection, on its event loop. While another process holds a read (an operator's `serve status`/`audit`, a hand-run `serve mirror`, a `sqlite3` shell), the TRUNCATE checkpoint waits up to the 5 s busy timeout. During that wait it blocks every request, not only writers: `health`, pulls and the wake-up of held pulls. ADR 0026:78 only says "holds the server's writers", and only for purges. The stall is bounded, and with no outside reader the checkpoint costs no more than copying the WAL frames written since the last automatic checkpoint. Worth one sentence in the ADR (rubric question 6: availability).
- F-2 · advisory · src/team/server.ts:217 · The hourly callback does not guard the checkpoint, and server.ts installs no uncaught-exception handler. A checkpoint that throws (SQLITE_FULL or an I/O error while it writes frames into the file) escapes the timer and can end the process. It also skips `mirror.hourly()` for that tick. Note that a busy log returns `busy=1` and does not throw. A try/log around the call, as `stop` already does for the lease release, keeps a housekeeping step from taking the server down (rubric question 6).

## Round 3
- F-1, defect (a second purge overwrote the owed-replay note): fixed. `noteOwed` (mirror.ts:396-407) reads the earlier note and merges this purge's folders into it. The union is written inside the erasure transaction (mirror.ts:682-696), which takes the write lock up front, so the read-modify-write is atomic against other writers. `purgeItem` then replays every owed folder (mirror.ts:699), including for a memory purge that touched no folder. The note is cleared only when no failure was added (mirror.ts:587), so if part of a combined replay fails, the whole union stays owed. That is extra work but correct. An unreadable note sets `mirror.rebuild` in the same transaction (mirror.ts:402), and `replayOwed` clearing the note does not clear that mark. The next run therefore rebuilds (mirror.ts:465), and the test at team-mirror.test.ts:699 proves the run side. The test at team-mirror.test.ts:662 proves the merge: the first purge's failed `shared` replay is finished by a second purge in another folder, and neither repository's history keeps its purged uuid.
- F-2, advisory (pending query cost): answered.
  - Query: `PENDING_SQL` (store.ts:586-589) now selects only `seq, uuid, revision, creator`. With `ORDER BY r.seq LIMIT 200`, SQLite's bounded sorter holds 200 small key tuples.
  - Per-batch scan: each batch still walks every remaining pending revision. The outer loop is the entries through `entries_pending`, the inner loop the `(uuid, revision)` primary-key range, with a lookup into the table row for `seq`. `seq` sits ahead of `frontmatter` and `body` in the record, so no overflow page of the texts is read for the sort.
  - Cost after `--rebuild`: `setMirrorRevision` runs after each applied revision, and `r.revision > e.mirror_revision` drops exported rows. The work therefore shrinks batch by batch, about P²/400 index probes in total. At the ADR's 20,000 revisions that is about 1M probes, a few seconds against roughly 35 minutes of git spawns.
  - Per-row fetch: `revisionAt` (store.ts:552) is one primary-key point lookup per revision, plus one for `previous`. That is O(P log P) and reads each text once, only when it is reached.
  - Memory: no batch and no sort holds text.
  - Remaining cost: the quadratic probing is a slower query with an index present, now negligible next to the git work.
- F-3, advisory (`wal` report): answered. mirror.ts:717 reports `truncated` when either cut succeeded. `checkpointWal(db)` sits on the left of `||`, so the second checkpoint always runs.
- F-4, advisory (the "next checkpoint" claim): answered. server.ts:217 runs a TRUNCATE checkpoint at each hourly tick while `mirror.child()` is null. ADR 0026:78 now names that checkpoint, and any later purge, as what cuts a log left `busy`. When no reader is present at the tick, this does remove the purged frames. Its effect on the running server is F-1 and F-2 above.
- F-5, advisory (writer stall): answered. ADR 0026:78 states the wait up to the 5 s busy timeout, twice per purge, and that it holds the server's writers. For a purge, which runs in the operator's own process, that description is accurate.
