## Findings
- F-1 · Major · spec.md, Goals and "Cost and time" (8 to 10 hours, ten phases) · The brief asks for six things: join, device tokens, invitations, admin and member roles, push and pull with a stale refusal, and an image with compose. The spec adds about a dozen more mechanisms on top: two-phase token rotation (`previous_hash`/`previous_until`), admin lock and reinstate-to-revision, `purge`, `repair`, a per-device daily quota, a per-member byte quota (`member_bytes`), a 507 free-disk check, a 503 health check on disk space, hourly feed pruning with a horizon and 410, a weekly `git gc`, restore detection through a high-water file, a contract header with an N-1 window, an async git queue with backoff, and the `mirror_files` slug-collision table. The pilots are one small team, and part 6, the only client, has not been written. A reader would build all of this in one session, and the budget would not hold: the spec measures it against the viewer, which "took about a day" for routes with no queue and no git. The overrun rule only pushes the image out, not the speculative parts. Simpler: the first slice is join, auth, invitations, revoke, push with stale and idempotency, pull with a cursor and wait, and the image. Rotation, quotas, purge, reinstate, pruning and horizon, and restore detection become named follow-ups once part 6 runs against a real team.
- F-2 · Major · spec.md, "The mirror (D-10)" and `serve repair` · The mirror is never read ("the sync never reads the mirror"). It exists only to satisfy the mission's phrase "repositories on volumes". It costs a queue, a `mirror_revision` column, a `mirror_files` table, crash recovery from commit trailers, retry backoff, a new `runGitAsync` twin of `runGit`, a committer split in `gitEnv`, `safe.directory`, `gc`, and history rewriting in `purge`. Yet `serve repair` already rebuilds every repository from `entry_revisions`, one commit per revision. So the readable history can come from an on-demand `serve export <dir>`, which is `repair` pointed at a folder, with no live queue. Purge then only has to delete rows, not rewrite git history. Two things to settle with the person: whether the mission's phrase is met by repositories written on demand, and whether the high-water file (`repos/.feed`) has to live in the mirror at all.
- F-3 · Major · spec.md, the `serve backup` subcommand, the Non-Goals line "beyond `serve backup`", and AC-9 · concepts_brief.md drops `serve backup` ("`serve backup` is dropped", and it is listed under Alternatives rejected). The spec brings it back without a D-number that records the reversal. It also re-implements `src/backup/backup.ts`, which already does `VACUUM INTO`, gzip, a lease, and a checked restore (`inspect` before putting the copy in place). Either drop it as the brief decided, or reuse that module with a target file name. In the second case, a restore command built on its restore path can renew `server.instance` itself, and that makes the high-water restore detection (F-4) unnecessary.
- F-4 · Minor · spec.md, "Restore detection" and D-13 · The high-water file only catches a restore of the database alone. That is exactly the case an operator controls through the runbook. A restore of the whole volume defeats it, and still needs `serve instance renew` "in bold". The file is also written by the mirror queue, so the restore signal depends on git keeping up. Renewing the instance inside the one restore path the product ships covers the same ground with less machinery.
- F-5 · Blocker · spec.md, the source list and Push step 2 ("part 1's `fileHash`") · There is no `fileHash` in the code. Part 1's content hash is `hashOf(bytes)` in `src/modules/knowledge/repo.ts:341`, the first 16 hex characters of SHA-256. A builder looking for the named function will not find it, and might write a second hash that disagrees with the client's ledger. Name `hashOf`.
- F-6 · Major · spec.md, The mirror ("Part 1's runner is used with its root given … `runGitAsync`, a twin of `runGit`") · `runGit` and `gitEnv` take a `KnowledgeStore`, not a root. They call `store.renew()` (a lease), take `GIT_CEILING_DIRECTORIES` from `knowledgeRoot(store.dataDir)`, and log through the store's data directory (`src/modules/knowledge/repo.ts:374-469`). The spec presents "takes its root as a parameter" as a small seam, but it is a refactor of part 1's store abstraction. On top of that, a twin async runner duplicates the isolation rules (the `configArgs` list), and the two copies will drift. If the mirror stays, factor out one runner that is shared, with a sync and an async entry point. If F-2 is taken, the synchronous runner in a CLI subcommand is enough and no twin is needed.
- F-7 · Minor · spec.md, "One instance" (`serve.lock` with `O_EXCL` and a pid check) · The repository already has two answers to this: leases in `src/store/meta.ts` (`claimLease`, `leaseActive`, `releaseLease`) and the viewer's exclusive pid state file (`src/ui/state.ts`). A third locking mechanism is not needed. A lease in `team.db`'s `meta` table, or the viewer's pattern, does the same job.
- F-8 · Minor · spec.md, D-18 and the Authentication paragraph (`X-WCM-Contract`, "from the next bump on, the one before it") · The API is already versioned by its `/v1/` prefix. A second version axis, with a promise to accept N-1, is a compatibility policy for clients that do not exist yet. `contract: 1` in `/v1/me` and the join answer is enough until a second contract is real.
- F-9 · Minor · spec.md, D-15 and Push step 7 (the 20,000-a-day quota, 1 GiB per member, 507 under 1 GiB free) · The spec stacks three accounting layers (the in-memory token bucket, the daily quota table, the per-member byte table) plus two disk thresholds, and no load or abuse has been measured. For a single-team pilot, the body cap, the per-push item cap and the per-device rate limit already bound the damage. The quota tables are speculative and add one write to every applied item.
- F-10 · Minor · spec.md, Rotation (D-14) · The two-phase rotation, with a grace window and `previous_hash`, is built so that a client can rotate without a gap. Part 6 does not exist, and revoking a device plus a device invitation already covers a leaked token. Defer it, or make rotation single-phase.
- F-11 · Minor · spec.md, "One store boundary (D-1)" and AC-14 · The boundary itself is the person's answer. The test that scans `src/team/` with a regex for template strings starting with an SQL keyword enforces that boundary for a Postgres that "this part ships SQLite alone" will not have. It is brittle (any log message or error text that begins with SELECT, UPDATE, etc. fails it) and adds little over code review. Keep `store.ts` and drop the regex test, or narrow it to imports of `db.ts`.
- F-12 · Nit · spec.md, Design (the full DDL, every env variable, the Dockerfile line by line, the Caddyfile contents, the release job steps, exact log strings) · This is plan altitude, not spec altitude, and `plan.md` exists for it. The spec should state the data model's entities and invariants, the API contract and the deployment shape. The column lists, pinned `apt-get` flags and workflow action names can move to the plan, where they can change without a spec revision.
- F-13 · Nit · spec.md, Push step 4 and memory send (`findSecrets` on the server, justified as "one old client must not leak") · There are no old clients: contract 1 is the first. The check reuses `findSecrets` (`src/core/redact.ts:212`) cheaply, so the cost is low, but the reason given is speculative. Say that it is defence in depth, not compatibility.
