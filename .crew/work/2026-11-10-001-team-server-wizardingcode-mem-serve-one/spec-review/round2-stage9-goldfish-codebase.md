## Findings
- F-1 · Major · Tasks 5 and 13 (knowledge-git-host and team-mirror test cases); Scope "Modify" · The tests rely on `stubGit` to show git's arguments: "a host's `extraConfig` is passed after the runner's own `-c` arguments", and "`stubGit({ dumpEnvTo })` shows … `--template=` on init and the `-c safe.directory=*` argument after the runner's own". In `tests/helpers/stub-git.ts`, `StubBehaviour` has no way to record arguments. `dumpEnvTo` writes `env` only, so no argument can be checked through it. The helper is also not listed under Modify. As written, the implementer either cannot write these assertions or edits a shared helper the plan never names. The plan must add an argument-recording option to `stub-git.ts` (and list the file as Modify), or say how the arguments are captured. Separately, every call in the plan is written `stubGit({ … })`, but the real signature is `stubGit(dir: string, behaviour: StubBehaviour): string`, which returns the folder to put first on `PATH`.
- F-2 · Major · Signatures, `src/store/db.ts` (`openDb` "becomes `openFile(...)` followed by `migrateModules(...)`, so its behaviour … unchanged") · In today's `openDb`, `migrateModules` runs inside the same try/catch as `migrate`, so the handle is closed and the error rethrown. `restrict(…, 0o600)` on the three files also runs after both migrations. In the plan's version, `openFile` closes on its own errors and restricts before returning, and `migrateModules` then runs outside it. Built as written, a failed module migration leaks an open handle, and the files are restricted before the module migrations instead of after. The plan must say that `openDb` closes the handle and rethrows when `migrateModules` fails, and where `restrict` runs, if it wants behaviour unchanged.
- F-3 · Major · Signatures, `src/store/db.ts` (`openExistingFile(dir, file, options?: { before?; latest? })`; "`openExisting` calls it with `DB_FILE`") · Today `openExisting(dataDir, { allowNewer })` checks the version against `LATEST_VERSION` unless `allowNewer` is true, and `src/cli/commands/history.ts:97` calls it with `allowNewer: true`. The plan does not say what an absent `latest` means (no check, or some default). It also does not say how `allowNewer` maps onto `latest`, or that `openExisting` keeps its `busy_timeout = 2000`. An implementer could make `latest` default to `LATEST_VERSION`, or drop `allowNewer`, and either one breaks `history`'s probe. The plan must state that an absent `latest` means no check, and that `openExisting` passes `latest: allowNewer ? undefined : LATEST_VERSION`.
- F-4 · Major · Signatures, `src/team/store.ts` `advanceSequence(db, table, to)` / `sequenceHighWater` and `src/team/instance.ts` `checkRestore` · `sqlite_sequence` holds a row for `changes` or `audit` only after that table's first AUTOINCREMENT insert. On a fresh or empty `team.db`, both functions meet a missing row. Example: `feed.seq` survives while `team.db` is replaced by a new one, the case `checkRestore` exists for. The plan does not say that `sequenceHighWater` reads 0 when the row is missing, or that `advanceSequence` must insert the row when it is absent (an `UPDATE sqlite_sequence` silently changes nothing). An implementer who writes the obvious UPDATE leaves the sequence at 1 and loses the 1,000,000 margin that D-13 requires.
- F-5 · Major · Signatures, `src/team/routes.ts` `handle` ("refuses a `Content-Length` above `limits.bodyBytes` with 413") with `Bun.serve({ maxRequestBodySize: 2_097_152 })` · Only the header is checked. A chunked request has no `Content-Length`, so a body between 1 MiB and 2 MiB reaches `jsonObject`. That breaks the published `LIMITS.bodyBytes` whenever the server is reached without Caddy (in-process tests, or a deployment without the proxy). The plan must say whether the bytes actually read are also capped at `bodyBytes` (and how), or state that the 2 MiB `maxRequestBodySize` is the only bound for a body without the header.
- F-6 · Nit · Scope "Create" lists `src/team/instance.ts` under (D); task 7 (B) creates it with `checkRestore` · Task 7 asserts that `checkRestore` "renews the instance, advances the sequence and rewrites the file". That needs `renewInstance`, `readHighWater`, `writeHighWater` and `currentMarks` in Phase B. Tasks 9 and 11 also write and read `feed.seq` through `onWrite`. Yet task 12 (D) says "grow `src/team/instance.ts` (`renewInstance`, `writeHighWater` after every write)". The phase given for the file and for these functions should match where they are first needed.
- F-7 · Nit · Signatures, `src/cli/main.ts` ("the legacy block runs only when `!SKIPS_LEGACY.has(name)`") · In `main.ts` the takeover is two steps: `applyLegacyEnv(process.env)`, which renames `SHIBAOX_*` variables in place, and the `migrateLegacyData()` block that `WIZARDINGCODE_MEM_MIGRATE` controls. The plan should name which of the two `serve` skips.
- F-8 · Nit · Opening paragraph and Phase 0, the part 1 and part 4 imports · `remoteAliasOf` (`src/core/project.ts`), `entryUid`, `memoryUid` and `MEMORY_HASH_FIELDS` are listed as imported and checked in Phase 0. No step, signature or test of the plan uses them, except `MEMORY_HASH_FIELDS` indirectly through `memoryHash`. Either name their use or drop them from the import list.
- F-9 · Nit · Signatures, `src/modules/knowledge/repo.ts` (`commitPaths(…, committer?: Identity)` and `gitEnv(host, { …; committer? })`) · `commitPaths` reaches `gitEnv` through `runGit`'s `GitOptions` (repo.ts:362), and that type has no `committer` today. The plan should say that `GitOptions` gains `committer`. It should also say that `mirror.ts` `memberIdentity` uses the email form `<member id>@members.wizardingcode.invalid`, which the spec gives and the plan's signature leaves out.
