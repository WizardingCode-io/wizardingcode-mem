## Findings
- F-1 · Blocker · spec.md, Push, steps 8 and 9 vs Critical User Journey 3 and AC-4 · The stale check (step 8) runs before the idempotency check (step 9). Take the retry in Journey 3: the second device resends with `baseRevision` 1 after its push already applied as revision 2. Step 8 sees base 1 ≠ current 2 and answers `stale`, so step 9 never runs. Journey 3 and AC-4 expect `applied` with revision 2 and no change. Someone who builds the steps in the order written fails the acceptance test, and someone who builds to the test has broken the written order. On top of that, step 8 attaches `appliedAs` only for "an earlier revision", so it is unclear whether the current revision counts.
- F-2 · Major · spec.md, Push, steps 6 and 7 and the 507 check · The checks for the admin lock, the quota and free disk all run before the idempotency check. So a retry of an item that already applied gets `refused quota` once the device reaches 20,000 for the day or the member reaches 1 GiB, and gets 507 when the disk is low. The client then believes an applied item failed and keeps retrying. The spec's shutdown claim ("a client whose push was cut retries, and every applied item answers `applied` by the idempotency rule") is false under quota or disk pressure.
- F-3 · Major · spec.md, Push step 7 and step 10; memory send; `member_bytes` table · `member_bytes` only grows. Step 10 and the memory send add the payload bytes on every apply, including when a memory's own row is replaced in place. Nothing subtracts on withdraw, purge, a memory replacement or member disable, and there is no admin route or CLI command to reset it. A member whose agent keeps rewriting memories or a large entry drifts to 1 GiB of "bytes" the server does not actually hold. After that they are `refused quota` permanently, and nobody can fix it.
- F-4 · Major · spec.md, The team database ("its single connection serialises writes"); Pull; NFR Latency · bun:sqlite is synchronous, and every request, the pruning, the long-poll wakeups and the mirror bookkeeping share one connection on one event loop. A `since=0` pull has to compute "the newest `changes` row per uid" across the whole feed, join each row to its payload (entries and revisions, or memories) and serialise up to 2 MiB of JSON. That work blocks pushes, held pulls and the health probe while it runs. A full pull in 500-item pages repeats an O(N) group-by on every page, so the total cost is roughly O(N²/500). The NFR's figures (200 items under 2 s, 500 rows under 500 ms) are tied to no data size, and the "load the limits keep far below SQLite's" claim (Alternatives, Postgres) is unbacked: every limit is per device, and none is per server.
- F-5 · Major · spec.md, whole document · There is no sizing anywhere: no expected member or device count, no number of entries or memories per project, no peak pushes or pulls per minute, no disk budget. D-15's change from 5,000 to 20,000 items a day "so a first sync of a large store takes days" implies stores of 100k+ items. Each such store, fanned out to every device that names the alias, multiplies memory rows, pull pages and client storage. Without a target, a reader cannot check the limits, the single connection or the retention against anything.
- F-6 · Major · spec.md, Pull (`projects` filter, one cursor) · The cursor is global, and project rows are filtered by the `projects` list at read time. Suppose a device already holds cursor C and starts working on a new project, so it adds alias X. It never receives X's items with seq ≤ C. The only remedy is `since=0`, which re-downloads everything: shared entries, every workspace entry and every project already held. The spec does not name this. Part 6 will either miss data silently or full-pull every time someone opens a new repository, and that is the most expensive operation the server has (F-4).
- F-7 · Major · spec.md, Restore detection; The mirror · The high-water file `repos/.feed` is written by the mirror queue. The mirror only handles entries (rows with `mirror_revision < revision`), so memory pushes never advance it. It also lags whenever the mirror is backing off (up to an hour, or failing for days). If a database is restored after a period that was mostly memory pushes, or while the mirror was stuck, `.feed` is not ahead of the restored `MAX(seq)`. The instance is then not renewed. AUTOINCREMENT resumes from the restored `sqlite_sequence` and hands out seq numbers that clients have already passed with their cursors, so those changes are missed silently. That is the exact failure D-13 says it prevents. Separately, the concepts brief's restore path (a snapshot of the whole volume) restores `.feed` too, so the automatic detection never fires there and everything depends on the manual `serve instance renew`.
- F-8 · Major · spec.md, One instance (`serve.lock` with a pid liveness check) · The lock lives on the persistent volume, and its liveness test is "the pid is alive". Inside a container the server's pid is deterministic: tini is PID 1 and the server gets a small fixed number. After an unclean exit (OOM kill, `docker kill`, a host crash), `restart: unless-stopped` starts a new container. The stale lock's pid there is either the new server's own pid or tini's, so the check reports "alive" and the server exits 1 "another serve holds", in a restart loop. The spec does not say whether a pid equal to the process's own counts as stale. The test is also meaningless across pid namespaces: the host CLI against a bind mount versus the container.
- F-9 · Major · spec.md, One instance ("repair, purge, backup and instance renew refuse while the lock is held… The one form the runbook teaches is `docker compose exec server …`") · `exec` needs a running container, and the container's main process is the server. So the four subcommands that require a stopped server can never succeed through the one form the runbook teaches. Separately, `serve backup` is `VACUUM INTO`, which SQLite runs safely online, yet it is gated behind a stop. Every backup becomes an outage for no technical reason.
- F-10 · Major · spec.md, Push "For a `withdraw`"; D-12 · A withdraw carries no `baseRevision`, so it is never checked as stale. Member A, the creator, withdraws a shared entry that member B revised to revision 3 a minute earlier, and A has never seen B's revision. B's current text vanishes from every client. It is kept in `entry_revisions`, but nothing tells anyone. That is the silent overwrite the mission forbids, done as a withdraw.
- F-11 · Major · spec.md, Admin routes `disable { withdraw: true }`; Journey 6; D-19 · "Tombstones every item of the member" does not say whether that means items they created or items they last wrote. Under the creator rule it reads as created. Disabling a departed member would then tombstone shared and project entries that the rest of the team has been revising since. One admin click withdraws live team knowledge.
- F-12 · Major · spec.md, The mirror (`runGitAsync` with "the same isolation and timeout"; "the weekly maintenance runs `git gc --quiet`"; `gc.auto=0`) · The mirror makes one commit per applied item, which means a stream of loose objects. Automatic gc is off, so the weekly `git gc` is the only compaction. It runs under part 1's 15 s runner timeout. On a repository with tens of thousands of loose objects on a small VPS, gc gets killed before it finishes, every week. Loose objects and inodes then grow without bound, and the disk guard (507 at 1 GiB free) eventually trips because of the mirror rather than the data. The CPU and memory cost of gc, running in the serving container, is not budgeted either.
- F-13 · Minor · spec.md, Deployment, Caddyfile `request_body { max_size 1MB }` vs `maxRequestBodySize: 1_048_576` and `me.limits.bodyBytes` · Caddy parses `1MB` as 1,000,000 bytes, not 1 MiB. A client that sizes its batches to the published 1,048,576 gets 413 from Caddy, with Caddy's body instead of the server's JSON problem, for any body between 1,000,000 and 1,048,576 bytes. The proxy and the binary disagree on the limit, and the client is told the wrong one.
- F-14 · Minor · spec.md, Waiting for the next change (signal fired "after each applied … item") · A 200-item push commits 200 separate transactions and fires 200 signals. Every held pull answers on the first signal, and its client re-pulls straight away mid-push. It may do so many times, each re-pull a feed query filtered per caller, and with N devices that is up to N×200 queries per push. Nothing coalesces the signals, for example with a short debounce or by firing once at the end of the push. Clients also risk the 600-a-minute bucket during bursts.
- F-15 · Minor · spec.md, One instance (CLI writes "safe beside it"); Waiting for the next change · `serve disable --withdraw`, `revoke` and the other CLI writes run in another process. They do not fire the in-process `ChangeSignal` and do not nudge the mirror queue. Held pulls learn of a CLI tombstone only when their 25 s wait times out. The mirror does not remove withdrawn files until the next push from some device, or a restart. Meanwhile `serve status` reports a backlog the server is not working on.
- F-16 · Minor · spec.md, D-11 and Pull ("every member's workspace entries", memories per alias) · Every device always pulls every member's workspace entries, and every device's memories for each alias it names. Storage and transfer therefore grow with members × devices × store size, and the spec puts no cap on what a device receives, for example by memory importance or kind. On the token-economics lens: all of it lands in each client's store and becomes a candidate for agent context. The server sends no signal that would let part 6 bound what gets injected. "Keeps machines small" is asserted, not shown.
- F-17 · Minor · spec.md, Memory send; `changes.revision NOT NULL`; "`stale` with the stored `updatedAt` as `current.revision`" · Memories have no revision, yet the feed row and the answer require one, and `current.revision` gets overloaded with a millisecond timestamp. The spec does not order the "same hash → applied unchanged" check against the "older `updatedAt` → stale" check, so the two rules give different answers for the same input. Also, `memoryHash` covers neither `remoteAlias` nor `updatedAt` (src/sharing/hash.ts), so a payload whose alias changed but whose hash is the same is answered "applied, unchanged" and the stored alias stays wrong.
- F-18 · Minor · spec.md, Limits (in-memory join limiter per source address); image `WIZARDINGCODE_MEM_TEAM_TRUST_PROXY=on` · The image trusts `X-Forwarded-For` and `X-Forwarded-Proto` by default. A `docker run -p 8787:8787` without Caddy, which the runbook forbids but nothing prevents, lets a caller forge both. Forged addresses get round the join limit, and the per-address buckets grow without bound in memory. Failed bearer tokens on the other routes have no per-address limit, so each one costs a DB lookup.
- F-19 · Minor · spec.md, Deployment `HEALTHCHECK … CMD wizardingcode-mem serve health` · Every 30 s the health check starts a second full Bun runtime, the compiled binary, inside the container. That is a recurring memory and CPU spike on a small VPS just to make one HTTP GET. The cost is neither stated nor weighed against a lighter probe.
- F-20 · Minor · spec.md, Cost and time ("eight to ten hours … the viewer … took about a day") · The estimate covers fifteen routes, a migration-runner split, an async git runner, a mirror with repair and purge, the long-poll, quotas, a multi-arch image, release and CI jobs, and an ADR. Its only basis is a server with fewer moving parts that took longer. The overrun limit (five hours before Phase C) is reached before half the risk (E, F, H) has been touched.
- F-21 · Nit · spec.md, Push steps 1-2 and AC-4 ("part 1's `fileHash`") · There is no `fileHash` under src/. Part 1's function is `hashOf` in src/modules/knowledge/repo.ts, which returns the first 16 hex characters of SHA-256 (64 bits). That truncation is what `baseHash`, idempotency and `appliedAs` compare on, and the spec should name it.
- F-22 · Nit · spec.md, Deployment (`ENTRYPOINT ["tini", "--", …]` and compose `init: true`) · The process runs under two init processes, Docker's injected tini and the image's own. That is harmless but redundant, and D-16 names only one.
