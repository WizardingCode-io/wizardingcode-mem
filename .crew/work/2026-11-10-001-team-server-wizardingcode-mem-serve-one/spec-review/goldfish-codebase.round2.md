## Findings
- F-1 · Blocker · Signatures, `src/team/validate.ts` (`ALIAS = /^[a-z0-9][a-z0-9-]{0,39}$/`, `ENTRY_UID`, `checkMemoryPayload`), `src/team/feed.ts` (`parsePullQuery` checks each of `projects` against `ALIAS`), `src/team/mirror.ts` (`repoFolder` → `projects/<alias>`) · The code's remote alias is not that grammar: `src/core/project.ts` `identify`/`remoteAliasOf` build it as `` `remote:${normalizeRemote(url)}` `` (e.g. `remote:github.com/acme/site`), `src/cli/commands/share.ts` binds levels with `remoteAliasOf`, and `src/sharing/levels.ts` `isHostLedAlias` only accepts aliases that start with `remote:` followed by a host. `entryUid` in `src/sharing/types.ts` therefore produces `project:remote:github.com/acme/site:<uuid>`. As written, every project entry and every memory (whose `remoteAlias` is required) would be `refused shape`, every real `projects=` value would be 400, and `repos/projects/<alias>` would nest folders on `/` and carry `:`. The plan has to take the alias grammar from the code (a `remote:` + host/path form with a bounded length), parse the entry uid so that the alias can hold `:` and `/` (for example, the UUID is the last 36 characters), and derive the mirror's project folder from the alias, for example with `projectFolderName` in `repo.ts`, never from the raw alias.
- F-2 · Blocker · `src/team/validate.ts` `checkEntryPayload` ("frontmatter slug ≠ `payload.slug` → `shape`") and task 10's case "a frontmatter slug ≠ payload.slug → shape" · An entry's frontmatter has no `slug` key. `renderEntry` in `src/modules/knowledge/entry.ts` writes id, title, kind, area, context, subject, status, author, version, created, updated, supersedes and pinned, and `ENTRY_KEYS` has no slug, because the slug is the file name (`parseEntry(text, slug, …)` takes it as a parameter). Every real payload, the `entryPayload` helper's own output included (it renders with `renderEntry`), would be refused as `shape`. The plan has to drop the equality check or say where the slug is compared, and keep `checkSlug(payload.slug)` → `slug`.
- F-3 · Blocker · Scope Modify `src/ui/server.ts` and task 2 ("the inline copy of the `jsonObject` logic in the settings route") · The settings route (`PUT /api/settings`, line 423) already calls `jsonObject`. The inline copy is in the `/api/memories/:id` POST/PATCH handler (lines 523-531), and it differs: it checks only `body === null || typeof body !== "object"`, so it accepts an array, which `jsonObject` refuses. Replacing it changes that route's behaviour, which contradicts "the viewer's tests unchanged" and the no-behaviour-change claim. The plan has to name the right route and either keep its array behaviour or state the change and test it.
- F-4 · Blocker · Signatures, `runGit(host, …)` ("the timeout `host.gitTimeoutMs ?? GIT_TIMEOUT_MS`") · Today `runGit` uses `options.timeoutMs ?? store.gitTimeoutMs` (`repo.ts` line 467), and `GitOptions.timeoutMs` is used by part 1's test `tests/unit/knowledge-repo.test.ts:537` ("a call that does not return in time is killed", `timeoutMs: 50`). Dropping the per-call option breaks that test, against "part 1's tests unchanged" (AC-16, AC-27). The rule has to be `options.timeoutMs ?? host.gitTimeoutMs ?? GIT_TIMEOUT_MS`. Also, `KnowledgeStore.gitTimeoutMs` is already a required per-store timeout, so "a per-host timeout" is not new.
- F-5 · Major · Scope Modify, the `GitHost` passage ("`KnowledgeStore` satisfies it as it is (`root` set by `openStore`…)") · `KnowledgeStore` in `types.ts` has no `root`, so adding one is a change, not "as it is". `src/doctor/checks.ts:649-659` builds a `KnowledgeStore` literal without `openStore`, so a required `root` fails `bun run typecheck` in a file the Modify list does not name. The plan has to add `src/doctor/checks.ts` to Modify, or make `root` optional with a default of `knowledgeRoot(dataDir)` inside `gitEnv`.
- F-6 · Major · Phases B and C (tasks 9 and 11) against Phases D and F · `routes.ts`'s `Context` needs `log: TeamLog` and `handle` "writes the log line". Task 9 asserts "bootstrap logged once as JSON", and task 11 asserts "the log line's `push.refusals`" and "the signal's fire count". But `TeamLog`/`createTeamLog` is created in Phase F (`src/team/log.ts`), and `ChangeSignal` in Phase D ("the signal arrives in D as a no-op here"). B and C cannot be green as written. Move `src/team/log.ts` into Phase B, and the signal-count assertion into D, or give B and C the stubs they need.
- F-7 · Major · Phase F task 14 · The process test runs "`serve health`" (the legacy-skip case), but task 14 creates `serve.ts` with "the `serve` form only", and the `health` subcommand arrives in task 15. Task 14's green run cannot pass. Use `serve` itself for that case, or move `health` into task 14.
- F-8 · Major · `src/team/push.ts` `applyEntry`/`applyPush` (the disk rule) · `PushResult.result` has no value for insufficient storage, and `applyPush` returns `PushResult[]`. Yet AC-19 wants "a new item is 507 and a retry of an applied one is still `applied`" in one push. The plan does not decide what the HTTP answer is: a 507 status with the results so far, a per-item result, or what the remaining items carry. Under the zero-decision rule, the plan has to fix the answer's status and body.
- F-9 · Major · `src/team/mirror.ts` `runMirror` · The plan allows a move (the same UUID under another scope or alias, AC-19), but the mirror handles only a slug rename "in that folder". A revision whose scope or alias changed writes into the new repository and leaves the old file in the old one, together with its `mirror_files` row. The plan has to state the cross-repository rule (remove from the old folder and commit there) and say which folders `purgeItem` rebuilds for an entry whose revisions span several.
- F-10 · Major · `runMirror` ("orders their pending revisions by `at, seq`") · `entry_revisions` in the plan's own schema has no `seq` column; `seq` is in `changes`. The tie-break needs a join on `changes(key = uuid, revision)` or the table's rowid, and the plan does not say which.
- F-11 · Major · `src/team/mirror.ts` `mirrorHost` ("`renew` a no-op") and `src/team/lease.ts` `holdLease` · The spec has `mirror.lease` at 10 minutes, renewed per repository. A no-op `renew` means a `--rebuild` of thousands of revisions outlives the lease, and a second run can start. The serve lease's 30 s TTL and 10 s renewal (spec "Process") appear nowhere in the plan. `holdLease(db, key, ttlMs, now: number)` gives `renew()` no clock, so a test's clock cannot drive it. The plan has to state the TTLs, the renewal points and `now: () => number`.
- F-12 · Major · `mirrorHost(dataDir)`, `ServerOptions.git?: string`, `runMirror(ctx: { …; git? })`, `spawnMirror(dataDir, binary, log)` · `runGit` finds git through `host.env.PATH` (`Bun.which("git", { PATH })`), but `mirrorHost` takes no env, and the plan never says what `env` holds (PATH, HOME or none) or what `git` is (a PATH to prepend? a binary?). It also never says how `binary` is resolved. Under `bun src/cli/main.ts` (as `spawnCli`/`runCliWith` run it), `process.execPath` is bun, so `[binary, "serve", "mirror", …]` would run `bun serve`. The plan has to define all three.
- F-13 · Major · Task 13 ("`stubGit({ failOnce: "commit" })` on one repository … the next run exports it") and `ensureMirrorRepo` · `failOnce` in `tests/helpers/stub-git.ts` fails the first `commit` the stub sees, process-wide (one marker in the stub folder), not per repository. In a fresh mirror, that first commit is `ensureMirrorRepo`'s `team: init` commit, which leaves a repository with `.git` and no HEAD. The plan does not say that `ensureMirrorRepo` completes such a half-initialised repository on the next run, so the "next run exports it" case is undefined. The same function runs `git init -q` without part 1's `--template=` (`createRepository`), against the spec's "no templates".
- F-14 · Major · `insertChange` / the feed schema, for memories · `changes.scope` is NOT NULL and the pull reads one `changes_scope` range per scope (`shared`, `workspace`, `project` per alias), but the plan never says which `scope` and `remote_alias` a memory's feed row carries. If it is not `project` with the memory's `remoteAlias`, memories never reach the alias filter of AC-22.
- F-15 · Major · `src/team/log.ts` `installLogSink`, `src/cli/commands/serve.ts` · The plan does not say which commands install the sink. The `serve mirror` child (whose stdout the server forwards) and the CLI writers call `runGit`/`logError`, which without a sink append to `<team dir>/logs/wizardingcode-mem.log` (`src/util/log.ts`) and never reach the forwarded JSON lines. State that every `serve` subcommand installs it.
- F-16 · Nit · Signatures, `src/store/db.ts` `backup(db, folder, version, prefix)` · `backup` is called only from the private `upgrade(db, path, dir, plan)`, which `migrateModules` also uses. The plan does not say that `upgrade` and `migrateModules` gain the folder and prefix that `openDb` passes (`join(dir, BACKUPS_DIR)`, `wizardingcode-mem`).
- F-17 · Nit · `src/team/db.ts` `requireTeamSchema` · A file at `user_version` > 0 with no `meta` table throws SQLite's "no such table", not `NotATeamDatabaseError`. Say that it is refused the same way.
- F-18 · Nit · Task 18 (`src/core/redact.ts`) · `findSecrets` keeps the earlier of two overlapping rules, so `Authorization: Bearer wcm1_…` is named `auth-header` by the existing second `auth-header` rule unless `team-token` sits before it in `PATTERNS`. The plan does not give the position.
- F-19 · Nit · Signatures, naming · The class is `Buckets`, but `Context.buckets` is used as `buckets.devices`/`buckets.joins`. `Limits` is never defined (only `LIMITS`). `onFeedWrite` (tasks 11 and 12) and `onWrite` (signatures) name the same hook. `resolveTeamDir(env)` calls `defaultDataDir()` without `env`. The empty wait answer `{ items, next, more }` lacks `snapshot`. `mintInvitation` does not validate `expiresInHours` 1 to 720. `area` checked by `AREA_ID` alone skips `AREA_MAX` (40).
