## Findings
- F-1 · Major · plan.md, route table rows `POST /v1/items/:kind/:uid/withdraw` and `/reinstate` · A project entry's uid is `project:remote:github.com/acme/site:<uuid>`, which holds slashes, so the router cannot match it as one path segment. The plan doesn't say whether the client URL-encodes the uid, or whether the router decodes it or takes everything between `:kind/` and the last segment. An implementer with a segment-split router answers 404 for every project entry, and no test case names a project uid on these routes. State the encoding and matching rule, and add a test with an `ALIAS_A` project uid.
- F-2 · Major · plan.md, `src/team/push.ts` `applyMemory` (the list "shape, size, hash, secrets, idempotency, storage, the updatedAt rule") · No step checks `locked_by_admin` for memories. `withdrawByAdmin` sets the lock on a memory and nothing reads it, so the owner's next send with a later `updatedAt` brings back a memory an admin withdrew. Add the lock step (`refused withdrawn-by-admin`) to `applyMemory` and say where it falls in the order, add a store read if one is needed, and add a test case.
- F-3 · Major · plan.md, `applyMemory` and the feed (`insertChange`) · A memory re-sent under another `remoteAlias` keeps the key `<device id>:<uid>`. Its old feed row goes to `current = 0` and nothing stays current in the old alias's range. A device that pulls only the old alias never learns the memory left and keeps a stale copy. Entries get a `tombstone` with `moved_to` for this case; memories get nothing. Decide the rule: either a tombstone row keyed `<device id>:<uid>@<revision>` with `moved_to` in the old range, or a stated reason why none is needed. Then add the test.
- F-4 · Major · plan.md, `applyWithdraw` (the memory branch, "the same retry rule") · The retry rule needs "the tombstone's writer is the caller's device or member". Memories have no revision rows, so that writer can only come from the current `changes` row of the key. The store function list has no read by key (only `insertChange`, `changesSince`, `hasChanges`, `markPurged`), and the plan doesn't name the source. Name the column (`changes.member_id`/`device_id` of the current row) and add a store function such as `currentChangeOf(db, key)`.
- F-5 · Major · plan.md, `applyPush` ("`buckets.bytes.take(deviceId, size)` after each applied item and 429 when it refuses") · The plan doesn't say what happens to the push when the bytes bucket refuses mid-way. Items before it are already committed. Open questions: are the remaining items skipped; does the push still call `onWrite` (signal, `feed.seq`, mirror timer) for the rows it wrote; is the answer a bare 429 `{ error: "rate limited" }` that hides the committed results; does the take come before or after the item's write. As written, an implementer throws and skips `onWrite`, so held pulls miss the change for up to 5 s and the mirror timer is not armed. Decide each point.
- F-6 · Major · plan.md, task 11 (Phase C) against task 16 (Phase G) · Task 11's `team-push` test asserts "a push past 64 MiB in an hour is 429". Task 16 is where `limits.ts` "fills the bytes bucket and the sweep", and the bucket is wired into `applyPush` without its arithmetic until then. Phase C cannot go green as ordered, and the midway gate runs after C. Either move the bytes-bucket implementation into B or C, or move that assertion to task 17.
- F-7 · Major · plan.md, `parsePushBody` ("`HttpError(400)` for a malformed body or over 200 items") · The plan doesn't define a malformed envelope. Missing pieces: which item fields are required for each `op`/`kind`; the allowed types of `epoch`, `baseRevision` and `baseHash`; whether an absent `baseRevision`/`baseHash` on a send means 0/"" or is 400; whether a bad `op` or `kind` fails the whole push (400) or only that item (`refused shape`); and the 400 `error` texts. Two implementers would give different answers to the same body. List the checks, the defaults and the texts.
- F-8 · Major · plan.md, `src/cli/commands/serve.ts` and task 15 · The output contract of the subcommands contradicts itself and is incomplete. Every CLI write "prints JSON lines", yet `invite` prints "the code alone on standard output", and `status`/`members` print plain `key: value` and column lines on the same stdout as the JSON log sink. The event names and fields of each write's line are not given, nor the output of `audit`, `invitations`, `revoke` and the others, nor what `purge` does without `--yes`. Flag parsing for each subcommand (`--role`, `--name`, `--for`, `--expires`, `--withdraw`, `--json`, `--limit`, `--url`, `--rebuild`, `--yes`) is left to the spec's prose with no errors or exits stated. Give the line each subcommand prints and its exit code for every refusal.
- F-9 · Major · plan.md, `serve.ts` ("every CLI write goes through `openTeamForWrite`") against spec AC-32 ("every CLI subcommand writes an audit row") · The readers (`status`, `members`, `invitations`, `audit`, `health`) open through `openTeamExisting`, which is read-only, and `health` opens no database. They cannot write the audit row the AC demands. Decide which subcommands audit, and how a reader writes its row (a second write handle, or exempt by rule), and assert it in task 15.
- F-10 · Major · plan.md, `src/team/lease.ts` `holdLease(...).renew` and `runMirror` ("the lease renewed") · The plan doesn't say what happens when a renewal's `claimLease` returns false, for example after the event loop stalls past 30 s and a second `serve` takes the expired lease. Two servers would then write one directory. For the mirror, a run that lost its lease would go on committing. Decide the behaviour (stop the server and exit 1, or log and carry on; abort the mirror run and record the error) and test it.
- F-11 · Major · plan.md, `store.ts` `advanceSequence(db, table, to)` and `renewInstance` · `sqlite_sequence` has no row for `changes` until the first insert. A naive `UPDATE sqlite_sequence` does nothing on a restore of a database that never had a feed row (the "copy taken before a revoke" case can be such a database), so the 1,000,000 margin is silently lost. State the upsert, including insert when absent, and never lowering the value.
- F-12 · Major · plan.md, task 12 (`wait=1` with no push "answers after about a second"; `wait=30` clamped; held pull answered "by the timer") · `startTestServer` runs on `fakeTimers` and a fake clock by default, and `pullWithWait` measures "remaining" with `now()` and waits with `signal.wait`, whose timers are fake. With the defaults that pull never answers unless the test advances the clock. The test either needs real timers through an override or an explicit `clock.advance`, and the plan picks neither. State which for each wait case.
- F-13 · Major · plan.md, `src/store/db.ts` `openExistingFile(dir, file, { before?, latest? })` and "`openExisting` calls it with `DB_FILE`" · Today `openExisting(dataDir, { allowNewer })` checks against `LATEST_VERSION`, and `src/cli/commands/history.ts:97` passes `allowNewer: true`. The plan doesn't say what `openExistingFile` does when `latest` is absent, how `allowNewer` maps (omit `latest`, or pass `Infinity`), or whether the `busy_timeout = 2000` stays. Followed literally, `openExisting` either loses `allowNewer` or loses its version check. Give `openExisting`'s new body.
- F-14 · Major · plan.md, `src/team/server.ts` `selfCommand()` · `src/util/self.ts` already exports `selfCommand(...args)`. It decides compiled versus source with `isCompiled()` (`Bun.main` contains `$bunfs` or `~BUN`). The plan adds a second `selfCommand` with a different rule (`process.argv[1]` ending in `.ts`/`.js`). If the compiled binary's `argv[1]` ever ends in `.js`, the server spawns a child whose first argument is that path, the binary reads it as an unknown command, and the hourly mirror never runs. Reuse `src/util/self.ts` (`selfCommand("serve", "mirror", "--data", dir)`) and drop the new one.
- F-15 · Nit · plan.md, `openDb` "becomes `openFile(...)` followed by `migrateModules(...)`" · Today `migrateModules` runs inside `openDb`'s try, which closes the handle on error and restricts the `-wal`/`-shm` files after it. Moved after `openFile`, a module-migration error leaks the open handle. That is not "behaviour unchanged"; say that `openDb` keeps its own close-on-error around `migrateModules`.
- F-16 · Nit · plan.md, task 7 against tasks 9 and 12 · Task 7 creates `checkRestore` and its test asserts the instance renewed, the sequence advanced and an audit row. That needs `renewInstance`, `writeHighWater` and the store's `insertAudit`, which tasks 9 and 12 say they create. Move those into task 7, or say task 7 creates them.
- F-17 · Nit · plan.md, task 12 ("Modify `src/team/push.ts` (the feed rows' `seq` into the revision rows)") · `entry_revisions.seq` is `NOT NULL` in migration 1, so task 11 must already write it. The D step reads as new work; drop it or reword it.
- F-18 · Nit · plan.md, `withdrawByAdmin(...): void` against the route answer `{ uid, revision }` · The function returns nothing the route can answer with. The behaviour of an admin withdraw on an item its owner already withdrew is also unstated: a new tombstone revision and feed row, or only the lock.
- F-19 · Nit · plan.md, "Every 401, 403, 409 and 410 body carries `serverId` and `instance`" · `requireAdmin`, `join`'s 410, `checkContract`'s 409 and `requireNoServer` take no ids. Say that `handle` adds the two ids when it converts an `HttpError` with one of those statuses. Also say on which routes `checkContract` runs (join? health?); the route table has no column for it.

- F-22 · Nit · plan.md, task 11 ("the signal's fire count") · Neither `ChangeSignal` nor `TeamServer` exposes a count, and `startTestServer` returns no signal. Name the accessor or the observation the test uses.
