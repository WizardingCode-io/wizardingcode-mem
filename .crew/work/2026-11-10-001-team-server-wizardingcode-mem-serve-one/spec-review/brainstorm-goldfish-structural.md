## Findings
- F-1 · Blocker · spec.md, Pull ("`meta.feed.horizon` is set to the highest `seq` pruned … A `since` below the horizon is 410") with AC-7 ("`next` the last `seq`") · The pull cursor does two jobs: it marks a client's place in the feed, and it resumes a paged full pull. Pruning only removes rows that have a newer row or are tombstones, so live rows with low `seq` stay below the horizon forever. A full pull larger than 500 items or 2 MiB returns as page 1's `next` the `seq` of an old live row. That value is below the horizon, so page 2 gets 410 `fullPull: true`, the client starts from zero again, and it loops. On any server older than 90 days with a store bigger than one page, a full pull can never finish. The `since=0` exemption isn't stated either. Pages 2..n also carry `snapshot: false`, so the rule "absent from a snapshot means gone" has no defined scope across pages, and a client that crashes mid-snapshot loses it.
- F-2 · Major · spec.md, One store boundary (D-1), with Waiting (D-22) and AC-14 · The boundary as written can't be built. `withWrite` is banned outside `store.ts`, but push applies each item as a 10-step read-decide-write inside one `withWrite`. So either the push rules move into `store.ts`, which breaks "one exported function per statement", or `push.ts` breaks the lexical test. `ChangeSignal` lives in `feed.ts` and is fired by `writeChange`, which has to be in `store.ts` because it writes SQL. AC-14 forbids `store.ts` from importing anything in `src/team/` except `db.ts` and `errors.ts`. The builder will improvise a way round, and that workaround becomes the real boundary.
- F-3 · Major · spec.md, D-1 ("Another engine would be a second `store.ts` behind the same signatures") · This placeholder will outlast its purpose. The signatures take bun:sqlite's synchronous `Db`, and a Postgres driver is async, so every caller would change. The design's correctness also depends on one process with one connection: writes are serialised by "its single connection", and these all live in memory or on local disk: `ChangeSignal`, the rate-limit token buckets, the mirror queue, `serve.lock`, the `repos/.feed` high-water file, restore detection through `MAX(seq)`, and `VACUUM INTO` backups. D-22 makes this worse, because the waiting pull only works when writer and waiter share a process. The boundary keeps the SQL in one place but doesn't make the store swappable. The ADR should say so instead of recording that another engine is an option.
- F-4 · Major · spec.md, the `entries` table and the uid comment; ADR 0025 "Identity of an item" · The uid `project:<remote alias>:<uuid>` puts a mutable, client-derived string into the primary key of `entries`, `entry_revisions` and `changes`, and into the mirror's folder name (SHA-256 of the alias). Renaming a repository, moving a remote, or two members whose alias derivation differs all turn one UUID into two server items with separate revision histories, and no migration path exists. ADR 0024 D-8 says the UUID is the identity, but the server keys on scope plus alias plus UUID, so moving an entry between scopes also creates a new item. This becomes data debt from the first push on.
- F-5 · Major · spec.md, Push memory rule, the feed's `uid` ("`remote:<device alias>:<uid>`"), and the admin route `POST /v1/items/<kind>/<uid>/withdraw`; ADR 0025 Provenance ("its `item_uid` is `remote:<the server's uid>`") · One memory has three identities: what was pushed (`<generation>:<row id>`), the server key (`(device_id, uid)`), and the feed form (`remote:<alias>:<gen>:<row>`). ADR 0025 then has the client prefix `remote:` again, which gives `remote:remote:…` unless someone rules otherwise. The admin route takes a single `<uid>` and doesn't say which form, while the server key needs the device. These are colon-joined strings parsed by position, and they will be frozen by contract 1.
- F-6 · Major · spec.md, Push step 8 and the memory rule ("`stale` with the stored `updatedAt` as `current.revision`"); changes `revision INTEGER NOT NULL` · `revision` means two things. For entries it is the server's counter. For memories it carries a client timestamp, and the spec never says what a memory's feed row puts in `revision`. Contract 1 freezes this type confusion into the client's ledger (`version`) and into every later contract that has to stay compatible with it.
- F-7 · Major · spec.md, Terms ("the client's frontmatter `version` … stays in the file bytes"), Push steps 2, 8 and 9 · Two version counters live side by side permanently. The hash covers the whole frontmatter, including the writing machine's local `version` and `author`. Two machines that make the same content edit hash differently, so `appliedAs` and idempotency never match across devices. Received bytes also carry another machine's local `version`, which breaks part 1's local stale check (ADR 0024 D-2) on the receiving side. This spec locks in "verbatim bytes" and leaves the consequences to part 6.
- F-8 · Major · spec.md, the mirror ("a commit already carrying this uid and revision … marked without a second commit") with `serve backup` and restore detection · Revision numbers aren't unique over time. When `team.db` is restored but `repos/` is not, the server issues revision N of a uid again with different bytes. The mirror's HEAD trailer check sees `Uid`/`Revision: N` from the lost future, skips the commit, and the mirror quietly diverges from the authority. Restore detection itself depends on `repos/.feed`, which the mirror queue writes. It falls behind while the mirror is backing off (up to a day per item), it is never said to advance for memory-only changes, and it sits inside the derived tree that `repair` and `purge` rebuild. Server state is kept inside the mirror.
- F-9 · Major · spec.md, D-18 and Authentication ("absent or `1` is accepted") · Compatibility is versioned twice, by the `/v1/` path and by the contract header, with no rule for which one bumps. A missing header means contract 1 forever. "Accept current and the one before" plus "server upgrades first" assumes one server. Under D-21 a client talks to several independently run servers, at contracts it doesn't control, so it has to speak every contract any of them might run. Pinned key lists plus `refused shape` make every additive field in part 4's types a contract bump, and the server must keep a key list per accepted contract.
- F-10 · Major · spec.md, D-21; ADR 0025 D-9 and the part 6 obligation "a second server is a second destination" · The ledger and policy are keyed by `destination`, but the server exposes no stable identity to key them by. The URL changes when the domain moves. `instance` is renewed on purpose at every restore, so a restore would orphan every ledger row keyed by it. `server.created_at` isn't published. D-21 says "the server needs nothing for it beyond this independence", but a durable server id is exactly what it needs, and adding one after clients have keyed ledgers costs a migration on every machine.
- F-11 · Major · spec.md, D-15 quotas and `member_bytes`; ADR 0025 (a memory uid changes with the generation; "a store has 90,000 memories") · The limits are hard-coded constants published in `/v1/me`, with no configuration and no admin override. `member_bytes` counts every kept revision and is never said to decrease, except perhaps on `purge`, so an active member reaches 1 GiB in time and is locked out with no remedy. Every client restore renews the generation, which means re-sending the whole store under new uids. At 90,000 memories against 20,000 a day, that is about 5 days, it doubles the member's bytes, and the old copies stay alongside for 90 days.
- F-12 · Minor · spec.md, D-11 and the feed `scope: workspace` · `workspace:<uuid>` is relative to one person on the client but global on the server, and every device pulls every member's workspace entries. The feed row carries the writer, not the owner, so the client can't route a teammate's workspace entry without assuming that the writer is the creator. That holds today only because of D-12's workspace write rule.
- F-13 · Minor · spec.md, schema · The whole schema assumes one tenant: there is no destination or team column, and `entries.uid` is unique across the server. "Teams within a server" is a listed non-goal, but if it is ever wanted, every primary key and the feed index would need migrating. The ADR should record this as accepted, not leave it implicit.
- F-14 · Minor · spec.md preamble ("where `concept.md` and the brief differ, the brief and this spec rule") versus the brief · The layers reverse each other with no precedence between brief and spec: `serve backup` is dropped in the brief but present in the spec (and in Non-Goals line 35), member-minted invitations, 5,000 versus 20,000 items a day, and who may withdraw (the last writer or the creator). D-3, D-9, D-12 and D-15 record some of these as superseded clauses. `serve backup`, the two-phase rotation, `purge` and the horizon rule are binding only in prose. AC-13 has the ADR record D-1 to D-22 "as rulings", so these reach the ADR without a decision behind them.
- F-15 · Minor · spec.md, the Design subsections · Part 6's obligations are scattered through the server's design: reconciling on a new instance, the meaning of snapshot absence, recording `appliedAs` in the ledger, deduping copied stores, the contract header, the single open pull. They are gathered only in AC-13's list for the ADR. The spec has no section of its own on what part 6 must do, though ADR 0025 has one for its consumer, so part 6's author has to dig them out.
- F-16 · Nit · spec.md, Open Questions ("None open. Three defaults the person may want to look at") · These are open questions labelled closed. D-11's "not a permission" and D-12's creator-withdraw rule are policy choices that will be hard to reverse once clients depend on them.
