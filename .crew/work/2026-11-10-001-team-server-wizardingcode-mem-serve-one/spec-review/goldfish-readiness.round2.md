## Findings
- F-1 · Blocker · plan.md Signatures, `src/team/validate.ts` (`checkEntryPayload`: "frontmatter slug ≠ `payload.slug` → `shape`"), task 10 ("a frontmatter slug ≠ `payload.slug` → `shape`") and `tests/helpers/team.ts` `entryPayload` (renders with `renderEntry`) · Part 1's entry frontmatter has no `slug` key: `ENTRY_KEYS` in src/modules/knowledge/entry.ts is id, title, kind, area, context, subject, status, author, version, created, updated, supersedes, pinned, and `renderEntry` writes no slug. The slug is the file name, which `parseEntry(text, slug, …)` takes as an argument. As written, every payload `entryPayload` builds would fail the rule and be refused `shape`, and the "wrong slug" test cannot be written. Also, `parseFrontmatter` returns `{ map: Map<string, FrontValue>, … }` with no typed `id` or `area`, so the plan must say how they are read (through `parseEntry(text, payload.slug, null)` or from `map`) and what a missing value or a list value gives. The plan must drop or redefine the slug-agreement rule (and D-20's wording through the session) and name the reader.
- F-2 · Major · plan.md task 6 (`team-store-boundary` fails on "an import of … `src/store/db.ts`") against the Signatures (`Context.db: Db`, `TeamServer.db: Db`, every `members.ts`/`auth.ts`/`push.ts`/`feed.ts` function taking `db`) · Every file under `src/team/` needs the `Db` type, and it lives in src/store/db.ts. A builder writes `import type { Db } from "../store/db.ts"` and the boundary test, as specified, fails on it. The plan must say whether `import type` is exempt or whether `src/team/db.ts` (or `store.ts`) re-exports `Db` for the rest of the folder.
- F-3 · Major · plan.md Signatures, `GitHost` ("`KnowledgeStore` satisfies it as it is (`root` set by `openStore` …)") and Scope "Modify" · `KnowledgeStore` (src/modules/knowledge/types.ts) has no `root` field, so it does not satisfy `GitHost` as it is. It needs a new field. Adding a required `root` breaks the hand-built `KnowledgeStore` literal in src/doctor/checks.ts:649-659, which is not in the Modify list, so `bun run typecheck` fails in task 5. The plan must add `root` to the interface explicitly, list src/doctor/checks.ts (and any test that builds the literal), or make `root` derived inside `gitEnv`.
- F-4 · Major · plan.md Signatures, `src/store/db.ts` (`backup(db, folder, version, prefix)`, `migrateFile(db, path, options, busyTimeoutMs)`) · Today `backup` is called only from the private `upgrade(db, path, dir, plan)`, which `migrateModules(db, path, dir, schemas)` also calls with the data dir. The plan changes `backup`'s second argument from the data dir to the backups folder, but says nothing about `upgrade` and `migrateModules`. A builder who leaves `migrateModules` passing `dir` puts the client's module-upgrade copies in the store root instead of `backups/`, and breaks AC-16's "its upgrade copies still land in its own `backups/`". The plan must name the new parameters of `upgrade` and `migrateModules` and what `openDb` passes to each.
- F-5 · Major · plan.md Signatures, `mirrorHost(dataDir): GitHost` and `ServerOptions.git` / `runMirror` `ctx.git?` · `GitHost` requires `dataDir` and `env`, but `mirrorHost` names neither: no PATH source, no HOME. `git?: string` is never defined: a git binary path, or a PATH directory as `stubGit` returns? Nor is it said how it reaches `Bun.which("git", { PATH: host.env.PATH })`. Task 13's isolation test (`stubGit({ dumpEnvTo })`) depends on this. The plan must give `mirrorHost`'s full value, its signature (with `env`/`git`), and the meaning of `git`.
- F-6 · Major · plan.md Signatures, `src/team/lease.ts` and `startTeamServer`; `runMirror` ("claims `mirror.lease` for 10 minutes"; `mirrorHost` "`renew` a no-op") · The serve lease's TTL (30 s) and its 10-second renewal timer are in the spec but in no plan step: `startTeamServer`'s list of what it starts has no renewal. Built as written, the lease goes stale after 30 s, so a second `serve` starts and `requireNoServer` lets `purge`/`--rebuild` run beside a live server. `holdLease(…, now).renew()` takes no clock, so how it reads the time is undefined. The spec's "mirror.lease renewed per repository" is dropped: `renew` is a no-op, so a run longer than 10 minutes can overlap the next hourly child. The plan must name the TTLs, the renewal timer (and that `stop()` clears it), the clock `renew` uses, and where the mirror renews.
- F-7 · Major · plan.md Signatures, `src/team/push.ts` `applyWithdraw` and `PushItem.uid` · AC-20 requires a memory withdraw by "another device of the same member, or by an admin". Memories are keyed `(device_id, uid)`, and a push item's memory `uid` is the caller's own `<generation>:<row id>`. The plan does not say which uid form a push withdraw uses to name another device's memory (the feed form `remote:<alias>:<uid>` through `parseFeedUid`?). Nor does it say what `baseRevision`/`baseHash` mean for a memory withdraw (the stale rule "applies first"). The plan must give the accepted uid forms per kind and the memory withdraw's base rule.
- F-8 · Major · plan.md "The team schema" (`changes.scope TEXT NOT NULL`) and `feed.ts` `pull` (ranges for `shared`, `workspace` and each alias over `changes_scope`) · An `OutgoingMemory` has no scope, and the plan never says what `scope` a memory's `changes` row carries. A builder who writes `'memory'` or anything but `'project'` makes every memory invisible to the pull's alias branch, which breaks AC-22's "only that alias's project entries and memories". The plan must state the memory feed row's `scope` (and `remote_alias`).
- F-9 · Major · plan.md `tombstoneMemberItems(…, by: Caller | "cli")`, `withdrawByAdmin`/`reinstateByAdmin`, `purgeItem` and the schema (`entry_revisions.writer_member/writer_device NOT NULL`, `entries.writer_device REFERENCES devices(id)`, `changes.member_id/device_id NOT NULL`) · A CLI withdraw, a `disable --withdraw` and a purge have no member or device. The plan does not say what goes into these NOT NULL columns, whether `entries.writer_*` is updated, or what `revision`/`hash` the `purge` feed row carries. With `foreign_keys = ON`, a sentinel such as `'cli'` written to `entries.writer_device` fails the insert, and a pull's `member: { id, name }` join finds no member. The plan must give the values for CLI- and admin-origin rows.
- F-10 · Major · plan.md Signatures, `src/team/routes.ts` route table · The plan gives answer bodies and success status codes only for `join`, `me`, `push` and `pull`. For `POST /v1/devices/me/rotate`, `POST/GET /v1/invitations`, invitation revoke, `GET /v1/members`, `GET /v1/devices`, device revoke, disable (`{ devices }`?), enable, role, the item withdraw/reinstate routes, `GET /v1/audit` (clamp or 400 outside 1 to 1000) and the 503 health body, a builder invents the shapes, field names and 200/201. These are outside contracts that part 6 and the tests depend on. The plan must give each route's request and answer shape.
- F-11 · Major · plan.md `runMirror` ("writes or removes the file (renaming on a slug change)") and `purgeItem` ("rebuilds that entry's repository folder") · The plan makes an entry's move (same UUID, other scope or alias) a new revision of one row, so its revisions span several repository folders. `runMirror` does not say to remove the file from the old folder when a revision lands in a new one, which leaves a stale copy behind. `purgeItem` rebuilds one folder, so an earlier revision's file survives in the old folder's history, against AC-21 ("no longer holds the file in any commit"). The plan must state the mirror's rule for a folder change and that purge rebuilds every folder the entry's revisions touched.
- F-12 · Major · plan.md `runMirror` ("orders their pending revisions by `at, seq`") · `entry_revisions` has no `seq` column (the schema gives `uuid, revision, …, at`), and two revisions of different entries share `at` within one push. A builder must guess whether `seq` means the matching `changes` row (joined on key and revision), the rowid or something else. The rebuild's "same files, in order" depends on it. The plan must name the order's exact columns and their source.
- F-13 · Major · plan.md `routes.ts` `handle` ("refuses a `Content-Length` above the cap with 413") and task 17 ("a `Content-Length` above the cap is 413 with a request id") · Both caps are 1,048,576. The spec states that Bun refuses a larger body with 413 before the handler runs, so a request whose Content-Length is above the cap never reaches the handler's check, and the request-id assertion cannot pass as designed. The plan must say which layer answers which case (for example, Bun's limit set above the handler's) or drop the assertion.
