## Findings
- F-1 · Major · spec.md, Push, step 7 "Ownership" and "Entries keyed by the UUID" · Step 7 checks only the prefix of the incoming uid, and a push that changes an entry's scope is a new revision of the same row. So member B can pull A's `workspace:<uuid>` with its revision and hash, then push `shared:<uuid>` on that base. The push is applied, and A's private workspace entry is moved into the team's scope and overwritten. Ownership must be checked against the stored row's scope and creator as well as the incoming uid, and rules are needed for which moves across scopes are allowed (workspace to shared or project, and back), with a case in AC-19.
- F-2 · Major · spec.md, Push, the withdraw paragraph ("the stale rule applies first … an item already withdrawn is withdrawn again with nothing changed") · A withdraw whose answer was lost is retried with its original base n, but the row now stands at the tombstone's revision n+1, so the stale rule answers `stale`. The tombstone has no payload hash, so `appliedAs` cannot rescue it. The "withdrawn again" branch can never be reached by a real retry, which contradicts the success criterion "a retry of an applied item is idempotent whatever else is going on". The spec must say that a withdraw whose base is the revision just before a tombstone the same caller wrote answers `withdrawn`, or must add an `appliedAs` for tombstones.
- F-3 · Major · spec.md, Push, withdraw for memories, and AC-20 · A memory withdraw "carries baseRevision and baseHash like a send, and the stale rule applies first", but a memory send has no base rule (it is ordered by `updatedAt`). For memories the stale check on a withdraw is undefined, and so is what AC-20's "a second withdraw is withdrawn with nothing changed" compares. The spec must state the memory withdraw's precondition.
- F-4 · Major · spec.md, Push step 9 and `entries` / pull item shape · The stale rule requires `baseHash` to equal the row's `hash`, and a re-send "on the tombstone's base" reinstates, but the spec never says what `entries.hash` and the tombstone feed row's `hash` hold after a withdraw: the previous hash, an empty string, or a hash of the tombstone. Server and part 6 will each pick something, and every re-send after a withdraw will then be `stale` forever. The tombstone's hash must be defined.
- F-5 · Major · spec.md, Push step 9 (`appliedAs`) · `appliedAs` is granted whenever the payload's hash equals any earlier revision's hash of the UUID, whoever wrote it. A deliberate revert (device X pushes revision 1's content on base 2 while revision 3 has landed) is told "your earlier push applied". Part 6 records it as a success and takes revision 3, and the revert is lost silently, which is the overwrite D-7 forbids. Limit `appliedAs` to an earlier revision written by the same device (or member) on that item.
- F-6 · Major · spec.md, Pull "Cursors and restores", Restore detection, Risks "A restore" · The claim that "the 410 above catches the clients whose cursor is ahead even when that step is forgotten" is false once pushes land after a whole-volume restore. `AUTOINCREMENT` continues from the restored `sqlite_sequence`, so new rows reuse seq numbers that offline clients have already passed. A laptop that was closed during the restore pulls `since=1000` after the sequence has reached 1050, gets no 410, and silently misses every row between the restored high-water and its cursor. Either state the limit honestly or close it, for example by having `serve`'s start refuse to run until the instance is renewed when the file and the database agree but the volume was restored, or by bumping `sqlite_sequence` at renewal.
- F-7 · Major · spec.md, Restore detection ("renews server.instance, logs and audits … and carries on") · The spec does not say that `feed.seq` is rewritten to the database's values after a detection. Until the next write, every restart (a crash loop, a deploy, the rollback procedure in Risks) detects the restore again and renews the instance again, and each renewal sends every device into a full pull from zero. The spec must state that the file is rewritten in the same step as the renewal.
- F-8 · Major · spec.md, Pull (D-11) and the `changes` index by `(scope, remote_alias, current, seq)` · When an entry moves out of an alias a device names, into an alias it does not name, the old row's `current` drops to 0 and the new current row lies in a range the device never reads. The device is never told the entry left, so it keeps a stale copy until its next full snapshot. The same holds for a move from `project` into `workspace`, or from shared into a project the device does not name. A move must also emit a tombstone (or a "moved" row) in the scope it left, and the snapshot rule ("absent is gone") must not be the only remedy.
- F-9 · Major · spec.md, The mirror ("a slug change renames the file in the same commit") · Only slug changes inside one repository are handled. An entry whose scope or alias changes (which the design explicitly allows as a new revision of the same row) is written into the new repository, and its file is never removed from the old one. The mirror then diverges from the database, and `--rebuild` behaviour for such histories is unspecified. The spec must state that a move removes the file from the old repository in the same run, and that a per-repository rebuild (as purge uses) replays revisions by the scope each revision had.
- F-10 · Major · spec.md, The mirror (`mirror.lease`, "10 minutes, renewed per repository") and Sizing ("holds at ten times that") · A first export or a `--rebuild` of a repository with tens of thousands of revisions runs several git spawns per commit and can take far longer than 10 minutes. The lease then lapses mid-repository, and the quiet-minute trigger or the hourly timer can start a second child on the same repository (index.lock failures, duplicate commits). The lease must be renewed per commit, and Sizing must give the mirror's throughput and the rebuild time at the stated volumes, since no number backs "holds at ten times".
- F-11 · Major · spec.md, Sizing, D-15 and D-25 (quotas deferred) · Sizing counts items but gives no storage estimate, and `entry_revisions` keeps every revision forever. One device looping on edits (for example a part-6 bug) may write about 600 requests/min × 1 MiB ≈ 600 MiB/min of revisions within its rate limit. The only backstop is the 200 MiB disk floor, which then answers 507 to the whole team. The design's growth needs bounding: estimate bytes, cap revisions or bytes per device per minute, or name this denial-of-service in Risks with its operator remedy.
- F-12 · Major · spec.md, Compatibility (D-18) and Alternatives rejected ("Accepting the previous contract too") · The rejection assumes skew only runs "newer client against an older server". But the operator chooses when the server is upgraded, and each member's plugin updates on its own schedule. When contract 2 ships, a server that accepts only [2] answers 409 to every member who has not updated, and pushes and pulls stop. The spec must say whether a server keeps accepting older contracts after a bump. As written, a reader would build one that drops them.
- F-13 · Major · spec.md, Push step 5 and Compatibility (`CONTRACT_FINGERPRINT`) · The server refuses with its own `findSecrets` patterns, but the contract fingerprint covers keys, shapes and reasons, not the pattern set. A server image that adds a rule permanently refuses entries an older client could not redact ("refused as final for that item and that content"), and nothing in the contract signals the skew. Either put the pattern set's identity in the contract or state the risk and its remedy in Risks.
- F-14 · Major · spec.md, Push step 10 ("507 insufficient storage for this item and the rest of the push") and AC-19 · It is undefined whether 507 is the HTTP status of the whole response or a per-item result. AC-19 needs "a new item is 507" and "a retry … still applied" in one push. Yet `insufficient-storage` is not in the fixed reason list that the contract fingerprint pins, so the result shape cannot be built from the text. Define it as a per-item `result` with a reason code, or as a whole-response status with no item applied.
- F-15 · Major · spec.md, Members ("an admin's withdraw locks until reinstated"), `disable { withdraw: true }`, CUJ 6 · The spec does not say whether the tombstones written by disable-with-withdraw are admin locks. If they are, CUJ 6's "the member joins again … and writes their workspace entries again" fails with `refused withdrawn-by-admin`. Nor does it say whether an admin's ordinary push-withdraw of their own entry locks it, which D-23 makes ambiguous. State which withdraws set `locked_by_admin`.
- F-16 · Major · spec.md, Deployment (`Caddyfile` … "Caddy's automatic HTTPS and HSTS") · Caddy's automatic HTTPS obtains certificates and redirects HTTP to HTTPS, but it does not send a `Strict-Transport-Security` header unless a `header` directive is configured. The claim about the outside system is false, and the reader would believe a protection exists that the given Caddyfile does not provide. Add the header to the Caddyfile or drop the claim. Also state that a client posting `join` to `http://` sends its code in clear before the redirect.
- F-17 · Nit · spec.md, Process (lease 30 s) · After a crash (kill -9 or an out-of-memory kill), the restarted server has a new holder id and finds its own previous lease still fresh. It exits 1 and loops on `restart: unless-stopped` for up to 30 s, and `purge`, `--rebuild` and `instance renew` refuse for that time too. Name this in Risks or the runbook.
- F-18 · Nit · spec.md, `changes` and Pull ranges · The `scope` a memory's feed row carries is never stated. The pull's per-scope ranges and AC-22's "only that alias's … memories" assume `project`, so say so.
- F-19 · Nit · spec.md, `entries` ("`bytes`") and `audit` ("id") · `bytes` is ambiguous (a size, or the payload; the pull must join `entry_revisions` for the payload either way). Restore detection reads `audit`'s high-water from `sqlite_sequence`, which needs `audit.id` declared `AUTOINCREMENT`, and the entity list does not say so.
- F-20 · Nit · spec.md, Join ("a failure audited with the address") and the rate limiter · Unauthenticated join failures each write an audit row (and rewrite `feed.seq`), the per-address buckets live in memory until the hourly sweep, and nothing is pruned. Join spam from many addresses grows both without bound. Name it in Risks.
- F-21 · Nit · spec.md, Authentication ("loads the device by token_hash, compares … with timingSafeEqual") · The constant-time compare comes after an exact-match index lookup on the digest, so it adds nothing. Harmless, but the Security NFR presents it as a property.
- F-22 · Nit · spec.md, Cost and time ("Six to eight hours … the viewer … took about a day") · The basis argues this part is smaller than the viewer, yet it also splits the core migration runner, adds the `GitHost` seam, the image, CI and release jobs, a child process and restore detection, across fourteen dense acceptance criteria. The estimate reads optimistic. The overrun limit mitigates it, but the basis should account for that work (Heilmeier Q6/Q7).
- F-23 · Nit · spec.md, Problem and Terms · Heilmeier Q1 asks for no jargon. The opening is dense with project terms (generation, epoch, remote alias, feed, mirror) before the plain statement of what is attempted. One plain-language sentence at the head of Problem would satisfy it.
- F-24 · Nit · spec.md, Pull, Snapshots (`snapshot=1`) · The server-side effect of `snapshot=1` on later pages is never stated: as written, the result is identical with or without it. Either say what it changes or drop it from the contract.
