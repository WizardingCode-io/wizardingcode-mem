Lens: migration and backward compatibility (rollback, server/client upgrade order, restores, first deploy).

## Findings

- F-1 · Blocker · spec.md "Restore detection" + plan.md Signatures `mirrorOne` ("writes the high-water file with the change's seq") and `applyPush` ("one `mirror.nudge()` when any entry applied") · The high-water file `repos/.feed` is written only by the mirror queue, so it lags the database in two ways. First, memory pushes, memory withdraws and disable-with-withdraw of memories never go through the mirror. Second, entries wait in the mirror backlog for up to a day under the spec's own backoff (one minute, five minutes, an hour). Restore a database copy taken after the last mirrored seq but before the newest change, and `fileSeq > dbSeq` is false: no instance renewal. Because the restored `sqlite_sequence` is lower, AUTOINCREMENT then gives new changes seq numbers that clients have already passed, and those clients skip the changes for good. That is the silent loss D-13 claims to prevent. The mirror also works in `updated_at, uid` order, not seq order, so the file can move backwards. The spec has to say who writes the high-water mark and when. It must be written for every `changes` row, in seq order, after the database commit, and not by the mirror. Plan Phase D does this as an interim step, and Phase E then moves it into the mirror, which is the wrong direction.

- F-2 · Major · spec.md "Restore detection" ("compares it with `MAX(seq)` of `changes`") + "Pull, the feed" pruning rule ("a tombstone 90 days after it was written") · This produces false positives. If the newest row in the feed is a tombstone and nothing happens for 90 days, the hourly prune deletes it, `MAX(seq)` drops below `.feed`, and the next restart reports `restore detected`. The instance is renewed and every client of the team does a full pull from zero, for nothing. The comparison has to use `sqlite_sequence` (the AUTOINCREMENT high-water) or keep the newest row.

- F-3 · Blocker · spec.md "One instance" (lock with `{ pid, startedAt }`, liveness by `process.kill(pid, 0)`) + Deployment (`tini` as ENTRYPOINT, `restart: unless-stopped`) · Inside a container the pid of serve is the same small number on every start: 1 is tini, serve gets roughly 7. Suppose the container stops uncleanly (OOM kill, SIGKILL after the 30-second grace while git hangs, host reboot), so `serve.lock` stays on the volume. On the next start the new process checks its own pid or tini's, finds it alive, and exits 1 with `another serve holds`. `restart: unless-stopped` then loops forever, so the first unclean stop leaves the team server permanently down until someone deletes a file on the volume by hand. The lock is also too loose: a second container on the same volume (a stray `docker run` during an upgrade, or a second compose project) sees a pid from another namespace as dead, replaces the lock, and two servers write `team.db` and the same git repositories. The lock needs a namespace-independent identity: `flock`/`O_EXCL` held for the life of the process, or a hostname plus boot id, and it must never treat its own pid as another holder.

- F-4 · Blocker · spec.md "One instance" ("`repair`, `purge`, `backup` and `instance renew` refuse while the lock is held... The one form the runbook teaches is `docker compose exec server wizardingcode-mem serve <sub>`") · `docker compose exec` works only on a running container, and a running container means serve holds the lock. So every stop-the-server subcommand refuses in the only form that is taught. That includes `serve instance renew`, the step the spec says the runbook prints in bold after a whole-volume restore, and `serve backup`. An operator therefore cannot run the restore procedure, and cannot repair or purge. The spec has to name the form for the stopped case (`docker compose stop server && docker compose run --rm server serve <sub>`) and make sure F-3's lock does not refuse that container.

- F-5 · Major · spec.md "Restore detection" and Risks "A restore" ("every client pulls from zero and reconciles") · Restoring an older database also loses every device joined after the copy and every token rotation after it. Those devices get 401 `missing or wrong token`, the same answer as a wrong token, and a revoked device gets 401 `device revoked`. Nothing tells the client "this server forgot you; re-join", and the spec does not say the 401 answer carries `instance`. Part 6 cannot tell a restore apart from a bad token, so sync on those machines stops silently. The admin's own device may be among them, and then the only way back is `serve invite --role admin` through F-4's broken path. The restore has to define the 401 body for an unknown device on a renewed instance (at least `instance`) and the runbook step for re-inviting.

- F-6 · Major · spec.md "The mirror" ("Before committing, the queue reads HEAD's trailers: a commit already carrying this uid and revision ... the row is marked without a second commit") + `serve backup` ("the mirror is derived and is not copied") · After restoring only `team.db` from `serve backup`, the repositories on the volume still hold commits for revisions the restored database never had. The next push reuses revision N for different bytes. If the last commit for that uid is at HEAD, the trailer check sees `Uid`/`Revision: N` and skips the commit, and the mirror's file silently disagrees with the database. Revision numbers are reused across a restore, so the trailer is not an identity; it needs the hash in it. Alternatively, the restore procedure for a database-only restore must include `serve repair`, and neither the spec nor the plan says so.

- F-7 · Major · spec.md D-18 ("the server accepts contract 1 and, from the next bump on, the one before it; ... the server upgrades first") and release.yml (one tag publishes both the client binaries the plugins fetch and, per this plan, the image) · "Server first" cannot be enforced. Client binaries reach machines through plugin updates the operator does not control, while the VPS runs whatever `WIZARDINGCODE_MEM_VERSION` pins in `.env`. The realistic skew is a newer client against an older server. An old server cannot accept a contract it has never heard of, so every request of the upgraded client is 409, sync on that machine stops, and the plan's "accept the one before" rule never helps. The compatibility window must sit on the client: it speaks the highest contract both sides share, read from `/v1/me` or the 409's `accepted`. The ADR has to say this, and part 6 needs it as a requirement now.

- F-8 · Major · spec.md D-18 ("an unknown payload field is `refused shape`") + plan.md `checkEntryPayload` (keys from part 4's `OUTGOING_ENTRY_KEYS`, `parseFrontmatter`, `checkSlug`, `AREA_ID` from part 1) · The server's acceptance rules are compiled from the same client modules. If a later release adds a key to `OutgoingEntry`/`OutgoingMemory`, or relaxes part 1's slug or area rule, upgraded clients send payloads the old server refuses per item with `refused shape`/`slug`. That is a per-item 200 answer, not a 409, so a client treats it as a final refusal of that item rather than a version problem. Nothing ties a change to those key lists or rules to a contract bump. The spec needs that rule and a test that fails when the key lists change without `CONTRACT` changing.

- F-9 · Major · spec.md Risks "Rollback" ("The image can be replaced by a previous tag; a newer `team.db` makes an older binary exit 3") · This describes how a rollback fails, not how it is done. Once a team migration 2 exists, rolling the image back means a restart loop at exit 3 under `restart: unless-stopped`. The only way back is the migration runner's upgrade copy in `backups/`, and restoring it loses every write since the upgrade. The spec does not say that F-1/F-2 detection then has to renew the instance, or that clients must re-push. The spec needs a rollback procedure across a schema bump: which file, which command, what the clients see. It also needs a rule against writing subcommands migrating a database that a live older server holds. Today `invite`/`revoke`/`disable`/`role` "write through SQLite's lock ... beside it", so a newer binary on the host could run `openTeamDb` and migrate under a running older server.

- F-10 · Blocker · plan.md task 18 (release `docker` job builds "from the `binaries` artefact") and Dockerfile ("the binary copied from `dist/...`") · `actions/download-artifact` does not keep the executable bit. The existing `publish` job has to `chmod +x` for exactly that reason (release.yml line 72), and nothing in the Dockerfile or the job does a chmod or uses `COPY --chmod=0755`. The released image would hold a non-executable binary and fail to start on the first deploy. The CI step builds from `dist/` in the same job that ran `bun run build`, where the permissions are still intact, so CI stays green while the release image is broken.

- F-11 · Major · plan.md task 18 (tags `ghcr.io/${{ github.repository_owner }}/wizardingcode-mem:${GITHUB_REF_NAME#v}`) · Two problems, and each one alone stops the first release from pushing an image. First, `repository_owner` is `WizardingCode-io`, and Docker references must be lower case. Second, `${GITHUB_REF_NAME#v}` is shell parameter expansion, which is not evaluated inside a `with: tags:` input. Separately, the `docker` job runs beside `publish` with no ordering, so when it fails the GitHub release with new client binaries still goes out without a server image. That is F-7's skew built into the pipeline. Making `publish` depend on `docker` would close it.

- F-12 · Major · spec.md Deployment ("the package is made public once (a runbook step)"), with the runbook as part 7 · GHCR creates a package as private on its first push. Until someone flips it, `docker compose up -d` on a VPS fails with `unauthorized`, and the step that says so is in a later part. The first deploy of this part therefore fails as documented. Either the step belongs in this part's acceptance (AC-11), or the compose file must say a login is needed.

- F-13 · Major · plan.md and spec.md D-7/D-21 versus part 4's `sharing_ledger (destination, kind, uid, direction, version, hash, epoch, times)` · The server's contract forces a change in the client store that no part owns. The ledger records a server revision, not part 1's version. The destination is now one of several servers (D-21), where it used to be the single `team`. Revision numbers become meaningful only together with the instance, because a restore reuses them (F-6). Any ledger rows part 4 already writes (destination `team`, `version` = local counter) need a migration. The spec names neither the migration nor the owning part; it only says "part 6 reconciles".

- F-14 · Minor · spec.md Deployment (`ENV ... WIZARDINGCODE_MEM_TEAM_TRUST_PROXY=on` baked into the image) · Anyone who runs the image any other way than the shipped compose file meets a broken first deploy. `docker run -p 8787:8787` to try it, or a load balancer that terminates TLS without `X-Forwarded-Proto`, makes every authenticated request 400 `https required`. Published directly, `X-Forwarded-For` can also be spoofed for the join rate limit and the audit. Trust-proxy belongs in `compose.yml`, not in the image's defaults.

- F-15 · Minor · spec.md "The command and the data directory" (`backups/` holds "the migration runner's upgrade copies") versus plan.md `openFile`/`backup(db, dir, ...)` (backup written into `dir`, the data directory) · The spec and the plan disagree on where upgrade copies land, and the rollback procedure in F-9 depends on that path. Also, a migration that fails on a full disk under `restart: unless-stopped` writes another backup copy on every restart and fills the disk faster. The plan has no rule for that case.

- F-16 · Minor · spec.md Deployment (`WIZARDINGCODE_HOME=/data/home`, `useradd --no-create-home`, `read_only: true`) · I could not check whether `WIZARDINGCODE_HOME` is the variable `resolvePaths()` actually reads; the concept names only `<data dir>` and `loadSettings`. If the name is wrong, any product path that runs before `setLogSink` is installed resolves to a home directory that does not exist on a read-only root and fails at start. That covers `loadSettings` and a `logError` file write. The spec should cite the variable from the code.

- F-17 · Minor · spec.md "Restore detection" + Risks "A restore" ("a restore of the whole volume needs `serve instance renew`") · Detection of a whole-volume restore depends entirely on a manual step, and that step cannot be run (F-4). Copying `server.instance` into `.feed` (or into a sidecar file outside the volume snapshot) would not help a whole-volume restore. What would help is a monotonic stamp the clients hold: if a client's cursor is ahead of the server's sequence high-water, the server answers 410 `fullPull`. That catches the case the manual step misses.

- F-18 · Nit · spec.md Deployment (`ENTRYPOINT ["tini", "--", ...]`) and compose `init: true` · Docker's own init then runs as PID 1 and tini runs under it, so there are two init processes. tini warns that it is not PID 1 and does not reap unless started with `-s`. Choose one of the two.

- F-19 · Nit · plan.md task 18 CI step ("`docker stop wcm` exits 0") versus AC-11 ("`docker stop` exits the container with 0") · The exit code of `docker stop` says whether the stop command worked, not how the container exited. Asserting the drain needs `docker inspect -f '{{.State.ExitCode}}'`.
