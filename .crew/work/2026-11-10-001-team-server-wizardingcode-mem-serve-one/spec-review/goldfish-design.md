## Findings
- F-1 · Blocker · spec.md "Push", entry send rule 6 (Idempotency) against rule 11 and the `entries` paragraph ("a renamed remote or a moved entry never splits one history in two") · Rule 6 runs before the write and answers `applied` with nothing changed whenever the row is not withdrawn and the hash matches. The hash covers only `frontmatter + body`, and the frontmatter carries no scope, alias or slug (`ENTRY_KEYS` in src/modules/knowledge/entry.ts: id, title, kind, area, context, subject, status, author, version, created, updated, supersedes, pinned). So the motivating case fails: a renamed remote, or any move or slug rename whose file bytes stay the same, is swallowed. No revision, no move tombstone, no feed row. The entry stays under the old alias and devices reading the new alias never get it. The same hash-only test makes rule 9's `appliedAs` mistake a stale move for an earlier success. Rule 6 (and `appliedAs`) must also require the stored scope, remote_alias and slug to equal the payload's, as the memory rule already does with `remoteAlias`. AC-33 must pin a byte-identical move and a byte-identical slug change as new revisions.
- F-2 · Major · spec.md "Push", memory send paragraph, and "Pull … Moves"; AC-34 ("the same hash with another remoteAlias replaces") · When a memory row changes `remoteAlias`, it gets a new `upsert` in the new alias, and the old row of its key becomes `current = 0`. No `tombstone`/`movedTo` row is left in the alias it left, as entries get in rule 11. A device that names only the old alias keeps the memory forever in incremental pulls: its next pull sees nothing in that range, and only a fresh snapshot would show the absence. The spec must state the memory move rule (a `tombstone` keyed like the entry's `<key>@<revision>` in the old alias), and AC-34 must pin it.
- F-3 · Major · spec.md D-24, "serve purge", and "What part 6 must do" · Purge deletes the `entries` row and its revisions and keeps no record of the UUID. Any device that still holds the item then re-creates it: a send on base 0 is "no row" and applies as revision 1, and a client on an old base gets `stale` with `current { revision: 0 }` and will rebase to 0. Part 6's obligations never mention `op: purge` (drop the local copy and the ledger row, never re-send). Erasure, the stated purpose of purge, is therefore not durable. The design needs a purged-UUID guard on the server (refuse with a reason code, which bumps the contract) or an explicit part 6 obligation, plus a named risk.
- F-4 · Major · spec.md "The command and the data directory" (`mirror.lease`, 60 seconds, renewed after every commit) against "The mirror" (the host's 60-second git timeout) · One revision takes several git calls (stage or remove, commit, and for a move two repositories), each allowed up to 60 s. The lease is renewed only after a commit, so a slow but live run can outlive its 60-second lease. The next hourly or quiet-minute child then claims it and exports the same `mirror_revision < revision` rows at the same time. The result is duplicate commits for one revision (breaking "one commit per applied revision") or `index.lock` failures. The lease must outlast the longest step (or be renewed before each git call), and the server must not spawn while its own child is alive.
- F-5 · Major · spec.md "Limits, rate limits, logs" (SIGTERM: "a running mirror child left to finish on its own (it holds its own lease)") and D-26 ("retried at the next run") · In the compose deploy the spec prescribes, `serve` exiting ends the container, and the kernel kills the child. Docker's init does not hand SIGTERM to grandchildren by default. A git killed mid-commit leaves `.git/index.lock` (or a ref lock), and every later run fails on that repository with the same error. Nothing removes a stale lock, so "retried at the next run" never succeeds until someone runs `--rebuild` with the server stopped. Any deploy during an hourly run can wedge the mirror. The spec must say how stop treats the child (signal it and wait within the 30-second grace) and how a run clears locks left by a dead holder, and AC-35 must pin it.
- F-6 · Major · spec.md "Sizing" (a rebuild of 20,000 revisions takes about 35 minutes), "serve purge" and "mirror --rebuild" (server stopped), and "Risks and mitigations" · At pilot size, `--rebuild` after a database restore, and a purge of a shared entry (which rebuilds `repos/shared`, holding most revisions), each mean about half an hour with the team server down. That outage is the price of erasure and of every restore without the mirror, and no risk, operability item or ADR item names it. An operator would schedule a GDPR-style purge expecting seconds. It must be named with its size, or the rebuild must run beside the server under `mirror.lease`.
- F-7 · Nit · spec.md "One server per data directory" and Risks "A crash and the lease" ("may refuse once or twice") · Docker's restart policy backs off from 100 ms, doubling, so a 30-second fresh lease gives about eight to nine exit-1 restarts, not one or two. The count is unbacked. Say "repeatedly for up to 30 seconds".
- F-8 · Nit · spec.md Risks "Rollback" (`team-<time>-v<n>.db`) against AC-30 (`backups/team-<ms>-v1-<pid>.db`) · The two spell the upgrade copy's name differently. An operator copying the rollback command would miss the pid part. Use one form.
- F-9 · Nit · spec.md "Sizing" · "At most 5 GiB of entry revisions … more with their revisions" contradicts itself. The real ceiling is also left unstated: with no stored quotas and no pruning (D-25), the per-device bytes bucket allows 25 × 64 MiB = 1.6 GiB an hour across the team, against a 200 MiB floor and an unstated volume size. Give the growth bound and the volume size the runbook should assume.
- F-10 · Nit · spec.md "Limits, rate limits, logs" and AC-31 ("a push that takes a device's applied payload past 64 MiB in an hour [is] 429") · The spec never says whether the bytes bucket is charged by body size before any item applies or by applied bytes during the push. Nor does it say whether crossing it mid-push is a whole-push 429 or a per-item result, or whether idempotent retries are charged. Two builders would do this differently. State the point of the check.
- F-11 · Nit · spec.md "Push" (the handler refuses a `Content-Length` above 1 MiB) · A chunked body without `Content-Length` up to 2 MiB passes both the handler's check and Bun's `maxRequestBodySize` when no proxy is in front (loopback, CI). The published 1 MiB cap should be enforced on the bytes read, not only on the header.
