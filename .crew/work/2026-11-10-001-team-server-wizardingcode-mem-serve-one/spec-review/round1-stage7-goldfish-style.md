## Findings
- F-1 · Major · spec.md, Critical User Journeys 3, last clause ("when a device retries a push whose answer it lost after a third member pushed on top, then `stale` with `current` and `appliedAs: 2`, so the client … takes revision 3 as received") · The journey never applies a revision 3, never introduces a third member, and does not say which device's lost push is retried, while AC-19 tests the same case as `appliedAs: 1`. Someone building the test from the journey would expect `appliedAs: 2` and someone building it from the AC would expect `appliedAs: 1`. "takes revision 3 as received" is not defined anywhere. The journey must name the third push that makes revision 3, name the retried push, and give the same `appliedAs` value as AC-19.
- F-2 · Major · spec.md, Sizing ("The design holds at ten times that") · Nothing measures this claim. The only seeded test (Data model, AC-22) uses a 100,000-row feed, which is the pilot size and not ten times it. Ten times the pilot means about 1,000,000 feed rows and 2,000,000 memory rows, and no figure or test covers that. A reader would take the scale limit the rubric asks for as proven. Either measure it at that size or state it as an untested expectation, saying which parts rest on index reasoning alone.
- F-3 · Major · spec.md, Terms ("An admin is a member who may … purge") and D-5 ("purging any item") against D-24 and Design `serve purge` ("by the operator with a shell on the server and the server stopped … no API route erases anything") · The spec says purge is an admin power, but "operator" is never defined and purge runs only through the CLI with the server stopped. Someone reading Terms or D-5 alone could add a purge permission or route for admins. Define "the operator" in Terms and say purge belongs to whoever has a shell on the host, not to the admin role.
- F-4 · Nit · spec.md, Problem, first paragraph ("within seconds while both are online") · "both" has no antecedent, because the sentence talks about "each machine". Name the two machines, as D-22 does ("while both machines are online").
- F-5 · Nit · spec.md, Sizing ("the high-water file") · The term is used here before it is defined. The definition only arrives in Design as "`feed.seq` (the high-water file)". Add it to Terms.
- F-6 · Nit · spec.md, D-1 ("one git repository per server scope") · "server scope" is not a defined term. Terms defines scope as a client term, and the mirror uses shared, per-alias and per-member folders. Say "one repository for shared entries, one per remote alias and one per member", or define the term.
- F-7 · Nit · spec.md, Alternatives rejected ("would make every other client's `decide` see `received-same`"; "ADR 0018's worst case across people"; "a twin asynchronous runner"; "four of the round's blockers") · These lean on part 4 and brainstorm vocabulary that this document never defines, so a reader new to the project cannot check the reasons. Give each a short gloss or a file reference.
- F-8 · Nit · spec.md, Alternatives rejected ("an export costs little"; Postgres: "a load the limits keep far below SQLite's in one process") · Both are judgements with no measure. Replace them with the facts behind them, such as the child process run hourly or Sizing's 60 pushes a minute, or cut them.
- F-9 · Nit · spec.md, Goals ("JSON logs with a request id that answer 'why does my teammate's machine not see my entry'") and Limits, rate limits, logs · This promises more than a server log can deliver, because client-side causes (the policy, an alias the device does not name) never reach it. Say what the line records (the cursor, the refused uids and reasons) and stop there.
- F-10 · Nit · spec.md, Pull, "Waiting for the next change" ("Caddy neither buffers nor times out a 25-second answer") · This is stated as fact with no source, no Caddyfile setting and no acceptance criterion. Cite the Caddy default it relies on, or mark it as unverified.
- F-11 · Nit · spec.md, Non-Functional Requirements, Security ("the pull feed shows members' names and times, not device ids"; "tokens and codes redacted by the client's store") · The first claim is false for admins, whose view adds `device` (Pull). The second names the wrong component, since `redact` lives in `src/core/redact.ts`. Qualify the first with "to members" and name the redaction module in the second.
- F-12 · Nit · spec.md, Pull ("a single item larger than the cap is sent alone") · No item can exceed the 2 MiB page cap, because entries and memories are capped at 256 KiB, so this clause describes a case that cannot happen. Remove it, or say why it is kept.
- F-13 · Nit · spec.md, Design, `serve purge` ("marks them `op: purge`, writes one tombstone feed row `purge`") · This mixes two of the defined ops, `tombstone` and `purge`, in one phrase. Say "one feed row with op `purge`".
- F-14 · Nit · spec.md, Critical User Journeys 7 ("when it starts again, then it runs") · The "then" carries no checkable outcome. Name what is observed, for example that health answers `ok` and the lease is held.
- F-15 · Nit · spec.md, AC-17 · The health 503 under 100 MiB is stated twice in one criterion ("is 503 when free disk is under 100 MiB" and "503 with free disk injected just under 100 MiB and 200 just above"). Keep the second, precise form.
- F-16 · Nit · spec.md, AC-29 ("imports nothing from `src/team/` but `db.ts` and `errors.ts`") · `errors.ts` appears nowhere else in the spec. Name it in the design's module list, with what it holds (for example `NotATeamDatabaseError` and `SchemaTooNewError`).
- F-17 · Nit · spec.md, Goals, second bullet ("with the refinements below") · The refinements follow in the same bullet's parentheses, not below. Drop "below".
- F-18 · Nit · spec.md, Terms ("The person owns a machine…") against the sources line and the Decisions table ("the person's answers of 2026-11-10") · One term is used for both any machine owner and the one person who took the decisions. Give the decider a separate name.
