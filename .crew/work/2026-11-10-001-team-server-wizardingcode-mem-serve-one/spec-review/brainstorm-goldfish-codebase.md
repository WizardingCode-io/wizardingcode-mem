## Findings
- F-1 · Blocker · spec.md Push step 2, plan.md "Order against the other parts" and `validate.ts`/`tests/helpers/team.ts` signatures · Part 1 has no `fileHash`, and nothing named that exists anywhere in `src/` or `tests/`. The one content hash is `hashOf(bytes)` in `src/modules/knowledge/repo.ts:341`. It gives the first 16 hex characters of the SHA-256, and `readRepoFiles` in index-store.ts:517 uses it to fill `EntryItem.hash`, which `decide` compares (policy.ts:408). Phase 0 says it "checks the names", but every later task imports a name that does not exist.
- F-2 · Blocker · plan.md Modify `src/modules/knowledge/{types,store-open,repo}.ts` ("`supportPaths(root)` and `ensureSupportFolders(root)` take the root"); spec.md "repos/ … `.support/` for the runner" · `supportPaths`, `ensureSupportFolders` and any `.support` folder do not exist. The plan describes them as existing functions to change. The code says the opposite: repo.ts:411-414 reads "The store keeps no folder or file of its own for git to be pointed at", and isolation comes from `-c` arguments and `GIT_CONFIG_GLOBAL=/dev/null`. The task "store.root changes supportPaths" (task 11) cannot be written.
- F-3 · Major · plan.md `members.ts` `checkName` ("part 1's author rule through `src/modules/knowledge/author.ts`"); spec.md Subcommands · author.ts has no name rule. The rule is `authorNameProblem` in `src/settings/settings.ts:143` (`AUTHOR_MAX = 80`, no CR/LF, not `agent:`). It does not trim, but the plan says "1 to 80 characters after trim". A reader would either reimplement the rule in author.ts or apply a trim the client's rule lacks. A name with spaces at either end would then be valid on one side and not the other.
- F-4 · Major · spec.md "The team database" and AC-1 ("a client store's file renamed `team.db` is refused as 'not a team database'"); plan.md `openTeamDb` = `openFile(...)` then `requireTeamSchema` · In `src/store/db.ts:166-175`, `migrate` throws `SchemaTooNewError` when `user_version` is above the list's latest. A client store is at `user_version` 7 and `TEAM_LATEST` is 1, so the schema check never runs. Instead `serve` exits 3 and prints "team.db was written by a newer wizardingcode-mem; upgrade the image". At 3 AM that sends the operator to upgrade an image when the real fault is a wrong file. AC-1 cannot pass in the order the plan gives. The meta check has to come before `migrateFile`.
- F-5 · Major · spec.md "One store boundary" versus "Every write is one `withWrite`"; plan.md `push.ts applyItem` ("one `withWrite`"), `members.ts join` ("one transaction"), `repair.ts purge` ("one transaction") · AC-14's test fails on `withWrite` in any `src/team/` file except store.ts and db.ts. The ten-step push, the join and the purge each need reads and conditional writes in one transaction. The documents never say how a caller outside store.ts opens one, for example a `store.transaction(db, fn)` export. A builder either breaks AC-14 or moves the push rules into store.ts. Either way the rule "no logic in the store" or atomicity is lost without anyone noticing.
- F-6 · Major · spec.md "Restore detection" ("After every applied item the mirror queue writes the item's `seq` to `repos/.feed`"); plan.md `mirrorOne` writes the high-water file · The mirror handles entries only. Memory pushes, memory tombstones and CLI-made changes never advance `.feed`. A failing entry also holds the mirror back for up to a day through the backoff. So `.feed` lags `MAX(seq)` by exactly the window a restore would lose. A database restored inside that window is not detected. Because `sqlite_sequence` is restored with it, `AUTOINCREMENT` then reuses `seq` numbers above the clients' cursors, and clients silently skip changes, the failure D-13 exists to prevent. Restore detection must not depend on git staying healthy.
- F-7 · Major · spec.md "One instance" (`serve.lock` `{ pid }`, "a stale lock (a dead pid) is replaced"); plan.md `acquireLock` (`process.kill(pid, 0)`) · In the container, process ids are fixed per PID namespace (tini or docker-init, then the binary). After any unclean stop (SIGKILL past the 30 s grace, OOM, host crash), `restart: unless-stopped` starts the binary at the same pid that is written in the lock. `kill(pid, 0)` succeeds against the process itself, so `serve` exits 1 with "another serve holds /data" and the container loops on restart. The rule needs a check for its own pid and a boot or start identity. A pid alone cannot judge a lock on a volume.
- F-8 · Major · spec.md "One instance" ("The one form the runbook teaches is `docker compose exec server wizardingcode-mem serve <sub>`") versus `repair`, `purge`, `backup` and `instance renew` refusing "while the lock is held … stop the server first" · `exec` needs the server's container running, and while it runs the lock is held. So the runbook's only form cannot run the four subcommands that need the server stopped. The operator needs `docker compose run --rm server serve repair` with the server stopped. The spec never names that form or says what it does with the lock.
- F-9 · Major · spec.md "Limits" (1 MiB = 1,048,576, published in `/v1/me`); spec.md Deployment `Caddyfile` `request_body { max_size 1MB }` · Caddy reads `1MB` as 1,000,000 bytes (`MiB` is 1,048,576). A client that sizes its batches from `limits.bodyBytes` therefore gets Caddy's own 413 for any body between 1,000,001 and 1,048,576 bytes. That 413 is plain text, carries no `X-Request-Id`, and leaves no server log line, because the Caddyfile turns off Caddy's access log. AC-11's deploy-files test pins the wrong value.
- F-10 · Major · spec.md "Push" ("the body at most 1 MiB (`Bun.serve`'s `maxRequestBodySize`, answered 413 before parsing; the authentication runs before the body is read)") and "every answer carries `X-Request-Id`" · When Bun refuses a body over `maxRequestBodySize`, it does so before `fetch`, so `handle()` never runs. No request id, no JSON log line, and no authentication run first. An unauthenticated caller gets 413, not 401. The spec's claims about ordering and request ids do not hold for this path, and an oversized push is invisible in the logs. The text either has to accept this or check `Content-Length` in the handler below Bun's cap.
- F-11 · Major · release.yml (`upload-artifact` then `download-artifact`, and `publish` has to `chmod +x wizardingcode-mem-*`, line 72); spec.md Dockerfile ("the binary copied from `dist/...` into `/usr/local/bin/wizardingcode-mem`") · Artifacts lose the executable bit, which is why the existing `publish` job chmods. The new `docker` job builds from the `binaries` artifact, and the Dockerfile as specified has no `COPY --chmod=0755` or `chmod`. The released image's `ENTRYPOINT` would fail with permission denied. CI would not catch it, because CI builds from the local `dist/`, where the bit is kept.
- F-12 · Major · spec.md "Logs" (fields `{ at, level, event, requestId, deviceId?, memberId?, route, status, ms, address?, items?: { applied, stale, refused, withdrawn } }`) · On call, the likely page is "my teammate's machine does not see my entry". The log line cannot answer it: a pull logs neither `since`, `next`, the `projects` filter, the number of items returned, nor whether it was held, and a held pull's 25 s `ms` hides real latency. A push logs counts but not the refused uids or their reasons (`secret` with its rule, `quota`, `shape`, `not-owner`, `withdrawn-by-admin`), and the audit records no refusals. The operator cannot tell "filtered out by alias", "refused secret" and "never pushed" apart. These fields need to be in the log line, without payloads.
- F-13 · Major · spec.md "The mirror" ("logs the error … an item still failing after a day is logged at `error` once a day"); plan.md `LogSink = { at, scope, name, message }` · The sink's entry has no uid, revision, repository folder, attempt count or next retry time. Errors that go through `logError` have no request id either. Every mirror git failure goes through part 1's `runGit` fail path (repo.ts:456-458), which names the subcommand as the first argument that does not start with `-`. With `GIT_CONFIG_EXTRA = ["-c", "safe.directory=*", …]` passed as leading `args` (plan.md `mirror.ts`), that first argument is `safe.directory=*`. Every mirror error would then read "git safe.directory=* in … failed". The one diagnostic line misnames the failing command and does not say which item is stuck.
- F-14 · Major · spec.md "serve status" ("the mirror backlog … with the last mirror error and its time") and "The mirror" ("also kept in memory for `serve status`"); plan.md `readStatus` reads `repos/.mirror-error.json` · `serve status` is another process (`docker compose exec`), so it cannot read the server's memory. The spec text and the plan disagree about where the error lives. The plan's file sits inside `repos/`, which `repair` empties of "every repository folder … but `.support` and `.feed`", and whether that wipe covers the error file is not stated. Rate-limit state, held pulls and the time of the last successful mirror commit are not visible to the operator anywhere.
- F-15 · Major · spec.md Push step 2 ("its bytes (`frontmatter` plus `body` … which is the file's text and part 1's hash input)") · No code produces an `OutgoingEntry` yet (`src/sharing/` only declares the type), so how frontmatter and body are split is unpinned. `parseFrontmatter` drops one trailing newline from the body (entry.ts:170-171) and `renderEntry` adds one back (entry.ts:186). A client that sends the parsed `body` gets a hash that differs from its own `EntryItem.hash` (repo.ts `hashOf` of the file). Separately, `redactForSend` changes the bytes of any entry it redacts. The server then answers a hash that never equals the sender's `item.hash`, so `decide` (policy.ts:408) answers `send` and never `already-sent`, and the sender pushes the same entry again on every sync. The server's hash rule has to name the exact bytes and say whether they are taken before or after redaction.
- F-16 · Minor · spec.md "Process" and plan.md task 13 ("`run` resolves only on a signal") with the hourly maintenance timer and `ChangeSignal` timers; `src/cli/main.ts:81-91` sets `process.exitCode` and never calls `process.exit` · Unless the documents say that `stop()` clears the maintenance interval and every waiter timer, the process stays alive after `run` resolves. Docker then sends SIGKILL at the 30 s grace, which leaves the lock behind (feeds F-7). Also, the weekly `git gc` "every 168th hour" counts from process start, so a server redeployed more often than weekly never runs it.
- F-17 · Minor · spec.md "Subcommands" (`invite`, `revoke`, `disable`, `role` "safe beside" a running server) · A CLI `disable --withdraw` writes tombstones from another process. It does not fire the server's `ChangeSignal` and does not nudge the mirror, so the withdrawn files stay in the mirror until some later push or a restart, and `serve status` shows a backlog with no error. The spec says nothing about this.
- F-18 · Minor · spec.md "Authentication"/"Rotation" · A token that was rotated out, and one never issued, both get 401 `missing or wrong token`. If a client loses the rotate answer, after ten minutes its device is locked out for good, and the operator sees an "active" device whose `last_seen_at` has stopped and nothing that says why. The request id is also generated by the server only. Accepting a client `X-Request-Id`, or echoing one back, would let part 6's logs be matched to the server's.
- F-19 · Minor · spec.md "Push" step 4 ("`refused secret` naming the rule"); plan.md `PushResult` has `reason` only · No field carries the rule name, so neither the client nor the log can say which rule matched (see F-12).
- F-20 · Minor · plan.md `repo.ts` modifications · `gitEnv` sets `GIT_CEILING_DIRECTORIES` to `knowledgeRoot(store.dataDir)` (repo.ts:382), so for the mirror the ceiling is `<team dir>/knowledge`, not `repos/`. The plan changes the support paths but not the ceiling. Also, `-c safe.directory` is honoured only by gits that read it from command-line configuration, while part 1's floor is `GIT_MIN_VERSION` 2.32. The image's git version is not pinned to one that honours it.
- F-21 · Nit · spec.md "Redaction" · The new `PATTERNS` entries must carry the `d` and `g` flags (redact.ts:20). The spec gives bare patterns. The "Bearer" precedence also does not depend on rule order: `auth-header`'s class has no `_`, so it never matches `wcm1_…` (redact.ts:60).
- F-22 · Nit · spec.md "Push" step 3 · `scope` and `slug` are not frontmatter keys (`ENTRY_KEYS`, entry.ts:308). They are `OutgoingEntry` fields, so "the frontmatter is parsed; … `scope` must agree" names the wrong source. `AREA_ID` has no length cap (`AREA_MAX` 40 is separate), and `ENTRY_UID`'s `[0-9a-f-]{36}` is looser than part 1's `UUID`.
- F-23 · Nit · plan.md task 2 (`src/ui/server.ts` "its own copies deleted") · The viewer also has an inline copy of the `jsonObject` logic at server.ts:528-531, which the move would leave behind. The viewer's 500 answer exposes `error.message` (server.ts:766), and the team server rightly does not copy that.
