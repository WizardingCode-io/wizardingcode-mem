## Paraphrase
The concept adds a `serve` command to the existing binary. It runs a long-lived HTTP server whose own SQLite database (`team.db`) is the authority for the team's shared knowledge entries and memories, and it writes a git "mirror" of the entries afterwards as readable history. Only devices holding a token from an admin-issued, single-use invitation can reach it, and the first admin's invitation is printed on the first start. Part 6's sync client pushes batches of part 4's payloads, each checked against the server's revision and hash and answered per item (applied, stale, refused or withdrawn). It also pulls a feed by cursor that can wait up to 25 s for the next change. The server ships as one non-root Docker image behind Caddy, which terminates TLS, and the operator manages members, devices, status, repair, purge and backup through `serve` subcommands run against the same data directory.

## Findings
- F-1 · Blocker · spec.md, "One instance" ("`repair`, `purge`, `backup` and `instance renew` refuse while the lock is held by a live pid … The one form the runbook teaches is `docker compose exec server wizardingcode-mem serve <sub>`") · `docker compose exec` only works while the server container is running, and the server in that container holds the lock. So under the only form the runbook teaches, every subcommand that needs the server stopped can never succeed. Because the root filesystem is `read_only` and the user is 10001, `serve backup <path>` also needs a path on `/data`, and the spec never names one. The operator is never given a working sequence for these commands: stop the service, then something like `docker compose run --rm server serve backup /data/…`. As written, backup, repair, purge and instance renew cannot be run in the deployment the spec ships.
- F-2 · Major · spec.md, "One instance" (stale lock = "a dead pid") with Deployment (`tini` as PID 1, `restart: unless-stopped`) · Inside a container the server's pid is the same small number on every start. Suppose the container was killed without the lock being removed (OOM, `docker kill`, a host crash). On the next start the pid stored in `serve.lock` is "alive", because it is the new server's own pid or tini's. The server then exits 1 with `another serve holds <dir>`, and `restart: unless-stopped` turns that into a restart loop. The lock rule does not say how it compares against its own pid or against a different pid namespace, so an implementer following the text builds a server that will not restart after a crash. Separately, `init: true` in compose and `tini` in the ENTRYPOINT run two inits. Nothing says which one is meant.
- F-3 · Major · spec.md, Members ("the member is an admin named … `admin`"; `join { code, label }` carries no name) · The first admin is always named `admin`, and no route or subcommand renames a member. That name is what every mirror commit author shows and what every pull's `member.name` shows. The operator has no way to make the bootstrap admin "André". The only workaround is to invite a second admin by name and disable the first one, and that is not stated.
- F-4 · Major · spec.md, Roles ("cannot … have its last device revoked … 409 `the last admin stays`") · Take a team whose only admin has lost a laptop. They cannot revoke that device, which is exactly when revocation matters. The recovery is to mint `serve invite --for <admin id>`, join from a new machine, then revoke. Neither the spec nor the error says this, and the error tells nobody what to do next. The 409 should name the way out, and the spec should state the recovery workflow.
- F-5 · Major · spec.md, "Admin routes" and Subcommands · `disable` has no inverse: no enable or re-enable route or subcommand. Workspace entries belong to the creating member (`refused not-owner` for anyone else). So a member disabled by mistake and re-invited becomes a new member id, and that new member can no longer write their own workspace entries. The workflow for undoing a disable, or for a returning member, is missing. A builder would ship an irreversible action with no warning.
- F-6 · Major · spec.md, Subcommands versus Admin routes · Some admin powers exist only over HTTP: listing invitations, revoking an invitation, withdrawing or reinstating an item, and `GET /v1/audit` (the last one does have `serve audit`). An HTTP client for these arrives only with part 6, or never. An operator on the VPS who learns that an invitation code leaked has no CLI to revoke it. Bootstrap has the same gap: `serve invite` prints a code, but this part ships no way to use it other than a hand-written `curl POST /v1/join` whose JSON answer holds the only copy of the token. The spec never says that the image released by this part cannot be used by a person until part 6 ships, and it never says the release should wait for part 6.
- F-7 · Major · spec.md, Restore detection, plus concepts_brief.md ("the runbook (part 7) snapshots the volume with the server stopped") and Risks ("a restore of the whole volume needs `serve instance renew`, which the runbook says in bold") · Automatic detection covers only a database restored without the mirror. The documented primary backup is a volume snapshot, which restores `repos/.feed` along with the database. That path depends on the forgotten manual step the spec rejects as a restore signal ("a forgotten step makes every client miss changes"). Further gaps:
  - `.feed` is written by the mirror queue, so a mirror that has been failing for a day leaves it behind and blinds the check.
  - The spec never says whether memory items, which are never mirrored, advance `.feed`.
  - After restoring a `serve backup` copy, the mirror still holds commits for revisions the database no longer has. The spec does not say whether `serve repair` is required.

  An operator following the runbook's own method gets silent missed changes.
- F-8 · Major · spec.md, Risks "Rollback" ("The image can be replaced by a previous tag; a newer `team.db` makes an older binary exit 3") · These two clauses contradict each other once a release migrates the schema. A previous tag then exits 3 and keeps restarting under `unless-stopped`. The real rollback is to restore `backups/team-*` (the runner's upgrade copy) and then let restore detection renew the instance, so every client pulls from zero. That path is not described. An operator who reads "replace the tag" gets a crash loop.
- F-9 · Major · spec.md, Pull (`projects=` filter; "`snapshot` … the client treats a uid absent from a snapshot as gone") · The spec does not say what a device does when it starts working on a new project. An incremental pull with the new alias added returns only changes after the cursor, so the older items of that project never arrive. The only remedy is a `since=0` snapshot, and the API does not say that a changed project list needs one. "Absent from a snapshot means gone" also clashes with the filter: a project item outside the named aliases is absent from the snapshot without being gone. Part 6 will build against this, and the server contract leaves it to guesswork.
- F-10 · Major · spec.md, Push step 8 ("A row withdrawn by its owner counts as current … a re-send after its own withdraw … reinstates") with step 5 ("A `shared:` or `project:` uid is the team's") and D-12 ("an owner's re-send after its own withdraw") · The spec does not say whether any member can resurrect a shared entry the creator withdrew by pushing on the tombstone's base, or only the creator. Step 5 implies any member, D-12 implies only the owner, and "owner" is undefined for a team entry whose withdraw right belongs to the creator. A builder will pick one, and the creator's withdraw may be silently undone by a teammate.
- F-11 · Major · spec.md, `serve purge <uid> --yes` ("removes the entry's current row, its revisions …") · Purge is defined for entries only. Memories are keyed `(device, uid)`, so a bare memory uid is ambiguous, and a withdrawn memory keeps its payload in `memories.payload`. A secret that slipped into a shared memory has no erasure path, even though the spec calls purge "the erasure path" (D-19).
- F-12 · Major · spec.md, the command (`--trust-proxy` and "https required") · Without `--trust-proxy`, a bare-host operator who runs `--host 0.0.0.0` with no proxy (a case the spec names as supported: "the server also runs without the proxy … on a bare host") accepts bearer tokens over plain HTTP, and nothing warns. The opposite case also fails: someone who runs the image directly with `-p 8787` for a quick test gets 400 `https required` on every authenticated call, because the image sets `TRUST_PROXY=on`, and also accepts a client-forged `X-Forwarded-For`. The spec needs a start-up warning or refusal for a non-loopback host without the proxy flag. It also needs to explain the image's default to someone who is not using compose.
- F-13 · Major · spec.md, Limits (D-15: 20,000 items a day, 1 GiB per member, 507 under 1 GiB free) · Every limit is hard-coded: no flag, environment variable or admin command changes one. `refused quota` says neither which quota was hit nor when it resets (UTC midnight for the daily one, never for the member one). On a small VPS the 1 GiB free-disk floor may be most of the disk. An operator cannot tune any of this, and a client cannot tell "wait until tomorrow" from "ask an admin".
- F-14 · Major · spec.md, Terms paragraph and throughout · The spec relies on terms that drive the API's rules but never defines or links them: "remote alias" (the pull filter, the uid prefix and the mirror folder all depend on it), "workspace" entries and scope, the memory uid's "generation", "epoch", "ADR 0018's worst case", "the legacy migration" (`applyLegacyEnv`, `migrateLegacyData`), and "the lazy command table". A reader cannot tell what a member types in `projects=`, or why workspace entries are per member, without reading parts 1 and 4.
- F-15 · Minor · spec.md, Memory send ("`stale` with the stored `updatedAt` as `current.revision`") · A timestamp is returned in a field named `revision`, which entries use for a small counter. A client developer will compare it as a revision. It needs its own field, or an explicit note in the response schema.
- F-16 · Minor · spec.md, Goals ("a two-phase rotation") and Rotation · The text describes one call followed by a 10-minute grace window, not two phases. A reader expects a confirm step. The lost-answer case is also not walked through: what happens when the client never receives the new token and retries rotate with the old one.
- F-17 · Minor · spec.md, Bootstrap ("a restart within the 24 hours prints nothing") with Deploy CUJ (`docker compose logs server`) · `docker compose up -d` after any compose change recreates the container and drops its log. The code is then gone, and no reprint is offered. The remedy, `docker compose exec server wizardingcode-mem serve invite --role admin --name <you>`, should be stated where the loss happens. Also, the bootstrap line is plain text while every other line is JSON, so a log shipper or a `jq` filter will miss or break on it.
- F-18 · Minor · spec.md, The mirror (`repos/projects/<first 16 hex of SHA-256 of the remote alias>/`, `repos/members/<member id>/`) · The mirror is justified as "a readable history", but a person browsing the volume cannot tell which folder is which project or member. `knowledge.json` holds "the server scope", and the spec never says whether that includes the alias or the name.
- F-19 · Minor · spec.md, Non-Goals ("beyond `serve backup`") versus concepts_brief.md ("`serve backup` is dropped") and concept.md ("the two files to copy") · The spec brings `serve backup` back without recording it in the Decisions table's superseded column. The deployment is now three files (`compose.yml`, `Caddyfile`, `.env.example`), not two, and nothing says where an operator gets them, since they are not in the image. `.env.example` leaves `WIZARDINGCODE_MEM_VERSION=` empty, which gives an invalid image reference, and the expected tag format (`1.2.3` or `v1.2.3`) is not stated.
- F-20 · Nit · spec.md, Sources paragraph ("where `concept.md` and the brief differ, the brief and this spec rule") · "The brief" could mean `brief.md` or `concepts_brief.md`.
- F-21 · Nit · spec.md, Pull (`projects=<comma list of remote aliases>`) · The spec does not say how an alias that contains a comma or other reserved characters is encoded.
