## Findings
- F-1 · Blocker · spec.md Terms "A remote alias … matching the `[a-z0-9][a-z0-9-]{0,39}` grammar of part 4's area ids", and every use of it (Push step 1 "part 4's alias grammar", memory `remoteAlias` "matching the alias grammar", Pull `projects`, The mirror `repos/projects/<remote alias>/`; plan.md validate.ts `ALIAS = /^[a-z0-9][a-z0-9-]{0,39}$/`, `parseEntryUid`, `parsePullQuery`, `repoFolder`) · This is false against the code the spec says it consumes. Part 4's `remoteAlias` is the project's host-led `remote:` alias, for example `remote:github.com/acme/site` (src/sharing/report.ts `entryAliases`, src/sharing/levels.ts `isHostLedAlias`, src/core/project.ts `identify`, ADR 0025 D-16). The `{0,39}` grammar is the id part of `SHARE_AREA`, which applies to area ids and not to aliases. Built as written: every real project entry and every memory is `refused shape`; every `projects=` value is a 400; `project:<alias>:<uuid>` holds two extra colons that the uid parser must handle; and `repos/projects/<alias>` becomes a nested path built from a raw string with `/` and `:` in it. The fix: take the alias grammar from part 4's code (the `remote:` prefix and a host-led normalized remote), state how the server parses the uid around it, derive the mirror's project folder through a slug or hash as `nameSlug` already does for members, and correct the Terms line and AC-19, AC-20, AC-21 and AC-22 to match.
- F-2 · Major · spec.md "One server per data directory (D-17)" ("the same shape as the client store's `claimLease` in `src/store/meta.ts`, implemented in `store.ts` over the team's table"); plan.md store.ts `getMeta`, `setMeta`, `leaseFresh`, `claimLease(db, key, holder, until, now)`, `renewLease`, `releaseLease`, and lease.ts `holdLease` · `src/store/meta.ts` already exports `getMeta`, `setMeta`, `leaseActive`, `claimLease` and `releaseLease`. They work on any `Db` that has a `meta(key, value)` table, and the team schema creates exactly that table. A holder id with no pid in it (`newHexId()`) is trusted until expiry, so the pid concern behind D-17 does not arise. As planned, a second implementation would exist under the same name `claimLease` with a different argument order (`holder, until, now` against `owner, now, leaseMs`), so the two lease rules would drift and the shared name would invite the wrong import. The fix: `store.ts` re-exports or wraps meta.ts's functions, which keeps the boundary test intact, and the spec says "reused" in place of "implemented in store.ts".
- F-3 · Nit · plan.md Signatures, `src/team/contract.ts` `REASONS = ["shape", …] as const; type Reason` · `src/sharing/types.ts` already exports a `REASONS` and a `Reason` with another meaning (the predicate's reasons), and contract.ts imports from that same module for the key lists. Give the push reason codes a distinct name such as `PUSH_REASONS` / `PushReason`.
- F-4 · Nit · plan.md `ServerOptions.lease?: boolean` ("claims the lease unless `lease === false`") · No criterion or test names a use for this switch. It is a production path that starts a server without the one-process guard (D-17). Remove it, or name the test that needs it.
- F-5 · Nit · spec.md "The mirror" (`mirror_files` and the `<slug>--<8 hex>.md` collision rule); plan.md `fileNameFor`, `setMirrorFile`, `clearMirrorFiles` · The collision table holds state derived from replay order. After a purge and a rebuild, a file can change its name (`<slug>--x.md` becomes `<slug>.md`). A fixed name such as `entries/<slug>--<first 8 hex>.md`, or the bare UUID, would drop the table, the rename-on-collision logic and its tests for an export that is only read. Consider the simpler naming, or state why readable bare slugs are worth the table.
- F-6 · Nit · spec.md "Snapshots" (`snapshot=1` on the following pages); plan.md `PullQuery.snapshot` · As specified, the server only echoes the flag: nothing it answers depends on it, and the client already knows it opened a snapshot at `since` 0. Drop the parameter, or say what it changes on the server.
- F-7 · Nit · spec.md Design (The command and the data directory, Deployment, Redaction) · The spec's Design holds code-level detail that belongs in the plan or the files: `SKIPS_LEGACY = new Set(["serve"])`, the exact `docker run` hardening flags, the full Caddyfile text, the regex literals and the `dg` flags, the 16-hex and 12-base32 lengths. The plan already carries all of it. Keep the interfaces and invariants in the spec and leave the literals to plan.md, so the two texts cannot disagree.
