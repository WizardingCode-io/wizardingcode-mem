## Findings
- F-1 · Major · `spec.md` Design › Push, entry `send` step 7 "Ownership" (with step 9 and the "move" rule in The team database › `entries`); `plan.md` Signatures › `applyEntry` · Step 7 checks who owns the **uid being pushed** ("A `workspace:` uid belongs to the member who created it … A `shared:` or `project:` uid is the team's"). But entries are keyed by UUID, and a push of the same UUID under another scope counts as a move. So member B can push `shared:<uuid of A's workspace entry>` on the current base. B learns that base from the pull, because D-11 gives every device every member's workspace entries. Step 7 lets the push through because the uid says `shared`. The result is that B rewrites A's workspace entry as revision n+1 and moves it out of A's workspace, which breaks D-12 ("workspace entries by their member's devices"). A builder who follows step 7 as written ships that hole. AC-19 only tests the move between project aliases. **Change:** step 7 must also check the existing row: a row whose current scope is `workspace` takes a send of any scope only from its `created_by_member`. Add an AC-19 case where another member pushes `shared:<a workspace UUID>` and gets `refused not-owner`. Also say whether a move from `shared` or `project` into `workspace` is allowed, and for whom.
- F-2 · Minor · `spec.md` Design › The command and the data directory, "One server per data directory" ("the same shape as the client store's `claimLease` in `src/store/meta.ts`, implemented in `store.ts` over the team's table"); `plan.md` `src/team/store.ts` (`getMeta`, `setMeta`, `leaseFresh`, `claimLease`, `renewLease`, `releaseLease`) and `src/team/lease.ts` · The plan writes a second copy of code that already exists. `src/store/meta.ts` has `getMeta`, `setMeta`, `claimLease` (which also renews, since it extends a lease the caller already holds), `releaseLease` and `leaseActive`. All of them take any `Db` and run against a `meta (key, value)` table, and the team schema creates exactly that table. The boundary still holds if `store.ts` (the one file allowed to touch SQL) re-exports or wraps them. There is one trap to name if they are reused: `ownerAlive` reads a leading run of digits in the holder as a pid. A `newHexId()` holder such as `4821ab…` would then be checked as process 4821, which the spec rules out on purpose because pids repeat in containers. **Change:** have `store.ts` wrap `src/store/meta.ts`'s functions and give the holder a non-numeric prefix (for example `serve-<hex>`), or state in the spec why the team needs its own copy. Either way, a second implementation should not appear without anyone deciding on it.
- F-3 · Minor · `plan.md` The team schema, `CREATE INDEX changes_current ON changes(current, seq)`; `spec.md` Design › `changes` ("Indexes on `(current, seq)`, `(key, seq)` and `(scope, remote_alias, current, seq)`") · Nothing in the design reads through `changes_current`. The pull, the snapshot and `hasChanges` all use `changes_scope` (the spec says so, and the `EXPLAIN QUERY PLAN` test pins it). `insertChange` and `markPurged` find a key's rows through `changes_key`, and `sequenceHighWater` reads `sqlite_sequence`. The index is built for a query nobody makes, yet every push, tombstone and purge has to write to it. **Change:** drop `changes_current`, or name the query that needs it and pin that query's plan the way the pull's is pinned.
- F-4 · Nit · `spec.md` Design (for example "`main.ts` gains `SKIPS_LEGACY = new Set(["serve"])`", the `openFile` and `migrateFile` split in The team database, the Dockerfile line by line and the CI step commands under Deployment, the boundary test's list of forbidden tokens, and the `startTeamServer({...})` options under Tests in-process) · The spec's Design is written at the plan's level: helper names, constructor arguments and shell commands that `plan.md` › Signatures and Phase H repeat. The two copies have already drifted. Tests in-process lists `startTeamServer`'s options without `lease`, while the plan's `ServerOptions` has `lease?: boolean`. The `GitHost` shape in The mirror's prose is `{ dataDir, root, env, renew }`, while the plan's interface also has `gitTimeoutMs` and `extraConfig` (the prose describes them further on, but not in that shape). **Change:** keep signatures and commands in `plan.md` only. The spec's Design should describe components, interfaces and data flow, and point to the plan for the code-level detail.

The D-1 to D-26 rulings are left alone as binding. That covers the store boundary, the contract fingerprint, restore detection with `feed.seq`, the 410 and `instance renew`, the mirror as a child-process export, the rate limiter and the size of the slice. Within them I found no other speculative abstraction, unmeasured caching or queue, or design that closes off later growth.
