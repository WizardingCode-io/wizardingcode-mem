## Returns
- R-1 · .crew/work/2026-11-12-007-three-tests-fail-intermittently-on-the-m/spec.md:26 · AC-4 asks that ADR 0024 "no longer says that the store leaves git's housekeeping as it is", but that sentence is the premise of a security limit that this change leaves open. `docs/adr/0024-knowledge-module.md:193` says the files under `.git/objects/` are unchecked, that an automatic gc removes and rewrites files there and could do so through a link, and that the store "does not turn off git's own housekeeping (`gc.auto`, `maintenance.auto`)". D-1 keeps maintenance on, only in the foreground, so all of that stays true; `refuseLinksInside` still skips the files inside the folders of `objects/` (`src/modules/knowledge/repo.ts:273`). Reword AC-4 so the ADR names the two settings and says the housekeeping still runs, now inside the commit, and so the known limit at line 193 (unchecked files, gc writing below `objects/`, "the sync part closes both") is kept, not removed or reported closed. As written, the criterion is met by deleting the limit.
- R-2 · .crew/work/2026-11-12-007-three-tests-fail-intermittently-on-the-m/spec.md:31 · The Risks sentence "a repack that exceeded it would report a failure for a commit that landed; the store's next open reads the repository as it is" does not match the code, and D-1 was taken on that cost (`conclave.md:14`, `conclave.md:22`). Read from the code, not run:
  - On a timeout `runGit` throws (`src/modules/knowledge/repo.ts:487`), and `commitChange` catches it and runs `undoStaged` then `clearIntent` (`repo.ts:1161-1169`).
  - For every `created` path, `undoStaged` runs `git rm --cached` and removes the file from the disk (`repo.ts:976-980`). With the commit already landed, a new entry ends up in HEAD but deleted from the index and the working tree, with no intent record for the next open to act on.
  - The timeout sends `SIGKILL` to the spawned `git commit` only (`repo.ts:472-483`); nothing there kills the foreground `git maintenance` child. That child would go on writing under `.git/objects` while the undo runs, and a killed one would leave `maintenance.lock` behind. This is the state the spec's title says cannot exist.
  - The mirror has no undo: its `commitPaths` calls (`src/team/mirror.ts:245`, `:278`, `:289`) just throw.

  The window existed before but covered only the commit; the change widens it to the whole repack. Line 31 must state what the store and the mirror actually do on that timeout, and the spec must then do one of two things. Either add a criterion for the path: a commit whose maintenance exceeds the timeout leaves the tree equal to HEAD and no git process running. Or record the consequence as accepted by the author, with the real cost stated, as an amendment to D-1.
