## Findings
- F-1 · Major · Design §3 "What" (older) and J-5 · J-5's line says "the agents run it from their next session", but hooks run the staged path on every call, so the new binary is live in the current session as soon as `status` stages it. Meanwhile the session's `mcp` server, the sync and the viewer keep running the old one. If the new hooks migrate the store, those old processes hit `SchemaTooNewError` for the rest of the session. ADR 0030 names this exact hazard ("the viewer and the sync keep writing to a store a newer binary migrated") as a reason not to replace the binary, yet the spec answers it for staging only with "as hooks and install already did". It does not face that it adds a new, silent trigger from a command that looks read-only, and the user-facing sentence about timing is wrong.
- F-2 · Major · Design §3 "What" (missing) and J-7 · "Missing" leads to staging, and `decide` only skips when `<data dir>/bin` or its nearest existing parent belongs to someone else. So a fresh Homebrew copy that was never installed, or one run after `uninstall`, creates the data directory and a full copy of the binary in `bin/` just because someone typed `status` or `doctor`. Nothing runs that copy. The spec never says whether this is intended after `uninstall`, or how it squares with uninstall leaving nothing behind; an implementer will build it exactly as written.
- F-3 · Nit · Design §3 "What" (older) · `stageBinary` re-reads the staged version just before it copies, and may return `kept` (a newer binary arrived in between). The spec does not say what `reconcile` then prints or does. Built literally, it prints the J-5 line "<version> is now in <path>", which would be false, where it should hand over or stay quiet.
- F-4 · Nit · Non-Functional Requirements ("Cost") · Heilmeier Q7 (how long it takes) has no answer; "one item and one pull request" is not a duration. Q8's midway checks are also not named apart from the final acceptance criteria and the first-release read.

## Not answerable
- Bun's `fetch` with `redirect: "manual"` inside a compiled binary on each platform · the probe ran from source only, and the spec's tests use a fake `fetch`, so the shipped binary's behaviour is first seen on the first release (the probe states this).
- github.com's rate limiting and its answer while a release's assets upload · these need the live service; the spec lists them as not verifiable.
- Whether adding `WIZARDINGCODE_MEM_UPDATE` to `SETTING_KEYS` with no viewer field breaks a viewer test or check that expects a field for every key · I did not read `ui/` or the settings tests.
