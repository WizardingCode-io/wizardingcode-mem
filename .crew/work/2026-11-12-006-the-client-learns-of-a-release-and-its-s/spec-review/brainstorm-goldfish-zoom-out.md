## Findings
- F-1 · Major · The hypothesis, points 3 and 6 · Self-replacement is applied to plugin installs too, whose updater is already the marketplace (the brief notes it removes the author's ability to hold a release by holding the marketplace), and point 6 only adds a test for the skew it creates; the simpler cut is notice-only for plugin installs and replacement only where no channel manager exists (script and direct installs), which also shrinks the hook-contract test's burden.
- F-2 · Major · The hypothesis (whole) / brief "Alternatives Weighed" · The concept drops the brief's cheaper re-stage rule (a CLI run from outside the data dir that is newer than the staged copy stages itself), which with the npm shim's existing forward-only staging covers Homebrew and npm with no network code; without it, once the self-updater is cut back the channels' own upgrades still never reach `<data dir>/bin`, and the concept never states which installs are left needing a self-replacing binary once notice plus re-stage exist (by the code read, only `scripts/install.sh` installs and stale marketplaces).
- F-3 · Major · Point 5 / src/cli/commands/install.ts:234 · Hand-over to a newer staged binary already exists but only for `install` (`binaryOrHandOver`); after a self-update, a Homebrew or npm `wizardingcode-mem status|doctor` on PATH is the older copy, the very command meant to show the notice, and it meets a store the newer binary may have migrated (SchemaTooNewError); extending the existing hand-over to every command is the missing piece, not a new mechanism.
- F-4 · Major · Point 3, "verifies the sha256 as src/embed/download.ts does" · download.ts is model-specific (pinned `MODEL_BYTES`, `modelPath`, a sweep keyed on `MODEL_FILE`), and four other download-verify-stage implementations already exist (scripts/install.sh, the plugin template's `fetch()`, the npm shim, plugins/opencode/binary.js); "as download.ts does" will be read as a fifth copy, so the concept should say either extract a generic verified download from download.ts or reuse the staging shape, and name which.
- F-5 · Major · Point 4, "the store's recorded binary version" · No such record exists: the sync's "newer version takes over" is the version in the lease owner name (`sync-<pid>-<version>`, `takeOverLease` in src/store/meta.ts), and mcp.ts and ui.ts do no version or schema check after opening; extending it to the MCP server and the viewer needs new state (a recorded version or a per-process lease), so "the item adds no new state" is false.
- F-6 · Major · Point 4, "the agent … starts the new one" · An MCP server that ends itself in the middle of a session is generally not respawned by the host until the next session, so the agent loses its memory tools for the rest of that session; the alternative the brief already named (defer the swap to the next session start when an older process holds the store) avoids it, and the concept picked the riskier branch without saying why.
- F-7 · Major · Point 2 · Lease plus failed-start backoff plus 24-hour stamp copies the sync's machinery, which exists for a continuously running process; for a daily task, one conditional write that claims `update.checked_at` (or a guarded step after the drain, beside `healVectors`, `suggestLinksSafely` and `proposeRulesSafely` in distill.ts) dedupes concurrent sessions with no new lease, no new backoff key, no new `anyLeaseActive` entry and no fifth detached spawn from the session-start hook.
- F-8 · Major · Point 8 / README.md:446 · The README's headline promise is "No telemetry, no account, no network — except …" and the product is "local by default"; a daily request on by default reverses that line rather than adding a note to the Privacy section, and the concept never states the default of `WIZARDINGCODE_MEM_UPDATE` (on, check or off), a product decision that closes a door once shipped.
- F-9 · Nit · Point 7 · Bringing the five version readers to one rule is hardening moved in from item 2026-11-12-005 that the update does not depend on beyond `stagedVersion`; bundled here, it widens the item and its review for no gain to the hypothesis.
- F-10 · Nit · Point 3, "behind one function, so a signature check can replace the checksum later" · A seam for an out-of-bounds future (signatures are listed as out of bounds); one function is cheap, but the concept should not present it as a requirement.
- F-11 · Nit · Point 1 · `scripts/install.sh` already reaches the latest release through `github.com/<repo>/releases/latest/download` with no API call; reading the tag from that redirect would keep the check on github.com and avoid naming `api.github.com` and its unauthenticated rate limit in the privacy text.
- F-12 · Nit · Points 3 and 7 (altitude) · Part files, streamed hashes, stale-part sweeps, 10-second timeouts and "blanks, carriage returns and newlines" are implementation mechanics in a brainstorm concept whose open questions are who replaces what and when; the brief already flagged this altitude problem.
- F-13 · Nit · Point 5, "each replacement writes one line to the log" · src/util/log.ts has only `logError` (per the brief); a success line needs a new log function, and the concept does not name it.
