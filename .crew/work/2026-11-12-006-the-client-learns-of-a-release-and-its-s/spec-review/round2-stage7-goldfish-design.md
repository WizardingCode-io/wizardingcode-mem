## Findings
- F-1 · Major · Design 2, table row order ("the last event is a failure" before "the latest is higher") and the doctor bullet · once a check has recorded a newer release, any later failed check (a flaky network, a captive portal, a corporate block on github.com, a 429) changes `status` to "could not check …; last known 0.10.0", leaves out the commands and turns `doctor`'s `update` check from `warn` to `ok`; under hourly retries the notice flips on and off, and on a network that keeps failing it never comes back, so G-1 fails exactly where people are least likely to notice a release by other means.
- F-2 · Major · Design 1 "The mode" with J-3 and the README bullet · the mode comes from the process's own environment, so `status` typed in a shell that exports `WIZARDINGCODE_MEM_UPDATE=off` (or `CI`) prints `update: off`, while the `distill` that the agent's hooks start (often from a GUI-launched agent that does not inherit that shell's environment) still sends the request; for a privacy switch the report can say "off" while requests are going out, and the spec neither names this nor makes `<data dir>/env` the documented way to turn it off.
- F-3 · Major · Problem 3 and G-4 / J-6 · the hand-over runs only in a copy that already contains this item, so every channel copy shipped before it (0.8.x Homebrew and downloaded binaries) still fails with `SchemaTooNewError` against a store a newer staged binary migrated; the first copies that benefit are those released after this item, and neither Limits nor Risks says so, which overstates what the item fixes.
- F-4 · Nit · J-4 and Design 2 (`update` with mode `off`) · the fixed hint "set WIZARDINGCODE_MEM_UPDATE=check in <data dir>/env to turn it on" does nothing when the `off` came from the environment, which wins over the file; the line does not say where the value came from.
- F-5 · Nit · Design 1 "One check" · `attemptAt` is written before the request, so in a data directory that cannot be written the check throws every time and is only logged, and `status` stays at "not checked yet" with no reason; the spec does not name this case.
- F-6 · Nit · Risks "Not verifiable here" · the probe says it did not test Bun's `fetch` with `redirect: "manual"` inside a compiled binary, which is what ships; this can be checked by building, but it is in neither Risks nor an acceptance criterion (the AC-18 e2e covers the hand-over, not the request).
- F-7 · Nit · Design 2 `stagedFacts` · `stagedVersion` is said to be "remembered for the process" but the spec does not say what key it is remembered by, and `stageBinary` calls it too; it should be kept by path so a later read cannot get a stale answer. Even when this process is the staged binary, `status` from it still spawns its own `--version` (up to 10 s), which the NFR does not count.
- F-8 · Nit · AC-12 · it says `checkForRelease` makes no request "when `CI` is set" with no exception, while Design 1 and AC-25 make a forced `update` ask in CI; the two criteria read as contradicting each other.
- F-9 · Nit · Heilmeier Q7/Q8 · how long the work takes and what the midway check is are not stated; "one item and one pull request" covers cost, and the only check of success named is the author reading `update` on the first release after the merge.

## Not answerable
- github.com's behaviour under rate limiting, while a release's assets upload, and after `gh release edit … --latest` · needs live network and a real release; the spec already says these cannot be verified here.
- Whether Bun's `fetch` honours `HTTPS_PROXY` in the compiled binary (Limits) · I ran nothing.
