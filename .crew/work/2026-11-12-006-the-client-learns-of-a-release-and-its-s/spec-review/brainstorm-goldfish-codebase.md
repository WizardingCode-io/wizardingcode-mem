## Findings
- F-1 · Blocker · Hypothesis 4 · "the store's recorded binary version" does not exist: no binary version is written to the store anywhere in src/. The sync's "newer version takes over" is only the lease owner string `sync-<pid>-<version>` (src/sync/context.ts:34) compared by `takeOverLease` (src/store/meta.ts:146-163). The MCP server and the viewer hold no lease and have no owner, so there is nothing for them to compare; the concept adds new state while saying it adds none.
- F-2 · Major · Hypothesis 4 · The takeover it means to extend does not happen after an update today. `startSync` returns "running" without spawning while the old lease is unexpired and its pid is alive (src/sync/spawn.ts:79-82). So a newer binary never starts a newer `sync --auto` to take over, and the old sync keeps running until its 15-minute idle exit, or forever while it stays busy. A person debugging this sees the old version in the lease and nothing that says why.
- F-3 · Major · Hypothesis 4 · SchemaTooNewError reaches the long-lived processes unevenly. The viewer (src/ui/server.ts:216) and the sync (src/cli/commands/sync.ts:29) each open the store once and never check user_version again, so they do not refuse a migrated store: they keep writing to it silently. The MCP server opens per call (src/modules/memory/tools.ts:232) and logs `mcp <tool>` errors on every call without ending. On-call needs to know which of these three happened, and the concept says none of them.
- F-4 · Major · Hypothesis 5 ("each replacement writes one line to the log") · There is no non-error log. `logError(scope, error)` (src/util/log.ts:44) writes only errors, to `<data dir>/logs/wizardingcode-mem.log`, and on rotation (1 MB) keeps a single previous file, wizardingcode-mem.log.1. A success line needs a new writer, and a busy sync's error lines can rotate the update's line away.
- F-5 · Major · Hypothesis 2/5 · Only `update.latest` and `update.checked_at` are kept, with no record of the last failure (when, at which step, and the reason). `status`, `doctor` and About therefore cannot say "the last attempt failed: checksum mismatch". The sync's model for this is `sync.last_failed_start` with `reason` and `failures` (src/store/meta.ts:228-261), and status and doctor read it.
- F-6 · Major · Hypothesis 2 · It never says whether a failed check sets `update.checked_at`. If it does, a failure stays hidden for 24 hours. If it does not, every session start spawns again until the unspecified "failed-start backoff" engages. Either way the person cannot tell "checked, nothing new" from "could not check".
- F-7 · Major · Hypothesis 1 · Everything that goes wrong (offline, 403/429 rate limit, captive-portal HTML, a bad tag) becomes one "unknown". Unauthenticated GitHub API calls are limited to 60 per hour per IP, so behind a shared NAT the answer is often 429. Status and doctor need the cause kept, as download.ts keeps its reasons (src/embed/download.ts:139-160).
- F-8 · Major · src/util/self.ts:14-20 · `spawnDetached` sends the child's stdin, stdout and stderr to "ignore". If `update --auto` dies before reaching `logError` (a Bun panic, the downloaded binary killed during its `--version` probe, OOM), it leaves no trace. The concept has the process write no step marker in meta (for example "downloading v X since T") that status or doctor could show.
- F-9 · Major · Hypothesis 2 · `update.lease` gets no owner format. `pidOfOwner` recognises only a bare pid, `ui-` and `sync-` (src/store/meta.ts:71). An owner such as `update-<pid>` would count as "names no process" and be trusted until it expires (src/store/meta.ts:80-83). A killed updater then blocks the next check for the whole lease, and nothing can say which pid held it.
- F-10 · Major · Hypothesis 2 · "a failed-start backoff, as meta.ts does" cannot be reused as it stands. `readFailedStart`, `writeFailedStart` and `clearFailedStart` hardcode `SYNC_LAST_FAILED_START` (src/store/meta.ts:235-265); only `parseFailedStart` and `failedStartBackoffMs` are generic.
- F-11 · Major · Hypothesis 3 / src/install/binary.ts:34-56 · `stageBinary` does not return the version it replaced. `stagedVersion` is not exported, so a "from X to Y" log line needs another `--version` spawn. When the source resolves to the target it returns `{kept:null}` without copying (line 44), and the caller cannot tell that from a real replacement. It writes nothing anywhere. It also uses a fixed temporary name, `${target}.new`, where the plugin script uses mktemp (wizardingcode-mem.sh:52), so overlapping writers can collide.
- F-12 · Major · src/install/binary.ts:44-54 · When the target is the running executable, `stageBinary` replaces it by `renameSync` over it. On macOS and Linux the running process keeps the old inode, so whatever reports from that process (`pkg.version`) shows the old version after the replacement. The concept never says the running and staged versions must be shown separately once a replacement has happened.
- F-13 · Major · Hypothesis 5 · `status` reports `pkg.version` of whatever binary the person typed (src/status/report.ts:507). For Homebrew or npm that is not the staged `<data dir>/bin` binary the agents' hooks run. `status`, `doctor` and About need three things shown apart: the running version, the staged version and the latest known. Today no doctor check shows the staged binary's version at all (src/doctor/checks.ts).
- F-14 · Major · Hypothesis 5 · "the one command for this install's channel" has nothing to read: no code records or detects the install channel (no channel, Homebrew or npm marker in src/). Telling plugin, direct, install.sh, Homebrew and npm apart is unspecified, so a wrong hint is likely.
- F-15 · Major · Hypothesis 3 / who moved the binary · Six writers replace `<data dir>/bin/wizardingcode-mem`: the plugin script (silent, `> /dev/null 2>&1`, wizardingcode-mem.sh:76), the npm shim, the OpenCode binary.js, install.sh, `install` through `stageBinary`, and now `update`. Only the new one would log. When the binary is wrong on someone's machine, nobody can tell which writer put it there or when.
- F-16 · Major · Hypothesis 7 · All five readers exist, but they do not share the rule today. `installed()` in the shell template has no timeout and no exit-code check, and does not strip CR (wizardingcode-mem.sh:67-69). `version_of` in install.sh takes `head -n 1`, so a multi-line answer passes, and it has no timeout and no exit-code check (install.sh:95-98). OpenCode's `installedVersion` has no timeout (plugins/opencode/binary.js:31). The npm reader checks exit and timeout but not the shape (npm/bin/wizardingcode-mem.js:32-35). Only `stagedVersion` matches the stated rule. POSIX sh on macOS has no `timeout(1)`, so "within 10 seconds" in the two shell readers needs a stated way to enforce it.
- F-17 · Major · Hypothesis 2 / tests · The hook starts background work only through injected `HookDeps` (spawnDistill, spawnViewer, spawnSync: src/hooks/handle.ts:28-36), with test switches DISTILL=off, UI_AUTO_OPEN=off and SYNC=off. The concept names no `spawnUpdate` dependency and does not say that `WIZARDINGCODE_MEM_UPDATE=off` is the tests' switch, so hook tests could make real requests to api.github.com.
- F-18 · Nit · Hypothesis 2 · The session-start hook already starts detached work under different guards: the viewer is skipped on `source === "resume"`, CI, SSH or no display (src/cli/commands/hook.ts:67-74, handle.ts:204); the sync runs on session-start and prompt under SYNC=off. The concept does not say which of these guards the update check takes, for example whether it runs in CI.
- F-19 · Nit · Hypothesis 2 · `anyLeaseActive` counts drain, backup, history, embed, embed download, sync and the knowledge leases (src/store/meta.ts:298-310), and not `ui` or a future `update.lease`. The concept does not say whether a move, restore or compact must wait for an update in progress.
- F-20 · Nit · Hypothesis 3 · "a sweep of stale parts, as download.ts does": `sweepStaleParts` is tied to the model's folder and `MODEL_FILE` prefix (src/embed/download.ts:65-83), and its size check depends on a size pinned in code, which a release asset does not have. These parts need generalising, not reusing.
- F-21 · Nit · Hypothesis 1 · Release tags are `v<version>` (CLAUDE.md, release flow), and `isVersion` rejects a leading `v` (src/util/version.ts:1). The concept should say the `v` is stripped, or every check will read as "unknown".
- F-22 · Nit · Hypothesis 5 · About is a static card showing `state.version` and links (ui/src/components/settings/About.vue:16), and no API field carries the latest version or the check time. The viewer must read these from meta, since nothing may leave for the network from the viewer.
- F-23 · Nit · Hypothesis 3 · The `--version` probe of a freshly downloaded binary can be slow on macOS the first time it runs (the system scans new executables), and the concept gives no distinct failure reason for a timeout, as opposed to a wrong answer, to log.
