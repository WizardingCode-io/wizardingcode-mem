## Findings
- F-1 · Blocker · Hypothesis 4 · The concept says the item "adds no new state" and that the MCP server and the viewer end themselves when they find "the store's recorded binary version" higher than their own. No such record exists. The sync's "a newer version takes over" works only through the version in the lease owner's name (`sync-<pid>-<version>`, `takeOverLease` in src/store/meta.ts:136-163), so a new meta key and a rule for who writes it are needed. It is also unsaid what happens to that key after `install --force` goes back to an older version: if it stays higher, every older process keeps ending itself.
- F-2 · Major · Hypothesis 4 / src/ui/server.ts:216, src/cli/commands/sync.ts:29 · The viewer and `sync --auto` each hold one database connection open for their whole life, and `SchemaTooNewError` is checked only when a connection opens (db.ts:194, 457). After the new binary's next hook migrates the store, these old processes go on reading and writing the newer schema with no refusal. A builder who trusts "the old process gets SchemaTooNewError" will miss old code writing rows into the new schema.
- F-3 · Major · Hypothesis 4 · "The agent starts the new one" is not backed for the MCP server. A stdio MCP server that exits in the middle of a session is generally not restarted by the host until the session restarts. Ending `mcp` itself when a newer version appears removes the memory and knowledge tools for the rest of every open session on that machine, on the day of every release.
- F-4 · Major · Hypothesis 1-2, rate limit · Unauthenticated `api.github.com` allows 60 requests per hour per IP. Many machines behind one office NAT, or self-hosted CI behind one egress, will get 403/429 in the morning burst. The concept does not say whether "unknown" sets `update.checked_at`. If it does not, every session start on a limited machine spawns another check, which uses up the shared quota faster. If it does, `update.latest` is lost or a day is skipped. Either way the failure needs its own backoff, and jitter, which the sync's failed-start backoff (for a process that failed to start) does not give.
- F-5 · Major · Hypothesis 2-3, CI machines · A CI job starts from a fresh data directory with no `meta` timestamp, so every job that runs an agent session checks, and replaces the staged binary CI pinned with the newest release (about one binary's size downloaded per job). That makes CI runs depend on the release date, and the detached process can be killed mid-download when the job ends. Nothing says the update is off or check-only under CI (`CI=true`) or on an ephemeral home.
- F-6 · Major · Hypothesis 2 / tests rule · The project's tests stop background work with `WIZARDINGCODE_MEM_DISTILL=off` and `UI_AUTO_OPEN=off` (hook.ts:46-73). The concept names only `WIZARDINGCODE_MEM_UPDATE`, default on. As written, existing hook tests would start real `update --auto` processes that reach GitHub and can replace a staged binary. The concept must say which switches stop the spawn and that the default under test is no request.
- F-7 · Major · Hypothesis 2, clocks · "Older than 24 hours" with `now - checked_at` never fires again if `checked_at` is in the future: the clock went back, a VM snapshot was restored, or the store was restored from another machine. Updates then stop with no sign. A timestamp in the future must count as stale, and the comparison should run on the same clock that wrote it.
- F-8 · Major · Hypothesis 3 / src/install/binary.ts:45-54 · `stageBinary` reads the version and then copies, with no lock, and uses a fixed temporary name `${target}.new`. Meanwhile the plugin script (wizardingcode-mem.sh:64 `mv -f`), the npm shim and `install` each write the same file under their own read-then-write. A concurrent `update --auto` and a plugin session-start fetch can put an older binary over a newer one, which breaks forward-only and makes the update repeat the next day. Two `stageBinary` callers can also interleave on `.new` and rename a torn binary. `update.lease` serialises update processes only, not the other writers.
- F-9 · Major · Hypothesis 3, a bad release · Within 24 hours every self-updating machine runs the new release: there is no staged rollout, no hold window and no remote "skip version" list. Because every channel is forward-only, the only fleet-wide way back is a higher release, plus `install --force` by hand on each machine. If the bad release breaks `update --auto` or the hook's spawn, machines stop following releases. If it migrated the store, an older binary refuses the store even after `install --force`. The concept names none of this.
- F-10 · Major · Hypothesis 3, an attacker with release assets · `checksums.txt` comes from the same release and the same TLS channel as the binary, and the macOS signing is ad hoc (release.yml:4). So anyone who can publish a release (a stolen token or workflow), or a TLS-intercepting corporate proxy, gets their code run on every machine with the update on within a day. The `--version` check runs that code immediately in the detached process, with the person's environment. Publishing `v999.0.0` would also lock out every real fix on every channel, since all of them are forward-only. Putting signatures out of bounds leaves this as the item's main risk, and the concept never says it.
- F-11 · Nit · Hypothesis 2, several sessions at once · Every session start that sees a stale timestamp spawns `update --auto` before any of them takes the lease. That is N process starts on top of the distill, viewer, sync and backup spawns already on that path, which the lease reduces to one survivor only after the fact. The concept also does not say that the lease is renewed during a download that can take longer than its lifetime on a slow link, or that `anyLeaseActive` (move, restore, compact) should or should not count it.
- F-12 · Nit · Hypothesis 1, a partial or hostile answer · Nothing caps the API body or sets a deadline for the whole request ("a short timeout" may only cover the connection). The asset has no pinned size, unlike `MODEL_BYTES`, so a stream that never ends fills the disk until the idle timeout (download.ts:130, which limits stalls, not total time). `isVersion` accepts a pre-release suffix (version.ts:1), so "a plain version" needs its own stricter test.
- F-13 · Nit · Hypothesis 3, disk full · Downloading to a part file and then `stageBinary` copying it to `.new` writes the binary twice. A copy that fails partway (ENOSPC) leaves `bin/wizardingcode-mem.new` behind, because stageBinary does not clean up and the embed sweep only matches the model's part-file prefix. If the part file is not on the same filesystem as `bin/`, an atomic rename is not available.
- F-14 · Nit · Hypothesis 1 · GitHub's `releases/latest` returns the most recently published non-pre-release, not the highest semver. A backport patch on an older line becomes "latest". That is harmless to forward-only, but `status`, `doctor` and About would show a "latest" below the running version.
- F-15 · Nit · Hypothesis 5 · The GitHub release is created before distribute.yml publishes to npm, the tap and the marketplace. For a while, "the one command for this install's channel" (for example `brew upgrade`) names an upgrade that does not exist yet on that channel.
