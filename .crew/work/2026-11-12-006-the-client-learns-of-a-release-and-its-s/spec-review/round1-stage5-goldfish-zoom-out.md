## Findings
- F-1 · Major · plan.md Phase 1, `writeState` ("<file>.<pid>.tmp, mode 0600, rename"); spec Design 1 "State" · `src/util/atomic-write.ts` already has `writeFileAtomic` (a 0600 temporary file, then a rename), and the plan writes a second version by hand. Its fixed `.update.json.tmp` name with `flag: "wx"` could clash when `distill` and `update` write at the same moment, so a builder would either copy it or call it and hit that clash. The design should say to reuse it, and to give it a per-process temporary name if concurrent writers matter, not add a parallel helper.
- F-2 · Nit · plan.md Phase 2, "it moves to or is imported from where it lives" · `agoLabel` is a private function in `src/doctor/checks.ts:178`, so it cannot simply be imported. Importing it from `src/update/` would also tie the update folder to doctor. The plan should decide: move it to `src/util/` and have both callers import it from there.
- F-3 · Nit · plan.md Phase 1, `PLAIN` "exported from `check.ts`'s sibling" · `src/util/version.ts` already holds the project's version shape (`isVersion`). A second, stricter regex in `src/update/` is justified for the redirect and the strict read, but it should sit beside `isVersion` with a note on why it is narrower, so there is one place for version shapes.
- F-4 · Nit · spec Design 1, "`check.ts` and `state.ts` ... name nothing of this product" · Making these two files product-neutral by taking the repository and mode as parameters serves a reuse no requirement states. Product-specific constants in a module only this product calls would be simpler. The parameters do help tests, but the stated reason is speculative.
- F-5 · Nit · spec Design 1 `due` / AC-11 · For one GET a day that runs only when a turn ends, the six-step exponential backoff, the 60 s in-flight window and the future-time healing take up a large share of the tests (the plan's `due` table). A flat "1 h after a failure, 24 h after a success", with any future time treated as due, would meet G-1/G-2 just as well. No measured need for the backoff curve is given.
- F-6 · Nit · spec Design 3, last paragraphs (`realpathSync` on both sides, `<target>.<pid>.new`, `lstat` sweep of day-old files, "removed first if it exists") · These are file-system implementation steps in the spec's architecture section and repeat what the plan's Phase 4 says. The spec should state the rule (one temporary file per process; stale ones cleaned; never followed through a link) and leave the mechanics to the plan.
- F-7 · Nit · spec Design 3 "runs the staged binary's `--version` at most twice (once to decide, once for the report)" · `reconcile` has already read the staged version when `status`/`doctor`/`update` run in the same process, yet the report spawns the staged binary again. Passing the value along, or caching it in the process, would shorten the data path and drop the second spawn of up to 10 s.
- F-8 · Nit · plan.md Phase 5 tests, "the command names are taken from the source text of `src/cli/main.ts` ... by a regular expression over the object literal" · Parsing source text with a regex to list the commands is fragile. The new `reconciled.ts` leaf exists only because `main.ts` runs when it loads. Moving the command-name list into that leaf, or another leaf, would let the test import it.
- F-9 · Nit · plan.md Phase 4 test paragraph, "(with a spy on `renameSync` through a source that records the temporary name, or by listing the folder from a `copyFileSync` wrapper is not available)" · This sentence does not parse. Of the three test approaches it mentions, only the planted link is a real choice. The other two should be cut.
