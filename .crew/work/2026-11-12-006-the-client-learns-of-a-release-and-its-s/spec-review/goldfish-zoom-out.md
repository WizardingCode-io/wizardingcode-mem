## Findings
- F-1 · Major · spec.md Alternatives / Design 3 · The Alternatives never weigh the simplest answer to Problem 3: the older copy only tells, the same way D-3 makes the newer copy only tell (a second line naming the staged path, or the SchemaTooNewError text naming `<path> doctor`). The hand-over brings `decide` with its root and owner rules, `WIZARDINGCODE_MEM_HANDED`, the `reconciled.ts` leaf, `COMMAND_NAMES`, a new Limit ("runs the staged file") and an e2e suite. Without that comparison a reader cannot tell whether running a binary from the data directory on every `status`/`doctor`/`update`/`ui` is worth its cost over a one-line notice.
- F-2 · Nit · spec.md Design 1 "The state" / plan.md Phase 2 · `failures` is counted, validated, tested ("a failure … counts") and reset, but nothing reads it: `due` uses a flat hour, and neither the lines nor the report show it. It is left over from the rejected 1-2-4-…-24 h backoff and could be dropped.
- F-3 · Nit · spec.md Design 1 "The request" and AC-10 vs plan.md Phase 2 `latestRelease` · The spec says `Location` is "matched whole", but the plan compares it "after lower-casing the owner and repository on both sides". The two disagree on whether a `Location` whose letter case differs from the constant passes. The probe shows github.com echoes the request's case, so the exact match the spec states is enough.
- F-4 · Nit · spec.md Design 3 "Whether" vs plan.md Phase 5 `reconcile` · The spec checks the owner of `<data dir>/bin` "or, when it does not exist, its nearest existing parent", but the plan uses `binOwner` null when `bin` is missing. The plan's version is enough because with no `bin` there is nothing to hand over to, so the spec's nearest-parent rule is over-built and the two should say the same thing.
- F-5 · Nit · spec.md AC-25 vs plan.md Phase 4 `update.ts` · The spec says `update` "exits 1 only when its check failed", but the plan also exits 1 when the state cannot be written ("could not record the check").
- F-6 · Nit · spec.md Design 2 vs plan.md Phase 3 · The parameter that says whether this call asked is named `checked` in the spec's `updateReport` signature and `asked` in the plan's.
- F-7 · Nit · plan.md Phase 3 · The `StagedFacts` interface has no `exists`, but the prose below it adds `exists: boolean`. The test line promises `agentsLine` "in its five cases" and then lists six.
- F-8 · Nit · spec.md Design 2 `stagedFacts` / plan.md Phase 3 · `stagedFacts` always runs the staged binary's `--version`, even when `isSelf` is true and the answer is already `pkg.version`. So every `status` and `doctor` typed through the staged binary or a hook-run path starts itself once for no reason.
- F-9 · Nit · plan.md Phase 1 `src/util/ago.ts` · `ago` moves to `src/util/` for reuse, but `agoLabel` in `src/doctor/checks.ts:178` does the same job and stays. The new `update` check in that same file will then use one form and the `backups` check the other.
- F-10 · Nit · spec.md Design 1 and 3 (`due` order, regex digit limits, `decide`/`handOver` signatures) · The spec holds algorithm- and signature-level detail that the plan repeats. Keeping two copies is why F-3, F-4 and F-6 have already drifted apart. The spec could state the rules and leave the step order and signatures to the plan.
- F-11 · Nit · plan.md Phase 4 / Phase 5 `COMMAND_NAMES` · The full list of commands in a leaf, with `main.ts`'s table typed by it, exists mainly so that a test can check `reconciles` is true for exactly four names. A check of `RECONCILED` and the `ui --auto` case would cover the same rule without a second list of commands to keep in sync.
