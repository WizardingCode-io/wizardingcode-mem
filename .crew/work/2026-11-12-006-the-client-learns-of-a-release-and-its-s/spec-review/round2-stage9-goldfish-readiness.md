## Findings
- F-1 · Major · Phase 4, `src/doctor/checks.ts` ("a check `update` after `backups`") · tests/unit/doctor-knowledge.test.ts:69 asserts that `knowledge` comes right after `backups`, so putting `update` there breaks an existing test the plan does not list; `bun run test` fails unless the position changes or the test is added to the Files table.
- F-2 · Major · Phase 4, doctor check, and Files ("`src/ui/server.ts` [is] not changed") · the viewer's `GET /api/doctor` calls `runChecks` (src/ui/server.ts:601), so the new check runs `stagedVersion` through a synchronous `Bun.spawnSync` (up to 10 s) inside the long-running viewer, and the per-process memo means the viewer keeps showing an old staged version after another process stages a new one; the spec says the viewer's side is the next item, and the plan never decides whether the viewer gets this check or how the memo is invalidated there.
- F-3 · Major · Phase 1, last paragraph ("`src/util/atomic-write.ts`'s existing test gains") · there is no test for src/util/atomic-write.ts (the only `writeFileAtomic` test, tests/unit/knowledge-repo.test.ts:1815, tests it through the knowledge module's re-export), so the plan names no file and the engineer has to choose where the new test goes.
- F-4 · Major · Phase 2 tests, AC-10 ("a `fetch` that never settles with `timeoutMs: 20` gives `timed out`") · the design says the timeout comes from an `AbortController` signal passed to fetch, but a fake that never settles ignores the signal, so built as written the test hangs; the plan must say either that the fake rejects when its `signal` aborts or that `latestRelease` races the fetch against the timer (and that the timer is cleared after the fetch settles, so `distill` does not stay alive 5 s).
- F-5 · Major · Phase 5 tests (AC-23 "`--version`, `--help`, no command and an unknown command never reach it") · the only case is `--version` with staged `0.0.1`, which reconciliation would not hand over to anyway, so it cannot fail; `--help`, no command and an unknown command have no case. A case with staged `99.0.0` and no `called.txt` is needed for each.
- F-6 · Major · Phase 5 tests (AC-18 "`install` hands over through the same function") · no test checks that `install`'s hand-over now passes `WIZARDINGCODE_MEM_HANDED=1` through `handOver`, or that `install`'s `run` deletes the variable; tests/e2e/install-forward.test.ts is declared unchanged, so an `install` that still calls `Bun.spawnSync` itself passes the suite.
- F-7 · Nit · Files table vs Phase 1 vs spec Design 3 · the Files table says "`stageBinary` is not changed", Phase 1 says it deletes the memo entry, and the spec says "`stageBinary` and its callers are not changed by this item" while the plan also changes its caller `binaryOrHandOver` in install.ts; the three statements disagree.
- F-8 · Nit · Phase 5 `reconcile` vs spec Design 3 "Whether" · the spec judges the owner of the nearest existing parent when `<data dir>/bin` is missing; the plan sets `binOwner` to null (no skip) in that case.
- F-9 · Nit · Phase 5 `reconcile` ("reads `stagedVersion(path)` once") · the plan does not say whether `path` is the real path it gathered or `stagedPath(dataDir)`. The memo is keyed by that text, so passing the real path while `stagedFacts` passes `stagedPath` runs `--version` twice, against the spec's NFR of once.
- F-10 · Nit · Phase 3 `update/report.ts` · the `StagedFacts` interface is printed without `exists`, which the prose adds two paragraphs later; the spec's `updateReport(… checked)` and `updateLine(report)` differ from the plan's `asked` and its separate input object.
- F-11 · Nit · Phase 3 tests ("`agentsLine` in its five cases") · the list in brackets has six cases.
- F-12 · Nit · Phase 3, `updateLine` · a state that `readState` accepts with `latest` null and `checkedAt` set (or with only a `failedAt` older than `checkedAt` and no latest) matches no row of the spec's table, so its line is left to the engineer.
- F-13 · Nit · Phase 4, `src/cli/commands/update.ts` · `updateReport` needs `facts` and `running`, but the step does not say that `update` calls `stagedFacts(dataDir)` and passes `pkg.version`.
- F-14 · Nit · Phase 4, `status.ts` (report built "before the store's `try`") · a throw from `stagedFacts` (for example `realpath` refused) escapes to `main`'s handler and ends `status` with no output; the plan does not say whether a failing update report should stop `status`.
- F-15 · Nit · Phase 4 tests, AC-26 for `status` and the `doctor` `runCli` case · the state's `latest` is not given; the "no `bin`" case and the child-process `doctor` case both need a `latest` higher than `pkg.version`, not just higher than `0.0.1` or the fixed `facts` version.
- F-16 · Nit · Phase 2, `latestRelease` (lower-cased owner and repository) and Phase 6 (README test only for `shell` true commands; "Nothing leaves your machine for knowledge" kept) · both loosen the spec's wording ("`Location`, matched whole"; "every command of `CHANNEL_COMMANDS`"; "no longer says 'nothing leaves your machine'") without saying the spec is being narrowed.
- F-17 · Nit · Phase 1, `atomic-write.ts` ("Nothing else changes") · with a temporary name per process, the `rmSync` before the write no longer clears a leftover from a crash, so stale `.<base>.<pid>.tmp` files build up beside update.json, servers.json and the received knowledge files; the plan does not say whether that is accepted.
- F-18 · Nit · Phase 3, `channels.ts` · the exact `channel` labels printed in `  <channel>: <command>` and the plugin sentence are not written out; "the four lines of the spec" leaves the label text to be inferred from the spec's bullets.
