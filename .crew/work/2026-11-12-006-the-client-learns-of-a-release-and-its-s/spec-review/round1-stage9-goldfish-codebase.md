## Findings
- F-1 · Blocker · Phase 3, `src/doctor/checks.ts` bullet · Says `context.env` is "a new optional field of `DoctorContext`, defaulting to `process.env` in `src/doctor/context.ts`". It already exists: `env?: Record<string, string | undefined>` at src/doctor/checks.ts:104, set to `process.env` at src/doctor/context.ts:38, and read as `context.env ?? process.env` at checks.ts:638 and 928. The Files row "`src/doctor/context.ts` Modify" therefore has nothing to change.
- F-2 · Major · Phase 2, "Ages use the project's existing `agoLabel`" (Files row says `ageLabel`) · `agoLabel` is a private, unexported function in src/doctor/checks.ts:178. It works in minutes, so it prints "0 min ago" and gives negative output for a future time. The plan leaves "moves to or is imported from where it lives" undecided. Importing it from `src/doctor/checks.ts` would pull the store, modules and sync into `src/update/report.ts`, which breaks AC-20's intent while still passing its textual test. It also ignores `ago(now, at)`, which is already exported from src/status/report.ts:151 and handles seconds and null.
- F-3 · Major · Phase 3, `src/status/report.ts` bullet · `StatusReport` gains `update`, but the plan does not say whether `statusReport()` computes it or the field is optional and only `status.ts` fills it (as with `history?`). `statusReport` also serves the viewer's `/api/status` (src/ui/server.ts:767) and about 30 test call sites. The first choice spawns the staged binary's `--version` on every viewer poll and every test. The second leaves `--json` and the viewer different. `src/ui/server.ts` is not in the Files table either way.
- F-4 · Major · Phase 3, `src/doctor/checks.ts` bullet · `updateReport` needs `running`, `staged`, `stagedPath` and `isStaged`, but the doctor check is described as built "from `context.dataDir`, `context.now` and `context.env`" only. Nothing says the check spawns `stagedVersion` or how it computes `isStaged` (realpath of `process.execPath`). `runChecks`' contract ("Looks, and changes nothing", checks.ts:1076) and its in-process tests are affected.
- F-4b · Major · Phase 2 and Files row for `src/update/report.ts` · The Files table promises `updateLine` and `agentsLine`, and spec AC-14 tests `updateLine` as "the only place these texts are written". The plan never gives their signatures or inputs, and its report test targets `updateReport` only.
- F-5 · Major · Phase 2 line-1 order vs Phase 3 `update` command · Line 1 puts `ci` before any state, so `wizardingcode-mem update` run in CI makes its forced request (the plan allows force in mode `ci`) and then prints "update: not checked in CI". That contradicts what it just did and contradicts spec J-4 and Design 2 ("in CI it checks").
- F-6 · Major · Phase 3, `src/cli/commands/update.ts` · Spec J-4 says that with the check off, `update` "prints that the check is off and how to turn it on". The plan defines no such sentence (the only off text is `update: off (WIZARDINGCODE_MEM_UPDATE)`). It also does not say whether the four channel commands are printed when off.
- F-7 · Major · Phase 1, `writeState` · The data directory is never created (no `mkdirSync`). A forced `update`, or a `distill` check, on a machine with no `<data dir>` yet throws ENOENT. In `update`, nothing catches it, so main.ts:96 prints a raw error and exits 1. The plan also skips the existing `writeFileAtomic` (src/util/atomic-write.ts) without saying why.
- F-8 · Major · Phase 5, `decide` (`uid`, `binOwner`) · On Windows `process.getuid` is undefined, so `uid` is null, while `lstat().uid` is 0. The rule "binOwner is a number other than uid" then always answers `none`, so Windows channel copies silently never reconcile; the plan does not say whether that is intended. On POSIX, `getuid` is the real uid while the spec says "the effective user" (`geteuid`).
- F-9 · Major · Phase 3, `tests/preload.ts` · `process.env.WIZARDINGCODE_MEM_UPDATE ??= "off"` keeps a developer's shell export of `check`. Every hook-spawned `distill` in the suite would then make real github.com requests, against G-2 ("never made by the project's own tests"). The preload already deletes other behaviour variables from the shell for this reason (`WIZARDINGCODE_MODULES`, tests/preload.ts:40). Separately, `spawnCli` (tests/helpers/cli.ts:52) inherits nothing, and the plan only adds a comment there rather than any guard.
- F-10 · Nit · Phase 1, `PLAIN` · "exported from `check.ts`'s sibling so both use one" does not say which file exports it, and neither Files row lists `PLAIN`.
- F-11 · Nit · Phase 1, settings · Adding `update` to `Settings` breaks the whole-object `toEqual` defaults test at tests/unit/settings.test.ts:27-45, and the plan's list of settings.test.ts changes does not name it.
- F-12 · Nit · Phase 4, `tests/integration/install.test.ts` paragraph · The sentence "(with a spy on `renameSync` … or by listing the folder from a `copyFileSync` wrapper is not available)" is garbled, and it leaves the choice of method open before settling on the planted link. The plan also does not say what `stageBinary` returns when `known` is newer (presumably `kept: known`).
- F-13 · Nit · Phase 4, temporary name · The plan runs `rmSync(…, { force: true })` and then a plain `copyFileSync`, which still follows a link planted between the two calls. Spec Design 3 says the file is "never written through a link"; `fs.constants.COPYFILE_EXCL` would close that gap.
- F-14 · Nit · Phase 5, `handOver` · Bun's `spawnSync` `exitCode` can be null (killed by a signal), and the plan does not keep install's current `?? 1` (install.ts:250). The spawn-failure text also changes from `wizardingcode-mem install: could not run` to `wizardingcode-mem: could not run` without saying so.
- F-15 · Nit · Phase 5 · `install` is not reconciled, so the `WIZARDINGCODE_MEM_HANDED=1` it now passes to the handed-over staged `install` is never deleted from that child's environment. That is against spec Design 3's "removed from the environment the handed-over command gives its own children".
- F-16 · Nit · Phase 5, `reconcile` · The plan never says how the data directory is found (`defaultDataDir()` or `resolvePaths`). It also leaves `failedAt`-later-than-`checkedAt` undefined when `checkedAt` is null, and `status --json` output in the catch path unspecified.
- F-17 · Nit · Phase 3, doctor test · It says the summary is `1 warning.` and then says the count is asserted elsewhere through `runChecks`. The two statements contradict each other about what the test actually asserts.
