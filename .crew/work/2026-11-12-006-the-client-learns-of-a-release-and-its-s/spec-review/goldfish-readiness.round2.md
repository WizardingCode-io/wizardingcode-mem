## Findings
- F-1 · Major · Phase 3 vs Phase 4 · Phase 3 has `status`, `doctor` and the report's callers read `staged` with `stagedVersion`, but `stagedVersion` is only exported (with its limit) in Phase 4, so Phase 3 does not typecheck as ordered and the phases are not each buildable.
- F-2 · Major · Phase 2, "Ages use the project's existing `agoLabel`" · `agoLabel` is a private function in src/doctor/checks.ts:178, a file that imports src/store, src/modules and src/sync and that itself imports src/status/report.ts; "moves to or is imported from where it lives" leaves the choice open, and importing it would create a cycle (checks → status/report → update/report → checks) and pull the store into src/update; an exported `ago(now, at)` that clamps negative ages already exists in src/status/report.ts:151 and the plan does not mention it (the Files table also calls it `ageLabel`).
- F-3 · Major · Phase 2 / Phase 3, callers of `updateReport` · no function gives the staged binary's path or `isStaged`: binary.ts computes the target inline (with `.exe` on win32), and status, doctor, the `update` command and reconcile each need it plus the realpath comparison, so every caller would write its own copy; doctor's check is told to use only `context.dataDir/now/env`, which do not include running, staged or isStaged.
- F-4 · Major · Phase 3, `src/status/report.ts` · `StatusReport.update` is defined as the report without `lines`, yet `formatStatus(report)` must print the lines and the commands when `out`; the plan does not say where `formatStatus` gets `lines` and `out`, whether `update` is required or optional on `StatusReport` (src/ui/server.ts also calls `statusReport`), or that status.ts assigns it after `statusReport` returns.
- F-5 · Major · Phase 3, `src/cli/commands/status.ts` catch · "in the `catch`, the version line and the update lines are printed on standard output" says nothing about `--json`; as written, `status --json` against a broken store writes plain text to stdout, and the shape for that case is not decided.
- F-6 · Major · Phase 3, `src/cli/commands/update.ts` · J-4 requires that when the check is off, `update` "prints that the check is off and how to turn it on"; the plan only says it prints the report's lines (`update: off (WIZARDINGCODE_MEM_UPDATE)`), with no text for how to turn it on and no exit code for off / off-unknown.
- F-7 · Major · Phase 1, `due` ("as the spec's Design 1") · the rule is not given for a state that has `attemptAt` but neither `checkedAt` nor `failedAt` (the first request killed mid-flight), or `failures > 0` with `failedAt` null after the future-time reset; a reader can make `due` return false forever and the client never checks again; the plan also does not say how "after a success" is told from "after a failure" (`failures > 0` or `failedAt > checkedAt`).
- F-8 · Major · Phase 3 tests, `doctor` case · the sentence says the summary is `1 warning.`, then says the count is not asserted because other checks may warn, then switches to `runChecks` in-process; the assertion to write for AC-15's "exit code stays 0 with that warning alone" cannot be read from it.
- F-9 · Nit · Phase 3, `src/doctor/checks.ts` · `env` is described as "a new optional field of `DoctorContext`", but `env?` already exists (checks.ts:104) and doctorContext already sets it to `process.env` (context.ts:38); a reader may add a duplicate field.
- F-10 · Nit · Phase 1, `PLAIN` · "exported from `check.ts`'s sibling so both use one" does not name the file; the Files table puts `REASONS` in check.ts, and state.ts and check.ts import each other.
- F-11 · Nit · Phase 4 tests · the sentence "(with a spy on `renameSync` through a source that records the temporary name, or by listing the folder from a `copyFileSync` wrapper is not available)" is garbled; only the planted-link assertion that follows can be built.
- F-12 · Nit · Phase 4, `known?: string | null` · the plan does not say whether `known: null` counts as "given" (skip the read, treat as unreadable) or as absent.
- F-13 · Nit · Phase 5, `handOver` · the case where `Bun.spawnSync` returns a null `exitCode` (the child was killed by a signal) is not decided; the current `binaryOrHandOver` uses `?? 1`.
- F-14 · Nit · Phase 5, `decide` · on Windows `uid` is null and the `bin` owner is a number, so `decide` always answers `none`, and a downloaded Windows copy never reconciles; the plan neither states this nor rules it out (the e2e is skipped on Windows), and it does not say what `staged` is when the staged file is missing.
- F-15 · Nit · Phase 2/3, the commands block · the printed format of `CHANNEL_COMMANDS` in `status` and `update` (a heading, indentation, channel labels) is not given, and neither are the signatures of `updateLine` and `agentsLine`, which the Files table lists.
