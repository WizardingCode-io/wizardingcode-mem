## Findings
- F-1 · Major · Phase 1, atomic-write test · The plan says "`src/util/atomic-write.ts`'s existing test gains" two cases, but no test file for atomic-write exists. Its only test is tests/unit/knowledge-repo.test.ts:1810 ("a temporary file name that is already a link is not written through"), which plants a symlink at the fixed `.target.md.tmp`. Once the name becomes `.<base>.<pid>.tmp`, that test still passes but no longer tests anything, and the file is missing from the Files table. The implementer has to guess where the new cases go and will leave the symlink guard with no real test.
- F-2 · Major · Phase 4, doctor check `update` · src/ui/server.ts:601 serves `/api/doctor` from `runChecks`, so the new check also runs inside the long-lived viewer. There it runs the staged binary's `--version` and keeps the answer in the per-process memo for the viewer's whole life, because only a `stageBinary` in the same process clears the entry. The plan says `src/ui/server.ts` "is not changed", and the spec says the viewer is left for the next item. Neither says that the viewer's doctor panel gains this row, or that its version can go stale.
- F-3 · Major · Phase 2, `latestRelease` · The plan never says to clear (or unref) the `timeoutMs` timer once `fetch` settles. main.ts only sets `process.exitCode` and never calls exit, so an armed 5000 ms timer keeps `wizardingcode-mem update`, and every `distill`, alive for up to 5 s after the answer. The plan should state `clearTimeout` in a `finally`.
- F-4 · Major · Phase 2, AC-10 timeout case · The plan's only mechanism is an AbortController "aborted by a timer". A fake `fetch` that "never settles" and ignores `signal` would never reject, so the case hangs instead of giving `timed out`. The plan has to say either that the fake honours `signal` or that `latestRelease` races the call against the timer; otherwise the implementer picks one and the test may not test what AC-10 says.
- F-5 · Major · Phase 5, `reconcile` vs Phase 3, `stagedFacts` · `reconcile` takes "the real path of `stagedPath(dataDir)`" and then calls `stagedVersion(path)`, while `stagedFacts` calls it with `stagedPath`, which is not resolved. The memo is keyed by `target` (src/install/binary.ts), so where the data directory sits behind a symlink (macOS `/var` → `/private/var`, a linked `~/.wizardingcode`) the staged binary's `--version` runs twice. That breaks the spec's NFR "once", and `stageBinary`'s memo deletion misses the resolved key. The e2e realpaths its home, so it cannot catch this. The plan must name which path is the memo key and which path is printed in J-6.
- F-6 · Major · Phase 2, tests/unit/settings.test.ts · Only "the whole-object defaults case (line 27)" is named as gaining `update: "check"`. The "reads the file" case (lines 48–69) also compares the whole `Settings` object with `toEqual` and goes red once `Settings` gains `update`.
- F-7 · Nit · Phase 4, `src/cli/main.ts` · With `"strict": true` (tsconfig.json), typing `COMMANDS` as `Record<(typeof COMMAND_NAMES)[number], …>` makes the existing `COMMANDS[name]` (name: string, main.ts:62) a TS7053 error. The plan does not give the lookup guard that keeps unknown commands at `EXIT_USAGE`.
- F-8 · Nit · Phase 5, `reconcile` · `binOwner` is "the uid of `lstatSync` on `<data dir>/bin` or null when it does not exist". The spec's Design 3 says "or, when it does not exist, its nearest existing parent". The outcome is the same today because no staged file means no hand-over, but plan and spec disagree.
- F-9 · Nit · Phase 3, `src/update/report.ts` · The `StagedFacts` interface in the code block has no `exists` field; the prose then says it "gains `exists: boolean`". Also, the `agentsLine` test is said to have "five cases" but lists six.
- F-10 · Nit · Phase 3, `updateReport` · The plan calls the input `asked?`; spec Design 2 calls it `checked`.
- F-11 · Nit · Phase 4, distill guard · The snippet uses `REPOSITORY`, `defaultDataDir` and `loadSettings` without saying where they are imported from (distill.ts imports none of them today; it uses `resolvePaths`). The doctor check also does not say that its mode comes from `mode(loadSettings(env, dataDir).update, env)`, and checks.ts does not import `pkg` today.
- F-12 · Nit · Phase 2, `Settings.update` · "the raw value … never normalised": `rawSettings` (src/settings/settings.ts:116) trims the environment's value and treats an empty variable as unset, so `loadSettings` does not return the environment value byte for byte. The test "returns the raw unknown value" should expect the trimmed value.
- F-13 · Nit · Phase 1, `src/util/atomic-write.ts` · Removing the fixed-name `rmSync` means a crashed writer's `.<base>.<pid>.tmp` is never cleaned up and builds up beside knowledge entries, `.git` intent records and `servers.json`. The plan does not say this is accepted.
- F-14 · Nit · Phase 4, doctor check `update` · Unlike `knowledge` and the `readingDb` checks, nothing is said to contain a throw from `stagedFacts` or `updateReport`. One exception would end all of `runChecks`, for both `doctor` and `/api/doctor`.
