read: .crew/work/2026-11-12-006-the-client-learns-of-a-release-and-its-s/spec.md (whole), concepts_brief.md (same folder), rubrics/spec-feature.md, rubrics/spec-heilmeier.md, src/install/binary.ts, src/cli/commands/install.ts:170-269, src/cli/main.ts, src/cli/commands/distill.ts, src/hooks/handle.ts:160-200, src/util/self.ts, scripts/install.sh (grep), README.md (grep), CLAUDE.md

## Findings
- F-1 · Blocker · Risks and rollback, "The shape is the one `scripts/install.sh` already relies on" (also concepts_brief.md Analysis) · False: scripts/install.sh:26 fetches `https://github.com/$repo/releases/latest/download/<file>` and lets curl follow it; it never requests `releases/latest` and never reads a `Location` matching `/releases/tag/v<x.y.z>`, so the one piece of evidence offered for the redirect's shape does not exist and the check's core assumption has no backing until the first real release.
- F-2 · Major · Design 1 "Where it runs" and G-1 · The check runs only inside `distill`, and the hook spawns `distill` only after it opens the store and finds queued turns (src/hooks/handle.ts:191). So "it runs whether or not the store opened" never happens on the path that matters: when the staged binary refuses the store (`SchemaTooNewError`, the case used to justify keeping the state outside the store), or when no turn is queued, nothing ever checks. A builder will claim AC-13 is met while G-1 fails in exactly that case.
- F-3 · Major · Words used here, "staged binary … the one copy the agents' hooks and MCP servers run, whatever channel put it there" · False for `install --binary <path>` (src/cli/commands/install.ts:208-216), where the hosts run `<path>` and not `<data dir>/bin`. For such installs, reconcile stages a channel copy that no agent runs, and `status` prints "the agents run <v>" about the wrong file. The spec neither excludes these installs nor detects them.
- F-4 · Major · Design 3, `decide({ … uid, binOwner })` and the staging rename · Windows is not addressed. `process.getuid` and the directory owner have no POSIX meaning there, so the root and owner rules are undefined. On Windows, `renameSync` over a staged .exe that a running `mcp` or viewer holds open fails, so every reconciled command from a downloaded Windows copy would print the staging-failure sentence while any agent runs. Neither the J-7 path nor AC-17 says what Windows does.
- F-5 · Major · Design 3 `stageBinary(…, { known })` / ADR 0030 limit "no lock is shared by the writers" · Passing `known` makes the forward-only decision from a version read before the copy and rename. This widens the existing check-then-rename window, so two writers racing (a plugin refresh against a Homebrew copy's `status`) can move the staged binary backwards, after which the agents meet `SchemaTooNewError`. The limit is named, but the spec neither mitigates it (for example by a re-read just before the rename) nor says the "only moves forward" invariant in CLAUDE.md no longer holds.
- F-6 · Nit · Design 1, `latestRelease` exact `Location` match · The match is against a fixed repository string. A transfer or rename of the repository (the brand was already renamed once), or a difference in letter case from GitHub's canonical name, gives a 301 to the new repository or a non-matching `Location`, so every shipped client reads "not a release redirect" for good. Only "github.com may change the shape" is named, not the product's own repository moving.
- F-7 · Nit · Design 1 State, "written through a temporary file and a rename" · No temporary name is given for `update.json`, though the same spec moves `stageBinary` away from a fixed `.new` name because concurrent writers collided. `distill` and `update` can write at the same time.
- F-8 · Nit · Design 1 `due` / `checkForRelease`, "A second call at the same `now` … makes no request" · `attemptAt` is a plain read-then-write with no lease. Two `distill` processes, or `distill` and `update`, that both read before either writes both make the request. This is harmless at this scale but contradicts the stated guarantee.
- F-9 · Nit · Design 3, "runs the staged binary's `--version` at most twice" · After a hand-over, the staged child's own `status`/`doctor` report runs `stagedVersion` again. On macOS, a freshly staged, unscanned binary's first `--version` can be slow. Neither the per-command count nor the added latency of every `status` is stated correctly.
- F-10 · Nit · Design 3 / main.ts · `update` is a new command, but the spec never says it joins `COMMANDS` and `USAGE` in src/cli/main.ts. Reconciliation runs after the unknown-command return, so a missed entry silently disables `update`.
- F-11 · Nit · whole document (spec-heilmeier Q6, Q7, Q8) · No cost or effort estimate, no duration, and no midway check of success. The only check is reading `wizardingcode-mem update` on the day of the first release after the merge.

## Not answerable
- GitHub's actual `releases/latest` response (status code, absolute vs relative `Location`, canonical-case owner/repository, rate limiting on unauthenticated github.com HTML endpoints) · no network access, and the spec itself admits it cannot be verified before release.
- Whether Bun's `fetch` with `redirect: "manual"` exposes the 3xx status and `Location` header in the compiled binary on every platform · it would need running code, which this role does not do.
