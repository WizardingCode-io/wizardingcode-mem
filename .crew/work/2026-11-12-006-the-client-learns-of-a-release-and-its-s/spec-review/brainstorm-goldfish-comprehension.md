## Paraphrase
Once a day, a background process started by the session-start hook asks GitHub for the latest release. On macOS and Linux, if that release is newer than the copy in `~/.wizardingcode/mem/bin`, the process downloads it, checks it, and swaps it in, so every install is updated whatever channel it came from; on Windows the person is only told. The person sees the running version, the latest known version and when it was checked in `status`, `doctor` and the viewer's About; they can set `WIZARDINGCODE_MEM_UPDATE=check` (check and tell) or `off` (no request), or run `wizardingcode-mem update [--check]` themselves.

## Findings
- F-1 · Major · Hypothesis 5 · When the binary changes by itself, the only trace is "one line to the log": no log file is named, and nothing reaches the person unless they happen to run `status`/`doctor` or open About, so a person whose behaviour changed overnight has no way to learn that an update happened, from which version, or when.
- F-2 · Major · Hypothesis 5 · A failed update writes its reason to the log only: `status`/`doctor`/About as described show running, latest and checked-at, but not "the last attempt failed: checksum mismatch / no space / --version did not answer"; a person sees "newer exists" with no reason and no next step, and nothing says whether a failure retries every day, backs off or stops.
- F-3 · Major · Hypothesis 5 · `off` is said to make "no request", but not what `status`/`doctor`/About then show (a stale "latest", "unknown", or "updates off"?), whether `doctor` warns or reports ok, and whether a manual `wizardingcode-mem update` still contacts GitHub under `off`. A person who turned it off cannot confirm that it is off.
- F-4 · Major · Hypothesis 3, 5 · On Windows "the notice is shown", but "the notice" is never defined: where it appears (a hook's output? `doctor` only?), what it says, and which command updates a Windows install (`npx wizardingcode-mem install`? downloading the `.exe` again?). A Windows person is told that a release exists and is not told what to do.
- F-5 · Major · Hypothesis 5, Out of bounds · On Homebrew and npm, the command on PATH (the Cellar or global npm copy) falls behind the staged binary, and a newer staged binary may migrate the store (`SchemaTooNewError`). The person types `wizardingcode-mem doctor`, the old copy runs it, and it fails or reports a "running version" older than what the agents run. The concept does not say whether channel copies hand over to the staged binary, which version "running" means, or what the person is told.
- F-6 · Major · Hypothesis 5 · "The one command for this install's channel" is not knowable as written. "Channel" is undefined, there is no detection rule, and one machine commonly has several channels at once (a plugin, plus Homebrew, plus a direct install). The concept never lists which command maps to which channel, or says when such a command shows at all, given that the staged binary updates itself on macOS/Linux.
- F-7 · Major · Hypothesis 5, README:26, README:446 · The default (automatic download and replacement, with a daily request) is never named as a value (`on`? `auto`?), and it contradicts the README's promise "nothing leaves your machine unless you ask" and its "no network except…" bullet. Point 8 only changes "Privacy and your data", so the tagline would stay false.
- F-8 · Major · Hypothesis 5, README:352 · The README says every setting can be changed from the viewer, but this concept adds an env key and no Settings page or field for it. A person following the README looks for the update setting in Settings and does not find it. The key is also missing from the "settings by hand" table.
- F-9 · Major · Hypothesis 4 · When the MCP server "ends itself cleanly" after a newer version takes over, the agent's memory tools disappear mid-session. Many agents do not restart a stopped MCP server until the next session, and nothing tells the person why `memory_search` stopped working or that a new session (or an agent restart) is the fix.
- F-10 · Major · Background (`install --force` as the way back) · There is no way back a person can act on. `install --force` reinstalls a staged binary, but the concept does not say where an older binary comes from, the old one is not kept, and a store migrated by the new version refuses the older binary anyway. Someone hit by a bad release cannot roll back.
- F-11 · Nit · Hypothesis 5 · `check` and `off` read well, but `check` is both an env value and the `--check` flag with slightly different scope (the flag runs in the foreground). Neither the value that means "replace" nor the existing convention (other keys use `on`/`off`) is stated.
- F-12 · Nit · Hypothesis 5 · "The viewer's About" is not one of the viewer pages the README lists (Settings pages: Agents, Health, Judge, …). A reader cannot tell whether About exists or is new.
- F-13 · Nit · Hypothesis 5 · `doctor`'s new `update` line has no status level: whether "newer available" or "check failed (403/429)" is `ok`, `warn` or `FAIL` decides `doctor`'s exit code (`doctor.ts:31`) and is left open.
- F-14 · Nit · Hypothesis 8 · "The host its release assets redirect to" is not named, so a person behind a firewall or proxy cannot allow it. CI, SSH and container sessions (where the viewer deliberately stays closed, README:254) are not said to skip or keep the daily check.
- F-15 · Nit · Where this comes from · D-5, D-6, D-7, "piece 1/2/3", "goal 3" and "the parent brief" are used as if known. A new reader must open another item's files to learn the decisions this concept rests on.
- F-16 · Nit · Hypotheses 2, 4, 6 · These project terms are used and never defined here: "staged binary" (the README only says "one copy in bin"), `meta`, "failed-start backoff", "the store's recorded binary version" (recorded where, and by whom?), "the hook-contract compatibility test", and the "floor" in point 6's title, which its body never explains.
