## Findings
- F-1 · Blocker · Hypothesis 4 · The concept says each long-lived process ends itself "when it finds the store's recorded binary version higher than its own", but no binary version is recorded in the store. The only version anywhere is the `sync-<pid>-<version>` lease owner (src/store/meta.ts:136-160). An engineer would have to invent the record: its key, who writes it (every open? only the hook?) and what happens when an older binary writes after a newer one.
- F-2 · Blocker · Hypothesis 4, "extends the sync's 'a newer version takes over'" · That takeover only happens when a newer `sync --auto` is actually spawned. `startSync` returns "running" for any live lease and never compares versions (src/sync/spawn.ts:78-82), so after a self-update the old sync keeps running until its 15-minute idle exit. The precedent the concept leans on does not work for this case.
- F-3 · Blocker · Hypothesis 3 and 5 against ADR 0029:21,57 · After `install --force` back to an older binary, the daily `update --auto` puts the newer version back within 24 hours, so ADR 0029's "person's way back" quietly stops working. The concept does not decide whether a forced downgrade pins the version (a meta mark? the env setting `WIZARDINGCODE_MEM_UPDATE=off`?) or what `install --force` tells the person.
- F-4 · Major · Hypothesis 4, store schema · A self-update means the next session-start hook opens the store with the new binary and migrates it, making the upgrade copy on the hook path under a 150 ms busy timeout (hook.ts:18). This now happens without the person acting. No command restores an upgrade copy (`<store>/backups/wizardingcode-mem-<ms>-v<n>-<pid>.db`; `backup --restore` reads the configured backups), so the way back from a store migrated by an unwanted update is undefined.
- F-5 · Major · Hypothesis 4, MCP server · `mcp` opens the database on each tool call (src/modules/memory/tools.ts, src/modules/knowledge/tools.ts). Once the store is migrated past it, every call throws SchemaTooNewError rather than the process ending cleanly. "The agent starts the new one" assumes hosts restart a stdio MCP server that exits, but most only restart it with a new session. The concept should say what the old server answers between those two moments.
- F-6 · Major · Hypothesis 4, viewer · `ui --auto` shows a viewer that is already running and answers its probe (src/cli/commands/ui.ts:23-26). The viewer keeps its open connection (src/ui/server.ts:216) and never checks `user_version` again. So "the next `ui --auto` starts the new one" is false unless the old viewer ends itself, and how it would learn to do that is F-1.
- F-7 · Major · Hypothesis 3, older npm shims · ADR 0029:60-61 says the 0.4.4 npm shims (still on machines, also in npx caches) replace the staged binary on any version difference. The daily update and such a shim would fight: the shim downgrades, the old binary refuses the migrated store and hooks fail open silently, then the update moves it forward again. The concept says nothing about detecting this loop or reporting it in `doctor`.
- F-8 · Major · Hypothesis 3, concurrency between writers · `update.lease` covers only update processes. The plugins' script checks `older` and then does `mv -f` with no check after the download (template:75-76,64), and `stageBinary` checks and then copies through a fixed `${target}.new` (binary.ts:45-54). An older plugin's session-start fetch that overlaps an update can therefore put the lower version back, and two `stageBinary` calls share one temporary name. The concept needs a locking rule shared by all five writers, or a check again just before the rename.
- F-9 · Major · Hypothesis 3, "puts it in place with `stageBinary`" · `stageBinary(source, dataDir, {version})` copies `source` to `bin/wizardingcode-mem.new` and runs `--version` on the target only. Left undecided: where the download's part file lives (bin/ or the model sweep's folder), whether `stageBinary` gains a sweep, and whether `--version` is checked on the part file before staging or after.
- F-10 · Major · Hypothesis 5, "the one command for this install's channel" · Every channel stages the same bytes, and nothing records which channel staged a binary (plugin, npm, Homebrew, curl, direct install). The engineer would have to design channel detection and a stored channel record, and say what is shown when more than one channel is present.
- F-11 · Major · Hypothesis 1, 3 and tests · The only stand-in for GitHub in the tests is `WIZARDINGCODE_MEM_RELEASE_BASE`, a fixed download base for one version served by a loopback `Bun.serve` (plugin-script.test.ts:47-66, also npm-shim, install-script and plugins-packaging). Nothing stands in for `api.github.com/repos/.../releases/latest`. The concept does not name the override for the API URL, how the download base is built from the tag found, or whether these overrides may come from `<data dir>/env` (a security review already flagged the existing override, which lets the same base supply matching checksums).
- F-12 · Major · Hypothesis 6 · "Every shipped generated script" means the scripts and hooks files of past releases, but the repository holds only the current generated copies (`generated()` in scripts/plugins.ts). The concept does not say how far back to go or where the old scripts come from (git tags at test time? frozen fixtures?). It also leaves out the OpenCode package's bridge and the hooks files and MCP configuration that direct installs (ADR 0016) wrote in earlier versions.
- F-13 · Major · Hypothesis 7 · "Exit 0 within 10 seconds" cannot be enforced portably in the POSIX `sh` readers: `installed()` in the template has no time limit, there is no `timeout` command on stock macOS, and `version_of` in install.sh takes `head -n 1` rather than refusing an answer of several lines. `plugins/opencode/binary.js:31` also has no timeout. The mechanism for the shell readers has to be chosen, and copies already shipped will not change.
- F-14 · Major · Hypothesis 2 and tests · The hook's spawn of `update --auto` needs a `HookDeps` seam (as `spawnSync` has) and a switch the tests can turn off (as `WIZARDINGCODE_MEM_SYNC=off` does). Without one, every existing hook test would start a detached process that makes requests to the network. The concept names neither the seam nor the switch, nor whether `WIZARDINGCODE_MEM_UPDATE=off` is that switch.
- F-15 · Major · Hypothesis 4, tests · A test that a long-lived process ends cleanly when a newer binary migrates the store needs two schema versions. The only way to get them is `OpenOptions.migrations`/`moduleSchemas` (db.ts:56-58) in one process, not two real binaries. The concept does not say whether that test runs in one process with injected migrations or needs a new harness with two builds.
- F-16 · Major · Hypothesis 2 · The 24-hour timestamp and the backoff live in `meta`, inside the store. A store that is refused (SchemaTooNewError after a downgrade) or unreadable therefore never runs a check, which is exactly when an update would help. The concept does not decide whether the update state belongs in the store or in a file in the data directory, as `ui.json` is.
- F-17 · Nit · Hypothesis 1 · The concept does not say whether a person on a staged pre-release (from `next`) follows later pre-releases or waits for the next plain release, nor how an answer whose tag has a `v` prefix is normalised before `isVersion`.
- F-18 · Nit · Hypothesis 8 · README:446 says "No telemetry, no account, no network — except …". That sentence must be rewritten, not only added to, and the concept names the section but not this bullet.
- F-19 · Nit · Hypothesis 7 · "Removing surrounding blanks, carriage returns and newlines" is narrower than `.trim()` in binary.ts:17 and the two JS readers, which also remove tabs and other Unicode white space. The table must say which of the two rules wins.

## Not answerable

- Whether macOS accepts a signed binary renamed over a running one and run straight away (no quarantine, code signature check on the new inode), and whether each host restarts an MCP server that exited · seen only on real machines and real hosts.
- What status.ts, doctor.ts and mcp.ts print and do today · not read line by line; findings about them rest on grep for openDb and the CLAUDE.md description.
- The pre-0029 generated plugin scripts and direct-install hook files · not in the tree; only ADR 0029's account of how they behave was read.
