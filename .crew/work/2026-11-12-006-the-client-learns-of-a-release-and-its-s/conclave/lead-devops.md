## Notes
- Question 1 holds as designed: `.github/workflows/release.yml:147-148` marks every hyphenated tag `--prerelease`, and GitHub never serves a pre-release at `releases/latest`; the spec's own filter (spec.md:48) is a second guard. Not checked here: that `gh release create` publishes only after its assets are uploaded, and the redirect's exact status and `Location`; the conclave already lists these as seen on the first real release.
- A plain tag cut on an older line after a higher release still gets a GitHub release, although `distribute.yml` refuses it (`docs/runbooks/release.md:60`). If GitHub marked it latest, clients would read "X is the latest" with X below their own version. The spec does not define `updateLine` for a latest lower than the staged binary (spec.md:59-60); the same case arises after the withdrawal in R-1. Worth one sentence and one test case in AC-5.
- Homebrew command: correct for this tap. The formula is `wizardingcode-mem` in `WizardingCode-io/homebrew-wizardingcode` (template:4-5, README.md:159) and runs nothing after install (template:33-41), so "then any `wizardingcode-mem` command" is needed. "Any" is inexact, though: `--version` and `--help` must not stage (R-2). Print a concrete command instead, for example `brew upgrade wizardingcode-mem && wizardingcode-mem status`.
- The formula's caveat (template:37-41) still says only `wizardingcode-mem install`; it stays true and needs no change.
- npm command: `npx wizardingcode-mem@latest install` is right, since the plain release goes out under the dist-tag `latest` (`docs/runbooks/release.md:54`) and the shim stages forward-only (`npm/bin/wizardingcode-mem.js:98`). README.md:177 has `npx wizardingcode-mem install` without `@latest`; AC-9's "every command of `CHANNEL_COMMANDS` is in the README" needs an update line there, not a change to the first-install command.
- Script command: the URL is identical to `scripts/install.sh:6` and README.md:162/168. It is the one channel that already works between the GitHub release and the end of `distribute.yml`.
- The four commands have no line for a downloaded Windows `.exe` (README.md:180) or for the direct installs of ADR 0016. The npm line covers Windows; say so in the README.
- Plugins: the binary a plugin fetches follows the marketplace manifest, which `distribute.yml` writes; the generic sentence is acceptable since agents differ.
- A user's CI: `CI` set and not empty means no request (spec.md:51), consistent with `src/cli/commands/hook.ts:70`. Agents run in containers or over SSH without `CI` will check once a day per data directory; the README's sentence covers it.
- Developer hazard from Design 3: `bun run build` then `./dist/wizardingcode-mem-<platform> status` on a branch whose version is already bumped (`docs/runbooks/release.md:7`) stages an unreleased build into the developer's real `<data dir>/bin`, and the agents run it. Say in ADR 0030 or CLAUDE.md how to avoid it (a throwaway `WIZARDINGCODE_HOME`, or `WIZARDINGCODE_MEM_HANDED=1`), and check that the e2e and perf tests driving the compiled binary always set a data directory.
- `uninstall` typed from a newer channel copy stages that copy before uninstalling, since only `install` is excepted (spec.md:75). Decide whether that is wanted.
- Rollback: a revert removes the check only from the next release on. Every shipped version keeps asking github.com daily and keeps reconciling until its user upgrades, and nothing server-side turns that off except moving or withdrawing the release (R-1). Add this to Risks at spec.md:116.
- Rollout: versions before this one never check, so the first notice anyone sees is for the release after the one carrying this change. The 0.4.4 npm shims (`docs/runbooks/release.md:103`) can still put an older binary back after a channel copy staged a newer one; ADR 0030's limits should name it beside the missing shared lock.
- The temporary name `<target>.<pid>.new` is compatible with the other writers (`npm/bin/wizardingcode-mem.js:89` and `scripts/install.sh:73` already use unique names); a leftover `<target>.new` from an older binary is not covered by the one-day cleanup as written.
