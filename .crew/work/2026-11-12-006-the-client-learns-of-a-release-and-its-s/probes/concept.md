# Concept: the client learns of a release and its staged binary follows

Mode: brainstorm. The hypothesis the lenses attack.

## The problem

An install that came through a plugin follows a release when the agent updates the plugin: the plugin's script (`scripts/templates/wizardingcode-mem.sh`) stages the plugin's pinned version at session start. Every other install stays where it was put until the person acts: the direct installs (Qwen Code, Droid, Copilot, Antigravity, Cursor: hooks file and MCP server, no plugin; ADR 0016), `scripts/install.sh`, a Homebrew binary that ran `install`, and a plugin whose marketplace the agent has not refreshed. Nothing tells the person a release exists.

## The hypothesis

1. **One function says what was released.** `latestVersion()` asks GitHub for the repository's latest release (the `releases/latest` endpoint of `WizardingCode-io/wizardingcode-mem`) with a short timeout and reads the tag. Anything else (no network, a 403 or 429, a captive portal's HTML, a tag that is not a plain version) is "unknown". A pre-release is never "latest".
2. **A daily check, off the hook path.** The session-start hook starts a detached `wizardingcode-mem update --auto` when the last check is older than 24 hours (a `meta` timestamp), under a lease `update.lease` and a failed-start backoff, as `src/sync/spawn.ts` and the leases of `src/store/meta.ts` do. The hook itself makes no request and waits for nothing. The result (`update.latest`, `update.checked_at`) is kept in `meta`.
3. **The staged binary follows.** When the latest version is higher than the staged binary's (`olderThan`, `src/util/version.ts`), the same detached process downloads the platform's asset and `checksums.txt` from the release, verifies the sha256 as `src/embed/download.ts` does (part file, streamed hash, a sweep of stale parts), checks that the downloaded binary answers `--version` with the expected version, and puts it in place with `stageBinary` (atomic rename; forward-only). The verification sits behind one function, so a signature check can replace the checksum later. macOS and Linux only; on Windows the check runs and the notice is shown, and nothing is replaced.
4. **Long-lived processes.** `mcp`, `sync --auto` and the viewer keep running the old file after the rename. The new binary may migrate the store past what they accept (`SchemaTooNewError`). The hypothesis: this is the situation a plugin update already creates today, so the item adds no new state; it extends the sync's "a newer version takes over" to the MCP server and the viewer (each ends itself cleanly when it finds the store's recorded binary version higher than its own, and the agent or the next `ui --auto` starts the new one).
5. **What a person sees and controls.** `status`, `doctor` (a line `update`) and the viewer's About show the running version, the latest known and when it was checked, and, when a newer one exists that was not installed, the one command for this install's channel. `WIZARDINGCODE_MEM_UPDATE=check` checks and tells without replacing; `off` makes no request. A manual `wizardingcode-mem update [--check]` does the same in the foreground. Each replacement writes one line to the log, each failure its reason.
6. **The plugin's pin becomes a floor.** A plugin's script already keeps a newer staged binary. A binary ahead of its plugin runs under an older plugin's hooks and MCP configuration, so a test runs the hook invocations of every shipped generated script against the current binary (the hook-contract compatibility test the parent brief asks for).
7. **One rule for reading a staged binary's version** (moved here from item `2026-11-12-005`; its findings are in `docs/real-use/findings.md`, the row with `version_of`). Five readers (`stagedVersion` in `src/install/binary.ts`; `installedVersion` in `npm/bin/wizardingcode-mem.js` and in the generated `plugins/opencode/binary.js`; `installed()` in `scripts/templates/wizardingcode-mem.sh`; `version_of` in `scripts/install.sh`) agree on: exit 0 within 10 seconds, and an answer that is exactly one version after removing surrounding blanks, carriage returns and newlines. One table of answers (`tests/fixtures/`) is run against all five, as the version order's table is.
8. **Privacy text.** The README's "Privacy and your data" says the daily request plainly: to `api.github.com` for the version and, on a replacement, to `github.com` and the host its release assets redirect to; what is sent (no identifier beyond what any HTTPS request carries); and how to turn it off.

## Out of bounds

The team server's own upgrade (piece 3). Signatures on release assets. A banner in the viewer (only if About proves not to be enough). Replacing a Homebrew Cellar copy or a global npm package: their managers own those files; this item only moves the staged binary the agents run.
