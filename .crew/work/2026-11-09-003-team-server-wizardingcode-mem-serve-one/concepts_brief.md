# Concepts brief: the team server

## Overview

The same binary, started as `wizardingcode-mem serve`, is the team's server: its own SQLite database under a data directory is the authority for what members share (knowledge entries and the memories of projects set to Knowledge and memories), the git repositories beside it are a versioned mirror written after each applied item, every request carries a device token an admin's invitation created, admins and members are told apart, and part 6's sync client pushes batches of items shaped by part 4's payload types and pulls what changed since a cursor for the projects its machine works on. A stale base is refused with the server's current version and hash. One Docker image and a compose file with Caddy terminating TLS are the deployment. The concept (`concept.md`) went to six reviewers in brainstorm mode (`spec-review/brainstorm-goldfish-*.md`, 163 findings); this brief is the concept after them.

## Analysis

**Three stores cannot share one truth.** The concept had the file and its commit, the `entries` row and the `changes` row written by one push with no order and no recovery, and an index "rebuilt from the files" that cannot hold the owner, the feed or the withdrawal (readiness, design, structural, codebase, zoom-out). The team database is the authority: a push is applied in one transaction that stores the payload bytes as sent, the server's version, the hash, the owner and the feed row; the git repositories are a mirror written after the commit by one in-process queue (one commit per applied item, the member as author, the server as committer), and rows still pending at start are mirrored then. The sync never reads the mirror; `serve repair` rewrites it from the database. The mission's "repositories on volumes" is kept as the team's readable history; the zoom-out reviewer's case against git on the server is answered by making it a mirror, not a source.

**Whose version decides.** Part 1's `version` is a local counter and part 4 made the hash the judge; the concept left the server's version undefined (every lens). The server owns a counter per entry (plus one per applied push); a push carries the server version and hash the client built on (`baseVersion`, `baseHash`; 0 and empty for a first send); the server applies only when both equal its current ones and answers the new ones, which the client records in its ledger; a retry whose hash equals the server's current answers `applied` (idempotent); the payload bytes are stored verbatim, so the hash is the client's. A memory carries `updatedAt` and is applied only when not older than the stored one.

**One member, several machines; one memory, one device.** `join` created a member per machine, device ids were cut from the token hash, memories were keyed by the client's uid alone, which breaks part 4's device scoping and refuses a copied store forever (comprehension, structural, design, codebase). An invitation may be bound to an existing member (made by an admin or by the member from a device they hold); a device id is a random value; memories are keyed `(device, uid)` on the server and pulled as `remote:<device id>:<uid>`; a device rotates its own token and keeps its id; tokens and codes carry prefixes `wcm1_` and `wci1_` so `redact` recognises them (a rule added to `src/core/redact.ts`); invitations can be listed and revoked, and revoking a device cancels the unused invitations it created.

**Who may write what.** No entry had an owner and every member pulled everything (design, structural). Shared and project entries are the team's: any member may push a new version on the current base, the last writer is recorded; a member's workspace entries are written by that member's devices only; a withdraw is accepted from the last writer's member or an admin, otherwise `refused not-owner`; an admin's withdraw locks the item until an admin reinstates it; the owner's re-send after its own withdraw is a new version on the tombstone's base. A device pulls the shared and the members' workspace entries always and project items only for the remote aliases it names (ADR 0018's rule carried across people); a disabled member's items stay attributed, and an admin may withdraw them all in one call.

**The feed must survive time, restores and purges.** Tombstones purged after 90 days left old cursors blind; a restored database lowered the sequence under the clients' cursors; `seq` without `AUTOINCREMENT` could reuse numbers (design, structural, readiness, comprehension). The feed keeps tombstones and superseded rows 90 days, never reuses a number, answers 410 to a cursor older than what it kept, answers one current row per uid since the cursor (a full pull is `since` zero), and every answer carries the server's instance id, minted at first start and renewed by the runbook's restore step, so a client that sees a new instance pulls from zero and re-sends what the server lost. `serve backup` is dropped: the runbook (part 7) snapshots the volume with the server stopped.

**Limits that fit together.** 200 items of up to 256 KiB do not fit 1 MiB; pulls had no byte bound; joins had no limit; nothing was published (design, structural, readiness, codebase). 1 MiB per body (413 before parsing), 200 items per push, 256 KiB per entry payload (`refused size`), 500 items or 2 MiB per pull page, 600 requests a minute per device, 10 joins a minute per source address, 5,000 applied items per device per day; the limits are in `/v1/me` so part 6 sizes batches by bytes and by count.

**The server is a process, not a hook.** Part 1's runner is synchronous and 15 s per call; a push of 200 commits would stall every device and the health probe; `Bun.serve` closes idle connections at 10 s; PID 1 ignores SIGTERM (design, readiness, codebase). The push answers after the database commit; the mirror queue runs git asynchronously, one repository at a time; `idleTimeout` is 120 s; SIGTERM and SIGINT stop accepting requests, finish the item in flight, drain the queue for at most 20 s and close the database; compose sets `init: true` and a 30 s stop grace.

**Reuse with the right seams.** `openDb` hard-codes the client's file and schemas; `json`, `problem` and `jsonObject` are private to the viewer's server; part 1's runner is bound to `<data dir>/knowledge/` and one identity; `main` runs the legacy migration before every command (codebase, readiness, zoom-out). The core migration runner takes a file name and a migration list so `team.db` has its own (`moduleSchemas` empty); the three HTTP helpers move to `src/http/respond.ts` and the viewer imports them; part 1's runner takes its root as a parameter and its commit takes an author and a committer apart; `serve` skips the legacy migration and logs JSON lines to standard output (request id, device id, route, status, milliseconds, per-item counts; never a token, a code after its first print, or a payload).

**Deployment that fails safe.** `--host 0.0.0.0` "inside the container" had no bare-host default; the image had no HTTP client for the health check, no fixed user, no registry permissions (every lens). The binary defaults to loopback and refuses another address without `--host`; the image sets the host by environment, runs as user 10001 owning `/data` (a named volume; a bind mount must be owned by that user), passes `safe.directory` to git, and probes health through `wizardingcode-mem serve health`; the release workflow gains `packages: write`, buildx for amd64 and arm64 (mapping to the two Linux binaries), a login to the GitHub container registry, the version tag and `latest` for a non-prerelease; CI builds the image and probes it once.

**What the server checks and what it does not decide.** A raw frontmatter string written to disk could spoof `author`, carry a traversing slug or disagree with the uid (design, structural). The server parses the frontmatter, requires `id` equal to the uid's UUID and the scope to agree with the uid's prefix, checks the slug against part 1's rule before any path is built, caps the payload, and treats `author` as informational (the commit author is the member); a payload is checked against the key lists part 4 pins and refused `shape` otherwise; `/v1/me` carries `contract: 1`, and a client of another contract is answered 409 so the upgrade order is server first. The server never calls `decide`: it stores the client's `epoch` with the feed row for the audit and decides nothing of policy.

**Observability.** `serve status` reads the database and prints the version, the schema, members and devices, a pending first admin, the last sequence, the mirror backlog and the instance id; `serve audit` lists the last changes; `/v1/health` answers only liveness (the database opens, the disk has room) without the version; the audit records CLI subcommands with source `cli`; the pull feed gives members the writer's name and the time, never the device id (admins see it).

**Not taken, with the reason.** Dropping the git mirror (zoom-out): the mission names repositories on volumes; it is a mirror, never a source. A password-hashing function for tokens (concept): 256-bit random secrets need no slow hash. A server web page, e-mail invitations, SSO, teams within a server: later items.

## Goals vs. Non-Goals

Goals: `serve` and its subcommands (`invite`, `members`, `devices`, `revoke`, `status`, `audit`, `repair`, `health`, `instance renew`); the team database and its migrations; join, tokens, rotation, invitations, roles; the sync API (`me`, `push`, `pull`) with the rules above; the git mirror; the limits; the logs; the Dockerfile, the compose file, the release and CI steps; the `redact` rule for tokens and codes; ADR 0026.

Non-goals: the sync client (part 6); the runbook and README (part 7); backups beyond the runbook's volume snapshot; a second destination per server; purging history; a server-side taxonomy (the shared taxonomy stays a client file until part 6 decides); e-mail, SSO, a web page.

## Alternatives Weighed

- Git repositories as a source of truth on the server: rejected; three stores cannot share one transaction, and the feed cannot be rebuilt from files.
- No git on the server at all: rejected; the mission names repositories on volumes, and a mirror costs one async queue.
- Last write wins for entries: rejected; the mission says versions decide, never a silent overwrite.
- Memories keyed by the client uid alone: rejected; part 4 scopes them by device, and a copied store would be refused forever.
- A member per join: rejected; one person has several machines, and ownership follows the member.
- Every device pulls everything: rejected; ADR 0018's worst case across people.
- A password hash for device tokens: rejected; high-entropy random secrets.
- `serve backup` with `VACUUM INTO` and bundles: rejected; two instants, the same volume, and the runbook owns restores.
- Health through curl in the image: rejected; the binary probes itself.
- `0.0.0.0` as the binary's default: rejected; loopback by default, the image sets the host.
