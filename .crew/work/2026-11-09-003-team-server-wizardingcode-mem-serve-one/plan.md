# Plan: the team server (`wizardingcode-mem serve`)

The spec is `spec.md` in this folder. The plan is ten phases, 0 and A to I, 24 tasks; each task names its criterion, its test file, the files it creates or modifies and the command that proves it. Test first, as `CLAUDE.md` rules: in every task the test is written, run and seen failing (the red run recorded on the item) before the code, and run green after. Phase order is dependency order: A gives the seams every later phase imports; B the database, identities and authentication every route needs; C and D the two sync routes; E the mirror, which reads C's revisions; F the command, which wires A to E into the binary; G the limits and the redact rule, which touch A to F lightly; H and I the deployment and the documents, which need nothing more from the code.

**Order against the other parts.** This part imports part 1 (`src/modules/knowledge/entry.ts`: `parseFrontmatter`, `checkSlug`, `AREA_ID`, `ENTRY_MAX_BYTES`; `src/modules/knowledge/index-store.ts`: `fileHash`; `src/modules/knowledge/repo.ts`: the git runner; `src/modules/knowledge/author.ts`: the author rule; `tests/helpers/stub-git.ts`) and part 4 (`src/sharing/types.ts`: `OutgoingEntry`, `OutgoingMemory`, `OUTGOING_ENTRY_KEYS`, `OUTGOING_MEMORY_KEYS`; `src/sharing/hash.ts`: `memoryHash`; `src/sharing/levels.ts`: `SHARE_AREA` is not needed; the uid shapes). Both are in `main` since PR #28 (2026-11-10) and on this branch; Phase 0 checks the names. Where this plan names a function of part 1 or part 4, the name is the one in that part's plan ("Signatures" sections); a rename there is a rename here.
