# design findings for 2026-11-09-003-team-server-wizardingcode-mem-serve-one
reviewer: goldfish-design
read: .crew/work/2026-11-09-003-team-server-wizardingcode-mem-serve-one/concept.md (whole), .crew/work/2026-11-09-003-team-server-wizardingcode-mem-serve-one/brief.md (whole), .crew/work/2026-11-09-002-sharing-policy-per-project-local-only-kn/spec.md (whole, part 4), .crew/work/2026-11-08-003-knowledge-store-entries-as-markdown-with/spec.md (whole, part 1), src/ui/server.ts, src/store/db.ts, src/store/meta.ts, src/core/redact.ts, docs/adr/0018-linked-projects.md

## Findings
- F-1 · Blocker · The sync API, memory `send` · The concept says another device's push of the same memory uid is `refused`, so the server keys memories on the client's bare `<generation>:<row id>`; part 4 D-11 (binding) says the server scopes that uid by the device token. Under the concept's reading, a store copied to a second machine (same generation, which part 4 names) gets every memory refused forever, and the `remote:<server uid>` a client stores on receipt is not globally unique.
- F-2 · Major · The sync API, entry `send` · `baseVersion` is not defined against part 1's version, which is a local per-machine counter that several local edits raise between syncs. Nobody can tell whether the server's `version` is the payload's frontmatter `version`, a server-assigned counter, or the ledger's last-synced value, nor what `version:` the server writes into the file. Two competent builders would build incompatible stale checks.
- F-3 · Major · The sync API, push · A retried push is not idempotent. If the answer is lost after an item applied (or after the git commit and before the database commit), the retry with the same `baseVersion` comes back `stale` against the client's own write and part 6 records a false conflict. The design needs a rule such as "same hash as current answers `applied`", or a per-item idempotency key.
- F-4 · Major · Storage on the server · The stale check (SQLite) and the git commit cannot share one transaction (part 1 rejects holding the write lock through a commit). Nothing serialises check-then-commit per repository except the accident that part 1's `runGit` is `Bun.spawnSync`. Once git is made asynchronous, two concurrent pushes of one entry both pass the check and one silently overwrites the other, which breaks the brief's core constraint.
- F-5 · Major · Storage / runtime · Part 1's git runner is synchronous (`Bun.spawnSync`, 15 s timeout per call). On a long-running server, one 200-item push means hundreds of blocking spawns. A hung git stalls every device, `/v1/health` included, so the healthcheck can restart the container in the middle of a write.
- F-6 · Major · Storage on the server, the index · Saying `entries` is "rebuilt from the files … as part 1's client index is" is false. `member_id`, `device_id`, `remote_alias` and the `changes` sequence are not in the files: commits carry only a name at a `.invalid` address. A crash between the commit and the database write leaves a version that the index picks up but the pull feed never announces.
- F-7 · Major · Members, devices · The Assumptions say "a salted SHA-256 at rest"; the sketch says `sha256(token)` looked up by hash. A per-token salt makes lookup by hash impossible, so one of the two statements is wrong and a builder will follow one or the other.
- F-8 · Major · Members, devices · Token rotation is missing: no route, no CLI. A suspected leak needs revoke plus re-invite, and because the device id is derived from the token hash, the new device is a different device that no longer owns the old device's memory uids (F-1). They become unchangeable and cannot be withdrawn by their owner.
- F-9 · Major · Invitations · Invitations cannot be listed or revoked. There is no `GET`/`DELETE /v1/invitations`, and `serve members` shows only members and devices. A leaked or mis-sent invitation, admin ones included, stays live until it expires (72 h by default).
- F-10 · Major · Authorisation · A leaked admin token can mint admin invitations and join new devices. Revoking the leaked device does not remove those, and nothing ties an invitation to the device that created it. Revocation needs to name, or cascade to, the invitations that device created.
- F-11 · Major · Bootstrap · The first-admin code goes to stdout, so it lives in Docker's json-file log (readable by the docker group, possibly shipped to aggregators) and in `first-admin.txt`. Three things are undefined: its expiry, whether a restart before use mints a new code or reuses the old one, and how to recover if it expires. Meanwhile `/v1/join` is reachable from the internet before the first admin exists.
- F-12 · Major · Abuse · The rate limit is per device, so the unauthenticated `/v1/join` has none. Behind Caddy every request comes from the proxy's address, and the design does not say whether `X-Forwarded-For` is trusted, which a per-IP limit and the audit's source address both need. `member.name` and `device.label` have no length bounds.
- F-13 · Major · Authorisation, entries · No entry has an owner. Any member can overwrite any entry in any scope given the current base version, including another member's `members/<id>/` workspace entries. It is also undefined who may `withdraw` an entry, so one member's local privacy downgrade (part 4's `withdraw`) tombstones a shared entry for the whole team.
- F-14 · Major · Authorisation, read · Every device pulls every project's memories and entries ("a member sees every item"). This is ADR 0018's worst case (one client's decisions in another client's sessions) moved across people. It also copies team-wide data onto every laptop, and the design neither states this nor bounds it.
- F-15 · Major · Sync semantics, tombstones · What happens after a withdraw is undefined. Can the owner re-send to resurrect it, with base 0 or the tombstone's version? After the 90-day purge the server "does not know" the uid, so base 0 is accepted. An admin's withdraw of a member's memory is undone by that device's next edit, because "a send from the owning device replaces".
- F-16 · Major · Sync semantics, pull cursor · A device whose cursor is older than the 90-day tombstone purge never learns of the withdrawals, and the server has no "cursor too old, start a full pull" answer (for example 410). Withdrawn text then stays on that machine forever.
- F-17 · Major · Sync semantics, `changes` · `seq INTEGER PRIMARY KEY` without `AUTOINCREMENT` lets SQLite reuse the highest rowid after the newest rows are purged, so clients holding that cursor skip the new rows. The table also grows forever, with no compaction.
- F-18 · Major · Sync semantics, full pull · Undefined for `since=0`: whether it replays every historical change or one row per uid, whether it includes tombstones, and how an old `upsert` row is answered once its item has moved on or been withdrawn.
- F-19 · Major · Backups / restore · A restored older `team.db` has a lower maximum `seq` than every client's cursor, so clients silently miss everything written after the restore. The cursor needs a server instance or generation id that a restore renews, as part 4 does for memories.
- F-20 · Major · Backups · `VACUUM INTO` and a `git bundle` per repository are taken at different instants while the server writes, so the database and the repositories disagree on restore. Backups go to `<data>/backups/` on the same volume (not a backup against losing the disk) and have no retention count, no schedule and no encryption.
- F-21 · Major · Data at rest, history · A withdraw tombstones the database row, but the text stays in git history, in every bundle and in any read-only clone a person takes from the volume. `redact` is pattern-based and fallible (its own header says so), so a secret sent by mistake cannot be purged. Part 4 D-10 rejected `git push` for exactly this reason.
- F-22 · Major · Data at rest, members · Disabling or removing a member deletes nothing. There is no path to remove a departed member's memories and entries apart from item-by-item withdraws, which still leave the text in history and backups (F-21).
- F-23 · Major · Abuse, sizes · The 1 MiB body cap is above part 1's 256 KiB file cap, so an accepted entry becomes a file the rebuild marks as a problem. There is no per-member or per-device quota on item count or bytes. At 600 requests a minute with 200 items each, one token can create about 120,000 git commits a minute until the disk fills.
- F-24 · Major · Abuse, pull · A pull page is capped at 500 items, not by bytes. With entries up to 256 KiB, one page can be over 100 MiB built in memory. A byte cap per page is needed.
- F-25 · Major · Validation · `OutgoingEntry.frontmatter` is a raw string written to disk. The design does not say the server parses and validates it, so these are open: `id` must equal the uid's UUID, `author` can be spoofed (and disagree with the commit author), the slug must be checked against part 1's rule before a path is built (traversal), and the payload's scope must agree with the uid's prefix.
- F-26 · Major · Storage, slugs and taxonomy · Two members can push different entries with the same slug into `shared/` or the same project repository, so `entries/<slug>.md` collides and the outcome is undefined. Server repositories also have no defined `taxonomy.md`, and part 1 validation marks any area outside it as a problem.
- F-27 · Major · Sync semantics, memories · A memory replace has no ordering check. Two background pushes from one device that arrive out of order, or a delayed retry, let an older `updated_at` overwrite a newer one.
- F-28 · Major · Tokens, redaction · Device tokens (43 base64url characters) and invitation codes have no recognisable prefix, and `src/core/redact.ts` has no rule for them; only a literal `Bearer …` is caught. A token pasted into a session can be distilled into a memory and pushed to the team server itself.
- F-29 · Major · Deployment, container · `HEALTHCHECK` on `/v1/health` needs an HTTP client, but the image installs only `git` and `ca-certificates` (no curl or wget). As written the check cannot run, unless the binary gets a health subcommand.
- F-30 · Major · Deployment, non-root · The image's user id and the ownership of `/data` are unspecified. A bind mount owned by the host user fails on first start, and git 2.35.2 or newer refuses repositories owned by another uid ("dubious ownership"); part 1's isolated runner suppresses the global config where `safe.directory` would normally go. Reading the repositories "read-only from the volume" as another user hits the same refusal.
- F-31 · Major · The command, `--host` · The `0.0.0.0` default is stated only "inside the container". The binary's default outside a container is not given. A bare `serve` on a VPS would expose plain-HTTP bearer tokens unless it defaults to loopback and refuses a non-loopback bind without an explicit flag.
- F-32 · Major · Compatibility · Refusing any unknown payload field (`shape`) means a client upgraded before the server gets every push refused. The upgrade order (server first) and how `/v1/` evolves are not stated.
- F-33 · Nit · Members, devices · A device id of 8 hex characters of the hash is 32 bits. It needs a unique constraint with a retry on collision, and it is sent to every member in the pull feed.
- F-34 · Nit · Roles · "The last active admin cannot be … demoted", yet no route or command changes a role. Revoking an admin's last device locks them out, leaving the host CLI as the only recovery; the design should say so.
- F-35 · Nit · Push · What the server does with `epoch` (store it, check it, ignore it) is not stated.
- F-36 · Nit · Operability · `serve status` and `serve members` have no defined output. Missing pieces: the audit's retention and reader, a log format with a rule that tokens and bodies are never logged, any view of refused or stale counts per device, disk-space reporting, and `git gc` of repositories that get one commit per item.
- F-37 · Nit · Health · `/v1/health` answers `ok: true` without checking that the database and volume are writable or have free space. It also tells anyone on the internet the exact version.
- F-38 · Nit · Privacy · The pull feed gives every member each item's `member`, `device` and `at`, which is a timeline of who worked on which project and when. Not stated.
- F-39 · Nit · Deployment · The design does not say that Caddy needs ports 80 and 443 open and DNS pointing at the host for ACME, and does not mention HSTS. The images are not pinned by digest or signed.
- F-40 · Nit · Admin CLI · Subcommands run on the host or in the container bypass token authentication. The audit should record them with source `cli`.

## Not answerable
- Whether Caddy's default access log redacts `Authorization` headers · not in the files I was given; it decides whether device tokens reach the proxy's logs.
- Part 6's client-side token storage and retry and concurrency behaviour · out of the range given; F-3, F-27 and F-28 depend on it.
