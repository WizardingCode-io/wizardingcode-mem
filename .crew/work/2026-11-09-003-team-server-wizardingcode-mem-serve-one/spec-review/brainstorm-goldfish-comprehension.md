## Findings
**What this proposes**
The same binary gets a long-running `wizardingcode-mem serve` command. It is the team's server: it holds the knowledge entries and memories that members choose to share, in its own SQLite database (`team.db`) and in git repositories under a data directory, and it is shipped as one Docker image behind Caddy, which terminates TLS. People join through single-use invitations an admin creates. Each joined machine gets its own bearer token, which the server stores only as a hash. There are two roles, admin and member. The sync client in part 6 pushes batches of items shaped by part 4's payload types and pulls changes after a sequence cursor. An entry push built on a version the server no longer holds is answered `stale` with the server's current version and hash. Per the concepts brief, the database is the authority and the git repositories are an asynchronous, read-only mirror. Device ids are random. Memories are keyed by (device, uid). Pulls are filtered by the remote aliases a device names. The brief adds stricter limits, an instance id, a contract version, and loopback as the default bind address.

**How the existing system works, per these documents**
Today nothing in the product listens on a network. The viewer is a loopback-only `Bun.serve` that checks a random token and the Host header on every request. It keeps its JSON helpers private, opens the person's own store, and stops when idle. Part 1 keeps knowledge as Markdown files with frontmatter, one git repository per scope under `<data dir>/knowledge/`. Every git call goes through a 15 s synchronous runner that ignores the person's git configuration, and an index is rebuilt from the files. Each entry carries a local `version` counter beside a content hash. Part 4 provides `decide` (send, withdraw or keep), the payload types `OutgoingEntry` and `OutgoingMemory`, the uid formats (`workspace:<uuid>`, `project:<alias>:<uuid>`, `<generation>:<row id>`), `redactForSend`, and a `sharing_ledger` that the client writes. One destination, `team`, exists. Releases build five binaries, and there is no Docker image yet.

- F-1 · Major · concept.md, the whole Design sketch, against concepts_brief.md · The concept was not revised after the brief. At least twelve of its statements are now contradicted: the index is rebuilt from the files (brief: the database is the authority, git is a mirror); device id = first 8 characters of the token hash (brief: random); memory keyed by uid alone (brief: (device, uid)); `serve backup` (brief: dropped); `--host 0.0.0.0` default (brief: loopback); `/v1/health` returns the version (brief: it does not); pull items carry `device` (brief: members never see it); every member pulls everything (brief: filtered by alias); tombstones purged after 90 days with no 410; no idempotent retry; no token prefixes; `HEALTHCHECK` on an HTTP route with no client in the image. A reader holding both documents cannot tell which one to build from, and `concept.md` would be built wrong.
- F-2 · Major · concepts_brief.md, Key Decisions · "D-1 to D-16 as recorded on the item" and "D-17 to D-20 … recorded with their defaults" are cited, but none of them appears in the documents I was given. The decisions that bind ADR 0026 cannot be checked against either text.
- F-3 · Blocker · concept.md, Assumptions vs Members, devices · The Assumptions say "a salted SHA-256 at rest", while the design stores `sha256(token)` and looks the device up by that hash. A per-token salt makes lookup by hash impossible unless there is a separate public id in the token. Neither document says which. The brief's random device id needs a way to find the row from the presented token, and that is never defined.
- F-4 · Major · concept.md, Members, devices · "Compares in constant time" comes after a lookup by the hash. What is compared, and against what, is not stated, so an implementer will guess.
- F-5 · Blocker · concept.md, Storage on the server, with part 1's slug rule · Project and shared entries are written to `entries/<slug>.md` in one server repository per scope. Two members can push different uuids under the same slug for the same project alias, because each slug is unique only within the pushing machine's repository. Neither document says what the server does with the second one (refuse it, rename it, or overwrite the file).
- F-6 · Major · concepts_brief.md, Whose version decides · Payload bytes are stored verbatim, so a mirror file's frontmatter `version` is the client's local counter, not the server's version. A person cloning the mirror "read-only from the volume" sees a version number that disagrees with the one the API reports. Nothing says this is expected.
- F-7 · Major · concepts_brief.md, Whose version decides · "The server owns a counter per entry (plus one per applied push)" can be read two ways: one counter per entry, or that plus a global counter. If both exist, what the second counter is for is never said.
- F-8 · Major · concept.md and concepts_brief.md, the sync API · A `stale` answer gives the current version and hash but not the content. Neither document says the client must then pull to get the content it has to merge, or how it pulls a single uid. The only pull is a cursor scan, which is heavy work for one conflict.
- F-9 · Major · concepts_brief.md, Who may write what · "Project items only for the remote aliases it names" does not say how a device names them: a query parameter on pull, a registration on `/v1/me`, or a field of push. Part 6 cannot build against that.
- F-10 · Major · concepts_brief.md, Who may write what · Every device pulls "the members' workspace entries always". Those arrive as `workspace:<uuid>`, which is the same uid form as the receiver's own workspace entries. Where another person's workspace entry lands on the receiving machine, and why everyone should get it, is not explained.
- F-11 · Major · concept.md, POST /v1/push · The result codes are listed, but the `reason` vocabulary is only partly given (`shape` in the concept; `size` and `not-owner` in the brief). There is also no answer defined for a withdraw of an unknown uid, for the 5,000-per-day cap (429 or `refused`?), or for an admin-locked item. A client author cannot write actionable error handling without a closed list.
- F-12 · Major · concepts_brief.md, What the server checks · "A client of another contract is answered 409", but how the client states its contract (a header, a body field, a query parameter) is never said. Neither is the 409's body, so the upgrade message a person sees is undefined.
- F-13 · Major · concept.md, the command and the data directory · The subcommands "run on the host or in the container" assume setup that is never stated. On the host you need the binary, read and write access to a volume owned by user 10001, and safe concurrent SQLite access while the server runs. In the container, `ENTRYPOINT ["wizardingcode-mem","serve"]` makes `docker compose run server invite` and `docker compose exec server wizardingcode-mem serve invite` behave differently, and the documents do not say which command to use.
- F-14 · Major · concept.md, Deployment · Caddy's automatic TLS needs DNS for `SERVER_DOMAIN` pointing at the VPS and ports 80 and 443 reachable. It is also not said whether the GHCR image is public or needs a `docker login`. Without those, the two-file deploy fails, and nothing tells the operator why.
- F-15 · Major · concept.md, Bootstrap, against concepts_brief.md, Logs · The first admin code is printed to stdout and read with `docker compose logs`, so it stays in the Docker log driver for the life of the logs. The brief's rule ("never … a code after its first print") does not cover a code that persists in container logs and in `first-admin.txt` until it is used. The risk is not named.
- F-16 · Major · concept.md, POST /v1/join · The body always carries `member: { name }`, so a second machine's join creates a second member. The brief binds an invitation to an existing member, but gives no route, field or CLI flag for creating a bound invitation, or for "made by the member from a device they hold".
- F-17 · Major · concepts_brief.md, One member, several machines · "A device rotates its own token and keeps its id" names no route, no grace period for the old token, and no client flow.
- F-18 · Major · concepts_brief.md, The feed must survive · "A client that sees a new instance pulls from zero and re-sends what the server lost" does not say how the client knows what the server lost: by comparing its ledger with a full pull? The recovery is said to be handled without saying how.
- F-19 · Major · concept.md, Admin routes · "The last active admin cannot be revoked or demoted", but there is no demote route or command. `serve revoke <device id>` revokes a device, not a member, and member disable exists only as an API route. The concept never says what "revoking" an admin means (all of their devices?).
- F-20 · Nit · concept.md, The command · `serve` is both the long-running server and the parent of its admin subcommands (`serve members`, `serve health`, `serve instance renew`). A developer would expect a separate noun, such as `team` or `server`, and could misread `serve status` as starting the server.
- F-21 · Nit · concept.md, Storage · `projects/<hash of the remote alias>/` does not name the hash or its length. Part 1 uses the first 16 hex characters of SHA-256, and whether they match is unsaid.
- F-22 · Nit · concept.md, Storage · "Rebuilt from the files on start when their heads differ" does not say whose heads differ from what. The brief supersedes this, but the concept's sentence is unparseable on its own.
- F-23 · Nit · concept.md, GET /v1/pull · `limit` has no default. The brief's "one current row per uid since the cursor" conflicts with the concept's per-change items, and the brief's 2 MiB page bound has no stated behaviour when a single item is close to it.
- F-24 · Nit · concept.md, GET /v1/me · The server's time is returned with no stated use (clock skew for `updatedAt`?), and the brief makes memory ordering depend on client `updatedAt`. How skew is handled is not said.
- F-25 · Nit · concept.md, POST /v1/push · `epoch` is required, but the concept never says what the server does with it. Only the brief says it is stored for the audit.
- F-26 · Nit · concepts_brief.md, Analysis · The reviewer lens names (readiness, design, structural, codebase, zoom-out, comprehension) are used as citations with no definition and do not help a new reader.
- F-27 · Nit · brief.md, Context · "The mission (part 3 of the goal)" and concepts_brief.md's "ADR 0018's rule carried across people" / "ADR 0018's worst case" point to texts I was not given. CLAUDE.md describes ADR 0018 only as linked projects.
- F-28 · Nit · concept.md, Deployment · "The two files to copy and the three commands" never names the three commands.
- F-29 · Nit · concept.md, invitations · 26 base32 characters carry 130 bits, not 128. Harmless, but the figures should agree.
