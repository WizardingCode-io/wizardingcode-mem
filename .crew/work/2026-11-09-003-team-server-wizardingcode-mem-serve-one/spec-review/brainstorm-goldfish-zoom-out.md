## Findings
- F-1 · Major · Storage on the server (the case against the hypothesis) · Server-side git repositories make a second source of truth beside `team.db` (`entries` plus the `changes` feed, which no rebuild from files can recreate), couple the server to part 1's client-side runner, and keep withdrawn text in history forever; a single SQLite table with each item's versions does every job the sync needs, so put the brief's "git repository per server scope" clause back to the person as the costliest one before committing to it.
- F-2 · Major · Storage on the server, entries as files · Part 1's runner is fixed to `<data dir>/knowledge/` (`.no-hooks`, `.template`, `.gitconfig-empty`, `GIT_CEILING_DIRECTORIES`), and `writeEntry` rewrites `version`, `author` and `updated` itself, so it cannot store a client's bytes as they arrive. "Reuse part 1's format and runner" fails as written against `<data>/repos/`. Say that the runner takes its root as a parameter and that the server writes raw bytes through it, never through `writeEntry`.
- F-3 · Major · The command and the data directory / Storage · `openDb` hardcodes `DB_FILE = "wizardingcode-mem.db"`, and from part 1 on it applies every `MODULE_SCHEMAS` entry on each open, so `team.db` would get the knowledge and sharing tables. Reuse the `migrate` runner with a file name parameter, the server's own migration list and `moduleSchemas: []`. Do not write a second runner, and do not call `openDb` as it stands.
- F-4 · Major · The sync API, push of a memory · Part 4's D-11 scopes a memory's uid on the server by device, then generation, then row id, because a copied store keeps its generation. Refusing another device's push of the same uid turns a copied store's memories into `refused` when they should be kept apart. The server's `memories` key has to be (device_id, uid), not uid alone.
- F-5 · Major · The sync API, push of an entry · The concept never says who assigns an entry's version after `applied`: the payload's `version` (part 1's local file counter), `baseVersion + 1`, or a counter of the server's. Two clients would build different stale checks. Fix one rule and say what the client writes back to its file and to `sharing_ledger`.
- F-6 · Major · The sync API, withdraw and pull · Tombstones are purged after 90 days, but `pull?since=<seq>` has no answer for a cursor older than the purge. A device offline longer than that silently keeps withdrawn items. Pull needs a "cursor too old, pull from 0" answer.
- F-7 · Major · Storage, withdraw of an entry · The concept does not say what a withdraw does to the entry's file (a removing commit or not). Either way the git history keeps the text that part 4's D-10 refused to let leave through history, and anyone who reads the volume or clones the repositories sees it. Name this limit, or drop git per F-1.
- F-8 · Major · The command, `--host` default · The default is `0.0.0.0` "inside the container", but nothing gives a bare-host default. A bare `serve` on a VPS would then accept bearer tokens over plain HTTP on every interface. Default to `127.0.0.1` and let the image set `--host 0.0.0.0`.
- F-9 · Major · Assumptions vs Members, devices · The Assumptions say "a salted SHA-256 at rest", while the design keeps `sha256(token)` and finds the device by that hash. A salted hash cannot be looked up that way, so readers will build one or the other. Keep the unsalted hash (sound for 256-bit random tokens) and remove "salted".
- F-10 · Major · Storage, `serve backup` · No requirement asks for a backup subcommand with `git bundle` archives, and its restore belongs to part 7's runbook. It also re-implements the `VACUUM INTO` that `backup()` in `src/store/db.ts` already does. Leave it out, or reuse that helper and let part 7 decide on it.
- F-11 · Nit · The sync API, rate limit · A limit of 600 requests a minute per device has no measured abuse and no requirement behind it, for a pilot team of a few people. Move it to the reverse proxy (Caddy) or drop it.
- F-12 · Nit · What exists, the viewer's server · `json`, `problem` and `jsonObject` are private to `src/ui/server.ts`. Reusing them means moving them into a small shared HTTP module, so name that move. Do not write copies of them.
- F-13 · Nit · The sync API, `refused (shape)` · Part 4's payload types are TypeScript types with nothing to check at runtime. Check the payload against the key lists that part 4's contract test pins (AC-15), so that adding a field changes the server too.
- F-14 · Nit · Members, devices (altitude) · Base32 code length, "first 8 characters of hash" for device ids, and a constant-time compare after a lookup by hash are plan-level detail. Eight hex characters (32 bits) can also collide with no stated handling. Use a random device id instead.
- F-15 · Nit · Storage, `members/<member id>/` repositories · The concept does not say who may update another member's workspace entries, or how an admin's "withdraw any item" interacts with the owner's next push. State who may write to each scope.
- F-16 · Nit · Members, bootstrap · `first-admin.txt` puts a second copy of the admin secret on the volume, which is also what gets backed up. Standard output is enough, since compose's logs already show it.
