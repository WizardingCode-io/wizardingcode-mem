## Findings
- F-1 · Blocker · Sync API, memory `send` · The rule "another device's push of the same uid is `refused`" contradicts part 4's contract. Part 4 spec D-11 and Storage (lines 55, 155) say the server scopes every memory uid by the device token (device, then generation, then row id), so a store copied to another machine never collides; and the client's ledger records a received memory as `remote:<server uid>` (line 128). Fix: key server memories by (device_id, uid), refuse nothing on a cross-device uid, and define the server uid that pull returns.
- F-2 · Major · Storage on the server, entries · "Written with part 1's … git runner (author the member's name, committer the server)" cannot be built as part 1 specifies the runner. `runGit`/`gitEnv` take one `identity`, and spec line 129 sets both `GIT_AUTHOR_*` and `GIT_COMMITTER_*` to the writer. Fix: name a separate committer option for the runner, or drop the split.
- F-3 · Major · Storage on the server, index · "The index rebuilt from the files … as part 1's client index is" does not fit part 1's shapes. `rebuildRepo`/`ensureFresh` take a `KnowledgeStore` and a `Repo` resolved by `resolveRepo` through a `ScopeRef` with a `projectId` and `project_aliases`. They write `knowledge_repos`/`knowledge_entries`, and the leases need a `meta` table (meta.ts:3-15). The server's `entries(uid, remote_alias, member_id, …)` in team.db has none of these. Fix: say which part 1 functions are reused unchanged and which the server reimplements.
- F-4 · Major · Storage on the server, repos path · Part 1 ties its isolation to `<data dir>/knowledge`. `knowledgeRoot(dataDir)`, `supportPaths` (`.no-hooks`, `.template`, `.gitconfig-empty`) and `GIT_CEILING_DIRECTORIES=<data dir>/knowledge` are all fixed there (part 1 spec lines 128-129; plan line 21). `<data>/repos/` falls outside them. Fix: use `<data>/knowledge/…`, or make the root a parameter of the runner.
- F-5 · Major · The command and the data directory · "Its own SQLite database, its own migrations" has no opener today. `openDb` hard-codes `DB_FILE = "wizardingcode-mem.db"` (db.ts:35, 165), defaults to the memory `MIGRATIONS` (db.ts:172), and with part 1 also applies `MODULE_SCHEMAS` on every open. `openExisting` is fixed to the same file (db.ts:194). Fix: name a file-name option and a schema list for team.db, or a separate opener.
- F-6 · Major · Backups · `serve backup` writes under `<data>/backups/`. That is the folder `openDb`'s migration backup uses (db.ts:36, 73-83), and that backup prunes every `.db` file there except the newest 2. A `VACUUM INTO` copy left there as `.db` would be deleted by the next upgrade. Fix: use a different folder, or a non-`.db` archive only.
- F-7 · Major · Storage on the server, git per item · Part 1's runner is `Bun.spawnSync`, up to 15 s per call, and blocks its process (part 1 spec line 126, NFR line 330). In a multi-user `Bun.serve` process, every push stalls all requests, `/v1/health` included. Fix: state an async runner (`Bun.spawn`) or a single writer queue for the server.
- F-8 · Major · Sync API, push · A 200-item push that commits per item can run past `Bun.serve`'s default `idleTimeout` of 10 s, and Bun then closes the connection. server.ts:693 sets no timeout. Fix: set `idleTimeout` (at most 255 s) or call `server.timeout(req, …)`, and bound push time.
- F-9 · Major · Sync API, limits · The 1 MiB body cap and 200 items per push do not fit together. Part 1 allows entries of 256 KiB (`ENTRY_MAX_BYTES`), so four large entries already fill a batch. Fix: enforce the cap with `Bun.serve`'s `maxRequestBodySize` (413), and tell part 6 to batch by bytes as well as by count.
- F-10 · Major · Sync API, versions · Whose version `baseVersion`/`current.version` is stays undefined. Part 4 says an `OutgoingEntry`'s version and hash are part 1's local file counter and the hash of the file's bytes (part 4 spec line 237). If the server rewrites `version` in the frontmatter, its hash never equals the client's, and `decide` step 5 resends forever. Fix: state that the server stores the client's bytes verbatim, or that it owns a separate counter, and say which hash the ledger records.
- F-11 · Major · Hypothesis / Sync API · Part 4's Goals say "the team server and the sync client call `decide` and nothing else decides" (part 4 spec line 21). The concept never has the server call it (the server has no client policy), and it does not say what the server does with the pushed `epoch`. Fix: state that the server does not decide and only stores and audits `epoch`, or what it checks against it.
- F-12 · Major · Members, devices · Two statements conflict. The design keeps `sha256(token)` and derives the device id from the hash for lookup; the Assumptions say "a salted SHA-256", and a salted hash cannot be looked up. A lookup by unsalted hash also makes the "constant time" compare moot. Fix: choose unsalted SHA-256 with lookup by hash; `Bun.password` is not needed for high-entropy tokens.
- F-13 · Major · The command, defaults · "`--host 0.0.0.0` inside the container" has no way for the binary to know it is inside a container. A single default of 0.0.0.0 on a host exposes plain HTTP. Fix: default to 127.0.0.1, and set `--host 0.0.0.0` in the Dockerfile's CMD or ENV.
- F-14 · Major · The command, data directory · `WIZARDINGCODE_TEAM_DATA` breaks the `WIZARDINGCODE_MEM_*` naming (paths.ts:13-21; settings.ts:10-26). A `/data` default for host subcommands (`serve members` run on the host) points at the wrong place. `logError` without a dataDir writes to `defaultDataDir()` under the non-root user's HOME or `WIZARDINGCODE_HOME` (log.ts:21), which is off the volume. Fix: name the variable in the product's convention, and pass the server data dir to every log call.
- F-15 · Major · Observability · There is no logging design for a long-running process. The only logger appends redacted error lines of at most 300 characters to `<dataDir>/logs/wizardingcode-mem.log` (log.ts:21-37), so `docker compose logs` shows nothing but the first-admin code. Fix: name the stdout/stderr line format (request id, device id, route, status, ms, per-item result counts for push), a log level, and what is never logged (tokens, codes after first print, payloads).
- F-16 · Major · Observability · Nothing can be traced at 3 AM. `audit` has no reader (no route, no `serve audit`), `serve status` has no defined content, and `/v1/health` returns only `{ok, version}` without checking that team.db opens, git is present (`requireGit`) or the repositories are clean. Fix: define `serve status` (members, devices, last_seen, changes seq, repository heads and dirty state, git version), an audit listing, and a health that fails on a broken store or a missing git.
- F-17 · Major · Deployment, Dockerfile · `debian:bookworm-slim` ships no curl or wget, so `HEALTHCHECK` on `/v1/health` has nothing to run. Fix: give the binary a probe subcommand (for example `serve health`), or add a tool to the image.
- F-18 · Major · Deployment, signals · With `ENTRYPOINT ["wizardingcode-mem","serve"]` the binary is PID 1, which has no default SIGTERM action. `docker stop` then waits and SIGKILLs it mid-commit, leaving part 1's intent record. Today only ui.ts:11-14 installs handlers. Fix: SIGTERM/SIGINT handlers that stop accepting requests and finish the current item, plus `init: true` (or tini) in compose.
- F-19 · Major · Deployment, release · `release.yml` has `permissions: contents: write` only (line 11-12). Pushing to GHCR needs `packages: write`, a login, `docker/setup-buildx`/QEMU, and a job after `build` that takes the `dist/` artifact. The Dockerfile must map `TARGETARCH` amd64→`wizardingcode-mem-linux-x64` (a baseline build) and arm64→`-linux-arm64` (build.ts:16-17), and `*-*` prerelease tags must not move `latest`. Fix: list these in the concept.
- F-20 · Major · Members, invitations · Rate limiting is per device, but `POST /v1/join` is unauthenticated and has no device, so failed joins are neither limited nor logged. Fix: a per-IP limit on join behind the proxy (`X-Forwarded-For` trusted only from Caddy; `server.requestIP` otherwise sees Caddy) and an audit row per failed join.
- F-21 · Nit · What exists today · `json`, `problem` and `jsonObject` are module-private in server.ts:150-178, not exported, so the server cannot import them without extracting them. The viewer's token check is a plain `!==` (server.ts:254), not constant time, so it is no template for the device check; use `node:crypto` `timingSafeEqual` where a compare is needed.
- F-22 · Nit · What exists today · The viewer's Host check accepts only `127.0.0.1:<port>` and `localhost:<port>` (server.ts:238). Behind Caddy the Host is the domain. The concept does not say whether the server checks Host (against `SERVER_DOMAIN`) or drops the check.
- F-23 · Nit · The command · `serve` must join `COMMANDS` as a lazy `import("./commands/serve.ts")` (main.ts:11-28). It must use no top-level await (bytecode builds emit CommonJS, main.ts:78), and its `run` must stay pending until a signal. `main` runs `applyLegacyEnv` and `migrateLegacyData()` (legacy.ts:68-111) before every command, the server included, against the container user's HOME. USAGE lists no commands at all.
- F-24 · Nit · The command · Subcommands share the word with the server: `serve invite` against `serve --port`. With the ENTRYPOINT, `docker compose exec server wizardingcode-mem serve invite` and `docker compose run server invite` read differently. The runbook needs one form.
- F-25 · Nit · Part 4's contract · The ledger columns are `item_kind`, `item_uid`, `policy_epoch`, `at`, `withdrawn_at` (part 4 spec lines 125-136), not "kind, uid, epoch, times".
- F-26 · Nit · Bootstrap · The first-admin code printed to stdout stays in `docker logs` after it is used. Say that it expires (72 h) and is single use, or print only the path of `first-admin.txt`.
- F-27 · Nit · Deployment · A non-root user with `VOLUME /data`, plus `openDb`'s 0700/0600 modes (db.ts:164, 177), breaks on a host bind mount owned by another uid. State the uid and gid, or a named volume only.
- F-28 · Nit · Deployment, CI · ci.yml builds and runs every binary (`__spike all`) but never builds the image, so the first image build is at release. Add a buildx build plus a `/v1/health` smoke test in CI.
- F-29 · Nit · Tests · The brief wants in-process HTTP tests, as ui-settings.test.ts does with `startUi({ port: 0, now, env })`. The concept names no `startTeamServer(options)` with `dataDir`, `port: 0`, `now` and `env` injection for that.
