## Findings
- F-1 · Blocker · Members, devices, invitations, roles · `POST /v1/join` always takes `member: { name }` and `invitations` has no target member column, so a second machine's invitation creates a new member, not a second device of the same one. The "two devices of one member" model, the "own items included" pull rule and per-member ownership cannot be built as written.
- F-2 · Major · The sync API (push, memory send) · Part 4 (D-11, Storage) says the server scopes a memory uid by device, then generation, then row id, so that copied stores never collide. The concept instead keys `memories(uid)` on the client's `<generation>:<row id>` alone and refuses a second device's push. A copied store's memories are refused for good instead of kept apart, which contradicts part 4's contract.
- F-3 · Major · Members, devices / Storage · A memory belongs to a device, and a device is one token with no rotation path. After a reinstall, a lost laptop, a revoked device or a disabled member, those memories can never be updated or withdrawn by their owner. What happens to a departed member's items (kept, withdrawn, reassigned) is not decided anywhere.
- F-4 · Major · Members, devices, invitations, roles · The device id is "the token's first 8 characters of hash". This ties identity to the secret, so any future rotation changes the id. The id is also only 32 bits for lookup, and it is published to every member through pull's `device` field and the admin routes. The id should be an independent random value.
- F-5 · Nit · Assumptions vs Members, devices · The token at rest is decided twice and differently: "a salted SHA-256" under Assumptions, plain `sha256(token)` in the design. Also, a constant-time compare after a hash-keyed lookup adds nothing.
- F-6 · Major · The sync API (stale check) · Which version is the authority is undefined. Part 1's `version` is a local counter inside the client's frontmatter, and part 4 calls version informational with the hash as judge. Here, push compares `baseVersion` first and `baseHash` second. Neither side says whether the server assigns current+1 or takes the payload's `version`, or what the client writes into its file after `applied`. Client and server counters will drift.
- F-7 · Major · Storage on the server (files) · If the server rewrites the entry file with "part 1's entry format" (author, version), its bytes, and so part 1's hash of the bytes, differ from the client's. Every later `baseHash` check then fails. If it writes the client's frontmatter string verbatim, the server holds no authority over `version` or `author`. The design must choose one.
- F-8 · Major · Storage on the server (repositories) · The server has no `taxonomy.md`, and area ids come from each member's own workspace taxonomy (part 1 D-9). The server can neither validate `area` nor tell that two members' `sales` mean the same thing. The shared repository's taxonomy is not synced.
- F-9 · Major · Storage on the server (`members/<member id>/`) · Workspace entries are stored per member but pulled by every member under the uid `workspace:<uuid>`, which carries no member. Undecided: where a receiving client files another member's workspace entry, and whether its edit pushed back targets the author's repository. `entries(uid)` also collides when two members hold a copied file with the same UUID.
- F-10 · Major · Storage on the server (`projects/<hash of the remote alias>/`) · Part 4 binds the level to "the first remote alias by name". A project with two remotes can bind different aliases on two machines, which gives the server two repositories and two uids for one entry. Nothing on the server reconciles aliases.
- F-11 · Nit · Storage on the server (tables) · `entries.scope` and `remote_alias` repeat what `entryUid` already encodes, and `memories.remote_alias` repeats the JSON payload. These are decided in two places and can disagree.
- F-12 · Major · The sync API (tombstone) · Tombstones are pruned after 90 days, but pull has no cursor floor. A device whose cursor is older, or a `since=0` full pull, never learns that an item it holds was withdrawn. It needs a "cursor too old, reconcile" answer (for example 410 with the full id set).
- F-13 · Major · The sync API (push) · Re-sending a withdrawn uid is undefined: is it a resurrection, and with what `baseVersion`? The result `withdrawn` is ambiguous between "your withdraw applied" and "refused because tombstoned".
- F-14 · Major · The sync API (roles) · Entry ownership is undefined. `entries.member_id`/`device_id` reads as last writer, yet only "an admin may withdraw any item" is stated. Undecided: whether a member may withdraw an entry another member created or edited, and whose policy's `withdraw` wins.
- F-15 · Major · Storage on the server (git history) · Withdraw only tombstones the index. The withdrawn text stays forever in the server's git history, in the read-only clones and in `git bundle` backups. That is exactly what part 4 rejected `git push` for (D-10), and it breaks the Sharing page's promise that a lowered level is withdrawn.
- F-16 · Major · Storage on the server / Backups · There are three sources of truth: `entries` is rebuilt from the files, while `changes` and `memories` live only in the database. A rebuild does not regenerate the feed. `VACUUM INTO` plus per-repository bundles is not one atomic point. A restore that lowers `seq` below clients' cursors makes every client silently skip changes, so the feed needs a server epoch or id the client checks.
- F-17 · Major · Storage on the server (git runner) · Part 1's runner, leases, `ensureFresh` and index are bound to the client store object: leases in the client's `meta`, the `knowledge_repos` and `knowledge_entries` tables, a fingerprint over `proposals/`. Reusing them "as part 1's client index is" either couples `team.db` to the client's module schema or forks a second rebuild path that will drift.
- F-18 · Major · The sync API (`shape` refusal) · Refusing any unknown payload field per item ties the server to the exact pinned key sets of `OutgoingEntry`/`OutgoingMemory`. Any field part 4's contract test lets grow means a lockstep upgrade of the server and every member. There is no contract version in `/v1/me` or in push.
- F-19 · Nit · The sync API (`epoch`) · Push carries the client's policy epoch, but no table stores it and no rule uses it. It is decided but has no reader.
- F-20 · Major · The sync API (limits) · Part 1 allows entries of 256 KiB, so 200 items cannot fit in a 1 MiB body. It is undefined whether an oversized batch is a 413 or a per-item answer. Pull's 500-item page has no byte bound, and the limits are not published to the client (for example in `/v1/me`).
- F-21 · Nit · The sync API (pull) · `changes` keeps one row per change while the payload is read from the current row. A uid changed several times since the cursor appears several times with the same payload, so the feed should be compacted per uid. A `stale` answer carries no payload either, so the client must pull to merge, which should be said.
- F-22 · Major · The command and the data directory · `--host 0.0.0.0` is stated as the default "inside the container", and the default for a bare-host `serve` is unstated. Today nothing in the product listens on a network interface. The binary's own default should be loopback, with the image setting 0.0.0.0 explicitly.
- F-23 · Major · Deployment (image) · The fixed non-root uid owning `/data`, the volume layout (`team.db`, `repos/`, `backups/` and the bootstrap file in one volume) and port 8787 baked into the Caddy config are hard to change once teams have volumes. Backups on the same volume as the data are not backups.
- F-24 · Nit · Deployment (release) · `release.yml` has only `contents: write`, and pushing to GHCR needs `packages: write`. The image must rename `wizardingcode-mem-linux-x64` and `wizardingcode-mem-linux-arm64` to `wizardingcode-mem`. The `/v1/health` version disclosure on an unauthenticated route is a small leak.
- F-25 · Nit · Bootstrap · The first-admin code stays in Docker's log driver after use. Undecided: what happens when the 72 h code expires unused, and whether the `serve` CLI subcommands, run in the container as root or the image user, can read `team.db` and write `first-admin.txt` with the volume's ownership.
- F-26 · Nit · Roles · "The last active admin cannot be revoked or demoted", but no demote or role-change route exists. What an admin-role invitation used by an existing member means is undefined.
- F-27 · Nit · Storage on the server (`audit`) · `audit` and `changes` grow without a bound. Only tombstones have a retention rule.
