# design findings for 2026-11-09-003-team-server-wizardingcode-mem-serve-one
reviewer: goldfish-design
read: .crew/work/2026-11-09-003-team-server-wizardingcode-mem-serve-one/concept.md, brief.md, concepts_brief.md (whole); .crew/work/2026-11-09-002-sharing-policy-per-project-local-only-kn/spec.md (whole); .crew/work/2026-11-08-003-knowledge-store-entries-as-markdown-with/spec.md (whole); src/ui/server.ts; src/store/db.ts; src/store/meta.ts; src/core/redact.ts; docs/adr/0018-linked-projects.md

## Findings
- F-1 · Major · concepts_brief "Who may write what" · Project items are filtered by "the remote aliases it names", and the device itself names them. Any member can name a guessable alias (github.com/acme/client-x) and pull that project's entries and memories. This is a client-side filter, not authorisation, yet the text presents it as ADR 0018's protection across people; a builder would believe members are kept out of projects they do not work on.
- F-2 · Major · concepts_brief "Who may write what" · A withdraw is accepted from "the last writer's member". Any member may push a new version of a shared or project entry and so become the last writer, which means any member can withdraw any team entry in two calls. The ownership rule does not hold.
- F-3 · Major · concepts_brief "Who may write what" · Any member may overwrite any shared or project entry on the current base. Nothing defines how an admin rolls a vandalised or mistaken version back: "reinstate" names no target version, and the server keeps no earlier payloads it could serve.
- F-4 · Major · concepts_brief "One member, several machines" · A member may mint an invitation bound to themselves "from a device they hold". A stolen device token can therefore join a fresh device. Revoking the stolen device cancels only unused invitations, so the attacker's redeemed device survives the revocation; nothing cascades or tells an admin.
- F-5 · Major · concepts_brief "One member, several machines" vs "Observability" · Memories are pulled as remote:<device id>:<uid>, but the feed promises members "never the device id (admins see it)". The uid itself carries the device id, so either the promise is false or the client cannot form the uid.
- F-6 · Major · concepts_brief "One member, several machines" · Token rotation has no overlap. If the answer carrying the new token is lost after the server commits it, the device holds a dead token and is locked out until an admin re-invites it. The design needs a grace period or a two-phase swap: the old token stays valid until the new one is first used.
- F-7 · Major · concept "Members, devices…" · The joiner chooses their own member name. The name becomes the mirror's commit author and the feed's writer name, and names are not unique, so anyone with an invitation can appear as "André". The admin should fix the name when inviting, or the server should show the member id beside it.
- F-8 · Major · concepts_brief "Limits" · "10 joins a minute per source address": behind Caddy every request comes from Caddy's container address. The limit either throttles all joins as one source or, if X-Forwarded-For is trusted without a trusted-proxy rule, can be spoofed. The same unknown source address goes into the audit. Neither the header nor the trust rule is named.
- F-9 · Major · concepts_brief "Whose version decides" · The hash is "the client's" and the payload is stored verbatim, and nothing says the server recomputes it. A client that sends a hash that does not match its bytes makes every other client's decide see "received-same" and never take the change, and it makes the idempotent "applied" answer lie. The server must recompute the entry and memory hashes from the payload.
- F-10 · Major · concepts_brief "Whose version decides" · Idempotency rests on "hash equals current". Suppose a push was applied, its answer was lost, and another member then pushed on top: the retry answers stale against a version built on the client's own. The client then shows a false conflict. There is no idempotency key, and no check of the hash against the item's earlier versions.
- F-11 · Major · concepts_brief "Three stores" vs "repositories … the team's version history" · `serve repair` "rewrites [the mirror] from the database", but the database keeps only the current payload, plus 90 days of change rows with no payloads. A repair therefore destroys the history the mission keeps the mirror for. Either the database stores every version's payload, or repair is not a recovery path.
- F-12 · Major · concepts_brief "The feed must survive…" · The instance id is renewed by a manual runbook step. If the operator forgets it after a restore, `seq` restarts below the clients' cursors, and clients silently skip every item written until new numbers pass their cursor. The server could detect this itself: keep a high-water mark outside team.db, or derive the instance from the restored database's own identity.
- F-13 · Major · concepts_brief "The feed must survive…" · The 410 answer needs a stored purge horizon (the highest seq of a purged tombstone), and none is defined. A full pull after a 410 returns current rows only, so the client must treat an absent uid as deleted, and the answer does not mark itself as a complete snapshot that allows that.
- F-14 · Major · concepts_brief "The feed must survive…" · After a new instance, "re-sends what the server lost" meets server version counters that were reset. Every client's ledger baseVersion is stale, every member re-sends at once, and the conflicts that follow have no defined resolution. That reconciliation contract is unstated for part 6.
- F-15 · Major · concept "Storage" + Non-goals "purging history" · A secret that redaction missed, once withdrawn, stays forever in the mirror's git history and in the database row. There is no admin erase path that rewrites the mirror and removes the payload, and nothing for a departed member's erasure request. This is the incident-response gap a server holding private memories must name.
- F-16 · Major · concepts_brief "What the server checks" · The server never runs `findSecrets`, so redaction depends entirely on every member's client version being correct. One buggy or old client leaks to the whole team. A server-side check that refuses with `refused secret` costs one pass over at most 256 KiB and is not policy.
- F-17 · Major · concepts_brief "Limits" · There is no total or per-member storage quota, and no behaviour at disk full. 5,000 items × 256 KiB is about 1.25 GiB a day per device into team.db plus the git mirror on one volume. The mirror can fill the disk and take the database down with it (SQLITE_FULL mid-push, a failed WAL checkpoint).
- F-18 · Major · concepts_brief "Limits" · The cap of 5,000 applied items per device per day collides with a first sync. A store at `all` can hold tens of thousands of eligible memories (ADR 0018 records 67,988 active memories on the author's store), so an initial upload takes days. The answer past the quota (429 or refused) and how part 6 shows it are not said.
- F-19 · Major · concepts_brief "The server is a process" · Part 1's runner is `Bun.spawnSync`, up to 15 s a call. An "asynchronous" queue in the same process that reuses it still blocks the event loop on every commit, stalling every request and the health probe. The runner must gain a `Bun.spawn` variant, and the text only says it "takes its root as a parameter".
- F-20 · Major · concept "The command" · The subcommands run "on the host or in the container" on the same files. A `docker compose exec` or `run` as root creates team.db-wal and -shm or git objects owned by root, and the server (user 10001) can no longer open them. The design also sets no lease or lock between `serve repair` or `serve invite` and the running server's mirror queue and writes.
- F-21 · Major · concept "Storage" (shared scope) · The text does not say the server refuses a new uid whose slug already exists in its scope. Two members creating `entries/pricing.md` in shared with different UUIDs would collide in the mirror, where the later file overwrites the earlier one.
- F-22 · Major · concepts_brief "Who may write what" · Members' workspace entries are pulled by everyone as `workspace:<uuid>` (part 4's uid form). The server's key for them is not said: uid alone, or (member, uid). The form in which another member's workspace entry is pulled is also unspecified, and it would share the receiver's own workspace uid namespace.
- F-23 · Major · Deployment / Non-goals "backups beyond the runbook" · One VPS, one volume, one process, and the only backup is a manual snapshot with the server stopped, so in practice there is none. The server becomes the only copy of a departed member's items. A hot backup of team.db (`VACUUM INTO`, which db.ts already uses) needs no downtime, and the "two instants" objection to it falls away because the mirror is derived.
- F-24 · Major · concept "Assumptions" vs "Members…" · "A salted SHA-256 at rest" contradicts the design's `sha256(token)` used for lookup. A per-row salt makes lookup by hash impossible, so a builder following the assumption writes a scan of every device. Say unsalted SHA-256 of a 256-bit secret, or put the device id inside the token.
- F-25 · Nit · concept "Bootstrap" · The first admin code is printed to stdout, kept indefinitely by Docker's json-file driver (and by any log shipper), and written to first-admin.txt, which a volume snapshot captures. What happens when it expires unused is unsaid. So is the rotation of Docker's logs, which share the host disk.
- F-26 · Nit · concepts_brief "Limits" · "413 before parsing" needs `maxRequestBodySize` set on Bun.serve (its default is far above 1 MiB) and `request_body max_size` in Caddy, and authentication checked before the body is read. The 1 MiB cap on unauthenticated join bodies is not tied to either. A memory payload's own size cap is not stated.
- F-27 · Nit · Deployment · Nothing refuses plain HTTP from a source that is not the proxy. One `ports: 8787:8787` added by an operator (Docker's published ports bypass ufw) sends bearer tokens in clear. The design could require `X-Forwarded-Proto: https`, or bind to the compose network only.
- F-28 · Nit · Deployment · No `read_only`, `cap_drop: ALL`, `no-new-privileges`, image pinning by digest for bookworm-slim and Caddy, or plan for base-image CVE rebuilds.
- F-29 · Nit · concept "Members…" · `devices.last_seen_at` is written on every request, which means a write transaction for every authenticated request (up to 600 a minute per device). It needs a throttle, for example once a minute.
- F-30 · Nit · concepts_brief "What the server checks" · `contract: 1` answered 409 for any other contract makes every client fail at once on the next bump; accepting N and N-1 would avoid that. How a client declares its contract (header or field) is not said.
- F-31 · Nit · src/ui/server.ts fetch catch · The viewer answers 500 with `error.message`. If `serve` copies that pattern, internal paths and SQL text go to internet clients; the server should answer a request id only.
- F-32 · Nit · concept "Storage" · The `audit` and `changes` tables and the per-commit mirror repositories have no retention or gc rule. Commit counts and object stores grow without bound.
