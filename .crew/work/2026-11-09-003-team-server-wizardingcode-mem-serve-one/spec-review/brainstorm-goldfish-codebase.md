## Findings
- F-1 · Major · concepts_brief "The server is a process, not a hook" · The brief says the mirror queue "runs git asynchronously". Part 1's runner is synchronous (part 1 plan.md:21 `runGit` returns `{ stdout, exitCode }`; spec.md:126 says it uses `Bun.spawnSync` with a 15 s timeout). Each mirror commit would therefore block the event loop for up to 15 s, stalling pushes and the health probe. The seams paragraph never names an async variant. Fix: name an async runner built on `Bun.spawn`, or a worker, as a change to part 1's runner.
- F-2 · Major · concepts_brief "Reuse with the right seams" · The brief says part 1's runner only needs its root as a parameter and its author split from its committer. The code it plans to reuse needs much more. `runGit` takes a `KnowledgeStore` from `openStore({ db, dataDir, … })` and calls `store.renew`. `withRepoLeases` uses `claimLease` on a `meta` table (src/store/meta.ts:73-86). `openRepo` goes through `resolveRepo`, which reads `knowledge_repos`. `ensureRepo` commits as `personAuthor(store)` and writes a default nine-area `taxonomy.md` (part 1 plan.md:21-23, spec.md:122). A reader would build a team.db with no `meta` table and a server that commits "you" with the default taxonomy. Fix: list each seam and what team.db must hold.
- F-3 · Major · concepts_brief "Observability" · Git failures in the mirror would not appear in `docker compose logs`. Part 1's runner writes them with `logError` to `<dataDir>/logs/wizardingcode-mem.log` (part 1 plan.md:21; src/util/log.ts:21-37), a file of at most 1 MiB with one rotation, not to standard output. Anyone on call at 3 AM would see only "mirror backlog" in `serve status` and no cause. Fix: route server-side `logError` calls to the JSON lines on standard output, and add the last mirror error, its repository and its time to `serve status`.
- F-4 · Major · concepts_brief "Reuse with the right seams" · The plan moves `json`, `problem` and `jsonObject` into `src/http/respond.ts`. The viewer's catch-all answers a network client with `problem(500, error.message)` (src/ui/server.ts:696-702), which can hold SQLite errors and file paths. Its token check `presented !== token` (src/ui/server.ts:254) is a plain comparison. Neither suits a server on a network. Fix: say the server's 500 answers carry only a request id, and that this request id also goes back to the caller in a response header, so a member's report can be found in the logs.
- F-5 · Major · concepts_brief "Limits that fit together" · The limit of "10 joins a minute per source address" cannot work behind Caddy. The only address the server would see (`server.requestIP`) is Caddy's on the compose network, so every join shares one bucket and one attacker locks everyone out. Fix: read `X-Forwarded-For` only from the trusted proxy (configured by environment), and log the address the limit was applied to.
- F-6 · Major · concepts_brief "Deployment that fails safe" · Bun.serve listens on `0.0.0.0` when `hostname` is left out. Today the viewer is loopback only because it passes `hostname: "127.0.0.1"` explicitly (src/ui/server.ts:693-695). The "loopback by default" rule therefore has to be an explicit default in the code, plus a test. Without it, a plain `Bun.serve({ port })` exposes the server.
- F-7 · Major · concepts_brief "Reuse with the right seams" · The brief says the core migration runner will take a file name. `openExisting` also hard-codes `DB_FILE` and compares against the core `LATEST_VERSION` (src/store/db.ts:190-209), so a `serve status` built on it would look for the wrong file or throw `SchemaTooNewError`. `backup()` writes `wizardingcode-mem-<ts>-v<n>-<pid>.db` into `<dir>/backups` (src/store/db.ts:72-84), which would put misleading copies on the volume. Also, a list of migrations can already be passed today (`OpenOptions.migrations`, db.ts:55, marked "For tests"). Fix: name `openExisting` and the backup's file prefix in the seam.
- F-8 · Major · concepts_brief "Whose version decides" · Under part 4's contract, an entry's `version` is part 1's local file counter, and that counter sits inside the `frontmatter` the server stores verbatim (part 4 spec.md:237). The ledger's `version` column is that same counter. The brief has the server's own counter recorded in the client's ledger and pushed back as `baseVersion`. The result is two different "versions" for one entry: one in the git mirror's file bytes and one in the API. Fix: state which version the mirror's frontmatter carries and which version the ledger column means, or rename the server's counter.
- F-9 · Major · concepts_brief "Whose version decides" · An entry's `hash` is the first 16 hex of the SHA-256 of the file's bytes (part 4 spec.md:237; part 1 spec.md:249). `OutgoingEntry` sends `frontmatter` and `body` separately, and part 4 never defines how they are joined back into a file. So the server cannot check that `hash` matches the content. Idempotent retries and stale checks would then depend on a hash the client asserts. Fix: pin the joining rule (with part 4 or part 6), and have the server recompute the hash and refuse a mismatch with `hash`.
- F-10 · Major · concepts_brief "What the server checks" · The server "parses the frontmatter" with part 1's parser. Part 1's `parseEntry(text, slug, taxonomy | null)` treats an `area` outside the taxonomy as a validation failure, which forces the entry to `draft` with a problem (part 1 spec.md:102; plan.md:14). Meanwhile the shared taxonomy stays a client file (a non-goal here), so the server has none. Fix: say what null means for the area check on the server, or every entry is a problem.
- F-11 · Major · concepts_brief "One member, several machines" · The brief says a member's name becomes the commit author. Part 1 requires an author name of 1 to 80 characters, no newline, not starting with `agent:`, and derives the `.invalid` e-mail from it (part 1 spec.md:96, AC-9). The join route's `member.name` has no rule. Fix: validate it at join with part 1's rule.
- F-12 · Major · concepts_brief "One member, several machines" vs "Observability" · Pulled memories are named `remote:<device id>:<uid>`, yet the pull feed promises members "never the device id (admins see it)". The uid itself would hand every member every device id. Fix: use an opaque per-device alias in the pulled uid, or drop the promise.
- F-13 · Major · concept "Assumptions" · The concept says "a salted SHA-256 at rest". It also says the server hashes the presented token and looks the device up by that hash, and the brief keeps the lookup. A salt per row makes an indexed lookup impossible. Fix: say "unsalted SHA-256 of a 256-bit token, looked up by index". This also makes the "compare in constant time" step moot; if it stays, name `timingSafeEqual` from node:crypto, which Bun has.
- F-14 · Nit · concept "What exists today (facts from the repository)" · `module_migrations`, `runGit`, `gitEnv`, `rebuildRepo`, `ensureFresh`, `decide`, `OutgoingEntry`, `redactForSend` and `sharing_ledger` are listed as facts, but none exists in src/ (no src/modules/knowledge, no src/sharing; db.ts has only `user_version`). They exist only in the part 1 and part 4 plans, where they match. Fix: put them under a heading for planned work, not "exists today".
- F-15 · Nit · concept "What exists today" · "A random token in the URL checked on every request" is not quite true: fonts under `/assets/` are served without the token (src/ui/server.ts:241-250).
- F-16 · Nit · concepts_brief "One member, several machines" · The brief says memory uids keyed by uid alone "break part 4's device scoping". Part 4 scopes memory uids by the store's generation (`memoryUid(generation, id)`, eight random hex characters, part 4 plan.md:13 and 18), not by the device. That is exactly why a copied store collides. Fix: correct the wording.
- F-17 · Nit · concepts_brief "Reuse with the right seams" · "`serve` skips the legacy migration" is a change to `main`. `applyLegacyEnv` and `migrateLegacyData` run before any command module loads (src/cli/main.ts:54-73). The same is true of every `serve health` probe the HEALTHCHECK runs. Fix: name src/cli/main.ts as the file that changes.
- F-18 · Nit · concepts_brief "One member, several machines" · The new `wcm1_` and `wci1_` rules belong in `PATTERNS` (src/core/redact.ts:28-80). Note that `Bearer wcm1_…` is already caught by the `auth-header` rule (line 60), because base64url fits its character class. A test should pin which rule wins for the bare token.
- F-19 · Nit · concepts_brief "The server is a process, not a hook" · The viewer stops with `server.stop(true)` (src/ui/server.ts:221), which closes connections at once. "Finish the item in flight" needs `stop()` without force plus the 20 s deadline. Also, `idleTimeout` in Bun.serve has a maximum of 255 s; 120 is within it.
- F-20 · Nit · concepts_brief "Limits that fit together" · "413 before parsing" maps to Bun.serve's `maxRequestBodySize`. Name it, so nobody builds the check after `request.json()`.
- F-21 · Nit · concept "Storage on the server" · "A person can clone them read-only from the volume" conflicts with modes already in place. Part 1 creates folders 0700 (spec.md:122) and `openDb` uses 0700 and 0600 (db.ts:164, 177), all owned by uid 10001, so a host user cannot read them without root.
- F-22 · Nit · concept "Members, devices, invitations, roles" · 26 base32 characters carry 130 bits, not 128. Also, `WIZARDINGCODE_TEAM_DATA` breaks the `WIZARDINGCODE_MEM_*` naming that settings.ts and paths.ts use.
- F-23 · Nit · concepts_brief "Deployment that fails safe" · The release workflow grants only `contents: write` at the top level (release.yml:11-12). Its binaries reach `publish` only through the `sign` job's `binaries` artifact, so an image job must depend on `sign` and download that artifact. Also, `TARGETARCH` amd64 has to map to `wizardingcode-mem-linux-x64`, which is built from `bun-linux-x64-baseline` (scripts/build.ts:16).
