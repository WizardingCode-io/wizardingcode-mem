## Findings
- F-1 · Blocker · Storage on the server / sync API (push) · An applied entry touches three stores: the file and git commit, then the `entries` row, then the `changes` row and the `audit` row. The concept gives no order between them and no intent record or recovery step. A kill after the commit and before the SQLite commit leaves HEAD ahead of the index. The rebuild-on-start may restore the `entries` row, but the `changes` row cannot be rebuilt from the files, so no pull ever delivers that item. The concept must say which store commits first and how startup finishes or reverts a half-applied item.
- F-2 · Blocker · Storage on the server (entries as files) · The `OutgoingEntry` payload carries the client's `frontmatter` text, `version` and `hash` (a hash of the file's bytes). The concept does not say whether the server writes those bytes verbatim or re-renders the entry with its own version, author and timestamps. If it re-renders, the server's hash never equals the client's ledger hash, and part 4's `already-sent` and `received-same` checks fail on every item. If it writes verbatim, the client's local version counter becomes the server's version, and two members' counters collide. Either way the stale check in `push` cannot be built.
- F-3 · Major · Storage on the server (reuse of part 1) · Part 1's runner is bound to the client. `KnowledgeStore` needs the client `db`. The support paths and `GIT_CEILING_DIRECTORIES` are `<data dir>/knowledge/` (the server uses `<data>/repos/`). The leases are `knowledge.lease:` rows in the client's `meta` table. `openRepo` goes through `resolveRepo`, which reads `knowledge_repos` and `project_aliases`. The concept does not say which functions get a server-side store type, or what replaces the leases and the repository lookup.
- F-4 · Major · Storage on the server (commit identity) · The concept wants the member as author and the server as committer. Part 1's `commitPaths(…, identity, …)` and `gitEnv` set author and committer from one `Identity`, so a signature change is needed. The concept also does not say how the server checks the frontmatter's `author` against the member. As written, a member could push `author: "someone else"` or `agent:claude-code`, and the server's files and history would record that name.
- F-5 · Major · Storage on the server (index rebuild) · "Rebuilt from the files on start when heads differ" cannot rebuild `member_id`, `device_id`, `remote_alias` or `withdrawn_at`, because no file holds them. Part 1's `parseEntry` checks `area` against the root's `taxonomy.md`, and the server repositories have none. A rebuild with part 1's code would mark every entry a problem with status `draft`. The concept must name the server's own rebuild and say what it does without a taxonomy.
- F-6 · Major · Storage on the server (scopes) · Files are addressed as `entries/<slug>.md`, but the server indexes entries by uid. Two members can push different UUIDs with the same slug to `shared/`, or to one project repository. The concept has no rule for that collision (refuse? rename?), and no rule for a slug that differs from the one the server already holds for that uid.
- F-7 · Major · Sync API (withdraw, tombstones) · For an entry, the concept does not say whether `withdraw` deletes the file in a commit. It does not say what `baseVersion` a re-send after a withdraw needs. It also leaves a gap after the 90-day purge: a client whose cursor is older than a purged tombstone never learns of the deletion. Pull needs an answer for "cursor too old, full pull needed", and `changes.seq` needs `AUTOINCREMENT` so a purge cannot reuse seq numbers.
- F-8 · Major · Sync API (retries) · Push has no idempotency rule. A client whose request timed out after the server applied it retries with the old `baseVersion` and gets `stale`, with the version it just wrote as `current`. The concept must say that a retry with the same uid and the hash the server already holds answers `applied`, or define some other replay key.
- F-9 · Major · Sync API (limits) · No status code is given for a body over 1 MiB (413? checked before parsing, given that Bun's `maxRequestBodySize` default is far larger?), or for 201 items. Nothing says what happens to a `limit` over 500 (clamped or 400). A 500-item page of entries up to 256 KiB each is about 125 MiB with no byte cap. Push allows four or more 256 KiB entries per request, but those alone can exceed the 1 MiB body cap. The rate limiter's store (memory, reset on restart), the `Retry-After` value and whether `/v1/join` and `/v1/health` are limited are all open.
- F-10 · Major · Sync API / command (blocking) · Every git call is a synchronous `spawnSync` of up to 15 s. A 200-item push runs about 200 commits on the one event loop, so every other request waits, the HEALTHCHECK included. Bun.serve's default `idleTimeout` (10 s) may close the push connection mid-batch. The concept states neither a time budget per push nor a timeout setting.
- F-11 · Major · The command (stop and restart) · Nothing covers SIGTERM. `docker stop` gives 10 s, then SIGKILL, and a compiled Bun binary running as PID 1 with no handler may simply not stop. The concept should say: stop accepting requests, finish the current item, close `team.db`, and use `init: true` or tini in compose. It should also say how the restart then repairs per F-1.
- F-12 · Major · The command and the data directory (migrations) · `openDb` hard-codes `DB_FILE = "wizardingcode-mem.db"`, the client's `MIGRATIONS` and `user_version`, the backup folder, and (after part 1) the module schemas. `migrate` is private. The concept does not say how `team.db` gets its own migration list, version marker, upgrade backup and too-new refusal without one module importing the other's.
- F-13 · Major · Deployment (main.ts) · `main()` runs `applyLegacyEnv` and `migrateLegacyData` before every command, `serve` included. Inside the container that touches a home folder the non-root user may not have. The concept should exempt `serve` or set `WIZARDINGCODE_MEM_MIGRATE=off` in the image. It also does not say whether `serve` reads `/data/env` through `loadSettings`, or where `logError` writes (`<data>/logs` rather than stdout).
- F-14 · Major · Deployment (Dockerfile) · `debian:bookworm-slim` has no `curl` or `wget`, so `HEALTHCHECK on /v1/health` needs a command the binary provides, and none is named. buildx's `TARGETARCH` gives `amd64` and `arm64`, but the files are named `linux-x64` and `linux-arm64`, so the Dockerfile needs a mapping. The concept also does not fix the user's UID/GID or say what happens when a bind-mounted `/data` is owned by the host's UID.
- F-15 · Major · Deployment (release workflow) · The workflow has only `contents: write`. Pushing to ghcr needs `packages: write`, a login step and QEMU or buildx setup. Unstated: which job builds the image (after `build`, from the unsigned Linux binaries?), the image name, whether `latest` moves, and how a `-` prerelease tag is tagged.
- F-16 · Major · The command (first start) · The bootstrap invitation's expiry is not given, and neither is what happens when it expires unused, or what a restart does while it is pending (a new code? the old file?). "Nothing else is reachable" does not say whether `/v1/health` still answers or whether `serve invite` on the CLI still works. "Empty database" is not defined (no members, or no file?).
- F-17 · Major · The command (`serve status`) · Its output is not given. The concept does not say whether it reads `team.db` directly or asks the running server, or which lines it prints (version, schema, members and devices, pending bootstrap, last seq, repository heads against the index, last backup). Its exit codes are not given either.
- F-18 · Major · Storage (backups and restore) · `serve backup` runs `VACUUM INTO` and per-repository `git bundle` at different instants while pushes continue, so the database and the repositories in one archive can disagree. Writing to `<data>/backups/` puts the backup on the same volume as the data. After a restore the server's seq is lower than the clients' cursors, so a client asking `since=<its cursor>` gets nothing new, and a client whose ledger says `already-sent` never re-sends what the restore lost. The concept needs a server instance or epoch id in `/v1/me` and in pull answers, so a client can tell it is talking to a restored server.
- F-19 · Major · Deployment (image upgrade and volume move) · The concept does not say whether a server migration takes a backup first, what an older image does on a newer `team.db`, or that a volume move must carry `team.db` with its `-wal` and `-shm` files while the server is stopped. It also does not say how `/v1/` stays compatible when part 4's payload types gain a field: "unknown field is refused (shape)" means a newer client against an older server gets every item refused.
- F-20 · Major · Storage (memory ownership) · `memories(uid, …)` has no `device_id` in its key, while part 4's D-11 says the device token scopes the uid (device, then generation, then row id). With a copied store, every memory of the second machine comes back `refused`. The concept should key on `(device_id, uid)`, or state the refusal as the intended rule and say what part 6 shows the person.
- F-21 · Major · The command (`--host`) · `--host 0.0.0.0` is the default only "inside the container". The default outside it is not given. Run directly on a host, the binary would serve tokens over plain HTTP on every interface. Also open: whether a Host check or `X-Forwarded-For` (trusted only from Caddy) is used for the rate limit and the audit.
- F-22 · Major · Sync API (testing in-process) · No function like `startUi` is named (for example `startServe({ dataDir, port: 0, now, env, git })` returning `{ origin, stop }`). Nothing says how a test gets the bootstrap code without scraping stdout (a return value or an `onBootstrap` callback), how a test injects the rate limiter's clock, or how a test makes git fail at a chosen step to prove F-1's recovery.
- F-23 · Nit · Assumptions vs Members · The assumptions say "a salted SHA-256 at rest". The design says `sha256(token)` and looks the device up by that hash, which a per-token salt would make impossible. Pick one.
- F-24 · Nit · Members (device id) · "The token's first 8 characters of hash" is ambiguous (characters of the hash, or of the base64url token?). Its collision rule on insert is not stated.
