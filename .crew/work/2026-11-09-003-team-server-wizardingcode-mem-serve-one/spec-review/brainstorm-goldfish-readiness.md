## Findings
Lens: migration and backward compatibility, and what the builder and the operator must know.

- F-1 · Major · concept "What exists today" · The concept presents part 1's module migrations, `runGit`, `rebuildRepo` and leases, and part 4's `decide`, `OutgoingEntry` and `sharing_ledger`, as facts of the repository. None of them is in this worktree: `src/store/db.ts` has no `module_migrations` or `moduleSchemas`, and there is no `src/modules/knowledge/` or `src/sharing/`. A builder who trusts that section starts too early. The spec needs a start condition: parts 1 and 4 merged into the journey branch.
- F-2 · Major · concepts_brief "Reuse with the right seams" (migrations) · "The core runner takes a file name and a migration list" leaves several things open. Does team.db version itself by `user_version` or by a `module_migrations` row? What are the constant names (`TEAM_DB_FILE`, `TEAM_MIGRATIONS`) and the first schema? Does the `backup()` file name stay `wizardingcode-mem-<t>-v<n>`, with `BACKUPS_KEPT` 2 under `<data>/backups`? A builder will fork `migrate` or `openDb` in incompatible ways.
- F-3 · Major · migrations, read-only opens · `openExisting` checks a fixed `DB_FILE` against the client's `LATEST_VERSION` (7). `serve status`, `members` and `audit` cannot use it on team.db: they would refuse a team schema above 7, or accept a client's `wizardingcode-mem.db` without complaint. The spec needs a `openTeamDb` / `openTeamExisting` pair, and a marker that refuses a client store opened as team.db (such as a `team.schema` meta key).
- F-4 · Major · migrations, module schemas · Part 1's `openDb` defaults `moduleSchemas` to `MODULE_SCHEMAS`, which is knowledge plus sharing. If any server code path forgets `moduleSchemas: []` (a CLI subcommand, a test helper), team.db silently gains `knowledge_*`, `sharing_*` and a `sharing.generation`. One wrapper must be named as the only way to open team.db, with a test asserting `module_migrations` is absent.
- F-5 · Major · upgrade and downgrade · The documents do not say what `serve` does when team.db's schema is newer than the binary (an older image tag started on newer data). Exit code, log line and health result are all unstated. With a compose restart policy this becomes a silent crash loop. The rule and the operator's message are missing.
- F-6 · Major · upgrade · A schema migration takes `VACUUM INTO` a backup of team.db but none of `repos/`. The disk-room part of the health check does not count that copy. A rollback after a failed migration can leave the mirror ahead of the database. The upgrade's order is missing: stop, mirror drained, migrate, start. So is what a failed migration leaves behind.
- F-7 · Major · runner reuse, root parameter · Part 1's `runGit` and `gitEnv` take a `KnowledgeStore` (db, dataDir, settings from the env file, renew). They derive `.no-hooks`, `.gitconfig-empty`, `.template` and `GIT_CEILING_DIRECTORIES` from `knowledgeRoot(dataDir)`. "Takes its root as a parameter" does not give the new signature. Nor does it say whether the support folders move to `<data>/repos/`, or what stands in for `KnowledgeStore` on a server that has no env file.
- F-8 · Major · runner reuse, committer · Part 1 sets `GIT_AUTHOR_*` and `GIT_COMMITTER_*` from one `Identity`. `identityOf` derives a person's e-mail from the name, so two members with the same name get the same author address. The new signature (`commitPaths(..., author, committer)`) is not given, nor the server committer's name and e-mail, nor whether the member e-mail is keyed by member id.
- F-9 · Major · runner reuse, sync vs async · Part 1's runner is `Bun.spawnSync` with a 15 s timeout, but the brief says the mirror "runs git asynchronously". That is a new async runner, not a reuse. Its function, how timeouts and kills work, and whether part 1's leases and `store.renew` apply are all unstated.
- F-10 · Major · runner reuse, which functions · The documents do not say which part 1 functions the mirror calls. `writeEntry` re-renders frontmatter (version, author, updated) and so cannot store bytes verbatim. `ensureRepo` writes a nine-area `taxonomy.md` and calls `personAuthor`, which runs `git config --global user.name` and, with no git name in the container, falls back to "you". `openRepo` reverts intent records. The list of functions reused and functions not used is missing.
- F-11 · Major · mirror queue, state · There is no column or table for "pending" (for example `entries.mirrored_seq`, or a `mirror_queue(seq, uid, repo)`). That leaves open whether two pending versions of one uid become two commits or one, and in what order across repositories. "Rows still pending at start are mirrored then" cannot be built without it.
- F-12 · Major · mirror queue, crash recovery · A crash after `git commit` but before the row is marked mirrored makes the next start redo the item. `commit --only` with no change then fails with "nothing to commit", or an empty commit appears. The idempotence rule is missing: compare the file bytes or HEAD's blob, or put a `Seq: <n>` trailer in the commit and check it.
- F-13 · Major · mirror queue, failure · Part 1's failure rule restores the tree from HEAD and refuses. For a mirror, retry, backoff, a maximum number of attempts and handling of an item that always fails are undefined. One item that always fails would block its repository's queue for ever and grow the backlog `serve status` shows.
- F-14 · Major · mirror queue, withdraw and paths · The documents do not say how a withdraw or tombstone appears in a mirror repository (file deleted, `status: archived`, or moved). Nor do they say what happens when two uids in one server scope carry the same slug, so that both map to `entries/<slug>.md`. A builder will guess both.
- F-15 · Major · `serve repair` · "Rewrites the mirror from the database" is open: a new commit with the difference, a history rewritten from scratch, or repositories deleted and rebuilt. It is also open whether repair may run while the server's queue is live, from a second process on the same volume.
- F-16 · Major · stop and restart, single writer · Nothing stops a second `serve` on the same data directory, such as `docker compose run` or a host process beside the container. Two mirror queues would commit into the same repositories, and the 10-joins and 600-requests limits would double. The single-instance lock is missing (a lease in team.db `meta`, or a lock file under `<data>`), along with the message a second start prints.
- F-17 · Major · API tests in-process · There is no start function: no `startServe({ dataDir, port: 0, host, now, env, log, mirror })` returning `{ origin, stop, bootstrapCode, mirrorIdle() }` in the style of `startUi` and `tests/integration/ui-settings.test.ts`. Without it a test cannot read the bootstrap code except by parsing stdout or the file. It cannot wait for the async mirror before asserting commits, and it cannot move the clock for the 72 h expiry, the 90-day purge or the per-minute and per-day limits.
- F-18 · Major · limits, clocks and persistence · The documents do not say where the 5,000-items-per-day counter and the rate-limit windows live. If they are in memory, a restart resets them. They also do not say when tombstones and superseded rows older than 90 days are purged (at start, on a timer, or inside pull), or how the 410 cursor floor is stored.
- F-19 · Major · limits behind the proxy · "10 joins a minute per source address" behind Caddy sees one address, the proxy's, so the limit becomes global. Trusting `X-Forwarded-For` needs a rule: from which peer it is trusted, and what happens when the binary runs bare on loopback. Request ids and logs have the same gap.
- F-20 · Nit · limits, body size · "413 before parsing" needs the mechanism: Bun.serve's `maxRequestBodySize`, a check of `Content-Length`, and a streaming cap for chunked bodies. It also needs whether Caddy's `request_body` limit is set to match.
- F-21 · Major · logs · Part 1's runner and `logError` write to `<dataDir>/logs/wizardingcode-mem.log`, so on the server they go to `/data/logs/`. That file grows without bound and never reaches `docker compose logs`, which contradicts "JSON lines to standard output". The routing of `logError` under `serve` is missing.
- F-22 · Major · first start · The documents leave open what happens to the bootstrap code if the container restarts before the code is used: is it printed again, does `first-admin.txt` stay, or is a new code minted? They also do not say whether `serve invite --role admin` from the CLI is allowed while "nothing else is reachable", which is the operator's way back after missing the log. And they do not say whether "prints once" survives a log rotation.
- F-23 · Major · Docker, environment names · Only `WIZARDINGCODE_TEAM_DATA` is named. The variables that set the host and the port in the image, and how they combine with `--host` and `--port`, are unnamed. So is the rule "refuses another address without `--host`" when the address comes from the environment. The Dockerfile and the binary cannot agree without the names.
- F-24 · Major · Docker, health · `serve health` is unspecified: what it connects to (`127.0.0.1:<port from env>`), its timeout, its exit codes, and the free-disk threshold behind "the disk has room". It is also unsaid whether it skips `applyLegacyEnv` and `migrateLegacyData`, which `main` runs before every command and which would look at `$HOME` on every probe.
- F-25 · Major · Docker build and release · The release job's steps are missing. It needs `needs: build` and the `unsigned` artifact, which holds the Linux binaries. It needs a buildx `TARGETARCH` mapping (amd64 to `wizardingcode-mem-linux-x64`, arm64 to `wizardingcode-mem-linux-arm64`), the Dockerfile's build context and its `COPY` path. The order of the image push relative to `gh release create` is unstated, as is what happens when one of the two fails.
- F-26 · Major · release, registry · The image name (`ghcr.io/<owner>/wizardingcode-mem` or `-server`) and whether `packages: write` sits on the job or the whole workflow are missing. A new GHCR package is private by default, so an operator's `docker compose pull` fails without a login. The step that sets its visibility, or the runbook's login, must be stated.
- F-27 · Major · compose · The Caddy configuration is missing: an inline Caddyfile or a third file (the runbook promises "two files"), `reverse_proxy server:8787`, the body limit, and the forwarded headers. Also missing are which image tag compose pins (`latest` or `${VERSION}`), the restart policy, and the upgrade steps (`pull`, `up -d`) together with the 30 s stop grace.
- F-28 · Major · restore · The restore relies on the operator running `serve instance renew`, and nothing detects a restore when they forget. Clients then keep cursors above the restored sequence and silently miss changes. The documents do not say whether the server can refuse to start until the step is taken, for example a marker written at clean stop that a restored snapshot lacks. Nor do they say what `instance renew` changes besides the id (the cursor floor, purges).
- F-29 · Major · `serve status` · Missing: its exact lines and exit codes, whether it says if a server process is running (there is no pid or lease to read), which schema number it prints, and whether it has a `--json` form for the runbook. "Mirror backlog" also depends on F-11's undefined pending state.
- F-30 · Nit · stop and restart · "Finish the item in flight" leaves the rest of a 200-item push unapplied, with the connection cut. The spec should say the client sees a failed request and retries, that every applied item answers `applied` on retry because the hash matches, and what exit code `serve` returns after the 20 s drain is exceeded.
- F-31 · Nit · git growth · One commit per item, up to 5,000 a day per device, with no stated `gc.auto` setting under the isolated config. Git's detached auto-gc may start inside the container or be killed by the runner's timeout. The documents should state the gc policy.
- F-32 · Nit · concept vs concepts_brief · The concept still describes `serve backup`, device ids cut from the token hash, a member made per join, `0.0.0.0` inside the container, an index rebuilt from the files, and 90-day tombstones. The brief overturns each of these. The spec should say once that the brief supersedes the concept's design sketch wherever they differ.
