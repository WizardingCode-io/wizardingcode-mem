## Findings
- F-1 · Blocker · Phase A, step 1 · The plan says `tests/unit/settings.test.ts` "passes" without changes. It cannot: `tests/unit/settings.test.ts:28` and `:66` compare the whole `loadSettings(...)` result with `toEqual`, so a new `Settings.sharing` field fails both cases. The file is also missing from Scope's Modify list. Fix: add the file to Modify, with the `sharing` default (`{ roots: [], areas: [], problems: [] }`) added to both expected objects.
- F-2 · Blocker · Phase F, step 13 · The plan says the copy test "skips with a message when the file is absent, as `tests/unit/build.test.ts` handles its artefact". `tests/unit/build.test.ts:1-43` never checks for or skips on a built artefact, so the pattern being pointed at does not exist. Fix: state the skip mechanism (for example `test.skipIf(!existsSync(...))` and the message), or drop the comparison.
- F-3 · Major · Phase F, step 14 (Sharing.vue Save) · A widening save goes "through `saveSettings`" after the dialog. But `ui/src/settings.ts:24` and `ui/src/api.ts:216` send only a `SettingsPatch`, which is typed to `SettingKey` and has no `confirm`. Step 12 makes the server answer 400 to a widening without `confirm: true`, so every widening save from the page would fail, and the string-only copy test would not catch it. Fix: name a call (or a `confirm` parameter on `saveSettings`/`api.saveSettings`) that sends `confirm: true` after the dialog, and say how a 400 `{error}` (not `errors`) is shown.
- F-4 · Major · Signatures `src/sharing/report.ts`; steps 7 and 14 · `Report` only counts what leaves under the current policy (step 7: `finance` is not counted, B at `local` has `entries: 0`). Yet step 14 needs `<n> entries` beside toggles that are off, and both dialogs need the counts "for what the change releases" (spec §Changes). From a level of `local`, `api.sharing()` "filtered to the project" always gives 0. Fix: define how the hypothetical counts are produced (for example `wouldLeave` over a candidate policy, or per-area totals that ignore the shared state).
- F-5 · Major · Signatures `levelOf`; step 5 decide cases · `levelOf` gives `no-project` for "a project without a row". `setLevel` to `local` deletes the row, so a real project at Nothing never has a row. That makes `level-local` unreachable from a store, yet step 5 ("project at `local` → `level-local`"), the memory cases and AC-4/AC-5 expect it. Fix: say whether a missing row for a known project reads `level-local` and keep `no-project` for project 0, unknown projects and orphans, or say `policyWith` may hold a `local` row that the store never writes.
- F-6 · Major · Signatures `src/status/report.ts`; step 16 · `statusReport(db, project, dataDir)` (`src/status/report.ts:134`) receives no `env` and no `now`, and is called that way from `src/cli/commands/status.ts:16` and `src/ui/server.ts:577`. `loadPolicy` and `wouldLeave` need both. The plan neither changes the signature nor names the source (today's precedent, `judgeReport`, reads `process.env`), so the preamble's promise that tests pass their own `env` cannot hold for `tests/unit/status-sharing.test.ts`. Fix: state the new signature, or say that `process.env` and `Date.now()` are used.
- F-7 · Major · Signatures `generationOf`, `memoryItems`, `wouldLeave` · `generationOf` "mints and stores one when absent, inside `withWrite`". `status` and `doctor` open the store read-only (`openExisting`, `src/store/db.ts:196`). The plan never says when `wouldLeave` calls `generationOf`, so on a store whose `sharing` migration has not run yet, the call would try to write a read-only database and `status` would throw. The step 15 test uses a writable `openDb` with `moduleSchemas: []`, so it would not catch this. Fix: say that `wouldLeave` reads the generation with `getMeta` and never writes, or that it skips memories when no project is at `all`.
- F-8 · Major · Preamble; steps 9 and 15 · The plan says "no test reads the person's settings or environment". But `runCliWith` merges `process.env` (`tests/helpers/cli.ts:22`), and `tests/preload.ts:22-40` does not remove `WIZARDINGCODE_MEM_SHARE_ROOTS`/`_AREAS`. A developer shell that exports either one narrows every CLI, status and doctor test. Fix: add `tests/preload.ts` to Modify, deleting both keys next to `WIZARDINGCODE_MODULES`.
- F-9 · Major · Step 3, `reconcileSettings` cases · Only "no baseline and empty lists → nothing" is specified. `loadPolicy` raises the hand-edit problem only "when the baseline exists" (spec §Policy). So a file edited to roots `workspace` before any viewer or CLI use (baseline null) is never logged and never warned. Fix: decide what happens with a null baseline and non-empty lists (log with source `file`, or treat null as `{[],[]}`) and add the case.
- F-10 · Major · Step 15, "a failing reset" backup case · The test turns `sharing_levels` into a view and expects `failed`. Step 16 runs `resetSharingInCopy` "when `sharing_levels` exists" without saying how that is checked. A check on `sqlite_master` with `type = 'table'` skips the view and returns `sharingReset: 0`, and the test fails. Fix: state the existence check (`name = 'sharing_levels'` of any type), and how the test edits the gzipped copy in the folder target.
- F-11 · Major · Signatures `wouldLeave` (`refresh`) · The spec says "an `ensureFresh` failure is logged and counted as it is". The plan's signature and its step 7 cases leave out this failure path. If `refresh` throws (for example, no git), `GET /api/sharing` would answer 500 and `share status` would exit 1. Fix: state the catch, the log scope, and add a test with a throwing `refresh`.
- F-12 · Nit · Signatures `src/settings/settings.ts` (`publicSettings`) · "the environment's list differs from the file's or equals it" is always true, so the rule reduces to `ignored === 0`. The spec says it plainly: "a subset of the file's". The plan also does not say that an empty environment variable counts as unset, as `rawSettings` does (`src/settings/settings.ts:91-92`). Fix: say "when set and `ignored` is 0", and keep the empty-is-unset rule.
- F-13 · Nit · Scope (`src/ui/server.ts`) · "three routes and the settings route's logging": step 12 adds two routes plus a change to `PUT /api/settings`, and no logging is described anywhere. Fix: name the routes and drop or define "logging".
- F-14 · Nit · Step 14 (Confirm.vue usage) · `Confirm.vue:7` requires a `title` prop, and neither the plan nor the spec gives its text for either dialog. Fix: give the title strings.
- F-15 · Nit · Signatures `ui/src/api.ts` · "the three it lacked": after part 1, which adds `WIZARDINGCODE_MEM_AUTHOR` to `SETTING_KEYS` but does not touch `ui/src/api.ts`, the union lacks four keys. Fix: say whether `WIZARDINGCODE_MEM_AUTHOR` is added too.
- F-16 · Nit · Step 15, doctor cases · The expected detail is `1 projects share knowledge`, followed by "the helper `plural` renders `1 project shares knowledge`; use its output". Part 1's `plural(n, singular, pluralForm)` gives no verb agreement, so the expected string is left to the implementer. Fix: write the exact detail string.
- F-17 · Nit · Step 16 (`epochOfFile(current)`) · The spec reads the replaced database's epoch "through the `lock` connection it already opens, before `BEGIN IMMEDIATE`" (`src/backup/backup.ts:130`). The plan opens a separate connection before `lock`, so the plan and spec describe two different mechanisms. Fix: make the two documents agree.
- F-18 · Nit · Step 5, "logged once per process" · The plan gives no key and no reset for the once-per-process guard. `bun test` may run several files in one process, so an earlier in-process throw could leave the `boom` case without its log line. Fix: say how the guard is keyed, or that tests can reset it.
