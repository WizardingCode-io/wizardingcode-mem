## Findings
- F-1 · Blocker · Storage, "Core migration 8" · Part 1 says "PRAGMA user_version stays 7" and that 0.6.0 "ignores the tables (the core version is unchanged)". Part 2 says "the rollback target is 0.6.0, which ignores the tables". Parts 1 and 2 built the module namespace so that rollback would work. A core migration 8 makes all three statements false the moment the release opens a database: 0.6.0's `migrate` throws `SchemaTooNewError` because current is 8 and latest is 7. The concept names no release boundary, never says the rollback target changes, and never weighs keeping `user_version` at 7. That could be done with a module-owned table such as `(project_id, level)` under `module_migrations`, which 0.6.0 would ignore. A builder who follows the text breaks the rollback the earlier parts promised.
- F-2 · Major · Storage / rollback · Once migration 8 has run, a 0.6.0 binary fails on every hook without a sound. `src/cli/commands/hook.ts` catches the `SchemaTooNewError` from `openDb`, logs it and exits 0. No memory is captured, nothing is injected, and `hook_runs` is never written. This happens on a machine with two binaries (the Homebrew CLI upgraded while a host's plugin cache or OpenCode's npm plugin still runs 0.6.0), and after any downgrade. The concept does not say what the person sees, whether `doctor` names a hook binary that is older than the schema, or whether the README warns that every installed binary must be upgraded together.
- F-3 · Major · Rollback · The concept says nothing about getting back to 0.6.0. The only v7 copy is the `VACUUM INTO` file `migrate` writes under `<store>/backups/` (`wizardingcode-mem-<t>-v7-<pid>.db`), and `BACKUPS_KEPT = 2` prunes it after two later upgrades. Copying it back by hand loses every memory written since. There is no command that drops the column and resets `user_version` to 7. A builder ships with no stated downgrade path and no ADR line about it.
- F-4 · Major · Storage / first open · Migration 8 is the first core migration since parts 1 to 3, so the first hook after the upgrade takes a full `VACUUM INTO` backup of the whole database under the write lock. Other hooks wait up to `UPGRADE_WAIT_MS` (10 s) meanwhile. `backup()` writes straight to a `.db` name with no temp file. If the host kills the hook mid-copy, a partial `.db` is left that sorts as the newest, and the next prune can keep that partial file over the good v7 copy. The concept does not say whether this cost on the hook path is accepted, or that the downgrade copy is safe.
- F-5 · Major · Backups and restores · A restore can widen sharing without warning. `restoreBackup` swaps only the database; `<data dir>/env` is not in the backup. Say a v8 backup was taken while project A was `all`, the person later lowered A to `local`, and then restores that backup: A is `all` again. The workspace switch and the area list, meanwhile, keep their current values. The first sync of part 6 after such a restore would send what the person had withdrawn. The concept does not say whether a restore resets the levels to `local`, reports the levels it changed, or makes parts 5 and 6 ask for confirmation again.
- F-6 · Nit · Backups and restores · Two restore cases are unstated. When the new binary restores a v7 backup (0.6.0's `inspect` accepts it), the next `openDb` applies migration 8 and resets every project to `local`. Going in the other direction, 0.6.0 refuses a v8 backup with "upgrade first". Both should be stated so the person knows a restore can silently drop levels they set. Failing closed here is correct, but it is unsaid.
- F-7 · Major · resolveProject adoption · `adoptable()` in `src/core/project.ts` gives an `imported:<name>` project (from `importClaudeMem`) to the first directory seen whose basename is `<name>`. If the person set that imported project to `knowledge` or `all` before it was adopted, an unrelated repository that happens to share the folder name (an `api` or `web` folder) inherits the level. Its memories then become shareable without anyone choosing it. The concept does not say whether adoption resets the level to `local`, or whether the selector stays disabled on a project that is only known by an `imported:` alias.
- F-8 · Nit · History and claude-mem imports · Both create projects with an explicit column list (`INSERT INTO projects (key, name, created_at)`), so the `DEFAULT 'local'` applies and nothing needs to change. But `importedProject` reuses the `imported:` alias of a project that has since been adopted, and the history index pass and backfill distill old turns into the resolved project. So a later import into a project already at `all` makes third-party or months-old memories shareable at once. The ADR should say so, and say that the counts shown when the person chose the level were a snapshot.
- F-9 · Major · Storage, the CHECK · SQLite cannot change a CHECK constraint without rebuilding the table. The concept itself expects a later part to add a level ("a later part may offer them", meaning the user rules). That change would mean a 12-step rebuild of `projects`, which `project_aliases`, `sessions`, `memories`, `project_links` and others reference with `ON DELETE CASCADE`. One step done wrong there deletes memories. The concept does not weigh the CHECK (pinning the enum) against validating in code with the column as plain TEXT, and does not record the rebuild rule for the next part.
- F-10 · Major · Settings, `WIZARDINGCODE_MEM_SHARE_AREAS` · The concept says "an unknown area is kept and warned by doctor", so an id listed before it exists is armed in advance. The area becomes shared as soon as someone adds it to either taxonomy: part 1's `addArea`, or part 6 pulling in a shared repository whose taxonomy carries that id. The same happens when an id is removed and added again with another meaning. The list is also one set over two independent taxonomies, so `sales` shares both the workspace's `sales` and the shared repository's `sales`. A builder cannot tell whether an unknown id must be ignored by the predicate or honoured.
- F-11 · Major · Settings, loading · `loadSettings` drops an invalid value to the default, but only `validatePatch` checks values. A hand-edited `env` file never goes through `RULES`. The concept does not say what a malformed `SHARE_AREAS` or a `SHARE_WORKSPACE` of `yes` loads as. For a setting that guards egress, the whole list must fail closed to empty, not keep its valid items. The `onOff` fallback must also be `false` for this key, not copied from a key whose default is `on`.
- F-12 · Major · Settings, environment wins · The environment overrides the file (`rawSettings`). One stray `WIZARDINGCODE_MEM_SHARE_WORKSPACE=on` in a shell profile, or in a host's env block, therefore shares the workspace from that process only. Meanwhile the viewer, started elsewhere, may show the value from the file, and the sync of parts 5 and 6 may run from a process with a different environment than the one where the person looked. The concept does not say whether the sharing keys follow the env-wins rule, or which process's view the sync must use.
- F-13 · Major · The policy, "loaded once per call site" · A long-running process (the viewer, or a future sync daemon) that caches the policy keeps sending after the person lowers a level or turns an area off. Lowering a level cannot recall anything already on the server. The concept does not say the policy is re-read at the start of every sync run and every batch. It also does not say that a downgrade of a level affects only future sends, a fact the ADR should state.
- F-14 · Major · Before the first sync · The concept does not list the conditions the predicate's inputs must meet. Five are missing:
  - the column exists (`user_version` ≥ 8), and the loader fails closed to `local` when it is missing;
  - the knowledge module's state is `current` (`moduleSchemaState`);
  - the repository is fresh (`ensureFresh` before reading `status` and `area`): part 2's hooks read a stale index, so an entry a person hand-edited from `active` to `draft` would still read as `active`;
  - a repository with no `knowledge_repos` row, or a `project_id` with no `projects` row (an orphan folder, a repository created after the backup that was restored), answers `local`;
  - `disabled` is read in the same query as `sharing`.
  Without these, parts 5 and 6 inherit no stated contract.
- F-15 · Nit · Status and doctor on an older schema · `status` and `doctor` open the database with `openExisting`, which never migrates. On a v7 database read by the new binary before its first hook, `SELECT sharing FROM projects` throws. The concept should say that the `sharing` lines go through `readingDb`'s skip ("needs the newer schema"), so they skip instead of failing, and the same for `GET /api/sharing`.
- F-16 · Nit · Store move · `moveStore` and `verifyCopy` compare `user_version` and the memory count only, so a move carries the column untouched. Nothing needs to change, but the risks section should say so, alongside the restore cases.
- F-17 · Nit · Settings, downgrade · `renderEnvFile` keeps unknown keys, so a 0.6.0 viewer saving settings leaves the two `SHARE_*` keys in place. They come back in force after a later re-upgrade, while the project levels are back to `local` if the v7 copy was restored. That mixed state should be stated.
