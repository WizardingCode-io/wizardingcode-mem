## Findings
- F-1 · Major · spec Storage (`sharing_ledger`, `sharing.generation`, received items) and The policy and `decide` steps 3 and 5 · This part designs, tests and pins the sync's ledger: its key, `sent`/`received`, `withdraw`, `already-sent`, `received-same`/`received-elsewhere`, generation-scoped memory uids and echo rules. Yet it writes no ledger row itself (Non-Goals), and parts 5 and 6, whose protocol would prove that shape, do not exist yet. The risk a builder misses: the ADR fixes every ledger branch, but each is tested only against hand-made rows, and part 6 will have to reopen a pinned contract if the server's identity model differs (for example, every restore renews the generation, so every memory goes up again as a new item). Simpler: this part fixes `decide` as allowed or not, with a reason, per item and destination. The ledger table, withdraw and received semantics and the generation ship with part 6 as `sharing` migration 2. "One predicate, nothing else decides" still holds.
- F-2 · Major · spec Storage (`sharing.settings_seen`, `reconcileSettings`) and Changes, confirmation, epoch · The baseline, the reconcile step and the `file` source exist so a hand edit of the env file can bump a stored epoch. That makes `GET /api/sharing` and every `share` subcommand write to the database before they act, and part 6 must remember to reconcile at every batch. The risk: three call sites have to remember a write-on-read, a missed one leaves the epoch stale while the policy has changed, and `status` and `doctor` need a separate pending-edit warning. Simpler: build the epoch from the levels' change counter plus a hash of the effective roots and areas, computed in `loadPolicy`. A hand edit then moves it with no baseline, no reconcile and no GET that writes. `sharing_changes` keeps logging viewer and CLI changes.
- F-3 · Major · spec The viewer (`PUT /api/settings`) and plan task 12 vs spec `applySettingsPatch` · "Widening" is defined twice, in two layers. The route compares the new list with the file's current list (`parseShareList` on `readEnvFile`), while `applySettingsPatch` compares effective lists, after the environment's narrowing. With the environment narrowing, adding an id the environment removes asks for `confirm` at the route, while the store reports `widened: false`, and nothing says which definition the CLI's prompt uses. Fix: put one `widens(old, new)` for settings in `src/sharing/store.ts` and have the route and `share roots`/`share areas` call it, so the route holds no policy logic.
- F-4 · Major · spec Counts, lists and previews (`hash: ""` for candidates without a ledger record) · This optimisation targets a ledger that is always empty in this part. It rests on an unenforced invariant: `decide` never reads `hash` unless a `sent` record exists. If part 6 changes `decide` to compare hashes in any other branch, every unhashed candidate silently compares `""`. Simpler: compute no hash for counting at all in this part, since there is no ledger to compare against. Or, if kept, make the type say so (`hash: string | null`), so `decide` cannot read a sentinel as a real value.
- F-5 · Nit · spec Levels, roots, areas, destinations and D-9 · Levels are keyed per `(project, destination)`, but the roots and areas are not, and any destination other than `team` answers `unknown-destination` whatever its level. The generality buys nothing now: part 5 must still add destination-keyed roots and areas. Nothing leaves before part 6, so the rejected alternative's reason ("cannot be fixed once data has left") does not apply yet. A `destination` column added by migration with a `team` default when part 5 binds the server would do.
- F-6 · Nit · spec Design (whole section) vs plan Signatures · The spec's Design section holds code-level detail: parameter lists with defaults (`io = { writeEnvFile }`), module-level flags and `resetSharingLog()` for tests, which alias wins when several qualify, full SQL, and every UI string. The plan's Signatures then restate most of it, so two copies must stay in step, and the spec runs past one read. Keep interfaces, data flow and the contract in the spec, and leave the signatures and exact copy to the plan.
