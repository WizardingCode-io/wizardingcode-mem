- F-1 · Major · Signatures, src/sharing/report.ts and src/cli/commands/share.ts (steps 7, 9) · `decide` needs each item's `LedgerRecord[]`, but no signature reads them from `sharing_ledger`. The only reader is `ledgerUids(db, kind): Set<string>`. So `wouldLeave` (which per the spec runs "each candidate through `decide` with its ledger records") and `share explain` each have to invent the query, the per-uid grouping and the `withdrawn_at`→`withdrawnAt` mapping. Fix: add a function such as `ledgerRecords(db, kind, uids): Map<string, LedgerRecord[]>` and say which callers use it.
- F-2 · Major · Signatures, src/sharing/report.ts `Change` and `sharingPreview` (steps 12, 14) · `withChange` takes a single-key union (`{level}` | `{roots}` | `{areas}`). The spec's `POST /api/sharing/preview` body allows `roots` and `areas` together, and Sharing.vue's Save builds a patch that holds both and asks for one preview. The plan does not say whether a body with both keys is applied as two changes, refused with 400, or sent as two calls. It also does not say how invalid root or area tokens in the body are answered. Fix: let `withChange` accept `{ roots?, areas? }` together, or state the rule, and add a test case for it.
- F-3 · Major · Signatures, `setLevel` and `setProjectSharing`, step 3 · "The same level twice writes no change row" is checked against the stored row. A project whose level reads `local` because of `unbound-alias` still has its row, so choosing Knowledge again in the dock or the CLI is a silent no-op: it never re-binds to the project's current remote alias, and the page keeps showing Nothing. Fix: say that a stored row whose `bound_alias` no longer belongs to the project (or the effective level, not the stored one) is the baseline, and add a test.
- F-4 · Major · steps 10, 12 (`share project`, `share roots|areas`, `setProjectSharing`) · The confirmation has to come before the write. Yet the only `widened` values in the signatures (`setLevel`, `applySettingsPatch`) are returned after the write. Only `PUT /api/settings` says what its pre-check compares against (the file's lists through `parseShareList`). For the two CLI subcommands and `PUT /api/projects/<id>/sharing`, the reader has to choose the baseline: stored row or effective level, file list or effective list. With an unbound or narrowed baseline, that choice decides whether a widening skips the prompt. Fix: name the baseline and the helper for each of the three paths.
- F-5 · Major · Signatures, `effectiveSharing` (step 1) · It returns one `problem: string | null` per key and no `ignored` count. But `Settings.sharing.problems` must carry, for one key, a file-token problem, an environment-token problem, and the spec's "the environment's <key> names <n> more than the file; ignored". The plan does not say where the ignored-ids sentence is built, what its exact text is, or which problem wins when several apply. `doctor` and `status` both read these problems. Fix: return `ignored` and a `problems: string[]` per key, with the exact sentences.
