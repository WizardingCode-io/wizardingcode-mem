## Findings
- F-1 · Major · What exists today, "`disabled` is the per-project memory off" · No production code ever sets `projects.disabled`. The only `UPDATE projects SET disabled = 1` statements are in tests/ (for example tests/integration/hooks.test.ts:358), and src/cli/main.ts has no command for it, nor does src/ui/server.ts have a route. So the concept's "a disabled project shows `local` and the selector off" and its doctor warning "a project set to knowledge or all is disabled" describe a state a person can only reach with raw SQL. A builder would write UI and checks for a path no user can trigger, or would assume a toggle exists.
- F-2 · Major · The viewer and the CLI, Across projects · `listProjects` in src/ui/api.ts:37-51 does not select `disabled`, and the viewer's `Project` type (ui/src/api.ts:14-23) has no `disabled` field. The Across projects view cannot know a project is disabled, so it cannot "show local and the selector off" unless `ProjectSummary`, `/api/overview` and `Project` gain `disabled` and `sharing`. The concept does not list these changes.
- F-3 · Major · Storage, "Core migration 8" · Raising `user_version` to 8 makes every 0.6.0 binary refuse the database with `SchemaTooNewError` (src/store/db.ts:126, 201; ADR 0018, "Migration 7 and older binaries": "Every agent's binary has to move together"). Part 1's spec deliberately keeps `user_version` at 7 through a module migration namespace so that 0.6.0 still opens the store. The concept neither notes that it undoes this nor asks whether the column belongs in a module-owned table instead.
- F-4 · Major · Status and doctor · `doctor` and `status` open the store with `openExisting`, read-only and without migrating (src/store/db.ts:186-209). doctor reports a v7 store as "will be migrated on next use" (src/doctor/checks.ts:117). On a store not yet at v8, any query on `projects.sharing` fails with "no such column". The concept does not say that a missing column means every project is `local`, or what status and doctor print in that case.
- F-5 · Major · What exists today, Part 1 · Part 1 and Part 2 are presented as facts from the repository, but none of their code exists in this worktree. `src/modules/` holds only `memory/`, and `knowledge_repos`, `taxonomyFor` and the area pattern (`AREA_ID`) exist only in part 1's plan.md and spec.md. The concept's references to them are dependencies on unbuilt parts and should be labelled that way, along with the build order they imply.
- F-6 · Major · Storage, Settings · `RULES` only checks values that come through `PUT /api/settings` (`validatePatch`). Values set in the environment or written into the file by hand are parsed by `onOff` and by plain string reads that fall back silently (src/settings/settings.ts:99-100). So `WIZARDINGCODE_MEM_SHARE_WORKSPACE=yes`, or an area list with a stray space or capital letter, quietly means off or private. The concept needs a normalised parse of the area list (trim, lower-case, dedupe, as `moduleList` does) and a doctor warning on an invalid raw value; without them a person cannot see why an area is not leaving.
- F-7 · Major · The policy · `mayShareEntry` and `mayShareMemory` return a bare boolean. Nothing in the concept tells a person why a given entry or memory would or would not leave: project level, a disabled override, a private area, the workspace switch, a non-active status, a user rule, or a proposal. At 3 AM, "why did X leave" and "why didn't Y" need a reason code from the predicate and a command such as `share explain <entry|memory>`, and the concept has neither.
- F-8 · Major · The viewer and the CLI, PUT /api/projects/<id>/sharing and settings writes · A change of level or of the area list is not logged anywhere. `saveSettings` writes the env file silently (src/settings/settings.ts:244-249), and the new column keeps only the current value. Once parts 5 and 6 send data, nobody can reconstruct which policy was in force when something left. The concept should record each change with its time, old value, new value and source (viewer, CLI or env) in meta or a table, and show the last change in `share status`.
- F-9 · Major · Status and doctor, doctor · `Check.status` has only `ok`, `warn`, `fail` and `skip` (src/doctor/checks.ts:29-33); there is no information level. The Settings nav counts every `warn` as a badge on Health (ui/src/components/Settings.vue:45). Until part 5 ships, "sharing configured but no team" would be a permanent warning badge for everyone who set a policy, which contradicts "said as information".
- F-10 · Major · Status and doctor, status · `statusReport` describes the project of the current directory and also serves `/api/status` (src/ui/server.ts:574-578). The proposed `sharing` line is global and leaves out the current project's own level, which is the first thing a person debugging one repository would ask. The concept also does not say how "entries that would leave" is counted: from the knowledge index (module-owned, possibly `behind`, `too-new` or stale until `ensureFresh` runs) or from the files. That decides whether the count can disagree with what the sync later sends.
- F-11 · Major · Settings, the Sharing card · Existing ui/src/components/settings/Team.vue already promises users that "Sharing is opt-in, per project" and that "Anything marked private, or inside a `<private>` block, never leaves your machine". The concept never mentions this card. Its predicate does not involve `<private>` (src/core/redact.ts:86 handles it), and it does not say whether Team.vue is replaced or reworded or keeps that promise beside the new card.
- F-12 · Nit · Settings, the Sharing card · ui/src/api.ts:92-104 keeps its own `SettingKey` union, and it is already out of step with `SETTING_KEYS` (it lacks `SEMANTIC`, `HISTORY_DAYS` and `MODULES`). The two new keys have to be added there too. Settings.vue is also one page per nav entry (`Page`/`PAGES`, lines 35-36), not stacked cards, so "a Sharing card" means a new page id and nav item.
- F-13 · Nit · Settings, the Sharing card · Because the environment wins over the file, a toggle whose key is set in the environment has no effect. The concept does not say the card uses `fromEnvironment` (ui/src/settings.ts:52) to disable such toggles and show their source. Without that, a person flips a switch, sees nothing change, and cannot tell why.
- F-14 · Major · The policy, a memory leaves · The memory conditions check only `status` and the user rule. They leave out `stale = 1` (active but flagged stale) and `scope = 'branch'` memories (src/store/migrations/0001_init.sql:73-78), so both would leave under `all`. They also do not cover a project id the `projects` table does not know, or `knowledge_repos.project_id = 0` (part 1) on a project-scope repository, which `projectLevel` must answer as `local`.
- F-15 · Nit · The policy, the shared scope · The concept says the shared scope's entries leave "always", while the brief says an entry leaves when "the workspace, or the shared scope" is shared, which implies the shared scope has a switch of its own. Separately, part 1 gives the workspace and the shared repository separate taxonomies, but `sharedAreas` is one flat set of ids, so the same id in both taxonomies is shared or private in both at once. Neither point is stated.
- F-16 · Nit · The viewer and the CLI, `share project <level>` · "The project of the current directory" via `resolveProject` (src/core/project.ts:71) creates a project on first sight. `findProject` (line 39) does not create anything. The concept does not say which one is used, or what the command prints when the directory is not a known project.
- F-17 · Nit · The policy, "loaded once per call site" · The concept does not say when a change takes effect for a long-running reader (the viewer, and the sync in parts 6 and 7) that loaded the policy earlier. It also does not say whether `share status` or doctor reports that data already sent under a broader level stays sent after the level is narrowed.
