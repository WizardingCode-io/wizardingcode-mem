## Findings
- F-1 · Blocker · Design › Levels, roots, areas, destinations · `SHARE_AREA`'s second group `[a-z][a-z0-9-]{0,39}` is said to "equal part 1's `AREA_ID`", and a test is meant to assert both accept and refuse the same strings, but part 1's spec defines an area id as `^[a-z0-9][a-z0-9-]*$` (at most 40 characters), which allows a leading digit. The stated test cannot pass. Worse, under D-14 a taxonomy area such as `2026-launch` would empty the whole area list when someone shares it. Fix: make the leading class `[a-z0-9]`, or have the code use part 1's `AREA_ID` directly.
- F-2 · Major · Design › Storage / resetLevels; Risks › restore · The spec says "the epoch never falls back", but that only holds for a copy that already has the sharing tables. A v7 copy taken before this part has no `sharing.epoch`, so the next `openDb` migration starts it again at 0 (the spec's own wording: "minted ... as on a fresh store"). A sync that remembered epoch 7, and ledger rows with `policy_epoch` 7, then face a smaller epoch. AC-12 tests only the case with tables. Fix: restore writes `max(floor, 0) + 1` into the copy's `meta` even when it has no tables, or the migration seeds the epoch from a floor the restore passes it.
- F-3 · Major · Design › `status`, `doctor`, restore › restoreBackup · The spec never says how the unpacked copy is opened for `resetLevels`: a raw `Database`, `openDb` (which would run core and module migrations, and may take a backup, on a temporary file), or something else. `withWrite` needs a `Db`. A writable open can also leave `-wal`/`-shm` files beside `.restore-<now>.db`; `renameSync(unpacked, current)` does not move them and the `finally` does not delete them. A builder can lose the reset, or leave stray side files. Fix: name the opener, the journal mode and the checkpoint/close step before the rename.
- F-4 · Major · Design › Storage / reconcileSettings and loadPolicy · The rules only act "when the baseline exists". When `sharing.settings_seen` is null (a fresh upgrade whose env file already holds sharing keys, written by hand or by provisioning), nothing says whether `reconcileSettings` logs a change, and `loadPolicy` raises no problem. Lists widened before the first viewer or CLI save are then never recorded and never warned. Fix: define the null baseline as the empty lists, or have the migration's `run` step seed it from the file.
- F-5 · Major · What leaves with an item › contract test · The contract test asserts that the key sets of `EntryItem`/`MemoryItem` "are exactly the fields above". But the `Item` type given to `decide` (uid, scope, projectId, area, status, problem, version, hash / stale, origin, isUserRule) is not the payload list (frontmatter, body, slug, alias / title, body, kind, importance, created_at…). The spec also never defines the types `EntryItem` or `MemoryItem` (only an `Item` union). A builder cannot tell whether the predicate's input or the outgoing payload is pinned, and the payload is the one that guards against leaks. Fix: name two types, the decide input and the outgoing payload, and say which key set each test pins.
- F-6 · Major · Design › decide step 3 / D-11 · "Never back" means a received entry, edited locally, is `keep` `received-same` forever. In a team-knowledge feature, a member's improvement to shared knowledge therefore never reaches the team, and this ADR binds parts 5 and 6 to that rule. Neither Risks nor the ADR list names this limit. Fix: state it as a limit with the intended remedy (for example, a local edit becomes a new version owned by this machine), or narrow the rule to "never echo the unchanged received version".
- F-7 · Nit · Design › restoreBackup · `sharing.epoch` of the live store is read "before `BEGIN IMMEDIATE`", so a CLI `setLevel` that commits between the read and the lock can make the floor stale. The copy can then end on the same epoch value as a different policy, which an equality check in the sync would miss. Fix: read it after `BEGIN IMMEDIATE` on the lock connection.
- F-8 · Nit · Decisions D-20 vs Design › reconcileSettings and AC-12 · D-20 limits doctor to warning about "invalid, ignored, unbound and inert only". The Design text (`status` and `doctor` report the difference) and AC-12 add a fifth warning, a pending hand edit. Fix: align D-20.
- F-9 · Nit · Design › Settings, narrow-only · The spec does not say what `publicSettings` reports as the source when the environment's value holds an invalid token, which empties the list. It is also unclear whether the control is then locked. Fix: name the source in that case.
- F-10 · Nit · Design › Counts / NFR · A wall-clock assertion (90,000 memories under 1,000 ms "on the test machine") in the unit suite is flaky on loaded CI runners. Fix: keep the figure as a reported gate measurement, not a pass/fail unit assertion, or give it a margin.
- F-11 · Nit · Design › Storage · "No backup, since no module had a `sharing` row before" depends on how you read part 1's rule, "a backup only when a module already had a recorded version": per module or any module. When knowledge's row already exists, the second reading takes a backup on the hook's first open. Fix: cite the per-module reading or drop the claim.
- F-12 · Nit · Acceptance criteria · AC-15 is listed before AC-14. `NEVER_LEAVES` "matches the ADR's list" implies a unit test that parses markdown, and the spec does not say how. Fix: renumber, and say whether the test reads the ADR or the ADR quotes the constant.
