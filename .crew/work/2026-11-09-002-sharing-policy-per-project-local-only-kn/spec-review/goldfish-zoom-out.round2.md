## Findings
- F-1 · Major · Decisions D-1 / Design "Settings" and "Storage" (`applySettingsPatch`, `reconcileSettings`, `sharing.settings_seen`) · The roots and areas live in the env file while the levels live in the database, so the spec needs a lot of machinery to keep the two in step: a file write and a database write in one path with a crash window, a baseline copy kept in `meta` to spot hand edits, a reconcile step in every route, CLI command and sync, a doctor warning while a hand edit is unrecorded, a new narrow-only rule with its own `publicSettings` source rule, and a restore that resets the levels but not the roots and areas. Under Alternatives rejected, only "the levels in the env file" is rejected; keeping roots and areas as rows in the `sharing` namespace is never weighed. That one change would remove most of this, and the environment could still narrow at load time; weigh it, or say why the file must hold these two keys.
- F-2 · Major · Storage `sharing_ledger`, `sharing.generation`, `memoryUid`, `received`/`withdraw`/`already-sent` in `decide`, epoch-stop rule · This part designs and freezes part 6's sync state in a v1 schema before anything writes to it. Nothing in this part writes a ledger row, and the tests can only reach these branches through rows inserted by hand. Since nothing leaves before part 6, the "fix the contract before data leaves" argument does not need this now. Simpler: `decide` answers allowed or kept with a reason, and part 6 adds the ledger, the generation and the received/withdraw rules as `sharing` migration 2, written by the code that uses them. Otherwise the competent reader builds tables part 6 has to work around.
- F-3 · Major · D-9, `levelKey`, `SharingPolicy.destinations`, reason `unknown-destination` · The destination dimension is half-built for a second server that no requirement asks for. Levels are keyed by destination, but roots and areas are not, so the abstraction is inconsistent the day a second destination arrives. Module migrations make adding the column later cheap, so dropping it now closes no door. Simpler: one level per project now, and the destination is added by the part that adds a second server.
- F-4 · Major · Counts and lists / NFR (`wouldLeave` SQL pre-filter, hash only for ledger candidates, the 90,000-memory under-1,000 ms test) · This is optimisation with no measured bottleneck. It also states D-15's memory rules twice: once in the SQL pre-filter (`status`, `stale`, `scope`, `origin`, `user_memories`) and once in `decide`, which breaks "nothing else decides". If the two drift apart, the counts in the confirmation dialog will be wrong. The hash-only-for-ledger path can never run in this part, because the ledger is always empty. Simpler: select the projects at `all`, pass each candidate through `decide`, and add a pre-filter only once a measurement shows it is needed.
- F-5 · Nit · Plan Phase E `confirmWidening` (new, on `node:readline`) · `src/cli/commands/install.ts:106` already has a TTY check plus a `[Y/n]` prompt with `--yes` handled by its caller. Extract it, with the default answer as a parameter, instead of adding a second prompt helper.
- F-6 · Nit · Design `redactForSend` in `src/sharing/edge.ts` · This is a new file holding a one-line wrapper over `redact` (src/core/redact.ts:226), for a caller that does not exist yet. The contract test can pin `redact` directly, and part 6 can call it.
- F-7 · Nit · Design (SQL, the `crypto.randomBytes` detail, the order of steps inside the route, every toast string) and Plan "Signatures" · The spec's Design section reads at the plan's level: it holds code-level detail, and the plan then repeats the same signatures. Keep the interfaces and data flow in the spec, and leave copy strings and implementation steps to the plan.
- F-8 · Nit · Spec Settings "Narrow-only" against plan `publicSettings` · The spec describes the rule as "a subset of the file's"; the plan says "ignored is 0 and the environment's list differs from the file's or equals it", which is the same rule written confusingly. Under both, an environment value that partly narrows reports `file` and leaves the control unlocked even though the environment is narrowing. Use one wording, and decide what the lock shows in that case.
- F-9 · Nit · `NEVER_LEAVES` constant in `src/sharing/types.ts` · No code reads this list; it exists only to match the ADR's prose in a test. It is documentation kept as a constant, so keep it in the ADR alone, or let part 6's serializer use it.
