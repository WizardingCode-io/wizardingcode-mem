## Findings
- F-1 · Major · Storage, `reconcileSettings` and `sharing.settings_seen` · The baseline holds the effective lists after the environment's narrowing, and each process narrows with its own environment (the viewer server keeps the `env` it started with, while the CLI and part 6's sync have their own). So when the viewer and the CLI or the sync run with different `WIZARDINGCODE_MEM_SHARE_*` values, every `GET /api/sharing` and every sync batch finds a "difference". Each one writes a false `file` change and bumps the epoch, and the sync then stops "when the epoch moved". This also contradicts the claim that "a narrowing environment causes no difference by itself" (AC-6). Fix: keep the file's own lists as the baseline, apply the environment only when reading, and add a test that runs two processes with different environments.
- F-2 · Major · Identity (D-16), `loadPolicy` downgrades and `setLevel` · A disabled project's level, or a level whose alias was lost, reads `local`, but its row is kept. Re-enabling the project, or getting the remote alias back, therefore brings the wider level back with no confirmation, no `sharing_changes` row and no epoch bump. That breaks the success line "every change is logged and a widening is confirmed first", and the sync's epoch check misses it. Fix: delete or invalidate the row when the downgrade is found (log it and bump the epoch), or count re-enabling as a widening.
- F-3 · Major · `setLevel` ("A setLevel to the same level writes nothing") · `setLevel` compares the new level with the stored row, not with the effective level. A person whose project shows Nothing because of `unbound-alias` picks Knowledge in the dock, the stored row already says `knowledge`, and the call answers unchanged. Nothing is rebound and the project stays at Nothing, while `doctor` keeps warning and offers no way to fix it. Fix: compare against the effective level and rebind `bound_alias` when it is gone.
- F-4 · Major · Storage, the ledger and the payload `version`/`hash` · A memory's `version` is `updated_at` and its `hash` covers title and body only, but `OutgoingMemory` also carries kind, importance and status. `src/judge/rejudge.ts:138` changes kind and importance without touching `updated_at`, so `decide` answers `already-sent` and the server keeps the old values. In the other direction, `evidence_count` bumps (`memories.ts:112`, `mcp/tools.ts:396`) move `updated_at` with no content change, so unchanged memories are sent again. The spec also does not say whether the hash is taken before or after redaction. Fix: hash every field of the payload (after redaction) and pin that in the contract test.
- F-5 · Major · D-11, entry identity · An entry's uid is its UUID alone, but part 1's key is `(repo_id, id)`, which allows the same UUID in two repositories (for example, an entry file copied from the workspace into a project repository). Their ledger records then mix: one copy reads as `already-sent` or `withdraw` because of the other. Fix: scope the entry uid by repository (scope plus remote alias), or make `decide` refuse a UUID that appears in more than one repository.
- F-6 · Major · Storage, `sharing.generation` · A memory's identity stays unique only because `restoreBackup` renews the generation. A store file copied by any other means (Time Machine, rsync to a new laptop, a second machine seeded from the file, or `moveStore` used as a copy) keeps the same generation and the same row ids. Two live stores then send different memories under the same uid `<generation>:<id>` to one team server. Fix: name this limit and its answer (renew the generation when the store finds it is not at the path it was minted for, or have part 5 scope uids by device), or record it as a risk for parts 5 and 6.
- F-7 · Major · `resetLevels` and restore (D-16, AC-12) · The restore resets the levels, the epoch and the generation, but `sharing.settings_seen` comes back from the copy, while the env file (not in the backup) keeps today's lists. When the sharing settings changed after the copy was taken, the next reconcile records a hand edit with source `file` for a change that was confirmed through the viewer or the CLI, and `doctor` warns about an "unrecorded hand edit". This corrupts the change log. Fix: have `resetLevels` set the baseline to the env file's current lists, and add that to AC-12.
- F-8 · Nit · Settings, narrow-only `source` rule versus AC-2 · By the rule, an empty file with the environment set to `none` removes nothing, so `source` is `default`. AC-2 says the environment `none` gives `source: "env"` without stating the file's value. State which file AC-2 assumes.
- F-9 · Nit · Settings, hook cost · "a second raw read for the two keys" and "two more map lookups and no parsing when absent" read as two different costs. Say whether the hook reads the env file once or twice.
- F-10 · Nit · Changes, confirmation · Widening is defined against the file list in `PUT /api/settings` and against the effective lists in `applySettingsPatch`, and `share roots`/`share areas` do not say which one they use. Name a single comparison.
- F-11 · Nit · The command, `share project` · The spec uses `remoteAliasOf` as if it existed, but `src/core/project.ts` exports only `findProject` and `resolveProject`. Only `plan.md` declares it as new. Name it in the Design.
- F-12 · Nit · Counts, `POST /api/sharing/preview` · The spec does not say whether the preview runs `wouldLeave` with `fresh: true` (git calls on each dialog open) or with `fresh: false`. If it uses `fresh: false`, the dialog's counts can differ from the page's.
