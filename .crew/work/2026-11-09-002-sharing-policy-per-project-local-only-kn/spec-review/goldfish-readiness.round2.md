## Findings
- F-1 · Blocker · Phase C step 5 (loader cases), step 15 (status on `moduleSchemas: []`), Signatures `loadPolicy` · The plan reads `moduleSchemaState(db, "sharing", 1) === "behind"` as "the tables do not exist", but part 1 says the state is `current` when `module_migrations` is missing (part 1 spec §The index; part 1 plan step 3: `moduleSchemas: []` gives `current`). On such a store `loadPolicy` will query a `sharing_levels` table that does not exist, throw, and return `closed: true` with a problem. That breaks "closed: false, no problem", the default status line and AC-1/AC-11. Fix: say that `loadPolicy` also checks `sqlite_master` for `sharing_levels`, and that a missing table reads as every default.
- F-2 · Blocker · Signatures `SHARE_AREA`; Phase A step 1 ("the id group … and part 1's `AREA_ID` accept and refuse the same list of twelve strings") · This is false. Part 1's area id is `^[a-z0-9][a-z0-9-]*$` (up to 40 characters, so it can start with a digit), while `SHARE_AREA`'s group is `[a-z][a-z0-9-]{0,39}`. A taxonomy area such as `2fa` is valid in part 1 but can never be shared, and an invalid share id fails the whole list closed. The twelve strings are not named either, so the implementer chooses them and can hide the gap. Fix: copy part 1's pattern exactly, or record the narrowing as a decision, and list the twelve strings.
- F-3 · Major · Signatures `levelOf`; Phase C step 5 decide cases; spec CUJ 1 · `levelOf` answers `no-project` for any project with no row, and `setLevel(…, "local")` deletes the row. So in a real store every project at Nothing explains as `no-project`, never `level-local`. CUJ 1, `share explain` and the memory case "at `local` → `level-local`" can then only pass with a hand-built `local` row that never exists in practice. Fix: `levelOf` should answer `local`/`level-local` for a known project without a row and keep `no-project` for project 0 and orphans; that means the policy must carry the set of known project ids.
- F-4 · Major · Phase F step 14 (Sharing.vue "saves through `saveSettings`"), `ui/src/api.ts` changes · The server refuses a widening `PUT /api/settings` without `confirm: true`. But `SettingsPatch` is `Partial<Record<SettingKey, …>>` and `api.saveSettings`/`settings.ts saveSettings` send only the patch, so as written every widening save from the page gets a 400. The 400 body is also `{ error }`, not `{ errors }`, so `saveSettings` rethrows it rather than returning false. Fix: name the change, e.g. a `saveSettings(patch, { confirm })` that adds `confirm` to the body, and say how its error becomes the "Sharing not saved" toast.
- F-5 · Major · Phase F step 14 (both Confirm dialogs), spec §Changes ("the counts … for what the change releases") · `wouldLeave` and `GET /api/sharing` count only under the policy in force. For a project at Nothing, `perProject` is 0, so the dock dialog will always say "0 knowledge entries … would leave". The same goes for unshared area toggles and the Settings dialog. No API takes a proposed level or patch. Fix: specify how the hypothetical counts are computed, for example a `GET /api/sharing?project=<id>&level=<l>` or a patch preview built on a policy with the change applied.
- F-6 · Major · Signatures `applySettingsPatch`, `reconcileSettings` · `applySettingsPatch` must set `sharing.settings_seen` to "the lists now in force", but it receives no `env`, so it cannot narrow. `reconcileSettings` compares against `policy.areas`, which leaves out inert ids, while the file list includes them. With an env narrowing or an inert id, every save will flip the baseline: a spurious `file` change row, an epoch bump and a standing doctor warning. Fix: add `env` to `applySettingsPatch`, and define the baseline as the effective settings lists (env-narrowed, before taxonomy filtering), compared as `areas ∪ inert`.
- F-7 · Major · Phase G step 16 (`src/status/report.ts`) · `statusReport(db, project, dataDir)` has no `env` or `now`, yet `loadPolicy` and `wouldLeave` need both, and the tests must pass their own env. The plan does not say which signature changes or what `level` is when `project` is null. `wouldLeave` also needs a generation for `memoryItems`, but `generationOf` writes when the key is absent, and status opens the store read-only (`openExisting`). Fix: give the new `statusReport` signature, the null-project level (`local`), and a read-only generation source that never writes.
- F-8 · Major · Signatures `resetSharingInCopy`; Phase G step 15 "a failing reset" case · The test swaps `sharing_levels` for a view, but the plan does not say how "when `sharing_levels` exists" is checked. If it copies `inspect`'s `type = 'table'` pattern, the view is skipped, `sharingReset` is 0 and the restore succeeds, so the test fails or the guard is wrong. Fix: state the check (`sqlite_master WHERE name = 'sharing_levels'` with any type) or change the fault injection.
- F-9 · Major · Phase F step 14 (Sharing.vue Save "writes both keys") · When the environment locks one key (source `env`, narrowed), Save still writes that key from the effective list shown. The file's wider value is overwritten with the environment's narrowing, and it stays narrowed after the variable is unset. Fix: leave out of the patch any key for which `fromEnvironment` is true.
- F-10 · Major · Phase F step 12 (`listProjects` LEFT JOIN) · The raw `sharing_levels.level` is returned as `sharing: Level`. A disabled project or one whose alias was lost will show a "Knowledge" pill while `decide` keeps everything, and a hand-inserted `wide` gives `LEVEL_LABELS[undefined]`. Fix: say whether `sharing` is the effective level from `loadPolicy` (recommended) or the raw row with a downgrade field.
- F-11 · Major · Phase G step 15 doctor `ok` case · The expected detail `1 projects share knowledge, 1 knowledge and memories` contradicts "the helper `plural` renders `1 project shares knowledge`; use its output". Part 1's `plural(n, singular, pluralForm)` pluralises the noun only, not the verb, so the assertion has no single answer. Fix: write the exact string and how it is built.
- F-12 · Major · Phase B step 3 / AC-13 (part 1's module-migrations test "nothing else changes") · Part 1 takes a module backup "only when a module already had a recorded version", and the plan does not say whether that is per module or for the whole store. With `sharing` added to `MODULE_SCHEMAS`, the withdrawn-shape case ("exactly one backup … `-v7-`") and any store already at knowledge 6 could get a second backup, against the spec's "no backup". Fix: state the rule this part depends on (the backup is decided per schema, by that schema's own recorded version) and the expected backup count in the withdrawn case.
- F-13 · Major · Test-first records; Phase C steps 5 and 6 · Step 5 creates `sharing-contract.test.ts` (AC-15) but names only AC-3, AC-4 and AC-5, and the records paragraph covers AC-1 to AC-12. So no `crew tdd before … AC-15` is made, while step 6 records an `after` for AC-15. The gate would see a criterion with no red record. Fix: add AC-15 to step 5 and to the records paragraph.
- F-14 · Nit · Signatures `publicSettings` · The source rule says "differs from the file's or equals it", which is always true, and the plan never says which `value` a sharing key reports: the env's raw list, the file's, or the effective list. Only the `none`/`env` case is pinned.
- F-15 · Nit · Phase G step 16 (doctor) · "`sharing` after `backups`": part 1 also inserts `knowledge` after `backups`, so the order of the two checks is unstated.
