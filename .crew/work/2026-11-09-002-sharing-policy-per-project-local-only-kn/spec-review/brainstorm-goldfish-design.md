# design findings for 2026-11-09-002-sharing-policy-per-project-local-only-kn
reviewer: goldfish-design
read: .crew/work/2026-11-09-002-sharing-policy-per-project-local-only-kn/concept.md (whole), .crew/work/2026-11-09-002-sharing-policy-per-project-local-only-kn/brief.md (whole), .crew/work/2026-11-08-003-knowledge-store-entries-as-markdown-with/spec.md (whole), .crew/work/2026-11-09-001-knowledge-for-the-agent-mcp-tools-search/spec.md (whole), src/settings/settings.ts, src/core/project.ts, src/store/links.ts, src/store/memories.ts (first 60 lines and its exports), src/store/migrations/0001_init.sql (projects, sessions, turns, memories), src/ui/server.ts (auth lines only), docs/adr/0018-linked-projects.md; lens: failure modes, consequences and limits of a policy that decides what personal and team data leaves a machine

## Findings
- F-1 · Blocker · The policy / unit of egress · The predicate decides per entry, but the concept never says what leaves: index rows, file bytes, or the git repository. Part 1 keeps every version, decided and rejected proposals with their bodies, and the old area and status values in git history, and part 1 names `base_hash` "for the sync", which points at moving repositories. If part 6 pushes or mirrors a repository, a per-entry predicate cannot stop past private versions, proposals or earlier private-area content from leaving. This part has to state that only the current file content of an allowed entry leaves, never history, or the "one place that decides" guarantee cannot hold.
- F-2 · Major · The policy / revocation · The predicate is stateless and only filters what goes out. Nothing says what happens to data already on the server when a project goes back to `local`, gets disabled, an area is taken off the list, or an entry goes from `active` to `archived` or `draft`. Parts 5 and 6 cannot tell "never shared" from "shared, now withdrawn" without a record of what left, so they will either keep stale private copies on the server or need a ledger this part does not define. Withdrawal semantics (a tombstone, a delete request, or "once sent, sent", said plainly in the viewer) have to be decided here.
- F-3 · Major · The policy / time-of-check versus time-of-send · `mayShareEntry` takes `{scope, projectId, area, status}`, which the caller will read from the index. Part 2's D-16 accepts a stale index, and a hand edit leaves the row stale until a rebuild. A file whose area was changed by hand from `sales` (shared) to `finance` (private), or whose status became `draft`, still passes on the old row while the sync sends the new bytes. The predicate must be fed from the bytes being sent, after `ensureFresh` and with a clean `git status`, and a dirty or problem file must never leave.
- F-4 · Major · The policy / snapshot staleness · "Loaded once per call site" means a long sync keeps a policy from before the person's change: a project set to `local` mid-sync keeps uploading. Nothing says how fresh the policy must be, or that it is re-read before each batch or each send.
- F-5 · Major · Storage / environment wins over the file · Settings follow the rule "the environment wins over the file". An exported `WIZARDINGCODE_MEM_SHARE_WORKSPACE=on` or `SHARE_AREAS` in one shell, in a host agent's MCP env block, or in direnv makes the policy differ by process. The drain or sync started by a hook inherits the host agent's environment, so whether data leaves depends on which agent triggered it, and the viewer's switch cannot turn it off (the file loses). The share keys either need to ignore the environment, or the policy has to be read from one place and doctor must warn when env and file disagree.
- F-6 · Major · Storage / hand edits and parse rules · `loadSettings` does not apply `RULES` at load time: it passes strings through raw (see `modules`) and falls back silently for on/off. The concept does not say how a hand-edited `WIZARDINGCODE_MEM_SHARE_AREAS` is parsed: `Sales`, ` sales `, `*`, `all`, a trailing comma, duplicates, an id with a path separator. Loading must fail closed (an invalid token means not shared, never a wildcard) and must be specified, because a lenient parser here turns a typo into egress.
- F-7 · Major · Storage / unknown area kept · "An unknown area is kept and warned" turns the list into pre-authorisation. An area id that was removed (part 1 allows `area remove`) and later re-added, or added for the first time with a different meaning (say `people` re-added for salaries), is shared the moment it exists, with no new consent. Unknown ids should be inert until the person confirms them again, or removing an area should take it off the share list.
- F-8 · Major · The policy / area ids are not root-qualified · Part 1's D-9 gives the workspace and the shared repository separate taxonomies, and their ids can mean different things, but `sharedAreas` is one flat set of bare ids. Sharing `finance` meant for the team's shared taxonomy also shares the workspace's and every `knowledge`-level project's `finance`. Either the set is keyed by root, or the concept states that one id means one thing in every root and the Sharing card shows both labels.
- F-9 · Major · The policy / memories ignore areas · Memories have no area, so a project at `all` sends every active memory, including ones about finance, people or client terms, whatever the area list says. The mission says "knowledge areas ... can be kept off the server", and the person will read private areas as protecting the subject everywhere. The asymmetry must be stated in the viewer and the ADR, or `all` needs its own filter (by memory kind, by `scope = 'branch'`, by `origin = 'imported'`).
- F-10 · Major · The policy / what else rides along · The predicate covers entries and memories only. Unaddressed: turns and history (raw prompts, final text, commands, `transcript_path`), sessions (`cwd`), `memory_files` paths and `terms` (absolute paths with the user name), `branch` and `commit_sha`, the project `key` and `name` (local `path:` aliases), entry `author` and commit e-mails, and `supersedes` ids pointing at private entries. The sync must name a project to the server somehow. The concept must list what never leaves and what metadata necessarily goes with an allowed item, or part 6 will invent it.
- F-11 · Major · Project identity / folder reuse · `resolveProject` keeps a project id when a folder or `gitdir:` path is reused by a new repository with no remote (`reused` is only computed when the new repository has a remote). A person who deletes a folder and runs `git init` on a different, private repository at the same path gets the old project id and its `all` level, so the new repository's memories and knowledge leave. A level of `knowledge` or `all` should be tied to the strongest alias at the time it was set, and dropped to `local` (with a doctor warning) when the identity changes.
- F-12 · Major · Project identity / adoption of imported projects · `adoptable()` merges any new directory with a matching basename into an `imported:<name>` project. If that imported project was set to `knowledge` or `all`, an unrelated new folder that happens to share the name inherits the level. Adoption has to reset the level to `local` or ask.
- F-13 · Major · Project identity / knowledge repository adoption · An entry's `projectId` comes from `knowledge_repos`, and part 1 lets `resolveRepo` adopt a manifest whose aliases intersect, and `rebuild` remap it. A repository adopted or remapped to another project takes on that project's level. Orphan and ambiguous repositories have no defined level. The concept must say that `projectLevel` is `local` for project 0 (when the scope is project), unknown ids, orphans and ambiguous manifests, and that remapping resets to `local`.
- F-14 · Major · Disabled projects / re-enable · "A disabled project is local whatever its column says" keeps the column, so turning memory back on silently restores `all`. A person who disabled a project because it turned sensitive resumes sharing without a new choice. Disabling should reset the column, or re-enabling should show the level and ask; doctor's warning comes too late for consent.
- F-15 · Major · Storage / core migration 8 breaks the rollback story · Parts 1 and 2 chose the module namespace so that `user_version` stays 7, and they state the rollback target is 0.6.0. ADR 0018 records that older binaries refuse a newer core schema. A core migration 8 shipped in the same release makes 0.6.0 refuse the database, which falsifies parts 1 and 2's rollback claims and forces every agent's binary to move together. Either keep the level in a module-owned table (`project_sharing(project_id, level)`, local when absent), or state the new rollback target.
- F-16 · Major · Storage / database restore and store move · The level lives in the database, which `backup` copies and restore swaps. Restoring a backup taken while a project was `all` silently re-grants sharing the person later revoked. Restore needs to keep current levels, or reset to `local` and report, or this behaviour has to be stated.
- F-17 · Major · The policy / failure of the policy load · Nothing says what happens when the policy cannot be built: the database is unreadable, the store directory is on a missing external disk, the module schema is too new, the column is missing, the env file is unreadable. The predicate and its loader must fail closed (nothing leaves, an error is logged), as a stated rule with a test, because a caller catching an error and sending anyway is the likely bug.
- F-18 · Major · The viewer and the CLI / consent forgery by agents · `wizardingcode-mem share project all` runs with no confirmation, and every host gives agents shell access, so an agent can set any project to `all` (and edit `<data dir>/env`) without the person knowing. Part 1 already names agent shell access as the guarantee's boundary; here it decides egress. At least: the CLI asks for confirmation on a TTY or needs `--yes`, every widening is logged with time and source, and status or doctor shows the last change.
- F-19 · Major · The policy / shared scope default contradicts "the team's" · "The shared scope always" combined with an empty `sharedAreas` by default means the team's own repository sends nothing until the person lists areas. Meanwhile the shared scope's content is partly what part 6 pulls from others, which the person never authored. The concept should say whether re-sending pulled entries counts, and whether a locally written entry in the shared scope in a private area stays local (it does as written), so part 6 does not special-case the shared scope.
- F-20 · Nit · The policy / one global area list · Areas are shared globally, so sharing `code` for one `knowledge`-level project shares `code` for every `knowledge`-level project. That is a product choice, but the viewer's per-project row should show the effective areas so the person sees the cross-project effect.
- F-21 · Nit · Status and doctor / counts on every call · `status` and `GET /api/sharing` count the memories that would leave over the whole store (about 90,000 rows on the author's store, by ADR 0018) on each call. That is cheap with an index on `(project_id, status)` but unmeasured. Name the query, the index it uses and a budget, and keep it off the hook path.
- F-22 · Nit · The policy / predicate inputs · `mayShareMemory` takes `isUserRule`, but memories also carry `scope = 'branch'`, `stale` and `origin = 'imported'` (imported before today's redaction patterns). The concept should say whether each is shared at `all`, and why.
