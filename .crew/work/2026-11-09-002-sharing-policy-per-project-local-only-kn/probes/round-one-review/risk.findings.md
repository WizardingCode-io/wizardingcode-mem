## Findings
- F-1 · defect · src/backup/backup.ts:122 · `resetSharingInCopy` runs `PRAGMA journal_mode = DELETE` on the unpacked copy. That setting is stored in the file, and `openDb` turns on WAL only when it creates a database (`enableWal` is called only when `current === 0`, src/store/db.ts:177). So the store that replaces the live one after any restore stays in rollback-journal mode for good. From then on, readers and writers (hooks, the drain, the viewer) block each other and get SQLITE_BUSY more often. Hooks fail open with exit 0 and empty stdout, so the lost captures and notes show up in no log line and no `doctor` check, and nothing switches WAL back on. The spec (spec.md:305), the plan (plan.md:31) and the ADR (0025:150) all ask for DELETE to avoid side files, but none of them says the store must go back to WAL after the swap, and the AC-12 restore tests never check the journal mode. One thing to confirm before acting: the copy comes from `VACUUM INTO` of a WAL store (backup.ts:68). The comment "so no side file is left beside it" suggests the raw open did create -wal/-shm files, which would mean the copy was WAL until this change. If the copy was already in DELETE mode, the same problem existed before this item and belongs under Outside the change. The fix in that case is the same: run `PRAGMA journal_mode = WAL` on the restored store after the rename, or have `openDb` turn on WAL whenever the file is not in WAL mode.
- F-2 · advisory · src/sharing/report.ts:509 · `GET /api/sharing` (`fresh: true`) calls `ensureFresh` for the workspace, the shared repository and every project repository above Nothing, one after another, through `Bun.spawnSync`. Each call is limited by `gitTimeoutMs`, but they all run in the viewer's process, so a slow or stalled git freezes the whole viewer for up to the number of repositories times the timeout every time the Sharing page loads. A failure is caught and logged (`sharing.refresh`), so it is visible and recovers, and the spec states that the cost grows with the person's choices (spec.md:362). An overall time budget for the refresh pass would make the first hour safer.

## Outside the change
- src/store/db.ts:177 · WAL is turned on only when a database is created, and `doctor` never reports the journal mode. Any path that puts a non-WAL file in the store's place (a restore, a hand copy, a legacy import) leaves it like that without anyone seeing it. This is existing debt, and F-1 is the first path in this item that triggers it for certain.
- src/settings/env-file.ts:38 · `readEnvFile` turns any read error, such as a permission error, into an empty map. For sharing this fails closed (empty lists). But `previewSettingsPatch` and `recordHandEdit` would then compare against empty lists, and an unreadable file would look like a hand edit back to `none`. This is existing behaviour that the new audit relies on.
