# security findings for 2026-11-09-002-sharing-policy-per-project-local-only-kn
reviewer: review-security
read: 7 files (the rubric; probes/round-one-change.patch, all of its src/ and ui/ hunks, skimming the tests; src/ui/server.ts; src/settings/settings.ts; src/settings/env-file.ts; src/core/git.ts), risk areas: data-migration, personal-data

## Findings
- F-1 · defect · src/ui/server.ts:432 · A caller holding the viewer token can widen sharing without confirming it. They send `PUT /api/settings` with no `confirm` and a non-sharing value that has a newline in it, for example `{"WIZARDINGCODE_MEM_AUTHOR":"Ana\nWIZARDINGCODE_MEM_SHARE_ROOTS=workspace,shared"}`. The new guard looks for a sharing key only in `validated.changes`, so it does not fire. The request goes to `saveSettings`, and `writeEnvFile` writes the value raw (`asString` trims only the ends, and `authorNameProblem` at settings.ts:349 checks only the `agent:` prefix). The file then holds a wider roots or areas line. That widening skips the server-side `NeedsConfirm` check (ADR 0025: "the server, not the viewer, is where confirmation is required") and is later logged with source `file` instead of `viewer`. This breaks the ADR's promise that every widening made through the viewer is confirmed and logged with its true source. Fix it where the input enters: refuse `\r` and `\n` in every setting value in `validatePatch`, or have `renderEnvFile` refuse them.
- F-2 · defect · src/sharing/store.ts:331 · `setLevel` treats any `remote:` alias as a team identity. `normalizeRemote` (src/core/git.ts:137 and :149) turns an origin that is a local path or a `file://` URL into `remote:/Users/<name>/…`. So a person can run `share project knowledge --yes`, or use the dock, in a repository whose origin is a local bare repo, and the level is bound to their home-directory path. The contract this item pins then carries that path to the team server in every `OutgoingEntry.remoteAlias` (types.ts:152), every `OutgoingMemory.remoteAlias` (types.ts:163) and every project entry uid `project:remote:/Users/…:<uuid>`. That is the local-path personal data the ADR's "never" list (`path:` aliases) is meant to keep in. Nothing is sent in this part, but the binding is stored now and part 6 is told to use it. Fix: accept only a `remote:` alias whose normalised form starts with a host (no leading `/` or `.`), and answer `no-remote` otherwise.
- F-3 · advisory · src/cli/commands/share.ts:194 · `share roots` and `share areas` call `applySettingsPatch` with `confirm` hard-coded to `true`, after a preview read from the file earlier. If the file is narrowed between the preview and the write (for example, from the viewer at the same moment), the list the person thought widened nothing is written as an unconfirmed widening. Pass `true` only when `--yes` was given or the question was answered yes, and let `NeedsConfirm` answer the race.
- F-4 · advisory · src/sharing/policy.ts:1777 (patch line; `areasInForce` in `readPolicy`) · An area id listed while it is not in any taxonomy (`share areas workspace:future --yes`, or a hand edit) comes into force when someone later adds that area to the taxonomy. Its entries then may leave with no confirmation showing their count; the confirmation given at listing time showed 0. The epoch moves, but nobody is asked.
- F-5 · advisory · src/backup/backup.ts:170 · Levels are reset only by this version's `restoreBackup`. A restore done by the 0.6.0 rollback binary, or by putting a `.replaced-<time>` file back by hand, keeps the copy's `sharing_levels` and its generation. After re-upgrading, those levels take force without being chosen again. The ADR names 0.6.0 as the rollback target but does not state this.
- F-6 · advisory · src/settings/settings.ts:1133 (patch line; `effectiveSharing`) · "The environment never widens" holds per key for one data directory. `WIZARDINGCODE_HOME` and `WIZARDINGCODE_MEM_STORE_DIR`, which the environment still controls, can point a process (a future sync among them) at another env file or database with wider lists or levels. The boundary paragraph should say so.
- F-7 · advisory · src/sharing/store.ts:331 · A reused folder with no remote inherits the old project's level, as ADR 0025 states. Because `project_aliases` only ever grows, `unbound-alias` cannot fire in practice today, so binding a level to a remote gives less protection than the ADR's text suggests. Consider reconciling when the folder's current repository has no `remote:` alias of its own.

## Outside the change
- src/settings/settings.ts:371 · `asString` and the existing rules for `WIZARDINGCODE_MEM_AUTHOR`, `TYPESAFE_API_KEY` and the S3 region/access/secret keys accept embedded newlines. Through `renderEnvFile` (src/settings/env-file.ts:64, which writes values raw), any setting can be injected into the env file, `WIZARDINGCODE_MEM_STORE_DIR` included, which the patch rules otherwise refuse. This is debt; F-1 is the consequence inside this change.

## Not answerable
- personal-data: right to erasure on the server · no server and no withdrawal path exist in this part (parts 5 and 6). Only `decide`'s `withdraw` for a memory that is no longer active could be checked, and it is correct.
- Boundary on Windows · Windows was not run. Whether `normalizeRemote` and `remoteAliasOf` turn a UNC or drive-letter origin into a `remote:` alias (the F-2 case) could not be observed.
