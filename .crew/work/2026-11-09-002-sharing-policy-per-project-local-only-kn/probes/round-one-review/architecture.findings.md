## Findings
- F-1 · defect · src/sharing/report.ts:167 · The identity in the contract does not survive the policy's own lifecycle (rubric Q2 and Q3).
  - What the base says: ADR 0025:122 says a project entry's uid uses "the one its level is bound to, also after the project lost it, so that what was sent under it can still be withdrawn". CUJ 6 and the README say lowering is withdrawn by the next sync.
  - What the change does: `entryAliases` takes the bound alias only from the live `sharing_levels` row. Two paths delete that row:
    - `reconcileLevels` (src/sharing/store.ts:366). This is exactly the case "the project lost its alias". ADR 0025:192 makes part 6 run it at every batch before it decides.
    - `setLevel(..., "local")` (src/sharing/store.ts:323).
  - The result: after the row is gone the uid falls back to `MIN(remote alias)`, or to the empty alias (`project::<uuid>`). `decide` then finds no `sent` record under the new uid and answers `keep`, never `withdraw`. This happens for every project that lost its bound alias. It also happens for a project lowered to Nothing whose bound alias was not its first by name (the CLI binds the folder's current remote, src/cli/commands/share.ts `remoteAliasOf`).
  - Fix, choose one:
    - (a) Keep the binding the uid depends on apart from the level row, so that reconcile and `local` delete the level but not the alias the ledger was written under. The ledger's own `sent` rows can also supply it.
    - (b) If the build keeps today's data model, state the limit in ADR 0025 (Identity of an item, Known limits, What parts 5 and 6 must do), with part 6's duty to withdraw ledger rows whose uid no current item produces. The spec's "empty alias" uid (`project::<uuid>`) also needs naming in the ADR's identity section.
- F-2 · defect · src/sharing/report.ts:207 · `readEntries` (and `areaTotals` at :274, used by `findEntry` and so by `share explain`) read `knowledge_entries` and `knowledge_repos` with raw SQL. Their only guard is `sqlite_master` (`tableExists`).
  - What the base says: CLAUDE.md:17 says `schema.ts` holds `requireSchema`, "which everything that reads or writes the tables calls". ADR 0020 K3 says modules own their tables.
  - What the change does: on a store whose knowledge schema is newer than this binary, the sharing counts read rows of a shape this version does not know. Or they throw, and `status` would then fail too, since `statusReport` → `sharingStatus` → `wouldLeave` has no try. Only the `fresh: true` path reaches `requireSchema`, through `ensureFresh`.
  - Rubric Q1 (a boundary crossed into another owner's tables) and Q4 (bypassing the module's guard).
  - Fix: check `moduleSchemaState(db, KNOWLEDGE_MODULE, KNOWLEDGE_SCHEMA_VERSION)` (or `requireSchema` through the store) before any read of the knowledge tables. When it is too-new, count zero entries and add one policy problem. Or read through a knowledge index function that already calls it.
- F-3 · defect · src/sharing/types.ts:164 · The pinned outgoing contract types the texts that leave as plain `string`: `OutgoingMemory.title`/`body` (:164) and `OutgoingEntry.frontmatter`/`body` (:153). The hash input `Pick<OutgoingMemory, …>` in src/sharing/hash.ts is typed the same way.
  - What the base says: the project has an outbound type for redacted text, the `Redacted` brand (src/core/redact.ts:5). The other edge where text leaves the machine requires it (src/judge/types.ts:15 `text: Redacted`), as do the stores (src/store/memories.ts:12). ADR 0025:124 and :190 make `redactForSend` "a required step of the contract", and `redactForSend` already returns `Redacted`.
  - What the change does: a payload built from unredacted text type-checks, and so does a hash taken over it. The pinned key lists guard field names, not this. Rubric Q3/Q4: a contract that does not carry the project's own guard for its integration edge.
  - Fix: type those fields `Redacted` in `OutgoingMemory` and `OutgoingEntry`, which carries through to `memoryHash`'s input, and say so in ADR 0025's contract table.
- F-4 · advisory · src/sharing/types.ts:242 · `LedgerRecord` (the input part 6 must map `sharing_ledger` rows into) and `Decision` (:252, `decide`'s output), like `Item`, have no pinned key list. ADR 0025:87 pins only the four item and payload types, so a field added to the ruling's input or output does not fail the contract test.
- F-5 · advisory · src/cli/commands/share.ts:114 · `policyInForce` (load, run both reconciles, load again) is written twice, here and at src/ui/api.ts:916. ADR 0025:192 asks part 6 to do the same, which would make a third copy. Rules in this codebase live in one place each (CLAUDE.md:17, "Three rules live in one place each"). Fix: export it once from src/sharing/policy.ts, which may import the store.
- F-6 · advisory · src/sharing/policy.ts:53 · `areasOf` re-implements the knowledge module's `taxonomyFor` (src/modules/knowledge/repo.ts:712), with the same `kindAt`, `readRegularFile` and `parseTaxonomy`, outside the module. CLAUDE.md:17 still names `doctor` as the one reader of the repositories that does not go through `openRepo`. Fix: reuse the module's reader, or name this second reader in CLAUDE.md. This may depend on whether `taxonomyFor` existed at 52c8acb (see Not answerable).
- F-7 · advisory · CLAUDE.md:35 · The settings line still says "the environment wins" with no exception. This change makes that false for two keys (ADR 0025 D-13). The new bullet at CLAUDE.md:18 says it, but the settings line it contradicts was left as it was.
- F-8 · advisory · src/sharing/store.ts:228 · `SetLevelInput.source` accepts any `ChangeSource` (`restore`, `file`, `system`). The data model allows only `viewer | cli` for `sharing_levels.source` (the migration SQL and ADR 0025:46). Narrow the type to those two.
- F-9 · advisory · ui/src/api.ts:31 · `sharingReason: string` copies the server's `Reason` by hand, while the same file already imports `Level` and `Root` from src/sharing/types.ts. Import `Reason` as well, so the viewer's contract follows `REASONS`.
- F-10 · advisory · src/backup/backup.ts:114 · `resetSharingInCopy` runs `resetLevels`, which deletes and writes in the copy's `sharing_*` tables, without checking the copy's recorded `sharing` schema version. Elsewhere a newer sharing schema closes the policy and refuses writes (ADR 0025:166). A v7 copy taken by a binary with sharing version 2 would be rewritten in a shape this binary does not know.
