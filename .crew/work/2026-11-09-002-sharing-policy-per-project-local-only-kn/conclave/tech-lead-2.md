# lead-security: 2026-11-09-002-sharing-policy-per-project-local-only-kn — spec
verdict: returned
R-1. spec.md "Settings" (Narrow-only, D-13) and "Changes, confirmation, epoch" (D-17): a hand edit of `<data dir>/env` that adds a valid root or area widens with no confirmation, no `sharing_changes` row and no epoch bump, so a sync that stops "when the epoch moved" never notices. Add a baseline, for example the last-seen roots and areas kept in `meta` and compared by `loadPolicy`. A difference that widens must be logged with source `file`, must bump the epoch, and must be shown by `doctor` and `share status`. Add an AC and a test for it.
R-2. spec.md "The viewer" (`PUT /api/settings` bullet) and AC-9: only `PUT /api/projects/<id>/sharing` requires `confirm: true`. A widening of the roots or areas through `PUT /api/settings` is saved and logged with no server-side confirmation, because the dialog lives only in the client. The route must refuse a patch that widens either sharing key without `confirm: true`, as `move` and `restore` do (400 "confirm: true is required to widen sharing"). AC-9 and `plan.md` task 11 need a case for it.
R-3. spec.md "Settings" and `decide` step 4: roots and areas are global, with no destination in their key. D-9 says a second destination "starts with every level `local`", but the first sync to a second server would send everything the roots and areas already release. Either key the lists by destination, or state in the contract and the ADR that `decide` allows only `team` and that a new destination needs its own root and area keys. Add a test that a destination other than `team` is `keep` even with roots and areas set.
R-4. spec.md `decide` step 3 and D-11: "a received item never travels on" holds only if parts 5 and 6 write the `received` record. There is no structural guard, and a received memory gets a new local row id on this machine. The contract must require that a received item is written together with its `received` ledger record in one `withWrite`. It must also require that a received memory has an `origin` (for example `team`) that step 4 excludes with a reason, and that received entries are marked so they are excluded too. Add a `decide` case for each.
R-5. spec.md "What leaves with an item, and what never does" and `plan.md` Phase C/H: the spec says the never-leaves list is "asserted by a test over the item types", but no `plan.md` task or AC contains that test. AC-14 is only "observed". Add a task and an AC that fail if `Item`, `EntryItem` or `MemoryItem` gain a field naming a body, a path, a branch, a commit, a transcript, a key or a user-rule payload. The test should also check that `REASONS` and `REASON_TEXT` stay in step.
R-6. spec.md "Redaction at the edge" and AC-14: redaction is named as a required step but is not testable in this part. Add a contract test in `src/sharing/` (a `redactForSend(text)` wrapper, or a pinned assertion that `redact` maps `<private>x</private>` to `[PRIVATE]`). The ADR must state that this is the only text-level protection: paths and secrets outside `<private>` are not stripped, which is also why entry and memory bodies leave as written.
