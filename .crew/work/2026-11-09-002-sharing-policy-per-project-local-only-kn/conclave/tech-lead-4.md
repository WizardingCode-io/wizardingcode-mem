# lead-etl: 2026-11-09-002-sharing-policy-per-project-local-only-kn — spec
verdict: returned
R-1 · spec.md:240 and plan.md:67 (step 16): `resetLevels` must run on the unpacked copy before `renameSync(unpacked, current)`, right after `inspect` (`src/backup/backup.ts:127-150`), not after the swap. If it throws after the swap, the outer catch (backup.ts:162) reports `failed` while the copy's wider levels are already live and `current.replaced-<now>` is already renamed. That is a fail-open restore. Run before the swap, a failure aborts with the old store intact. Say so, and add a test where `resetLevels` throws and the store is unchanged.
R-2 · spec.md:139, 278 and plan.md:39 (`resetLevels`): the restored copy carries its own `sharing.epoch`, which can be lower than the epoch the replaced store had reached and that a sync may already have recorded. Read the replaced file's epoch before the swap and write `max(copy, replaced) + 1`, so the epoch never goes backwards. Add this to the restore case in AC-12.
R-3 · spec.md:132 and 281 (Risks): "a memory's row id is stable on this machine" does not hold across a restore. `memories.id` is a plain `INTEGER PRIMARY KEY` (`src/store/migrations/0001_init.sql:65`), so an older copy hands ids already sent to other memories. State this in the Risks and in the ADR as a limit, and say what `restoreBackup` does about `sharing_ledger`. Either a documented reset or a recorded generation part 6 must scope the uid with, but not silent reuse.
R-4 · spec.md:137-138 and plan.md:60 (`saveSharingSetting`, `logSharingSettingChange`): the env-file write and the change row plus epoch bump are separate steps. A busy timeout or crash between them leaves a widened file with no `sharing_changes` row and no epoch bump. Fix the order: read `old` from the file's list, then inside one `withWrite` write the file, insert the change and bump the epoch. A failed file write rolls back the log. The viewer's `PUT /api/settings` must use this same single path, not a second factored-out call. Add a test with a throwing `saveSettings` that leaves no row and no epoch change.
R-5 · spec.md:155 and plan.md:13 (`SharingPolicy.levels`): `ReadonlyMap<number, …>` is keyed by `projectId` alone, but the storage key is `(project_id, destination)` (D-9, `sharing_levels` PK). A second destination would overwrite the first. Key it by destination and project (`Map<destination, Map<projectId, …>>`, or a composite key). `levelOf(policy, projectId, destination)` must read it that way, with a test of two destinations for one project.
R-6 · spec.md:197 and plan.md:20 (`memoryItems`, `wouldLeave`): the counts path computes `hash` (SHA-256 of title and body) and reads `title` and `body` for every candidate, up to 90,000 rows. That breaks the 200 ms budget (spec.md:289) at no benefit, since no ledger record exists in this part. Select only `id, project_id, status, stale, scope, origin, updated_at` for counting. Read `title`/`body` and compute the hash only for listed items (the 500 cap) and for candidates that have a ledger record. Add a 90,000-memory timing case to `tests/unit/sharing-report.test.ts`, as the spec itself promises a measurement.
