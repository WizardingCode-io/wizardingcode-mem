# lead-architects: 2026-11-09-002-sharing-policy-per-project-local-only-kn — spec
verdict: returned
R-1. spec.md:155 (`SharingPolicy.levels`) and plan.md:13: the two files give different types. The spec's `levels` has no `reason`, but `levelOf` returns downgrade reasons (`disabled`, `unbound-alias`) that only the plan's `levels` carries. The map is also keyed by `projectId` alone while the data model and `levelOf(policy, projectId, destination)` are per destination (D-9). A second destination, which part 5 or later may add, would overwrite the first. Key the map by destination and project, or use a nested map, and give the spec and the plan the same type with `reason`. Then parts 5 and 6 can build against `SharingPolicy` without reopening it.
R-2. spec.md:212 versus plan.md:60 and plan.md:18: the settings route is defined twice and differently. The spec says `PUT /api/settings` "calls `saveSharingSetting`", which writes the env file through `saveSettings` as well, so the file would be written twice. The plan has the route keep `saveSettings` and call a new `logSharingSettingChange`. That function is in no signature list and is created only inside task 12, after `store.ts` was built in Phase B. Pick one path. Declare `logSharingSettingChange` in the spec's store section and in the plan's `store.ts` signature, written in Phase B, and have `saveSharingSetting` call it. Also drop "the same `withWrite`" from spec.md:132 for the settings keys. A file write and a database write cannot share one transaction, so state the ordering instead (file first, then log and epoch, and what happens if the log fails).
R-3. spec.md:45 (D-11) and spec.md:111 (ledger `item_uid`): the uid contract is incomplete for `direction: "received"`. A memory's uid is its local row id, but a received memory would carry a server-side id in the same `item_uid` space. Either state that this design never receives memories (only entries, by UUID) and make `decide` and the ledger comment say so, or define the received-memory uid so it cannot collide with a local row id. Parts 5 and 6 would otherwise have to reopen the key.
R-4. spec.md:132, spec.md:139 and spec.md:240 (epoch and restore): `sharing.epoch` lives in `meta`, which travels in the backup, and `resetLevels` bumps the restored value. After a restore the epoch can fall back to, or equal, a value already used under a different policy. Part 6's rule "stop the run when the epoch moved" and the ledger's `policy_epoch` then lose their meaning. Make the epoch monotonic across a restore, for example by setting it to the larger of the pre-restore epoch and the restored one, plus one. Add the rule to the spec text and to AC-12, with a test in the plan (task 15, the backup cases).
