## Findings
- F-1 · advisory · src/sharing/report.ts:439 · `ledgerRecords` filters `item_kind = ? AND (destination = ? OR direction = 'received')`, and the OR means the primary key `(destination, item_kind, item_uid, direction)` cannot serve it, so every count (status, the viewer, `share status`) scans all of `sharing_ledger`, including every other destination's sent rows. The table has no writer in this part and the ADR (line 118) states the single scan, so this is a slower query and not a defect (rubric Q2).
- F-2 · advisory · src/sharing/report.ts:230 · Because of the `(?n IS NULL OR …)` predicates, `findEntry` (`share explain workspace/<slug>`) cannot use `knowledge_entries`' `UNIQUE (repo_id, slug)`, so each single lookup scans the whole knowledge_entries ⋈ knowledge_repos join even though an index exists. Small today, but a slower query (Q2). The query belongs to this item; the tables are the sibling item's.
- F-3 · advisory · src/backup/backup.ts:122 · `resetSharingInCopy` sets `PRAGMA journal_mode = DELETE` on the unpacked copy. The mode persists in the file that is then renamed into the live store, and `openDb` turns on WAL only for a new store (src/store/db.ts:177). So after a restore the live database is pinned to rollback-journal mode, and readers block the hooks' writers (Q6, availability). Whether the copy was already non-WAL before this change is not established (see Not answerable).
- F-4 · advisory · src/sharing/hash.ts:16 · `memoryHash` joins its fields with `\n`, but title and body can both contain newlines. An edit that moves a line between title and body gives the same hash, and `decide` then answers `keep, already-sent` where an update is owed. The hash also depends on `redactForSend(text, env)` with the calling process's environment, so the viewer, the CLI and the sync can hash the same memory differently and resend it. An encoding question (Q4) for part 6 before any ledger row is written.
- F-5 · advisory · src/sharing/migrations/0001_sharing_policy.sql:22 · The ADR states no retention or erasure for these tables. `sharing_ledger` will hold one row per memory: its `<generation>:<id>` uid, plus a hash of its redacted title and body (derived from personal text). Withdrawn rows are never pruned, and `sharing_changes` (line 41) grows with every change while `compact` does not touch it. This part writes no ledger row, and the change log holds levels and area ids only, so this is advisory: part 5 or 6 must state the ledger's retention before writing to it (Q5). `sharing_levels.bound_alias` holds a git remote that may name a personal account, but it duplicates `project_aliases` and is deleted with its row at Nothing or on reconcile, which the ADR states. No finding there.

Q1 (migrations) has no finding. The sharing migration only creates tables and inserts the generation with `INSERT OR IGNORE`, and is forward-only. Rollback to 0.6.0 is stated in the ADR (line 56). The run order is fixed by `MODULE_SCHEMAS` (knowledge, then sharing), the backup is decided per schema by that schema's recorded version (db.ts `migrateModules`), and nothing destructive runs. The restore reset deletes only the copy's `sharing_levels`, which is documented, and keeps the ledger. The memory candidate query uses `memories_rank`, which leads with `project_id`, and `user_memories`' primary key. Hashes are read in chunks of 500, as stated. Transactions span local file writes only (`applySettingsPatch`, the reset on the copy), never git or the network. `refreshRepos` runs outside any transaction. No finding falls in the sibling item's (2026-11-09-001) paths.
