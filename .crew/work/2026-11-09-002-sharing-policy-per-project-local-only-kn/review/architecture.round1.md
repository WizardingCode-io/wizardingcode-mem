## Findings
- F-1 · defect · src/ui/api.ts:86 · `listProjects` sets `ProjectSummary.remote` with its own SQL test, `EXISTS (… alias LIKE 'remote:%')`. Both the field's doc comment ("the one name a team can match it by, which a level is bound to") and ADR 0025 § Identity of a project say that only a host-led `remote:` alias (`isHostLedAlias`, src/sharing/levels.ts) names a project to a team, and that "the rule reaches every reader". `setLevel` (src/sharing/store.ts) and `entryAliases` (src/sharing/report.ts) apply that rule. This route does not, so the route contract now means something other than the domain rule (rubric Q1, a rule restated at the edge, and Q3, a field whose meaning differs from what it documents). Effect: for a project whose only remote is a local path or `file://` origin, the dock (ui/src/components/ProjectsView.vue:118, :303) enables the level control and hides "This project has no git remote". The PUT then answers 409 `no-remote`, and the person sees only the generic "Not changed". Fix: compute `remote` from the project's aliases through `isHostLedAlias` (for example, select the `remote:%` aliases and test them in code, as `entryAliases` does). Then pin it with a case in tests/integration/ui-sharing.test.ts for a project whose only remote is a path.
- F-2 · advisory · src/sharing/policy.ts:27 · The Design says `levels.ts` is the leaf both `store.ts` and `policy.ts` import "so neither imports the other". The loader imports `counterOf`, `levelRows`, `settingsSeen`, `fileListsOf`, `changedLists` and `hasLevelsTable` from `store.ts`. There is no cycle (store.ts never imports policy.ts), but the dependency direction differs from the Design and is not recorded in the spec, the ADR or CLAUDE.md. Either move the read helpers into a read-only leaf, or record the direction (policy → store readers, never the reverse).
- F-3 · advisory · src/sharing/policy.ts:53 · `areasOf` rebuilds the knowledge module's taxonomy read (`repoPath`/`kindAt`/`readRegularFile`/`parseTaxonomy`) beside the module's own `taxonomyFor` (src/modules/knowledge/repo.ts:712). Unlike `taxonomyFor`, it reads an unparseable file as "no taxonomy" and does not throw. The fail-closed reading is what the Design wants. Still, a second hand-written reader of a module's file is a rule kept in two places; a non-throwing variant in the knowledge module would keep one place.
- F-4 · advisory · ui/src/components/settings/Sharing.vue:120 · The Design defines a roots or areas widening against the file's own lists (`previewSettingsPatch`) and says "every path checks before it writes with those two functions". The page instead decides whether to open the dialog by comparing against the policy in force (`current.roots`, `current.areas`). In practice the two agree, because env-sourced keys and inert ids are left out of the patch, and the server refuses all the same. But the rule is restated in the viewer, and a mismatch would surface as "Sharing not saved" instead of the dialog. The preview route could answer `previewSettingsPatch`'s `widened` with the report.
