## Findings
- F-1 · advisory · src/sharing/policy.ts:20 · The spec's Design says `levels.ts` is the leaf that both `store.ts` and `policy.ts` import "so neither imports the other". The loader imports `changedLists`, `counterOf`, `fileListsOf`, `hasLevelsTable`, `levelRows` and `settingsSeen` from `store.ts`. The direction is still one way (`store.ts` imports nothing from `policy.ts`, so there is no cycle), and the Design itself has the loader read `levelRows`, so this is a Design detail read differently, not a crossed boundary (rubric Q5/Q6). Fix: change the Design's sentence to "store.ts never imports policy.ts" (which is what `levels.ts`'s own header comment already says), or move the six read helpers into a small read leaf.
- F-2 · advisory · src/sharing/levels.ts:6 · The doc comment that describes `DESTINATIONS` ("The destinations there are: the team's server, alone…") now sits above `REMOTE_ALIAS`, so `DESTINATIONS` (line 14) has no comment and `REMOTE_ALIAS` has two. Separately, src/sharing/report.ts:102 holds a comment with nothing under it ("The change counter an epoch was made from") left behind when `counterOfEpoch` moved to `levels.ts`. Fix: put the comment back above `DESTINATIONS` and delete the empty one in report.ts.
- F-3 · advisory · ui/src/api.ts:179 · The viewer takes `Level`, `Root`, `Reason`, `LEVELS`, `LEVEL_LABELS` and `buildSharingPatch` from `src/sharing/` as the Design says. But it writes `SharingReport`, `SharingChange` and `PolicyChange` again by hand, mirroring `Report` and `PolicyChange` (src/sharing/report.ts) and `ChangeRow` (src/sharing/store.ts) field for field. The neighbouring viewer types (`RestoreOutcome` and others) follow the same mirroring convention, so this is no drift. Still, no test pins these three route shapes, unlike the six contract types. Fix (optional): import them as types only, as is already done for `Level` and `Root`.

## Outside the change
- src/status/report.ts:186 · `knowledgeStatus` (the sibling item 2026-11-09-001's code, carried in this diff) reads `knowledge_entries` and `knowledge_shown` directly and guards with `moduleSchemaState` instead of the module's `requireSchema`. src/doctor/checks.ts:733 and src/store/compact.ts:52 do the same. This item's src/sharing/report.ts:90 follows that pattern, and its spec and AC-21 sanction it. CLAUDE.md's "requireSchema, which everything that reads or writes the tables calls" is therefore really followed inside the module only. Debt for the knowledge item: say so in CLAUDE.md or ADR 0024, or give readers outside the module one named guard.
