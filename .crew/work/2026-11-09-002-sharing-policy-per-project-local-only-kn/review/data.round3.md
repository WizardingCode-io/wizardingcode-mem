## Findings
- F-1 · advisory · src/sharing/report.ts:434 · `ledgerRecords` filters on `item_kind = ? AND (destination = ? OR direction = 'received')`. The primary key leads with `destination`, so the OR makes this a full scan of `sharing_ledger` on every `wouldLeave`, and that table will grow with every item parts 5 and 6 send. It is empty in this item and the scan is a stated choice (one grouped read instead of a uid list), so this is only a slower query. A second index on `(item_kind, direction)`, or the two branches run as a UNION over the key, would bound it once the ledger fills (Q2).
- F-2 · advisory · src/sharing/migrations/0001_sharing_policy.sql:51 · `sharing_changes_at` indexes `at`, but no reader in the diff filters or sorts on it: `recentChanges` orders by `id`. Every policy change pays for an index nothing uses (Q2, naming or cost only).
- F-3 · advisory · src/sharing/migrations/0001_sharing_policy.sql:22 · ADR 0025 and the migration state no retention or erasure for `sharing_ledger` and `sharing_changes`, and `compact` touches neither. The ledger keeps entry uids that carry a project's remote alias (`github.com/<owner>/<repo>`), and it keeps hashes of redacted memory text after a project goes back to Nothing and after a restore renews the generation. That is deliberate (ADR: part 6 computes withdrawals from the ledger). No row is written in this item, so this is not personal data without retention yet. Part 6 should state how long those rows are kept (Q5).

Answered with no finding:
- **Migrations (Q1):** the migration is forward-only, stated beside it ("Forward-only, like the core's"). It is additive only: three new tables, no foreign key or trigger on a core table, and `user_version` stays 7. The order is fixed: modules in `MODULE_SCHEMAS` order, each sorted by version, in one upgrade under the write lock. `mintGeneration` is INSERT OR IGNORE, so it never overwrites a generation a restore renewed. The backup is decided per schema, so the first sharing migration takes none, correctly, since it has nothing of its own to lose.
- **Restore:** `resetLevels` runs on the unpacked copy before the swap, in one transaction. On a failure nothing is renamed. It also works on a copy that has no sharing tables.
- **Queries (Q2):** the memory candidates use `memories_rank (project_id, …)`. `user_memories` joins on its primary key. The hashes are read 500 ids per query, one bound JSON value each. The knowledge joins use `knowledge_entries (repo_id, …)` and are guarded by `moduleSchemaState`.
- **Transactions (Q3):** in the GET /api/sharing route, the git refreshes run outside any transaction. `policyInForce` takes two short `BEGIN IMMEDIATE` transactions, measured at 0.35 ms p50 in probes/loader-latency.md.
- **Types (Q4):** `counterOf` guards against a value that is not a safe integer, and `stale` and `isUserRule` are compared with `=== 1`.

## Outside the change
- src/store/db.ts:116 (the `enableWal` call in `migrate`) · existing debt, advisory. `openDb` turns WAL on only when it creates the database. A `VACUUM INTO` copy is in rollback-journal mode, so every restore leaves the live store in DELETE mode. probes/restore-journal-mode.md shows this was already so before this item, and that this item's `PRAGMA journal_mode = DELETE` in `resetSharingInCopy` changes nothing. The fix is to check `journal_mode` on each open and turn WAL on when it is off.
