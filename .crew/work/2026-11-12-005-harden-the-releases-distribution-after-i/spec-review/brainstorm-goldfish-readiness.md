## Findings
- F-1 · Blocker · §2, "which is also the correct behaviour on a runner" · Today `gitEnv` sets `GIT_CONFIG_COUNT: "1"`, which drops any `GIT_CONFIG_KEY_n`/`VALUE_n` the environment carries on every call that holds the token. The hypothesis makes the token's clone, pull and push honour them instead, on a runner too. So any `url.<x>.insteadOf` or `pushInsteadOf` reaching the step's environment (for example written to `GITHUB_ENV` by an earlier step) sends the token-carrying push wherever that config points. That is the threat change 2 claims to remove ("the writer that holds the token takes its destination from the environment"), now through a general mechanism and no longer limited to off-runner. A second `http.https://github.com/.extraheader` in the environment would also put two Authorization headers on the request. The concept states as correct something that reopens the round-4 finding, and it names no guard (refuse or strip `url.*`/`http.*` keys from the inherited config, or append off-runner only).
- F-2 · Major · §2, gitEnv append · The behaviour for an inherited `GIT_CONFIG_COUNT` that is not a non-negative integer ("", "abc", "-1") is undecided: throw a `ReleaseError`, treat it as 0, or pass it through so every git call fails with git's "bogus count". So is whether stale `GIT_CONFIG_KEY_<count>`/`VALUE_<count>` slots from the environment are overwritten. An engineer would pick one, and the gitEnv unit test in tests/integration/release-push.test.ts ("the header is set for github.com only") needs the expected objects for count 0, count 2 and an invalid count.
- F-3 · Major · §2, the command's test · The concept doesn't say which tests in tests/integration/release-commands.test.ts change. `env()` (lines 393-407) feeds `PUSH_ORIGIN`/`PUSH_REMOTE` to the three local-repository cases, and the case "on a runner the two test overrides are ignored" (line 476) tests a mechanism that will no longer exist. A plan must say whether that case is deleted or becomes "on a runner, an inherited insteadOf is/isn't honoured", and its expected answer follows from F-1. It must also say that `env()` builds `GIT_CONFIG_COUNT=2` with `url.<origin.bare>.insteadOf=https://github.com/o/r.git` and `url.<remote>.insteadOf=<REMOTES[target]>` (the exact strings, including the `.git` suffix and the WizardingCode-io casing).
- F-4 · Major · §2, "for that to hold when a token is set" · None of the command tests sets `MARKETPLACE_TOKEN` today, so the append path (insteadOf at indexes 0 and 1, header at index 2) would never run end to end. At least one local-repository case must set a token, with an assertion that the push still lands. Even then nothing local can show that the header is sent, because after the rewrite the URL is a local path and `http.https://github.com/.extraheader` never matches. That the header still authenticates at github.com can only be seen in a real run.
- F-5 · Major · §1, tokenMask · Several choices are left open. Does `tokenMask(token)` return the line with or without a trailing newline, and do the conditions (token non-empty, `GITHUB_ACTIONS === "true"`) live in the command or in the function? Is the line printed before or after the `need(...)` checks, which run no git? Is it printed on a dry run, where clone still carries the token (it should be, but the text only says "when a token is set")? Where are the tests: a `tokenMask` unit case in release-push.test.ts, plus command cases in release-commands.test.ts asserting that `stdout.split("\n")[0]` equals `::add-mask::<base64("x-access-token:<t>")>` when on a runner with a token, and that the base64 appears nowhere in stdout or stderr off a runner or with no token.
- F-6 · Major · §1, "before any git call" · A test can't observe the ordering. The `run` runner captures the stub git's stdout and doesn't forward it, so stdout order says nothing about when git ran. The closest test is a stub git that fails at once (as in the line-476 case), showing that the mask line is still on stdout and is its first line. What only a real run can show is that the runner honours `::add-mask::` for this value and that later git trace output in the job is redacted. The plan should list that as checked only on the next release.
- F-7 · Nit · §1 scope · The mask is registered only in the push.ts step. In each of the tap and marketplace jobs, `token.ts` runs earlier in the same job with the same secret. If anything there handles a derived form of the token, it stays unmasked. Say whether token.ts was checked, so the engineer doesn't wonder.
- F-8 · Major · §4, scripts/install.sh · `version_of` is also applied to the freshly downloaded `$tmp` (line 102, `new="$(version_of "$tmp")"`), so the stricter rule changes the "the downloaded binary does not run" refusal too. The concept only talks about the staged file and doesn't say whether that is intended.
- F-9 · Major · §4, scripts/install.sh under `set -eu` · The obvious way to capture the exit status, `answer="$("$1" --version 2>/dev/null)"`, aborts the whole script under `set -e` when the staged binary exits 1. That is the exact case meant to be replaced, so a person with a broken staged binary gets a failed install instead of a replacement (the EXIT trap removes `$tmp` and the staged file stays). The plan must give the shape, for example `if answer="$(...)"; then ...; fi`, and the install-script test for "a higher version printed with exit 1" must assert both exit code 0 and the replaced file.
- F-10 · Major · §4, "its whole answer, trimmed" · The TS readers use `.trim()`, which strips leading and trailing whitespace and `\r`. Shell `$(...)` only drops trailing newlines, and the template's awk regex is anchored. For the shell readers to match, the plan must state the trimming, for example strip leading and trailing blanks and CR, then require a single line. Otherwise an answer like `1.2.3 ` or `1.2.3\r` is still kept by three writers and replaced by two, and the two named test cases won't catch it.
- F-11 · Major · §4, template's two-line case · The concept implies `installed()` already rejects a second line. That holds only because `older` passes the multi-line answer as `awk -v a=...` and the anchored regex fails. Whether a literal newline in a `-v` value is accepted the same way by macOS's BWK awk, gawk, mawk and busybox awk is unchecked. The tests run on one platform, so the plan should either make the rule explicit in `installed()` (a single line, exit 0) or accept that only the developer's awk is proven.
- F-12 · Major · §4, "each of the five writers has a test" · The concept names neither the test file per writer nor how a test sees "replaced". From the repository: install.sh → tests/integration/install-script.test.ts; template → tests/integration/plugin-script.test.ts (needs `hook <agent> session-start`, a stand-in release under `WIZARDINGCODE_MEM_RELEASE_BASE` whose checksum matches, and a fetched binary that answers the exec'd `hook ...`); npm shim → tests/integration/npm-shim.test.ts; opencode → tests/integration/plugins-packaging.test.ts or install-opencode.test.ts (undecided); stageBinary → tests/integration/install.test.ts "stageBinary" (assert `kept: null` and the target's bytes equal the source's). The concept's reading list leaves out four of these and includes release-commands.test.ts, which none of change 4 touches. In every case "replaced" should be asserted as the staged file's bytes now equal the release's or source's binary.
- F-13 · Nit · §4, one rule · The readers also differ in timeout: stageBinary and the npm shim allow 10 s, while the opencode `installedVersion`, `version_of` and `installed()` have none, so a hanging staged binary blocks those three indefinitely. Either bring timeouts into the rule or say they are out of scope, so "one rule" isn't overstated.
- F-14 · Major · §4, copies held equal · tests/unit/version-order.test.ts holds install.sh's `older()` block byte for byte against the template's. Nothing holds `version_of` and `installed()` together, and the concept doesn't decide whether they become one shared block under the same byte-for-byte test or stay two functions that can drift again. CLAUDE.md's rule ("a copy of `older()` is never edited alone") suggests the former, but it is a design choice the plan must make.
- F-15 · Major · rollout and rollback (all four) · The changes go live on different paths, and the plan should say so. distribute.yml runs push.ts from `main` (checkout without ref), so changes 1-2 apply on merge to any distribute run, including a re-run for 0.8.0. release.yml runs from the tag's commit, so the timeout in change 3 applies only to tags cut after merge. install.sh is fetched by users from `main`, so its new rule is live for everyone on merge. The template and the opencode/npm copies reach users only with the next release and the agents' plugin update, so for a time the fleet keeps both rules. Rollback is a revert on `main` for 1, 2 and install.sh, a new release for the plugins' scripts, and nothing for already-run tags. No stored format or data moves: every released binary prints `pkg.version` and exits 0 (src/cli/main.ts:58-60), so the stricter rule replaces no genuine staged binary today.
- F-16 · Nit · §4 hazard for later · Under the shared rule, any future binary that writes anything besides the version to stdout on `--version` (a notice, a warning) counts as having no version, and every writer replaces it with possibly an older one. Worth one line in the plan or in a comment next to `--version` in src/cli/main.ts.
- F-17 · Nit · §3 · The test is clear enough: extend the case "release.yml: ... distribute starts distribute.yml" at tests/unit/deploy-files.test.ts:166 to expect `job["timeout-minutes"] === 5` for `distribute`. Whether five minutes is enough for `gh workflow run` on a slow API day can only be seen in real runs.
- F-18 · Nit · closing the loop · The concept doesn't say that the four deferred rows in docs/real-use/findings.md (around lines 70-71) change status. It also doesn't say whether docs/runbooks/release.md or tests/unit/release-docs.test.ts mention the removed `PUSH_REMOTE`/`PUSH_ORIGIN` or need a line on the mask; I found neither name under docs/ outside the findings and the parent design.
- F-19 · Nit · §2, test environment · `GIT_CONFIG_COUNT`/`KEY`/`VALUE` need git 2.31 or later. tests/preload.ts deletes `GIT_CONFIG_COUNT` but not stray `GIT_CONFIG_KEY_n`/`VALUE_n`. That is harmless once the count is gone, but say so if the command tests start depending on these variables.
