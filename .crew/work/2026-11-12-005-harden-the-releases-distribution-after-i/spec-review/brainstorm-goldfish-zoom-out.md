## Findings
- F-1 · Major · §2, "For that to hold when a token is set, `gitEnv` no longer overwrites `GIT_CONFIG_COUNT`" · The command tests never set `MARKETPLACE_TOKEN` (release-commands.test.ts:393-407 and 479-488), and `gitEnv(null, …)` adds no `GIT_CONFIG_*` (push.ts:38), so `url.<path>.insteadOf` passed through the environment already reaches git with `gitEnv` unchanged. The append is for a token-bearing command test that nobody has asked for, and for a runner that "sets git configuration that way", which nothing in the repository shows (`actions/checkout` writes its header into the clone's config, not into `GIT_CONFIG_COUNT`). Drop the `gitEnv` change; the test needs only the environment variables.
- F-2 · Major · §2, `gitEnv` appending after the inherited `GIT_CONFIG_COUNT` · This reopens the thing §2 sets out to close. Today `GIT_CONFIG_COUNT: "1"` discards any inherited `GIT_CONFIG_KEY_n`. After the change, an inherited `url.https://github.com/WizardingCode-io/wizardingcode-plugins.git.insteadOf`, rewritten to another github.com repository, still matches the `http.https://github.com/.extraheader` scope, so the token's writer takes its destination from the environment, on a runner too and with no `GITHUB_ACTIONS` guard. A reader would add this and think it was hardening. If the overwrite stays (F-1), the door stays shut.
- F-3 · Nit · §2, the rationale "the writer that holds the token takes its destination from the environment" · Once `PUSH_REMOTE`/`PUSH_ORIGIN` are removed, git's own environment routes (`GIT_CONFIG_PARAMETERS`, `GIT_CONFIG_GLOBAL`, `HOME`'s `.gitconfig`) still let whoever controls the step's environment redirect the clone. The gain is that no named test knob is left in production code, not a narrower threat. Say that, so nobody later counts it as a security boundary.
- F-4 · Nit · §2, the test approach · Two simpler seams already exist. `stub("git", …)` and `log("git")` (release-commands.test.ts:476-492) already check where the command sends git, and `commitAndPush({ remote, origin })` is already exercised against local repositories in release-push.test.ts. A command test that checks only the wiring (the github.com URLs reach git) with the stub, plus the existing direct `commitAndPush` tests, would need no `insteadOf` plumbing at all. Also, the runner test at release-commands.test.ts:476-492 becomes moot once the overrides are gone; the concept should say whether it is deleted or rewritten.
- F-5 · Nit · §1, "`GIT_TRACE_CURL`, `GIT_CURL_VERBOSE` … would put a write credential … in the log" · This contradicts the sentence before it ("git redacts the header in its traces"). git redacts `Authorization` in curl traces unless `GIT_TRACE_REDACT=0`. The real exposures are an environment dump or a redaction turned off. State the threat accurately, so the test pins the mask line's presence and order and does not try to provoke a trace.
- F-6 · Nit · §1, `tokenMask` in push.ts · A structural alternative removes the encoded form from the environment altogether: a `credential.helper` that answers `password=$MARKETPLACE_TOKEN`. Actions already masks the raw token, and git builds the header in-process. The mask line follows `actions/checkout`'s pattern and is the smaller change, so this is only worth a sentence that explains why it was not chosen.
- F-7 · Nit · §4, the scope of the problem · Nothing shows that a real `wizardingcode-mem` binary ever prints a second line to `--version` or exits non-zero after printing one (src/cli/main.ts:58 prints the version). The divergence is real but cosmetic: aligning the two shell readers is cheap. Ten bespoke tests (five writers times two cases) are more than the finding needs. Consider extending the `tests/unit/version-order.test.ts` pattern (one table of answers held equal across the readers) instead.
- F-8 · Nit · §4, "Five writers" · `resolveBinary` (src/cli/commands/install.ts:223, named in findings.md:68 as "also stages") goes through `stageBinary`, so five is correct. Say so in one line, because the findings row that inspired the item reads as if there were a sixth.
- F-9 · Nit · §3 · This is proportionate and already covered: the job-shape assertion at tests/unit/deploy-files.test.ts:233 checks `timeout-minutes` for `distribute.yml`, so the new check should reuse that assertion rather than add a separate test. Nothing to cut.
