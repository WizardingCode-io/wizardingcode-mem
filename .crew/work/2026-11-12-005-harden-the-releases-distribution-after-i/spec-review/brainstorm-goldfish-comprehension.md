## Paraphrase

**What this proposes.** This is a follow-up to PR 38 (ADR 0029). It takes four small deferred advisories and changes nothing that gets distributed. (1) On a GitHub runner, `push.ts` first prints `::add-mask::` with the base64 Basic-auth value it gives git, so a curl or git trace cannot leak the token into a public log. Off a runner it prints nothing. (2) The command stops reading `PUSH_REMOTE`/`PUSH_ORIGIN`. Its test sends git to local repositories with `GIT_CONFIG_*` `insteadOf` entries instead, and `gitEnv` appends its header after any existing `GIT_CONFIG_COUNT` rather than overwriting it. (3) The `distribute` job in `release.yml` gets `timeout-minutes: 5`. (4) The two shell readers of a staged binary's version adopt the rule the three JS readers already use: a version counts only if the binary exits 0 and its whole trimmed answer is one version. Each of the five writers gets tests for "exit 1" and "a second line".

**How the existing system works, per this document.** A tag runs `release.yml`, whose `distribute` job dispatches `distribute.yml`. That workflow's jobs push to the tap and the marketplace through `push.ts`, with the token passed as a git HTTP header in the child's environment. Five writers place `<data dir>/bin/wizardingcode-mem`. Before replacing it, each asks the staged binary for `--version` and replaces it only with an equal or newer version. Today two shell writers read that answer more loosely than the three JS writers.

## Findings
- F-1 · Major · §4, "the two shell readers take the same rule" · `version_of` in `scripts/install.sh` runs twice: on the staged binary (line 109) and on the freshly downloaded `$tmp` (line 102), where an empty answer prints "the downloaded binary does not run" and exits 1. The concept talks only about the staged file. A reader cannot tell whether the stricter rule also gates the download. If it does, a downloaded binary that prints two lines would be refused with a sentence that says it "does not run", which tells the person the wrong thing.
- F-2 · Major · §4, "an answer that is exactly one version" · "One version" is never defined. `install.sh` uses a regex (`^N.N.N(-prerelease)?$`, no build metadata, no leading `v`). The JS readers use `stagedVersion`/`installedVersion`. The concept does not say which one is the reference, or whether they already agree on inputs like `v0.8.0`, `0.8.0+build` or trailing whitespace. A reader could build a shell rule that still differs from the JS one, which is the divergence this item is meant to close.
- F-3 · Major · §4, "each treats the staged file as having no version and replaces it" · For the person whose machine holds the staged binary, this rule can replace a higher version (the test case is "a higher version printed with exit 1") with a lower one. That is a downgrade, and it seems to contradict "the staged binary only moves forward". The concept never says why that is right: a binary that cannot answer is broken, so the forward-only rule does not protect it. A reader who holds the ADR 0029 invariant would expect the opposite outcome.
- F-4 · Major · §4, what the person sees · Nothing says what the person is told when an unreadable staged binary is replaced. `install.sh` will print only "installed <new> at …", the same as a fresh install. The plugins' script runs on session-start with all output discarded (`fetch > /dev/null 2>&1`). The npm shim and `stageBinary` are not described. Someone wondering why their binary changed version gets no clue. The concept should say whether that silence is intended or whether one sentence (for example "the binary in place gave no version; replaced") is wanted in `install.sh`, which already explains the opposite case at line 115.
- F-5 · Major · §3, what the author sees when the 5 minutes run out · The concept sets the limit but not what follows. A timed-out `distribute` job shows GitHub's "exceeded the maximum execution time" error and none of the runbook's summary lines (`distribute: refused: …`, `<target>: failed: …`, runbook line 52). Also, `gh workflow run` may already have dispatched `distribute.yml` before it stalled. The author needs to know whether a distribution may be running and what to do next. The runbook's recovery (start `distribute.yml` from `main` with the same tag, runbook line 60) would apply, but neither the concept nor the runbook's failure list names this case.
- F-6 · Major · §2, title "The command reads no test override" against the mechanism · The security point was that "the writer that holds the token takes its destination from the environment". After the change it still does, through git's `GIT_CONFIG_*` `url.*.insteadOf`. Also, `gitEnv` currently overwrites `GIT_CONFIG_COUNT` with 1 (push.ts:41), which throws away any configuration from the environment. Appending keeps it, so on a runner, environment configuration now reaches the token's writer where today it is dropped. The concept calls appending "the correct behaviour" but gives no reason, and does not say why a redirect through git's variables is acceptable when `PUSH_REMOTE` was not (for example: `http.https://github.com/.extraheader` matches the rewritten URL, so the header never reaches a redirected host). Without that argument, a reviewer reads this as the same override under another name.
- F-7 · Nit · §2, "index = the existing count" · The concept does not say what `gitEnv` does when `GIT_CONFIG_COUNT` is present but not a number, or when the `KEY_n`/`VALUE_n` variables do not match the count. The person who later debugs a failed push cannot tell from the concept whether such an environment is refused with a clear sentence or silently misnumbered.
- F-8 · Nit · §1, "its command prints that line first" · The concept does not name the stream (standard output, where `log` writes, or standard error). It also does not say what the author will see in the run's log. Once the runner processes the mask, the line itself is shown with the value replaced by `***`, so a reader of the log sees a near-empty `::add-mask::` line at the top of every push step. One sentence saying this is expected would save a question.
- F-9 · Nit · §1, "when the process runs on a runner (`GITHUB_ACTIONS` is `true`)" · `GITHUB_ACTIONS=true` is also set by local Actions emulators (such as `act`). There the `::add-mask::` line, and so the encoded credential, would be printed on a person's terminal, which is the leak the concept says it avoids off a runner. Either note that this case is accepted, or name the condition more precisely.
- F-10 · Nit · §2, the test's view · With `insteadOf`, the command's own log lines and summary will still name `https://github.com/...` while it writes to local paths. Someone reading a failing test's output may think it reached the network. Worth stating in the test, or in the concept, that the URLs shown are the pre-rewrite ones.
- F-11 · Nit · "Where this comes from" · Several project terms are left undefined for a newcomer: "judgement gates", "advisories", "piece 3 of the parent item", "the backlog's debt point", and "writers" (§4: "writer" means a placer of the staged binary there, but the person who holds the token in §2). Also "plan checking the ruleset on v* tags". Each needs a short gloss or a link (ADR 0029, the findings.md rows).
- F-12 · Nit · §4, the plugins' script · The concept says the plugins' scripts are "regenerated" but does not say from what or by which command (`scripts/templates/wizardingcode-mem.sh` through `bun run plugins`). It also does not say whether `plugins/opencode/binary.js`, already correct, comes out unchanged. A reader editing only the generated copies would break the rule that a copy is never edited alone.
