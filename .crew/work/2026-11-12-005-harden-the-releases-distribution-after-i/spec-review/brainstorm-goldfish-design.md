# design findings for 2026-11-12-005-harden-the-releases-distribution-after-i
reviewer: goldfish-design
read: .crew/work/2026-11-12-005-harden-the-releases-distribution-after-i/probes/concept.md (whole); scripts/release/push.ts, scripts/release/lib.ts (run, summary, command), scripts/release/token.ts, scripts/install.sh, scripts/templates/wizardingcode-mem.sh, src/install/binary.ts (stagedVersion), npm/bin/wizardingcode-mem.js, plugins/opencode/binary.js (installedVersion), src/cli/main.ts (--version), tests/unit/cli.test.ts (--version), .github/workflows/distribute.yml (tap, marketplace, concurrency), .github/workflows/release.yml (distribute job)

## Findings
- F-1 · Major · 2. The command reads no test override · The change does not take the destination out of the environment. It moves the override from the command, where it is ignored on a runner (`onRunner ? undefined : process.env.PUSH_REMOTE`, push.ts:219), to git, which honours it everywhere. Today `gitEnv` sets `GIT_CONFIG_COUNT: "1"`, so the authenticated clone and push drop any `GIT_CONFIG_*` the step's environment carries. After the append, a `url.<x>.insteadOf` for `https://github.com/WizardingCode-io/wizardingcode-plugins.git` in the runner's environment (written by any earlier step through GITHUB_ENV) reroutes the token-bearing writer. Because `http.https://github.com/.extraheader` is matched after the rewrite, the header still goes to any github.com repository the token can write, for example the tap and the marketplace swapped. On a runner this is strictly weaker than the current code. The text says the reverse ("the correct behaviour on a runner"), so a reader would ship it as hardening. The concept needs to say why that is acceptable, or give the test seam a shape the runner path ignores.
- F-2 · Major · 2. gitEnv appends its header · Appending also keeps every `http.*extraheader` already in the environment. If the runner's environment (or, as already today, a global or system gitconfig) holds another `http.https://github.com/.extraheader` with an Authorization header, git sends both, and GitHub rejects a request with two Authorization headers or authenticates with the wrong one. The concept says nothing about headers already present, and nothing about resetting the multi-valued key with an empty value before its own.
- F-3 · Major · 2. index = the existing count · The concept does not say what happens when the inherited `GIT_CONFIG_COUNT` is not a clean non-negative integer ("", "abc", " 2", "-1") or names keys that are missing. A naive `Number(...)` gives `NaN` or `0` and writes `GIT_CONFIG_KEY_NaN`, or overwrites `GIT_CONFIG_KEY_0` and silently drops the inherited setting, so the header lands where git never reads it. The push then fails with a 403 that push.ts reports as "MARKETPLACE_TOKEN may lack contents write", sending the operator to the wrong cause. Specify a refusal with its own sentence, and test it.
- F-4 · Major · 2. the command's test through url.insteadOf · In the test the header can never be observed. It is scoped to `https://github.com/`, the URLs are rewritten to local paths, and git matches `http.<url>.*` after the rewrite. A test that passes with a token set proves only that git accepted the config count and its indices. It does not prove the header is built, scoped or sent correctly: a mis-scoped key, wrong base64 or a header dropped by the index arithmetic would all pass. The concept should say which unit test of `gitEnv` holds the header's exact key, value and index next to inherited entries.
- F-5 · Major · 1. The token's encoded form is masked · The mask covers the run's log. The concept does not show that it covers the other place a failure sentence goes: `command()` appends git's standard error, unredacted, to `GITHUB_STEP_SUMMARY` through `summary()` (lib.ts:49-53, 61-76). Under `GIT_TRACE_CURL`/`GIT_CURL_VERBOSE` with `GIT_TRACE_REDACT=0`, that standard error carries `Authorization: Basic <b64>`. Whether Actions applies `add-mask` values to the step summary file has to be proved or cited, not assumed. Otherwise the leak moves from the log to the public summary.
- F-6 · Nit · 1. printed first, before any git call · The concept does not say how the line is written. If `process.stdout.write` to a pipe in Bun is buffered rather than synchronous, the mask line can reach the runner after output it should cover. Today every git output is captured by `run()` and printed only afterwards, so the risk is small now. It becomes real the day any git output is inherited or streamed. State that the line is written synchronously (or flushed) before `commitAndPush`.
- F-7 · Nit · 1. when GITHUB_ACTIONS is true · `GITHUB_ACTIONS=true` is also set by local emulators such as `act` and on self-hosted runners whose console a person reads, so "off a runner it prints nothing" does not fully hold. The same flag decides the mask and, until change 2 lands, the overrides. One sentence on that boundary would do.
- F-8 · Nit · 1. masks the same form · The forms that reach a log are the raw token (masked by Actions as a secret), the base64 of `x-access-token:<token>`, and the full header line, which contains the masked base64. Covering those three is enough only if no other encoding is ever built. Say so, so that a later change (for example a `Bearer` header, or a URL with userinfo, which would be percent-encoded) knows it has to add its own mask.
- F-9 · Major · 3. timeout-minutes: 5 · `gh workflow run` only dispatches. If the five minutes run out after GitHub accepted the dispatch (a slow response, or gh retrying), the release run turns red while distribute.yml is already running. The obvious recovery, "re-run failed jobs", dispatches a second run. distribute.yml's `concurrency: distribute` with `cancel-in-progress: false` queues it, and a third dispatch would cancel the queued one. The concept should say whether a second distribute for the same tag is harmless (npm already published, tap `already-at`), and the runbook should say what to do when the dispatch job times out.
- F-10 · Nit · 3. A stalled call would hold the release's run · push.ts's own git calls (clone, `pull --rebase`, push) have no time limit (`run()` passes no timeout). A stall there is cut only by the 15-minute job limit, possibly mid-push, with an outcome nobody records. That is outside this item, but it is the same failure mode the item names, and the concept should list it among what stays open.
- F-11 · Major · 4. One rule for the version a staged binary answers · The rule leaves out the time limit. `stagedVersion` and the npm shim bound `--version` at 10 s, and a hang counts as "no version", so they replace. The OpenCode `installedVersion` (plugins/opencode/binary.js:31) and both shell readers have no bound and wait forever. The plugin script does this on every session start, so the host's hook timeout kills the hook and the binary is never replaced. A staged binary that hangs is therefore still kept by three writers and replaced by two: exactly the disagreement this change says it removes. Either the rule includes the bound, or the concept says why hangs are out of scope.
- F-12 · Nit · 4. its whole answer, trimmed · "Trimmed" differs between the readers. JavaScript `.trim()` strips leading and trailing whitespace, including `\r`, while shell `$(...)` strips only trailing newlines. " 1.2.3" or "1.2.3\r" is a version to three writers and not to two. Name one normalisation, and give the shell readers' tests a case for it.
- F-13 · Nit · 4. scripts/install.sh version_of · The current reader pipes into `head -n 1 || true`, which loses the binary's exit status. The new reader has to capture the status without a pipe, under `set -eu`, so that `staged="$(version_of …)"` does not abort the installer when the staged file exits 1. The planned test (a higher version, exit 1, replaced) would catch it. The concept should still say that `version_of` also judges the downloaded `$new`, so a downloaded binary that exits non-zero is now "does not run".
- F-14 · Nit · 4. what it changes for binaries already on machines · Every released binary prints exactly `<version>\n` and returns 0 (src/cli/main.ts:58-61, held by tests/unit/cli.test.ts). The tightened rule therefore changes no real staged binary's fate, and the change is about consistency, not a fix. Plugins already installed keep their old generated script until they update, so the old rule stays on machines for a while. The concept should say both, and that `--version` printing one line with exit 0 is now a contract on every future binary: break it and every writer replaces the binary with its own version, possibly an older one.

## Not answerable
- Whether GitHub Actions applies `::add-mask::` values to the step summary (`GITHUB_STEP_SUMMARY`) as it does to the log · no documentation could be read from here (F-5).
- Whether Bun's `process.stdout.write` to a pipe is synchronous on the Linux runner · it depends on the runtime and I ran nothing (F-6).
- tests/integration/release-push.test.ts, release-commands.test.ts and plugin-script.test.ts were not read line by line · the findings above rest on the code they test, not on what the tests currently assert.
