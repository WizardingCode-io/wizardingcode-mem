## Findings
- F-1 · Major · spec AC-18 / plan Phase 4 "AC-18" · Nothing in the repository tests docs/real-use/findings.md today: the existing release-docs.test.ts cases hold documents to code (commands, files, summary lines), not to a status log. AC-18 adds a test that says which findings rows must still be `deferred` (the GIT_CONFIG_GLOBAL/time-limit/MARKETPLACE_TOKEN row, the decideHold/deploy-files row) and which must cite piece 2. A competent reader would build a test that breaks when the next item fixes one of those advisories and updates its row, so the follow-up items would also have to edit this item's test. Simpler: keep the findings rows as prose and check them in review, or check only that the rows cite 2026-11-12-005 and are no longer deferred, not which other rows stay open.
- F-2 · Nit · spec Design 1, last bullet; AC-10(b)(c); AC-16; plan Phase 2 step 4 · Even the spec calls the mask line defence in depth. No other step in the job holds the encoded value, and all of git's output is captured and redacted, so the mask covers no path that the redaction misses. It still costs a fixed ordering ("first statement, before need(VERSION)"), the GITHUB_ACTIONS gating, AC-10(c) (the VERSION-unset case, where no token can leak) and three AC-16 cases. Keeping `::add-mask::` as the platform's standard tool is defensible, but the ordering requirement and AC-10(c) protect nothing and could go.
- F-3 · Nit · spec Design 1 (the `commitAndPush` and `redact` bullets) · The architecture section holds code-level detail: the five throw sites listed one by one, the use of `process.stdout.write`, and the literal-string-versus-regex choice. The plan already carries this detail. In the spec, the one rule is enough: every git output is redacted where the runner is wrapped, and that rule is the guarantee.
- F-4 · Nit · spec J-4 · The user journey holds the whole runbook paragraph: what a second run answers per target (`already published`, `already at`, `latest: moved to`) and the "A bad release" exception. Design 3 then says to copy J-4 "in the words of J-4". A journey should state the outcome (the job is cut, and the person can tell whether distribution started and how to restart it safely); the per-target answers belong in the runbook text and AC-13.
- F-5 · Nit · spec AC-15 / plan Phase 4 "AC-15" · The test looks for exact phrases ("exact match", "no destination from its environment") in ADR 0029 and in CLAUDE.md's Releasing line. That holds wording, not facts that code can check, and any later rewording of either document will break it, even when the meaning is unchanged.
- F-6 · Nit · spec AC-11 / plan Verification · After the reads are deleted, the AC-11 case keeps setting `PUSH_REMOTE` and `PUSH_ORIGIN`, on and off a runner, to prove that a name nothing reads is ignored. The verification grep already shows that scripts/ never reads the names. The `clone`/`ls-remote` target assertion alone covers the requirement.
