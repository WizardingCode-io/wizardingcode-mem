# codebase findings for 2026-11-12-005-harden-the-releases-distribution-after-i

read: .crew/work/2026-11-12-005-harden-the-releases-distribution-after-i/probes/concept.md (whole); scripts/release/push.ts; scripts/release/lib.ts (run, summary, output, command); scripts/install.sh; scripts/templates/wizardingcode-mem.sh; scripts/plugins.ts (lines 45-139); src/install/binary.ts; src/util/version.ts; npm/bin/wizardingcode-mem.js; plugins/opencode/binary.js; .github/workflows/release.yml; .github/workflows/distribute.yml; tests/integration/release-commands.test.ts (push.ts block, lines 340-509); tests/integration/release-push.test.ts (gitEnv and env assertions); tests/unit/deploy-files.test.ts, tests/integration/plugin-script.test.ts, install-script.test.ts and npm-shim.test.ts (searched for their staged-binary fixtures and timeout assertions)

## Findings
- F-1 · Major · §2 "The command reads no test override" · The change moves the destination override somewhere else instead of removing it. Today `PUSH_REMOTE` and `PUSH_ORIGIN` are ignored on a runner (push.ts:215-222, held by the test at release-commands.test.ts:476-492), and with a token set `gitEnv` overwrites `GIT_CONFIG_COUNT` with 1 (push.ts:41), which throws away any `url.*.insteadOf` the environment carries for the clone and the push. If `gitEnv` appends instead, any `GIT_CONFIG_*` in the step's environment would reach the git calls that carry the token, on a runner too. That includes a value an earlier step wrote through `GITHUB_ENV` (the tap job runs checkout, setup-bun, token.ts and `gh release download` before push.ts, distribute.yml:121-141). An insteadOf pointing at another github.com repository would still get the `http.https://github.com/.extraheader` token. The concept calls this "the correct behaviour on a runner" and gives no runner-side guard, and it does not say what replaces the test at release-commands.test.ts:476 once its two variables are gone. A builder would ship a token writer whose destination the environment can again redirect, which is the exact objection the security lead raised.
- F-2 · Major · §2, gitEnv appending · The concept does not say what `gitEnv` does when the inherited `GIT_CONFIG_COUNT` is not a non-negative integer, or when the `GIT_CONFIG_KEY_<n>` and `GIT_CONFIG_VALUE_<n>` it names are missing. Git rejects a bad count and the clone fails with "git clone failed in <remote>: …" (push.ts:104). It also does not say how the existing assertions change: release-push.test.ts:250 and :253 read `GIT_CONFIG_VALUE_0` by fixed index, and :259-266 expects `GIT_CONFIG_COUNT: "1"` exactly. Those hold only while the test process's environment carries no count, so they need a case with a count already set (header at index n, count n+1, earlier keys kept).
- F-3 · Major · §2, which URLs get insteadOf · The concept says the test rewrites "the two https URLs the command uses". In code these are `https://github.com/${GITHUB_REPOSITORY}.git` for `ls-remote` and `REMOTES[target]` for clone and push (push.ts:157-160, :222). `ls-remote` runs without `authed` and inherits `process.env` only because `run` passes no `env` when none is given (lib.ts:29). The concept relies on that inheritance without stating it, so a later refactor that gives `ls-remote` an explicit environment would quietly send the test's origin to github.com.
- F-4 · Nit · §1 "No path prints it today … but GIT_TRACE_CURL, GIT_CURL_VERBOSE or a debug re-run would …" · This contradicts itself: the same sentence says git already redacts the header in its traces. Separately, nothing in the repository shows that an Actions debug re-run sets `GIT_TRACE_CURL` or prints a child's environment. The case for masking holds as defence in depth, but the stated leak paths are not shown.
- F-5 · Nit · §1 tokenMask · The concept does not say whether the mask covers the base64 of `x-access-token:<token>` alone or the whole `Authorization: Basic …` value (push.ts:43). It also does not say whether `tokenMask` and `gitEnv` share one encoding helper so the two cannot drift, or which test (release-push.test.ts or release-commands.test.ts) asserts that the mask line comes first on stdout, before `options.log`'s dry-run diff (push.ts:116-119) and before `summary` (lib.ts:50).
- F-6 · Major · §4 "Three already agree" · They agree on the exit status and the version's shape, but not on a time limit. `stagedVersion` waits at most 10 s (binary.ts:6, :15) and the npm shim 10 s (wizardingcode-mem.js:34). The OpenCode `installedVersion` has no timeout (binary.js:31, generated from plugins.ts:124), and both shell readers have none (install.sh:96, template :68). A staged binary that hangs on `--version` stalls OpenCode's plugin load and the session-start hook, and none of the five writers reports it. If the "one rule" leaves the time limit out, that difference stays in.
- F-7 · Major · §4 "its whole answer, trimmed, is one version" · The JavaScript readers use `.trim()`, which strips leading and trailing whitespace including `\r` (binary.ts:17, binary.js:32, wizardingcode-mem.js:35). Shell command substitution strips only trailing newlines, and awk's `^…$` (template :26, install.sh:50) then rejects `9.9.9 ` or `9.9.9\r`. Unless the concept defines "trimmed" for the shell readers, a third disagreement survives, and the two proposed test cases would not catch it.
- F-8 · Nit · §4 "installed() … ignores the exit status" · This is accurate, but the plugins' script already treats a second line as no version: `$(installed)` hands both lines to `older()`, whose awk anchors fail on the embedded newline (template :26, :75). Only install.sh's `version_of` reads the first line (install.sh:96). The second-line test for the plugins' script will already pass, so it is not the failing test that the TDD rule (write the test and see it fail first) requires.
- F-9 · Major · §4 "each of the five writers has a test" · The OpenCode package's `ensureBinary` has no test today. Only `older` is imported, in tests/unit/version-order.test.ts:23. The concept's reading list also leaves out the tests that do exist for the other writers: stageBinary's test is in tests/integration/install.test.ts, and the order fixture is in tests/unit/version-order.test.ts. A builder would have to invent a harness for binary.js (fetch, `Bun.spawnSync`, `WIZARDINGCODE_MEM_RELEASE_BASE`) without being told one is needed.
- F-10 · Major · §4 the two shell readers · `version_of` (install.sh) and `installed()` (the template) are separate copies, and the concept says nothing to keep them equal. CLAUDE.md requires that copies of `older()` never be edited alone and that tests/fixtures/version-order.ts hold them equal, but no such fixture or test covers the readers. Without a shared fixture across the five writers, the rule can drift apart again the next time someone edits one copy.
- F-11 · Major · §4 install.sh · `version_of` also decides whether the downloaded binary runs at all (install.sh:102-106, "the downloaded binary does not run"). The concept does not say whether the exit-0 rule applies there too. If `version_of` gets the exit-0 rule, a downloaded binary that prints its version and exits non-zero makes the install stop instead of being staged. That is a behaviour change outside "change nothing of what is distributed", and the concept does not mention it.
- F-12 · Major · §4, debugging · When a writer replaces a staged binary because it "has no version", nobody can see it. The plugins' script fetches silently (template :76, fail open). install.sh prints only "installed $new" (:119). The npm shim prints only "downloading" (:77). stageBinary returns `kept: null`. Someone chasing a staged binary that keeps getting replaced has no line saying which writer replaced it or what the old file answered, and the concept adds none, not even to install.sh's or the shim's existing messages.
- F-13 · Nit · §4 "Five writers of `<data dir>/bin/wizardingcode-mem`" · install.sh writes to `${WIZARDINGCODE_MEM_BIN_DIR:-$data/bin}` (install.sh:71), and stageBinary writes `wizardingcode-mem.exe` on Windows (binary.ts:42), so the path given is not the same for all five.
- F-14 · Nit · §3 · Confirmed against the code: the `distribute` job has one step and no `timeout-minutes` (release.yml:152-161), and every job of distribute.yml has 15 (lines 45, 76, 116, 148, 176). The Workflow type in deploy-files.test.ts already has `"timeout-minutes"?: number` (line 51), so this needs only one assertion beside lines 197-205. The concept does not name that test's line or assertion, and it does not mention that `build` (which runs `bun run check`) also has no limit and is left at six hours by choice.
- F-15 · Nit · §"What is asked of each lens" · The reading list leaves out files the four changes touch or depend on: scripts/plugins.ts (generates binary.js and the scripts; `OLDER_JS`), scripts/release/lib.ts (`run`'s environment inheritance, `command`), .github/workflows/distribute.yml (the steps before push.ts), src/util/version.ts (`isVersion`), tests/integration/install.test.ts and tests/unit/version-order.test.ts.
