# Plan: the sync client (part 6)

Revision 15 (both spec-review rounds' findings and the thirteenth and fourteenth validation rounds' returns applied; the history is in `conclave.md`). Every task names its criterion, marks each file `Create` or `Modify`, and ends with a red run then a green run; every phase leaves `bun run check` green, and a test case sits in or after the task that provides what it needs. Tests run with the pinned bun (`./node_modules/.bin/bun test <files>`); the hooks' switches `WIZARDINGCODE_MEM_DISTILL=off`, `WIZARDINGCODE_MEM_UI_AUTO_OPEN=off`, `WIZARDINGCODE_MEM_MIGRATE=off` and this part's `WIZARDINGCODE_MEM_SYNC=off` keep tests from starting background work. The in-process team server of `tests/helpers/team.ts` (`startTestServer(overrides, extra)`, `adminOf`, `invite`) is the server every client test talks to; task 2 makes `extra` take `clock` and `timers` and `TestServer` return both, so one `Clock` and one `fakeTimers` drive both sides of a test (one `fakeTimers` per clock: a second call on the same clock would silence the first's timers, which the helper's comment states). The write-lock bound of AC-75 is measured on wall time (`performance.now()`), never with the fake clock, which drives only the sync's own timers.

Two directories: `dataDir` (the env file, `knowledge/`, `servers.json`) and `storeDir` (the database); every function below names the one it takes, and `SyncContext` carries both. `SyncContext` (`src/sync/context.ts`, task 3): `{ db: Db; dataDir: string; storeDir: string; env: Record<string, string | undefined>; fetch: typeof fetch; clock: Clock; timers: Timers; pid: number; version: string; log: (line: string) => void }`; every function under `src/sync/` takes it as `ctx`. `Clock` (`{ now(): number }`) and `Timers` (`setTimeout`, `clearTimeout`, `setInterval`, `clearInterval`, with the shapes `fakeTimers` returns today) live in `src/util/clock.ts` (task 2). Phase order and midway checks: A to I in order; at the end of D an own entry reaches the in-process server within 5 s (journey 2), at the end of E a teammate's entry is on disk and in search within 5 s (journey 3).

Sharing v2, `src/sharing/migrations/0002_sharing_servers.sql` (add-only, defaults; the migration is named `sharing_servers`, which `module_migrations` records and `module-migrations.test.ts` pins):

```sql
CREATE TABLE sharing_servers (
  server_id TEXT PRIMARY KEY, url TEXT NOT NULL, name TEXT NOT NULL,
  device_id TEXT NOT NULL, device_alias TEXT NOT NULL, member_id TEXT NOT NULL,

CREATE UNIQUE INDEX sharing_received_memories_uid ON sharing_received_memories(server_id, remote_uid);

```

The `cursors` JSON is `{ "main": <cursor>, "mainAliases": [<alias>, …], "extra": { "<alias>": <cursor> } }`; the main set is sticky (an alias stays while the pull names it; one that stops being named, by an unbind, a disabled project, a lost alias or a `system` removal, leaves at the next pull, and one named anew follows the new-alias path; a free slot is filled by the first extra alias by its bytes). The `meta` key `sharing.resume_authorised:<serverId>` holds the uids a `resume` showed, consumed by the next withdrawal sweep. `stopped` holds null, `contract`, `unauthorized`, `rejoin` or `disabled`. The ledger's `direction` gains the value `applied` beside `sent` and `received`: the row of a teammate's revision applied to an own item, selected by `ledgerRecords` for its own destination only, never read by `decide`, and cleared with the `sent` row; the server's revision is written to the ledger's `version` column; a received memory's `item_uid` is the feed's `remote:<device alias>:<uid>`. A purged key is a `sharing_refusals` row with reason `purged` and hash `*`; a locally refused oversize item has reason `too-large`. Sharing v2's `run`, which `upgrade` in `src/store/db.ts` calls after its `sql`, resolves a project with more than one `sharing_levels` row above Nothing (the `team` row kept, else the row with the lowest `destination` in byte order, the table being `WITHOUT ROWID`; each removed row a `system` change in `sharing_changes`) and then creates `sharing_levels_one_server`; the `team` rows move at the first confirmed add. Both module migrations run in the one `BEGIN IMMEDIATE` of the module upgrade after the `VACUUM INTO` copy, so a failure leaves sharing 1 and knowledge 7, that open fails, and the next opener retries; `user_version` stays 7. `sharing_changes` keeps its shape; the `what` of a per-server change is `project:<id>@<serverId>`, `roots@<serverId>`, `areas@<serverId>` or `server:<id>`. The `meta` keys of this part: `sync.lease`, `sync.stop`, `sync.last_failed_start`, `sharing.restore_hold:<serverId>` (its value the reason, `restore` or `bulk`, and the time), `sharing.resume_authorised:<serverId>` (the uids a `resume` showed, each removed as its withdrawal is answered, the key deleted when empty).

The search rows of received entries use `repo_id` 0 (`RECEIVED_REPO_ID` in `index-store.ts`) and `entry_id` `<serverId>|<uid>`, which is also a received `Hit.id`, so `knowledge_shown` rows and the already-shown filter key on it; `rebuildAll`'s orphan deletion and `compact`'s shown-row deletion keep them; `ftsCount` counts received rows in `active`, and `indexReceivedRow` writes a search row only for an active received entry. The knowledge module's and the retrieval's own SQL read six sharing tables read-only (`sharing_servers`, `sharing_muted_members`, `sharing_levels`, `sharing_conflicts`, `sharing_received_memories`, and `sharing_ledger` for the `applied` rows that render the `revised by` marker and hold a pin); their column names are pinned by `tests/unit/sync-schema.test.ts`, and each reader (and `state.ts` and `ledger.ts`, which `status` and `doctor` reach through `openExisting`) checks `sqlite_master` once per open and reads nothing when the sharing schema is absent.
