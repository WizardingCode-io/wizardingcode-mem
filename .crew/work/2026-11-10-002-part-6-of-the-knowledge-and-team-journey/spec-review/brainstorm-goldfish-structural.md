Lens: long-term debt and maintenance. What this concept locks in, and what a later part would have to undo.

## Findings
- F-1 · Blocker · "applies withdraw, move and purge rows" + "received entries into the local knowledge repositories" · A received entry is committed into a local git repository, and a received memory becomes a memories row. ADR 0024 never rewrites history and never deletes an entry (D-2, D-5). Memory never deletes a memory (ADR 0025 Identity of an item, CLAUDE.md compact). So a server `purge` (ADR 0026 D-24, "what a person asks to have erased must not come back from a copy") cannot be carried out on a client: the text stays in every member's `.git` objects and in every `imported` row for good. As written, the concept promises a purge it cannot deliver. Either received items live somewhere that can be erased (not the person's versioned repositories), or purge locally becomes a history rewrite, which breaks part 1's guarantees. Choosing later means migrating every received item already written.
- F-2 · Blocker · "received entries into the local knowledge repositories" vs ADR 0024 "What parts 4 to 6 inherit" · ADR 0024 says an entry from outside this machine is not shown by a hook until it has passed a review the sharing design names, and that this is enforced in `visibleRepos`. Writing received entries straight into workspace, shared and project repositories makes them visible at once. Pinned entries reach session start, and other entries reach prompts through the floor. The concept names no review and no rule. Received memories in retrieval "like an imported one" (brief assumption) have the same problem: another person's text steers this agent with no review step. Retrofitting the gate later means telling apart received rows that were already shown as trusted.
- F-3 · Major · received workspace entries into "the matching local repository (workspace…)" · The server sends every member's workspace entries on every pull (ADR 0026 D-11), and only their creator may change them (D-12). Putting them in the person's own `knowledge/workspace` mixes repositories with different owners. A local edit of a teammate's workspace entry is allowed locally, sent, and then refused with `not-owner` forever. Their areas are checked against this machine's workspace taxonomy. Their uid `workspace:<uuid>` names no owner. Someone building this would write one workspace repository per machine, and later splitting out "other members' workspaces" means a new scope and a migration of uids and ledger rows.
- F-4 · Major · "keeps the local text as a proposal of kind sync conflict" vs `PROPOSAL_KEYS` in src/modules/knowledge/entry.ts · `kind` is already a proposal key and holds the entry's kind (knowledge, strategy, persona, pattern), so "kind sync conflict" needs a new key. An older binary keeps that key and reads nothing from it, so after a rollback a conflict looks like an ordinary agent proposal. Proposals are also bound by the quota (5 per target, 200 per repository, ADR 0024 Proposals and the quota). A conflict refused by the quota loses the local text, which breaks D-2's "never lost". The accept needs the target at the proposal's base version. Each later pull moves the target, so a conflict that waits goes stale, and no rebase path exists. This locks in a sync concept built on a workflow that was designed for agents.
- F-5 · Major · ledger "keyed by serverId", "`decide` is unchanged in shape" vs `LedgerRecord` (src/sharing/types.ts) · ADR 0026 asks the client to keep the server's revision and hash for the base of the next push (D-7), and the local hash beside the server's (What parts 6 and 7 must do), because the server hashes the redacted bytes. `LedgerRecord` has one `hash` and an "informational" `version`, and its key list is pinned (`LEDGER_RECORD_KEYS`, the D-19 test). Either `version` silently starts to mean the server's revision and `hash` means two different things, or the pinned type changes, which the concept rules out. Whichever is picked now, every later reader of the ledger inherits it.
- F-6 · Major · "roots and areas per server" + the derived epoch (ADR 0025 The epoch) · The epoch is one number over one pair of lists, and a sync run stops when the epoch moves. With lists per server, either the epoch stays global (editing server B's areas stops server A's runs, including the resumable first run) or it becomes per destination, which changes the shape of `SharingPolicy`. The env keys also need the serverId in their names (opaque random ids in a file people edit by hand). They also need the narrow-only rule, the baseline (`sharing.settings_seen`) and the hand-edit audit for each server. Every later setting is then keyed by an id people cannot read.
- F-7 · Major · "a level is needed only to send" + "the server knows its alias" vs "binds a project to one server at most" · Receiving items for every local project whose alias a server knows means the pull names this machine's project aliases to every server (up to 100 per pull, ADR 0026 Limits). So the list of a client's private projects reaches a different client's server. If two servers know one alias, both write into the same local project repository. The second copy is `received-elsewhere`, and a local edit is decided against two received rows. "Bound to one server" then covers sending only. Narrowing the receiving side later takes away items people already rely on.
- F-8 · Major · `share server remove` / a team that moves to a new server · `serverId` is minted once and never renewed (ADR 0026), so a server rebuilt from a lost volume is a new destination. Received rows under the old id make `decide` answer `received-elsewhere` "whatever the hash" (ADR 0025 rule 3). Every entry this machine received from the old server can then never go to the new one, including entries this person wrote and a teammate later edited. The concept does not say what `remove` does to ledger rows, received files or `team:<serverId>` memories. Without a rule now, orphaned ledger rows and items that can never leave build up for good.
- F-9 · Major · "after a new instance, after a 410" snapshots · The ledger key has no `instance` (`(destination, item_kind, item_uid, direction)`). After a server restore, ADR 0026 Rollback says clients "re-push what the copy lacks", but the ledger still says `already-sent`. "Absent from the snapshot is gone" then gets applied to local received copies. So an instance change must rewrite every ledger row for that server, a rule that every later ledger reader has to know about. Keying or stamping rows by instance now avoids that.
- F-10 · Major · "a stale push … applies the server's revision to the file" · The server's bytes carry another machine's `version`, `author` and `updated` lines. Writing them makes the local version counter follow other machines, and puts another person's name on the file. The concept does not say whose commit this is: the person's would break D-11's attribution rule, and a "sync" writer is a new writer kind the store cannot tell from a person or an agent. A file the person is editing by hand must not be overwritten (D-11, adopt), and the concept is silent on a dirty target. ADR 0024 (What the later parts add) also notes that a new operation's intent record is dropped without any undo by a binary that does not know its name, which is rollback debt.
- F-11 · Major · "received memories as `imported` rows with `judge = team:<serverId>`" · The concept stores provenance in the column that records which judge rated a memory. Every current and future command that selects on `origin = 'imported'` or on `judge` has to know about this: replace-imports needs narrowing now, rejudge must stay `claude-mem`-only, and so must anything later. A local withdraw or purge finds the row only through the ledger's `item_uid` (`remote:…`), and ADR 0025 accepts that the ledger row can be lost. A real provenance column (server, remote uid) costs one migration now. Later it costs a backfill that guesses from `judge`.
- F-12 · Major · the device token "in the person's own store file" · If "store file" means the database, the token goes wherever `backup` copies the database (a folder or a bucket, ADR 0024 Backups) and moves with `moveStore`. A store copied to a second machine (ADR 0025 Known limits) then gives two machines one device token. Both write under one device key on the server, and the device scoping the server relies on is gone. A restore brings back a token that may have been rotated, giving a 401 and a re-join. The place the token lives is hard to move once tokens are written, so it needs stating now, apart from the backed-up database.
- F-13 · Major · the sync process's shape ("push right after each local change", one per data directory) · Local changes happen in other processes: CLI writes, accepts, the drain's new memories, `adopt`. To meet 5 s, either the sync polls, or every current and future writer signals it, a hidden coupling each later writer must remember. The lease is per data directory, but ADR 0024 Known limits allows one database shared by two data directories. That case gives two sync processes over one ledger and double sends. For a product that says "One binary, no daemon" (CLAUDE.md), this is a long-lived networked process kept alive by a quiet-time heuristic. Its lifecycle rules become a contract the viewer, the hooks and later modules all have to follow.
- F-14 · Major · the taxonomy is not in contract 1 · Received entries are checked against this machine's taxonomy (parseEntry). An entry in an area a teammate added becomes a draft with a problem, which then never leaves and is never shown. ADR 0024 D-9 points to "the team's taxonomy is synced" as the fix. Syncing taxonomies later means bumping the contract and handling skew (ADR 0026 D-18), and the problem drafts written before then need repair.
- F-15 · Nit · "speaks the highest contract the server accepts" with CONTRACT 1 only · The client keeps a contract per server but knows only one value, so the skew path (a 409 with the accepted list, then falling back) is built with nothing to fall back to and goes untested until the first bump. F-5 and F-14 are both bumps waiting to happen. The first one will test this code for the first time in production.
- F-16 · Nit · "first run sends everything … batched under the server's limits" · The server takes 64 MiB of applied payload per hour per device, and its buckets reset on restart (ADR 0026 D-15). A store with tens of thousands of memories at `all` will hit `rate` for hours. A status that shows "resumable" while `rate` keeps answering looks the same as a sync that is stuck. That is a support cost unless status shows the bucket and an estimate.

## Not answerable
- How "alive while a session is active" is detected · the concept, the brief and the ADRs read do not say what signal the sync reads (a session row, `hook_runs`, a file), so the coupling in F-13 could not be sized.
- What "the person's own store file" names · it may be the database or a separate file, and nothing read settles it (F-12).
- Whether part 4 ever wrote `sharing_ledger` rows · ADR 0025 says this part writes none, so the ledger migration may move nothing, but no store's state was checked.
