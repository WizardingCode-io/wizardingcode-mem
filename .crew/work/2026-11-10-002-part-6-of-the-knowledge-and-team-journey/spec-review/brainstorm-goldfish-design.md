# design findings for 2026-11-10-002-part-6-of-the-knowledge-and-team-journey
reviewer: goldfish-design
read: .crew/work/2026-11-10-002-part-6-of-the-knowledge-and-team-journey/brief.md; docs/adr/0025-sharing-policy.md; docs/adr/0026-team-server.md (whole); src/team/server.ts (LIMITS); src/team/feed.ts; src/team/push.ts; src/sharing/policy.ts; src/modules/knowledge/store.ts (lines 170-419 and the function list); src/modules/knowledge/repo.ts (lines 330-509 and the export list); src/cli/commands/hook.ts (the spawns, BUSY_TIMEOUT_MS). Lens: cost, quota and token economics, plus failure modes and scale limits.

## Findings
- F-1 · Blocker · Moves and alias changes (outbound) · An entry moved locally between scopes, or a project entry whose bound alias changes, gets a new uid (`workspace:<uuid>` becomes `shared:<uuid>`). Under ADR 0025's rule that withdrawals are computed from the ledger's uids, the old uid is withdrawn. On the server `applyWithdraw` resolves an entry uid to its bare UUID (`parseFeedUid` → `parseEntryUid(...).uuid`) and never checks scope. So the withdraw of the old uid tombstones the entry that was just moved. If the new uid is sent first with base 0, the server answers `stale` with no `appliedAs`, because the row for that UUID already exists. D-2 then writes the server's old-scope text into the file and turns the person's move into a sync-conflict proposal. The concept has to say that a move is one send on the old uid's base, that the old uid's `sent` row is retired without a withdraw, and that the send happens before the withdrawal sweep sees the old uid. Otherwise the most ordinary reorganisation quietly removes team content.
- F-2 · Blocker · Snapshot "absent is gone", a new instance, a 410 · A snapshot after a server restore (new `instance`) or a 410 will not contain items this machine sent after the server's copy was taken. If "absent from the snapshot is gone" deletes local copies by uid, the machine deletes entries the person wrote. Deletion must be limited to items that have only a `received` row and no local authorship. There is a second half to this. After a new instance the `sent` rows still say `already-sent`, so `decide` keeps items the server no longer has. If the client re-pushes them on its ledger's base revision, the server's older revision makes every one `stale`, and D-2 rolls the person's files back to the server's text in bulk, each with a conflict proposal. The concept names the snapshot but not the ledger reset per instance, and not the rule that a stale caused by a server rollback is not a conflict.
- F-3 · Major · Local layout keyed by slug · Local entries live at `entries/<slug>.md` (store.ts:167). The server keys entries by UUID, and its mirror names files `<slug>--<8 hex>.md` because slugs collide. Every member's workspace entries (D-11: pulled always), and the shared entries of several servers, are written into this machine's one workspace and one shared repository. Two teammates' `coding-style` entries, or two servers' `onboarding`, map to the same file. `writeEntry` refuses `exists`, or one entry overwrites the other. The concept does not say where a received entry lands when its slug is taken, or whether other members' workspace entries are received into this person's own workspace repository at all.
- F-4 · Major · Echo loop: the entry hash after redaction · `decide` compares the local `item.hash` (ADR 0024's `hashOf` over the file's raw bytes) with the `sent` row's single `hash`. ADR 0026 has the client recompute the hash over the redacted bytes. Whenever `redactForSend` changes anything, the two differ. Every sweep then answers `send`, and the server answers `applied` by idempotency before the bytes bucket, so nothing visible fails, but each sweep spends a request and up to 1 MiB of upload per batch, forever. `LedgerRecord`'s keys are pinned (`destination, direction, hash, version, withdrawnAt`), so "record the local hash beside the server's" means either a column outside the pinned type or a change to the contract test. The concept does not choose. A smaller version exists on the receiving side: the received bytes must be written byte-for-byte so that `hashOf(file)` equals the server's hash, or `received-same` never matches and the received copy is pushed back as an update.
- F-5 · Major · Change detection and the 5 s target · Local changes are made by other processes (the MCP server, `distill`, the viewer, the CLI). The concept says "right after each local change" but does not say how the sync process learns of one: fs watch on the repositories, polling SQLite's `data_version`, or a nudge file. Polling at a few seconds already uses most of the 5 s budget. A full sweep per change is O(N) work. Sent memories' hashes have to be recomputed over redacted text to detect updates, which means redacting about 90,000 memories (ADR 0025's scale) on each sweep. The design needs a named, incremental change source and a debounce. Without them either latency or CPU fails.
- F-6 · Major · First run vs the 64 MiB/hour bucket · At about 1.5 KiB a memory payload, 90,000 memories are about 130 MiB, so at least about 2 hours of the device's applied-bytes bucket (about 18.6 KB/s refill). A single 256 KiB entry needs about 14 s of refill. Inside a push, the items that fail `gates.bytes` are refused `rate` while later, smaller items pass, so order inside a batch is not kept. Order matters for the move rule in F-1. During the backfill every live change competes with the backlog for the same bucket, so the "under 5 s" criterion fails for hours after a server is added, and again after every restore, when the generation renews and all memories are re-sent (also F-12). The concept needs live changes ahead of the backlog, retry timing derived from the bucket's refill rather than a fixed backoff, and batches sized by bytes as well as by 200 items. Otherwise each retry uploads up to 1 MiB to have a few items applied.
- F-7 · Major · Permanent refusals and purge with no local memory · `refused` (`secret`, `shape`, `size`, `not-owner`, `withdrawn-by-admin`) is "final for that content", but the ledger only has `sent` and `received` directions. With no stored refusal keyed by uid and hash, every sweep re-sends the item. "`purged` drops the copy and the ledger forgets it" is worse: once the ledger forgets, `decide` sees no record and answers `send` again, the server answers `refused purged` for good, and this repeats each sweep. Together with the stale/apply/re-push path, these are loops that can reach 600 requests a minute, and ADR 0026 names `serve revoke` as the remedy for a looping device. The concept needs stored refusals, a purged-key tombstone on the client, and a circuit breaker per server.
- F-8 · Major · "Alive while a session is active", "quiet quarter hour" · The sync is started only by the session-start hook and the viewer. The concept does not say what "active" is measured by (a heartbeat file, a hook touch, a viewer connection), or whether "quiet" means no local change or no session. A three-hour session with 15 minutes without edits lets the process exit, nothing restarts it until the next session start, and teammates' changes stop arriving. That breaks the goal. Also, `spawnViewer` is skipped under SSH, CI and headless Linux. The sync spawn must not inherit those gates, and the concept does not say so.
- F-9 · Major · Apply cost: synchronous git in a long-lived async process · `runGit` uses `Bun.spawnSync`, and each received entry is a `writeEntry`-style path: leases, `ensureFresh`, `statusOf`, a commit, then indexing. That is several spawns per entry. The server's own mirror estimate is about 35 min for 20,000 revisions at one spawn per commit. A first snapshot, or the full re-pull after a new instance or a 410, blocks the event loop for that long. Held pulls to other servers time out, pushes stall, and the repository leases (`KNOWLEDGE_LEASE_MS` 60 s) are held so that an agent's MCP knowledge write waits or fails. The concept needs one commit per page or per repository batch, skipping of items whose hash already matches, and git work off the event loop.
- F-10 · Major · Hook-path contention through SQLite · The sync never runs on a hook, but its writes share the store with hooks whose busy timeouts are 100 to 150 ms (`prompt`, `session-start`, `file-read`, `tool-failed`). Writing thousands of received `imported` memories or `received` ledger rows in large transactions holds the write lock past those timeouts, so hooks fail their reads or writes. The hook then waits on the network after all, one step removed. The concept does not bound the sync's write transactions, for example to a few milliseconds each per page chunk.
- F-11 · Major · Token budget and trust of received memories and entries · Received memories "take part in retrieval like an imported one". A shared project with ten teammates at `all` can bring several times this machine's own memory count into retrieval and the session-start injection. That crowds the token budget, and ADR 0025's count target (90,000 memories, 1,000 ms) is passed. Any member can write any shared or project item (D-12, and the alias filter is not a permission), so a teammate's text, or a compromised token's, reaches this person's agent context. That is a prompt-injection path. The concept sets no cap on the share of received items in injection, no ranking penalty, no marking in the injected text, and no way to mute one server or member. The dedupe by content of copied stores (ADR 0026, "What part 6 must do") is also missing from the concept.
- F-12 · Major · Restore of the client store · The device tokens are in "the person's own store file". The store's backups under `<store>/backups` then carry live bearer tokens, a secret at rest that nobody named, and a restore brings back a token that may since have been rotated (a 401 with a known instance). A restore also brings back an older ledger. Items sent after the backup have no `sent` row, so they are pushed on base 0 and come back `stale`, which means mass conflict proposals by D-2. The new generation re-sends every memory (the F-6 cost) and must withdraw the old generation's (up to 90,000 withdraws, which every teammate pulls). The concept states "nothing is sent under the old generation" but not this reconciliation or its cost.
- F-13 · Major · 401 with a known instance, network failure and sleep · The concept covers a 401 from an unknown instance (re-join) and a 409 (stop). A 401 from a known instance (the device was revoked or the member disabled) has no stated behaviour. Retrying it counts against the 60-a-minute auth bucket of the source address, which every teammate behind the same office NAT shares. A held pull through a laptop sleep or a network change can hang on a half-open TCP connection far longer than 25 s, because the server's idle timeout is 120 s and the OS's is minutes. The client needs its own deadline (about wait + 10 s), jittered backoff on 5xx, 429 and network errors, and a stop state for a known-instance 401.
- F-14 · Major · Inbound move and tombstone ordering · `applyEntry` writes the `upsert` row (new range) before the move `tombstone` (old range, `movedTo`) in the same transaction. In a feed that holds both ranges the client sees the upsert first, then the tombstone. If a tombstone is applied by UUID, as the server keys it, the client deletes the copy it just wrote. The concept says a tombstone whose `movedTo` names an unread range drops the copy, but not that a tombstone is applied to the (scope, alias) of its uid only.
- F-15 · Major · Taking up an alias, and the 100-alias / 8-held caps · Opening a one-alias snapshot while the main pull's cursor keeps moving has a gap. Rows for the new alias written after the snapshot's last item but before the alias joins the main pull's `projects` are missed if the main cursor passes them first, and nothing re-sends them. The concept needs a stated hand-over, for example resuming the main pull for that alias from the snapshot's `next`. A machine with more than 100 aliases on one server needs several pulls with separate cursors, and the server holds at most 8 per device, beyond which it answers an empty page at once. A client that treats an immediate empty answer as "wait elapsed" and re-polls spins against the 600-a-minute bucket.
- F-16 · Major · A received write onto a dirty or problem file · Writes refuse a path that is not clean (`requireClean` → `dirty`) or one indexed with a file/dup problem. Then one of two things happens. If the cursor waits for the item, that server's feed is blocked behind a person's unsaved hand edit. If the cursor moves past it, the revision is lost until the next full snapshot. The concept does not say which, or how the item is retried and shown in status. The point at which the cursor is saved (after the page is applied, so that a crash re-applies the page idempotently) is not stated either.
- F-17 · Nit · Single process as a single point of failure · One sync process per data directory, restarted only by a session start or the viewer, carries every server. A crash, or a lease left by a killed process (the server's own lease has a 30 s window), stops all syncing silently until the next start. Status shows "last error", but nothing warns that the process is not running. One server's slow apply or backoff should not hold back the others, and the concept does not say they are isolated.
- F-18 · Nit · Aliases in the URL · `projects=` carries up to 100 `remote:` aliases in the query string, about 6 KB, and these names are logged by proxies upstream of the server's own log. The constraint "never in a URL" is stated for the token but not weighed for repository names, which can be confidential (a client's repositories).
