Lens: migration and backward compatibility.

## Findings
- F-1 · Blocker · Constraint "token stored in the person's own store file" vs ADR 0025 "Identity of an item" · ADR 0025 says two machines never collide because the device token scopes every memory uid (`<generation>:<row id>`). If the token is stored in the store file, then a store copied to another machine, a `moveStore`, or a backup restored on a new laptop carries the same token and the same generation. Two devices then push the same uids under one device scope and overwrite each other on the server. The concept has to say what a copied or restored store does with the token: drop it and re-join, or detect the copy (for example with a machine fingerprint next to the token). Without that, the premise part 4 relies on is false.
- F-2 · Blocker · "Nothing is sent after a restore under the old generation: the old generation's items are withdrawn" · `restoreBackup` keeps the copy's `sharing_ledger` and throws away the live one. Items the live store sent between the backup and the restore exist only in the discarded ledger. Withdrawing "from the ledger's uids" (ADR 0025) cannot reach them, so they stay on the server for good. Two ways to fix it: carry the live store's not-withdrawn `sent` rows, or at least its generation, through `restoreBackup` (it already reads the live counter as a floor), or have the server list the device's uids by generation. Neither is named.
- F-3 · Blocker · "server remove" · Nothing says what remove does to the server's `sharing_levels`, `sharing_ledger` rows, cursor, env keys, or the items it delivered. The specific danger is received entries. They keep their scoped uid and carry no `imported` marker, so `received-elsewhere` (decide step 3) is the only thing that stops them going to another server. If remove deletes the `received` rows, the next pass sends the team's entries to the second server as this person's own work. That breaks "a received item never travels on". The cases needing a ruling: remove while offline (withdraw first or not), a remove that stops halfway, and re-adding the same `serverId` later.
- F-4 · Major · Restore and the knowledge repositories · `backup` does not copy the repositories (CLAUDE.md), so after a restore the received entry files are still on disk but their `received` rows may be missing from the older copy. Decide step 3 then answers `send` and echoes them back to the server, or out to another server. A reader would build the restore without a step that rebuilds `received` rows from the files. A marker in the entry file, or a check against a snapshot, would do it.
- F-5 · Major · "migrating the one destination `team` to the first server added" · This cannot be a SQL migration. `openDb` runs module migrations on every opener, hooks included, and at that time no `serverId` exists. The concept needs two steps: a schema step `sharing` v2 (the servers table, any new ledger columns such as the server's revision next to the local hash, the per-project binding), and a data step inside the `share server add` transaction. Neither is named. Also unsaid: what happens if the add fails after the join succeeded (the server has a device and the client has no row), and what happens to `team` rows a downgraded binary writes after the move. `reconcileLevels` keeps rows "for a destination this version does not know", so those rows would be silently ignored for good.
- F-6 · Major · "chooses roots and areas per server" / the env keys · `SETTING_KEYS` is a fixed `as const` list. `SettingKey`, `publicSettings`, `validatePatch`, `SHARE_LISTS` and `applySettingsPatch` all assume exactly two sharing keys. Per-server keys force a design choice the concept does not make: keys suffixed per server, a JSON value, or lists moved into the database. The env-file move also cannot be atomic with the database move, so a crash between the file write and the commit leaves the lists and the rows split, and the recovery rule is not stated. The baseline `sharing.settings_seen` is one object with no server key, so the first reconcile after the move would log the migration as a hand edit.
- F-7 · Major · Environment narrowing across the key move · Today `WIZARDINGCODE_MEM_SHARE_ROOTS`/`AREAS` in the environment narrow the file (ADR 0025 "Narrow-only"). If the first server's lists move to new keys, a narrowing variable an operator already set (for example `..._SHARE_AREAS=none`) stops narrowing anything. The migration itself then widens the policy, and no confirmation is asked. The concept must say which environment variables narrow which server's lists after the move.
- F-8 · Major · The epoch after the move · Today the epoch is `counter x 2^20 + hash20(roots|areas)` over one pair of lists, and `policy_epoch` in the ledger was recorded under it. With lists per server, someone must decide whether there is one epoch per server or one global epoch over every server's lists, and that the move bumps the counter. Otherwise a run in progress across the upgrade does not stop on "epoch differs", and two different policies can produce the same epoch.
- F-9 · Major · Binary downgrade to the part 4/5 release · (a) That release's `history replace-imports` still selects `origin = 'imported'` alone (ADR 0025: the narrowing ships in part 6). After a downgrade it archives every received memory (`judge = 'team:...'`). (b) Its `setLevel` writes `destination = 'team'` into a table whose other rows are keyed by `serverId`. If v2 adds a NOT NULL column without a default, the old INSERT fails. (c) Its `restoreBackup`/`resetLevels` runs on a v2 store and knows nothing about the generation withdrawal. The rollback target and what survives it are not stated. ADR 0025 gives 0.6.0 for parts 1 to 4; part 6 needs its own line, and ADR 0027 should list v2's columns as add-only with defaults.
- F-10 · Major · Sync processes from two binary versions · The lease is per data directory, but nothing says what happens when the lease holder is an older sync binary that is still running after an upgrade (detached processes outlive the replaced binary). The old process may write v1-shaped rows, or answer the new schema's `too-new` state by stopping. A newer hook that finds the lease held does nothing. The lease needs a version, and a newer binary needs to be able to take it over. `restore`, `move` and `compact` must also refuse, or wait, while the sync lease is held, as they do for `embed.lease`. Otherwise a held pull writes `received` rows into a store being replaced.
- F-11 · Major · Server restored (new `instance`) · ADR 0026 says every client "re-pushes what the copy lacks". But the client's `sent` rows still say `already-sent`, and `decide` answers `keep`. The concept says only "opens a snapshot". It must also say that the snapshot is checked against the client's own `sent` rows (missing ones cleared or marked so they go out again), while missing `received` copies are dropped. These are two different directions, and "absent from the snapshot is gone" must not delete the person's own entries.
- F-12 · Major · Where the cursor and the server list live · If they live in the database, a restore rolls the cursor back. That is safe: the pull re-applies. But it also brings back an old token, which may have been rotated or revoked, and then a 401 with a known `instance` has no rule. If they live outside the database, a restore leaves a cursor ahead of the restored rows and what came in between is never pulled again. The concept must choose, and say whether `restoreBackup` keeps the live store's server list, as it keeps the live counter.
- F-13 · Major · The device token in backups · `backup` copies the database to the configured folder or S3 bucket. With the token in the store file, every backup carries a live team credential off the machine, which conflicts with "never in the env file, the logs or a URL". Either exclude or blank the token in the backup copy, or state that this is accepted.
- F-14 · Major · "a project is bound to one server at most" · The `sharing_levels` key `(project_id, destination)` allows one row per server, so the schema does not enforce the rule. The concept must say where the binding lives (a column or table with a unique key on `project_id`) and how existing `team` rows map onto it.
- F-15 · Nit · Upgrade cost on a hook · Sharing v1 to v2 has `recorded > 0`, so `backupVersion` takes a full copy of the database on whichever opener comes first, possibly a session-start hook (ADR 0025 claimed no backup only for v1). This matches the existing knowledge 6-to-7 behaviour, but it should be written down as a known cost against the hook budgets the acceptance requires to "pass unchanged".
