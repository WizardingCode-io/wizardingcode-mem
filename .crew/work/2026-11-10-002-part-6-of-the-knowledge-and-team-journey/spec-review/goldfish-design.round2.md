## Findings
- F-1 · Major · spec.md:119 (Answers, "`stale` on a memory is re-sent on `current`") · ADR 0026 line 58 says a memory push has no base: a later `updatedAt` replaces it and an older one is `stale`. Re-sending "on current" changes nothing the server checks, so the same older `updatedAt` gets `stale` again on every sweep (at least every 60 s, and every 2 s while the stamp moves). That is the bucket-burning loop the Risks section says is handled, and it is reachable after a client restore or clock skew. The spec must say what a memory `stale` does (accept the server's copy and record it as sent, or bump `updatedAt` once and then stop) and give it an AC.
- F-2 · Major · spec.md:107 (the tick reads `stamp(db)`; "a change runs a sweep for every server") · `stamp` (src/embed/vectors.ts:123-127) counts the connection's own writes through `total_changes()`. Each sweep ends by writing `last_sweep_at`, `last_sweep_epoch` and `last_sweep_generation`, and each pull writes cursors and state rows, so the sync's own writes move the stamp and start another sweep 2 s later, for ever. That is a full candidate scan every 2 s and write-lock contention with the hooks. The spec must say the stamp is re-read after the sync's own writes (or that its own changes are excluded), and an AC must show that an idle sync makes no sweep between the 60 s marks.
- F-3 · Major · spec.md:146 ("any `setLevel` clears it") · The restore resets every level to Nothing, and one `setLevel` on any project clears the global hold. The next withdrawal sweep then withdraws every sent item of every project the person has not set again. That is exactly the "take the person's knowledge back from the team" the hold exists to prevent, and the person is not warned. The hold must be released per project (or per server), or the clearing `setLevel` must preview and confirm the withdrawals it unleashes, and AC-48 must cover it.
- F-4 · Major · spec.md:103 and spec.md:123 ("a restore unbinds nothing… the received project copies survive it"; `reconcileLevels`' "received copies stay until the server is removed") · Once a project is no longer bound, its alias drops out of the pull. Its received copies keep being searched and injected but no longer get updates, tombstones or `purge` rows, so an admin's purge (a leaked secret, an erasure) never reaches them on this machine. This security and staleness gap is not named in Risks. The spec must either stop serving copies of an alias that is not pulled or drop them, or state the gap and its remedy in Risks and in ADR 0027.
- F-5 · Major · spec.md:125 (`<folder>` is `members/<member id>`, "the server's own naming, `naming.ts`, tested against `repoFolder` of the server") · ADR 0026 line 74 names the server's workspace folder `repos/members/<member id>-<slug of the name>/`, so this claim is false for members, and a `naming.ts` test against the server's `repoFolder` would fail or force the name into the client's path (which works against part 7's erasure of a member's name). The spec must say which naming is meant and drop "the server's own naming" for members, or test only the shared and project folders against the server.
- F-6 · Major · spec.md:111 ("at most once per quarter hour, one detached spawn") · Nothing backs this bound. If `sync --auto` crashes or exits 1 at start (a carry owed that keeps failing, `openDb` failing, a token missing for a confirmed row, a lease lost in a loop), there is no live lease and no flag, so every prompt spawns a new process. The spawn needs a backoff (for example a `meta` mark of the last spawn or the last failed start) and an AC for a sync that keeps failing.
- F-7 · Major · spec.md:23 and spec.md:28 (Goals: "receive the team's changes within five seconds", "survive … a laptop's sleep") · The 5 s figure is proven only in-process (spec.md:204), and ADR 0026 line 66 shows a held pull wakes at once only on the server's in-process signal and otherwise every 5 s. The path is the teammate's 2 s tick, then their push, then the server's wake, then this pull and its apply, so the bound should be stated end to end with that reasoning. Sleep has no rule at all: what happens when the 60 s lease expires during sleep while the pid is still alive (does `ownerAlive` refuse the takeover, or can two holders run?), and what happens to a held pull past its 35 s deadline. Neither has an AC.
- F-8 · Major · spec.md:107 ("a newer binary takes over an older holder's lease (the holder … exits 1 after the current page or batch)") · For up to 20 s two processes sweep and pull with one token. Each can save its own cursor, so the older can write back an older cursor, and both can apply to the same own file. The spec claims safety without arguing it: it must say that cursor saves never move backwards (compare-and-set on the lease owner, or max) and that a process which lost the lease writes nothing.
- F-9 · Major · spec.md:119 ("`stale` without it on an entry whose `current.hash` is in the sent history is a server rollback") · A teammate who reverts the entry to a text this machine once sent has a hash in the sent history, so the revert is read as a rollback and silently overwritten by a re-send. Goal line 30 ("tell a server rollback from a conflict") is claimed but the rule cannot tell these two apart. The spec must use the server's instance or revision (a rollback lowers the revision or changes the instance; a revert raises the revision) or name this case as a known limit.
- F-10 · Major · spec.md:134 and spec.md:29 (received rows join "the prompt floor … every server's shared and workspace items"; "capped in a brief") · The cap of a third is stated only for memories. The floor's two entries per prompt (ADR 0024 line 299) can both be teammates' text, and every member's workspace is in scope. ADR 0024 line 311 measured the floor's false-injection rate on 18 entries and warns that thousands raise it; a team's received corpus is that case. ADR 0026 line 62 says any member may push to any alias, so any member can put text in any bound project's prompts. The spec must state the cap for received entries in the floor and the session-start block, and name this injection surface and its measurement in Risks.
- F-11 · Major · spec.md:117 ("Batches: at most 200 items and 900 KiB of payload") · The server caps the body at 1 MiB (ADR 0026 D-15, and Caddy's `max_size 1MiB`). JSON escaping of Markdown (newlines, quotes) plus the per-item keys of 200 items can push 900 KiB of payload past 1 MiB, and a 413 is not among the answers handled at spec.md:119. The spec must say the limit is measured on the serialized body, and what a 413 does (split the batch and retry).
- F-12 · Major · spec.md:115 (candidates are entries "whose index hash differs from the ledger's `local_hash`") · An edit made outside the store (an editor on a file under `knowledge/`, a `git` operation) changes neither the index nor `data_version` until something runs `ensureFresh`. Goal line 28 ("within five seconds of a local change") then does not hold, and the 60 s sweep only re-reads a stale index. The spec must say whether the sweep runs `ensureFresh` over the bound repositories, and at what cost, or narrow the goal to writes made through the store.
- F-13 · Major · spec.md:127 (a received memory's row id "may be reused by SQLite, which is harmless") · `memory_vectors` is keyed by `memory_id` (src/embed/vectors.ts:35-37), and the deletion list here names provenance and ledger rows but not the vector or other tables keyed by memory id. A reused id can inherit a deleted teammate memory's vector (for example when the new row is written without a model), so retrieval would match the wrong text. The deletion must name every table keyed by memory id, or "harmless" must be argued.
- F-14 · Major · spec.md:123 (a pull names "the shared scope, every member's workspace, and the aliases … in groups of at most 100 aliases, each with its own cursor") · The spec does not say which group carries the shared scope and the workspaces. If every group does, they are pulled once per group. If they ride with the alias group, every bind or unbind is a new group whose snapshot from 0 re-reads the whole shared corpus and every workspace, a cost that grows with the team and is not sized. The spec must give the shared and workspace scopes their own cursor, or state and size the re-snapshot.
- F-15 · Major · spec.md:97 (`remove --withdraw` "pushes a `withdraw` for every not-withdrawn sent row (a failure refuses the removal…)") · A withdraw must name the current base (ADR 0026 line 60). The server is already `removing`, so pulls stop and a teammate's revision since the last pull makes the withdraw `stale`. As written, that refuses the removal for good unless the withdraw is retried on `current`. The spec must state the stale-withdraw rule for `remove`.
- F-16 · Major · spec.md:16 and spec.md:123 (every member's workspace is received as read-only copies under `members/<member id>`) · The same person on a second machine receives their own workspace entries as a teammate's: read-only, marked `from <their own name>`, editable only after `take`, and not counted as their own items. D-9's alternative (spec.md:171) shows a second machine is an expected journey, but no rule or journey covers the member's own other devices. The spec must state how items of the same member from another device are treated.
- F-17 · Major · spec.md:93 (the token goes to the file first, then the row; a re-run of `add` replaces it) · If the join's answer is lost (a network error after the server minted the device), there is no token, and the re-run needs a code the server may already have consumed. The spec does not say whether codes are single-use or what the person does next. Concurrent writers of `servers.json` (the CLI, the viewer and the sync, spec.md:89) have no lock, so a lost update erases a token and forces a re-join with a new code. The spec must state the file's write lock or compare-and-swap, and the remedy for a lost join answer.
- F-18 · Major · spec.md:63 (Sizing) and spec.md:175-190 · Heilmeier questions 6 to 8 are unanswered: there is no time estimate, no cost beyond a file count, and no midway check, only final ACs across about 28 source files and 22 test files. A reader would build it as one big-bang change with no verifiable intermediate slice (for example join plus outbound before inbound plus conflicts). The spec must state an estimate and the midway checks.
- F-19 · Nit · spec.md:111 (`startSync` "reads one row …, the lease and the stop flag") · That is three reads, while AC-17 and spec.md:205 say "one read". Either say it is one query or change the claim.
- F-20 · Nit · spec.md:127 (dedupe: "not inserted, its `received` ledger row written all the same") · A later revision of a deduped remote uid has no `sharing_received_memories` row, so it goes in as a new import beside the person's own copy. State what a later revision of a deduped uid does.
- F-21 · Nit · spec.md:101 ("the counter is global: a change to one server's lists moves every server's epoch") · Each such change also makes every server's next sweep rehash every memory (spec.md:115 and spec.md:206). Name that cost.
- F-22 · Nit · spec.md:134 (`knowledge_get` reads `<server>:<slug>--<8 hex>`) · The spec does not say whether `<server>` is the id, the name or the host. Names can collide or contain `:`. State which one, and the rule for ambiguity.
- F-23 · Nit · spec.md:11 ("above Nothing, or is `receive`") · `receive` is already above Nothing in `LEVELS` (spec.md:103), so the "or" is redundant and suggests `receive` is a separate case.
- F-24 · Nit · spec.md:3 · The revision history takes one sentence of about 150 words, and Heilmeier question 1 (no jargon) is not met anywhere: the Problem section assumes ADR vocabulary. Move the history out and add a plain-language summary.
- F-25 · Nit · spec.md:175-190 · AC numbers are out of order (15, 35, 17, 18, 40, 47, …) and carry "supersedes" chains that only the history can explain. Renumber, or add an index of what each covers.

## Not answerable
- Whether the viewer's `POST /api/servers` routes are protected against a cross-site request (a page joining the machine to an attacker's server and sending the yes) · I saw only that the viewer mints a token (src/ui/server.ts:752-757), not how routes check it, and the spec does not say.
- Whether invitation codes are single-use · ADR 0026 lines 56-95 and its decisions table do not say, so F-17's remedy could not be checked.
- Whether a GET pull naming 100 `remote:` aliases in its query string fits the URL limits of Bun and Caddy · the limits are not stated in the ADRs I read, and I did not check outside docs.
