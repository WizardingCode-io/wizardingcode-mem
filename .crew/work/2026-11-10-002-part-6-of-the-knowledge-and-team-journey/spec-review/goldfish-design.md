## Findings
- F-1 · Blocker · spec.md:147 and spec.md:157 ("one cursor per alias group", "a snapshot over its aliases only") · The server cannot answer a pull like this. `parsePullQuery` in src/team/feed.ts accepts only `scope=all`, which in `feedSql` (src/team/store.ts:854-863) always adds the shared and workspace ranges to the named aliases, or `scope=project` with exactly one alias. So a pull for a group of 2 to 100 aliases also returns the whole shared corpus and every workspace under that group's cursor. A group snapshot from 0 downloads them again, any shared change wakes every group's held pull, and the comparison "over its own request's scopes and aliases only" has to treat shared and workspace rows that the group cursor does not own. The non-goals forbid server changes, so the spec must state the real request (scope=all with the group's aliases, and the client ignores or de-duplicates shared and workspace rows on group cursors, with the cost this adds to a snapshot and to wakes), or use `scope=project` one alias at a time and drop the "no one-alias snapshot" rule.
- F-2 · Major · spec.md:157 ("else `since=<cursor>&wait=25`") · The spec never says whether the scopes cursor and each group cursor are held one after another or all at once. Held one after another, a change on the second cursor waits up to 25 s behind the first, which breaks the 5 s goal (spec.md:29, spec.md:263). Held all at once, they meet ADR 0026's cap of 8 held pulls per device, and a ninth gets an empty page at once, which the empty-page rule (spec.md:164) reads as a failure and backs off. A builder will pick one at random. State the concurrency, the count of held pulls per server against the cap of 8, and what happens above it.
- F-3 · Major · spec.md:147 ("in groups of at most 100 aliases ... keyed by the hash of its sorted aliases") · The spec does not say how aliases are split into groups when there are more than 100. If a builder cuts the sorted list into chunks of 100, binding one alias shifts every later chunk, so every group's key changes and every group re-snapshots from 0, against the 600 requests/min bucket and the hook-time write lock. State a stable rule that assigns aliases to groups (for example, append to the last group that is not full; split only the group that changed).
- F-4 · Major · spec.md:121 (lease rule 1) and AC-50 at spec.md:234 · "A sleeping machine keeps its pid alive, so no second holder appears" is false under the existing code: `holds` in src/store/meta.ts:64-65 needs `until > now` as well as a live pid. After a 90 s sleep the 60 s lease has expired, and the session-start hook that fires on wake can claim it before the holder's timer renews. Also, `ownerAlive`'s pattern `^(?:ui-)?(\d+)` does not read the pid out of `sync-<pid>-<version>`; it returns "alive" for any owner it cannot parse. The spec must say that `ownerAlive` changes, and either that the sync lease is held by a live pid regardless of `until` (and how that reacts to pid reuse after a crash) or that the takeover on wake is expected and safe under rule 3. As written, AC-50's sleep case fails with `claimLease` as it is.
- F-5 · Major · spec.md:29, spec.md:136, spec.md:138 and AC-59 at spec.md:235 · The spec contradicts itself on hand edits. The goal and AC-59 say an edit made outside the store (an editor) leaves at the next 60 s sweep. The send rule says the text is read only after "a clean `git status` for its path (a dirty path is skipped and counted)", and `ensureFresh` (src/modules/knowledge/index-store.ts:774) re-indexes without committing. So an editor's change that is not committed never leaves, and nobody is told. State who commits a hand edit (the sweep, under the repository lease, or the person) or narrow the goal to committed edits; otherwise AC-59 passes only because its test commits.
- F-6 · Major · spec.md:136 (withdrawal sweep: "every not-withdrawn `sent` row whose item is gone") · Nothing guards against an item that is only gone for a moment. `refreshStale` forgets a repository whose folder is gone; an unmounted drive, a renamed folder or a branch checkout without the knowledge files would empty the index for that repository, and the next sweep withdraws every entry of it from the team. The restore hold covers only restores. State a guard (for example, no withdrawal for a repository that is missing or unindexed, or a threshold that asks for a yes, as `resume` does).
- F-7 · Major · spec.md:136 ("records `last_sweep_at` ... at its end") · If `last_sweep_at` is the time the sweep ended, a memory written during a sweep, after its candidate read, has `updated_at` below the new mark and is never a candidate again until the epoch or the generation changes. The rule also assumes every writer stamps `updated_at` with the current wall clock; `insertMemory` takes `memory.now` from its caller, so an import that keeps the source's times, or a clock stepped backwards, slips under the mark. State that the mark is the candidate read's start time and what happens to rows stamped in the past.
- F-8 · Major · spec.md:126 (the baseline "the sync re-reads after its own writes") · There is a race here. A write by another connection (an agent's tool, a hook) that lands between the sync's own write and its re-read of `stamp(db)` goes into the baseline and starts no sweep, so that change waits for the 60 s sweep, against the 5 s goal. With hooks writing on every prompt and tool use, this window is hit often. State how it is closed (for example, the sync counts its own `total_changes()` and compares against that, or the next tick re-sweeps once after each of its own writes).
- F-9 · Major · spec.md:265 ("no whole-store scan per tick") and spec.md:136 · Nothing backs this claim. Any write by another connection starts a sweep of every server every 2 s, and during an active session the hooks write all the time. Each sweep compares `entryItems` across every own entry with the ledger, and the withdrawal sweep checks every not-withdrawn `sent` row against `decide`, so both scans are as large as the whole corpus and run every 2 s. Give the cost on a stated fixture (entries and sent rows) and the index or limit that keeps it bounded, or stop sweeping on every stamp change.
- F-10 · Major · spec.md:161 (memory dedupe by `(title, body)` hash) and spec.md:157 (50 ms chunks) · Memories have no content hash column (src/store/memories.ts), and the spec adds none: core tables gain no column, and knowledge v8 and sharing v2 add no such index. So each received memory's dedupe scans and hashes the project's memories inside a chunk transaction that must stay under 50 ms. A first snapshot of thousands of memories against a large store breaks that bound, which the hooks' busy timeouts depend on. AC-53 measures "the largest chunk" on no stated fixture size. State where the dedupe hash comes from (for example, an in-memory map built once per page outside the transaction, or a stored hash in a sharing table) and the fixture AC-53 measures on.
- F-11 · Major · spec.md:159 and spec.md:249 (a teammate's revision applied to an own entry, keeping the local `pinned` line) · There is a security gap here that the risks section does not cover. Any member may revise a shared or project entry (ADR 0026 checks ownership only for workspace entries). If the person had pinned that entry, the teammate's new body goes into the person's own repository and is shown pinned in the session-start block, which the received-item mitigations (none at session start, one on the floor, a third of a brief) do not cover; the "revised by" marker is promised only in "the agents' results". State what the session-start block and the floor show for a pinned own entry that a teammate revised (for example, hold its pin until the person edits or confirms it, or always mark it), and add it to the risks.
- F-12 · Major · spec.md:138 ("a single item whose serialized size is over the cap is refused locally (`too-large`)") · The spec does not say which cap. ADR 0026 D-15 has a 256 KiB per-item cap beside the 1 MiB body cap. If a builder uses the body cap, an item between 256 KiB and 900 KiB is sent, comes back `refused size` and costs a request every time its hash changes. State that the local `too-large` check uses the per-item limit `/v1/me` publishes, measured as the server measures it.
- F-13 · Nit · spec.md:132 ("one statement over `sharing_servers` and `meta`") and spec.md:91 ("the readers check `sqlite_master` once per open") · The hook's spawn decision is not one statement. Lease liveness needs `process.kill(pid, 0)` as well as SQL, and a store without the sharing schema needs the `sqlite_master` check first, or the `SELECT` fails on the hook path. Say what the hook actually costs and that it fails open.
- F-14 · Nit · spec.md:161 ("the `received` ledger row (`remote:<uid>`)") · The feed already shows a memory's uid as `remote:<device alias>:<uid>`, so prefixing `remote:` again gives `remote:remote:…`, or the two collide. State the exact `item_uid` form.
