The lens is observability and debugging.

## Findings
- F-1 · Blocker · "started by the session-start hook ... like `ui --auto`" · A process started "like `ui --auto`" will not run where it is most needed. `src/hooks/handle.ts:194` starts the viewer only when `input.source !== "resume"`. `spawnViewer` in `src/cli/commands/hook.ts:66-73` also returns early under `CI`, `SSH_CONNECTION`/`SSH_TTY`, a Linux machine with no display, `WIZARDINGCODE_MEM_UI_AUTO_OPEN=off` and `uiAutoOpen` false. If the sync copies that path, it never runs over SSH or in a resumed session. Combined with the quarter-hour quiet exit, a long or resumed session stops syncing without any sign. The person sees "my change never arrived" while `status` shows an old last push and no error. The concept has to say which hook events start the sync (turn-end too, where the drain is started at `handle.ts:189`?), and that none of the viewer's guards apply to it.
- F-2 · Blocker · "a proposal of kind sync conflict" · No proposal kind exists today. In `src/modules/knowledge/types.ts:103-133` and `renderProposal` (`entry.ts:517-548`), a proposal's `kind` is the entry's kind (the same field as `KnowledgeEntry.kind`). The proposal has no field that marks it as a conflict. `Writer` (`types.ts:16-18`) is only `person` or `agent`, so there is no writer for a sync. As written, a conflict proposal cannot be told apart from an agent's proposal, and nobody looking at `proposals/` at 3 AM can tell that the server overwrote their text. The concept needs to name the new field or `proposed_by` value (for example `sync:<serverId>`), the server revision it is based on, and the member who wrote it.
- F-3 · Major · "alive while a session or the viewer is active" · Nothing in the code says that a session is active. The viewer writes no lease. It is tracked in `ui.json` at the brand level (`src/ui/state.ts`, written with `wx`, checked with `probeUi`) and stops after 30 minutes without a request (`server.ts:131`). Hooks leave only `hook_runs` rows with `at` (`hook.ts:173`). Without a stated signal (for example the newest `hook_runs.at` within 15 minutes, or a live `ui.json` that answers the probe), an implementer will pick one, and "why did sync exit / why is it still running" has no answer. Name the signal, and have `status` show it next to the sync's state.
- F-4 · Major · "one per data directory by a lease" · `ownerAlive` in `src/store/meta.ts:53-55` reads a pid only from an owner shaped like `<pid>-...` or `ui-<pid>`. An owner such as `sync-<pid>` "names no process" and is trusted until the lease runs out, so a crashed sync blocks the next one with nothing to show for it. The lease also has to outlast a held pull: the server holds a pull up to `pullWaitSeconds` 25 (`src/team/server.ts:28`), and the lease must be renewed during that await. The concept has to state the owner format, the lease length and how it is renewed. Separately, `anyLeaseActive` (`meta.ts:120-131`), which guards a store move and a restore, does not include a sync lease. A restore while the sync is running is exactly the "old generation" hazard that the brief's constraint "nothing is sent after a restore" addresses. Say whether the sync lease joins it.
- F-5 · Major · whole concept: where the diagnostics live · The sync's own output goes nowhere. `spawnDetached` (`src/util/self.ts:14-20`) ignores stdout and stderr. `logError` (`src/util/log.ts:44-60`) writes errors only, never information, into one 1 MB file with one previous copy kept. A pull loop that fails every 25 s while offline (one line per attempt, in every server's loop) will rotate out the drain's and the knowledge store's errors within hours, so the first cause is gone by 3 AM. The concept needs to say: (a) per-server state (last push and last pull attempt *and* success, cursor, instance, counts, last error with its HTTP status and time) is kept in the database, and which table or `meta` keys hold it; (b) a repeated identical error is logged once, with a count, until it changes; (c) the log scope names the serverId, never the URL with credentials or the token. `redact.ts` names `team-token`, but the scope is not redacted.
- F-6 · Major · pull, "one pull per server stays open with `wait`" · The server answers an *empty page at once* without an error when the device already holds `heldPullsPerDevice` (8) pulls (`src/team/feed.ts:198-199`), and also when its signal is closed (`feed.ts:206`). A client that re-pulls as soon as it gets an empty answer goes into a hot loop, with no error in the log and nothing on the status line. Two sync processes on one device token, or stale connections, cause this. The concept needs a rule (an empty page that came back well before `wait` means back off) and a counter that `status` can show.
- F-7 · Major · pull, failure paths · There is no client-side timeout. A pull that gets no answer (a half-open TCP connection behind a proxy) leaves "last pull" frozen with no error recorded. The concept should set a client deadline of `wait` plus a margin, record "pull started" separately from "pull answered", and show both. The server sends `x-request-id` on every answer (`src/team/routes.ts:496-497, 537`) and accepts one from the client. The concept does not say that the client sends or records one. Storing the last request id with the last error is how a person matches their status line to the operator's JSON log (`src/team/log.ts` `RequestLine`). The concept should also say that `Retry-After` on a 429 (`routes.ts:527-528`) drives the `rate` backoff, and show the next retry time.
- F-8 · Major · "Success: ... zero items leave outside the policy" · Afterwards, this cannot be shown from the store. The ledger columns read by `ledgerRecords` (`src/sharing/report.ts:425-445`) are uid, destination, direction, version, hash and withdrawn_at. They hold no policy epoch and no `decide` reason. A `sent` row does not say which ruling let it out, and `share explain` (`src/cli/commands/share.ts:267-291`) only shows today's ruling against `TEAM_DESTINATION`. If a `sent` row records the epoch and reason, and `explain` gains `--server` plus the ledger history (sent at, revision, refused with reason, purged), the question "why did this leave, or why is it stuck" gets an answer. Without that, the success metric cannot be checked.
- F-9 · Major · "Success: a change reaches another connected machine in under 5 s" · Nothing measures it, and nothing in the code tells the sync that something changed locally. Knowledge files change in other processes: MCP tools, the CLI, hand edits indexed only by the drain's `refreshStale` (at most 3 repositories) or by a tool call. Memories change in `distill`. The client has no change signal; the one in `feed.ts` is the server's, in-process only. Say how the sync learns of a change (by polling what, how often) and record per item the delay between the local change and `applied`, and between the feed item's `at` and the local apply. Otherwise "it's slow" cannot be investigated, and the 5 s figure is untested. A hand-edited file reaches nobody until something refreshes the index. Say whether the sync does that refresh.
- F-10 · Major · "applies received entries into the local knowledge repositories" · Several things are unspecified. `commitChange` (`repo.ts:1134-1179`) takes a `Writer` and a commit message, and the concept names neither for a received write. `git log` on an entry is the first debugging tool, and it should show the server, the member and the revision. A received write needs the repository lease, which fails with `locked` while a person's write runs (`repo.ts:1396-1429`). The concept does not say that the cursor stops at an unapplied item, or how many items are held back. Without that, `status` shows a cursor that moved past items that were never applied.
- F-11 · Major · `status` / `doctor` lines · The concept says only "status". `formatSharing` (`src/status/report.ts:279-297`) prints a single line read against `TEAM_DESTINATION`. The doctor `sharing` check (`src/doctor/checks.ts:917-944`) states "sharing chosen with no team server configured is no warning". With servers in place, that sentence and both readers have to change. The concept needs to name the per-server lines and the doctor checks: token file not 0600, a non-https URL, a 409 contract stop, a 401 that needs a new invitation, a sync lease held by a dead owner, sharing chosen but no sync run for N hours, open sync-conflict proposals. `doctor` must not touch the network, or the concept must say so if it does. There is also no viewer view for knowledge ("no view yet", CLAUDE.md), so the Servers card is the only place in the viewer where a conflict or a stopped server can appear. Say that it shows them.
- F-12 · Major · hook path · The hook tests depend on `WIZARDINGCODE_MEM_DISTILL=off` and `WIZARDINGCODE_MEM_UI_AUTO_OPEN=off` (CLAUDE.md conventions) to keep hooks from starting background work. A new spawn needs its own off switch, or a stated reuse of one of those, or tests will start real sync processes. The hook should also skip the spawn on a machine with no server and while the sync lease is held, as `handle.ts:189` does with `drainActive`. Otherwise every session start pays for a spawn, and `hook_runs.ms` and the perf budgets in the acceptance test take the cost.
- F-13 · Nit · received memories `judge = 'team:<serverId>'` · `judgeReport` (`src/status/report.ts:141-162`) groups the project's memories by `judge`, so `status` will print a long `team:<uuid>` key for each server. Say whether status shows the server's alias instead.
- F-14 · Nit · "one per data directory by a lease ... like `ui --auto`" · `ui --auto` takes no meta lease. It claims `ui.json` at the brand level with `wx` (`src/ui/state.ts:63-68`, `src/ui/server.ts:755-763`). The comparison holds only for "becomes or finds the running one", and that should be said.
