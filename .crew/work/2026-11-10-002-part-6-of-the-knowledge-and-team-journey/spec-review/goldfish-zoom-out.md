## Findings
- F-1 · Blocker · spec.md line 85 ("Where things live", the retrieval's SQL) with plan.md line 104 (task 15) against spec.md line 237 (AC-53) and line 170 · AC-53 says an unbound alias's copies are hidden from "search, `knowledge_get`, the floor and the brief", and spec line 170 says the hiding works through a `sharing_levels` row above Nothing for the alias. But `brief.ts`/`notes.ts` may only read `sharing_servers`, `sharing_muted_members` and `sharing_received_memories` (spec line 85, plan task 13), and the boundary test in plan task 15 lets only `src/sharing/` and `index-store.ts` name `sharing_levels` in SQL. Built as written, either the brief shows an unbound alias's received memories until the reconcile runs, or the boundary test fails. The fix is to add `sharing_levels` to the retrieval's allowed tables in both documents and in the boundary test, or to drop the brief from that AC clause and say why. A smaller related mismatch: spec line 84 lists `contribute.ts` as reading `sharing_levels`, and plan task 15 allows only `index-store.ts`.
- F-2 · Major · spec.md "Restore of the client store", lines 186-199; plan.md task 17, line 109 · The restore after the rename relies on a second recovery mechanism: the `sharing.carry_owed` and `sharing.carry_done` marks, `completeOwedCarry` run again at the sync's start (which is why `src/sync/run.ts` imports `src/backup/`), the sweep and pull held while a carry is owed, a `doctor` check for a replaced file newer than the done mark, and the clearing of stale marks inside the copy. All of it exists only because the carry runs after the rename. `restoreBackup` (/Users/andreagroferreira/AIProjects/ai-mem/.crew/worktrees/ai-mem-2026-11-08-001-j-knowledge-base-and-team-collab/src/backup/backup.ts lines 159-185) already edits the raw copy before the rename while the live store is frozen (`resetSharingInCopy`). The structural fix is to also upgrade the copy's module schema and write the carried rows into the raw copy there, so the rename is the one commit point and a failure changes nothing. That would remove the owed and done marks, the carry at the sync's start, the `doctor` replaced-file check, the `run.ts`→`backup/` import and about half of AC-61. The obstacle is that `openDb`'s upgrade makes its `VACUUM INTO` copy; that is a reason to call the module upgrade without the copy, not a reason to keep the crash-recovery machinery. If the design keeps the after-rename carry, the spec should say why the before-rename option was rejected; it is not under Alternatives.
- F-3 · Major · spec.md lines 82-93 ("Where things live") and lines 113-115 ("The policy per server"); plan.md lines 9-71 and task 15 · The spec's architecture sections hold code-level detail: function signatures, `OR direction = 'received'` clauses, `Bun.semver.order`, the byte-order tie-break "since the table is `WITHOUT ROWID`", the full column list of `sharing_servers`, which file may name which table in SQL, and test-file names. The plan restates the same detail with its own SQL, and the two are on different revisions (spec 13, plan 12). F-1 is one disagreement this has already produced. The risk: a builder takes the spec's wording where the plan says otherwise, and the next reviewer cannot tell which document is the authority. The spec should keep the data flow, the ownership of each table and the invariants, and the plan should be the only home for column lists, function lists and the boundary test's table-by-file matrix.

- F-6 · Nit · spec.md line 147 and line 225 (alias groups) · Cursor groups keyed by the hash of their sorted aliases exist only for a person who binds more than 100 projects to one server, and no goal or journey states that need. Since a refusal at the 101st binding was weighed and rejected, the spec should state the re-snapshot cost of a bind in "The inbound side", so the trade-off is visible.
- F-7 · Nit · spec.md line 99 (the token file) · The text says `servers.json` is "read and written by the sync process", but no step of the sync process writes a token: only `add`, `rejoin` and `remove`, from the CLI and the viewer, do.
