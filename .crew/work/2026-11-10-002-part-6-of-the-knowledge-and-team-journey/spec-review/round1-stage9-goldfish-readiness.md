## Findings
- F-1 · Blocker · plan.md line 91 (task 10, "`entryBytes` hash") with line 77 (task 5) · `entryBytes` is exported from `src/team/validate.ts` (line 64), but the boundary test the plan pins says `src/sync/` imports nothing of `src/team/` except `contract.ts`, so `outbound.ts` cannot import it as written. The plan has to say where the function goes (moved into `src/team/contract.ts`, moved into `src/sharing/`, or written again in `src/sync/` and tested against the server's) and list that file as Create or Modify.
- F-2 · Major · plan.md line 108 (task 18, "Modify ... `src/sync/state.ts`") · No earlier task creates `src/sync/state.ts`, so "Modify" is wrong. The spec (line 80) puts the per-server state rows in `state.ts`, but task 3 puts `updateState` in `servers.ts`. The plan must mark `state.ts` as Create and say which file owns the state-row writes and which owns the reads, or an engineer will split them across two files at random.
- F-3 · Major · plan.md line 74 (task 2, `stopSync(db, who, now, waitMs)`) · The signature says neither whether the function is synchronous or async nor how it waits: no clock or timers parameter, yet the test runs it "under the fake clock". Its callers differ today: `compact` (src/store/compact.ts:70) is synchronous, while `moveStore` and `restoreBackup` are async. The plan must give the exact signature (async, with an injected clock and timers, and the poll interval) and state the change task 17 makes to `compact`'s signature and its callers.
- F-4 · Major · plan.md line 103 (task 16, "the take-over of an older holder") and line 74 (task 2) · Today `claimLease` (src/store/meta.ts:73) refuses whenever a live holder exists. No task says which function compares versions, how two versions are compared (semver, or string order), or where the running binary's version comes from. An engineer would either never take over or take over on any difference. The plan must name the function, its file and its comparison rule.
- F-5 · Major · plan.md lines 91, 97, 103 (`sweep(ctx, server)`, `pullOnce(ctx, ...)`, `runSync(ctx, ...)`) and line 3 · The `ctx` type every sync function takes is never defined in `src/`. Only the test helper is described. The plan must name the type, its file and its fields (db, dataDir, env, fetch, clock, timers, pid, version, and whatever else the code needs), otherwise each task invents its own shape.
- F-6 · Major · plan.md line 98 (task 14) and line 73 (task 1, "the column names of `sharing_servers` and `sharing_muted_members` are pinned") · To leave out a muted member's received memories, the retrieval must know which member sent each memory. That is only in `sharing_received_memories.member_id`, since `memories` has no member column. So `src/retrieve/` reads a third sharing table by its own SQL, and neither the plan nor the pin test covers it. The plan must state the join and add `sharing_received_memories` to the pinned columns.
- F-7 · Major · plan.md (no task) vs spec.md line 142 ("the session-start line of the knowledge module count the open rows") · No task modifies the knowledge module's session-start line to count open `sharing_conflicts` rows, and no test case covers it. The module may not import `src/sharing/` or `src/sync/`, so this would be another own-SQL read of an unpinned table. The plan must add the file, the query and the pin.
- F-8 · Major · plan.md line 26 (`sharing_pending_rows` schema) and line 97 (task 13) · A pending row stores only seq, uid, kind, reason, tries and at, with no payload. The spec says it "is retried once an hour", but the pull API only reads forward from a cursor, so the row cannot be fetched again by its seq. The plan must decide how a retry gets the row's content (store the payload, or re-read from some cursor), and add the hourly retry and the "dropped by a later row of the same uid" rule to task 13 with test cases. Neither appears today.
- F-9 · Major · plan.md line 83 (task 8, "`add` as the spec states", `adoptTeamRows(db, serverId, now)`) · The spec's yes transaction also copies the env file's roots and areas into the server's lists and re-sets the `sharing.settings_seen` baseline. Neither is assigned to a function. `adoptTeamRows` has no dataDir or env parameter to read the env file. The plan must give the signature and list every write in that one transaction.
- F-10 · Major · plan.md line 87 (task 9, `loadPolicy(db, dataDir, env, serverId?)`) · The plan does not say what `loadPolicy` returns when servers are confirmed but no `serverId` is passed: which roots, areas and epoch. Today's callers (`ui/api.ts`, `status`, `doctor`, `previewLevel`) call it without one. The plan must state the rule, or require the argument once a server exists, and name each caller's new argument.
- F-11 · Major · plan.md (no task) vs spec.md line 150 (`logError` under `sync.<serverId>.<operation>`, one line per distinct error with a count, `last_error` through `redact`) · No task builds the error logging, the per-error dedupe with its count, or the redaction of `last_error`, and no test asserts that a token, a code or a payload never reaches the log. The plan must name the file, the dedupe state and a test.
- F-12 · Major · plan.md line 117 (task 21) vs spec.md line 189 (AC-27, "the one-time copy sharing v1 to v2 takes on the first opener is read beside the budgets") · No task measures the upgrade copy's time or says where the figure is recorded. The plan must name the measurement (file, store size, where the number goes) or drop the clause from the AC.
- F-13 · Major · plan.md line 96 (task 12) · `received.ts` must use `reachedByFolders` (src/modules/knowledge/repo.ts:1012), which is not exported. Task 4's `applyRevision` in `store.ts` runs "under `underOwnLease`" (repo.ts:1437), which is also private to `repo.ts`. The plan must say which functions become exported, or where the new code lives, so the boundary and the file list stay true.
- F-14 · Nit · plan.md line 96 (task 12) · The signatures `reindexReceived(dataDir)`, `deleteServerReceived(serverId)` and `reconcileReceived(serverId)` leave out the db, dataDir or both that each one clearly needs. Write the full parameter lists.
- F-15 · Nit · plan.md line 73 (task 1, "a `run` made to fail (an injected error)") · The plan does not name the seam that injects the error into sharing v2's `run` (an exported hook, an env switch, a table that makes the statement fail). Name it.
- F-16 · Nit · plan.md line 77 (task 5) · A task listed under Phase A but written in Phase F reads out of order. Move it to Phase F beside task 16.
- F-17 · Nit · plan.md line 3 (`Create tests/helpers/sync.ts`) · The helper is created in the preamble, not in a task or phase, yet task 2's test already needs its fake clock. Put the creation in the first task that uses it.
- F-18 · Nit · plan.md line 82 (task 7, "push, withdraw and pull") · The client lists no `withdraw` method. The server has no client withdraw route, only `POST /v1/push` and the admin `.../withdraw`, so a withdraw is presumably a push item. Say so, so nobody adds a method or calls the admin route.
