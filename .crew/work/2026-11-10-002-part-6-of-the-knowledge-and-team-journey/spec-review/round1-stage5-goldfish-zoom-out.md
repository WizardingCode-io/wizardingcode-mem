## Findings
- F-1 · Major · spec.md:146 "Restore of the client store" (and plan.md:107 task 17, AC-48 at spec.md:184) · The restore copies eight tables from the live store into the restored copy, with a crash-recovery layer on top (`sharing.carry_owed`, `sharing.carry_done`, `completeOwedCarry` called from both the restore and the sync's start, a doctor check for `<db>.replaced-*` files newer than the done mark, stale marks cleared in the raw copy). This is the heaviest mechanism in the part, and it serves a rare operation. Two things the spec already builds cover most of it. First, the snapshot comparison at spec.md:130 reconciles every `sent` and `received` row against the server, and the restore already sets `snapshot_due`. Second, conflict texts already survive a restore: proposals live in the git repository under `proposals/` (src/modules/knowledge/repo.ts:57), which the store restore does not touch. A reader will build and test the whole owed-carry state machine. What must change: carry only what the server cannot give back (the `sharing_servers` rows with their cursors, and the mutes), let the snapshot rebuild the ledger, and let refusals be learned again from the server. Otherwise the spec must state which loss forces the full eight-table carry, and why that loss justifies the owed and done marks.
- F-2 · Major · spec.md:97 "share server remove" (plan.md:99 task 15, AC-44) · `remove` brings in a second way to stop the sync: a `removing` value of `stopped` that the loop checks before every page, chunk and file write, a `sync.busy:<serverId>` meta marker, and a 30 s wait. The spec already has a stop mechanism at spec.md:109 (the `sync.stop` flag, `stopSync` in plan task 2), and restore, move and compact already use it the same way. Two mechanisms mean two sets of checks in the loop and two kinds of race to test. What must change: `remove` calls `stopSync`, does the removal, and lets the next spawn restart the sync. Otherwise the spec must say why stopping every server's loop for a CLI removal is not acceptable.
- F-3 · Major · spec.md:76-146 "Proposed architecture" (and the whole of plan.md) · The architecture section is written at implementation altitude. It lists table columns, meta keys and function names, sets out per-statement transaction order and crash windows, and has paragraphs of over 500 words (spec.md:123, :146). The plan repeats most of this word for word, and the two documents are at different revisions (spec "revision 5 … this revision answers the seventh", plan "Revision 7"). A competent reader cannot separate the decisions (D-1 to D-9, the boundaries, the data flow) from the mechanics, and will miss where the spec and the plan disagree after the next round. What must change: the spec keeps the components, their boundaries, the data flow and the invariants (nothing leaves before the yes, received items stay apart, the hook never touches the network, text is never lost). Schema columns, meta keys, crash ordering and function names move to the plan or the ADR, stated once.
- F-4 · Nit · spec.md:130 "three consecutive failures open a breaker that halves the retry rate" · src/judge/breaker.ts already has a meta-backed `Breaker` (three failures to open, backoff doubling, success resets). Name it for reuse (generalising its meta key and `ErrorKind`), or say why the sync's in-process loop needs a different one.
- F-5 · Nit · spec.md:80 and :134 `agentName` in a new `src/core/agent-name.ts` · src/modules/knowledge/store.ts:740 already defines the same control-character pattern (`CONTROL = /[\x00-\x1f\x7f]/g`). The new leaf should own that pattern and the store should import it, so there is one definition of "control character" and not two.
- F-6 · Nit · spec.md:89 servers.json "the temporary file is opened at 0600, then renamed" (plan.md:75 task 3) · The codebase already has 0600 temp-then-rename writers: `writeFileAtomic` (src/modules/knowledge/repo.ts:330, `mode: 0o600, flag: "wx"`) and the env-file writer (src/settings/env-file.ts:82). Name the one to reuse or move into a shared place instead of writing a third.
- F-7 · Nit · spec.md:142 `sharing_conflicts` keeps `local_text` · The proposal file in the repository already holds the local text, and proposals are never deleted (they move to `proposals/decided/`). Copying the text into the database duplicates it, and that duplicate is part of what the restore carry (F-1) exists to protect. Keeping only the proposal id and the hashes would be enough, unless a case is named where the proposal file is lost and the database row is not.
- F-8 · Nit · spec.md:123 alias groups "of at most 100 aliases, each with its own cursor keyed by the hash of its sorted aliases" · Grouping is needed only when more than 100 projects are bound to one server (ADR 0026 caps a pull at 100 aliases). No goal states that case, and ADR 0026 D-21 says the author runs one server per client. A single cursor per server, re-snapshotted when the alias set changes, with a refusal at the 101st binding, would be simpler. Otherwise the spec should name the requirement for more than 100.
- F-9 · Nit · spec.md:80 the `src/sync/ledger.ts` bullet · Ownership is defined by layered exceptions ("every read of them but the two read-only reads … and but the restore's carry, … the one import of `src/backup/` from `src/sync/`"). This is hard to read and points to the boundary being drawn around F-1's carry. State the rule in one sentence and put the exceptions in the boundary test.
- F-10 · Nit · spec.md:3 the header · It says "Revision 5", then lists revisions 6, 7 and 8, then "this revision answers the seventh". The document's own revision number is wrong, and the round history belongs in the conclave records, not the spec's opening paragraph.
- F-11 · Nit · plan.md:77 task 5 · The task sits under Phase A but says "Written in phase F as the red of task 16". Move it to Phase F, where it runs.
