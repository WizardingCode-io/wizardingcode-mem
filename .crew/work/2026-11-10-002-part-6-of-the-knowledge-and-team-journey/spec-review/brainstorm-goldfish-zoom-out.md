## Findings
Lens: contrarian. Does this need to exist now? Yes. Parts 4 and 5 deliver nothing until a client sends, ADR 0026 D-10 rules out syncing through the mirror's git repositories, and no library speaks this API. Multiple servers per person was ruled by the author (ADR 0026 D-21), so it is a requirement, not speculation. The risks are in how the concept handles lifetime, change detection and the ADR obligations it does not mention.

- F-1 · Major · "alive while a session or the viewer is active, exiting after a quiet quarter hour" · Only the session-start hook starts the sync. If a long session has 15 quiet minutes, the process exits and nothing restarts it until the next session starts, so team changes stop arriving in the middle of the session. That breaks the "< 5 s" success criterion. "Quiet" is also undefined: an open `wait` pull is never quiet, and if quiet means "no sessions", ended_at is not set reliably when an agent crashes. A builder will pick one reading and get one of two bugs: the process never exits, or it dies under a live session. Reuse what already exists rather than inventing a liveness signal: `sessions.last_seen_at` / `ended_at` (src/store/sessions.ts) for sessions, and `readUiState` + `probeUi` (src/ui/state.ts, used by `ui --auto`) for the viewer. State which event restarts the sync during a session. A bare `spawnDetached("sync","--auto")` on the prompt hook is cheap because the lease refuses a second process, but it puts a spawn on that hook path and has to be weighed against the "never on a hook path" constraint.
- F-2 · Major · "pushes … right after each local change" · The concept never says how a separate process learns about a change. Memories are written by `distill`, entries by MCP tools, the CLI, the viewer, or a person editing the Markdown by hand. A builder may invent IPC, a socket or an fs watcher. The simpler route is to poll what exists: `stamp(db)` in src/embed/vectors.ts (`PRAGMA data_version` + `total_changes()`) costs nothing when nothing changed, and `refreshStale` / `ensureFresh` already find repositories that differ from the disk. Name the poll interval so the 5 s budget adds up: poll interval + push + the server waking the other machine's held pull.
- F-3 · Major · the concept as a whole versus ADR 0025/0026 "What parts … must do" · The concept leaves out several obligations those ADRs give part 6, and a builder working from the concept would miss them:
  - dedupe copied stores' memories by content (ADR 0026, which also lists it as a known limit until part 6 does it);
  - re-read the policy at every batch, run `reconcileSettings` / `reconcileLevels`, and stop when the epoch moves;
  - read an entry only after `ensureFresh` and a clean `git status` for its path;
  - compute withdrawals from the ledger's uids, never from the live binding;
  - narrow `history replace-imports` before the first memory is received;
  - record the local hash beside the server's (the ledger has one `hash` column today).

  The brief carries some of these but not all.
- F-4 · Major · "keys the sharing policy … by serverId … roots and areas per server" against "`decide` is unchanged in shape" · `SharingPolicy` holds one `roots` / `areas` set, and `DESTINATIONS` is a constant `Set(["team"])` in src/sharing/levels.ts. Per-server roots and areas therefore need either a policy reshaped to hold lists per destination (which touches `decide`'s inputs and the epoch), or one policy loaded per server. The simpler choice keeps `decide`, `SharingPolicy` and the epoch exactly as they are: `loadPolicy(db, dataDir, env, serverId)` returns that server's policy, and `DESTINATIONS` becomes the server list. Leaving this open invites a builder to put a map keyed by destination inside `SharingPolicy`. Separately, env keys named after an opaque serverId (`…_SHARE_ROOTS_<id>`) make hand-edit detection and the env file hard for a person to read. Decide that before the migration is written.
- F-5 · Major · "a proposal of kind sync conflict" · A proposal's `kind` is the entry's kind, checked against `KINDS` (`knowledge|strategy|persona|pattern`, src/modules/knowledge/entry.ts:9). Taken literally, `kind: sync-conflict` makes the proposal a `problem` and it reads as a broken file. The existing proposal fields already express a conflict: `proposed_by: sync:<serverId>` (or `team:<serverId>`), `base_version` / `base_hash` set to the server's revision, and `on_behalf_of` the person. That needs no new frontmatter key and no change to `PROPOSAL_KEYS`.

Lens: code minimisation, what already exists.

- F-6 · Major · "the first run … sends everything the policy allows" and the per-change push · The candidate enumeration exists and should not be rewritten: `entryItems`, `memoryItems`, `withHashes` (memory hashes computed in chunks of 500, only for items with a record), `ledgerRecords` (one scan, no parameter lists, already safe at 90,000 memories) and `wouldLeave` in src/sharing/report.ts. The same goes for `memoryHash` (src/sharing/hash.ts) and `redactForSend` (src/sharing/edge.ts). The first run and the incremental push are the same loop over these functions with a different starting set.
- F-7 · Major · "one per data directory by a lease" · Reuse `claimLease` / `releaseLease` / `leaseActive` from src/store/meta.ts, the client store's meta leases. Do not import src/team/lease.ts, which belongs to the server's store. Add the sync lease to `anyLeaseActive` there: otherwise a restore or a store move can run in the middle of a push, which is the "sent under the old generation" case the brief forbids.
- F-8 · Nit · wire types · `CONTRACT` and `CONTRACT_FINGERPRINT` live in src/team/contract.ts, which imports only `node:crypto` and src/sharing/types.ts, so the client can share it. `PushResult` and `PullPage` live in src/team/push.ts and src/team/feed.ts, which pull in the server's store. Move the result shapes into contract.ts and import them on both sides rather than redeclaring them in the client. The fingerprint test then pins the client's view too.
- F-9 · Nit · "`share server add | remove | list | status`" · `share status` already exists (src/cli/commands/share.ts, `formatShareStatus`). Showing per-server sync state there, one line per server, avoids a second status command that says half the same things. The other server subcommands are justified.
- F-10 · Nit · tests · tests/helpers/team.ts already gives an in-process server with an injected clock and timers. Client integration tests against it need no mock HTTP layer.
- F-11 · Nit · altitude · The concept carries implementation constants (batches of 200, a quarter hour, `judge = team:<serverId>`) next to architecture choices. The constants already in ADR 0025/0026 (200 items, the limits published in `/v1/me`) should be cited from there, not restated as new decisions in ADR 0027.
