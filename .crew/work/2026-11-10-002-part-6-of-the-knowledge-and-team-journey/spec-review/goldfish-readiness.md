Fix: either move `spawn.ts`, the start steps and the tick (or a stated stub) ahead of phase B, or move each of those test cases to phase F, and say what the task-2 helper's `runSync` does before task 16.
- F-2 · Blocker · plan.md:105 (task 16) against plan.md:109 (task 17) · `run.ts` (task 16, phase F) calls `completeOwedCarry` of `src/backup/carry.ts`, but that file is created in task 17, phase G. - F-3 · Major · plan.md:104 (task 15) · The boundary test is told to assert "`src/sync/run.ts` is the only importer of `src/backup/`". That is false for the tree as it stands: `src/cli/commands/backup.ts`, `src/ui/server.ts`, `src/doctor/checks.ts` and `src/cli/commands/hook.ts` all import `src/backup/` today. An engineer who writes the assertion as stated gets a red they cannot fix. Fix: limit the rule to importers under `src/sync/` (as the spec means), and say whether `hook.ts`'s existing import of `src/backup/schedule.ts` is allowed. `backup.ts` will import `carry.ts`, so "`carry.ts` not reachable from hook.ts" needs the graph it is checked over stated.
- F-4 · Major · plan.md:78 (task 4) and plan.md:93 (task 10) · `propose` in `src/modules/knowledge/store.ts` is private, typed `AgentWriter`, takes a structured `EntryChange` and is reachable only through `writeEntry`, which task 4 makes throw on the sync writer. The plan never says how `src/sync/conflicts.ts` creates the conflict proposal. Missing: whether `propose` is exported or a new exported function wraps it; its signature with the sync writer; how the local file's text becomes an `EntryChange` (parse the frontmatter, keep `pinned` or not); whether `{ force }` skips both quotas (`OPEN_PER_TARGET` and `OPEN_PER_REPO`); and how `base_version`/`base_hash` are set to the post-apply file. `applyRevision`'s return value is not given either (the new version and hash that conflicts.ts writes into the `sent` row's `local_hash` and the proposal's base).

As written, the implementer designs the API.
