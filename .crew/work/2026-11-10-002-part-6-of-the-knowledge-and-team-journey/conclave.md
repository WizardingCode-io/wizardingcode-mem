## Assumed by good practice

- One side is the truth for each field (sync): a shared or project entry's current text is the server's once sent, and the client sends on the base it last saw, so a mismatch is `stale` and never a silent overwrite; a memory's truth is its own device; an echo (the server's hash equal to the ledger's) is skipped. AC-18, AC-30, AC-20.
- A ledger line per item and direction, idempotent runs, the first run bounded by the server's limits and preceded by the person's yes at the join (sync). AC-15, AC-18.
- The token through one file at mode 0600, revoked on the server's side and forgotten on removal; a 401 stops the server with the remedy; the check in one place, `src/sync/client.ts`; no token, code or payload in any log line (auth). AC-15, AC-17, AC-31, AC-23, AC-25.
- Sharing v2 and knowledge v8 are add-only with defaults; the core runner copies the store before the upgrade; the `team` rows move inside the add's transaction; a restore brings back the sync's rows the spec names and nothing it does not (migration-or-restore). AC-15, AC-32, AC-33.
- `remove` deletes received copies (copies, not the person's data), forgets the token, keeps the person's own items, refuses with open conflicts without `--yes`, and writes a `sharing_changes` row (deletion). AC-25.
- Every state the viewer's diff adds is enumerated on AC-24 and captured; labels tied to inputs; keyboard and focus; the widths 360, 768 and 1280; the dark scheme; no motion; copy in English; no call the page does not need (screen). AC-24.
