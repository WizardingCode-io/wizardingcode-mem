## Returns
- R-1 · .crew/work/2026-11-10-002-part-6-of-the-knowledge-and-team-journey/spec.md:88 · Something can leave before the person says yes. The `sharing_servers` row, and on the first server the move of the `team` levels, is written before the counts are shown and the yes is asked. Meanwhile any session-start or prompt hook runs `startSync`, which counts `WHERE stopped IS NULL` (spec.md:100). It sees the new row, spawns `sync --auto`, and that sweeps the moved levels before the yes. The same holds between the two calls of `POST /api/servers` (spec.md:141). This breaks CUJ 1, "nothing leaves before the yes" (spec.md:63). What must change: write the row in a state the spawn and the sweep skip (for example `stopped = 'pending'` or a null `confirmed_at`), and leave it only on the yes, or move the levels only after the yes. Say that a no or an interrupted add leaves the row in that state. Add an AC-1 case and a test in plan.md:74 (task 7): a sync running during the prompt sends nothing.
- R-2 · .crew/work/2026-11-10-002-part-6-of-the-knowledge-and-team-journey/spec.md:114 (also spec.md:129) · A teammate's revision of the person's own entry gets past D-6. On an upsert, and on a conflict, the server's bytes are written into the person's own file. `pinned` is a frontmatter field (src/modules/knowledge/entry.ts:321, :371, :397), and `frontmatter` travels whole in the payload (src/sharing/types.ts:211). So any member, or a stolen token, can set `pinned: true` on an entry this person shared. The text then reaches every session start as the person's own, unmarked, by way of `pinnedEntries`. D-6 says "never pinned, marked". What must change: the spec states that a received revision never changes the local pin (the local `pinned` value is kept, or the pin lives outside the file), and says how a teammate's text applied to an own file is marked to the agents (or held back) until the person has seen it. Add the cases to AC-5 and AC-6: a teammate revision that adds `pinned: true` is not pinned, and an applied revision carries the marker.
- R-3 · .crew/work/2026-11-10-002-part-6-of-the-knowledge-and-team-journey/spec.md:112 · Project names leak to every server. A pull to each server names the `remote:` aliases of all this machine's enabled projects. Those include projects at Nothing and projects bound to another server, so in CUJ 5 (spec.md:67) client A's repository names reach client B's server. They travel in the query string, which ends up in proxy and server logs (ADR 0026 "Limits and logs", docs/adr/0026-team-server.md:82). This outflow is not on ADR 0025's list of what leaves (docs/adr/0025-sharing-policy.md:134), and D-5 only covers what arrives ("as soon as ... the server knows its alias"). What must change: narrow the aliases a pull names to one server. At minimum, exclude projects bound to another server. Better, name only projects the person opted in to receive for that server. If not, record the outflow as the person's ruling and state it in ADR 0027's "what leaves". Add an AC-6 case: a project bound to server A is never named in server B's pull.
- R-4 · .crew/work/2026-11-10-002-part-6-of-the-knowledge-and-team-journey/spec.md:119 · A disabled member gets 403 `member disabled`, not 401 (src/team/auth.ts:30). The spec's 401 rule promises "revoked or the member disabled", but it has no 403 rule, and the plan's typed failures in plan.md:73 (task 6) have no 403. So a disabled member's sync falls into an unnamed path and keeps calling the server. What must change: add 403 `member disabled` as a stop state with its remedy, plus a 403 `admin only` rule for the admin calls if any are made. Test both in AC-7 and in the client test of task 6.
- R-5 · .crew/work/2026-11-10-002-part-6-of-the-knowledge-and-team-journey/spec.md:119 · The `unauthorized` and `rejoin` remedies cannot be followed. They say "`share server add` again", but `add` refuses a `serverId` already listed (spec.md:88). The only way round today is `remove`, which deletes the ledger and the received copies, and whose `--withdraw` cannot run on a revoked token. What must change: define a re-join on a stopped server with the same `serverId`. It replaces the device and the token (the old one forgotten) and keeps the ledger. Withdrawals still work: ADR 0026 lets another device of the same member withdraw a memory (docs/adr/0026-team-server.md:60). Add an AC-1 or AC-7 case: revoke, join again, the sync resumes.
- R-6 · .crew/work/2026-11-10-002-part-6-of-the-knowledge-and-team-journey/spec.md:84 · Two claims about the token file are wrong. (a) "Not under the store dir": by default the store dir is the data dir (src/util/paths.ts:38), so `servers.json` sits beside `memory.db`. Copying that folder to a new laptop gives two machines one device, which is the premise ADR 0025 relies on (readiness F-1). The real guarantee is "not inside the database file". (b) "Read by the sync process and the CLI only": the viewer's `POST /api/servers` joins and `DELETE /api/servers/<id>` withdraws (spec.md:141), so the viewer writes and reads the file too. What must change: correct both sentences. State the copied-data-directory case as a known limit, or detect it. Name the viewer as a holder of the file, and state that no route (`GET /api/servers`, `GET /api/sync`, the `POST` answers) and no CLI output (`share server list`, `status --json`) returns the token. Pin that in AC-1 and AC-10.
- R-7 · .crew/work/2026-11-10-002-part-6-of-the-knowledge-and-team-journey/spec.md:88 (and plan.md:73) · The https rule covers only the stored URL. The client is a `fetch` that follows redirects by default, so a 3xx from the server or from a proxy in front of it can send the request, with its `Authorization: Bearer`, to an `http://` or foreign origin. "Loopback" is also not defined: `localhost` resolves through the resolver, and `localhost.example.com` matches a loose test. What must change: every request uses `redirect: "error"` (or `manual`, with a 3xx treated as a failure). Loopback is the literal set `127.0.0.0/8`, `::1` and `localhost` only. Add test cases to task 6: a redirect from the server never reaches the target, and `http://localhost.example.com` is refused.
- R-8 · .crew/work/2026-11-10-002-part-6-of-the-knowledge-and-team-journey/spec.md:114 · The received store builds file paths from values the server supplies: `serverId` (from the join answer), the member id, the slug and the alias. The client writes files from a remote party, but the spec does not say these are checked before they become path components. It also does not say that `received/<serverId>/` must be a real folder, not a link. A server or a member able to put `..` or `/` in one of them writes outside `knowledge/received/`. What must change: `receivedPath` (plan.md:87, task 11) checks each component against a strict grammar (the server's own id and hex formats, the entry module's slug rule) and goes through real folders only (the store's `reachedByFolders` rule). Before the agents see them, the member name and the server name rendered in `from <member> via <server>` and `(team: <name>)` are stripped of newlines and control characters and bounded in length. Add test cases to AC-6.
## Notes
- What holds: the token is kept out of the database, the backup and the logs (D-7, spec.md:84). The `team-token` and `team-invitation` redaction rules sit ahead of the header rules (src/core/redact.ts:60-61), so a token or a code that reaches a log line is masked.
- What holds: every text that leaves passes the edge. Frontmatter and body are each put through `redactForSend` (src/sharing/edge.ts:12), and the hash is recomputed over the redacted bytes (spec.md:106), as ADR 0026's part 6 list asks (docs/adr/0026-team-server.md:110).
- What holds: received items never travel on. Received memories are `imported` rows, and `decide` refuses `imported` (src/sharing/policy.ts:358). Received entries live in `knowledge_received`, which `entryItems` does not read. `received-elsewhere` stays in place (src/sharing/policy.ts:392).
- What holds: the 401, 409 and 410 bodies carry `serverId` and `instance` (src/team/routes.ts:37, :158), so the spec's split between `unauthorized` and `rejoin` (spec.md:119) rests on real fields. The join's answer carries the token, and the server requires https behind the proxy (docs/adr/0026-team-server.md:94).
- What holds: the restore carries the server rows, and the token file stays outside it (spec.md:133). `remove` forgets the token (spec.md:90). The conclave's O-2 (the code in shell history) is answered by the prompt that never echoes.
- Preference, not a return: `remove` leaves the device live on the server, since only an admin can revoke it. The command's output could say "ask an admin to revoke device <alias>".
- Preference, not a return: received memories enter the person's backups (folder or bucket), which a server purge never reaches. The next snapshot after a restore drops them again (spec.md:119), but ADR 0027 should state that the backup files keep them.
- Preference, not a return: create the token file's temporary file at 0600 when it is opened (not chmod after), store `last_error` through `redact`, and have `doctor` warn when `NODE_TLS_REJECT_UNAUTHORIZED=0` is set for the sync.
