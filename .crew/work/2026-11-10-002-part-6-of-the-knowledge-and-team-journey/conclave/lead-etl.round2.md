## Returns
- R-1 · .crew/work/2026-11-10-002-part-6-of-the-knowledge-and-team-journey/spec.md:88 · The spec says the first add moves "every … `sharing_changes` row of destination `team`", but `sharing_changes` has no destination column (src/sharing/migrations/0001_sharing_policy.sql:41-50; `logChange` in src/sharing/store.ts:98-113 writes `at, source, what, old, new`). Per-server lists (`setServerLists`, plan.md:78) and per-server levels then record changes that do not say which server they were for. Two ways to fix it. Either add `ALTER TABLE sharing_changes ADD COLUMN destination TEXT NOT NULL DEFAULT ''` to plan.md:7-42 and move it with the rows, or name the `what` grammar per server (`project:<id>@<serverId>`, `roots@<serverId>`, `areas@<serverId>`, `server:<id>`) and remove `sharing_changes` from the move sentence. Then pin it with a test in sync-schema or sharing-per-server.
- R-2 · .crew/work/2026-11-10-002-part-6-of-the-knowledge-and-team-journey/spec.md:183 · The downgrade claim does not hold. (a) An older binary's `setLevel` writing a `team` row for a project another server already binds above Nothing fails on the new unique partial index `sharing_levels_one_server` (plan.md:41), so the older binary throws instead of "reading Nothing until it writes one". (b) "which the next upgrade's first add moves again" is false: the move runs only when the add is the first server (spec.md:88), and after a re-upgrade servers already exist, so `reconcileLevels` removes those `team` rows as an unknown destination (spec.md:94). State what really happens in both cases (the older write refused, the re-upgrade drops the `team` rows with a logged `system` change), or change the design. Add a case to plan.md:112-123 (AC-2) proving it.
- R-3 · .crew/work/2026-11-10-002-part-6-of-the-knowledge-and-team-journey/spec.md:123 · Received search rows (`repo_id` 0, plan.md:61) and their `knowledge_shown` rows are deleted by code the plan does not touch:

- R-4 · .crew/work/2026-11-10-002-part-6-of-the-knowledge-and-team-journey/spec.md:116 · Three gaps on received memories. First, deleting one on a tombstone or purge can fail its chunk for good: `memories.superseded_by REFERENCES memories(id)` with `foreign_keys = ON` (src/store/migrations/0001_init.sql:74, src/store/db.ts:358), and history distillation can supersede a local memory by an imported one (src/distill/pipeline.ts:387-389). The spec must say what happens to rows that point at the deleted memory: set `superseded_by` to null and the referrer back to `active`, or keep the row archived instead of deleting it. Second, the spec writes `judge` `team`, but ADR 0025 binds `judge = 'team:<destination>'` (docs/adr/0025-sharing-policy.md:120, :198) and says `replace-imports` is narrowed by that judge. Follow it, or state the change and add the ADR 0025 amendment to AC-12 (spec.md:172). Third, ADR 0026's "dedupe copied stores by content" (docs/adr/0026-team-server.md:110) is missing for received memories: state the rule, or say why it is dropped.
- R-5 · .crew/work/2026-11-10-002-part-6-of-the-knowledge-and-team-journey/spec.md:104 · Memories become sweep candidates only when `updated_at` is at or after the last sweep's start. A widening (a project put at `all` after the first sweep) and a restore (every memory gets a new-generation uid, spec.md:133) change no `updated_at`, so the old memories are never sent. The spec must say that an epoch different from the last sweep's, or a generation different from the last sweep's, makes the next sweep consider every memory. It must also name where the last sweep's start, epoch and generation are stored (no column in plan.md:10-21 holds them). Add an AC-4 case: put a project at `all` after a sweep, and its 10 old memories leave.
- R-6 · .crew/work/2026-11-10-002-part-6-of-the-knowledge-and-team-journey/spec.md:112 · Three gaps in the cursor rules:
  - A new alias is never snapshotted. ADR 0026 requires a snapshot "for one alias when a machine takes up a project" (docs/adr/0026-team-server.md:110), and the hand-over to the main cursor is unstated (design lens F-15).
  - The alias groups are keyed `cursor:<n>` by position, so adding or removing a project shifts which aliases a stored cursor covers. Key each cursor by its alias set, or reset it when the set changes.
  - "The cursor saved after the page" (line 112) contradicts "the cursor does not pass it" for a dirty row (line 117), and one file left dirty would stall every later row of that server for good. State that the cursor stops at the stuck row's `seq` (items carry `seq`, src/team/contract.ts:44), and set a bound: after N pulls the row is set aside in a pending list and the cursor goes on, shown in status. Add the AC-6 case.

## Notes
- Sharing v2 and knowledge v8 are add-only with defaults as stated: `ALTER TABLE … ADD COLUMN … NOT NULL DEFAULT ''` and new tables only (plan.md:9-59), with no foreign key or trigger on a core table, so ADR 0025 D-8 holds (docs/adr/0025-sharing-policy.md:24). The `team` move is a data step at the add, not a migration (plan.md:44), which answers readiness F-5.
- `LEDGER_RECORD_KEYS` gaining `localHash`, `instance` and `reason` with the contract test updated (plan.md:65; spec.md:172) follows ADR 0025's rule that the lists and the record change together (docs/adr/0025-sharing-policy.md:89). `decide` stays unchanged (AC-2).
- The partial index `sharing_levels_one_server` can be created on an existing store, since v1 has only the `team` destination (src/sharing/levels.ts:14).
- Withdrawals come from the ledger's uids (spec.md:104), and a move retires the old row with reason `moved` without a withdraw, as ADR 0025 requires (docs/adr/0025-sharing-policy.md:146, :195) and as design F-1 asked.
- Stored refusals, purged keys (a `sharing_refusals` row with hash `*`), the sent-hash history (last eight) and the breaker answer design F-7.
- The token outside the store (D-7) answers readiness F-1, F-12 and F-13.
- Advisory: deleting a received memory whose row id is the highest lets SQLite reuse that id for the next local memory, since `memories.id` is INTEGER PRIMARY KEY without AUTOINCREMENT. That is harmless to the ledger (a received row is never sent under `<generation>:<id>`), but ADR 0027 should state it next to the "memories are never deleted" exception.
- Advisory: the counter is global, so a change to one server's lists moves every server's epoch and stops their sweeps too. That is safe; it could be said in ADR 0027.
- Advisory: going from sharing v1 to v2 takes a copy of the store on the first opener, which may be a hook (readiness F-15). AC-13's perf budgets should be read with that one-time cost in mind.
- Advisory: a shared entry sent to two servers that a teammate on one server revises then reads `received-elsewhere` for the other, so the person's later edits never reach the second server (src/sharing/report.ts:436). That fails closed, but ADR 0027 should say so.
