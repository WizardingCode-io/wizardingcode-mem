## Findings
- F-1 · advisory · src/sync/outbound.ts:319 · Round 1's F-2 still stands. The sync still reads the knowledge module's tables with its own SQL: `knowledge_repos` here, `knowledge_entries` at outbound.ts:376 and conflicts.ts:80, and `knowledge_proposals` at conflicts.ts:182. The spec gives the sync a module function for everything else it needs from knowledge (`receivedRow`, `ensureFresh`, `applyRevision`, `proposeConflict`), and the boundary test pins only the sharing tables, so no test covers this coupling to the module's schema. Fix: move these reads into `index-store.ts` (or `store.ts`) and call them from the sync. (Q1)
- F-2 · advisory · src/ui/servers-api.ts:22 · Round 1's F-5 still stands, and it also applies to doctor. The spec says "`status`, `doctor` and the viewer's routes read the server rows through `state.ts`". The viewer's route module reads them through `src/sync/servers.ts` (`listServers`, `findServer`) and `src/sync/ledger.ts` (`openConflictCount`), and `src/doctor/checks.ts:70` imports `src/sync/servers.ts` too. Neither runs SQL over a sharing table of its own, and the boundary test passes, so no boundary is crossed. The spec line and the code disagree only on which module these readers go through. Fix: route them through `state.ts`, or correct the spec line. (Q5)
- F-3 · advisory · src/team/contract.ts:236 · Round 1's F-6 still stands, and there is now a concrete case. `RefusalShape` declares `accepted` and `retryAfterSec`, and the client reads both (`client.ts:97` and `client.ts:116`; the server's 409 at `auth.ts:48` sends `accepted`). But `RESULT_SHAPES.refusal`, the key list that feeds `contractFingerprint`, lists only `error`, `instance` and `serverId`. So the client relies on a field of the answer that the pinned contract does not name, and the answer types in general are still not tied to `RESULT_SHAPES`. Fix: add a key-list check from each type to its `RESULT_SHAPES` entry, or list the optional refusal keys in the pinned list (a contract bump). (Q3)
