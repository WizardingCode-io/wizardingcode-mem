## Findings
- F-1 · defect · src/modules/knowledge/index-store.ts:956 · `RECEIVED_VISIBLE` still treats a project as bound when it has any alias equal to `x.remote_alias` (`JOIN project_aliases a … AND a.alias = x.remote_alias`, with no tie to `l.bound_alias`). `receivedScope` (tools.ts:121) and `take` (knowledge.ts:232) pass `hostLedAliasOf`, which returns the project's alphabetically first host-led alias, not the bound one. Round 3's F-3 disagreement, which this round fixed in `aliasBoundTo` and `boundAliasesOf` (levels.ts:79-106), therefore survives in the search, browse and get reads: for a project with two host-led aliases, the copies under the unbound alias show and those under the bound one do not (Q2/Q3).
- F-2 · defect · src/sync/conflicts.ts:39 · the new `parseEntryUid` writes the entry-uid grammar a second time beside src/team/validate.ts:53's `parseEntryUid`, and the two already differ: the sync's copy accepts any alias (`project:(.+):`) and any 36 characters of `[0-9a-f-]`, while the server's requires a host-led `remote:` alias and the UUID pattern. The diff already moved `entryBytes` into contract.ts (validate.ts:5952) so that both sides share it, and the grammar could sit there or beside `entryUid` in sharing/types.ts (Q2).
- F-3 · advisory · src/sharing/levels.ts:96 · `aliasBoundTo` now agrees with `boundAliasesOf`, but it does so by copying that function's SQL with one more `AND l.bound_alias = ?`, so the two queries are kept in step by hand, and `noteUnbound` (src/sharing/store.ts:316) is a third form that skips the `project_aliases` join; one rule for "bound under this alias" would remove the copies (Q2).
- F-4 · advisory · src/sync/conflicts.ts:149 · the `applied` row's reason is `agentName(remote.member.name)` with no fallback, while the git author (src/modules/knowledge/author.ts:55) uses `agentName(…) || writer.member.id`, and ADR 0027's fourth-round bullet says both fall back to the member id; an empty name leaves the hook's marker reading "revised by  via …" (Q6).
- F-5 · advisory · src/sync/inbound.ts:373 · the main path drops every pending row of the uid (`deletePendingRows(ctx, …, item.uid)`), and the hourly path (line 493) drops only the rows at or below the applied seq (`deletePendingRowsUpTo`): two rules for one event, "a row of this uid applied" (Q2/Q6).
- F-6 · advisory · src/sync/inbound.ts:320 · `parsed.alias !== null` cannot be false once `parsed.scope` is `"project"`, and the same holds for `alias !== null` at src/sync/outbound.ts:744; these guards exist only because `parseEntryUid`'s return type is not a union discriminated on `scope` (Q9).
