## Findings
- F-1 · defect · src/sync/inbound.ts:226 · When a later revision of a received memory arrives, the code changes `title` and `body` with its own `UPDATE memories …` and never calls the store's vector refresh. The base routes every change to a memory's text through `src/store/memories.ts`: there `insertMemory`'s update path calls `refreshMemoryVector`, which rewrites the vector or drops it "so that a search never matches the old text" (ADR 0014/0017). The spec also puts received-memory writes in `memories.ts` (`deleteReceivedMemory`). As written, a received memory whose vector was already backfilled keeps the old text's vector. `healVectors` only fills vectors that are missing, so `memory_search` and the palette keep matching the teammate's old text. This answers rubric questions 1 and 4: a core-table write bypasses the core store's own writer. Fix: add an `updateReceivedMemory(db, id, fields, now)` beside `deleteReceivedMemory` in `src/store/memories.ts` that writes the row and calls `refreshMemoryVector`, and call it here. Move the follow-up `UPDATE memories SET status = ?, created_at = ?` at line 265 into that same writer, or into an `insertMemory` option.
- F-2 · advisory · src/sync/outbound.ts:327 · The sync reads the knowledge module's tables with its own SQL: `knowledge_repos` (here), `knowledge_entries` (outbound.ts:384, conflicts.ts:80) and `knowledge_proposals` (conflicts.ts:179). Everywhere else the spec gives the sync a module function for its knowledge needs (`receivedRow`, `indexReceivedRow`, `applyRevision`, `proposeConflict`, `serverByName`). The boundary test pins where the sharing tables are named but not the knowledge tables, so this coupling has no pin; one or more `index-store.ts` reads would keep the module the owner of its schema.
- F-3 · advisory · src/sharing/migrations/0002_sharing_servers.sql:64 · The sharing namespace creates `sharing_memories_updated` on the core table `memories`. ADR 0027 records this, so the departure is decided. But the file's own header (line 2) still says "no core table changes", and ADR 0025's Storage section still says the namespace touches no core table except by foreign key or trigger. Correct the header and add a line to ADR 0025's Storage, so that the base and the migration say the same thing.
- F-4 · advisory · CLAUDE.md:18 · The change edits CLAUDE.md but leaves claims this part made false. The knowledge bullet still says "The module's version is 7" and "is at 7" (this part adds migration 8). It still says "The store keeps no file of its own under `knowledge/` beside the repositories", but this part adds `knowledge/received/`. The sharing bullet (line 19) still lists the levels as `local | knowledge | all` without `receive`, and names only the three part-4 tables.
- F-5 · advisory · src/ui/servers-api.ts:22 · The spec says "status, doctor and the viewer's routes read the server rows through `state.ts`". The new viewer route module reads them through `servers.ts` (`listServers`, `findServer`) and `ledger.ts` (`openConflictCount`). It runs no SQL of its own, so no boundary is crossed; the spec line and the code disagree only on which module the route goes through.
- F-6 · advisory · src/team/contract.ts:168 · The new answer types (`JoinAnswer`, `MeAnswer`, `PushResultShape`, `FeedItemShape`, `PullPageShape`, `RefusalShape`) are written by hand beside `RESULT_SHAPES`, but only `RESULT_SHAPES` feeds `contractFingerprint`. If a field is added to one type and not to the other, the fingerprint test does not fail. A key-list check tying each type to its `RESULT_SHAPES` entry, like part 4's pinned key lists, would close that gap.
