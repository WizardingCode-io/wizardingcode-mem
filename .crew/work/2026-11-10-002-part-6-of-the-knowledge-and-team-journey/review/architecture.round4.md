## Findings
- F-1 · defect · src/modules/knowledge/index-store.ts:952 · The knowledge reads do not use the binding the fourth round made the one rule. ADR 0027:58 and :60 say a project sees its received project entries while it is "bound under" the alias, and the fourth-round bullet (ADR 0027:96) makes `boundAliasesOf`'s rule (`a.alias = l.bound_alias`) the binding that `aliasBoundTo`, the pull's scopes and the reconcile read; src/retrieve/received.ts:48 reads it that way too. `RECEIVED_VISIBLE` (diff.patch:1997-2008) does not. It keeps `x.remote_alias IS ?` (the scope's alias is `hostLedAliasOf`, the project's first host-led alias by name, contribute.ts:115) and accepts any level whose project has that alias (`a.alias = x.remote_alias`, line 956), never `l.bound_alias`. `aliasToBind` (sharing/store.ts:339) keeps a level on a caller-named alias, or on an older alias the project still has, so the two can differ for a project with two remotes. In that case the agent is shown copies under an alias no pull refreshes, and the copies under the alias the level is bound to are hidden. This is the same any-alias reading round 3 upheld in `aliasBoundTo`, still standing in a second reader. Fix: tie the EXISTS to `a.alias = l.bound_alias AND l.bound_alias = x.remote_alias`. Make the scope's alias the bound alias of the project's level (or pass the bound aliases), not `hostLedAliasOf`'s first by name. Pin it with a two-remote test. (Q2)
- F-2 · advisory · src/sync/outbound.ts:317 · Round 2's F-1 still stands, unchanged. The sync still runs its own SQL over the knowledge module's tables: `knowledge_repos` here, `knowledge_entries` at outbound.ts:374 and conflicts.ts:81, and `knowledge_proposals` at conflicts.ts:183. The boundary test pins only the sharing tables, so no test covers this coupling to the module's schema. Fix: move these reads into index-store.ts or store.ts and call them from the sync. (Q1)
- F-3 · advisory · src/team/contract.ts:70 · Round 2's F-3 still stands, unchanged. `RefusalShape` (contract.ts:240-241) declares `accepted` and `retryAfterSec`, and the client reads both. But `RESULT_SHAPES.refusal`, the list `contractFingerprint` pins, names only `error`, `instance` and `serverId`. Fix: list the optional refusal keys in the pinned list (a contract bump), or check each answer type's keys against its RESULT_SHAPES entry. (Q3)
- F-4 · advisory · src/sync/conflicts.ts:39 · The entry uid's grammar is now split across two layers. Its writer, `entryUid`, is in the sharing leaf (src/sharing/types.ts:345, the module of "the item and payload types"). Its one parser, `parseEntryUid`, which the fourth round makes the only reader (ADR 0027:96), is in the sync's conflict module, and outbound.ts and inbound.ts import it from there. The two halves of one format can drift without either file showing it. Fix: move `parseEntryUid` beside `entryUid` in src/sharing/types.ts and import it from there. (Q6)

Round 3's F-2 (the readers the ADR names) is closed: ADR 0027:72 now names servers.ts, the ledger's count and `checkServerUrl`. Round 3's F-4 (share.ts's shadowing `destinationOf`) is closed: the local helper is `chosenDestination`, and share.ts:360 and ui/api.ts:1043 call the leaf's `destinationOf`. `failureAnswer` in state.ts imports only the client's failure type, so state.ts gains no runtime dependency on the HTTP client. The re-index's `entryUid` and `HitProvenance.id` match the ADR's fourth-round bullet.
