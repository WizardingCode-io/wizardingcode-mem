# risk findings for 2026-11-10-002-part-6-of-the-knowledge-and-team-journey

## Findings
- F-1 · defect · src/sync/inbound.ts:630 · `compareSnapshot` builds `seen` from the last page of a snapshot only (`new Set(body.items.map(...))`, after an early return on every page with `more` true). On any snapshot longer than one page (more than the server's 500 items or 2 MiB), every `received` row from an earlier page is deleted with its file, and every `sent` row from an earlier page is cleared and re-pushed on base 0. This goes against spec.md:180 ("compared after its last page over its own request's scopes"). Every client restore triggers it (backup.ts sets `snapshot_due` on every server), and so do a rejoin, a 410 and a server instance change. Nothing undoes it: the cursor has already moved past those rows, so the copies do not come back until each item changes again, and the next snapshot deletes them again. Nothing reports it either: no status count, and no test covers a snapshot of more than one page.
- F-2 · defect · src/sync/run.ts:330 · The pull loops are built once, from `confirmedServers` when the process starts. A server that `share server add` confirms while `sync --auto` is already running for another server is swept but never pulled. `startSync` returns `running`, and the idle exit never comes while sessions keep writing `hook_runs`, so the team's items never arrive from the second server (journey 5). `status` shows that server as `ok`. Only `doctor`'s 24-hour no-success check would ever show it. No test adds a server while the sync runs.
- F-3 · advisory · .crew/work/2026-11-10-002-part-6-of-the-knowledge-and-team-journey/spec.md:272 · The rollback section says the modules are add-only and an older binary simply reads no `team` row. It leaves out that a 0.6.0 or 0.7.0 binary treats knowledge v8 (`src/modules/knowledge/migrations.ts:12`) as too new. After a downgrade the knowledge module goes silent: no pins in the brief, no floor, and the knowledge tools and CLI refuse (`contribute.ts:49`, `schema.ts`). The sharing policy also loads closed. It can be undone by upgrading again and no data is lost, and `doctor` and the log say it, but the stated rollback promises more than it gives.
- F-4 · advisory · .crew/work/2026-11-10-002-part-6-of-the-knowledge-and-team-journey/spec.md:272 · The rollback does not say to stop the detached sync before a downgrade. A `sync --auto` that is already running keeps its old inode after the binary is replaced. The older binary has no stop flag and no `sync stop`, and its hooks keep writing `hook_runs`, so the idle exit never comes. The process keeps pushing, pulling and applying revisions to own files under a release the person rolled back from, and only `kill` stops it. The manual step (`wizardingcode-mem sync stop` before downgrading) is not named anywhere.
- F-5 · advisory · src/sync/inbound.ts:318 · When a row fails to apply for any reason other than `locked` (a refused path component, a disk-full write), the error is logged and the row counted `skipped`, and the cursor moves past it. That received item is lost until it changes on the server or a snapshot runs. `status` and `doctor` count nothing; the only trace is a deduplicated log line.
- F-6 · advisory · src/sharing/report.ts:402 · The tick's memory read uses `INDEXED BY sharing_memories_updated`, an index on the core `memories` table that sharing v2 owns (0002_sharing_servers.sql:64). If the index is ever missing while the module version reads 2, every tick sweep fails with "no such index" instead of running slowly. That can happen on the development stores the ADR names, or after a future core rebuild of `memories`. The failure is visible only through `last_error` and the log. ADR 0027 already notes the hand fix for development stores.

## Outside the change
- src/store/db.ts:284 · The one-time module upgrade (a `VACUUM INTO` copy, then `BEGIN IMMEDIATE`) is paid by whichever process opens the store first, often a session-start hook. Its cost grows with store size: 124 ms at 66.8 MB, and other openers wait up to 10 s. The repository already carried this; this part adds one more run of it.
