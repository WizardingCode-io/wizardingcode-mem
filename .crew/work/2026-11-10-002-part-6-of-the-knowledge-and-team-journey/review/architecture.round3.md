## Findings
- F-1 · advisory · src/sync/outbound.ts:317 · Round 2's F-1 still stands, unchanged. The sync still runs its own SQL over the knowledge module's tables: `knowledge_repos` here, `knowledge_entries` at outbound.ts:374 and conflicts.ts:80, and `knowledge_proposals` at conflicts.ts:181. Everything else it needs from knowledge goes through a module function, and the boundary test pins only the sharing tables, so no test covers this coupling to the module's schema. Fix: move these reads into index-store.ts or store.ts and call them from the sync. (Q1)
- F-2 · advisory · src/ui/servers-api.ts:22 · Round 2's F-2 still stands, and one more import edge now has the same shape. ADR 0027:72 and the spec say status, doctor and the viewer read the sync through `src/sync/report.ts` "through `state.ts` and `ledger.ts`". The viewer's routes still import `listServers` and `findServer` from `src/sync/servers.ts` (and `openConflictCount` from ledger.ts). src/doctor/checks.ts:69 now also imports `checkServerUrl` from `src/sync/client.ts`, the HTTP client, for a pure check. That import makes no network call (the ADR says doctor "asks the network nothing"). Neither file runs SQL of its own and the boundary test passes, so no boundary is crossed. Fix: route the reads through state.ts and move `checkServerUrl` to a leaf both sides import, or correct the ADR and spec line to name the modules actually read. (Q5)
- F-3 · advisory · src/team/contract.ts:70 · Round 2's F-3 still stands, unchanged. `RefusalShape` (contract.ts:235-241) declares `accepted` and `retryAfterSec`, and the client reads both. But `RESULT_SHAPES.refusal`, the key list that feeds `contractFingerprint`, lists only `error`, `instance` and `serverId`, so the pinned contract does not name a field the client relies on. Fix: list the optional refusal keys in the pinned list (a contract bump), or tie each answer type to its RESULT_SHAPES entry with a key-list check. (Q3)
- F-4 · advisory · src/cli/commands/share.ts:177 · ADR 0027:95 says `destinationOf` in src/sharing/levels.ts "is the one rule for the destination a level is read for". share.ts declares its own module-local `destinationOf` with the same name and a different signature and rule (`serverId ?? TEAM_DESTINATION`). At share.ts:354, `share status` then writes the leaf's rule again by hand (`boundServerOf(db, here.id) ?? destination`), instead of calling `destinationOf(db, policy, here.id)` as status/report.ts:411 and ui/api.ts:1025 do. Fix: call the leaf's `destinationOf` at line 354, and rename the local helper (for example `chosenDestination`) so it does not shadow the shared rule's name. (Q6)
