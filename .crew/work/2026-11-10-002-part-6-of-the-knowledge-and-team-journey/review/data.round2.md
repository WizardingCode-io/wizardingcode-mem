## Findings
- F-1 · defect · src/sync/inbound.ts:487 · The hourly re-apply of pending rows calls `deletePendingRows(ctx, serverId, row.uid)`, which deletes every pending row of that uid as soon as the oldest one applies. A newer set-aside revision of the same uid is then applied only from the in-memory list. If that apply throws or answers `retry`, the row is already gone from `sharing_pending_rows` and the cursor is already past its `seq`, so the teammate's revision is lost until the item changes again. Since round 1, any apply error is set aside at once, which makes two pending rows of one uid more likely. Deleting by `(server_id, seq)` for the row just applied would close this (Q1, a data loss).
- F-2 · advisory · src/sync/inbound.ts:121 · `dedupeKeys` reads `id, title, body` of every memory of the project (`WHERE project_id = ?`, served by `memories_rank`) once per pull that carries a memory row of that project, and hashes them all. A held pull every 25 s therefore loads the whole project's memory text whenever a teammate's memory arrives. An index is present, so this is a cost, not a scan (Q2).
- F-3 · advisory · src/sync/ledger.ts:111 · `sentRowByUuid` filters `item_uid LIKE '%:' || ?` within the server's sent entry rows. The outbound sweep (src/sync/outbound.ts:397) calls it for every sendable entry that has no sent row of its own, so a first full sweep of N entries scans the server's entry ledger N times (Q2).
- F-4 · advisory · src/sharing/migrations/0002_sharing_servers.sql:69 · The round-1 fixes added `sharing_memories_superseded`, `sharing_ledger_applied`, `knowledge_received_fts` and `knowledge_entries_id` by editing the already-numbered migrations 0002 and 0008 rather than adding new ones. A development store that ran the earlier text never gets them. ADR 0027 tells such stores to create by hand only `sharing_memories_updated` (the index `INDEXED BY` names at src/sharing/report.ts:402, where a missing index still fails the tick instead of slowing it); it does not mention these four. They are performance-only, and the migration is unreleased (Q1, run order).
- F-5 · advisory · src/sharing/migrations.ts:61 · As in round 1: when a project has a `team` row, the resolve deletes every other row above Nothing, though the index it then creates would allow one server row beside `team`. The deletion is logged as a `system` change, and the forward-only rule is stated (Q1).
- F-6 · advisory · src/backup/backup.ts:332 · As in round 1: the unpacked copy is brought to the current schema while the live store is held under `BEGIN IMMEDIATE`, so an old backup's core and module migrations run under the live write lock while hooks wait (Q6).
- F-7 · advisory · src/store/compact.ts:140 · As in round 1: `x.server_id || '|' || x.uid = k.entry_id` compares an expression, so the `(server_id, uid)` key goes unused and compact scans `knowledge_received` once per shown row of repository 0 (Q2).
- F-8 · advisory · src/sync/ledger.ts:369 · Resolved `sharing_conflicts` rows (`local_text`, the person's whole text) are only stamped `resolved_at`. No retention or prune is stated, and only a server's removal clears them. Every session start counts them with `WHERE resolved_at IS NULL`, which no index serves (src/modules/knowledge/contribute.ts:148), so that hook-path read grows with the table (Q5, Q2).
- F-9 · advisory · src/sync/ledger.ts:544 · As in round 1: `receivedMemoryIds` for an alias resolves it through the local project's current `project_aliases`, because `sharing_received_memories` stores no remote alias. Received memories of an alias the project has since lost are never matched by `reconcileReceived`, nor by `compareSnapshot` (inbound.ts:697-700), so they stay stored but unreached (Q5).
- F-10 · advisory · src/sync/inbound.ts:488 · A pending row whose re-apply keeps throwing is only logged. Its `tries` never moves, and nothing drops it but a later row of the uid, an instance change or a server removal. The payload, which holds a teammate's text and name, has no stated retention beyond those events (Q5).

## Outside the change
- src/modules/knowledge/migrations/0006_knowledge_store.sql:60 · `knowledge_entries` still has no index on `id` alone in its own migration; 0008 now adds `knowledge_entries_id` from the knowledge namespace, which settles round 1's debt for every read that filters on `id`.

## Not answerable
- Availability on a large store · `scripts/proof/upgrade-copy.ts` measures the first open on a 66.8 MB fixture with a 500-row ledger. No figure exists for a server removal with many received memories, a first full sweep over many entries (F-3), or a restore of an old backup under the live lock (F-6), so whether the new indexes bring these within the stated bounds is unmeasured.
