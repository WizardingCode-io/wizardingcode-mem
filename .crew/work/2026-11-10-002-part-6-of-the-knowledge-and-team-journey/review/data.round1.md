# data findings for 2026-11-10-002-part-6-of-the-knowledge-and-team-journey
reviewer: review-data
read: 17 files (the rubric, files.txt, the diff's hunks for db.ts, backup.ts, compact.ts and memories.ts, and in full or in the relevant parts sharing/migrations.ts, 0001_sharing_policy.sql, 0002_sharing_servers.sql, knowledge migrations.ts, 0008_knowledge_received.sql, sync/ledger.ts, sync/received.ts, sync/inbound.ts, sync/outbound.ts, sync/join.ts, sharing/report.ts, modules/knowledge/index-store.ts, retrieve/received.ts, scripts/proof/upgrade-copy.ts and ADR 0027), the schema and migrations read (the core 0001–0007 index, trigger and FK lines; the sharing 0001–0002; the knowledge 0006–0008), risk areas: data-migration, personal-data

## Findings
- F-1 · defect · src/backup/backup.ts:134 · The restore carries the live `sharing_ledger`, with its `received` memory rows, into the copy but keeps the copy's own `sharing_received_memories` and memories. A teammate's memory received after the backup was made therefore comes back as a ledger row with no provenance. `receivedMemoryRow` (src/sync/ledger.ts:597-603) reads that as a deduped uid (`memoryId: null`), so the next upsert with the same hash is skipped and the memory never returns to this machine. Going the other way, a received memory that was tombstoned or purged after the backup comes back alive with no ledger row, and the cursor (carried from live) is already past its tombstone. This is data lost or revived across the restore's run order (Q1, Q5).
- F-2 · defect · src/sync/received.ts:354 · `orphanServerIds` finds orphan servers only through `knowledge_received` rows and folders under `knowledge/received/`, never through `sharing_received_memories`. A server dropped by a restore (backup.ts reports it in `pendingDeletion`, "whose received copies the sync's next start deletes") that delivered only memories, or whose folder is already gone, is never deleted. Its teammates' memories stay in `memories`, and their member ids and names stay in `sharing_received_memories`, with no path left to erase them (Q5, the erasure ADR 0027 D-6 promises).
- F-3 · defect · src/store/memories.ts:185 · `deleteReceivedMemory` starts with `UPDATE memories … WHERE superseded_by = ?`. The schema has no index on `memories.superseded_by` (0001_init.sql:74), so every call scans the whole memories table. `deleteServerReceived` (src/sync/received.ts:347) and `reconcileReceived` (received.ts:400) call it once per received memory inside one write transaction, and `removeServer` also runs the recursive `rmSync` of the server's folder inside its `withWrite` (src/sync/join.ts:340-341). Removing a server with thousands of received memories holds the store's write lock for memories × received scans while hooks wait (Q2, Q6).
- F-4 · defect · src/modules/knowledge/index-store.ts:1104 · `HELD_PIN` is a new correlated `NOT EXISTS` over `sharing_ledger` filtered on `direction`, `item_kind`, `local_hash` and `item_uid LIKE '%:' || e.id`. The ledger's only key leads with `destination`, so the subquery scans the whole ledger (every sent and received memory and entry) once per pinned entry, on every session start (`pinnedEntries`, line 1228). `withRevisions` (line 1080) scans the ledger the same way on every search. No index on `(direction, item_kind, local_hash)` serves either (Q2).
- F-5 · defect · src/modules/knowledge/index-store.ts:946 · `RECEIVED_VISIBLE` checks `NOT EXISTS (SELECT 1 FROM knowledge_entries e2 WHERE e2.id = x.id)`, but `knowledge_entries` is keyed `(repo_id, id)` with no index on `id`. Each received row costs a scan of the entries, unless the planner builds an automatic index per statement, in the browse and search reads. Separately, `searchReceived` joins `knowledge_received x ON x.fts_rowid = f.rowid` (line 1039) with no index on `fts_rowid`, and `knowledge_received` is WITHOUT ROWID. Migration 8 adds `knowledge_received_project` and `knowledge_received_entry`, but not the indexes these new reads filter on (Q2).
- F-6 · defect · src/sync/inbound.ts:316 · In `applyPage`, any apply error other than a `locked` KnowledgeError (SQLITE_BUSY past the busy timeout, a full disk in `writeFileAtomic`, any other throw) is logged and counted as `skipped`, and `applyAndSave` then saves the cursor past the page (line 518). That teammate's revision never lands on this machine until the item is revised again. The ten-try set-aside covers only dirty or locked rows, and the snapshot repairs entries only, never memories (Q1/availability of the data).
- F-7 · advisory · src/sharing/report.ts:487 · `ledgerRecords` filters `WHERE item_kind = ? AND (destination = ? OR direction = 'received')`, which no index serves, so it reads every ledger row of the kind across all servers. The sweep now calls it on every tick that has even one candidate (src/sync/outbound.ts:349, 373), so the cost of a busy tick grows with the whole ledger rather than the window (Q2).
- F-8 · advisory · src/sharing/migrations/0002_sharing_servers.sql:64 · The namespace now owns an index on the core table `memories`, while the file's header says "no core table changes" and 0001's says no sharing table touches a core table. The window query names it with `INDEXED BY` (src/sharing/report.ts:402). If a later core migration rebuilds `memories`, or a store ran migration 2 without the index (ADR 0027 already names such development stores), every tick fails with "no query solution" instead of running slower (Q1, run order across namespaces).
- F-9 · advisory · src/sharing/migrations.ts:61 · When a project has a `team` row, `oneServerPerProject` deletes every other row above Nothing, but the index it then creates (`… AND destination != 'team'`) would have allowed `team` plus one server row. The resolve therefore removes more than the constraint needs. The deletion is logged as a `system` change with the old level, and the forward-only rule is stated, so the irreversibility has its stated reason (Q1).
- F-10 · advisory · src/backup/backup.ts:298 · Under the restore's `BEGIN IMMEDIATE` on the live store, the unpacked copy is brought to the current schema (`openStoreFile`), and the old copy may need every core and module migration. The live store's write lock is held for the whole upgrade, where previously only `resetLevels` ran under the freeze. Hooks fail open while they wait (Q6).
- F-11 · advisory · src/store/compact.ts:140 · The new kept-shown test, `x.server_id || '|' || x.uid = k.entry_id`, compares an expression, so the `(server_id, uid)` key cannot be used. Compact pays one scan of `knowledge_received` per shown row of repository 0. Splitting `entry_id` at the `|` would use the key (Q2).
- F-12 · advisory · src/sync/ledger.ts:369 · A resolved `sharing_conflicts` row (`local_text`, the person's whole text) is only stamped `resolved_at` and is never pruned. `compact` does not touch it, and only a server's removal clears it, so the table grows with no stated retention (Q5).
- F-13 · advisory · src/sync/ledger.ts:544 · `receivedMemoryIds` for an alias resolves the alias through the local project's current `project_aliases`, because `sharing_received_memories` stores no remote alias. Received memories of an alias the project has since lost or changed are never matched by `reconcileReceived`, and they stay invisible but stored (Q5).
- F-14 · advisory · src/sync/inbound.ts:296 · The docstring says a page is applied in chunks of 50 "each in one transaction", but each row commits on its own through `guarded`. That is one commit per row, and a crash mid-chunk leaves part of it applied (safe only because the apply is idempotent by hash) (Q3).

## Outside the change
- src/store/migrations/0001_init.sql:74 · `memories.superseded_by` is a self-referencing foreign key with no index, so every `DELETE FROM memories` also scans memories for the FK check; this is debt the new deletion path inherits.
- src/modules/knowledge/migrations/0006_knowledge_store.sql:60 · `knowledge_entries` has no index on `id` alone (its key is `(repo_id, id)`); this is debt behind F-5.

## Not answerable
- Availability on a large store · `scripts/proof/upgrade-copy.ts` measures the first open on a 66.8 MB fixture with a 500-row ledger, but no figure exists for F-3's removal, F-4's session-start read or F-10's restore under a large ledger or an old backup.
