# Concept brief: the sync client (part 6)

## Overview

A person's machine joins one or more team servers (part 5, ADR 0026) with an invitation code and, from then on, what the sharing policy (part 4, ADR 0025) allows reaches each server within seconds of a local change, and what the team shares reaches this machine within seconds of a change there. The sync is one detached process per data directory, never on a hook path. What is received lives apart from the person's own repositories, read-only and erasable, so a server's purge can be honoured and a teammate's text never becomes the person's own work. The policy and the ledger are keyed by server; a project is bound to one server at most for sending; receiving needs no level. The CLI and the viewer's Servers card both ship.

## Analysis

The six lenses (spec-review/*.md) found four things that change the design, and a set of rules the concept left open.

**Where received items live.** Writing received entries into the person's own repositories (workspace, shared, the project's) fails three ways: a server purge cannot be honoured in a client that never rewrites history or deletes a memory (structural F-1); received text reaches the agents without the review ADR 0024 names, through pins and the prompt floor (structural F-2, design F-11); every member's workspace entries would land in this person's workspace, with slug collisions and `not-owner` refusals after a local edit (structural F-3, design F-3, comprehension F-7). The concept therefore keeps received items apart: entries as byte-for-byte files under `knowledge/received/<serverId>/…` with no git history, indexed with their server and member, read-only, never pinned, shown to agents only through search, get and the prompt floor with a provenance marker; memories as rows with a provenance table, never through the `judge` column (structural F-11). A received entry is deleted by a purge; a received memory is a copy and may be deleted by a purge, the one exception to "memories are never deleted", stated in ADR 0027. To change a received shared or project entry, the person adopts it into their own repository under the same uid; from then on it is theirs.

**Identity and the token.** The token in the database travels into backups and buckets and with a copied store, so two machines would push under one device (readiness F-1, F-13; comprehension F-12; structural F-12). The token lives in `<data dir>/servers.json` (0600), outside the backup and outside a store copy; a copied store has no token and re-joins as a new device. The server list, the cursor and the per-server state live in the database, where a restore rolls the cursor back, which is safe.

**Conflicts and moves.** A proposal's `kind` is the entry's kind, so "a proposal of kind sync conflict" cannot exist as such (zoom-out F-5, comprehension F-4, codebase F-2, structural F-4): a conflict is a proposal with `proposed_by: sync:<serverId>` and `on_behalf_of` the person, with the server's revision as its base, outside the proposal quota, and its local text also kept in a `sharing_conflicts` row so it is never lost; status and the viewer name it. A local move changes the uid: it is one send on the current base (the server applies a move), and the old uid's `sent` row is retired without a withdraw (design F-1). A `stale` whose `current.hash` is one this machine sent before is a server rollback, not a conflict: the item is re-sent on the current base (design F-2); the ledger keeps the last eight sent hashes per uid.

**Lifecycle and change detection.** "Like `ui --auto`" would skip SSH, CI and resumed sessions, and a quiet quarter hour inside a long session would stop the sync (zoom-out F-1, codebase F-1/F-3, design F-8, comprehension F-6). The sync is started by the session-start hook and the prompt hook (skipped when no server is configured or the lease is held, which costs one meta read) and by the viewer; it has none of the viewer's guards; "active" is the newest `hook_runs.at` within fifteen minutes or a live viewer; it exits after fifteen minutes with neither. The lease is a client-store meta lease with owner `sync-<pid>` (so a dead owner is seen), 60 s renewed every 20 s, held across a `wait`, and joins `anyLeaseActive` so a restore, a move or a compact waits (zoom-out F-7, codebase F-4). Changes are found by polling, not by watching: `stamp(db)` every two seconds for memories and the knowledge index, candidates by `updated_at` since the last sweep, a withdrawal sweep from the ledger on each policy change; hand-edited files reach the index through `refreshStale`, which the sync runs for the bound projects' repositories at most every thirty seconds (zoom-out F-2, design F-5, codebase F-9).

**Per-server policy.** `decide`, `SharingPolicy` and the epoch keep their shape; `loadPolicy` takes a server and returns that server's policy (zoom-out F-4). The two env keys stay the person's hand-editable ceiling for every server (narrow-only, as today); each server's own roots and areas live in `sharing_servers`, edited by the viewer and `share roots | areas --server`; the effective lists are the intersection, and the epoch is per server over its effective lists (readiness F-6/F-7/F-8, structural F-6). "Bound to one server at most" is enforced in `setLevel` and by a unique partial index on `sharing_levels(project_id) WHERE level != 'local'` (readiness F-14).

**Migration.** The schema step is sharing v2 (add-only, defaults): `sharing_servers`, `sharing_conflicts`, `sharing_refusals`, `sharing_sent_hashes`, a `received_memories` provenance table, `local_hash` and `instance` on the ledger; the data step runs inside `share server add` for the first server: the `team` rows of `sharing_levels` and `sharing_ledger` move to its `serverId` in the same transaction as the join, and `sharing.settings_seen` is re-baselined so the move is not read as a hand edit (readiness F-5/F-6). A downgraded binary writes `team` rows that the next upgrade moves again, and its `history replace-imports` would archive received memories: ADR 0027 states the rollback target and that received memories under a downgrade are read-only until re-upgrade (readiness F-9). The sync lease carries the binary's version; a newer binary takes over an older holder's lease (readiness F-10).

**Restore of the client store.** The copy's ledger is older: items sent since have no `sent` row and would be re-sent on base 0 and answered `stale` in bulk (readiness F-2, design F-12). `restoreBackup` carries the live store's `sharing_servers` rows, its ledger's not-withdrawn `sent` rows and the token file through the restore (as it carries the counter), so the new generation withdraws the old generation's memory uids from the ledger it kept; received files on disk whose rows the copy lacks are re-indexed from the `received/` folder, which is the truth for received entries (readiness F-4).

**Server restored (new instance) and 410.** A snapshot pull; `received` rows absent from the snapshot are dropped with their copies, and only those; `sent` rows are compared with the snapshot: absent means the row is cleared and the item re-sent on base 0; present with a hash this machine sent means nothing; present with another hash is a teammate's later change, a conflict by D-2. `sent` rows carry the instance (design F-2, structural F-9).

**Failure paths.** Refusals are stored by uid and hash (`sharing_refusals`; `purged` keys never re-sent); an empty pull page that came back well before `wait` means the held-pull cap and backs off; the client's own deadline is `wait` plus ten seconds; 5xx, 429 (with `Retry-After`) and network errors back off with jitter up to ten minutes; a 401 on a known instance stops that server with a line that names the remedy; a 409 stops it naming both contracts; a circuit breaker per server; each server's loop is isolated from the others (design F-7, F-13, F-15, F-17; codebase F-6, F-7). The first run puts live changes ahead of the backlog, sizes batches by bytes as well as by count, and derives its retries from the bytes bucket's refill; status shows the backlog and an estimate (design F-6, structural F-16). Write transactions are bounded to a page chunk so hooks' busy timeouts hold (design F-10). A received item whose target is dirty or locked is retried and shown; the cursor is saved after the page is applied, and a page is applied idempotently (design F-16). Tombstones are applied to the (scope, alias) of their uid, never by bare uuid (design F-14). An alias taken up resumes the main pull for that alias from the snapshot's `next` (design F-15).

**Observability.** Per-server state in the database (last push and pull attempt and success, cursor, instance, counts, backlog, last error with status, request id and time); repeated identical errors logged once with a count; the log scope names the serverId, never the token; `status` prints a line per server and the sync's own state (running, idle since, not running and what starts it); `doctor` checks the token file's mode, a non-https URL, a 409 stop, a 401 that needs an invitation, a dead lease holder, sharing chosen with no run for hours, open conflicts, and touches no network; `share explain --server` shows the ledger's history for an item (codebase F-5, F-8, F-11, F-15). The sent row records the epoch and the reason, so "nothing left outside the policy" can be checked after the fact.

**The person's confirmation.** `share server add` shows the would-leave counts for that server and asks, or takes `--yes`; a non-interactive add without `--yes` refuses; the texts "nothing is sent now" and "until a team server is configured" change to name the server; the join says that every member's workspace and the shared entries will be received (comprehension F-2, F-3). The invitation code is prompted for when `--code` is absent.

**Token budget and trust.** Received memories take at most a third of the slots of a brief or a prompt's notes and are marked `(team: <server name>)`; received entries are never pinned and carry `from <member> via <server>` in the agents' results; a server or a member can be muted (`share server mute`). The server's display name comes from `/v1/me` where the server gives one, else the URL's host.

**What stays as decided.** D-1 (its own process), D-2 (the server's revision to the file, the local text kept as a proposal), D-3 (CLI and viewer), D-4 (the first run automatic) and D-5 (receiving whenever there are changes, a level only to send) hold, with the mechanisms above.

## Goals vs. Non-Goals

Goals: join by code; several servers; a project bound to one server for sending; the policy and the ledger per server; a change reaches a connected machine in under five seconds while both run; nothing leaves outside the policy, provable from the ledger; received items apart, read-only, erasable, marked for the agents; conflicts never lose text; the sync never on a hook path; status, doctor and the viewer say what the sync does.

Non-goals: a Team view in the viewer; changes to the MCP tools beyond provenance in their results; `serve forget` and the runbook (part 7); a taxonomy sync (a later contract bump; received entries are not parsed against the local taxonomy); editing a received entry in place (adopt it instead); a second contract version; certificate pinning; the viewer's per-server area editor beyond the two lists.

## Alternatives Weighed

- Received entries written into the person's own repositories (the first concept): rejected, since a purge cannot erase git history, received text would be pinned and shown without a marker, and teammates' workspace entries would collide with the person's own and be refused `not-owner` after a local edit.
- A review gate before any received item is shown to agents (ADR 0024's wording): rejected for this part, since the person asked for the team's changes to arrive whenever they happen (D-5); the marker, the pin rule, the one-third cap and the mute are the safeguards instead, and a gate stays possible later because received items are apart.
- The device token in the database: rejected, since backups, buckets and store copies would carry a live credential and two machines could share one device.
- A file watcher or a signal from every writer for change detection: rejected, since every current and future writer would have to know the sync; polling the store's stamp costs nothing when nothing changed.
- The sync inside the viewer or the MCP server: rejected (D-1), since neither runs in every session, and the viewer is not started over SSH or in CI.
- Env keys per server for roots and areas: rejected, since opaque ids in a hand-edited file break hand-edit detection and readability; the env keys stay the ceiling and per-server lists live in the database.
- A proposal kind "sync conflict": rejected, since `kind` is the entry's kind; `proposed_by: sync:<serverId>` and a `sharing_conflicts` row carry it.
- "Absent from the snapshot is gone" applied to every local item: rejected, since it would delete the person's own entries after a server restore; only received copies are dropped, and the person's own are re-sent.

## Key Decisions

- K-1: Received items live apart under `knowledge/received/<serverId>/` (files without git) and in a `received_memories` provenance table; read-only; deleted by a purge; adopted into the person's repository to be edited.
- K-2: The device token lives in `<data dir>/servers.json` (0600), outside the backup and a store copy; the server list, cursor and state live in `sharing_servers`.
- K-3: Sharing schema v2 (add-only); the `team` rows move to the first server inside `share server add`; the epoch is per server; the env keys are the ceiling.
- K-4: The sync process is started by the session-start and prompt hooks (one meta read, skipped when no server or the lease is held) and the viewer, with none of the viewer's guards; a client-store lease with a pid owner, renewed across waits, in `anyLeaseActive`.
- K-5: Changes are found by polling the store's stamp every two seconds and the index by `updated_at`; hand edits enter through `refreshStale` at most every thirty seconds.
- K-6: A conflict is a proposal by `sync:<serverId>` on behalf of the person, outside the quota, plus a `sharing_conflicts` row; a server rollback is told from a conflict by the sent-hash history.
- K-7: Refusals and purged keys are stored; every server has its own loop, deadline, backoff and circuit breaker; the first run yields to live changes.
- K-8: `share server add` confirms the would-leave counts or takes `--yes`; received memories are capped at a third of the slots and marked; received entries are never pinned; a server or member can be muted.
