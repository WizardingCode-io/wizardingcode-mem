# security findings for 2026-11-08-003-knowledge-store-entries-as-markdown-with
reviewer: review-security
read: 14 files, risk areas: data-migration, personal-data

## Findings
- F-1 · defect · src/modules/knowledge/repo.ts:366 · Someone who can put a folder under `<data dir>/knowledge/` (the "later sync" the spec names) can give it a `.git/` whose `.git/config` is clean but which has a `commondir` file pointing at another directory, or sets `extensions.worktreeConfig` together with a `.git/config.worktree`. Either way the config git actually uses carries a `[filter "x"] clean=<program>` section, which, with a `.gitattributes` line `* filter=x`, makes the engine's `git add` (store writes, `adopt`) and the doctor's `git status` (src/doctor/checks.ts:787) run that program. Git honours both files, but `checkRepoConfig` only reads `.git/config` as text and the `-c` overrides at repo.ts:225 do not cover `filter.*`. This breaks AC-15/AC-19 ("a hostile `.git/config` refused and never run").
- F-2 · defect · src/modules/knowledge/repo.ts:527 · If `knowledge/workspace/.git` (or a project folder's `.git`) is a *file* (`gitdir: /other/repo`), `headOf` returns null because `isDirectory` uses lstat. `openRepo` with `create` then skips `checkRepoConfig`, since `.git` is not a directory. `createRepository` runs `git init` (repo.ts:470), which reinitialises the repository the gitfile points to. Every later `--git-dir <repo>/.git` add and commit lands in that external repository, under its own unchecked config, so its filters run. `checkRepoConfig` at line 532 then hits ENOTDIR on `.git/config` and returns silently (line 371). Anyone who can drop that file gets commits into a repository outside the store and program execution, against AC-2 and AC-15. Because `headOf` stays null, this repeats on every write.

## Outside the change

That database now also holds `knowledge_entries` / `knowledge_proposals` (entry bodies, author names), so this text now goes to whatever folder or S3 bucket is configured. ADR 0024 calls it a rebuildable cache but does not name the new audience (advisory, personal-data).

Advisories within the change (hardening; they do not block):
- A-1 · src/modules/knowledge/repo.ts:159-161 · `writeFileAtomic` writes the temp file `.<name>.tmp` with a plain `writeFileSync`, which follows a symlink already sitting at that name. Its bytes go to the link's target outside the repository, against AC-13 ("symlinks never written"). The fix is to remove the name first and open with `wx` / O_NOFOLLOW|O_EXCL.
- A-2 · src/modules/knowledge/store.ts:214-218, 299-301 · `checkTarget` lstats only the final path component. If `entries/` or `proposals/open/` is itself a symlink to a directory, the engine reads, lists (index-store.ts:310) and writes outside the repository. Git later refuses the path ("beyond a symbolic link"), but only after the write.
- A-3 · src/modules/knowledge/repo.ts:774 · `restoreKept` writes with `writeFileSync`, which follows a symlink at the target if one was put there between keep and restore.
- A-4 · src/modules/knowledge/store.ts:811-816, 866 and repo.ts:591,613 · paths read back from `git status` go to `add`/`commit --only`/`rm` as pathspecs. Pathspecs glob, so a hand-made file named with `*`, `?` or `[` matches other paths. Setting `GIT_LITERAL_PATHSPECS=1` in `gitEnv` (repo.ts:201) would pin them.
- A-5 · src/doctor/checks.ts:746 · doctor reads `knowledge.json` with `readFileSync`, which follows links and has no cap. This differs from `readRegularFile`, which the rest of the module uses.

Checked and sound: names are hashed or validated before any path is built (`projectFolderName`, `checkSlug`, UUID checks before proposal paths, `KEPT_NAME`, `restoreKept` refusing `.`/`..`); SQL is fully parameterised (the one interpolated column in index-store.ts:268 is a fixed literal); the agent path redacts text before the field limits and slug derivation, and refuses a slug that redaction would change; commit identities use `.invalid` addresses, and the test fixtures' e-mail strings are all `.invalid`; `runGit` builds its own environment (empty global config, NOSYSTEM, ceiling directory, no prompt, SIGKILL on timeout). On data-migration: 0006 drops the withdrawn module's tables only where they exist, after the backup `upgrade` takes when `module_migrations` already has rows (src/store/db.ts:142-143, 299-302). ADR 0024:119 states why this is not reversible. The migration runs inside one transaction, after the core migrations.
