## Findings
- F-1 · defect · src/modules/knowledge/repo.ts:808 · Suppose a person's write, accept or reject is interrupted after its rename and before its commit. Ctrl-C while git is held up for its 15 s is the ordinary case, and it leaves the intent record in place. The next `openRepo` then runs `restoreToHead` on those paths with no check of their current content. Any knowledge command triggers that openRepo, `knowledge adopt` included, and adopt is the command the product tells the person to run for hand edits. The revert overwrites the paths with HEAD (`git restore --worktree`) and deletes the created file from disk with `rmSync` (line 642). So if the person edited the new or changed entry in an editor in the meantime, that edit is destroyed, and nothing restores it. The only sign is a `logError` line (line 811). The command prints nothing on stdout, so the spec's "reports it" (spec.md:143) is a log file only. This contradicts the promise at spec.md:314 that "the person's own hand edits are never touched by that revert". The tests (tests/unit/knowledge-repo.test.ts:628-649) cover the revert only with the file still as the engine left it.
- F-2 · defect · src/modules/knowledge/repo.ts:801 · The adopt case has the same problem. When an interrupted adopt's paths still show changes, `restoreKept` (line 803, write at line 774) writes the bytes kept at adopt time back over the files. Any later hand edit of those files is silently replaced by the older bytes. Only the log line at 811 reports it.
- F-3 · advisory · src/store/db.ts:317 · `migrateModules` is not contained. If the module pass throws (BUSY past the 10 s upgrade wait, or a store where `knowledge_repos` exists without row 6, which matters because the SQL's `CREATE TABLE` at 0006_knowledge_store.sql:18 has no `IF NOT EXISTS`), `openDb` fails. Every hook then fails open with only a log line, so memory goes dark over a module that no hook reads in this part. Meanwhile `doctor`'s database check uses `openExisting`, never runs the pass, and reports `ok` (src/doctor/checks.ts:159). `moduleSchemaState` "behind" is never warned. The spec (spec.md:240) only covers the too-new case.
- F-4 · advisory · .crew/work/2026-11-08-003-knowledge-store-entries-as-markdown-with/spec.md:321 · The rollback has a stated reason (the tables and repositories stay, 0.6.0 ignores them, no down path). But it is manual, and no cleanup command is provided. Migration 6's drop of the withdrawn module's tables can only be undone by restoring the one backup the module pass takes (db.ts:5207 in the diff, `backupVersion`). That backup shares `BACKUPS_KEPT = 2` with core backups (db.ts:33), so two later upgrades rotate it away. This only affects stores that ran the withdrawn module, and the risk is stated as O-1.

## Outside the change
- src/store/db.ts:132 · The upgrade runner waits up to `UPGRADE_WAIT_MS` (10 s) under `BEGIN IMMEDIATE`, whatever the hook's own busy timeout is. This item makes every user take one upgrade at the first open, usually a prompt hook. That prompt can therefore stall up to 10 s once if a background drain holds the write lock. The core migrations already carried this.
- tests/perf · The p95 hook-latency budgets (53 ms against 50, 86 ms against 80 in one of four runs, medians inside) are already flaky on the gate machine. The roughly 9 µs module query cannot explain it. The flakiness predates this item, but it means a real regression on the hook path would be hard to tell from noise.

- Q1 (the first hour), how a failing module pass would be noticed on a user's machine · the diff gives no sign of whether `status` or the viewer show recent hook errors from the log. The `doctor` gap in F-3 is all that could be confirmed.
