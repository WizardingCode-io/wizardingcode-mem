## Findings
- F-1 · defect · tests/unit/knowledge-store.test.ts:831 · AC-18 says "a caller cannot set an entry's id", but no test fails if that is reverted. Only the type keeps `id` out today (`EntryChange` has no `id` field, src/modules/knowledge/types.ts:104). No test passes `{ ...change(), id: <uuid> }` to `writeEntry` (as a person or as an agent) and checks that the stored entry or proposal got a fresh id. So a change that let a caller's id through would pass every test. Fails rubric question 1. (The other half of AC-18, the id that belongs to another slug, is tested at line 831.)
- F-2 · defect · tests/unit/knowledge-store.test.ts:588 · AC-15 says the agent's title, context, subject and body are all passed through `redact`. The test puts a secret only in `body` and `context`. Remove the `clean()` call on `title` or `subject` in `propose` (src/modules/knowledge/store.ts:461,465) and every test still passes. The title case also matters for the slug, which is made from the redacted title (store.ts:468). Fails rubric question 1 for those two fields.
- F-3 · advisory · tests/unit/knowledge-store.test.ts:433 · AC-8, "a git call that does not return within the timeout is killed and the write refused": at this level the only call that times out is the `git --version` probe in `requireGit`. The slow stub sleeps before every call, the stub's PATH is new so the version is not cached, and `requireGit` re-throws a timeout (repo.ts:318). No git call inside the write (stage or commit) ever times out here. The runner-level test (knowledge-repo.test.ts:328) covers `runGit` in general, so this is not a defect.
- F-4 · advisory · tests/unit/knowledge-repo.test.ts:328 · AC-8 "killed": the test checks only the "timed out" message. Nothing checks that the git process (or its `sleep` child) is gone, so a timeout that gave up on the call but left git running would still pass.
- F-5 · advisory · tests/unit/knowledge-repo.test.ts:235 · AC-2's parent-repository case is weaker than it looks. The parent's `.gitignore` holds `data/`, so `realGit(parent, "status", "--porcelain")` at line 263 is empty whatever the engine writes under `data/`. Also `git init` runs before any git call inside the folder, so the commit-count check (line 264) would likely still pass without `GIT_CEILING_DIRECTORIES`. That guard is only held by the environment test at line 395, which checks how it is done (rubric question 5).
- F-6 · advisory · tests/unit/knowledge-repo.test.ts:358 · AC-13 says git's stderr is clipped in the log line too. The clip is checked only on the thrown message (line 367); no test reads a log line holding long stderr.
- F-7 · advisory · tests/unit/knowledge-resolve.test.ts:81 · AC-2 "a project that gains a remote is mapped through the manifest": this test runs with the `knowledge_repos` row still present, so the row picks the folder (resolve.ts:156) and the manifest lookup is not used. The manifest path is covered only by the separate lost-rows test at line 99, with no remote gained; no test does both. As you noted, this file was written after resolve.ts and passed on its first run. Reading the assertions (folder from the remote, path alias not strong, newest wins, claimed, numbered collision), each would fail if its rule were reverted. That rests on reading the tests, not on a red run.
