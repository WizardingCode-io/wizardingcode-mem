# security findings for 2026-11-08-003-knowledge-store-entries-as-markdown-with

## Findings
- F-1 · defect · src/modules/knowledge/repo.ts:66 · Someone who can drop a folder under `<data dir>/knowledge/` can still get a program run, through the store's own support folders rather than a repository. `supportPaths` puts `.no-hooks/`, `.template/` and `.gitconfig-empty` directly under `knowledge/`. `ensureSupportFolders` (repo.ts:79-86) accepts whatever is already there: `mkdirSync` on an existing folder, and `existsSync` keeps an existing file. Nothing checks these three paths. (a) A dropped `knowledge/.no-hooks/pre-commit` (or `post-index-change` / `reference-transaction`) runs on every store commit, because `core.hooksPath` points there (repo.ts:301). (b) A dropped `.gitconfig-empty` is `GIT_CONFIG_GLOBAL` for every git call, doctor's `status` included (repo.ts:284). With a `[filter "x"] clean=` line and a `core.attributesFile`, or any other setting that runs a program, it runs on `git add` or on a status refresh. `checkRepoConfig` never reads this file. (c) A dropped `.template/config` plus `.template/info/attributes` is copied into a new repository by `git init --template` (repo.ts:605). `createRepository` then runs `git add` at repo.ts:627, before the `checkRepoConfig` at repo.ts:716. Who: the same dropper as rounds 1 and 2. With what: a support file or folder next to the repositories. What they get: a program run under the person's identity on any write (and, for b, on doctor), against AC-15/AC-19's intent. A dangling `.gitconfig-empty` link is also written through by `writeFileSync` (repo.ts:85). Case (a) is reasoned from git's documented `core.hooksPath` behaviour. Cases (b) and (c) are reasoned and not run. Possible fixes: keep the support paths outside `knowledge/`; or check at each use that `.no-hooks` and `.template` are empty real folders and `.gitconfig-empty` is a zero-byte regular file; or pass `--template=` with an empty value.
- F-2 · defect · src/modules/knowledge/repo.ts:845 · A path from the intent record can still delete a file outside the repository. `ownPath` checks the text of a path, and `refuseForeign` checks only the top-level `entries`/`proposals`/`open`/`decided` folders. A link one level down is never refused, for example `entries/sub` pointing to `/Users/<person>/somewhere`. The setup: a dropped repository with that link, an index entry `entries/sub/f` marked intent-to-add, a HEAD that does not hold it, and a record `{operation:"write", created:["entries/sub/f"], written:{"entries/sub/f":<hash>}}`. `revertInterrupted` then finds the path pending: git reports an index entry beyond a link as deleted. `stateOf` (repo.ts:1030) follows the leading link with `lstat`/`open`, so `O_NOFOLLOW` guards only the last part, and it hashes the outside file. When that hash equals the record's value, `restoreToHead` passes the path as `created` to `undoStaged`. `git rm --cached --ignore-unmatch` does not object to an intent-to-add entry, and `rmSync(join(repo.path, "entries/sub/f"))` deletes the person's file through the link. Who: the dropper. With what: a nested link, a crafted index and an intent record. What they get: deletion of any file under 256 KiB whose path and content they know (a checked-out public LICENSE or README, for instance). This rests on two behaviours of git I reasoned from its source and did not run (see below). A possible fix: refuse a path when any of its parent folders under the repository is not a real folder (lstat each part), in `stateOf`, `undoStaged` and `restoreKept`.
- F-3 · advisory · src/modules/knowledge/repo.ts:963 · `readIntent` and `restoreKept` (repo.ts:1007) read their dropped files with `readFileSync`, which follows a link, has no cap and blocks on a FIFO. A FIFO at `.git/wizardingcode-op.json` hangs every command on that repository, and the git timeout does not cover it. `readRegularFile` would close this.
- F-4 · advisory · src/modules/knowledge/repo.ts:444 · `.git/objects/info/alternates` is not refused next to `commondir` and `config.worktree`. A dropped repository can make git read objects from any repository on disk, and a crafted HEAD can then check those objects out into `entries/` by `restoreToHead`. No program runs and nothing leaves the machine in this part, but it is the next thing to refuse before sync lands.

Round two's defects checked against the current code:
- R2 F-1 (header tokenizer) is closed. Verified from the code: `ALLOWED_SETTINGS` is an allow list, and `CONFIG_HEADER` takes any number of headers per line. I compared `CONFIG_SPACE`/`CONFIG_KEY` with git's `git_parse_source`/`get_base_var`/`get_value` (reasoned from git's source, not run). I found no line where git sees a setting the store misses or reads as allowed. Every header git reads is on a physical line the store also reads. Continuation lines are read as settings, so the store is stricter. `\v`/`\f` count as space for the store but are an error for git, which refuses the file. Escapes in a subsection are kept raw, but any subsection is refused. A partial BOM is an error for git. NUL, a lone `\r` and `\r` before `=` give the same result in both or are refused by both. probes/security-round-three.md case 1 matches.
- R2 F-2 (nested repository) is closed for `statusOf`, verified from the flag at repo.ts:775. Reasoned: `git rm` could start a child `git status` inside a gitlink through `bad_to_remove_submodule`, but every rm path comes from status output, which hides gitlinks with `--ignore-submodules=all`. Adopt refuses a trailing-slash path, `.gitmodules` is refused, and `submodule.recurse=false` is set. Probe case 2 matches.
- R2 F-3 (intent naming `.git/config`) is closed, verified from code: `readIntent` requires `ownPath` on `existed`, `created` and the `written` keys, a known operation and a `KEPT_NAME` match, and `restoreKept` writes only `entries/<name>`. The remaining intent-path risk is F-2 above.
- A-6 is closed: `writeFileAtomic` and `existsOnDisk` are in `createRepository`. A-7 is half closed: `undoStaged` now applies `ownPath`, but the guard is on text only (F-2).
- personal-data: nothing new in this round's change beyond README wording. ADR 0024's retention and erasure text still answers Q4.
- data-migration: nothing new in this round's change. The round-two advisories (irreversible drop with a stated reason and a backup first, backup rotation) stand.
