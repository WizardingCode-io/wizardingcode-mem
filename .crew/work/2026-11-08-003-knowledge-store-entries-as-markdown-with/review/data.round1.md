# data findings for 2026-11-08-003-knowledge-store-entries-as-markdown-with
reviewer: review-data
read: 14 files, the schema and migrations read (src/store/migrations/0001_init.sql for `meta`, `projects`, `project_aliases`; the core MIGRATIONS list; ADR 0020 "Migrations" for what versions 1 to 5 created), risk areas: data-migration, personal-data

## Findings
- F-1 · defect · src/modules/knowledge/index-store.ts:488 · `rebuildRepo` reads the files first (line 457) and only afterwards, inside the transaction, takes the head and fingerprint it records (`headOf`/`fingerprintOf` at 491-492). A file added or renamed in that gap by a hand edit (an editor or Obsidian save, which no lease covers), or by an engine write racing the unleased `ensureFresh` in `readEntry` (src/modules/knowledge/store.ts:725), ends up in the recorded fingerprint but not in the rows. `ensureFresh` (index-store.ts:559) then sees a match and never rebuilds, so the entry stays missing from `listEntries`/`countOpen` until some later change to the folder. Rubric questions 1 and 3 (index consistency; ordering of a step around a transaction). The fix is to take the head and fingerprint before `readRepoFiles`. `settle` → `recordRepoNow` (index-store.ts:158-159) has the same capture-after pattern.
- F-2 · defect · src/modules/knowledge/migrations/0006_knowledge_store.sql:45 · `knowledge_entries.author`, plus `knowledge_proposals.proposed_by`/`decided_by` (lines 67-69), store a person's name. The same name, and an e-mail derived from it (src/modules/knowledge/author.ts), is written into git commits that are never rewritten. Neither ADR 0024 nor the README says how long these are kept or how they are erased. The spec's "Personal data" line only says where they live. The project does state retention elsewhere (`compact`, `history forget`), so this falls under rubric question 5, personal data without stated retention or erasure. Removing the name needs a history rewrite and a re-index, and that should be said.
- F-3 · advisory · src/modules/knowledge/migrations/0006_knowledge_store.sql:7 · The step that drops the withdrawn module's `knowledge_entries`/`knowledge_fts`/`knowledge_proposals`/`promoted_memories` deletes data and cannot be undone. The reason is stated (line 5, ADR 0024:119, objection O-1), and `backupVersion` (src/store/db.ts:299-302) takes a `VACUUM INTO` copy first whenever `module_migrations` has a row. So this is not a defect. Note that the copy is pruned to `BACKUPS_KEPT = 2` (db.ts:33) by later migrations. Rubric question 1.
- F-4 · advisory · src/modules/knowledge/migrations/0006_knowledge_store.sql:12 · The step drops `injections_memory_shown` and `injections_memory_contexts`, two indexes on the core table `injections`. They belonged to the withdrawn module, and no core query in src/ relies on them (grep), so no reader loses an index. It is still an index removed from a core table, and the comment does not say it. Rubric question 1.
- F-5 · advisory · src/store/db.ts:143 · On a store that ran the withdrawn module, the first open after the upgrade is usually a hook. That open runs a full-database `VACUUM INTO` and the drops while the second connection holds `BEGIN IMMEDIATE`, and other writers wait up to their busy timeout. This matches the core runner and is stated in the spec and ADR. It is one-time, and only on such stores. Rubric question 6.
- F-6 · advisory · src/modules/knowledge/index-store.ts:106 · Proposal row ids for files with no usable id are `file:<file name>`, and duplicates are `dup:<file name>`. The name alone does not include the folder, so the same name under both `proposals/open/` and `proposals/decided/` produces the same `(repo_id, id)`. `INSERT OR REPLACE` (line 99) then silently replaces the open row with the decided one, which loses that file's listing and its problem. Using the path (`open/…`, `decided/…`) would avoid it. Rubric question 2/4.
- F-7 · advisory · src/modules/knowledge/index-store.ts:86 · `stateOf` indexes a file under `proposals/decided/` that has no `decision` key as `rejected`. `parseProposal` (entry.ts:449-453) records a problem only for a wrong value, not a missing one, so a hand-moved proposal counts as rejected with no problem shown. Rubric question 4 (a missing value read as present).
- F-8 · advisory · src/store/meta.ts:139 · `key LIKE ? || '%'` with a bound pattern cannot use the `meta` primary key, so it scans `meta` every time `anyLeaseActive` runs. The table is small. A range `key >= ? AND key < ?` would seek. Rubric question 2.
- F-9 · advisory · src/modules/knowledge/resolve.ts:98 · `SELECT alias FROM project_aliases WHERE project_id = ?` has no index on `project_id` (the primary key is `alias`, WITHOUT ROWID). `scanRepos` (resolve.ts:312-313) runs it once per project, plus `rowAt`/`rowFor` once per folder. The table is small and this is never on a hook path, and existing core queries scan it the same way (see Outside the change). Rubric question 2.

## Outside the change
- src/store/migrations/0001_init.sql:14 · `project_aliases` has no index on `project_id`, and existing readers already filter on it (src/core/project.ts:79, src/links/suggest.ts:42, src/retrieve/staleness.ts:15). Debt, advisory.

## Not answerable
- Migrations (question 1): whether the withdrawn module's migrations 1 to 5 created any trigger or view that references the dropped tables, especially on a core table such as `memories` or `injections`. Its SQL is not in the tree, and ADR 0020 lists only tables and indexes. A trigger left behind would break core writes after migration 6.
- Availability (question 6): how long the first open takes on the author's store (backup size and the drop under the write lock). No measurement is in the review inputs, and I ran nothing.
