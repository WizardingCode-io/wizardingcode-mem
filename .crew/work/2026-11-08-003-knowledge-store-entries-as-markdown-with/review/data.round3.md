## Findings
- F-1 · advisory · src/modules/knowledge/store.ts:359 · Carried from round two, unchanged in the code. `settle` takes the fingerprint after the files are written and committed. A file a person adds between the undisturbed check (store.ts:299) and line 359 is counted in the fingerprint but never read. It stays on disk and untracked, `doctor` reports it, and `adopt` or `rebuild` indexes it. ADR 0024:168 states this limit. Rubric Q3.
- F-2 · advisory · src/modules/knowledge/migrations/0006_knowledge_store.sql:7 · Carried, unchanged. The drop of the withdrawn module's tables cannot be undone. Its reason is stated, a backup is taken first, and that backup rotates out under the two-backup limit (ADR 0024:172). Rubric Q1.
- F-3 · advisory · src/store/db.ts:143 · Carried, unchanged. A store that ran the withdrawn module gets a one-time `VACUUM INTO` while the write lock is held. This is stated. Rubric Q6.
- F-4 · advisory · src/modules/knowledge/resolve.ts:94 · Carried. `project_aliases` is filtered by `project_id`, which has no index. `learnAliases` now runs this read twice per write open: once without the lease (repo.ts:665-672) and once again under it. The table is small and the read is off the hook path. Rubric Q2.
- F-5 · advisory · src/modules/knowledge/repo.ts:663 · `learnAliases` rewrites `knowledge.json` and commits it without writing an intent record. If the process is killed between line 663 and the commit, the changed manifest is left with nothing to revert it. The next `learnAliases` sees the file dirty and backs off. `adopt` then commits the engine's own alias change as the person's, which goes against the function's own comment ("never left for adopt to credit to someone"). No data is lost, and the alias is right. Rubric Q3.
- F-6 · advisory · src/modules/knowledge/store.ts:881 · `keepBytes` writes a copy of the person's entry bytes under `.git/` before `writeIntent` (line 896) names that file. A process killed between the two lines leaves a `wizardingcode-kept-*.json` that no record names, so no later path ever removes it. The same happens when `readIntent` rejects a record and line 1060 removes it without calling `dropKept`. The copy is entry text that ADR 0024's "Personal data" erasure steps (rewrite history, delete the folder) do not mention. The window is a single atomic file write wide. Rubric Q5.

What the round-three change does to stored data, checked against the code:
- db.ts:296 (`owner.get(migration) as string`) changes nothing in behaviour. `pending` returns the same `Migration` objects (`[...schema.migrations].sort` copies the array, not the elements), so the map always holds the key. If it ever did not, the bound null would hit `module TEXT NOT NULL` (db.ts:241) and the migration would fail loudly. Before, it would have recorded a row under the module "". That is the safer of the two.
- The per-path revert (repo.ts:1063-1105) closes round two's "landed decided once" and wrong-message advisories. A path that is clean against HEAD is now skipped, so the never-written path in probes/partly-written-operation.md case 3 is no longer reported. What each outcome leaves behind:
  - Interrupted write, commit not landed: the files go back to HEAD. The recorded head did not move and `settle` was never reached, so the index rows still describe HEAD. The fingerprint may differ because the folder mtime changed, which costs one extra `rebuildRepo` and nothing else.
  - Commit landed but killed before `settle`, or before adopt's `rebuildRepo`: every path is clean, the record is cleared, and `ensureFresh` (index-store.ts:588) sees the moved head and rebuilds.
  - Interrupted adopt: the pending paths are unstaged and only entry files still as adopt left them get their kept bytes back. The rows were never rebuilt, so they match the state before the adopt.
- The record reader (repo.ts:960-981) rejects a record whose operation is unknown or that names any path outside the store's own. Every record the store itself writes passes: commit's paths are entries/, proposals/ or taxonomy.md, and adopt's come from `statusOf` over those four pathspecs, where git never reports a `.git` component, and a nested repository's `x/` is now refused at store.ts:838 before `keepBytes`. So a rejected record can only be one the store did not write. It is removed (line 1060) and nothing is acted on. The files and git's index are left exactly as found, and the database rows are untouched. The next `ensureFresh` compares head and fingerprint: a moved head or an added/removed file means a rebuild, and that rebuild marks any dirty path CHANGED_OUTSIDE through `changedPaths`. An edit in place stays the design's stated dirty-check case. Rows and files cannot drift apart for good on this path.
- `learnAliases` under the repository lease (repo.ts:674-688) moves HEAD without updating `knowledge_repos.head`. The next `ensureFresh`, or the write's own `settle`, puts that right. The manifest is not an indexed row, so nothing is lost.
- Round two's F-2 is closed. ADR 0024:168 now says the window runs from the folder check to the indexing, for the time of the write's git calls. It quotes about 50 ms as measured; the upper bound is still the git timeout.
- Personal data: no new column. The intent record's `writer` (the name) is transient under `.git/` and is removed with the record, including a rejected one. The new adopt `written` map holds only hashes. The only open point is the kept bytes in F-6.
