## Findings
- F-1 · advisory · src/modules/knowledge/index-store.ts:589 · The new refusal protects only `rebuild`. A `write` under a second data directory creates `knowledge/` there and gives the project a `-2` folder, as probe (a) in known-limits-round-nine.md shows. From then on `rebuild` there is no longer refused, and it forgets the first data directory's rows; a project with only a `path:` alias then comes back only as an orphan. This is now stated in ADR 0024's known limits, the first directory's files are never touched, and no hook, tool or view reads the index yet. So it is a stated limit with a manual way back, not a silent loss.
- F-2 · advisory · src/modules/knowledge/index-store.ts:106 · The refusal message cannot say which data directory holds the knowledge, because the rows keep only relative paths. It also does not name `WIZARDINGCODE_MEM_STORE_DIR`, which is the setting that makes two data directories share one database. Its second way out ("make it again, empty, and run rebuild once more") forgets every row in the scope, and for a project with only a `path:` alias that cannot be undone. The message does not say so. A person who gets here by mistake (for example, they changed `WIZARDINGCODE_MEM_DATA_DIR` and forgot) can still get out from the message alone by taking the first way out. The cost is only that the destructive branch is described as a confirmation, without saying what it loses.
- F-3 · advisory · src/modules/knowledge/index-store.ts:103 · The refusal looks only at `knowledge/` itself. If `knowledge/` is there but `knowledge/projects/` was removed whole (or moved with the disk), `rebuild` still forgets every project's rows: they now read as "absent", and the refusal does not fire. This is the same "cannot tell gone from elsewhere" ambiguity one level down. A rerun under the right layout plus a write re-attaches projects with a remote or gitdir alias. Projects with only a `path:` alias come back as orphans (ADR known limit 1).
- F-4 · advisory · src/modules/knowledge/index-store.ts:561 · Carried from round eight's F-1, now stated in ADR 0024's known limits. A project folder that is still there but holds no repository keeps its old rows. In this round `rebuild` prints `<path>: not a repository` (knowledge.ts:239) but exits 0, and `doctor` warns. The next write puts the repository back in the same folder. The ADR now requires a future reader not to treat those rows as current. That requirement lives only in the ADR, so it should be carried into the spec of the item that first reads the index.
- F-5 · advisory · src/modules/knowledge/resolve.ts:121 · Carried from round eight's F-2, now stated in the known limits. A stray non-dot file under `knowledge/projects/` (`Icon\r`, `desktop.ini`) is a lasting orphan line and a `doctor` warning. It blocks nothing.
- F-6 · advisory · src/modules/knowledge/index-store.ts:595 · Carried. `kindAt` can still throw inside the deletion loop after the repositories were rebuilt. Rows deleted earlier in the loop stay deleted, and a rerun completes the job.
- F-7 · advisory · src/modules/knowledge/repo.ts:91 · Carried, partly addressed earlier. Refusals have code `invalid`, so `run` writes no log line (knowledge.ts:338), and the exit code is 1 as for any failure. The new refusal reaches stderr with its full text and exits 1, which is enough for a person at a shell but leaves no trace for anything after that.
- F-8 · advisory · src/modules/knowledge/repo.ts:351 · Carried. `gc.auto=0` is still not set; a collision with a detached gc is undone and a retry works.
- F-9 · advisory · src/modules/knowledge/index-store.ts:563 · Carried. A `locked` lease or a git timeout in one repository still stops the repositories after it.
- F-10 · advisory · src/modules/knowledge/repo.ts:1282 · Carried. An adopt's "was undone" still overstates. Separately (repo.ts:1245), a corrupt intent record is still reported as a version mismatch.

On the questions asked:
- **Can the new refusal stop a healthy store?** I found no way it can.
  - It fires only when both of these hold: `knowledge_repos` has rows in the scope asked for, and `lstat(<data dir>/knowledge)` gives ENOENT or ENOTDIR.
  - A store that has rows has written a repository, and every write creates `knowledge/` first. So in a healthy store the folder is there.
  - Any other lstat failure (EACCES, EIO) is still a refusal that names its code (repo.ts:82-92), not "absent".
  - A link or a file at `knowledge/` reads as "other", not "absent", and `refuseLinkedRoots` handles it.
  - A scope with no rows is not refused. Mutants 4 and 5 in round-nine-mutations.md are killed.
  - One case I reasoned through but did not probe: a data directory that is a link to a disk that is not mounted. The refusal fires there, which is the protective outcome. Before this round, `rebuild` there would have forgotten everything. Following "make it again" through a dangling link fails at `mkdir` rather than forgetting anything.
- **Can a person get out from the message alone?** Yes. The message names the missing path, the number of repositories, that nothing was forgotten, and both ways out. It goes to stderr with exit 1 (knowledge.ts:339-342). The limits of the message are in F-2.
- **`taxonomyFor`.** It now returns null for a link or a file at the root's name, so the root's taxonomy is not read through a link. The root is refused by name in the same run. Mutant 6 is killed by two tests. Before this round, a link there could have marked a project's entries against a taxonomy outside the store. The cost now is that the project's areas go unchecked for that run, which is visible because the root's refusal is printed. An unlookable root name raises a refusal, which `inEachRepo` sets aside.
- **The two tests that were missing in round eight** (test-quality's gate) are now there. Mutants 1 and 2 are killed.
