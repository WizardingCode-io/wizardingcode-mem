# risk findings for 2026-11-08-003-knowledge-store-entries-as-markdown-with

## Findings
- F-1 · advisory · src/modules/knowledge/repo.ts:1056 · This round added a cap. `restoreKept` now reads the kept bytes with `readRegularFile(file, RECORD_MAX_BYTES)`, which is 64 MiB. But `keepBytes` (repo.ts:1032) writes with no cap, and base64 makes the file 4/3 the size of the entries. So any adopt of more than about 48 MiB of entries (around 2,400 files of 20 KiB, far under the 5,000 × 256 KiB the folders allow) makes kept bytes the reader then refuses. A large adopt is also the one most likely to hit the 15 s git timeout. When that adopt fails or is killed, two paths go wrong:
  - In adopt's own failure path (store.ts:931), `restoreKept` returns early without writing anything back and without removing its file. `clearIntent` then leaves that kept file under `.git/` with no record to remove it, which breaks the ADR 0024:77 promise.
  - In the revert at the next open (repo.ts:1145-1146), nothing is written back, `dropKept` deletes the only copy of the person's original bytes, and the report says "was undone".

  The person's text survives inside adopt's stamped rewrite, so no content is lost. What is lost silently is their own frontmatter (for example `author` and `version`), and the message is false.
- F-2 · advisory · src/cli/commands/knowledge.ts:345 · With one refused repository, `list`, `rebuild` and `adopt` now print valid output for the others on stdout and still exit 1. Before this change, the same refusal also exited 1, but with no output. So a script, or the viewer later, cannot tell "one repository was refused" from "the command failed" by the exit code. One that treats 1 as total failure throws away good output. Also, only `invalid` is caught per repository (knowledge.ts:224-225). A `git` timeout or a `locked` lease in one repository's adopt still stops the repositories after it. The commits already made stay, and each is atomic. ADR 0024:172 states the exit code, and nothing reads it yet. A distinct code for a partial result would cost one line now and avoid a breaking change when the viewer calls these commands.
- F-3 · advisory · src/modules/knowledge/repo.ts:1007 · Round three's F-3 is closed for the record: a rejected record is now removed, its kept bytes with it, and reported (repo.ts:1113-1121). Two things remain:
  - **A rollback across a release can delete kept bytes.** A record is rejected when its `operation` is not in this binary's `INTENT_OPERATIONS` (repo.ts:945). If a later release adds an operation that keeps bytes and a person rolls back after an interrupted run, this binary deletes the kept bytes (`dropKept`, repo.ts:1114) and nothing is put back. ADR 0024:201 now tells the sync part to widen `ALLOWED_SETTINGS` in the same release. It says nothing about adding an operation name.
  - **The report can blame the wrong writer.** A record that is over the cap, or that cannot be read, is reported as "not one the store wrote", even when the store wrote it.
- F-4 · advisory · src/modules/knowledge/repo.ts:304 · The three git mechanisms were run only on macOS with git 2.54.0 (ADR 0024:173, probes/security-round-four.md:35). Reading git's behaviour, each one fails closed if it behaves differently on another system:
  - **The hooks path.** Pointing `core.hooksPath` at a file makes git look for `<file>/pre-commit`. That lookup fails with ENOTDIR/ENOENT on any OS, so no hook runs. If some git rejected a hooks path that is a file, every call would fail at the first `status`, before any write, and the person would see the git error on stderr and in the log.
  - **The template (repo.ts:598).** If `--template=` copied the default template, a template `config` setting would be refused by `checkRepoConfig`, and the person would see the setting named. The default template has no config and its hook samples are not active. One cost: a repository refused right after `init` stays refused until the person edits it.
  - **The global configuration on Windows.** `/dev/null` depends on git-for-Windows mapping that name to `nul`. If it did not, git would treat the path as missing and read no global configuration. The one way this fails open is a git that neither maps the name nor skips it, and that reads `C:\dev\null`, a path a non-admin user can usually create. That was not run.
- F-5 · advisory · src/modules/knowledge/repo.ts:304 · A data directory from an earlier build of this branch keeps `knowledge/.no-hooks/`, `.template/` and `.gitconfig-empty`. Nothing refers to them any more: no `-c` setting, no environment variable, no `init` argument. `listRepos` reads only `workspace`, `shared` and `projects/`, so they are inert. Nothing removes them either. They exist only on machines that ran unreleased builds of this branch, so the person can delete them by hand.
- F-6 · advisory · src/modules/knowledge/migrations/0006_knowledge_store.sql:19 · Changing migration 6 before it ships costs nothing on a store that has not yet run it. Migrations carry no checksum (db.ts:293-297), so a database where an earlier build of this branch already recorded knowledge version 6 does not fail. It simply never gets the `DELETE`, and keeps the three `meta` rows that nothing reads. The delete has no down path, but the backup taken before migration 6 covers it. That backup is taken exactly when `module_migrations` has rows (db.ts:299-302), which is the only case where these rows exist.
- F-7 · advisory · src/modules/knowledge/repo.ts:1156 · Carried from round three's F-4. For an adopt, "was undone" still lists paths that were only unstaged. F-1 widens this: it also lists paths whose kept bytes were never written back.
- F-8 · advisory · src/store/db.ts:317 · Carried, and stated in ADR 0024 Known limits: the module migration pass is not contained, and `doctor` gives no warning when the module schema is behind.
- F-9 · advisory · .crew/work/2026-11-08-003-knowledge-store-entries-as-markdown-with/spec.md:321 · Carried: the rollback is stated with its reason but is manual, and the backup taken before migration 6's drop rotates away under `BACKUPS_KEPT = 2`.
