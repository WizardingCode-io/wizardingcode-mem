## Findings
- F-1 · advisory · src/modules/knowledge/index-store.ts:563 · When `rebuildAll` refuses a repository whose folder is still a real folder (for example, a person added a remote to `.git/config`), it keeps that repository's `knowledge_repos`, `knowledge_entries` and `knowledge_proposals` rows as they were last indexed. Only a folder that is gone or turned into a link loses its rows at :575, because `isDirectory` uses lstat. Keeping the rows is right: they are rebuilt from the files, nothing is lost, and every reader reaches them through `openRepo`, which refuses the repository (store.ts:188, taxonomy.ts:168, the CLI's `opened`). The ADR does not say it, though. ADR 0024:154 says erasure is to rewrite the history and then run `rebuild`, "which replaces the index rows". On a refused repository it does not, so the person's name stays in the index columns until the setting is removed. doctor's `over_cap` read (src/doctor/checks.ts:696) also still reads the stale row. Rubric Q5 and Q3: one sentence at ADR 0024:154 or :172 would close it.
- F-2 · advisory · src/modules/knowledge/migrations/0006_knowledge_store.sql:19 · The new `DELETE FROM meta` cannot be undone. Its reason is stated beside it (:17-18), and on a store that ran the withdrawn module it runs after the upgrade's backup, which db.ts:299-302 takes because `module_migrations` has rows there. It deletes only the three exact keys the probe found as constants in the withdrawn `promote.ts`. No code under review reads or writes them (the only `knowledge.` meta keys in src are `knowledge.lease:<path>`, meta.ts:134). The test fixture shows that a row which is not the module's survives. On a store where the keys are absent, or with no withdrawn module, the statement deletes nothing, and the backup is skipped correctly there. It runs in the same `BEGIN IMMEDIATE` as the drops (db.ts:133-149), so a failure rolls it back with them. This only notes that the one backup holding these rows rotates out like the dropped tables (ADR 0024 known limits). Rubric Q1.
- F-3 · advisory · src/modules/knowledge/store.ts:360 · Carried from rounds two and three, code unchanged. `settle` takes the fingerprint after the commit, so a file a person adds between the check at store.ts:300 and line 360 is counted in the fingerprint but never read. ADR 0024 states this limit, and `doctor` and `adopt` pick the file up. Rubric Q3.
- F-4 · advisory · src/store/db.ts:75 · Carried. On a store that ran the withdrawn module, the first open takes a `VACUUM INTO` backup while the write lock is held (db.ts:133-143). This is stated, but it has not been timed (see Not answerable). Rubric Q6.
- F-5 · advisory · src/modules/knowledge/resolve.ts:94 · Carried. `project_aliases` is filtered on `project_id`, which has no index. `learnAliases` runs this read once before the lease and once under it (repo.ts:648 and :651). The table is small and the read is off the hook path. Rubric Q2.

What the round-four change does to stored data, checked against the code:
- Round three's F-5 is closed. `learnAliases` (repo.ts:654-682) now writes its record before the manifest. The record's `written` hash is taken from the same `manifestText(next)` that `writeManifest` writes, so after a kill the next open finds the manifest as the engine left it and restores it from HEAD; it is not left for `adopt`. If the commit landed, the path is clean and the record is cleared. The failure path clears the record only after `undoStaged` succeeds; when that call throws, the record stays. That is the case the new resolve test covers.
- The new record cannot overwrite another operation's record. In `openRepo`, `revertInterrupted` runs first (repo.ts:713) and clears the record on every path it finishes (:1134, :1151, :1115). When another process holds the lease, both steps are skipped by `underOwnLease`. Writes call `ensureRepo` (store.ts:188) before their own `writeIntent` (store.ts:306).
- Round three's F-6 is closed. `adoptIn` now names the kept-bytes file in the record (store.ts:897-903) before `keepBytes` writes it. A kill between the two leaves a record whose kept file is absent. The revert then unstages and calls `restoreKept`, which returns quietly on a missing file. Nothing has been rewritten at that point, so the person's bytes are where they were and nothing is lost. A rejected record now drops the kept file it names, under its lease (repo.ts:1113-1121), and only a name that matches `KEPT_NAME`.
- Index and files: `rebuildAll` catches only `invalid`. A throw inside `rebuildRepo` rolls back its one transaction, so a repository's rows are either rebuilt whole or left as they were. The removal loop (index-store.ts:573-582) runs after the catch, so a refused repository no longer stops the removal of rows whose folder is gone. A path beyond a link is now `undefined` in `stateOf` (repo.ts, `reachedByFolders`), so it is only unstaged and reported, never restored or removed. That changes the files and git's index, not the rows. The next `ensureFresh` compares the head and the fingerprint, and the rebuild marks the dirty path. I found no path where rows and files stay apart, apart from F-1's refused repository, which is unreadable until the person removes the setting.
- Personal data: the person's name is now also in learnAliases' record under `.git/` (`writer`), from :658 until :682. Every write's record already held it there. The record is cleared on success and on the failure path, and by the next open after a kill. Both erasure routes in ADR 0024:154 (`rebuild` opens the repository, and deleting the folder removes `.git/`) remove it. No column or table changed.
