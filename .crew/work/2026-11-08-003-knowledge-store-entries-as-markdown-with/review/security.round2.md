## Findings
- F-1 · defect · src/modules/knowledge/repo.ts:463 · Round 1's F-1 is only partly closed. Someone who can drop a folder under `<data dir>/knowledge/` can still get a program run. They write `.git/config` with two section headers on one line, `[core][filter "x"]`, followed by `clean = <program>`, and add a `.gitattributes` line `* filter=x`. Git's parser treats a `[` after a closed header as a second section header. `checkRepoConfig` only reads the first header (regex at line 458), sets `line` to the rest (`[filter "x"]`), and finds no key there because the key regex at 465 needs a letter. The `filter` section is never seen, and `clean`/`process` are not in `REFUSED_KEYS`. The engine's `git add` (writes, adopt) and doctor's `git status` (src/doctor/checks.ts:796) then run the program. AC-19 says a `.git/config` with a filter section is refused, so this breaks it. The same trick hides `[include] path=<any file>`, `[includeIf …]` and `[diff "x"] textconv=` from the check.
- F-2 · defect · src/modules/knowledge/repo.ts:683 · `statusOf` runs `git status` without `--ignore-submodules=all`. A dropped folder whose `.git/index` (attacker-written) holds a gitlink at, say, `entries/sub`, plus an `entries/sub/.git/` with its own config defining `[filter "x"] clean=<program>` and an `entries/sub/.gitattributes`, makes git start a child `git status` inside that nested repository. `checkRepoConfig` never read that repository's config, and the `-c` overrides do not cover `filter.*`, so the program runs. This happens on `knowledge rebuild`/`list` through `changedPaths` (src/modules/knowledge/index-store.ts:375), on adopt (store.ts:840) and on doctor (checks.ts:796). It is another way, which the round asked about, for git to read an unchecked configuration in a folder dropped under `knowledge/`, against AC-15/AC-19. I reasoned this from git's submodule-status behaviour and did not run it.
- F-3 · defect · src/modules/knowledge/repo.ts:885 · `openRepo` checks the configuration (line 635) before `revertInterrupted` (line 636), and that revert writes paths named by files under the dropped folder's own `.git/`. The intent record `.git/wizardingcode-op.json` and `.git/wizardingcode-kept-<hex>.json` both come from the dropper. The path guard at 885 refuses only empty, `.` and `..` parts, not `.git`. So an intent with operation `adopt`, `existed: [".git/config", "entries/x.md"]` (x.md untracked so status is not clean) and `written[".git/config"]` set to the current file's hash makes `restoreKept` write the kept bytes, a config with a filter, over `.git/config` after it was checked. The rest of the operation (`git add`) then runs the program. Refusing any path whose first part is `.git` (or any path outside `entries/`, `proposals/` and the three root files) closes this. This rests on `git reset -q -- .git/config …` (line 757) not failing, which I did not run.
