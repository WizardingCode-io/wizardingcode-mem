## Findings
- F-1 · defect · src/modules/knowledge/index-store.ts:514 · The Design says the knowledge store refuses to read or write with `ModuleSchemaTooNewError` when the recorded module schema is newer than the binary's ("The Index", 4th bullet), and ADR 0024:193 says the same. The write functions call `requireSchema` (store.ts:389, 603, 675, 721, 791; taxonomy.ts:24, 94, 117, 155), but the read and rebuild entry points do not: `rebuildAll` (index-store.ts:514), `ensureFresh` (index-store.ts:553) and `listRepos`/`saveRow` (resolve.ts:256, 63). So `wizardingcode-mem knowledge rebuild` (src/cli/commands/knowledge.ts:207) and `knowledge list` (src/cli/commands/knowledge.ts:253, through `opened` and `ensureFresh`) will, on tables a newer binary wrote, delete and re-insert `knowledge_entries`/`knowledge_proposals` rows and insert or rewrite `knowledge_repos` rows with this binary's columns. The data-model contract (rubric Q2/Q3) says these tables are left alone. Fix: call `requireSchema(store)` at the top of `rebuildAll` and `ensureFresh` (or once in the CLI's `run` before any subcommand, plus in `rebuildAll`/`ensureFresh` for the later parts that call them), and add a test beside AC-3's for rebuild and list.
- F-2 · advisory · src/modules/knowledge/resolve.ts:244 · The engine extends a project's manifest aliases (`writeManifest`) outside any commit. That leaves `knowledge.json` dirty, `doctor` then reports it as "changed outside the engine", and `adopt` credits the engine's own change to the person. ADR 0024's Known limits admits this, but it reads Goal 2 ("every write is one commit with its author") and D-11 more loosely than the Design states. A commit of the manifest under the leases at the next write would keep that rule.
- F-3 · advisory · src/modules/knowledge/repo.ts:32 · Two import cycles inside the module: repo.ts ↔ resolve.ts (`openRepo` calls `resolveRepo`, and resolve uses repo's path and manifest helpers) and repo.ts ↔ author.ts (`createRepository` calls `personAuthor`, and author calls `gitUserName`). Both are function-level and safe at runtime, and the plan implies the second. But the base works to avoid cycles: migration.ts was made a leaf "without a cycle" (spec, The Index), and types.ts:1-2 says so too. Moving the path and manifest helpers (and `gitUserName`) into a leaf the three files share would remove both cycles.
- F-4 · advisory · src/doctor/checks.ts:625 · The doctor check builds a `KnowledgeStore` by hand with `db: db as Db`, where `db` may be null, instead of `openStore`. It also re-implements the module's folder listing with hard-coded `knowledge/<scope>` and `knowledge/projects` paths (`foldersByHand`, `projectFolders`, checks.ts:590-611) and the git version comparison (checks.ts:661-665) instead of the module's `repoFolder`/`older`. It works today, but the module's layout and rules now live in two places, and a null read through `store.db` would only fail at runtime.
- F-5 · advisory · src/doctor/checks.ts:746 · The doctor reads `knowledge.json` with `readFileSync`, which follows a symlink. The Design's rule is "symlinked files are not followed on read (`lstat`, then `O_NOFOLLOW`)", and the module's own `readRegularFile`/`readManifest` already do this. Use `readRegularFile`.
- F-6 · advisory · src/doctor/checks.ts:573 · The new Knowledge section is inserted below the docblock "Looks, and changes nothing…" that belonged to `runChecks` (now at :835). That comment now sits on the knowledge code and `runChecks` has none. Move it back above `runChecks`.
- F-7 · advisory · src/settings/settings.ts:19 · `WIZARDINGCODE_MEM_AUTHOR` joins `SETTING_KEYS`, so the settings API returns and accepts it. The viewer's contract type `SettingKey` (ui/src/api.ts:92-104) does not list it. The README says the viewer has no field for it yet. This follows the existing precedent of `WIZARDINGCODE_MODULES`, so it is advisory only.

On the decisions you asked me to judge against the base: splitting out `scanRepos`/`readRepoFiles` keeps the read-only doctor away from writes, which matches the Design. Acting on the intent record only when no other process holds the lease, and only forgetting an operation whose commit landed, both stay inside the failure rule. `removeArea` doing a full `rebuildRepo` instead of `ensureFresh` is stricter than the Design and crosses no boundary; it is what AC-17 asks for. The knowledge check inside src/doctor/checks.ts, importing module code, is where the Design puts it, and doctor is not one of the surfaces ADR 0019 bars from naming a module. tests/helpers/knowledge.ts is test scaffolding and is recorded in CLAUDE.md. `src/store/db.ts` importing `src/engine/module-schemas.ts`, which imports only `src/modules/knowledge/migrations.ts`, is the dependency the Design calls intended, and it keeps module code off the hook path. None of these is a finding.
