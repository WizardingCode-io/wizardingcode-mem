## Findings
- F-1 · advisory · src/modules/knowledge/repo.ts:32 · Carried and unchanged: the function-level import cycles repo.ts↔resolve.ts (repo.ts:32) and repo.ts↔author.ts (repo.ts:29) remain. They are safe at runtime (Q6). `commitChange` now calls `identityOf` from author.ts, which uses the existing edge more but adds no new cycle. The fix is as before: move the path, manifest and folder helpers and `gitUserName` into a leaf module, the way schema.ts is one.
- F-2 · advisory · src/modules/knowledge/errors.ts:24 · Round four's F-2 is closed in the form it offered. The predicate now exists once (`isRefusal`, errors.ts:28), and `inEachRepo` is its only user for the "set aside and go on" rule. The CLI no longer decides it. What remains is how the code is read (Q3/Q6). The docstring at errors.ts:24 now defines `invalid` as "the store refusing one repository as it stands". But the module still raises `invalid` for bad input: store.ts:100 (and :758, the agent-adopts check, reachable inside `adopt`), taxonomy.ts:21 and entry.ts:67. None of these is reachable today from the CLI's three `inEachRepo` callers. `adopt` gets a person from `personAuthor`, and its only `invalid` mid-work is the nested repository at store.ts:786, which is a repository refusal. Still, a later caller passing a write that checks its input would see an input error set aside as "a refused repository". The fix: give repository refusals a code of their own, or say in errors.ts:24 that `invalid` covers both.
- F-3 · advisory · CLAUDE.md:22 · The file map now sits a little apart from where the two new single places live (Q1). CLAUDE.md maps `index-store.ts` as "the index rebuilt from the files", but `inEachRepo` (index-store.ts:551) is now also the loop `adopt` writes through. It maps `store.ts` as "the writes", but the core of every write, `commitChange`, is at repo.ts:1014. The same paragraph names `commitChange` and `inEachRepo` without saying which file holds them. Neither crosses a boundary. repo.ts already held the parts `commitChange` puts together (`writeIntent`, `stagePaths`, `removePaths`, `commitPaths`, `undoStaged`, `clearIntent`), and putting it there spares `learnAliases` a repo→store edge. The CLI already imported `rebuildAll`, `ensureFresh` and `listEntries` from index-store.ts, and it now imports neither `openRepo` nor `listRepos`, so the entry point reaches less far into the module than before. The fix is one clause in the map: "`repo.ts` … and the write's core `commitChange`", "`index-store.ts` … and `inEachRepo`".
- F-4 · advisory · CLAUDE.md:22 · CLAUDE.md says `refuseForeign` refuses "a link anywhere inside its `.git`". The code (repo.ts:162-184) and ADR 0024:86 say something else: they refuse anything but regular files and folders (so a fifo or socket as well, not just links), and they do not walk the folders under `objects/`. "Anywhere" claims more than the walk does. Use the ADR's wording.
- F-5 · advisory · docs/adr/0024-knowledge-module.md:155 · The new sentence about a refused repository's rows went in just before "A command that does this is a later part's work". That sentence now reads as if it refers to the refused-repository case, not to erasure. Move the new sentence after it, or name the erasure command in the last sentence.

It now also says that the first error is the one thrown. `store.commit` (store.ts) is a thin wrapper that adds the fingerprint. `learnAliases` now writes the manifest under the same rule, which ADR 0024:35 already required ("writes its record"). `Change` moved to repo.ts with no outside user of the old `Commit` name. `INTENT_OPERATIONS` is no longer exported, which narrows the surface.

The behaviour (go on, say each refused one on stderr, exit 1) is ADR 0024:173, and that line names `list`, `rebuild` and `adopt`, the function's three callers. `rebuildAll` keeps its return shape (now `InEachRepo<RebuildResult>`), and the CLI is its only reader.

- The `.git` walk has its line at ADR 0024:86. The doctor calls `refuseForeign`, so it gets the walk too, and CLAUDE.md's "same two guards" still holds. The new code comments point to "ADR 0024, known limits", and line 174 holds that line. The ADR's added "later parts" sentence (a new operation that leaves a record needs the same care as `ALLOWED_SETTINGS`) matches the reworded revert message at repo.ts (the "not one this version of the store writes" message). The adopt message's control characters written as `?` has its line at ADR 0024:116. The new latency figures replace the old ones in place.
