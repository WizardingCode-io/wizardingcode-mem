## Findings
- F-1 · defect · src/modules/knowledge/index-store.ts:592 · `rebuildAll` takes any `lstat` failure as "the folder is gone" (`isDirectory` at repo.ts:117-123 returns false on every error). `projectFolders` (resolve.ts:110-113) reads a `knowledge/projects` it cannot list as empty. `refuseLinkedRoots` (repo.ts:82) does not refuse a folder that cannot be searched, because `existsOnDisk` is false on EACCES as well. Take a `knowledge/` or `knowledge/projects/` whose permission bits are off (a person's chmod, or a restore tool). `knowledge rebuild` then deletes the `knowledge_repos`, `knowledge_entries` and `knowledge_proposals` rows of every repository under that folder, although the folders are still there. The `knowledge_repos` row is the only thing that ties a project with no remote and no gitdir to its folder (`strong`, resolve.ts:26). ADR 0024's known limits state that such a project is then reported as an orphan and never re-attached. Its next write creates a fresh `<name>-2` folder, so the repository it had, with the person's name in it, is cut off from its project. This is the case this round closed for `.git` (refuse anything but ENOENT), left open one level up. The fix is narrow: treat only ENOENT as gone, and refuse a root that cannot be searched or listed (Rubric Q1: a deletion of rows whose source is present).
- F-2 · advisory · src/core/git.ts:63 · `headOfGitDir` now reads as "no commit" any HEAD whose `ref:` is not a clean name under `refs/`. git's own `validate_headref` refuses those same HEADs, so the set is only ones git cannot use either. Two things follow:
  - **Read paths.** `openRepo` (repo.ts:760-761) returns null, and `inEachRepo` (index-store.ts:562-563) gives that repository neither a result nor a refusal. `rebuild` prints "not a repository" and exits 0. The folder exists, so the delete loop at :592 keeps its rows. They stay as last indexed, the author name included, and are never shown by `list`. ADR 0024 says rows stay for a *refused* repository, not for this state.
  - **Write paths.** `createRepository` runs on a repository that has history (repo.ts:763). It rewrites `.gitignore` with the store's text (:672) before `git add` fails under `GIT_CEILING_DIRECTORIES`. Nothing is committed, the error is code `git` and no row changes. The only file touched is the store's own `.gitignore`, which history keeps (Rubric Q3, Q5).
- F-3 · advisory · src/modules/knowledge/migrations/0006_knowledge_store.sql:19 · Carried, unchanged. The `DELETE FROM meta` of the withdrawn module's keys cannot be undone. Its reason is stated at :17-18, it runs after the pre-upgrade backup, and probes/withdrawn-module-meta-rows.md shows the keys have no other writer (Rubric Q1).
- F-4 · advisory · src/modules/knowledge/store.ts:302 · Carried, code unchanged. `settle` takes the fingerprint after the commit, so a file added by hand during the write's git calls is counted but never read. This is a stated known limit (ADR 0024, about 40 ms) (Rubric Q3).
- F-5 · advisory · src/store/db.ts:75 · Carried. The one-time `VACUUM INTO` backup under the write lock, on a store that ran the withdrawn module, has not been timed (Rubric Q6).
- F-6 · advisory · src/modules/knowledge/resolve.ts:94 · Carried. `project_aliases` is read by `project_id`, which has no index. This is on a write path, off the hook path, and the table is small (Rubric Q2).

What I checked against the facts given:
- **Round five's F-1 is closed.** The walk now lets through exactly one socket, `fsmonitor--daemon.ipc`, at the top of `.git` only (repo.ts:369, `entry.isSocket()`). Anything else that is neither a file nor a folder still refuses, which ADR 0024's known limits now state. A refusal still freezes rows, as the separate paragraph in the ADR says.
- **A `.git` folder that cannot be listed** now throws `invalid` (repo.ts:357-361), and only ENOENT is skipped. The repository is set aside by `inEachRepo` before `work` runs, so its rows are neither rebuilt nor removed. That is the stated behaviour.
- **`knowledge/` or `knowledge/projects/` as a link or a file.** `refuseLinkedRoots` uses `lstat` (repo.ts:117-133), so a link is never taken for a folder. It runs in `scanRepos` (resolve.ts:287), which `listRepos` calls first. `inEachRepo` calls `listRepos` at index-store.ts:556, outside its try, so the refusal leaves `rebuildAll` before the `SELECT`/`DELETE` loop at :585-599. No row is read, written or deleted, and `saveRow` (resolve.ts:266) is never reached. `resolveRepo` refuses at :204, before `ensureParents`, `writeManifest` or `saveRow`, so a write creates nothing and records nothing. The gap is the unsearchable case in F-1.
- **The head the index records.** `recordRepo` (index-store.ts:136) and `settle` (store.ts:301) record `headOf` after a commit that succeeded, which needs a valid HEAD, so a recorded head is never the new null by accident. If HEAD later turns odd, `ensureFresh` (index-store.ts:611) is not reached, because `openRepo` returns null first (F-2). If it were reached, null against the recorded sha would rebuild once and then settle on null, which is consistent.
- **CLI `list` and `adopt` printing inside `work`.** In `list`, the rows are read per repository after that repository's own `ensureFresh` (or as they stand while the lease is held), and the name is printed only after the refresh. A refusal in the refresh prints nothing for that repository, and `rebuildRepo`'s single transaction (index-store.ts:516-524) leaves its rows either whole or as before. In `adopt`, the line is printed after the commit and `settle`. The listing makes two queries per repository, not per row, so there is no N+1.
- **Personal data.** No column or table changed. This round removes two ways the writer's name was written outside the store: a whole project repository created through a linked `knowledge/projects`, and a reflog line through a link in an unlistable `.git` folder. The retention and erasure text in ADR 0024 is unchanged in substance. The refused-repository sentence now stands as its own paragraph, which resolves the architecture reviewer's placement advisory.
