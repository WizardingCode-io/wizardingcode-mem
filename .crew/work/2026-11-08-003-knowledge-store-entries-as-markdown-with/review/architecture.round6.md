## Findings
- F-1 · advisory · CLAUDE.md:22 · CLAUDE.md still says the doctor "reads by hand under the same two guards". As of this commit, knowledgeRepositories carries three of the module's guards by hand: refuseLinkedRoots (src/doctor/checks.ts:610), refuseForeign (:738) and checkRepoConfig (:792). The same edited sentence groups refuseLinkedRoots inside openRepo's first refusal, so "two" can be read either way, and the map no longer says which guards the exception has to copy. The exception still holds as code (Q1): with no database, the doctor lists folders through its own foldersByHand/projectFolders and never reaches scanRepos, so the hand call at :610 is what keeps that path under the new rule. With a database the rule now runs twice (at :610 and inside scanRepos at resolve.ts:287), which is harmless. Note what this means: every guard openRepo or resolveRepo gains must be copied into the doctor by hand, and nothing ties the two together. This round the copy was made. Fix: name the guards in CLAUDE.md, for example "under the same guards (`refuseLinkedRoots`, `refuseForeign`, `checkRepoConfig`)".
- F-2 · advisory · src/core/git.ts:53 · The refs/ rule (git.ts:61-66) is a git-format rule in core's process-free git reader, which is where such rules belong (Q1). It is reached only from the knowledge store (repo.ts:784, the only caller of headOfGitDir). readGitInfo, the hooks' path (git.ts:111-117), still parses HEAD on its own and calls resolveRef unchanged, so the hook path reads exactly as before. Two things remain. First, headOfGitDir's docstring (git.ts:53-56) does not state the new rule, while ADR 0024:88 states it as the store's. Second, core now has two HEAD readers that disagree on what a ref may be (Q6). Fix: add one clause to the docstring ("followed only to a name under `refs/`; anything else is read as no commit").
- F-3 · advisory · src/modules/knowledge/repo.ts:29 · Carried and unchanged: the function-level import cycles repo.ts↔resolve.ts and repo.ts↔author.ts. refuseLinkedRoots lives in repo.ts and resolve.ts calls it over the existing edge, so the commit adds no new edge.
