## Findings
- F-1 · advisory · src/modules/knowledge/repo.ts:937 · The round-1 defects at repo.ts:808 and :801 are closed. `revertInterrupted` now restores from HEAD (line 954), or writes back the kept adopt bytes (line 951), only for a path whose current hash still equals the intent's `written` value (line 943-946). `commit` (store.ts:303-311) and `adoptIn` (store.ts:886-896) fill that value. An edited path is only unstaged. A record with no `written` puts nothing back. The CLI now sends the report to stderr (knowledge.ts:306). Tests cover all of this (tests/unit/knowledge-repo.test.ts:736-858). One case is still wrong, a smaller one. Whether the commit "landed" is decided once for all paths together, at line 937. Suppose the commit did land and the person then edited one of its files. Every path is then treated as not landed. For an adopt, line 951 writes the pre-rewrite bytes over the other files, which already match the committed rewrite. Those files then differ from HEAD and have lost the `id`/`version` stamp, so the next `knowledge write` on them is refused as a hand edit until the person runs `adopt` again. No data is lost, because the rewrite is in HEAD and the bytes are the person's. No test covers the case of a commit that landed plus a later edit.
- F-2 · advisory · src/modules/knowledge/repo.ts:958 · The stderr report can describe the wrong thing, in two cases. (1) In the landed-then-edited case above, it says "was undone" for paths whose commit landed and where nothing was undone. (2) Suppose an operation was killed after it wrote some of its files but before the rest. The paths it never wrote show HEAD's content or no file. That differs from `written`, so they are reported at line 969 as "changed after it; run wizardingcode-mem knowledge adopt", though the person never touched them. In both cases the only first-hour signal tells the person to do the wrong thing. The tree itself stays safe.
- F-3 · advisory · src/store/db.ts:317 · Unchanged from round 1, and now stated as a known limit (docs/adr/0024-knowledge-module.md:163). `migrateModules` is not contained. A failing module pass makes `openDb` fail on every hook, and memory goes dark over a module that no hook reads. `CREATE TABLE knowledge_repos` (0006_knowledge_store.sql:21) still has no `IF NOT EXISTS`. `doctor` still warns only on "too-new" (src/doctor/checks.ts:704), never on "behind", and its database check never runs the pass. So the stated limit has no way to be seen in the first hour other than the hook log.
- F-4 · advisory · .crew/work/2026-11-08-003-knowledge-store-entries-as-markdown-with/spec.md:321 · Unchanged. The rollback is stated with its reason, but it is manual and there is no cleanup command. The one backup taken before migration 6's drop is now documented as rotating away after two later upgrades (ADR 0024:164). `BACKUPS_KEPT = 2` is at src/store/db.ts:33.

## Outside the change
- src/store/db.ts:132 · The upgrade runner waits up to 10 s under `BEGIN IMMEDIATE`. This item makes every user take one upgrade at the first open, usually a prompt hook, so that prompt can stall once if a drain holds the write lock. The core migrations already carried this.
- tests/perf · The p95 hook-latency budgets were exceeded in one run while the medians stayed inside them. The roughly 9 µs module query cannot explain that. The flakiness predates this item, but it masks a real regression on the hook path.
