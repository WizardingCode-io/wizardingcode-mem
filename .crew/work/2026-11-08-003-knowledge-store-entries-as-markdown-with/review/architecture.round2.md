## Findings
- F-1 · advisory · src/modules/knowledge/store.ts:188 · `learnAliases` (repo.ts:585-609) is new. It commits `knowledge.json` in the project repository. It runs inside `openRepo` from `ensureRepo`, and `underLeases` calls `ensureRepo` while holding only the root's lease. The repository's own lease is taken later, at store.ts:204 (adopt has the same order at store.ts:824-830). So this commit is a write to the project repository without that repository's lease. That goes against the Design's lease rule ("Writes to one repository are serialised… key `knowledge.lease:<path>`", spec.md:137; step 3 before step 4, spec.md:149-150) and against learnAliases's own comment "under the leases" (repo.ts:583). Every project write takes the root's lease first, so today it is serialised against writes, but not against `rebuild`, `list` or the revert, which take only the repository's lease. The fix is to take the repository's lease before `learnAliases` commits: run it after store.ts:204 has the lease, or wrap the commit in `withRepoLeases(store, [repo.relative], …)`.
- F-2 · advisory · src/modules/knowledge/repo.ts:32 · Round 1's two function-level cycles are still there: repo.ts imports resolve.ts (`resolveRepo`, `projectAliasesOf`) and resolve.ts:8-17 imports repo.ts; repo.ts:29 imports author.ts and author.ts:7 imports `gitUserName` from repo.ts. The change widened the first cycle: resolve.ts now also takes `refuseForeign` and `existsOnDisk` from repo.ts. They are safe at runtime. The base still works to avoid cycles (migration.ts made a leaf, spec.md:237), and the change did exactly that with schema.ts, so the same move would remove these two. Moving the path, manifest and foreign-folder helpers and `gitUserName` into a leaf that the three files share would do it.
- F-3 · advisory · src/doctor/checks.ts:626 · Round 1's F-4 is fixed only in part. The version rule now uses the module's `gitTooOld` (checks.ts:663), and the manifest is read with `readRegularFile` (checks.ts:749), which closes round 1's F-5. But the doctor still builds a `KnowledgeStore` by hand with `db: db as Db` (checks.ts:626-636), and it still lists the folders itself with hard-coded `knowledge/<scope>` and `knowledge/projects` paths (checks.ts:591-612) instead of `repoFolder`. There is also a new effect. The doctor never goes through `openRepo` or `refuseForeign`, so the foreign-folder guard the change added (ADR 0024:80) does not cover it: `readRepoFiles` at checks.ts:784 lists an `entries` or `proposals` folder that is a link, and reads the files outside the repository it points to. Calling `refuseForeign(repo.path)` before line 784 (and reporting its refusal as a warning) would keep the doctor inside the boundary the module now draws.
- F-4 · advisory · src/modules/knowledge/index-store.ts:109 · Three things depart from the spec's Design, and ADR 0024, which this item adds and which is the project's base, records each one:
  - Proposal problem rows are keyed `file:open/<file>` and `dup:decided/<file>` (ADR 0024:125); spec.md:251 says `file:<file name>` and `dup:<file name>`.
  - `checkRepoConfig` refuses more than the Design lists: `extensions.worktreeConfig`, `textconv`, `command`, `driver`, and the `commondir` and `config.worktree` files (repo.ts:412-422, ADR 0024:79); spec.md:130 lists fewer.
  - `refuseForeign` (repo.ts:134, ADR 0024:80) and the alias learning in `openRepo` as a commit (ADR 0024:69) replace "the manifest's aliases extended" by `resolveRepo` (spec.md:120).

  None of them crosses a boundary. Code, ADR and spec.md now say different things, though, so the spec's Design should be amended so that the later parts, which build on it, read the ADR's version.

That fits the base's rule of keeping the dependency direction out of cycles. Round 1's F-2 (aliases extended outside a commit) is answered by `learnAliases`, apart from the lease noted in F-1 above. Round 1's F-6 (the doc comment of `runChecks`) is fixed: the comment is back at checks.ts:843.
