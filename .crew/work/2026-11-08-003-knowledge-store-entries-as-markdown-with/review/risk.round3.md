# risk findings for 2026-11-08-003-knowledge-store-entries-as-markdown-with
reviewer: review-risk
read: spec, plan, 11 files

## Findings
- F-1 · advisory · src/cli/commands/knowledge.ts:236 · One refused repository can stop much more than that one repository. Since this round, the allow list (repo.ts:312, enforced at repo.ts:716) refuses common hand-made settings: a `remote`, a local `user.name`, `branch.*`. The README (line 319 of the spec) tells people to back up `knowledge/` like any folder, and adding a remote and pushing is a natural way to do that. When one project's repository is refused:
  - `opened()` maps `openRepo` over every repository and catches nothing. So `knowledge list`, `adopt` and `rebuild` without `--scope` fail for all of them, and `rebuildAll` (index-store.ts:550) also stops before its orphan-row cleanup.
  - When the workspace repository is refused, every project write fails too, because `ensureRepo` opens the root first (repo.ts:726).

  ADR 0024:169 says only "every command on that repository". The spec's "Risks and rollback" section does not mention this case at all. Nothing is lost: files and history stay as they are, the message names the setting and the file on stderr, and `doctor` gives it a warn line (checks.ts:789). The fix is manual: the person deletes the line by hand. With `--scope`, the other scopes can still be used.
- F-2 · advisory · src/modules/knowledge/repo.ts:312 · `ALLOWED_SETTINGS` holds only `core.*`. The sync part named in ADR 0024:197 (ADR 0026, not written) will need `remote.*` and probably `branch.*` in these same repositories. Without them, every repository a sync configures would be refused by this release's binary, and a rollback across that deploy would leave the person locked out until they remove the lines. Only CLAUDE.md ("add to ALLOWED_SETTINGS only what the store itself writes") hints at this ordering. The ADR's "What the later parts add" section does not say that the later part must widen the list and must ship together with the code that reads it.
- F-3 · advisory · src/modules/knowledge/repo.ts:1060 · The new reader rejects a record silently. When `readIntent` returns null, the record is removed with no `report` and no log line, and the kept-bytes file it names stays under `.git/` forever (only `dropKept` removes these files, and nothing calls it on this path). Spec.md:314 promises that an interrupted operation is reverted "and reports it". Real records are always in a valid form, because `Intent.operation` is now typed and every path comes from the store or from `git status` limited to the store's folders. So in practice this only affects a record that was dropped there or tampered with, or a path that git lists but `ownPath` refuses (for example a person's `entries/.GIT/x.md` on a case-sensitive file system, in an adopt killed between its rewrite and its commit). In that last case the person's file keeps the adopt's stamped rewrite instead of their own bytes; their content is still there, but nothing says so.
- F-4 · advisory · src/modules/knowledge/repo.ts:1095 · Round two's F-1 and F-2 are closed: each path is now judged by itself (repo.ts:1066-1080), and paths the operation never reached are neither touched nor reported. Tests: knowledge-repo.test.ts "a path the operation never reached…" and "an adopt whose commit landed…". One small inaccuracy remains. For an adopt, "was undone" also lists paths where nothing was written back, only unstaged: `taxonomy.md`, files in subfolders of `entries/`, and deletions, because `restoreKept` writes only `entries/<x>.md`. The tree is right; the sentence overstates what was done.
- F-5 · advisory · src/store/db.ts:317 · Unchanged from round two and stated as a known limit (ADR 0024). The module migration pass is not contained, and `doctor` does not warn when the module schema is behind. This round also replaced the `?? ""` fallback with `as string` at db.ts:296. That is harmless today, because the owner map is built from the same list, but a missing key would now fail inside `openDb` instead of writing an empty module name.
- F-6 · advisory · .crew/work/2026-11-08-003-knowledge-store-entries-as-markdown-with/spec.md:321 · Unchanged. The rollback is stated with its reason but is manual, there is no cleanup command, and the backup taken before migration 6's drop rotates away after two later upgrades (`BACKUPS_KEPT = 2`).

## Outside the change
- `biome.json` (lint gate) · In this checkout `bun run lint` processes 0 files, because the checkout sits under a folder biome ignores, and the engine still records the gate as passed. A check that runs on nothing and reports success is a failure nobody sees. The session's manual run over the folders by name (346 files, no errors) covers this item, but not later items run from a worktree.
- tests/perf/large-project.test.ts · In one full run the p95 was 80.3 ms against a 50 ms budget, at load average 24. Run alone it gave 21.9 and 21.5 ms. The flakiness predates this item, which does not touch that path, but it hides a real regression on the hook path.
- src/store/db.ts:132 · The upgrade runner waits up to 10 s under `BEGIN IMMEDIATE`. This item's first open takes that wait once. The core migrations already carried this.

## Not answerable
- Q5, a git whose built-in defaults are sha256 or reftable · probes/init-formats.md shows the pin only on git 2.54.0, and no such git was available. With the clean environment (`gitEnv`, repo.ts:268, does not pass `GIT_DEFAULT_HASH` or `GIT_DEFAULT_REF_FORMAT`) and the empty template, the pin should hold on any git that knows the two settings. Whether git writes some other `core` or `init` setting under different defaults was not run.
- Q1, git writing a local setting on its own · I could not confirm that no git call the store makes (`init`, `add`, `commit`, `status`, `reset`, `restore`), and no tool a person points at the folder (for example `git maintenance register`, or a GUI client), adds a line to `.git/config`. Any such line would make the repository refused (F-1). The store itself writes none (no `git config` call outside the global `user.name` read at repo.ts:415).
