## Findings
- F-1 · defect · docs/adr/0024-knowledge-module.md:87 · The new sentence "The data directory itself may be a link, or be moved (`WIZARDINGCODE_HOME`): that is the way to keep the knowledge on another disk" decides again what ADR 0010 already decided, and does not say so. The error text at src/modules/knowledge/repo.ts:160 repeats it ("move or link the data directory itself"). ADR 0010:18 ("Data directory ≠ store directory") records that the data directory stays where it is. The shims resolve `$data/bin` on their own, so "only the database moves" (`WIZARDINGCODE_MEM_STORE_DIR`, from Storage). ADR 0010:16 adds that the variables locating the data directory cannot live in the settings file, so they would have to reach every agent's hook environment. The sentence also names the wrong variable. Per src/util/paths.ts:10-20, `WIZARDINGCODE_HOME` moves the whole brand home: `ui.json` and every other module's data, not just this product. The variable that moves only this product's data directory is `WIZARDINGCODE_MEM_DATA_DIR`. The "link" half agrees with ADR 0010: the path stays the same, the shims and `defaultDataDir` read it unchanged, nothing in the product canonicalises the data directory, and the new test at tests/unit/knowledge-repo.test.ts:1770 covers it. The "moved" half is the drift (rubric Q2: the data directory's role reread; Q5: a decision outside the Design). Fix: keep "may be a link". Either drop "or be moved (`WIZARDINGCODE_HOME`)", or replace it with `WIZARDINGCODE_MEM_DATA_DIR`, a reference to ADR 0010, and the two facts a reader needs: the variable must be in every agent's environment, and the store directory does not carry the knowledge (D-1). Change the message at repo.ts:160 to match.
- F-2 · advisory · src/doctor/checks.ts:589 · The doctor and the module now disagree on what "not there" means. The doctor's hand copies, projectFolders (:589-598, `catch { return [] }` plus `isDirectory`) and foldersByHand (:583, `isDirectory`), still read any failure to look as nothing there. The module now refuses on any failure (repo.ts `kindAt`/`namesIn`, used by resolve.ts projectFolders and scanRepos). With a database the module's rule still reaches the doctor: `scanRepos` throws, :679 rethrows, and knowledge() (:828) turns it into a warning. With no database (:669-670), or on the no-tables fallback at :680, the hand copies run alone. A `knowledge/projects/` with its bits off (0o000, or 0o600 so names list but cannot be looked at) then gives "ok, N repositories", without the unseen project repositories and with no warning. `refuseLinkedRoots` at :610 does not catch this, because it needs only search permission on `knowledge/`. The newly amended CLAUDE.md:22 says the doctor "must be given" each guard openRepo gains, and this commit gave the module a stricter listing without giving it to the doctor. No boundary is crossed: the doctor writes nothing and forgets no row, so this is a misreport, not data loss (Q6). These functions are new in this item (diff.patch:800, :811), so this is in the change, not debt. Fix: build both hand copies on the exported `kindAt`/`namesIn`. knowledge() already turns their KnowledgeError into this check's warning.
- F-3 · advisory · docs/adr/0024-knowledge-module.md:88 · The new rule reads "A folder under `knowledge/` that cannot be looked at or listed refuses the command". The code applies it to `knowledge/`, `knowledge/projects/` and the repository folders (refuseLinkedRoots, scanRepos, resolve.ts projectFolders, rebuildAll:594), not to every folder under `knowledge/`. Three places still read an unseen folder as empty or absent:
  - index-store.ts:330-336 (listFolder, `catch { return { names: [] } }`): an `entries/` or `proposals/` folder that cannot be listed is indexed as empty, and rebuildRepo (:517) deletes that repository's entry rows.
  - resolve.ts:209: `isDirectory` with `refuseForeign`'s `existsOnDisk` gives null for a workspace or shared folder it cannot look at.
  - resolve.ts:231: `existsOnDisk` treats such a name as free.

  The harm is small. Entry rows are rebuilt from the files once the folder is readable, unlike the project row the ADR names as the only tie. The two resolve.ts lines are reachable only on a disk fault, or with a create under a 0o600 `projects/`, once refuseLinkedRoots has passed. Still, the ADR line says more than the code does (Q5/Q6). Fix: either word the line for the folders it covers ("`knowledge/`, `knowledge/projects/` and a repository folder"), or use `namesIn`/`kindAt` in listFolder and at resolve.ts:209/231 too.
- F-4 · advisory · src/modules/knowledge/repo.ts:29 · Carried, unchanged: the function-level import cycles repo.ts↔resolve.ts and repo.ts↔author.ts. resolve.ts now also imports `kindAt` and `namesIn` from repo.ts over the existing edge, so there is no new edge. The fix is as before: a leaf module for the path, manifest and folder helpers, which is where `kindAt`/`namesIn` would also belong.
