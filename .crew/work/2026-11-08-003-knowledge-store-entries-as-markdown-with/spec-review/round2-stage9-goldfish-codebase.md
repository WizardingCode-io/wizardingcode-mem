## Findings
- F-1 · Blocker · plan.md:36-37 (steps 5-6), with plan.md:12-14 and plan.md:17 · The phase order has forward dependencies, so step 6's green run and Phase C's typecheck (header, plan.md:3) cannot pass; `repo.ts` (step 6) uses `KnowledgeStore`, `Writer` and `ScopeRef`, which are declared in `store.ts` and created only in step 13; `ensureRepo` commits as the writer through `identityOf` from `author.ts` (step 8); it writes `taxonomy.md` from `DEFAULT_AREAS` in `taxonomy.ts` (step 17); `openRepo` is described as "(resolve, …)" but `resolve.ts` comes in step 10 and imports `Repo` back from `repo.ts`; the step-5 tests also need `openStore` (step 13) to build a store; `writeEntry` in step 13 checks `area` against `taxonomyFor`/`readTaxonomy` from Phase E.
- F-2 · Blocker · plan.md:45 (step 11) vs plan.md:12 · The test overrides "`GIT_TIMEOUT_MS` … to 50 through the store's options", but `openStore({ db, dataDir, env?, now? })` and `KnowledgeStore` have no timeout field; the header says the signatures are "used identically by the tests", so as written this test cannot compile, and the implementer has to invent the API.
- F-3 · Major · plan.md:18, plan.md:36 · `stubGit` cannot do what step 5 asks of it; its behaviours are `failOnce`/`fail`/`sleepMs`/`stderr`, yet step 5 needs "a stub printing `git version 2.31.0`" for `requireGit` and "a stub that prints its environment" for `GIT_OPTIONAL_LOCKS`; the plan also leaves the script's language/shebang open and does not say which options take a value (`--git-dir`, `--work-tree`, `-c`, `-C`) when it finds "the subcommand"; this is a shared helper, so every later test inherits whatever guess the implementer makes.
- F-4 · Major · plan.md:46 (step 12), bunfig.toml:1-2 · The 200-open-proposals case is "written by a loop" through `writeEntry`; that is about 600 git spawns plus quota counts, and bunfig sets no test timeout, so bun's default of 5000 ms per test applies; the plan gives neither a per-test timeout nor a faster seeding method (files written directly, then `rebuildRepo`), so a reader will write a test that times out; the 5,001-file case at plan.md:48 carries the same risk.
- F-5 · Major · plan.md:58 (step 18), tests/helpers/cli.ts:17-26 · `runCliWith` accepts only `input` and `env` and spawns with the test process's cwd, which is the ai-mem worktree; `knowledge write --scope project` uses `resolveProject` on the cwd (spec.md:243), so any project-scope CLI case would register ai-mem itself as the project; the plan does not change the helper (no `cwd` option) and does not say how the CLI test's project repository is made.
- F-6 · Major · plan.md:63-64 (steps 20-21), plan.md:13-14 · Doctor "never opens the index" (spec.md:254), yet the plan has it decide the author and run `git status` through `personAuthor(store)` and `runGit(store, …)`, and both need a `KnowledgeStore` with a `db: Db`; `runChecks` holds a `db` that may be null (src/doctor/checks.ts:533), and step 21's `knowledge(context)` takes no db; the plan also does not say what `gitVersion` does when `doctorContext` leaves it unset (src/doctor/context.ts:16-38 gains only `env`), or what `moduleSchemaState` returns when `module_migrations` is missing.
- F-7 · Major · plan.md:15, plan.md:40 · `listRepos` returns `{ repos: Repo[]; orphans: string[] }`, but step 9 expects it to report an `ambiguous` manifest and a manifest "already mapped to another project", and doctor (step 20) warns on `ambiguous`; no field or shape carries those reports, so the implementer has to design the return type.
- F-8 · Major · plan.md:40 (step 9) · The test says a project "whose aliases are `gitdir:` and `path:`" gets a manifest "listing the three aliases"; that project has two (src/core/project.ts:30-34 gives the list in order remote, gitdir, path), so the assertion contradicts its own setup.
- F-9 · Major · plan.md:14 (`withRepoLeases`, `commitPaths`) vs spec.md:134 · The spec renews the lease "before every git call"; the plan's signatures give `renew` only to the `withRepoLeases` callback, while `commitPaths` makes two git calls (`add`, then `commit`) and `ensureRepo` makes several, with no renewal between them; the plan never says where `renew()` is called, so a reader would renew once per helper, not once per call.
- F-10 · Major · plan.md:46 (step 12), src/core/redact.ts:226-235 · `redact` makes text longer (a 20-character `AKIA…` becomes `[REDACTED:aws-access-key]`, 25 characters), and `context`/`subject` are capped at 120 and `title` at 200; the plan does not say whether the limits apply before or after redaction, or whether an over-long result is refused or clipped; it also does not say whether `redact` gets `store.env` or the default `process.env` (the env-value rule depends on it), and the test computes its expected text with `redact` called with no options.
- F-11 · Major · plan.md:26, plan.md:48, with spec.md:102 and spec.md:232 · A file with a problem is "indexed from its name", and a symlink is never opened, but `knowledge_entries.kind`, `area`, `author` and `version` are `NOT NULL`; neither the plan nor `parseEntry`'s contract gives the values those columns get (or the proposal-row equivalents), so each implementer picks their own.
- F-12 · Major · plan.md:48 (step 14) · For a duplicated entry `id`, or a proposal id under both `open/` and `decided/`, the plan does not say which file keeps the real id and which becomes `dup:` (by folder, name order or mtime); for proposals this decides whether the index shows the proposal as open or accepted.
- F-13 · Major · plan.md:48-49 vs spec.md:237 · With 5,001 files in a folder the plan checks only the counts; the spec's rule ("the newest by name beyond the cap are indexed") contradicts itself, and the plan does not pin which 5,000 files are kept.
- F-14 · Major · plan.md:22, tests/preload.ts:22-40 · The preload list drops `GIT_DIR`/`GIT_WORK_TREE`/author and config variables, but not `GIT_INDEX_FILE`, `GIT_OBJECT_DIRECTORY`, `GIT_CONFIG_PARAMETERS`, `GIT_CONFIG_COUNT` or `GIT_CEILING_DIRECTORIES`; tests run the real git with `process.env` (`git log -1`, the parent repository's `git status`), so a suite started from a git hook, which exports `GIT_INDEX_FILE`, would write into the outer repository's index.
- F-15 · Major · plan.md:49 (step 15), plan.md:59 (step 19) · The plan has no Scope list, and not every file it touches is marked: step 15 changes `index-store.ts` and `store.ts` and step 19 changes `src/cli/main.ts`, none marked `Modify`; an unmarked file can be created over an existing one.
- F-16 · Nit · plan.md:36 · `runGit(store, repo, ["status", "--porcelain"], …)` and `checkRepoConfig(repo)` pass `repo`, but the signatures take `repoPath: string`; elsewhere `Repo` is an object type.
- F-17 · Nit · plan.md:53 (step 16) · "throw `invalid` or `exists`" should name the code for each case (`code` already present gives `exists`; the other three give `invalid`).
- F-18 · Nit · plan.md:12 · `readEntry` does not say whether it reads the file or the index row, or whether it calls `ensureFresh` first.
- F-19 · Nit · plan.md:39 (step 8), ui/src/api.ts:92-104 · The UI's `SettingKey` union is already not a mirror of `SETTING_KEYS` (it lacks `WIZARDINGCODE_MEM_SEMANTIC`, `WIZARDINGCODE_MEM_HISTORY_DAYS` and `WIZARDINGCODE_MODULES`), so adding the author key there is optional, and the plan does not say why it is added.
- F-20 · Nit · plan.md:68 (step 22), README.md:289 · The README section is called "Linked projects and your rules", not "Linked projects".
