Lens: load, cost, quotas, tokens, failure modes, scale limits.

## Findings
- F-1 · Blocker · The taxonomy ("renaming rewrites the taxonomy and every entry that carries the area in one commit") · The taxonomy lives in the workspace repository, but entries that carry an area also live in every `projects/<key>/` repository and in `shared/`. A git commit cannot span several repositories, so "one commit" cannot be built as written. The concept also does not say which repositories a rename touches or which ones a remove checks ("refused while an entry carries it"): this project, all known projects, or shared. If a rename covers the workspace alone, entries in other scopes are left with an area that no longer exists. They then fail validation and drop out of `active`.
- F-2 · Major · Versioning and writes (`Bun.spawnSync`) · No timeout is given for the git spawn. A git that hangs blocks the writer for good while it holds `.lock`. Causes include a leftover `.git/index.lock`, a stuck `core.fsmonitor`, an auto `gc` started by commit, or a filesystem that has stalled. The 60 s staleness rule then lets a second writer take the lock while the first one is still alive. That is exactly the two-writer case the lock exists to prevent. A builder would copy "stale after 60 s" and get a lock that is neither safe nor live. The engine already has leases that check whether the owning process is alive (`ownerAlive` in src/store/meta.ts). The concept does not say why it uses an age-only file lock instead, and it says nothing about a stale `.git/index.lock` left by a killed git. Every later commit to that repository fails until someone removes that file by hand.
- F-3 · Major · Versioning and writes (step order) · The order is: write the file, git add/commit, raise version, update the index. The steps are not atomic, and each crash point is left open. (a) A crash after the rename and before the commit leaves an uncommitted change in the working tree. The next writer's `git add` sweeps it into its own commit, so the change is credited to the wrong author, which breaks the brief's "every change committed with its author". (b) "Raise version by one" comes after the commit, but the version must be inside the committed file. As written, the committed file carries the old version. (c) A crash after the commit and before the index update leaves a stale index, and the concept does not say whether the base-version check reads the file or the index. The builder needs a stated order, a recovery step (such as checking `git status` under the lock before each write), and the source of truth for the check.
- F-4 · Major · The index ("rebuilt by `knowledge rebuild`"; "a write updates the index for the file it changed") · Nothing notices changes that do not go through the store. Examples are hand edits in an editor (the team's habit is Obsidian), a `git checkout` or `revert` in the repository, the part 6 sync, or a restored data directory. The only repair is a rebuild run by hand. ADR 0020 needed a fingerprint for exactly this reason (K5), and the concept drops it without saying why. Later parts' hooks "read only the index" (brief), so they would quietly serve stale or deleted entries. A hand edit also skips the version bump and the commit, so the "every change versioned" guarantee is only true for writes the store makes.
- F-5 · Major · The index / module migrations vs. "nothing in this part runs on a hook" · Every hook opens the database (`openDb` runs `migrate`). The module migrations are "applied after the core migrations", so the first hook after an upgrade creates the knowledge tables and the FTS5 table under the write lock. Every later open pays at least one `module_migrations` read. That is work on the hook path. The concept does not count it, does not budget for it, and does not reconcile it with its own constraint. It also does not say whether module migrations run under the same `BEGIN IMMEDIATE` and backup as the core ones. Nor does it say how `openExisting` (doctor, status) acts when the tables are missing, or what an older binary does when it finds them.
- F-6 · Major · The index (`knowledge rebuild`) at thousands of entries · Rebuild "deletes a scope's rows and reads the files again". The concept does not say whether that happens in one transaction. If it does, a large scope holds the SQLite write lock for the length of the rebuild. Memory's hooks wait out their busy timeout behind it and drop the turns they would have captured, since hooks fail open. If it does not, readers see an empty or half-built index while it runs. The concept also gives no limits: no file-size cap, no file-count cap, and no rule against non-regular files, all of which ADR 0020 had (256 KiB, 2,000 files, `O_NOFOLLOW` and `fstat`, FIFOs). Without them, one huge file or a FIFO named `x.md` can hang or bloat a rebuild. Storage is also tripled: the body is held in the file, in `knowledge_entries.body` and in the self-contained FTS copy, and there is no estimate of the size at scale. The concept also does not say whether rebuild takes the repository's `.lock`. If it does not, a write running during a rebuild can lose its index row.
- F-7 · Major · Proposals (quota) · Nothing limits how many proposals an agent can make. An agent in a loop, or one prompt-injected through repository content, can write thousands of `proposals/<id>.md` files. Each one is a git commit, a row and an FTS insert. Nothing bounds pending proposals per agent, per target or per scope. Nothing collapses repeat proposals for one target, and nothing ever trims the history (rejected proposals stay in it "forever" by design). The repository and the review queue grow without limit, and the person's accept and reject queue becomes the bottleneck. How proposal ids are made is also left out, so collisions between concurrent agents are possible.
- F-8 · Major · Proposals / authorship (security) · Whether a write is a person's (applied at once) or an agent's (a proposal) depends on who the caller says it is. The concept does not say how the store tells the two apart or enforces the difference. If part 2's MCP tool passes the author in, an agent can write as a person and skip the proposal step entirely. `agent:<id>` is also self-declared, so one agent can pose as another. The guarantee the brief rests on, that "agents cannot disorganise it" (Q-3), needs a stated point of enforcement in this part. The store is the only layer every caller goes through, so that is where it belongs.
- F-9 · Major · The entry / slugs (security, scale) · Slug rules are not given. `entries/<slug>.md` with a slug that is not validated allows path traversal (`../`). On macOS's case-insensitive APFS, `Foo` and `foo` are the same file, so two "different" entries overwrite each other. The concept does not say whether the store refuses symlinks inside the repository folders, which ADR 0020 did. For `target: new`, it does not say how the slug is chosen at accept time, or what happens when an entry with that slug was created after the proposal was made.
- F-10 · Major · The repositories (git config isolation) · "Hooks path pointed at an empty folder, no signing" covers only part of the global and system config git will still read. Settings such as `commit.gpgsign=true`, `user.useConfigOnly`, `core.fsmonitor`, `gc.auto`, `includeIf`, a `safe.directory` mismatch, `init.defaultBranch`, or a global `core.hooksPath` that wins over the local one can make a commit fail, hang, or run user code. The concept should state the isolation it relies on (for example, a git environment with the global and system config switched off), or it will break on some machines and not on others. The concept also does not say whether the minimum git version is checked.
- F-11 · Major · The repositories (truth without a backup) · The files in the repositories are now the truth, and the database is only a cache. But the existing backup copies only the database (`backup` in src/store/db.ts), and the store directory can sit apart from the data directory (`storeDirOf`). The concept does not say whether backups, a store move, or `anyLeaseActive` cover `<data dir>/knowledge/`. It also says nothing on recovering from a corrupt repository (a broken object, a truncated index, a disk-full write mid-commit) beyond "the index is a cache". That rebuilds the index, but it does not recover the history or the files. Losing the data directory loses all knowledge without a sound.
- F-12 · Major · The repositories (`projects/<key>`, "stable across clones" in the brief) · `projects.key` is fixed when the project is inserted (`aliases[0]` in src/core/project.ts). A project first seen with no remote keeps a `path:` or `gitdir:` key after it gains one. The brief's claim that the hash is "stable across clones of the same remote" is therefore false for those projects. The same repository then maps to different folders on different machines, which the part 6 sync will meet. The concept also does not say what happens to a project repository when projects are merged or adopted (`adoptable`), when a project is deleted, or when the project id held in the index stops matching the folder.
- F-13 · Major · Versioning (distributed `version`) · `version` is a local counter, raised by one at each write, and the stale-write check depends on it. It cannot survive the `shared` scope, which part 6 is to sync. Two machines that each write version 4 of one entry produce a conflict the store cannot see. This part fixes the file format and the check that later parts will inherit. The concept should at least say that the scheme is local-only, or tie the version to the git commit or the content hash (`hash` is already a column).
- F-14 · Major · The taxonomy (shared scope and stale proposals) · The shared scope "reuses" the workspace taxonomy. Each teammate's workspace taxonomy is local and can be edited, so a shared entry that is valid for its author can fail validation for a teammate and drop out of `active`. Separately, if a rename bumps the version of every entry it touches, every pending proposal against those entries goes stale at once. The concept does not say whether a rename bumps versions.
- F-15 · Nit · Versioning and writes (e-mail) · "e-mail `<slug>@knowledge.wizardingcode.invalid`" does not say whether the slug is the entry's or the author's. An author name like "André", or one with spaces, needs a slug rule before it can go into an e-mail address.
- F-16 · Nit · Versioning and writes (missing git) · The concept does not say whether the read path (listing, rebuild) works without the git binary, or how `knowledge_repos.head` is read without spawning git. The hooks already read `.git` by hand, but later hooks read only the index.
