# zoom-out findings for 2026-11-08-003-knowledge-store-entries-as-markdown-with
reviewer: goldfish-zoom-out
read: concept.md (whole), brief.md (whole), knowledge.md of the item; src/engine/module.ts, src/engine/modules.ts, src/store/db.ts, src/core/project.ts, src/settings/settings.ts, docs/adr/0019-one-engine.md, docs/adr/0020-knowledge.md; searched src/ for spawn, frontmatter/slug, leases/locks, atomic rename, sha256 helpers, git identity, and the core migrations (0007_links.sql)

## Findings
- F-1 · Major · Hypothesis / "Who it is for and what fails today" · Contrarian: part 1 does not fix the failure it names. The pain is that agents cannot reach the knowledge, but this part ships no MCP tool and no composer contribution. It also names no way for a person to write: `rebuild` is the only command listed. So when part 1 is finished, nobody can use the store except through tests. A reader would build six layers of storage before anyone confirms the entry shape and the scopes are right. The simpler cut is one slice that runs end to end: one scope, write and read through a CLI or MCP tool, index, then grow it. At least name the write path a person has in part 1.
- F-2 · Major · The repositories (`shared/`) and the taxonomy's "shared scope reuses it" · Speculative: the shared scope has no sync (part 6), no team server (part 5) and no sharing policy (part 4). Today it is just a third local folder that behaves exactly like workspace. Building it now fixes its layout before the sync design exists. It also validates shared entries against one person's workspace taxonomy, so two teammates with different taxonomies would produce shared entries that fail for each other. That closes a door for part 5. Leave `shared` out until part 4 or 5 says what it is.
- F-3 · Major · The taxonomy · Over-built for zero entries. It ships nine fixed areas, a rename that rewrites every entry in one commit, and removal refused while an entry uses the area. All of that is tooling for a corpus that does not exist (Q-4: start from zero). The simpler version is a list of areas in a file that a write is checked against; rename can wait until someone needs it. Validating `area` strictly also makes an entry written by hand with a new area turn into a "problem". That is friction for no stated need.
- F-4 · Major · The entry (`version`, `author`, `created`, `updated`) and Versioning · There are two sources of truth for history. Git already records author, dates and order. A `version` counter in frontmatter goes out of step on any hand edit, any `git revert` and any later sync merge. The stale-write check can use the file's content hash instead; the index already has a `hash` column for it. A competent reader will build a counter that a hand edit leaves stale. That edit is either refused forever or silently accepted, and it was never committed, so "every change versioned" is false for it. The concept also does not say what happens to a dirty working tree, meaning edits made outside the engine.
- F-5 · Major · Assumptions (brief) "a filesystem-safe hash of the project's strongest alias … stable across clones of the same remote" · This is false as stated. `resolveProject` (src/core/project.ts:116-120) sets `projects.key` to `aliases[0]` once, at insert, and never updates it. A project first seen before it had a remote keeps `gitdir:` or `path:` as its key for good. Hashing `projects.key` therefore gives a folder that differs across machines and clones. That is exactly what sync (part 6) needs to be stable. Derive the folder from the `remote:` alias when one exists, and say what happens to a project that later gains one.
- F-6 · Major · One writer per repository (`.lock`, stale after 60 s) · Already solved in the repository. `src/store/meta.ts` has `claimLease` / `releaseLease`: owner `<pid>-<uuid>`, expiry, and a check that the owning process is still alive (`ownerAlive`). That is better than a lock file that a crashed writer holds for 60 s. Use a lease key per repository, for example `knowledge.write.<scope>`, instead of a new lock mechanism.
- F-7 · Major · "Design sketch" overall versus the brief's "every file is written fresh" · Code minimisation: the clean-room rule in CLAUDE.md / CLEAN-ROOM.md is about claude-mem. `archive/knowledge-module` is this project's own code, reviewed and measured, as ADR 0020 records. The concept rebuilds things that branch already has:
  - the module migration namespace (K8: `migrations` on `EngineModule`, `module_migrations` table), which the concept copies almost word for word;
  - the self-contained FTS5 index, and the reason it must be self-contained;
  - the YAML-subset frontmatter parser with its problem rules;
  - the safe file read (`O_NOFOLLOW`, regular files only, 256 KiB cap, 2,000-file cap);
  - atomic temp-and-link writes;
  - strict slug validation.

  The concept keeps none of the read-safety limits, and a fresh rewrite is likely to lose them. Port these pieces, or state per piece why it is rewritten.
- F-8 · Major · Proposals versus the existing `rule_proposals` / `user_memories` (src/store/migrations/0007_links.sql) · The repository already has a "proposed, then a person accepts or rejects" flow for the author's standing rules. Memory also treats an accepted rule as authoritative. The concept's "Memory … never authoritative" is therefore not quite true, and it says nothing about how a user rule relates to a knowledge entry of kind `pattern` or `knowledge`. Left unstated, the product ends up with two curated-truth stores and two proposal queues that inject overlapping text later. Decide now whether user rules become knowledge or stay separate.
- F-9 · Nit · Proposals as files committed into `proposals/`, then removed · This works, but git has a native way to hold a pending change by its author: a branch or a commit not yet on the main line. Accepting it is a fast-forward or cherry-pick, and the history keeps both authors without a removal commit. Worth weighing before part 3 builds a merge view on top of the file convention.
- F-10 · Nit · The index (`knowledge_proposals`, `knowledge_repos.head`, `knowledge_fts`) · Nothing reads these tables in part 1. The FTS table and the proposals cache are built for part 2's queries before those queries exist, which is how the wrong columns get picked. The FTS columns in particular (title, area, context, subject, body) carry no weights and have no relevance floor (ADR 0020 spent three versions on that). Defer FTS to the part that searches.
- F-11 · Nit · Versioning (author fallback `you`, e-mail `<slug>@knowledge.wizardingcode.invalid`) · Commits authored as "you" are useless the moment a repository is shared, and putting the slug in the e-mail is odd for a person. Also, `git config --global user.name` spawns a process, which is fine off the hook, but the setting `WIZARDINGCODE_KNOWLEDGE_AUTHOR` (brief) is not yet in `SETTING_KEYS` / `RULES` (src/settings/settings.ts). Say that the work adds it.
- F-12 · Nit · Atomic writes (temp file, rename) and the project-key hash · Existing patterns to reuse: `src/settings/env-file.ts:88` and `src/install/hooks-file.ts:266` (temp then rename), and `src/install/hooks-file.ts:117-119` (sha256 sliced into a short key).
- F-13 · Nit · The repositories ("Never inside a project's own folder") · This reverses ADR 0020's K1 without saying why. The files now live under a hidden data directory that the team's current tool (Obsidian) and editors will not open by default, so editing by hand, which is the escape hatch, gets harder. One sentence giving the reason (sync, or not polluting client repositories) would stop a reader from "fixing" it back.
