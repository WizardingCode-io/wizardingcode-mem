## Findings
- F-1 · Blocker · Step 17a (plan.md:39) against step 15 / spec steps 5 and 8 · The test expects `writeEntry` on slug `link` to throw `invalid` naming the link. In the spec's order, the dirty check (spec step 5, `git status --porcelain -- entries/<slug>.md`) runs before the file is read or written, and an untracked symlink `entries/link.md` is listed as `??`. Built as written, the write throws `dirty`, not `invalid`. Step 17b (plan.md:40) says only "the `lstat` guard before a write". It does not say the guard must come before the dirty check, so the test fails. Step 17b also puts the guard in `index-store.ts`, but the write lives in `store.ts` (plan.md:33).
- F-2 · Blocker · Step 5 (plan.md:17) against step 6 (plan.md:18) · Step 6 has the git user name "cached per process". The test in step 5 then expects `Ana Lopes` from one `HOME/.gitconfig` and `you` with no git name, in the same test process. With a per-process cache, whichever case runs second gets the cached value. The same cache breaks the "no author" case in step 18 (plan.md:44), and the `gitVersion`/`requireGit` caching (plan.md:20) clashes with the empty-PATH and stub-git tests. The plan names no reset hook and no injection point.
- F-3 · Major · Signatures used in tests do not match the functions the plan creates. This affects plan.md:12/13, 19/20, 21/22, 26/27 and 33.
  - `moduleSchemaState(db, "knowledge")` takes 2 arguments in the test, but `moduleSchemaState(db, module, latest)` takes 3.
  - The test has `gitVersion()` parse the string `git version 2.54.0 (Apple Git-157)` and `requireGit` refuse `[2, 31, 0]`, but both are defined with no arguments. A pure parse function is needed.
  - The test calls `checkRepoConfig(repo)`, which no Create step lists.
  - The test uses "a stub hasher" in `resolveRepo`, but `resolveRepo(db, dataDir, ref, {create, writer})` has no hasher parameter.
  - The test calls `addArea(root, …)` and `taxonomyFor(ref)` with no store. Step 12 has `taxonomyFor(store, ref)`, and the lease needs `db`.
  - `ensureFresh(store, repo)` and `rebuildRepo(db, dataDir, repo, taxonomy, dirtyPaths)` differ from the spec's `ensureFresh(db, dataDir, repo)` and `rebuildRepo(db, dataDir, repo)`.

  An implementer has to pick each signature.
- F-4 · Major · Step 7 (plan.md:19) · The plan does not say who calls `checkRepoConfig`. The spec (spec.md:104) refuses a bad `.git/config` "before any git call on an existing repository". The plan's test, though, expects `runGit(... ["status","--porcelain"])` on an fsmonitor repository "neither writes the marker nor fails", so `runGit` cannot be the caller. Which of `ensureRepo`, `writeEntry`, `adopt`, `rebuildRepo` and doctor run the check is left open.
- F-5 · Major · Step 15 / step 17 (plan.md:33, 35) · The spec's `rebuildAll(db, dataDir, scope?)` (spec.md:204) is missing from the plan. That function walks `knowledge/`, maps folders to projects, reports orphans and deletes the rows of folders that are gone. `listRepos` in resolve.ts (plan.md:22) covers only part of it. No step owns deleting the rows of vanished folders, and no test covers it.
- F-6 · Major · Step 16 (plan.md:34) · The rebuild comparison drops `id` of `knowledge_repos`, but `knowledge_entries.repo_id` and `knowledge_proposals.repo_id` reference that id (spec.md:199-200). After `DELETE FROM knowledge_repos`, ids are reassigned in the order of the walk, which nothing specifies. The entry and proposal rows can then differ only by `repo_id`. The comparison has to map `repo_id` to the repository's path, or say why the order is stable.
- F-7 · Major · Step 4 (plan.md:13) · The plan does not say that `openDb` defaults `moduleMigrations` to `MODULE_SCHEMAS`. Step 3 requires it: a plain `openDb` records `('knowledge', 6, …)`, and `tests/helpers/open-db-worker.ts:17` passes no `moduleMigrations`. The plan also leaves the import direction open: `src/store/db.ts` would import `src/engine/module-schemas.ts`, while `src/engine/module.ts:2` already imports from the store. The default and the layering should be written down.
- F-8 · Major · Step 4 (plan.md:13) · The module backup uses `backup(db, dir, version)` (src/store/db.ts:72), which writes `-v<version>-` into the file name. The plan does not say which version goes there for a module pass: the core `user_version` or the module's. Restore and pruning read these names (src/backup/target.ts:30 for remote copies).
- F-9 · Major · Step 8 (plan.md:20) · `headOf(repo)` (`readGitInfo`) can return the wrong HEAD. `readGitInfo` walks up through parent directories until it finds a `.git` (src/core/git.ts:75-80). A repository folder without `.git` (the doctor case at plan.md:44), inside a data directory under a parent git tree (the case at plan.md:19), therefore gets the parent repository's HEAD recorded. The plan needs `<repo>/.git` checked first.
- F-10 · Major · Step 8 / step 17b (plan.md:20, 40) · `runGit` failure handling is underspecified, and `logError` writes to the wrong place.
  - `logError("knowledge.<operation>", …)` sits inside `runGit`, but `runGit`'s options carry no operation name, yet the test expects `knowledge.write`.
  - `logError`'s `dataDir` defaults to `defaultDataDir()` (src/util/log.ts:21), and the plan never says to pass the store's `dataDir`. The test reads `<data dir>/logs/wizardingcode-mem.log`, which the default may not point to.
  - `git config --global user.name` exits 1 when no name is set. Through `runGit`, that is a logged `git` error on every write on a machine without a git name. The plan does not say that `personAuthor` treats exit 1 as "no name" without logging.
- F-11 · Major · Step 8 (plan.md:20) · `runGit(dataDir, repo, args, …)` always targets a repository, and two calls don't fit that. `init` runs without `--git-dir` (spec.md:102). `git config --global user.name` (`allowUserConfig`) needs no repository and needs `HOME`/`XDG_CONFIG_HOME` back while `GIT_CONFIG_GLOBAL` is dropped. The plan does not define which environment keys `allowUserConfig` restores or how a call with no repository is made. It also never gives `runGit` an `env`, although `KnowledgeStore` holds one (plan.md:33), so where `PATH` comes from (needed by the stub-git tests) is left open.
- F-12 · Major · Step 8 (plan.md:20) · Spec values the plan omits: the default `timeoutMs` (15 s, spec.md:100), and the stderr clip to 300 characters in the `KnowledgeError` (spec.md:106), which is separate from `MESSAGE_MAX_CHARS` in src/util/log.ts:8.
- F-13 · Major · Step 8 (plan.md:20) · The lease is 60 s and is never renewed, while a single git call may take up to 15 s. A first project write runs `ensureRepo` for the workspace and the project (init, add, commit each) and then status, add and commit. That is about 9 calls, so up to 135 s. Past 60 s, `claimLease` (src/store/meta.ts:82) lets another live writer take the lease in the middle of the write. The plan needs a renewal (`claimLease` with the same owner) or a bound.
- F-14 · Major · Step 8 (plan.md:20) / src/store/meta.ts:120 · The plan does not say whether `knowledge.lease:*` joins `anyLeaseActive`. That function is what stops a store move or a restore from running during background work. A move or restore during a knowledge write would leave the post-commit index upsert going to the database being swapped.
- F-15 · Major · Step 19 (plan.md:45) against src/doctor/checks.ts:531 ("Looks, and changes nothing") · Doctor would run `git status` through `runGit`, which refreshes and rewrites `.git/index` and takes `index.lock`. It can collide with a write in progress, and it is a change. Its environment also points at `.no-hooks/` and `.gitconfig-empty`, which only `ensureSupportFolders` creates. The plan does not specify `--no-optional-locks`, nor what doctor does when the support folders are missing.
- F-16 · Major · Step 18/19 (plan.md:44-45) · Two gaps in the doctor check.
  - The spec says the knowledge store "refuses ... and `doctor` names it" for a module schema that is too new (spec.md:193). Doctor has no too-new case and no test for it.
  - For "no author", `personAuthor` falls back to `you` with no source, so doctor cannot tell the fallback from a person really named `you`. The return shape has to say where the name came from.
- F-17 · Major · Step 3 (plan.md:12) · AC-3 requires that a recorded module version 7 makes "the store's functions throw `ModuleSchemaTooNewError`" (spec.md:240). The plan tests only `moduleSchemaState(...) === "too-new"`, and no store test (steps 13-14) checks that `writeEntry` throws.
- F-18 · Major · Step 6 (plan.md:18) / tests/preload.ts:22-40 · The new setting `WIZARDINGCODE_MEM_AUTHOR` is read from the environment first (src/settings/settings.ts:91). A developer shell that exports it changes every author assertion, in process and in spawned CLIs (tests/helpers/cli.ts:22 inherits `process.env`). The preload drops `WIZARDINGCODE_MODULES` for exactly this reason. The plan does not modify tests/preload.ts to drop the new key. The same goes for the git variables `GIT_DIR` and `GIT_AUTHOR_*` on the `allowUserConfig` path.
- F-19 · Major · Steps 7, 13, 14, 17a (plan.md:19, 31, 32, 39) · Four test files depend on a stub `git` on PATH. It fails `commit` (once, in some tests), sleeps, or prints `fatal: boom`, and it must pass every other subcommand to the real git, finding the subcommand after `--git-dir`, `--work-tree` and many `-c` options. The plan names no shared helper (path, interface, how it finds the real git). Four implementations would diverge.
- F-20 · Major · Step 9 (plan.md:21) / src/core/project.ts:121-130 · `gitdir:` and `path:` aliases are reassigned to whichever project now occupies the folder (`ON CONFLICT ... DO UPDATE`). Mapping a manifest by alias intersection can therefore adopt another project's repository when a folder is reused by a different repository. The plan has no rule (for example, a stored remote alias wins and only path aliases conflict) and no test for this.
- F-21 · Major · Step 20 (plan.md:49) · `crew tdd before` must run "before Phase B's code", but it is numbered 20, after Phase F. Anyone following the steps in order captures the baseline after the code exists. It belongs before step 4.
- F-22 · Major · Phase G (plan.md:47-51) · The spec says the README states that the repositories are not in the database backup (spec.md:265). No step modifies README.md.
