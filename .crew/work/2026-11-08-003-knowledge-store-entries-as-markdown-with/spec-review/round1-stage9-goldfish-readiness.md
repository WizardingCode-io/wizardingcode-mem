## Findings
- F-1 · Blocker · plan.md:26-27 (Phase D, steps 11-12) · Phase D cannot be built in the order given. Test 11 calls `writeEntry` (store.ts, built at step 15). Step 12's `removeArea` "scans … through `listEntries`" and the spec has it run `ensureFresh` first, and both live in `index-store.ts`, also built at step 15. So the step 12 green run cannot pass, and `bun run typecheck` fails at the end of Phase D because the test imports a module that does not exist yet. Line 3 promises that "each phase leaves the tree buildable", and that is false here. Missing: put Phase D after Phase E, or move the AC-17 and `removeArea` cases into Phase E.
- F-2 · Major · plan.md:17-18 (steps 5-6) · There are two problems in this pair of steps. First, `personAuthor` gets git's name "through `runGit`", but `runGit` is only created at step 8, so the step 6 green run needs code from a later step. Second, "cached per process" breaks step 5's own cases: the second case reads `Ana Lopes` from one `HOME` and the third case, with no name, expects `you` in the same process. A cached value returns `Ana Lopes`. The same applies to `gitVersion()`/`requireGit()`, which are "cached" (line 20), when step 7 swaps in an empty `PATH`, a sleeping stub and a failing stub in one process. Missing: a cache key (`HOME`/`PATH`) or a named reset for tests, and an order where `runGit` exists before `author.ts`.
- F-3 · Major · plan.md:19-20, 31-32, 39 (stub `git` on PATH) · Many tests put a stub `git` or an empty folder "on PATH", but `runGit(dataDir, repo, args, {identity?, allowUserConfig?, timeoutMs?})` takes no environment. The plan never says whether `PATH` comes from `process.env` or from `KnowledgeStore.env`, so a reader cannot tell whether the tests must change the process's environment. A stub that "fails `commit`" also has to answer `--version`, `status`, `add`, `checkout` and `reset` by calling the real git, and the plan does not describe how the stub finds it. Missing: the env parameter of `runGit`/`gitEnv` and the stub's contract.
- F-4 · Major · plan.md:7-8, 13, 17-22, 26-27, 33 vs spec.md:204 · The signatures differ between the tests, the creation steps and the spec:
  - `moduleSchemaState(db, "knowledge")` in the test vs `(db, module, latest)` in step 4.
  - `withRepoLease(db, repo, fn)` vs `(db, repoPath, fn, now)`.
  - `ensureFresh(store, repo)` vs spec `ensureFresh(db, dataDir, repo)`.
  - `rebuildRepo(db, dataDir, repo, taxonomy, dirtyPaths)` vs spec `(db, dataDir, repo)`.
  - `addArea(root, id, label, person)` has no store/db, yet it must take a lease in `meta` and call `runGit(dataDir, …)`, while `readTaxonomy(store, root)` takes a store.
  - `gitVersion()` takes no input, yet the test makes it "parse `git version 2.54.0 (Apple Git-157)`".
  - Step 9 needs "a stub hasher" that `resolveRepo(db, dataDir, ref, {create, writer})` cannot receive.
  - `upsertProposal(...)` is elided.
  
  Missing: one signature per function, including the test seams. Also missing: what `resolveRepo` returns with `create: false` and no repository.
- F-5 · Major · plan.md:33 (step 15) vs spec.md:204 · `rebuildAll(db, dataDir, scope?)` is in no creation step. It walks `knowledge/`, maps folders to projects through the manifest, reports orphans and deletes the rows of folders that are gone, and the `knowledge rebuild` command and test 16's orphan cases depend on it. Step 10 gives `listRepos` "reports orphans", but the plan never says whether `rebuildAll` is that function or a new one, or which file holds it. The deletion of gone folders' rows also has no test.
- F-6 · Major · plan.md:19-20 (steps 7-8) · Test 7 calls `checkRepoConfig(repo)`, but step 8's export list for `repo.ts` does not include it, and nothing says which callers must run it before git (the spec says "before any git call on an existing repository"). Without that, a reader would build the function and never wire it into `runGit` or `ensureRepo`.
- F-7 · Major · plan.md:13 (step 4) · Two design choices are left open.
  - `OpenOptions.moduleMigrations?` is named, but the plan does not say what it holds (a `ModuleSchema[]`, despite the name) or where the default comes from. Step 3's two-process case calls `openDb` through `open-db-worker.ts`, which passes no option, so `db.ts` must import `MODULE_SCHEMAS` from `src/engine/module-schemas.ts` as its default. The plan does not say so, and that import goes from the store to the engine.
  - `EngineModule.migrations?` is added, but nothing sets or reads it. The plan never says the knowledge module is *not* an `EngineModule` in `BUILT_IN` in this part. If a reader registers it, these tests break, because they rely on `knowledge` being an unknown id: tests/integration/fixture-module.test.ts:173-231, tests/integration/ui-modules.test.ts:57, tests/unit/modules-setting.test.ts:50-58, tests/unit/mcp-tools-list.test.ts:149.
- F-8 · Major · plan.md:13 (step 4) · The plan says "backup first only when a module already had a version" (the spec, at line 191, says "had tables"). `backup(db, dir, version)` in `src/store/db.ts:72` is private and puts `v<version>` in the file name. The plan does not say whether to export it, or which version (core or module) to pass. Step 3's archived-fixture case takes that path but asserts no backup.
- F-9 · Major · plan.md:12, 31-32 vs spec.md:240 · AC-3 requires "the store's functions throw `ModuleSchemaTooNewError`", but no test calls `writeEntry`/`readEntry` with module version 7 recorded; only `moduleSchemaState` is tested. Step 6 also defines both a `KnowledgeError` code `too-new` and a separate class `ModuleSchemaTooNewError`, without saying which one is thrown or whether one extends the other.
- F-10 · Major · plan.md:44-45 (steps 18-19) vs spec.md:193 · The spec says "`doctor` names" a module schema newer than the binary, but the doctor check and its test have no such case. Step 19 also calls `personAuthor(settings, env)` for the author warning, but `DoctorContext` (src/doctor/checks.ts:35-58) has no env or `HOME`, and only `gitVersion?` is added. A reader cannot tell which environment the doctor reads or how the test makes "no git name".
- F-11 · Major · plan.md:34 (step 16) · The rows are "compared as JSON without `indexed_at` and `id` of `knowledge_repos`", but `knowledge_entries.repo_id` and `knowledge_proposals.repo_id` point at that id. Once the rows are deleted, the rebuild walks `projects/` before `workspace/` and gives out new ids, so the comparison fails as written. Missing: compare through `knowledge_repos.path` (or drop `repo_id` too).
- F-12 · Major · plan.md:19, 31 vs spec.md:245 · AC-8's write-level outcomes are not tested. "A write with no `git` on PATH … leaves no file behind" is only tested as `runGit` throwing. Being refused while another live process holds the lease, the takeover of a dead owner's lease "and the write proceeds", and a timed-out git call refusing "the write" are only tested on `withRepoLease`/`runGit`. The spec's exact message ("git 2.32 or newer is needed to version knowledge; found …") is never asserted. With no git, a reader would let `ensureRepo` create folders before it checks git.
- F-13 · Major · plan.md:39-40 (Phase E2) · Step 17b is a summary where a step should be: there is no "Modify <file>", only a list of things. It also places "the `lstat` guard before a write" in `index-store.ts`, though writes live in `store.ts`. `O_NOFOLLOW` is already required at step 15 (line 33), so 17a's symlink-read case is green before its "red run". `runGit` also has no operation parameter, so it cannot log `knowledge.<operation>` with `knowledge.write` as test 17a expects. Missing: an `operation` option on `runGit` (or the rule that the caller logs), and the files each 17b change goes in.
- F-14 · Major · plan.md:33 (step 15) · `openStore(options)` has no options shape. `KnowledgeStore {db, dataDir, env, now, settings}` does not say whether `now` is a number or a function. Tests 13 and 14 assert "`created` and `updated` equal to the store's `now`" over several writes, and the timestamps `decided_at`/`proposed_at` depend on it. A reader must choose.
- F-15 · Major · plan.md:7 (step 1) · "100 letters are cut at 80 on a hyphen" makes no sense, because 100 letters contain no hyphen. Under the spec's rule (cut at 80, then at the last `-` past the 40th character) the result is 80 letters. The input and expected value for the hyphen case are missing.
- F-16 · Major · plan.md:49 (step 20) · "`crew tdd before` … before Phase B's code" sits in Phase G, after step 19. A reader who works the numbered steps in order runs it after the code has changed and loses the baseline. It needs to come before step 3.
- F-17 · Major · plan.md:50 vs spec.md:265 · The spec says "The README and the ADR say so" (the repositories are not in `wizardingcode-mem backup`). The plan modifies the ADR and `CLAUDE.md` but not `README.md`, so the change ships without that warning to users.
- F-18 · Nit · plan.md:12 · The archived fixture's tables are "`knowledge_entries(project_id, slug, …)`" with the columns elided. The case also leaves out the `injections_memory_contexts` index, which the spec's drop list (spec.md:196) includes.
- F-19 · Nit · plan.md:34 vs spec.md:210-211 · The plural forms are not decided: "`adopted 1 change`" and "`1 problem`" in the test vs the spec's "`change(s)`" and "`p problems`". Either output passes the substring test.
- F-20 · Nit · plan.md:20 · `fingerprintOf(repo)` has no string format ("file count, total size, newest mtime" in the spec, but in what order and separated how).
- F-21 · Nit · plan.md:31-32 · The field limits (title 200, context and subject 120, label 60, area id 40) and the 200-per-repository proposal quota have no test case. The redaction case does not assert the replacement text.
- F-22 · Nit · plan.md:35 · The `knowledge` command does not say how it opens the database (busy timeout, store directory), or what `--scope project` selects (all project repositories or the cwd's project).
