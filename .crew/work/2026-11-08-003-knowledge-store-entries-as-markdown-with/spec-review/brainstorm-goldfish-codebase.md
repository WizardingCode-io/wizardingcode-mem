## Findings
- F-1 · Blocker · What exists today, "Hooks never spawn a process" · This is false. `src/cli/commands/hook.ts` imports `spawnDetached` and starts `distill`, `history index`, `ui --auto` and `backup` as detached processes (lines 47, 57, 72, 159). Only `src/core/git.ts` promises not to start a *git* process ("this never starts a `git` process"). A later part that relies on "hooks spawn nothing" would get it wrong. One example is whether the detached distill or drain that a hook starts may run knowledge work that spawns `git`.
- F-2 · Blocker · What exists today, `src/core/project.ts` bullet; brief Assumptions "stable across clones of the same remote" · `key` is not "its strongest alias". `resolveProject` writes `aliases[0]` once, at INSERT (line 118), and never updates it. A project first seen with no remote keeps `path:<root>` or `gitdir:<dir>` after it gains a remote. There is also a fourth form the concept does not list: `src/import/claude-mem.ts:109` creates projects with key `imported:<name>`, and `resolveProject`'s `adoptable()` adopts them while keeping that key. So `knowledge/projects/<hash of key>/` depends on how the project was first seen, and is not tied to the remote. Two clones of one remote can map to two folders, and an imported project's folder is named after a folder name. The concept has to say which value it hashes, and whether a key can ever change.
- F-3 · Major · The index, "applied after the core migrations" · `migrate()` in `src/store/db.ts` returns early when `user_version === latest` (line 127). It takes `BEGIN IMMEDIATE` and the backup only when the core version moves. Module migrations therefore need their own path, and the concept does not describe it: the lock, whether a backup is taken, and the order inside that one transaction. `openDb` is called by `hook.ts`, so on every hook it would also check `module_migrations`, and the first hook after an upgrade would create the FTS5 tables. That breaks the brief's "nothing in this part runs on a hook" unless the concept says otherwise. A builder would wire module migrations into `openDb` without saying that.
- F-4 · Major · The index; Doctor (absent) · `openExisting` and the `database` check in `src/doctor/checks.ts` look only at `PRAGMA user_version` against `LATEST_VERSION`. The concept never says:
  - what an older binary does when `module_migrations` holds a knowledge version newer than it knows (there is nothing like `SchemaTooNewError` for modules);
  - how doctor reports pending module migrations, given that it opens the database read-only and `module_migrations` may not exist yet. `readingDb` only turns an error into "skip" when the core version is behind; otherwise it becomes "fail: could not be checked".
- F-5 · Major · Versioning and writes, the order of steps · "write the file … `git commit` … raise `version` by one; update the index" contradicts itself. `version` is in the file's frontmatter, so it has to be raised before the write and the commit, or the commit records the old version. The failure paths are also unstated:
  - the rename succeeds and `git add` or `git commit` fails;
  - the commit succeeds and the index update fails.
  Each leaves a different inconsistent state: a dirty working tree, or an index behind HEAD. Neither the recovery nor what the person sees is given.
- F-6 · Major · Versioning and writes, the stale-write check · The base version is read from the file's own `version`. A hand edit (from an editor or Obsidian, which is where the team works today) changes the file without raising `version` and without a commit. The next engine write then passes the check and runs `git add`/`commit` over an uncommitted change. Nothing says whether a dirty working tree (as `git status --porcelain` would show it) refuses the write, and nothing says whether it is `git add <file>` or `git add -A`.
- F-7 · Major · The repositories, "created on first write (`git init` …)" · `git` run inside a folder with no `.git` of its own acts on the nearest parent repository. `readGitInfo` in `src/core/git.ts` walks up through parents in the same way. If the data dir is inside a git working tree (a dotfiles repository in `~`, or `WIZARDINGCODE_MEM_DATA_DIR` pointed into a project), a write before `init`, or an `init` that failed, would commit into that parent repository. The concept should require `-C <repo>` and an exact `<repo>/.git` check, plus `GIT_DIR`/`GIT_WORK_TREE`, or `GIT_CEILING_DIRECTORIES`.
- F-8 · Major · Observability: how a failed write is logged · Nothing names the log scope or the content of the log line. `logError` (`src/util/log.ts`) writes one line per error to `<data dir>/logs/wizardingcode-mem.log`. The message is redacted, clipped to 300 characters, and never carries a payload. The concept should say:
  - whether git's stderr is captured and logged (clipped or redacted), along with git's exit code and the repository path;
  - which scope string is used (for example `knowledge.write`);
  - what the caller sees compared with what the log holds: refused as stale, missing `git`, lock held, commit failed, parse problem.
  At 3 AM the only way to see why a write was refused is that log line.
- F-9 · Major · One writer per repository, `.lock` · The design leaves out:
  - What the lock file contains. With no pid, host or start time, nobody can tell who holds it, and "stale" can only mean the mtime is older than 60 s.
  - Where it lives relative to the work tree. Inside the repository it shows up as untracked, unless it goes in `.git/info/exclude`, and it can be swept in by `git add -A`.
  - What happens to a write that takes longer than 60 s (a slow disk, a large history). Its lock gets taken by another writer while it is still running.
  - What happens to git's own `.git/index.lock` left behind by a crashed `git`. It blocks every later commit, and nothing reports it.
- F-10 · Major · Doctor and status (absent) · The concept says only "doctor reports" missing `git`. Doctor already has `context.which`. It does not say what doctor shows per scope: whether the repository exists, its HEAD, whether the work tree is dirty, a lock held or stale, files with a `problem`, pending proposals, or whether the index's `knowledge_repos.head` matches the repository's HEAD. `status` (`src/status/report.ts`, `formatStatus`) is never mentioned. ADR 0020's own Doctor section had doctor read the files directly because it opens the database read-only and the tables may be missing. That constraint still holds here, and the concept does not deal with it.
- F-11 · Major · The index, "the index is a cache" · Stale detection is not specified. `knowledge_repos.head` exists, but nothing says who compares it with the repository's HEAD (which `readGitInfo` can read without spawning), or when: on each command, on tool calls, or in doctor. The cases that make it stale:
  - a hand edit or a hand `git commit` in the repository;
  - a database restore from a backup (`src/backup/backup.ts` copies the database only);
  - `knowledge rebuild` interrupted halfway, since a scope's rows are deleted first and the concept does not say whether delete and reread run in one transaction.
  A person sees old entries and has no way to tell.
- F-12 · Major · The repositories, where things are found · The repositories go under `<data dir>`, but the database can sit in a separate `storeDir` (`src/util/paths.ts` `storeDirOf`, `src/store/move.ts`). The concept leaves four things open:
  - Whether `knowledge_repos.path` is absolute. If it is, changing `WIZARDINGCODE_MEM_DATA_DIR` or `WIZARDINGCODE_HOME` leaves the index pointing at the old repositories.
  - Whether doctor's synced-folder warning (`SYNCED` in `checks.ts`, which tests only dataDir and storeDir) also covers git repositories under iCloud or Dropbox.
  - That backups copy only the database, so the knowledge files, which are the source of truth, are in no backup at all.
  - How a person maps `projects/<hash>/` back to a project. No command or field lists the hash next to the project name.
- F-13 · Major · Settings · The brief names `WIZARDINGCODE_KNOWLEDGE_AUTHOR`; the concept says only "the author setting". In `src/settings/settings.ts`, `RULES: Record<SettingKey, …>` is exhaustive, so a new key needs a rule, an entry in `Settings`/`loadSettings`, and a default in `publicSettings`. None of that is planned, and nothing says how the name is validated (empty, newlines, `agent:` prefix spoofing). The fallback `git config --global user.name` also spawns `git`, and nothing says whether it is read once per write or cached.
- F-14 · Major · Modules · Nothing says whether `knowledge` joins `BUILT_IN`. Nothing says whether writes and `knowledge rebuild` work when `WIZARDINGCODE_MODULES` does not list it: the default is `memory` alone (`DEFAULTS.modules`), and `enabledModules` filters on that list. Nothing says whether the module tables are created regardless (ADR 0020 K8 created them whether the module was on or not). Without this, a person debugging "rebuild did nothing" has nothing to check against.
- F-15 · Nit · What exists today, the ADR 0019 F2 bullet · The quote "until a real case exists" is not in F2. F2 reads "Modules' own tables wait for D2 … designed against the first real case". The phrase comes from ADR 0020 K3's paraphrase of it.
- F-16 · Nit · What exists today, the `project.ts` bullet · `ProjectRef` also carries `branch`, `commit` and `disabled`. The per-project "memory off" (`disabled`) is not addressed: does a disabled project still get a knowledge repository?
- F-17 · Nit · Proposals · `proposals/<id>.md`: nothing says how `<id>` is formed, unique or sortable, and the commit e-mail `<slug>@knowledge…` has no meaning for a proposal commit or a taxonomy commit. Without a fixed commit message format, `git log` cannot be searched by agent, slug or decision when tracing who changed what.
