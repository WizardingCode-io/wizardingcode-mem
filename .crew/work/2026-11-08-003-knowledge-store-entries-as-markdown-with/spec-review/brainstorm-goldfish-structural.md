# structural findings for 2026-11-08-003-knowledge-store-entries-as-markdown-with

Lens: long-term debt and maintenance.

## Findings
- F-1 · Blocker · Design sketch / The entry · An entry has no stable id. The slug is both the file name and the identity, and nothing in the frontmatter survives a rename. Sync (part 6) has nothing to match on, so a rename looks like one entry deleted and another added. Deep links from the viewer, proposal `target:` and the index key all break on a rename. Two machines that each create `discovery-call.md` give an add/add conflict, with both files at `version: 1`. Fix now: add a required `id:` (ULID or UUID) written at creation and never changed. Key the index, `target:` and links by `id`, and treat the slug as a name that can change.
- F-2 · Major · Versioning and writes · A `version` counter inside the file is a guaranteed merge conflict. Two machines that each edit version 3 both write `version: 4`. Git then conflicts on that line every time, even when the body edits don't overlap, and the counter keeps no order across machines. It also repeats what git already records, and it drifts on hand edits (see F-3). A builder will treat `version` as a global order, and sync will break on it. Fix now: base the stale check on the content hash of the file the caller read, or on the blob or commit id. If `version` is kept, document it as display-only and keep it out of conflict resolution.
- F-3 · Major · Versioning and writes · Hand edits and outside changes have no rule. The team comes from Obsidian, so files will be edited directly, and part 6 will `git pull` into these repositories. The concept doesn't say what a write does with a dirty working tree: commit only its own path, refuse, or sweep the other changes in. It doesn't say whether a hand edit that skipped the `version` bump counts as current. And `knowledge_repos.head` doesn't change on a working-tree edit, so it can't tell the index is stale. The brief says hooks in later parts "read only the index", but nobody is named to refresh the index after a pull or an edit. Fix now: writes commit their own pathspec only. Add a per-repo fingerprint or per-file hash compare as the staleness rule. Say what an uncommitted edit means.
- F-4 · Major · The repositories / brief Assumptions · The project folder hash is not stable across machines. `projects.key` is taken from `aliases[0]` when the project is first seen (`src/core/project.ts:118-120`) and never changes after. A project first seen without a remote, or adopted from an `imported:` alias, keeps a `path:` or `gitdir:` key forever. The brief's assumption ("stable across clones of the same remote") is therefore false for those projects. Machine A and machine B will hash the same project to different folders, and a project that gains a remote keeps its old folder. The hash also can't be reversed: from the folder alone you can't tell which project it belongs to. Fix now: hash the remote alias when one exists. Put a manifest file in each repository (scope, project aliases, format version) so a rebuild or a sync can map the folder back without the database.
- F-5 · Major · The taxonomy · The taxonomy lives in one machine's workspace repository, and entries in other repositories are checked against it. Entries in a shared repository (synced) are validated against each teammate's own workspace taxonomy, so the same shared entry is valid on one machine and has a problem on another. "Renaming rewrites ... every entry that carries the area in one commit" can't be one commit when the entries sit in workspace, project and shared repositories. One person also shouldn't rewrite the team's shared entries through their own taxonomy. Fix now: make area ids immutable and let only a label be renamed, so entries never need rewriting. Give the shared scope its own `taxonomy.md`, rather than "reuses it until part 5".
- F-6 · Major · Design sketch / The entry (validation) · Strict validation makes versions of the binary disagree. "A bad field" means a `kind` or `status` value the binary doesn't know. When a newer binary adds a kind (personas are the likely case, part of the stated product), older teammates' binaries list those shared entries with a problem and never count them `active`. Nothing reports it, and the team sees different knowledge. There is also no format version in the files or the repository. Fix now: add a format version in the repository manifest (F-4). Decide whether an unknown enum value is a problem or is kept and shown as unknown, depending on whether that format version is newer.
- F-7 · Major · Proposals · The proposal format is weak for both merging and sync. (a) `proposals/<id>.md` doesn't say what the id is. A local counter or a database rowid would collide across machines, so it needs to be globally unique. (b) `base_version` alone can't recover the base content, so the viewer's three-way merge (part 3) has nothing to merge against. Record `base_commit` or `base_hash`. (c) A proposal for `target: new` has no slug or id reserved, so two pending "new" proposals can produce the same slug at accept. (d) Proposals committed into the shared repository travel to the whole team before part 4's policy exists. (e) When accept and reject delete the file, the index loses the decision. Any decision history then means `git log`, which spawns a process: a cost the viewer and tools will pay forever. Fix now: use globally unique ids, store a base hash, and keep a decided proposal (or a decision record) in the index.
- F-8 · Major · The index · `project_id` will be NULL in the workspace and shared scopes. If it sits in the key (scope, project_id, slug), SQLite UNIQUE treats NULLs as distinct, so `INSERT ... ON CONFLICT` never fires and every refresh adds duplicate rows. A builder will get this wrong unless it is stated. Fix now: use a non-null sentinel such as 0, or key on (repo_id, entry id) with `knowledge_repos` holding a surrogate `repo_id`. Also, `project_id` is a local integer that means nothing on another machine. It must never be written into a file or a proposal.
- F-9 · Major · The repositories · The scope is a closed set of three, and `shared/` is singular. A team server (part 5) will almost certainly need more than one shared repository (several teams, a client space). Today that would change the folder layout, the `scope` column and the CLI flag `--scope workspace|shared|project` all at once. Fix now: lay out `shared/<space-id>/` and make the index key a repository id instead of an enum, even if only one space exists today.
- F-10 · Major · The index (module migration namespace) · The namespace is missing three rules that are hard to add once released. (a) What a binary does when `module_migrations` holds a version newer than it knows. The core has `SchemaTooNewError` (`src/store/db.ts:126`); the module namespace has no equivalent, so a downgrade may run against a table shape it doesn't know. (b) Who creates `module_migrations` itself, given that `user_version` "does not move". (c) Whether module migrations take the same backup and `BEGIN IMMEDIATE` lock as `migrate()`, and whether a module's tables are created when it is switched off (ADR 0020 K8 said yes). Also carry over ADR 0020's rule against module migrations putting indexes on core tables, or the reverse rule for when they do. Personas will be the second user of this namespace, so its contract is long-term debt.
- F-11 · Major · Versioning and writes (identity) · People are identified by display name. `author: André`, with a fallback to the git name and then `you`, gives no stable identity for the people part 4 grants permissions to and part 5 authenticates. Two people both called `you`, or one person renamed, merge or split attribution in git history for good. The e-mail `<slug>@knowledge.wizardingcode.invalid` doesn't say whose slug, and it can't be changed after commits exist. `agent:<id>` doesn't say what the id is: host, session or model. Fix now: settle the e-mail and identity scheme (a stable person id per install, mapped later to a team account) and the format of an agent id, because history can't be rewritten after sync.
- F-12 · Nit · The repositories · `git init` follows the user's `init.defaultBranch`, so machines will end up with `master` on some and `main` on others before sync exists. Fix it with `-b`. Pin `core.autocrlf=false`, or the `hash` column and the stale check will differ on Windows.
- F-13 · Nit · Versioning and writes · The `.lock` file sits in the repository folder and must be ignored by git, or every `git add` of the whole tree will pick it up. With `spawnSync` git on a large repository, the fixed 60-second staleness limit could break a live lock. Say where the lock lives (outside the work tree, or in `.git/`).
- F-14 · Nit · The index · `knowledge_fts` is described as self-contained but has no key columns. ADR 0020 shows it needs the entry key stored with it as UNINDEXED columns, so deletes can stay within a scope or repository without depending on rowids. The `hash` column doesn't say what it is a hash of: raw bytes, or the text after normalisation.
- F-15 · Nit · The entry · No relation fields are reserved. Part 2 will judge duplicates and contradictions, and the end state of an entry (`archived`) has no "replaced by". A `supersedes:` or `links:` field (by `id`, see F-1) added later means a format change in every repository. `created` and `updated` are dates only, so they can't order two writes on the same day for recency or for the viewer.
