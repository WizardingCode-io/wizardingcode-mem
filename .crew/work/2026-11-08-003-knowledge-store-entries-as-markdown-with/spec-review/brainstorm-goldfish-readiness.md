# readiness findings for 2026-11-08-003-knowledge-store-entries-as-markdown-with
reviewer: goldfish-readiness
read: .crew/work/2026-11-08-003-knowledge-store-entries-as-markdown-with/concept.md (whole), .crew/work/2026-11-08-003-knowledge-store-entries-as-markdown-with/brief.md (whole), src/store/db.ts, src/store/migrations/0007_links.sql, src/engine/module.ts, src/doctor/checks.ts (database check, readingDb, imports), docs/adr/0019-one-engine.md, docs/adr/0020-knowledge.md, plus src/backup/backup.ts (restoreBackup, removeHistoryIndex) and src/core/project.ts (resolveProject) to check the restore and project-key claims. Lens: migration and backward compatibility.

## Findings
- F-1 · Blocker · The index ("applied after the core migrations") · Nothing says where module migrations run in `openDb`. Today `migrate()` returns at `if (current === latest) return;` before it takes the lock. So a 0.6.0 database (already at `user_version` 7) gets no module tables if the module step sits inside `migrate()`. The plan has to say four things. (a) The module step is a separate pass that runs even when `user_version` is at the latest. (b) It runs under the same second connection's `BEGIN IMMEDIATE`, and reads `module_migrations` again under the lock so that hooks opening together apply it only once. (c) It takes a backup or not: today `backup()` runs only when core migrations are pending, so the first knowledge migration on an existing store runs with no backup. (d) What happens on the first hook after an upgrade. K8 puts table creation on whatever opens the database first, which is usually a hook, and the brief says "nothing in this part runs on a hook". The plan should state that this one-time DDL is allowed.
- F-2 · Major · The index / K8 ("an older binary ignores tables it does not know") · There is no rule for a binary that finds `module_migrations` rows for `knowledge` at a version higher than its own list. A later knowledge migration 2 might add a NOT NULL column or change the meaning of `version` or `hash`. A binary with only migration 1 would then fail its inserts or corrupt rows on write or `knowledge rebuild`, because `SchemaTooNewError` checks only `user_version`. Without a rule, an engineer will "ignore" the newer version as K8 says and ship the corruption. The plan must choose: module migrations are additive only (nullable or defaulted columns, no renames), or knowledge reads and writes are refused while the module version is newer. That would be a module-level too-new error, reported by `doctor` and checked against the backup name in `restoreBackup`.
- F-3 · Major · The index (archived module) · ADR 0020's knowledge module already used `module_migrations(module, version, name, applied_at)` with the id `knowledge`, versions 1 to 5, and tables named `knowledge_entries`, `knowledge_fts` and `knowledge_proposals` with different columns. It also put the index `injections_memory_shown` on a core table. Any store that ran the archived build (the author's development store, or a test copy kept around) already has rows `knowledge/1..5`. On such a store the new binary would skip its own migrations and run against the old schema. An engineer would reuse the name and version 1 as the concept implies. The plan must say what to do about this: detect the archived shape and drop it, start the new module at a version above 5, or state that no such store exists anywhere.
- F-4 · Blocker · The repositories (`projects/<key>`); brief assumption "stable across clones of the same remote" · This is false as written. `resolveProject` sets `projects.key` once, at creation, to whatever was the strongest alias then (`aliases[0]`), and never changes it. A project first seen without a remote keeps `path:<root>` after it gains one. An adopted import keeps its import-time key. A second machine, or a store rebuilt after losing the database, derives a different key for the same project. All of these give the same project a different folder hash. Separately, a hash cannot be reversed. If the tables are dropped or the database is lost, `knowledge rebuild --scope project` cannot map `projects/<hash>/` back to a `project_id` unless the repository records its own project key (a file in the repository, for example). So "deleting the tables loses nothing" is false for the project scope. The plan must fix two things: the key a repository is derived from (and that it is written inside the repository), and what happens to a repository whose project the database no longer knows (orphan listing, re-attach).
- F-5 · Major · The index (backup restore) · `restoreBackup` swaps only the database file in the store dir and leaves `<data dir>/knowledge/` alone. After a restore the index (`version`, `hash`, `knowledge_repos.head`) describes older commits than the files hold. Also, as `backup.ts` already notes for the history index, the copy "may give [ids] to other projects", so `knowledge_*` rows can sit under the wrong `project_id`. The concept does not say whether the base-version check reads the version from the file or from the index. If it reads the index, stale writes after a restore are wrongly refused or wrongly accepted, and old rows show under the wrong project. The plan must say that a restore invalidates the knowledge index, either by dropping its rows the way `removeHistoryIndex` drops the history index, or by checking `knowledge_repos.head` against the repository's HEAD before reading. It must also say that the version check reads the file.
- F-6 · Major · The repositories (backups and store moves) · The files are the truth (K2), but nothing backs them up. `backup` copies only the database, so the one copy of curated knowledge lives in local git, while the old index rows are what gets backed up. `store move` (`src/store/move.ts`) moves the database only. The database can live in a separate store dir, and `knowledge_repos.path` has no stated form, so an absolute path breaks when the data dir moves. The plan must decide whether backups include the repositories (or say plainly that they do not) and store `path` relative to the data dir, or not store it at all and derive it.
- F-7 · Major · Rollback of this part · A rollback to 0.6.0 leaves these behind: `module_migrations`, `knowledge_repos`, `knowledge_entries`, `knowledge_proposals`, `knowledge_fts` with its FTS5 shadow tables (`_data`, `_idx`, `_content`, `_docsize`, `_config`), and the git repositories under `<data dir>/knowledge/` with any pending proposals and `.lock` files. 0.6.0 tolerates them, since `user_version` did not move and there are no triggers on core tables. But nothing removes them: `uninstall` does not, and no `knowledge` cleanup exists. Upgrading again must accept existing repositories, rows, and proposals written before the rollback. The plan must state three things. Knowledge tables carry no foreign keys or triggers on core tables, so an older binary's writes to `projects` never touch them. A future core migration that rebuilds `projects` must not cascade into them (this is ADR 0020's `injections` rule again). And whether a rollback leaves the data in place or offers a removal step.
- F-8 · Major · Versioning and writes (a write stopped halfway) · The write steps contradict each other. "Raise `version` by one" comes after the commit, but `version` lives in the file being committed, so it must be raised before the rename. Nothing says what happens when the file has been renamed into place and then `git add` or `git commit` fails. Causes include a stale `.git/index.lock` from a killed git, a full disk, or a global setting such as `commit.gpgsign` or a commit template slipping past the per-repository config. The tree is then left dirty with a raised version and no commit, and the index may or may not be updated. The plan must give the order of the steps, the recovery (restore the path from HEAD, or detect a dirty tree at the next write and refuse or repair), and whether the index is updated before or after the commit. It must also say whether the repository-root `.lock` is excluded from git (`.git/info/exclude`), so that it is never committed.
- F-9 · Major · What must be true before the first write · The concept does not list these preconditions.
  - git is present at a minimum version, for the empty template, `core.hooksPath` and `-c commit.gpgSign=false`.
  - Global config does not leak in (`core.autocrlf`, `core.fsmonitor`, `include`). Either `GIT_CONFIG_GLOBAL` is isolated, or the author fallback reads `user.name` separately first.
  - The initial branch name is fixed.
  - `taxonomy.md` already exists in the workspace repository. It must, because every entry's `area` is validated against it, so a first write to a project or shared scope must create the workspace repository first, and the plan must say so.
  - The module tables exist.
  - The data-dir folders are created with mode 0700.
  - An unborn HEAD is handled: `git init` may succeed and the first commit fail.
  
  Without this list, an engineer builds a first write that fails on a fresh machine or inherits the user's global git hooks and signing.
- F-10 · Major · `knowledge rebuild` · Five things are undecided. Whether `--scope project` covers one project or all of them, and how it gets the project. Whether rebuild reads the working tree or HEAD; after F-8 these differ, and reading the tree indexes uncommitted content. Whether it takes the repository `.lock`, so it does not race a write. Whether the delete and the re-read happen in one transaction, so readers never see an empty index. What happens to rows for a repository folder that is gone.
- F-11 · Major · doctor (`src/doctor/checks.ts`) · Doctor opens the database read-only through `openExisting` and never migrates. `readingDb` decides "skip, will be migrated" from `user_version < LATEST_VERSION` only. A 0.6.0 database at version 7 that only doctor has opened lacks the module tables, so any knowledge check that reads the index reports `fail`, not `skip`. The plan must say whether the knowledge checks read files only (as ADR 0020's doctor did) or make the skip rule aware of module versions. It must also say whether the git check runs when knowledge is off.
- F-12 · Nit · The index ("the store reads every built-in module's list from a leaf file") · Neither the leaf file's path, the `ModuleMigration` shape (`version`, `name`, `sql?`, `run?`, the same as `Migration`?), nor a test seam like `OpenOptions.migrations` for module lists is named. These are small, but they belong in the plan.
