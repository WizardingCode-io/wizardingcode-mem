## Findings
- F-1 · Major · spec.md line 36 (CUJ 1), line 37 (CUJ 2), line 41 (CUJ 6), line 130 ("the viewer and the CLI pass the person"), line 16 / plan.md line 35 (`rebuild`, `adopt`, `list` only) · In this part a person has no way to write. The CLI has no write or area subcommand, and the viewer and MCP tools come in parts 2 and 3. So "a person saves an entry", "a person edits", and add/rename/remove area can only be called from tests. `adopt` cannot help either: it needs a repository, and `ensureRepo` only runs "on first write". The Problem (line 7: the team's knowledge sits in Obsidian where nothing reads it) is still unsolved for any person after this part ships. An implementer would build these CUJs as library calls only and miss that no person can carry them out. Simplest fix: either add a thin `knowledge write`/`knowledge area` command over `writeEntry`/`addArea`, or let `adopt` create a missing repository, or restate CUJs 1, 2 and 6 as store-API journeys and say plainly that part 1 has no write channel.
- F-2 · Major · spec.md line 190 (`EngineModule` gains `migrations?` and also `MODULE_SCHEMAS` in `src/engine/module-schemas.ts`), plan.md line 13 · Two places declare the same migration list. `openDb` reads only the leaf `MODULE_SCHEMAS`, because it must not import module code on the hook path. That leaves `EngineModule.migrations` with no reader. An implementer would fill in both, and a later module that sets only `migrations` on its `EngineModule` (the obvious place in `src/engine/module.ts`) would never get its tables. Keep the leaf list as the only source and drop the `EngineModule` field.
- F-3 · Major · spec.md line 190-191, plan.md line 13 (`ModuleMigration {version, name, sql}`, `migrateModules(...)`) · This already exists. `src/store/db.ts:15` defines `Migration {version, name, sql?, run?}`, and `migrate()` at `src/store/db.ts:117-160` already does the second connection, `BEGIN IMMEDIATE`, re-read under the lock, backup-first and apply-in-order steps that the spec describes again for modules. An implementer would write a second copy of that upgrade-lock logic, and the two copies would drift apart (backup rules, busy timeout, rollback). Reuse `Migration` as it is, and make `migrate()` work over a "read current version / record version" pair, so the core (`user_version`) and each module (`module_migrations` rows) share one loop.
- F-4 · Major · spec.md line 191 (two-column `module_migrations` upgrade via `PRAGMA table_info`), line 196 (start at version 6, drop the withdrawn tables), AC-16 line 254, plan.md line 12 (archived fixture) · ADR 0020 line 3 says the withdrawn module was "removed before any release". The only stores that hold its rows are development machines. The spec still builds and tests a permanent compatibility path for them in the open path every user runs: column detection, `ALTER`s, an eight-object drop list and a fixture. An implementer would carry that code forever for a population of perhaps one. If no released build ever wrote these rows, a one-off `doctor` hint or a manual cleanup note covers it, and numbering could start at 1. If some store outside the author's did run it, the spec should say which one.
- F-5 · Nit · spec.md line 14 (the shared scope with its own taxonomy), line 90, line 210 (`rebuild --scope shared`) · The shared repository and its separate taxonomy serve sharing that only arrives in parts 4 to 6. The brief (concepts_brief.md line 37) records why this was kept ("the mission names it"). I note it only as speculative surface whose cost should stay small. Nothing in this part reads a shared taxonomy except `removeArea` and the tests.
- F-6 · Nit · spec.md line 134 (quota of 5 per entry and 200 per repository, plus `redact`) · In this part no channel produces agent writes (line 21: no MCP tool). The quota limits a caller that does not exist yet, and its numbers are not based on any measurement. It belongs with part 2, where the tool and its abuse case exist. `redact` costs little and can stay.
- F-7 · Nit · spec.md line 102-104 · The `.git/config` scan refuses `hooksPath`, `fsmonitor` and `sshCommand`, but line 102 already says that the `-c` overrides neutralise exactly those keys. Only `include`/`includeIf` actually needs the scan. `core.sshCommand=` and `diff.external=` guard features this part never uses (no remotes, no diff). Fewer guards, each with its reason, would read more clearly.
- F-8 · Nit · spec.md line 78 (the `slugify` algorithm step by step), line 102-103 (the full `git -c` and environment list), line 110-126 (an eleven-step write with the exact git commands), line 157 (one paragraph for accept/reject) · The Design section is pseudocode and sits at code altitude.
