## Findings
- F-1 · Major · plan.md:19-20 · The tests in step 7 call `checkRepoConfig(repo)`, but the `repo.ts` export list in step 8 does not include it, and no step says who calls it. The test also requires `runGit(... ["status","--porcelain"])` to succeed on a repository with a hostile `.git/config`, while spec.md:104 says the config check runs "before any git call on an existing repository". An implementer will either put the check inside `runGit`, which breaks the step 7 test, or leave it uncalled, which leaves AC-15's refusal unwired.
- F-2 · Major · plan.md:19-20 · Step 8 defines `gitVersion()` with no arguments, cached, and `requireGit()` with no arguments. The step 7 test wants `gitVersion()` to parse the literal string `git version 2.54.0 (Apple Git-157)` and `requireGit` to refuse `[2, 31, 0]`. Neither signature can take that input, so the implementer has to invent a pure parser and a version parameter, and the tests as written do not typecheck.
- F-3 · Major · plan.md:17-18,44 · The git `user.name` lookup is "cached per process". But one test file needs three different answers in a row (the setting, then "Ana Lopes" from a HOME `.gitconfig`, then `you`), and the doctor test (step 18) needs "no git name". No reset seam is defined, and the cache is not keyed by HOME. What `allowUserConfig` actually changes in the environment is also unstated: does it pass HOME, and does it drop `GIT_CONFIG_GLOBAL` and `GIT_CONFIG_NOSYSTEM`? And `runGit(dataDir, repo, args, …)` requires a `repo` that a `config --global` call does not have.
- F-4 · Major · plan.md:20 · `runGit(dataDir, repo, args, {identity?, allowUserConfig?, timeoutMs?})` and `gitEnv(dataDir, identity?)` take no environment. Yet the tests at plan.md:19,31,32,39 depend on a substituted `PATH` (an empty folder, or stub `git` scripts), and `KnowledgeStore` carries an `env` (plan.md:33). The implementer must choose between mutating `process.env.PATH` and threading `store.env`, and tests that run in parallel depend on that choice.
- F-5 · Major · plan.md:40 · Step 17b puts `logError("knowledge.<operation>", …)` in `runGit`'s failure path, but `runGit` takes no operation argument (plan.md:20), so it cannot write the `knowledge.write` scope the test at plan.md:39 expects. Also, `logError`'s `dataDir` defaults to `defaultDataDir()` (src/util/log.ts:21), and the plan does not say to pass the store's `dataDir`. The test reads `<data dir>/logs/wizardingcode-mem.log`.
- F-6 · Major · plan.md:21-22 · The test forces a folder-name collision "by a stub hasher", but neither `resolveRepo(db, dataDir, ref, {create, writer})` nor `projectFolderName(aliasOrKey)` has a hasher seam. The `-2` collision case therefore cannot be written against the defined API.
- F-7 · Major · plan.md:12-13,26-27,32 · Several signatures differ between the tests and the implementation steps. The test calls `moduleSchemaState(db, "knowledge")`, but step 4 defines `(db, module, latest)`. The tests call `addArea(root, …)` and `taxonomyFor(ref)`, but step 12 defines `readTaxonomy(store, root)` and `taxonomyFor(store, ref)`. The test calls `acceptProposal(id, person)`, but spec.md:157 defines `acceptProposal(store, ref, proposalId, person)`. Whichever form is built, `bun run typecheck` fails on the other.
- F-8 · Major · plan.md:34 · The rebuild test compares rows "without `indexed_at` and `id` of `knowledge_repos`". But `knowledge_entries.repo_id` and `knowledge_proposals.repo_id` reference that id (spec.md:199-200). After `DELETE FROM knowledge_repos`, the rebuild can assign ids in a different walk order, so the entry and proposal rows differ even when the rebuild is correct. The comparison has to map `repo_id` to `path`, and the plan does not say so.
- F-9 · Major · plan.md:22,33 · spec.md:204 defines `rebuildAll(db, dataDir, scope?)`: it walks `knowledge/`, maps each folder through its manifest, reports orphans, deletes the rows of folders that are gone, and applies the scope filter. No plan file is given this function. `listRepos` in `resolve.ts` covers only the walk and the orphans, so the deletion of stale rows and the `--scope` filter that the CLI needs (plan.md:34) have no owner.
- F-10 · Major · plan.md:20 · `headOf(repo)` is built on `readGitInfo` (src/core/git.ts:72-80), which walks up the parent folders until it finds a `.git`. For a repository folder without `.git`, or before `git init`, inside a data directory that sits in a parent git tree (the case tested at plan.md:19), it returns the parent repository's HEAD. The recorded head and `ensureFresh` would then be wrong. The plan does not require `headOf` to check `<repo>/.git` itself first.
- F-11 · Major · plan.md:44-45 · spec.md:193 says that when the recorded module version is newer than this binary's list, "`doctor` names it". Step 19 does not read `moduleSchemaState`, and step 18 has no too-new case. The ruling is silently dropped.
- F-12 · Major · plan.md:45 · `runChecks` (src/doctor/checks.ts:532-558) only contains exceptions inside `readingDb` callbacks. A `knowledge(context)` check that reads folders, manifests and `.git`, and runs git, will take the whole of `doctor` down on any filesystem or parse error (EACCES, bad JSON in a manifest). The plan does not say the check must catch its own errors and report `warn` or `fail`.
- F-13 · Major · plan.md:45 · src/doctor/checks.ts:531 promises that doctor "Looks, and changes nothing". A plain `git status` refreshes `.git/index` and takes `.git/index.lock`. Run from doctor or `list`, it can make a concurrent write's commit fail on the lock. The plan does not ask for `--no-optional-locks` or `GIT_OPTIONAL_LOCKS=0` in the runner, or at least on read-only calls.
- F-14 · Major · plan.md:17,44 · `personAuthor` returns only `{kind, name}`, and the fallback is the name `you`. Doctor's "no author (no setting, no git name) gives `warn`" cannot tell that fallback apart from a setting or git name that is literally `you`. The plan defines no source field, such as `setting | git | default`, that the check could read.
- F-15 · Major · plan.md:18 · `RULES` run only in `validatePatch` (src/settings/settings.ts:218-242). `loadSettings` (settings.ts:112-148) passes environment and file values through unchecked. If `WIZARDINGCODE_MEM_AUTHOR=agent:x` comes from the environment or a hand-edited `env` file, a person's commit would be credited to `agent:x`, which breaks the person/agent attribution. The plan does not say that `loadSettings` drops an invalid author, the way `integer()` falls back to its default.
- F-16 · Major · plan.md:20 · The repository lease is 60 s and is never extended, while each git call may take up to 15 s (spec.md:100). A first project write runs `ensureRepo` for the workspace and then the project (init, add, commit each), plus status, add and commit, and `removeArea` scans every repository. Once `until` passes, `holds()` (src/store/meta.ts:64-65) lets a second process take the lease from a writer that is still running. The plan gives no renewal, and no bound on the git calls per lease.
- F-17 · Major · plan.md:3,34 · tests/preload.ts:38-40 removes shell variables that change behaviour (`WIZARDINGCODE_MODULES`), but the plan adds no such line for `WIZARDINGCODE_MEM_AUTHOR`. A developer who exports it changes the author in every spawned CLI test. Step 16 also never says which person name it expects (with HOME set to the empty test home by preload, presumably `you`).
- F-18 · Major · plan.md:50 · spec.md:265 states that "The README and the ADR say so" about the repositories not being in `wizardingcode-mem backup`. Step 21 modifies `CLAUDE.md` and creates the ADR but never modifies `README.md`, so the spec's claim ends up false.
- F-19 · Nit · plan.md:13 · Three points of `migrateModules` are unstated. `OpenOptions.moduleMigrations?` holds schemas, not migrations, and the plan does not say whether a test value replaces `MODULE_SCHEMAS` or adds to it (this changes whether row `('knowledge', 6)` appears in the "versions 1 and 2" case at plan.md:12). It does not say where `openDb` gets its default schemas (src/store/db.ts:49-56,172). And it does not say what version `backup(db, dir, version)` gets for a module backup, which the file name embeds (db.ts:76).
- F-20 · Nit · plan.md:13 · `EngineModule.migrations?` is added, but no knowledge `EngineModule` exists or is created (`BUILT_IN = [memory]`, src/engine/modules.ts:10), and nothing reads the field. `MODULE_SCHEMAS` is the real source, which leaves two declarations that can drift apart.
- F-21 · Nit · plan.md:18 · `ui/src/api.ts:92-104` declares its own `SettingKey` union. Adding `WIZARDINGCODE_MEM_AUTHOR` to `SETTING_KEYS` leaves the viewer's type behind what `publicSettings` returns, and the plan does not mention it.
- F-22 · Nit · plan.md:19 · The takeover test assumes pid 999999 does not exist. `ownerAlive` (src/store/meta.ts:53-61) probes the real pid, and on Linux `pid_max` can reach 4194304, so the test can fail now and then on a live process.
- F-23 · Nit · plan.md:20 · The knowledge lease key is not part of `anyLeaseActive` (src/store/meta.ts:120-130). A store move can therefore run during a knowledge write and leave that write's index rows in the old database. The plan says nothing either way.
- F-24 · Nit · plan.md:20 · `runGit`'s `timeoutMs?` has no stated default. The 15 s comes only from spec.md:100, and the plan's signature does not restate it.
