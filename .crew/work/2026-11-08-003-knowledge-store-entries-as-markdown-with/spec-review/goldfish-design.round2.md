## Findings
- F-1 · Blocker · spec.md:112, :124, :157 (rollback on a failed commit) · The spec says each staged path is "restored from HEAD (`git checkout -- <paths>`)". That is not what the command does. `git checkout -- <path>` restores the working tree from the index, and the index holds the content that `git add` just staged, so the command does nothing. A new file's staged add also stays in the index after the file is removed. The result is the opposite of what is promised. After a failed write, accept or reject, the failed content is still on disk and staged, `git status --porcelain` reports the path as dirty, and the next write is refused as `dirty`. `knowledge adopt` would then commit the failed agent or person content as the person's hand edit. A failed accept therefore does not leave the proposal "back under `open/` unchanged". The command needs to be `git checkout HEAD -- <paths>` (or `git restore --source=HEAD --staged --worktree`), with the index entries of new paths removed. AC-18 (line 252) tests the outcome, but whoever builds it will copy the wrong command from the spec.
- F-2 · Major · spec.md:118, :231, :260 (the lease) · Line 231 rejects a lock file because "an age-only lock can be stolen from a live writer". The lease has the same flaw. `claimLease` (src/store/meta.ts:64-65, 73-86) treats a lease as free once `until <= now`, even if its owner is still alive, and Risks (line 260) admits "of a live one after 60 s". Nothing renews the lease. The worst case is longer than 60 s: a project write that first creates the workspace repository (init, add, commit), then the project repository, then runs status, add and commit is about nine git calls with a 15 s timeout each. Adopt and `removeArea`, which runs `ensureFresh` over every repository, have no bound at all. So a slow but live writer can lose its lease halfway through, and a second writer can then run at the same time on the same work tree and index. The spec needs either renewal at each git step or a bound proven to fit within 60 s.
- F-3 · Major · spec.md:119 (step 4, a project write creates the workspace repository) · The workspace repository is created while only the project repository's lease is held. Two first writes to two different projects can both run `ensureRepo` on `knowledge/workspace/` at once: concurrent `git init` and commits of `knowledge.json` and `taxonomy.md` in one work tree, with no lease covering them. Whoever builds this will miss that step 4 needs the workspace lease as well.
- F-4 · Major · spec.md:104 (local `.git/config` refusal list) · The threat named here is a repository folder dropped in "by a person or a later sync". The deny list only covers `include`, `includeIf`, `hooksPath`, `fsmonitor` and `sshCommand`. A local `[filter "x"] clean = <cmd>` (or `process`), together with a `.gitattributes` in the work tree saying `* filter=x`, runs that command on the `git add` of every write and adopt. A `smudge` filter runs on the restore checkout. Nothing on line 102 neutralises these, so "Nothing of the person's git setup ... runs here" (line 103) and the security claim on line 274 are false for a planted repository. AC-15 does not cover it.
- F-5 · Major · spec.md:120, :161, :204, :217 (what counts as "changed outside the engine") · Dirtiness is defined as `git status --porcelain` being non-empty, but no `.gitignore` is written and nothing is excluded. Several ordinary things make a repository dirty: Finder's `.DS_Store`, an `.obsidian/` folder (the Problem says this knowledge lives in Obsidian today, so people will open these folders as vaults), editor swap files, and an `entries/.<slug>.md.tmp` left by a crash between steps 8 and 9. None of these are "entry files" or "proposal files", so `adopt` (line 161) never commits them. The result is a permanent doctor `warn` and, at repository level, a permanent "changed outside the engine" state, while `adopt` reports `clean`. The spec should say which paths are ignored, and clean up or ignore the temp file.
- F-6 · Major · spec.md:161 together with :80 (adopt of a file the parser rejects) · Adopt does "parse; raise `version` ...; rewrite". The spec never says what adopt does with a hand-edited or hand-added file that fails parsing. Examples: a new note written in an editor with no `id`, which is the obvious way a person writes in an editor; an `area` outside the taxonomy; a broken frontmatter. The options are to commit it as it is, skip it, refuse the whole adopt, or assign an `id`, and the spec picks none. Whoever builds it will guess. A hand-added note without an `id` would otherwise stay as `file:<slug>` with `status: draft` forever, because a person cannot set an id (line 110).
- F-7 · Major · spec.md:161, :184 (hand edits of `taxonomy.md` and `knowledge.json`) · Adopt only handles entry and proposal files. A hand edit of `taxonomy.md` therefore stays dirty for good. `addArea`, `renameArea` and `removeArea` have no dirty check (step 5 checks only `entries/<slug>.md`), so they rewrite the file and commit it with `--only`. That sweeps the hand edit into the engine's commit, which is the thing Goal 2 (line 12) and D-11 (line 234) forbid. A hand removal of an area also silently turns every entry using it into `draft` with a problem (line 80).
- F-8 · Major · spec.md:134-155 (an agent's proposal) · Three things are left open. (a) Where `base_version` comes from: the agent's `baseVersion` or the current file's version. And is an agent's stale or `exists` write refused at propose time, or recorded and only refused at accept? (b) Redaction covers title, context, subject and body, but not the slug. A slug derived from an unredacted title, or given by the caller, puts a token into the file's frontmatter and into the commit message `knowledge: propose <id> for <slug>`. Those are kept in a history "the engine never rewrites". (c) The per-entry quota of 5 never applies to proposals for new entries, since each gets a fresh UUID (line 139). One agent can open 200 proposals for the same new slug.
- F-9 · Major · spec.md:184 (removeArea and project writes) · The check that no repository uses the area runs under the root repository's lease only. A project write validates its area against the workspace taxonomy (step 2) under its own lease. A project write that passes validation just before the removal is committed leaves an entry whose area no longer exists. That entry is then silently forced to `draft` and "never counted active" (line 80). This is a time-of-check to time-of-use race between leases, and the spec does not mention it.
- F-10 · Major · spec.md:204 (the 5,000-file cap) and :226 (decided proposals kept) · Decided proposals are never deleted (D-10). Only open ones are capped (200), so `proposals/decided/` grows without limit, and it counts towards the same 5,000 files per repository as entries. The spec does not say what happens at the cap: are files dropped silently, which ones, is a problem reported? A repository that gets steady agent proposals will eventually push real entries out of the index. There is also no size estimate for the database: every decided proposal keeps its full `body` in `knowledge_proposals`.
- F-11 · Major · spec.md:94 (resolving a repository by alias intersection) · Manifest aliases are only ever extended, and they include `path:` aliases. If a folder is reused by a different project, or one repository is cloned twice, a second project can match an existing manifest. `knowledge_repos` has `UNIQUE (scope, project_id)` and `path UNIQUE` (line 198), so the second project's row insert fails, or two projects silently share one repository. The spec does not say what happens when two projects' aliases match one manifest, or one project's aliases match two manifests.
- F-12 · Major · spec.md:100 (`Bun.spawnSync` for every git call) · The store API blocks synchronously for up to 15 s per git call, and a write is at least three calls. Part 2's MCP server is said to call `writeEntry` (line 130), and that server is a long-lived process. Each write there would freeze every other tool call for as long as git runs, and for up to 45 s or more in the worst case. The spec rules out only the hook path, so whoever plans part 2 will not see that this cost is built in here.
- F-13 · Major · Heilmeier questions 6 to 8 (whole document) · The spec has no estimate of cost or effort (Q6), no duration (Q7), and no midway check (Q8). The acceptance criteria give only the final check. This part is large: a YAML-subset parser, an isolated git runner, the module migration namespace with a legacy-table repair, three commands, a doctor check and an ADR. Without a budget or a checkpoint, the plan stage has nothing to tell it when the part is overrunning or where to split it.
- F-14 · Nit · spec.md:273 (write latency) · "About 30 to 80 ms on the author's machine" per git call is not backed by any measurement, and the count of three ignores `git --version`, `ensureRepo` on the first write, and the author lookup.
- F-15 · Nit · spec.md:217 (doctor) · Doctor is said to read "files and `.git` by hand", but it also runs `git status --porcelain`, which starts a process, possibly once per repository. The spec should state this and its cost.
- F-16 · Nit · spec.md:142, :157 (`base_hash`) · `base_hash` is recorded but accept never checks it; only the version is compared. Nothing in this part uses it, and D-8 makes the version a counter local to one machine. The spec should say whether it is deliberately unused until the sync parts.
- F-17 · Nit · spec.md:157 together with :121 (a new-entry proposal whose slug now exists) · `base_version: 0` against the step-6 rule "no `baseVersion`" is ambiguous. The `exists` message, "write with base version N", gives a proposal no action it can actually take.
- F-18 · Nit · spec.md:251 (AC-14 kept beside AC-18) · AC-14 is marked superseded but still says adopt restores from HEAD, which contradicts AC-18 and line 112. It should be removed instead of struck through.
- F-19 · Nit · spec.md:128 (commit e-mail) · The e-mail is `<slug of the name>`. A name with no Latin characters slugifies to `entry` (line 78), so different people would all get `entry@people.wizardingcode.invalid`.
- F-20 · Nit · spec.md:3, :32 (decisions D-1 to D-11) · The spec relies on decisions that are "recorded on the item" and that "the validator applies where nobody watches". D-2, D-4 and D-6 are only implied by the alternatives section, so a fresh reader cannot check what each one decided.
