## Findings
- F-1 · Major · spec.md:145-146 · Step 2 checks the change against the root taxonomy before step 3 takes the leases. If `removeArea` (line 217) holds every lease, removes the area, commits and releases between those two steps, the write takes the leases and commits an entry whose area no longer exists. The guarantee that `removeArea` "is refused while an entry carries the id" fails, and the entry is valid in git but a draft with a problem in the index. An agent's propose ("after steps 1 to 5", line 162) has the same race. The check needs to run again under the lease. Only accept (line 190) does this today.
- F-2 · Major · spec.md:190 · `acceptProposal` and `rejectProposal` read, rewrite and move `proposals/open/<id>.md` and commit it, but they never run step 5's `git status --porcelain` check on that file. Only the entry path gets checked. An uncommitted hand edit to an open proposal is accepted and committed by the person as the agent's proposal, with the message `Proposed by agent:<id>`. That breaks the goal at line 12 ("a file changed outside the engine is never swept into another write's commit") and gets authorship wrong in both directions. AC-5 and AC-18 do not test it.
- F-3 · Major · spec.md:134 · Leases are renewed only before a git call. In src/store/meta.ts:64-65 `holds` treats an expired lease as free even when its owner is alive. `removeArea` (line 217) claims the root's lease and every local repository's lease up front, then runs `ensureFresh` on each one. Each can be a full `rebuildRepo` of up to 3 x 5,000 files of 256 KiB (line 237), and it renews only the lease of the repository it is calling git in. With many project repositories, the leases taken earlier pass 60 s, and a write in one of them goes ahead while the removal still assumes they are frozen. Adopt's re-index (line 194) and the index transaction under a 5,000 ms busy timeout are other gaps without git calls. The claim that "a lease can never be lost" holds only if nothing but git runs between renewals, and the design breaks that.
- F-4 · Major · spec.md:140,151-153 · The failure rule covers a git commit that fails, but not a process killed (SIGKILL, power loss, a closed terminal) between the rename in step 8 and the commit in step 9. Nothing records the operation that was under way. After a killed accept, the entry holds the agent's content uncommitted and the proposal is still open. The next write refuses, and the documented fix, `knowledge adopt` (line 194), commits the agent's text as the person's own hand edit, with no `Proposed by`. It also raises the version, so the open proposal is then refused as stale. The design needs an answer for interrupted operations, at least a named risk and a recovery that keeps attribution. Risks (lines 295-307) list neither.
- F-5 · Major · spec.md:102,149,194,237 · Adopt commits files that fail to parse "as the person left them" (line 194), so a broken file can be tracked and clean at HEAD. Nothing says what a later `writeEntry` to that slug does. Step 6 compares `baseVersion` with `current.version`, but an unparseable file has no trustworthy version. Step 10 upserts by `(repo_id, id)` while rebuild has already indexed that file as `file:<slug>` or `dup:<slug>`, so the upsert hits `UNIQUE (repo_id, slug)` (line 232) after the commit has landed. The hand removal of an area (line 217) creates exactly this state for every entry that used it. An implementer has to guess, and the obvious guess fails in the index after the commit.
- F-6 · Major · spec.md:237,190 · Decided proposals are never deleted (D-10). An agent with 200 open proposals per repository fills `proposals/decided/` without bound, and the spec gives no growth figure or ceiling. Past 5,000 files the cap keeps "the newest by name", but proposal files are named by random UUID (line 167), so "newest by name" is arbitrary for proposals. For entries it means the last slugs in alphabetical order, so `a…` entries drop out of the index silently. The cap protects reads but decides what the index holds at random, and the spec does not face that scale limit (rubric "Risks and limits"; Heilmeier Q6).
- F-7 · Major · spec.md:289 · Line 128 refuses a `.git/config` `filter` section, the one setting named that runs a command on `git add` or restore. AC-15 lists only `include`, `includeIf`, `hooksPath`, `fsmonitor` and `sshCommand`. The highest-risk code-execution guard therefore has no acceptance test, and a builder working from the ACs could leave it out.
- F-8 · Major · spec.md:237 · `ensureFresh` is defined here as the check "later parts call before a read". It `lstat`s every file in three folders, up to 15,000 per repository, to compute the fingerprint, and the spec gives no cost or budget. The NFR at line 311 keeps this part off the hook path, but part 2's context read is the obvious caller, and the spec does not bound or measure the cost it hands on. Write latency gets this treatment (line 313); read freshness does not.
- F-9 · Nit · spec.md:165 · The quotas (5 per target, 200 per repository) and accept's check that an entry id already belongs to another slug (line 190) are evidently read from the index. The write path never calls `ensureFresh`, so after a database restore or a hand `git` operation the index can undercount and let an agent past the quota. Say whether these counts come from the files or a refreshed index.
- F-10 · Nit · spec.md:120,162 · When the first write to a scope comes from an agent, `ensureRepo` commits `knowledge.json`, `.gitignore` and the nine-area `taxonomy.md` "by the writer", that is, as the agent. Line 217 says "an agent cannot change the taxonomy". Say whether repository creation is authored by the person, or that this case is accepted.
- F-11 · Nit · spec.md:166 · `redact` runs after step 2 has checked the fields, so a replacement can push a title past 200 characters or change a context's length without anyone noticing. For an update, "the slug is derived from the redacted title" seems to point the proposal at a different slug unless the agent gives one. Say that an update always takes the caller's slug.
- F-12 · Nit · spec.md:134 · `anyLeaseActive` today checks five fixed keys (src/store/meta.ts:120-130). Knowledge lease keys are dynamic (`knowledge.lease:<path>`), so it needs a prefix query on `meta`. The spec says it "counts any knowledge lease" without saying how, and no AC covers a store move or restore waiting for a write.
- F-13 · Nit · spec.md:254 · "It never opens the index" contradicts "`moduleSchemaState` through `openExisting`" in the same paragraph. Say that it opens the database read-only for that one check only.
- F-14 · Nit · spec.md:224-225 · For a store that ran the withdrawn module, the first open takes a `VACUUM INTO` backup (db.ts:72-84) as well as the DDL. That open is usually a hook, which line 225 calls "a one-time DDL". It affects few stores, but the hook cost is a full database copy, not DDL.
- F-15 · Nit · spec.md:280-292 · Several specified behaviours have no AC: the 200-per-repository quota, accepting a new-entry proposal whose slug now exists (`exists`), a caller's slug refused because `redact` would change it, the doctor warning for a project matching two manifests, `over_cap` being recorded and printed, lease renewal failing mid-operation, and exit code 1 on a `KnowledgeError`.
- F-16 · Nit · spec.md:52 · The estimate of four to six hours for 24 tasks gives no reason. Those tasks include a YAML-subset parser, an isolated git runner, refactoring `migrate()` in db.ts into a shared runner, the store, three command groups and the ADR. The split rule at line 54 reduces the risk, but Heilmeier Q7 wants the estimate backed.
- F-17 · Nit · spec.md:5-7 · Heilmeier Q4 (what difference success makes) is implied by the Problem section but never stated as a payoff or a measure. Nothing says how anyone will know the Obsidian notes have moved or that agents' proposals are being decided.
