## Findings
- F-1 · Major · spec.md:153 (`headOf`, "reads `<repo>/.git` by hand and never walks up"), plan.md:14 (`headOf(repoPath)`) · This already exists. `src/core/git.ts:41-51` (`resolveRef`) reads a ref from `.git` without starting a process, and it handles both loose refs and `packed-refs`. Only `readGitInfo` (lines 72-80) walks up to a parent folder. The design does not mention it, so an implementer would write a second ref reader that reads only `.git/refs/heads/main`. After `git commit`'s automatic `gc --auto` runs `pack-refs`, that loose ref is gone, so `headOf` returns null. `ensureFresh` would then rebuild on every read, and the "recorded head equals HEAD" checks in AC-7 would fail. Simpler: take the non-walking part of `src/core/git.ts` (`resolveRef` on a given `.git` folder) as a shared function and build `headOf` on it.
- F-2 · Nit · spec.md:249 ("Counts are rendered by one helper"), plan.md:59 ("the plural helper") · The same `plural` lambda is already copied in three places: `src/status/report.ts:167`, `src/cli/commands/doctor.ts:11` and `src/cli/commands/compact.ts:7`. The plan would add a fourth. That helper only appends `s`, so it would print "2 entrys" for the spec's own outputs ("<n> entries", "2 entries" in plan.md:63). Better to extract the existing helper once, add a plural-form argument, and use it here.
- F-3 · Nit · spec.md:223 (`MODULE_SCHEMAS` in `src/engine/module-schemas.ts`, "the one list `openDb` reads"), plan.md:32 ("the store importing the engine's leaf") · `src/store/` imports nothing from `engine/` or `modules/` today (it imports only `util/`). This design makes `src/store/db.ts` import `src/engine/module-schemas.ts`, which imports `src/modules/knowledge/migrations.ts`, which imports `Migration` from `src/store/db.ts`. The lowest layer would then depend on a module, with an import cycle back to itself. The design should say this inversion is intended and that the cycle is type-only. The simpler alternative is to have the engine's openers pass the list in through `OpenOptions.moduleSchemas`.
- F-4 · Nit · plan.md:46 ("with 200 open proposals (written by a loop with distinct slugs) the 201st throws `quota`") · The quota is read from the index (`countOpenAll`, plan.md:16). Writing 200 real agent proposals runs about 600 git processes in one unit test, only to test a counter. Inserting 200 `knowledge_proposals` rows directly, or making the cap a parameter, tests the same rule in milliseconds.
- F-5 · Nit · spec.md:237 (`over_cap` "printed by `rebuild` and `doctor`"), spec.md:254 (doctor "never opens the index", yet warns "when files were left out by a cap" and reads `moduleSchemaState` through `openExisting`), plan.md:63 ("`over_cap` is reported by `rebuild`, not by doctor (doctor counts the files and warns past 5,000)") · The two documents disagree on whether doctor reports the cap. The plan's version is a second cap check that recounts the folders, alongside `rebuildRepo`'s own check. Pick one source: doctor either reads `knowledge_repos.over_cap` through the `openExisting` connection it already opens, or drops the cap warning. Then make "never opens the index" say exactly what doctor does not read.
