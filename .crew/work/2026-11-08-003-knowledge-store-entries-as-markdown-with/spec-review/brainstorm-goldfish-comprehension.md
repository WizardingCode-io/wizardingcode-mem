# comprehension findings for 2026-11-08-003-knowledge-store-entries-as-markdown-with
reviewer: goldfish-comprehension
read: `.crew/work/2026-11-08-003-knowledge-store-entries-as-markdown-with/concept.md` (whole), `.crew/work/2026-11-08-003-knowledge-store-entries-as-markdown-with/brief.md` (whole), `CLAUDE.md`, `docs/adr/0020-knowledge.md`; no standard (brainstorm); lens: usability and developer ergonomics for a newcomer, a person who writes and accepts entries, and an agent that proposes them

## Findings

**What this proposes.** The concept adds a second engine module, `knowledge`, next to memory. An entry is one Markdown file with fixed frontmatter: kind, area from a taxonomy, free-text context and subject, status, author and a version counter. Entries are kept in three kinds of git repository under the data directory: one workspace repository per machine, one per project and one shared. Every write is a git commit by its author and is checked against a base version. An agent never writes an entry directly. It writes a proposal file, and a person accepts it (the entry is written and the proposal removed) or rejects it (the proposal is removed). SQLite tables owned by the module index the files and can be rebuilt from them, through a new module-migration mechanism. Tools, viewer, sharing and sync come in later parts.

**How the existing system works, per this document.** The engine has one module today, memory. Memory is observed, local, decays and has no authority. Modules declare id, share, contribute, tools and views, but no migrations. Core schema versions use `PRAGMA user_version`, and module-owned tables were put off by ADR 0019 F2. Projects have a "strongest alias" key (remote, gitdir or path). Settings are a fixed, validated list in `<data dir>/env`. Hooks never spawn a process. An earlier knowledge module kept files inside each project (ADR 0020). It was withdrawn and is now being brought back in a new form.

- F-1 · Blocker · Versioning and writes / Proposals (the author rule) · The concept never says how the store tells a person from an agent. It also never says which entry point each one uses in this part. The only command it names is `knowledge rebuild`, and there is no write, accept or reject command, function or API. The agents this product serves run shell commands. If "person" just means "whoever didn't say `agent:<id>`", any agent can write directly and skip the proposal step, which defeats Q-3's "agents cannot disorganise it". A builder cannot write the gate, and a person cannot find out how to accept anything.
- F-2 · Blocker · The taxonomy · "Renaming rewrites the taxonomy and every entry that carries the area in one commit". But the taxonomy is in the workspace repository, and entries carrying the area are also in every project repository and in the shared one. One commit cannot span several repositories. The rule also doesn't say whether renaming raises each entry's `version`. If it does, every open proposal on those entries goes stale at once. "Removing is refused while an entry carries it" doesn't say whether that covers all scopes and pending proposals.
- F-3 · Major · The entry (`author`, `version`, `created`, `updated`) · The concept doesn't say which fields the caller supplies and which the engine stamps. A person or agent writing a file will fill in `version: 3` and `author:` by hand and get them wrong. Three things are open. Does `author` mean whoever created the entry, or whoever last wrote it? After an accept, does the entry name the agent, the person, or both (the commit names both, the frontmatter field holds one value)? Inside a proposal file, what do `version` and `author` hold, beside `base_version` and `proposed_by`? A builder will produce two incompatible readings of the same file.
- F-4 · Major · The entry (parser rule) · "A line that is not `key: value`" makes a file a problem file, but `taxonomy.md` itself needs `areas:` as a list. The concept doesn't say which YAML subset applies: lists, quoted values, a title with a colon in it, comments, multi-line values. ADR 0020 spelled its subset out, and this concept doesn't. The team is coming from Obsidian, so they will write `tags: [..]` and `aliases:` lists. Those files would become problem files with no warning beforehand. "Unknown keys are kept" breaks down when the unknown key's value is a list.
- F-5 · Major · The repositories · The concept doesn't say whether a person may edit entry files by hand, in an editor or in Obsidian. Hand editing is the team's current habit. A hand edit makes no commit, doesn't raise `version` and leaves the index stale. Nothing describes the next engine write landing on a dirty working tree: does `git add` commit the hand edit under the wrong author? A person will do this on day one.
- F-6 · Major · Proposals · The concept never defines `agent:<id>`. Is `<id>` the agent product (`claude-code`), a session id, or a model? It doesn't say how proposal `<id>`s are made, what slug a `target: new` proposal gets (or whether a literal entry slug `new` collides with it), or the slug rules at all. ADR 0020 had strict slug rules. Several proposals on one target, or two `new` proposals with the same title, aren't covered. An agent can't fill these fields correctly, and a builder will make them up.
- F-7 · Major · Proposals (stale accept, reject) · "Refused as stale, and the person decides" leaves the person with nothing to act on in this part. There is no rebase, re-propose or edit-then-accept step, because the merge view belongs to part 3. Reject records no reason. The agent gets no signal and will propose the same change again. As written, both errors fail to say what to do next.
- F-8 · Major · The entry (`kind`, `context`, `subject`) · The four kinds are listed but not defined. `knowledge` is also the module's name, and `persona` is a kind here, while ADR 0020 deferred personas to a design of their own. `context` and `subject` are both free text, and the only rule separating them is one example. Agents will file inconsistently and people will argue over the choice. The concept defers judging these fields to part 2 and gives no guidance for writing them now.
- F-9 · Major · The repositories (`projects/<key>`) · The folder name is a hash, so a person can't find their project's repository by eye. Nothing says how to map one to the other: no command, no index column shown. The brief says the key is "stable across clones of the same remote". A project keyed `path:` or `gitdir:` that later gains a remote changes its strongest alias, which leaves its knowledge repository orphaned. The concept doesn't address this.
- F-10 · Major · The repositories / Assumptions (backups) · The files are now the authoritative truth, and they live under the data directory, not in a project's own git. CLAUDE.md says `backup` copies the database, and the database here is only a cache. The concept doesn't say whether the knowledge repositories are backed up, moved or restored. A reader would not see the risk of losing curated knowledge.
- F-11 · Major · Versioning and writes (author fallback `you`) · Commits authored `you` are harmless on one machine. In the shared repository that part 6 syncs, every teammate without a setting becomes `you`. The fallback also hides that `WIZARDINGCODE_KNOWLEDGE_AUTHOR` exists: it is named in the brief but not in the concept, and CLAUDE.md says `SETTING_KEYS` is a fixed list to extend. Nothing tells the person once that their name is missing.
- F-12 · Major · Versioning and writes (failure in the middle of a write) · The write sequence is: rename the file, commit, raise the version, update the index. The concept doesn't say what happens when the commit fails after the rename (a hook-less git that still errors, a full disk), or when the index update fails after the commit. A builder can't tell whether the file is rolled back, or how the next write and `knowledge_repos.head` find the gap. The 60 s stale lock could also be stolen during a slow write. The concept doesn't say how.
- F-13 · Major · The repositories (`shared`) and The taxonomy · Before part 6, `shared` is a local repository that nobody else sees. A person who writes there will believe the team has it. The shared scope also checks areas against each person's own workspace taxonomy, so one shared entry can be valid on one machine and invalid on another. The assumption admits this for "until part 5", but neither the person nor the entry is told.
- F-14 · Major · Scopes (choosing one) · The concept doesn't say how a writer picks a scope, or what the default is. Nor does it say what `rebuild --scope project` acts on: the cwd's project or every project. There's no rule for the same slug in two scopes. An agent asked to "save this" has no rule for where it goes.
- F-15 · Nit · The taxonomy / Proposals · The concept doesn't say whether an agent's change to the taxonomy, or an agent setting `status: archived`, is also a proposal. Nor does it say what happens when a proposal names an area that was removed after it was written.
- F-16 · Nit · Versioning and writes · The e-mail `<slug>@knowledge.wizardingcode.invalid` doesn't say whose slug it uses. If it's the entry's slug, one person gets a different e-mail on every entry, and `git log --author` stops being useful.
- F-17 · Nit · The index · "A leaf file", "pinned hook snapshots", "composer contribution", "judge call" and "ADR 0019 ruling F2" are used without a gloss or a link inside the concept. A newcomer has to go to CLAUDE.md or the ADRs to follow them. `knowledge_repos.head` and `indexed_at` have no stated purpose. "Workspace" also clashes with ADR 0018's "one workspace" link signal named in CLAUDE.md.
- F-18 · Nit · The entry (problem files) · "Never counted `active`" doesn't say what status a problem file shows instead, or where the person sees the list of problems in this part (no viewer yet; `doctor` is mentioned only for git).
- F-19 · Nit · The entry (`created`, `updated`) · Date only, with no timezone stated, and the concept doesn't say whether a person may set them.
