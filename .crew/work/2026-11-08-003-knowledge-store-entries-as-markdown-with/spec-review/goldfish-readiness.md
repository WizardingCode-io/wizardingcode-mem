## Findings
- F-1 · Blocker · plan.md:37 (step 6) and plan.md:3 · Phase C cannot be built as ordered. Every function in `repo.ts` (line 14), `author.ts` (line 13) and `resolve.ts` (line 15) takes a `store: KnowledgeStore` and uses `ScopeRef` and `Writer`. The step 5 tests also need `openStore` to build a store. All of these are declared in `src/modules/knowledge/store.ts` (line 12), which is first created in step 13 (line 47, Phase D). So `bun run typecheck` fails at the end of Phase C, and the step 5 to 10 green runs cannot happen. The plan has to say where those types and `openStore` are created in Phase C (for example a `types.ts` or an early `store.ts` holding `openStore`).
- F-2 · Blocker · plan.md:47 (step 13) and plan.md:37 (step 6) · The same phase-order break, for the taxonomy. `ensureRepo` (step 6, Phase C) has to write `taxonomy.md` with the nine areas, and those come from `DEFAULT_AREAS`. The person's write (step 13, Phase D) has to validate `area` against the root taxonomy, and the step 11 tests need `legal` refused and `sales` accepted, which takes `taxonomyFor`/`readTaxonomy`. All of these are declared in `taxonomy.ts` (line 17), first created in step 17 (Phase E). The plan does not say where `DEFAULT_AREAS` and the taxonomy lookup live before Phase E.
- F-3 · Major · plan.md:45 (step 11) and plan.md:12 · The test sets "`GIT_TIMEOUT_MS` overridden to 50 through the store's options", but `openStore({ db, dataDir, env?, now? })` and `KnowledgeStore` have no timeout field, and `GIT_TIMEOUT_MS` is a constant (line 14). The implementer has to invent the option: its name, its type, and whether `runGit` reads it from the store or from `options.timeoutMs`. Two implementers will build different APIs, and the test cannot be written against the stated signature.
- F-4 · Major · plan.md:18 and plan.md:36 (step 5) · `stubGit` can only forward, fail, or sleep (`failOnce`, `fail`, `sleepMs`, `stderr`). Step 5 needs "a stub printing `git version 2.31.0`" for `requireGit`, and "a stub that prints its environment" for the `GIT_OPTIONAL_LOCKS` assertion. Neither is in the helper's contract. The implementer will either write two unspecified ad-hoc stubs or extend `stubGit` with behaviour fields the plan does not name.
- F-5 · Major · plan.md:15 and plan.md:40 (step 9) · Step 9 asserts that `listRepos` "reports the other as `ambiguous`" and reports "a manifest already mapped to another project". But the return type is `{ repos: Repo[]; orphans: string[] }`, which has no field for ambiguous or already-mapped manifests. Doctor's `ambiguous` warning (line 63) depends on the same missing data. The shape of that report (a field name, its element type, and how it tells ambiguous from already-mapped) is left to the implementer.
- F-6 · Major · plan.md:63-64 (steps 20, 21) · The doctor check "never opens the index" (spec Doctor), and its context gains only `env` and `gitVersion`. Yet it has to give the `author` warning, which comes from `personAuthor(store)` (line 13), and that needs a `KnowledgeStore` with a `db`. It also has to detect "a project matching two manifests", which needs `project_aliases` from the database. And it has to count entries and drafts with no index. The plan does not say how doctor gets a store or the project aliases, or whether it parses every file with `parseEntry` (and against which taxonomy) to count `2 entries, 1 draft`. A reader will either open the index, against the spec, or guess.
- F-7 · Major · plan.md:58-59 (steps 18, 19) · The default `--scope` is left open for `accept`, `reject`, `adopt` and `list`, and for `write` when `--scope` is missing. Only `area` (workspace) has a stated default. The step 18 test runs `knowledge accept <id>` and `knowledge reject <id>` with no `--scope`, and `knowledge adopt` and `knowledge list` with none. The implementer has to choose whether the default is workspace, all repositories, or a usage error (64). Which flags are required, and so exit 64 when missing, is also stated only for `--title`.
- F-8 · Major · plan.md:40 (step 9) · AC-2 requires a project's folder to come from its `remote:` alias when it has one. No step 9 case creates a repository for a project that already has a `remote:` alias and checks that the folder is `projectFolderName(<remote alias>)`: the only creation case uses `gitdir:` and `path:` aliases, so the key is hashed. An implementation that always hashes the key passes every test listed. The "else the newest by `createdAt`" tie-break is also never tested.
- F-9 · Major · plan.md:49 (step 15) and plan.md:48 (step 14) · When a folder holds more than 5,000 files, the plan does not say which 5,000 are indexed. The spec's sentence ("the newest by name beyond the cap are indexed") can be read either way, the plan does not settle it, and the 5,001-file test checks only the count and `over_cap: 1`. One implementer will index the first 5,000 by name, another the last 5,000.
- F-10 · Nit · plan.md:46 (step 12) · Two things are left open on redaction. First, which environment `redact` is given, `store.env` or the default `process.env`. Second, the slug for the "caller slug that `redact` changes" case. A lower-case slug such as `sk-` followed by 24 letters matches `openai-key` in src/core/redact.ts:35, and naming it would remove the guess. Because the test computes its expected text with `redact` itself, a mismatch in the environment passed would show up as a test that passes or fails depending on what the shell exports.
- F-11 · Nit · plan.md:8 and plan.md:12 · `KnowledgeEntry`, `EntryChange`, `KnowledgeProposal`, `Manifest` and `Identity` are used in signatures, but no file is named as their home and their field casing is not stated. The tests imply camelCase (`baseVersion`, `decidedVersion`), and `entry.ts`, built first, must hold at least `KnowledgeEntry` and `KnowledgeProposal`. `acceptProposal`'s, `rejectProposal`'s, `adopt`'s and the taxonomy functions' `person` parameter is also not given a type (presumably `Writer & { kind: "person" }`).
- F-12 · Nit · plan.md:11 and plan.md:32 (step 4) · The internal `upgrade` signature leaves out `busyTimeoutMs`, which the current `migrate` (src/store/db.ts:117-128) needs for `enableWal`. `migrateModules` is named in step 4 but appears nowhere in the signatures list. `rebuildAll`'s `results` Map has an unstated key (relative path or `Repo.id`).
- F-13 · Nit · plan.md:31 (step 3) · The step says `tests/helpers/open-db-worker.ts` "passes no option". In fact it passes `migrations` (tests/helpers/open-db-worker.ts:17). The intended meaning, that it passes no `moduleSchemas`, holds, but the wording is false.
- F-14 · Nit · plan.md:36 (step 5) and plan.md:14 · `runGit(store, repo, ["status", "--porcelain"], …)` passes a repository where the signature takes `repoPath: string | null`. Also, `logError` (src/util/log.ts:30) clips the whole message to 300 characters, so the repository path that step 5 expects in the log line has to be put in the error message. The plan does not say where in the message the path goes.
- F-15 · Nit · plan.md:22 (step 0) · The new variables are "added to the variables dropped", but tests/preload.ts has two drop sites: `PATH_OVERRIDES`, commented as paths, and the standalone behaviour delete of `WIZARDINGCODE_MODULES`. The parenthetical points to the second, but the target is not named.
- F-16 · Nit · plan.md:63 (step 20) · "doctor counts the files and warns past 5,000" is stated inside the test list, but no test case for it exists. The detail text of that warning is also not given.
