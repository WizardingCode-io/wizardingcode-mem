The withdrawn module recorded a different shape: `module_migrations(module, version)` (`docs/superpowers/plans/2026-10-12-knowledge.md:31`, `docs/superpowers/specs/2026-10-12-knowledge-design.md:21`). - R-2 · .crew/work/2026-11-08-003-knowledge-store-entries-as-markdown-with/spec.md:196 and :202 · `knowledge_repos` has `UNIQUE (scope, project_id)` with `project_id` 0 for workspace and shared. `rebuildAll` indexes an unmapped project folder "with `project_id` 0 under scope `project`". A second orphan folder then violates the constraint, and one orphan aborts the rebuild transaction. Either the orphan is not indexed (it is reported only), or the key includes the path, or the orphan uses a distinct sentinel. Pick one and add a test with two orphan folders to AC-7 and plan task 16.
- R-3 · .crew/work/2026-11-08-003-knowledge-store-entries-as-markdown-with/spec.md:198 and :202 · `knowledge_proposals` has `PRIMARY KEY (repo_id, id)`. The rule that rewrites a duplicate to `dup:<slug>` names entries only. The same proposal id can sit in both `proposals/open/` and `proposals/decided/` (a hand copy, or an interrupted `git mv`). It can also repeat across files, or be missing or malformed. Either case makes the single-transaction rebuild fail on the PK. The spec must say how duplicate or invalid proposal ids are indexed (for example `dup:<file name>` with `problem`) and add the case to AC-7.
