## Findings
- F-1 · Major · Design, Freshness (D-16), and Risks and rollback, "A stale index on the hook path" · The spec says a hand edit reaches the hooks after a drain rebuild, and that a tool call or `knowledge rebuild` brings it into the index. The code says otherwise for two cases. First, `fingerprintOf` (repo.ts:856-876) is three folder listings plus the folders' mtimes, and its own comment says "an edit in place changes neither it nor HEAD". So an uncommitted in-place edit never sets a stale mark. `ensureFresh` (index-store.ts:623-631) uses the same comparison, so a tool call misses it as well, and the hooks keep showing the old text with no time bound. Second, when a rebuild does see an uncommitted change, `rebuildRepo` (index-store.ts:493-503) turns the entry into a draft with the problem "changed outside". Such entries are not searchable, so a hand-edited pinned entry vanishes from session start, the prompt and `knowledge_search` until a person adopts it. A reader would expect a hand edit to show up after the next drain. Neither outcome is named, and neither has a `doctor` warning.
- F-2 · Major · Design, What the agent is shown, Prompt (the floor and the probe), and Risks, "The lexical floor's known leak" · The precision claim (at most 1 of 28 unrelated prompts injects) was measured by ADR 0020 on an 18-entry probe, against a rule that also read tags. This part reads different fields (no tags or area; context and subject added), writes the probe fresh with 18 entries again, and runs on corpora the spec itself sizes at three repositories of 2,000 entries. Rule 2 (any three distinct non-generic words anywhere, bodies included) gets more likely to fire as the corpus and the bodies grow. bm25 picks the best 10 candidates from 6,000 long entries, so most prompts will find some entry that passes. The perf corpus measures speed only. Nothing measures false injections at the scale the design targets, so the "stays; the probe pins it" mitigation does not cover the real risk: unrelated entries in front of every prompt.
- F-3 · Major · Design, Migration 7 (Speed), and Risks, "A rebuild holds the write lock" · The rebuild's write transaction has a target of "under 100 ms, the shortest hook busy timeout", which leaves no margin. A hook that waits behind a 99 ms transaction still has to take the lock for `touchSession`. The figure comes from the gate machine (ADR 0020's proofs ran on an M4 Max), and slower user machines will pass 100 ms. The drain runs up to three rebuilds back to back, and tools call `ensureFresh` from the MCP server whenever they like. When the wait runs out, the spec says the hook prints nothing, memory's brief included. The target needs headroom below the timeout, or the spec must say that losing memory's output is the expected cost.
- F-4 · Major · Goals, bullet 5, against Design, The judgements, Neighbours · Goals says "The judgement covers every visible entry and open proposal." The design compares the draft only with the FTS best 8 entries, found with an unstemmed `unicode61` lexical OR query over the draft's tokens. A duplicate or contradiction worded differently from the entry is never sent to TypeSafe, so it is filed as new. A reader of the Goals would believe a configured TypeSafe catches semantic duplicates against the whole store. It does not, and no risk names this lexical recall ceiling.
- F-5 · Major · Cost and time · The effort is "four to six hours" for 22 tasks across eight phases: a composer rule change, a migration with an index-writer FTS table, two contributions, three tools with an agent-id handshake, a judge entry point, a drain refresh, a shared rate counter, status/doctor/compact, an OpenCode plugin regeneration, a perf corpus and an ADR. The stated basis contradicts the estimate. The comparable ADR 0020 module took "one day of sessions", and this part adds work ADR 0020 did not have (migration, judge, freshness, rate counter, redaction), so dropping its promotion pass does not make up the difference. A planner would under-budget by the gap. The midway checks catch the overrun but do not fix the estimate.
- F-6 · Major · Open Questions, D-9, and Decisions D-9 · The spec states its own rule: a default wider than the brief is the person's to take. It then records D-9 from "a general go-ahead for the whole mission, not a sentence about D-9" and writes the whole design, AC-3 and the first risk for that answer. Builders will treat as settled a behaviour that changes what every existing project sees at every session start, while the decision is unconfirmed by the spec's own account. Either the build waits for the confirmation, or the change list for the other answer must be kept as a live branch of the plan, not a footnote.
- F-7 · Major · Non-Functional Requirements, Security, and Design, What the agent is shown (rule 3, inert text) · The pinned entries of the shared repository go into every project's session start, and the shared repository is the one parts 4 to 6 will sync from teammates and a team server. The only defence named is `inert`, which neutralises `wizardingcode-…` tags, plus the "information, not instructions" intro. Nothing names the prompt-injection risk: text that someone other than the user wrote reaches every agent at every start, with no review between the sync and the injection. Since `visibleRepos` is designed so part 4 changes "one place", the risk belongs here, or the spec must say explicitly that part 4 inherits it.
- F-8 · Nit · Design, Session start · The count line `- +<n> pinned entries not shown; knowledge_search lists them` is not reserved inside the 840-character share. When the entry lines fill the share, the spec does not say whether the count line drops an entry or is itself left out, and AC-3 asserts it appears.
- F-9 · Nit · Design, What the agent is shown, rule 4, and The module and the composer (F5′) · Knowledge records its `knowledge_shown` rows in its own transaction before memory runs and before the hook prints. If the composer then discards the contribution (an overrun) or the output never reaches the host, those entries are marked shown for the context but were never seen. The spec does not say whether this is accepted.
- F-10 · Nit · Design, Rate and cost · The hourly counter is a fixed window (a window start plus a count), so an agent can make up to 40 calls within a minute across a window boundary. The `tool` bridge always proposes as `opencode`, so every OpenCode session on the machine shares one 20-per-hour budget. Neither is stated.
- F-11 · Nit · Acceptance criteria · AC-8 and AC-14 are kept only as "superseded" pointers. They add nothing for a fresh reader and make the list harder to cite.
