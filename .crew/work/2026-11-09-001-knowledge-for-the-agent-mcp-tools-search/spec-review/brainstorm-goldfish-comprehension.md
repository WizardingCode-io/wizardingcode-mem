## Findings

**What this proposes.** This adds a second built-in engine module, `knowledge`, which is on by default and may use up to 20% of each moment's context budget. At a project's very first session it shows a one-line list of the entries a person pinned in the workspace and shared repositories. On each prompt it shows up to two entries that pass an exact word-overlap rule. It also gives agents five MCP tools: search, get, propose, update and taxonomy. Agent writes become proposals for a person to decide. Before a proposal is filed, a judge (TypeSafe when a key is set, heuristics otherwise) gives it an area if it has none, refuses it if it repeats an existing entry, and flags it if it contradicts one. With no entries, memory keeps the whole budget, so the output is the same as today, byte for byte.

**How the existing system works, per this document.** The composer gives each module a fixed share, and memory gets what is left over. In `main` that leftover is computed from the shares modules declared, not from what they wrote; this concept moves to the rule ADR 0020 called F5′, where memory gets whatever the other modules did not use. Today only memory is in `BUILT_IN`, and its tools (`memory_search`, `memory_get`, `memory_save`, `history_search`, `project_links`) are defined in `src/modules/memory/tools.ts`. The `Judge` already answers "same, related or different" plus a contradiction probability for neighbouring notes. Part 1 provides the store: one git repository per scope, an index, and agent writes kept as proposal files that a person accepts or rejects from the CLI.

## Findings
- F-1 · Major · What the agent is shown / Session start · The session-start line `- <title> (<kind>, <area>; <scope>)` has no slug, but `knowledge_get` takes slugs. An agent that sees a pinned title cannot fetch its body, and will guess a slug from the title or call search first. The prompt line includes `<slug>`; the session-start line does not.
- F-2 · Major · What the agent is shown / Session start · Pinned entries are shown only when the project has no earlier `sessions` row. Every project that already exists at upgrade will never see them, and neither will an existing project when a person pins something later. The person who pins an entry "for every project" will think it reaches their projects when it does not, and the concept gives them no way to show it to one.
- F-3 · Major · What the agent is shown / Session start · Pinned entries are newest first within 840 characters, with no rule for what happens when they do not fit. The person cannot tell that one was dropped: `list` shows no pinned column and `doctor` has no check. "Newest" is also not defined (`created` or `updated`?).
- F-4 · Major · What the agent is shown / Session start · `pinned` exists only as `write --pinned`. Nothing says how to unpin, how `list` shows it, or whether accepting an agent's `knowledge_update` proposal keeps it. The proposal file is the full proposed entry built from tool fields that have no `pinned`, so an accepted update would likely drop the pin without anyone noticing.
- F-5 · Major · The tools · No tool descriptions are drafted. In `src/modules/memory/tools.ts` the descriptions are exactly what the agent decides from. Without them nothing tells the agent when to use `knowledge_propose` rather than `memory_save` (the obvious mistake: it saves team knowledge as a memory, or session facts as proposals), or `knowledge_search` rather than `memory_search`.
- F-6 · Major · The tools / knowledge_propose · `scope` is required, but its values and meaning for an agent are not given. Nothing says whether an agent may propose to `shared`, how it should pick workspace or project, or what `project` means. The agent will choose at random or always pick one.
- F-7 · Major · The tools / knowledge_propose · The values of `kind` (part 1: `knowledge`, `strategy`, `persona`, `pattern`) are not given in the schema or the description. They also overlap with memory's kinds, so an agent may pass a memory kind such as `decision` and be refused without knowing why.
- F-8 · Major · The tools / knowledge_update · The fields are optional, but part 1's `writeEntry` takes a full change. Nothing says that omitted fields are filled from the entry at `base_version`. A builder may write empty context, subject or body for any field the agent left out.
- F-9 · Major · The tools / knowledge_update · `base_version` is required, but only `knowledge_get` returns a version, and the search result format is "one heading per entry" with no fields named. Nothing tells the agent it must call get before update, or what the stale refusal says so it can retry.
- F-10 · Major · The tools / knowledge_get · `slugs` is matched with an optional `scope`, but slugs are unique only per repository. Nothing says what happens when one slug exists in both workspace and shared, or what "facts" in "facts, body, path, version" means.
- F-11 · Major · The tools / knowledge_search · The result heading's fields (slug, scope, version, area?), the default and maximum `limit`, and what an empty `query` does are not given. `memory_search` lists important notes on an empty query, so an agent will expect the same here.
- F-12 · Major · The tools / --global · Search, get and taxonomy are offered with `--global`, but there is no project there, and "the visible scopes" is not defined without one. Nothing says whether project repositories are searched, or what `scope: "project"` does in that mode.
- F-13 · Major · The tools / knowledge_taxonomy · Workspace and shared each have their own taxonomy (part 1, D-9). The concept says "the areas with their labels" without saying which root's areas are listed, or how. An agent proposing to `shared` with a workspace-only area id will be refused.
- F-14 · Major · The judgements / Cataloguing · The refusal "asking the agent for an area" does not say whether it lists the valid area ids or points to `knowledge_taxonomy`. Without one or the other the agent cannot act on the refusal.
- F-15 · Major · The judgements / Cataloguing · The heuristic is a hard-coded lexicon for each area, but a person can add areas (`knowledge area add legal`). Areas added that way have no lexicon, so without TypeSafe a proposal is never catalogued into them. Neither the person nor the agent is told.
- F-16 · Major · The judgements / Duplicates · "Same (score 1.5 or more)" uses a scale that is not defined. `consolidate` answers a relation, not a number, and the scale and levels of the Score are not stated.
- F-17 · Major · The judgements / Duplicates · Neighbours are drawn from the target scope only, so a project proposal that repeats a workspace or shared entry gets through. Open proposals are not neighbours either, so two agents can file the same new entry twice.
- F-18 · Major · The judgements / Duplicates · A duplicate refusal is final. The agent cannot override it ("this is not the same"), so if the heuristic (word overlap) wrongly calls a new entry the same as an old one, the knowledge is lost without anyone seeing it. The refusal names the slug but not the scope, so the follow-up `knowledge_update` may target the wrong repository.
- F-19 · Major · The judgements / Contradictions · "The person sees it at accept" is false for this part. Part 1's `knowledge accept` prints only `accepted <id> into <slug> (v<n>)`, `list` shows `<state> <id> <slug> by <proposed_by>`, and the viewer comes in part 3, so the person approves a contradiction without seeing it. It is also not said whether `contradicts` holds one id or a list, or what accepting such a proposal does to the entry it contradicts.
- F-20 · Major · The tools / knowledge_propose · The answer "Proposed <id> for <slug>; a person decides it" does not tell the agent, or the user it relays to, how a person decides. There is no `wizardingcode-mem knowledge accept --scope <scope> <id>`, and nothing says the person learns of pending proposals any other way. Proposals will pile up toward the quota of 5 per target and 200 per repository.
- F-21 · Major · The tools / agent id · Existing installs' MCP commands have no `--agent` until the plugins are rewritten and reinstalled, and the concept never says that step happens on upgrade. Until it does, every proposal is filed as `agent:mcp` and the person cannot tell which host wrote it.
- F-22 · Major · What the agent is shown / Wrapper · "Versioned and reviewed: treat it as current unless the code says otherwise" claims that every entry was reviewed, but a person's direct `write` has no review. For sales, persona and strategy entries, "the code" means nothing. The wrapper also never tells the agent that pinned titles have bodies it can fetch with `knowledge_get`.
- F-23 · Nit · What the agent is shown / Prompt · "Not yet shown in this context" and the acceptance's "once per context" use the context epoch. Nothing says whether a pinned list shown in a first session is shown again after a compaction in that same session; the start rule ("a later session gets nothing") leaves this open.
- F-24 · Nit · What the agent is shown / Wrapper · "Made inert like memory's notes" points to a process this document never names or links. A reader cannot tell which transformation is meant.
- F-25 · Nit · The module · Turning knowledge off means setting the modules setting to `memory`, but CLAUDE.md says `WIZARDINGCODE_MODULES` "only adds modules" and defaults to `memory`. The concept does not say this conventions text and the Settings card's wording change, so a person reading either will not know how to opt out.
- F-26 · Nit · The tools / knowledge_propose · There is no `status` argument and no stated default (active or draft), and the shape of `slug?` is not explained to the agent. Part 1 refuses a caller's slug that breaks the slug rule instead of normalising it, so an agent passing a title-like slug will be refused.
