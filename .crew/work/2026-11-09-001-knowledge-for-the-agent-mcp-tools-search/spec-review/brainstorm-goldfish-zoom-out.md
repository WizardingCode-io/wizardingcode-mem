## Findings
- F-1 · Major · Session start, "first session of a project" · The pinned entries reach almost no one. Every project the store already knows has a `sessions` row, and `ensureSession` (history import) creates rows for past sessions too. So after the upgrade, pinned knowledge never shows in any existing project, nor in a project whose history was imported. A new project sees it once, in one session, and a second agent such as codex in that project never sees it. Simpler, and closer to what "pinned" means: show pinned entries at every session start, once per context, within the 840 characters. Drop the first-session rule entirely.
- F-2 · Major · What exists today / Session start · The concept misses a mechanism the repository already has. The author's rules (`user_memories`, ADR 0018) are already shown at every session start in every project, within their own share of the brief (`src/retrieve/brief.ts` lines 9 and 121-129). On prompts they compete as candidates in every project (`extraCandidates` in `src/retrieve/prompt.ts`). The concept does not say how pinned knowledge relates to them. Part 1's spec explicitly leaves part 2 the question "whether the author's user rules become knowledge", and the concept never answers it. Without an answer, the same standing rule can reach the agent twice, as a memory note and as a knowledge entry, with nothing removing the duplicate across modules.
- F-3 · Blocker · The judgements, "Judge.consolidate, the existing interface" · The claim that the existing interface can be used as it is, is false. `ConsolidateInput` requires `draft.kind: MemoryKind` and `files`, and neighbours with numeric `id`. Knowledge kinds are `strategy`, `persona` and so on, and entry ids are UUIDs. The TypeSafe questions are worded about `new_memory`. The heuristic needs file overlap to call a pair `same`. So the call cannot type-check as written, and memory's question wording would judge knowledge. Either generalise the input type (an index-keyed neighbour list and a kind-free draft) or say that a knowledge-specific question set is needed. Then reuse `DUPLICATE` and `SUPERSEDE` from `src/distill/policy.ts` instead of inventing new thresholds.
- F-4 · Major · The judgements, Cataloguing (`Judge.catalogue?` and a per-area lexicon) · This is a second model plus a hand-written lexicon for nine business areas (sales, video, finance…) to choose a label that the calling agent, itself a language model, can choose. Simpler, with no code: build `knowledge_propose`'s `area` as a required `z.enum` of the root taxonomy's ids when the tools are listed. Refuse an id that has gone stale with the current list. That deletes the new Judge method, its question, the lexicon and the 0.6 threshold. A per-area word list in code is also a speculative maintenance surface: it goes stale the first time a person runs `knowledge area add`.
- F-5 · Major · The judgements, Relevance (`Judge.relevant?`) and `knowledge_search` · A network rerank, one Noul for each of 20 candidates, is built for a corpus nobody has measured. Part 1 has not shipped, the team has no entries yet, and its Obsidian notes are tens of entries, not thousands. bm25 over a handful of rows needs no reranker. If ranking by meaning is wanted, the repository already has a local embedding path (`semanticCandidates` and `fuseRanks` in `src/retrieve/semantic.ts`) that `memory_search` uses with no key and no network, yet the concept defers exactly that. Defer the rerank until a measured search misses.
- F-6 · Major · The tools (five tools) · Every tool description is sent to the model in every session (`src/mcp/server.ts`), so each tool has a standing cost. `knowledge_update` is `knowledge_propose` with a `slug` and a `base_version`, because part 1's `writeEntry` already takes an optional `baseVersion`. `knowledge_taxonomy` becomes unnecessary once the area ids sit in the propose schema (F-4), and search counts by area can answer the rest. Three tools (search, get, propose) cover the same need.
- F-7 · Major · What the agent is shown / Prompt (index freshness on the hook path) · The concept never says whether the hooks call part 1's `ensureFresh`. Part 1 says later parts call it before a read. On a mismatch it runs `rebuildRepo`, which spawns `git status`, and the brief forbids a process in a hook. Across workspace, shared and project, a fresh read is also nine directory listings on every prompt. ADR 0020's K5 already solved this: compare only on the hook, re-index inline under a small cap, otherwise let the drain refresh. Without that, a competent builder either spawns git in a hook or serves an index that stays stale indefinitely.
- F-8 · Major · Prompt, "the exact lexical floor of ADR 0020" · This would be a second lexical evidence rule beside memory's `hasEvidence` (`src/retrieve/prompt.ts` lines 339-368). Both build on `buildQuery`, `isGeneric`, `stem` and `searchTokens`, and both use identifier, telling-word and generic-word tiers. The two would drift apart. Extract one evidence function parameterised by the text fields, or say why knowledge needs a stricter floor. ADR 0020's probe is the evidence for that, and it should be carried over as a test fixture, not re-derived.
- F-9 · Major · The module / budget (missing) · A store change is missing. Part 1's migration 6 creates no full-text index and no `knowledge_shown` table, yet the concept uses both (FTS5 bm25 with weights title 4, area and context 2, body 1, and "recorded in knowledge_shown"). The concept does not name the module migration 7 that adds them, nor how the full-text index is kept in step with part 1's `rebuildRepo` and its one-row upserts. ADR 0020's note on the index (a self-contained FTS5 table, because there is no stable rowid with a text id) applies here too, since part 1's entries have a composite key on a text id.
- F-10 · Nit · The module, F5′ · F5′ is necessary for an on-by-default module that keeps the snapshots. But it is restated in prose as part of "the module", when it is an amendment to ADR 0019's F5 with its own test: the total never exceeds the budget, and the output is still joined in engine order. It belongs in its own ruling, not inside the module sketch.
- F-11 · Nit · The tools, `wizardingcode-mem mcp --agent <id>` · The server already learns which host started it. The host name arrives in the MCP `initialize` request (`clientInfo.name`), so a new flag across every host's configuration and the OpenCode bridge may not be needed. Check whether the SDK exposes it before changing `scripts/plugins.ts` for every host. Keep the flag only if `clientInfo` cannot be trusted to give a stable `AgentId`.
- F-12 · Major · Whole concept (the strongest case against it) · This part is designed on a store spec that the brief and the concept themselves say is still waiting for the person's approval. Its engine contract also reverses the standing note in ADR 0019 that knowledge and personas are a separate product, without saying why the reversal holds now. Everything on the agent side here (injection, five tools, three judgements) multiplies the cost of any change the person makes to part 1. The smallest answer to the brief's acceptance ("a new project starts with the team's knowledge, and agents have knowledge as well as memory") is read-only: pinned entries at session start, `knowledge_search`/`knowledge_get`, and `knowledge_propose` with an agent-chosen area. Duplicate, contradiction and relevance judgements wait until real entries and real proposals exist to measure them on.
