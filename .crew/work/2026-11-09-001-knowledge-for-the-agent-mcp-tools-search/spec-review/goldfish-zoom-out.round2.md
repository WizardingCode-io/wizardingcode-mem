## Findings
- F-1 · Major · The judgements (D-14); plan task 11-12 · The heuristic `relate` described here is the same thing as the existing heuristic `consolidate` in `src/judge/heuristic.ts:218-242`: Jaccard over title plus body, `same` at 0.6, `related` at 0.3, `contradicts` 0.8 on a `SUPERSEDES` phrase with overlap in [0.5, 0.9), else 0.1. Once `files` is empty, the only difference is that `files` term, and `src/links/rules.ts:425-437` already calls `heuristicJudge.consolidate` with `files: []` to compare text that is not a memory. The Score and Noul pair for TypeSafe in `src/judge/questions.ts:219-268` also matches the spec's `relate` questions except for the nouns ("new_memory", "current approach"). So "Reusing `Judge.consolidate` as it is. Rejected: memory-shaped input and questions" is half true: only the question wording is memory-shaped. As written, a builder adds a third optional judge method in four files (types, questions, typesafe, heuristic, plus fallback), copies the heuristic and its thresholds, and writes tests that pin those thresholds a second time. The two copies will drift. A builder would also build the `judged_by: none` path (AC-10), which exists only because `relate` is optional. Simpler: call `consolidate` with `files: []` and an adapted draft, and pass the noun or wording to `consolidateState`/`consolidateQuestions` as a parameter. If the name `relate` must stay, it can delegate to `consolidate`.
- F-2 · Major · Prompt (the `MATCH` string) and The tools (`knowledge_search`'s match string); AC-17 · `src/util/words.ts` already holds both halves of this match string. `anyOf` quotes each term and doubles `"`, so no term is read as syntax. `inProject`/`inProjects` confine an FTS5 query to an id column inside the `MATCH`. The spec describes the construction again ("each double-quoted, joined by OR, no operator passed through"; `repo_id:("1" OR "2") AND (...)`) and never names these helpers. The security return in AC-17 depends on getting this quoting right, and a builder who follows the text writes a second quoting routine where the first one is already tested. Reuse `anyOf`. Generalise `inProjects` for its column list and id column (today they are hard-coded as `{title body terms}` and `project_id`) rather than add a second confinement builder.
- F-3 · Major · Migration 7 (the `head`/`fingerprint` reset); NFR Rollout; AC-2 "a store that ran 6 only"; plan task 3 · The spec says parts 1 to 3 ship in one release (rollback target 0.6.0), and part 1 is still waiting for approval. No user's store will ever be at knowledge version 6 with files a person pinned by hand, because migrations 6 and 7 apply at the same first open. Even so, the design builds machinery for that state: a forced re-parse of every repository, a rollout window in which session start shows no pins until the first drain (with distillation off, until a tool call), a stale mark per repository on the first hooks, and a test for a store at 6 alone. A builder would ship all of that for a state only development checkouts can reach. Simpler: fold the new columns, the FTS table and its triggers, and `knowledge_shown` into the unreleased migration 6. Or, if 7 stays separate, drop the reset and the rollout clause and say why it is safe.
- F-4 · Nit · Prompt (the evidence primitives); plan Signatures, `src/retrieve/evidence.ts` · `isGeneric`, `STOPWORDS`, `stem` and `searchTokens` already live in `src/util/words.ts`, which `prompt.ts` and `links/rules.ts` share. `tellingOf` is `filter(w => !isGeneric(w))`, and the identifier test and the stem match are about four lines each inside `hasEvidence` (`src/retrieve/prompt.ts:345-351`). A new file in `src/retrieve` plus a refactor of memory's prompt path to share about eight lines is more than this needs. The two helpers can go into `util/words.ts` beside `isGeneric`. Separately, the proposed `namesIn` clashes with an existing export of the same name and a different meaning in `src/modules/knowledge/repo.ts:119` (it lists a folder's names), inside the module that will import both.
- F-5 · Nit · Migration 7 (`knowledge_shown`), The entry format (`KNOWN_KEYS`), plan Scope (`views.ts`) · Three things are built for later parts with no reader in this one. `knowledge_shown.version` and `hash` are written, but nothing in this part reads them: an entry already shown in a context is suppressed whatever its version. `KNOWN_KEYS`' `part: 1 | 2` field is metadata no code consults. `src/modules/knowledge/views.ts` is created empty "part 3 fills it", where `views: []` inline in `index.ts` would do.
- F-6 · Nit · Design (Migration 7, Prompt, Status/doctor/compact, The tools) · The spec's design sections go down to plan-level detail: the literal `ALTER TABLE` and `DELETE FROM knowledge_shown ...` statements, the bm25 weight vector, the exact `MATCH` string, and the client-name to agent-id mapping table entry by entry. The plan's Signatures repeat most of it as constants. The spec should state the properties (the search is confined inside the `MATCH`, the title is weighted highest, orphans are pruned in the same transaction) and leave the statements and constants to the plan.
- F-7 · Nit · plan Signatures, `src/mcp/agent-id.ts` `AGENT_ID_PATTERN (part 1's)` · Part 1 already exports this pattern as `AGENT_ID` in `src/modules/knowledge/entry.ts:12`. Say that `agent-id.ts` imports it, so a builder does not declare a second regex under a new name.
