## Findings
- F-1 · Blocker · Phase B task 3/4 (migration 7) · `tests/unit/module-migrations.test.ts` fails once version 7 exists, and the plan does not list it anywhere. It asserts that `KNOWLEDGE_MIGRATIONS` equals `[[6, "knowledge_store"]]` (l.75), that `moduleVersion(db,"knowledge")` is 6 (l.90), that the fresh tables do not contain `knowledge_fts` (l.89), the exact column lists of `knowledge_entries` and `knowledge_proposals` (l.255, l.275), and that a version 7 inserted by hand reads as `too-new` (l.104–112). It also expects `[["knowledge", 6]]` from the concurrent-open test (l.368). The gate's `bun run test` goes red, and the builder has to decide on their own how these pinned facts change.
- F-2 · Blocker · Phase C task 8 / Phase E task 16 (default `memory,knowledge`, the three new tools) · Two tests pin the memory-only tool lists under the default setting, and the plan does not list either. `tests/integration/mcp.test.ts` l.385–436 spawns `mcp` with no `WIZARDINGCODE_MODULES` and checks the exact sorted list of five tool names. `tests/unit/opencode-plugin.test.ts` l.185–191 checks `Object.keys(hooks.tool)` as the same five, and l.226–231 checks the generated plugin. Both go red at the gate.
- F-3 · Major · Phase C task 8 ("Modify the four tests that used `knowledge` as an unknown id to use `nonesuch`") · `tests/unit/modules-setting.test.ts` needs more than that rename. It also pins `BUILT_IN` as `["memory"]` (l.19), `enabledModules(undefined)` as `["memory"]` (l.37), and the blank values giving `["memory"]` (l.32). A builder who does only what the task says leaves the file red. The doc comment of `enabledModules` in `src/engine/modules.ts` (l.33: "Unset or blank means the default, memory alone") also becomes false, and the plan names only `BUILT_IN` there.
- F-4 · Major · Phase E tasks 16 and 17 (`GLOBAL_INSTRUCTIONS`) · These two tasks contradict each other against the code. `GLOBAL_INSTRUCTIONS` in `src/mcp/run.ts` is one constant, and `src/mcp/server.ts` l.36 passes it unchanged whatever modules are on. Task 16 makes that constant name the knowledge tools. Task 17 requires the `--global` instructions with the setting `memory` to be the old text byte for byte. Both can only hold if the instructions are built from the enabled modules, which means a change to `server.ts` (and probably a new hook on the module). The plan does not specify that change; task 14 changes `server.ts` for the agent id only.
- F-5 · Major · Phase C task 8, `contribute` / `visibleRepos(store, …)` · The hook path has no knowledge store and no data directory. `MomentInput` (`src/engine/module.ts`) carries `db` only. The hook command opens the database at `storeDir` (`src/cli/commands/hook.ts` l.143), but repositories sit under `dataDir`: `knowledgeRoot(dataDir)`, `repoPath(dataDir, relative)`, and the split in `resolvePaths` that every CLI uses. Several pieces need either a `KnowledgeStore` or an absolute repository path: `visibleRepos(store, …)`, the head/fingerprint comparison (`headOf`/`fingerprintOf`), and the area label read from the taxonomy. The plan does not say where `contribute` gets `dataDir`, `env` and `settings` (`resolvePaths()`? `process.env`?). The spec writes `visibleRepos(db, projectId)` while the plan writes `visibleRepos(store, projectId)`. The builder will make a choice that decides whether tests isolated through "the test's own env" are actually isolated.
- F-6 · Major · Phase C task 7 / spec "one count, cached for the process" · The plan does not say what the empty-`knowledge_repos` cache is keyed on or how it is reset. Task 7 runs several worlds in one test process, starting with "no repository". A cache with no key holds that zero and silences the module in every later world of the same file.
- F-7 · Major · Phase B task 3/4 (the FTS triggers) · `upsertEntry` (`src/modules/knowledge/index-store.ts` l.59) writes with `INSERT OR REPLACE`, and `src/store/db.ts` never enables `recursive_triggers`. In SQLite, a row that REPLACE deletes does not fire the `AFTER DELETE` trigger unless recursive triggers are on. A conflict on `(repo_id, id)` with a different slug therefore leaves the old FTS row in place while `AFTER INSERT` adds a new one, giving duplicate or orphan FTS rows. The plan's trigger design and its test cases (insert, update, delete, draft, problem) do not cover this path. The builder would ship triggers that drift from the table, and only `doctor`'s count check (Phase F) would ever notice.
- F-8 · Major · Phase D task 12 / Signatures `relateState(input)` · AC-17 requires `relateState` to redact "with the store's `env`". The plan's `RelateInput` is `{ draft: {title, body}, neighbours: […] }` with plain strings and no env, and `relateState(input)` takes nothing else. `redact` takes `{ env }` and otherwise falls back to `process.env` (`src/core/redact.ts` l.13–16). The existing pattern redacts upstream and types the field `Redacted` (`ConsolidateInput`, `src/judge/types.ts` l.48). The plan does not say how the env reaches the redaction, nor whether `body` becomes `Redacted`.
- F-9 · Major · Signatures `knowledgeStatus(db, now)` · `on: boolean` reflects the modules setting, which is read through `loadSettings(env, dataDir)` and is not in the database. The planned signature cannot compute it, yet the test "with the setting `memory` gives `on: false`" depends on it. `StatusReport` and `formatStatus` also need a new field, and the plan does not name it.
- F-10 · Major · Phase F task 18/19 (`compact` "counts them under `--dry-run`") · `CompactReport` (`src/store/compact.ts` l.18) has no field for the pruned shown rows. Its output is printed by `src/cli/commands/compact.ts` l.25 and returned by `src/ui/server.ts` l.421, and neither file is in the scope. The plan does not specify the count's field name, its printed text, or what the dry-run count means for sessions that are about to go but have not been deleted yet. A builder would add a count nobody can see.
- F-11 · Major · Phase C task 9/10 (`refreshKnowledgeSafely`) · The plan says "stale repositories rebuilt" and the spec says `ensureFresh`. Neither matches what the test cases need:
  - `ensureFresh` (`index-store.ts` l.623) takes no repository lease, whereas `rebuildAll` wraps each rebuild in `withRepoLeases` (l.606). A drain's rebuild without a lease can race a person's `knowledge write` in another process.
  - The test "a repository whose folder is gone clears its mark and deletes its rows" needs `rebuildAll`'s gone-folder branch (l.608–618), which `ensureFresh` does not have.

  The plan has to name the call, the lease, and how a Repo is obtained from a stale mark keyed by relative path.
- F-12 · Major · Phase E task 15/16 (`base_hash`) · The spec's `knowledge_propose` takes `base_hash?` ("must equal the entry's current hash"). Part 1's `EntryChange` (`src/modules/knowledge/types.ts` l.109) has no `baseHash`, and `propose` (`store.ts` l.489) fills `baseHash` from the current file. The plan has no signature, step or test case for `base_hash`, so the argument is either dropped or checked somewhere invented.
- F-13 · Major · Phase E task 15 (refusal answers) · Part 1's `propose` throws `KnowledgeError("missing", …)` for a slug plus a base version on an entry that does not exist (`store.ts` l.459–461), and `missing` is one of `KnowledgeErrorCode` (`errors.ts` l.5). The plan and spec list the refusal codes without `missing`. The plan also does not say what the tool answers for it, or for a non-`KnowledgeError` throw (today `server.ts` turns that into an `isError` answer).
- F-14 · Major · Phase E task 16 (`src/install/opencode-plugin.ts`, "the tool list") · The OpenCode plugin is static generated source; each tool's `args` are literal `toolApi.schema` calls (l.86–129). `knowledge_propose`'s `area` is an enum built from the taxonomies at listing time and cannot be written into that file. The plan does not state the three tools' OpenCode args (area as a plain string? which enums for `repo`, `kind`?) or their descriptions there.
- F-15 · Major · Signatures `sharedStems(queryWords, text): Set<string>` ("moved … without a change of behaviour") · Memory's rule (`src/retrieve/prompt.ts` l.351–359) weighs a list of matched query words: `matched.length - telling.length`, with each telling word counted. Two distinct query words with the same stem ("query", "queries") count twice. If `sharedStems` returns a set of stems, as its name suggests, they count once and memory's weights change. The plan should say the set holds the query's words, not their stems. Similarly, `tellingOf` adds a `STOPWORDS` filter that memory's code does not apply (harmless only because `buildQuery` already removes stopwords), and `namesIn`/`sharedStems`/`tellingOf` are inline logic in `hasEvidence`, not functions that exist today.
- F-16 · Major · Phase E (`judgeVersion`) · Under `makeJudge` with a key, the judge is `withFallback`, whose `version` is `"2+2"` and whose answering judge is known only from the verdict's `source` (`src/judge/fallback.ts` l.44–45). The plan does not say whether `judge_version` records `judge.version` or `judge.versions[source]`, or what to record with `judged_by: none`.
- F-17 · Major · Scope · The Create/Modify list misses files that the tasks change or that must change: `tests/unit/compose.test.ts` (task 1, "Modify"), `tests/unit/doctor-knowledge.test.ts` and `tests/integration/compact.test.ts` (task 18, "extend"), `tests/unit/module-migrations.test.ts` (F-1), `tests/integration/mcp.test.ts` and `tests/unit/opencode-plugin.test.ts` (F-2), and `src/cli/commands/compact.ts` / `src/ui/server.ts` (F-10). In addition, Phase F task 19 does not modify `src/modules/knowledge/index-store.ts`, although task 18 tests `rebuildAll` deleting shown rows (`rebuildAll` lives there, l.608–618).
- F-18 · Nit · Phase E task 14 · `runMcpServer`'s options (`src/mcp/server.ts` l.16–18) have no agent flag. The plan says `server.ts` uses `resolveAgentId(flag, …)` but does not name the new option. `server.server.getClientVersion()` exists, but the SDK marks it `@deprecated` (`node_modules/@modelcontextprotocol/server/dist/mcp-DIH4cS6P.mjs` l.1389).
- F-19 · Nit · Signatures `src/mcp/agent-id.ts: AGENT_ID_PATTERN (part 1's)` · Part 1 exports this pattern as `AGENT_ID` (`src/modules/knowledge/entry.ts` l.12). No `AGENT_ID_PATTERN` exists.
- F-20 · Nit · Phase B task 4 · The plan names "the new columns in the upserts" but not the reads. `listEntries` (`index-store.ts` l.209) and `listProposals` (l.243) select explicit columns and build `KnowledgeEntry`/`KnowledgeProposal`, so `pinned` (stored as an INTEGER, not a boolean), `contradicts` (JSON), `on_behalf_of`, `judged_by` and `judge_version` need mapping there too.

- F-22 · Nit · Phase E · There is no default for a `ToolCall` without `agentId` reaching `knowledge_propose`.
