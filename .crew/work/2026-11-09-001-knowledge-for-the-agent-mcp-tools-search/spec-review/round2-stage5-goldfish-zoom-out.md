## Findings
- F-1 · Major · spec "Freshness (D-16)", plan `contribute` step 5, `staleRepos`, `markStale`, `MomentInput.dataDir`, `refreshStale` steps 1-6 · On every prompt and session start, the hook compares head and fingerprint for each visible repository: three `readdir` calls over folders of up to 2,000 entries plus `stat` calls, times three repositories, inside the 80 ms prompt budget. It does this only to write a `meta` mark that the drain later reads. A builder would put that disk work on the hot path, add `MomentInput.dataDir`, `HookDeps.dataDir` and the `hook.ts` change (staleness is the only reason the hook needs `dataDir`), and keep a mark lifecycle in four places (`markStale`, `replaceRepoRows`, `dropRepoRows`, `refreshStale`'s queue and re-dating). The drain (`distill.ts`) is a background process that is allowed to spawn git. It could run part 1's own `ensureFresh` comparison over `knowledge_repos` and rebuild at most three changed repositories, with no mark at all. That fits D-16's "hooks use the index as it is" better than this design and removes a write from the hook. Also, `fingerprintOf` (repo.ts:856-863) does not change on an in-place edit, so the marks miss the most common hand edit, while Risks says "a hand edit … reaches the hooks only after a rebuild".
- F-2 · Nit · spec "One write transaction" rule 4, plan `contribute` step 6 · Every hook takes a write lock even when nothing is shown or marked. The `knowledge_shown` primary key already rules out a double record. A read followed by a conditional `INSERT OR IGNORE` write would do the same job and fail closed less often while a rebuild or `compact` holds the lock.
- F-3 · Nit · spec "Migration 7" (`knowledge_shown.event`, `rule`, the `at` index) and "Status" (`shown in 24 h`) · The once-per-context rule needs only `(session_id, context_epoch, repo_id, entry_id)`. Nothing reads `event` or `rule` except tests. The `at` index and the 24-hour status count are observability that no requirement asks for.
- F-4 · Nit · spec "knowledge_propose" `area` enum, plan `areaEnum` · The area is checked twice. First, a schema enum that is the union of two taxonomies, read once when the tools are listed and so stale for the server's lifetime. Second, `checkArea` against the target root, which is the real authority, and OpenCode's plain string already depends on it. The enum also makes the default tool-list snapshot depend on taxonomy files. A string field whose description lists the ids, with `checkArea` as the only check, would be smaller. This was decided in D-10, so it is flagged only.
- F-5 · Nit · plan "The judge", `Judge.relate` "a required member" · The existing `Judge` interface makes a capability that only some judges have optional (`personal?` at src/judge/types.ts:87-88). Making `relate` required forces edits to five stub judges in tests and `scripts/proof/quality.ts` that never relate anything. An optional `relate?` would follow the codebase's pattern.
- F-6 · Nit · plan `src/cli/commands/tool.ts` (asks the tools of built-in modules that are off) · To print "knowledge is off" the bridge loads the switched-off module's tools: zod, plus a taxonomy read for `areaEnum`. The exported `KNOWLEDGE_TOOL_NAMES` is enough to recognise the name with no load.
- F-7 · Nit · spec "What the agent is shown" (`resetKnowledgeLog()`), "The arithmetic" (25, 26, 60, 2 characters), `refreshStale(store, 3)` · A test hook, character-by-character arithmetic and a call signature belong in the plan, not the spec's Design section. The spec should state the share, the two-entry cap and the 80-character clip, and leave the arithmetic to the tests.
- F-8 · Nit · spec "Acceptance criteria" AC-8 and AC-14 · The two "superseded" placeholders are leftovers of earlier rounds. Dropping or renumbering them would make the list read cleanly.
