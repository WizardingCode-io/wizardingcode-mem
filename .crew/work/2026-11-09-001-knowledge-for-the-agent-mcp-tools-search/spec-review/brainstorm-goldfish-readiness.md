## Findings
- F-1 · Blocker · The tools, `--agent` in plugin files · The shared wrapper `scripts/templates/wizardingcode-mem.sh` runs `exec "$bin" mcp` in its `mcp)` branch and drops every argument after `mcp`, so putting `mcp --agent claude-code` into `.claude-plugin/plugin.json`, `plugins/codex/.mcp.json` and `plugins/cursor/mcp.json` through `scripts/plugins.ts` does nothing, and every plugin-installed host proposes as `agent:mcp`. The concept must say the template forwards the rest of its arguments (`exec "$bin" mcp "$@"` after a shift) and that the plugin-files test checks this.
- F-2 · Blocker · The tools, agent id on direct installs · The concept names only `scripts/plugins.ts`. A direct `wizardingcode-mem install <host>` writes its own MCP entry in at least five places, all with a bare `mcp`: `src/install/hooks-file.ts` (`withOurs` line 236 and `mcpServerEntry` line 390), `claude-code.ts` and `codex.ts` (`mcpAdd`), `copilot.ts` (`mcpEntry` and line 60) and `claude-desktop.ts` (`["mcp","--global"]`). Every host installed this way stays `agent:mcp`, and the guarantee that each proposal names its host's agent is false for them. The file list and the agent id for each host spec are missing.
- F-3 · Major · The tools, existing installs · Nothing says how a host installed with 0.6.0 picks up the new MCP command. A plugin host gets it only when its marketplace updates the plugin. A direct install gets it only when the person runs `install` again (the receipt or `planMcpServer` rewrite happens then and at no other time). Until then that host's proposals carry `proposed_by: agent:mcp`, permanently, in a git history the engine never rewrites. The plan needs a decision: re-register on the first run of the binary after an upgrade, a `doctor` warning when the entry has no `--agent`, or an accepted `mcp` writer that is documented.
- F-4 · Major · The tools, OpenCode · `src/install/opencode-plugin.ts` hardcodes its tool set (memory_search … project_links) and calls `tool <name> --project <dir>`, and `src/cli/commands/tool.ts` parses no agent flag. OpenCode therefore gets no knowledge tools until `pluginSource` lists the five tools and passes `--agent opencode` to a new flag in `tool.ts`. That reaches npm users only when the package updates, and direct installs only when `install opencode` runs again. Until then an old plugin talking to a new binary would propose as `mcp`. The concept says only that "the OpenCode bridge passes opencode", so the plugin change, the `tool.ts` flag and the version skew between them are unspecified.
- F-5 · Major · The tools, `--agent` value · Nobody says how `--agent` is validated or what happens on a bad value. Part 1 requires `^[a-z0-9][a-z0-9-]*$` and calls the value "the host agent's id (`AgentId`)", but `mcp` and `claude-desktop` are not `AgentId` members (src/core/types.ts). If part 1 checks against `AgentId`, the default writer `mcp` is refused on every proposal. The concept must say which of these it does: widen the type, validate against the pattern only, or fall back to `mcp` on an invalid value.
- F-6 · Blocker · What the agent is shown, the `pinned` field and the index · Part 1's `knowledge_entries` has no `pinned` column and keeps `pinned` only as an unknown key in the file. A session-start hook cannot parse files to find pinned entries, so a column (or side table) and a migration are needed, and neither is named. Rows part 1 already indexed would also never gain the value, because `ensureFresh` rebuilds only when the head or fingerprint changes. The migration must state its backfill, for example by clearing `knowledge_repos.head` and `fingerprint` to force a rebuild, or by rebuilding inside the migration.
- F-7 · Blocker · The tools and the prompt contribution, the FTS index and `knowledge_shown` · Part 1 defers both "the full-text index" and any shown table to this part, and its migration 6 drops `knowledge_fts` and `knowledge_shown` (the withdrawn module's names). The concept defines no migration for them: no module version (7?), no DDL, no choice between external-content FTS5 over `knowledge_entries` with triggers and an index kept by hand, and no backfill of entries already indexed. A builder cannot write the schema, and existing entries would be unsearchable after the upgrade.
- F-8 · Major · Rollback of this part · If part 2 records knowledge module version 7, rolling the binary back to a part-1-only build makes `moduleSchemaState` answer `too-new`. Every `knowledge write|accept|reject|list` then refuses with `ModuleSchemaTooNewError`, so the person cannot decide the agents' open proposals until upgrading again. Part 1's rollback text (the tables stay and 0.6.0 ignores them) covers 0.6.0 only. The concept must say what a rollback to part 1 leaves, or put part 2's tables under a module id or version that part 1 tolerates.
- F-9 · Major · Rollback, FTS kept in step · A part-1 binary (after a rollback), a hand edit followed by `rebuild`, or `adopt` changes `knowledge_entries` without touching an FTS table that part 2 maintains in code. After the upgrade again, search and the prompt hook miss or misrank those entries, and nothing marks the index stale. Either SQLite triggers on `knowledge_entries` (allowed: they are not on a core table) or a rebuild of the FTS index whenever head or fingerprint differ must be stated.
- F-10 · Major · Module on by default, how the change reaches existing installs · `DEFAULTS.modules = "memory,knowledge"` switches knowledge on for every install whose setting is unset or blank, at the first hook after the binary updates (the wrapper fetches at session start). Every MCP host then lists five new tools whatever the entries, so the default tool list changes even with no entries. The brief's acceptance says only that "the memory-alone tool list" is unchanged, and the new default-case snapshot must be stated as an intended change in the release notes. The person also gets one host permission prompt per new tool, and `knowledge_propose` makes git commits in the data directory.
- F-11 · Major · Module on by default, users with the setting saved · A user who saved `WIZARDINGCODE_MODULES=memory` (validation requires memory to be listed, so an explicit `memory` is common) never gets knowledge. That matches the intent of an explicit setting, but if the viewer ever saved the default value it shows (`publicSettings` fills in `DEFAULTS.modules`), the user cannot tell that choice from a deliberate one. The concept should say whether an explicit `memory` is honoured as opt-out and whether `doctor` or the release notes tell such users that knowledge exists.
- F-12 · Major · The module, composer F5′ and the snapshots · `shares()` in compose.ts reserves `2 * (speaking - 1)` separator characters, where `speaking` counts modules that have a `contribute`. With knowledge in `BUILT_IN`, memory's budget drops by 2 even when knowledge stays silent, so a memory output near its budget can change and break the pinned hook snapshots. F5′ also means knowledge runs before memory while its text is placed after it in module order. The concept's "plus the separators" must say that separators are reserved only for modules that actually wrote, and that knowledge is evaluated first but joined in `BUILT_IN` order.
- F-13 · Major · What the agent is shown, the first session after an upgrade · Because "first session" means no earlier `sessions` row, every project that existed before the upgrade (and every project brought in by history import through `ensureSession`, or opened once by another host) never sees pinned entries. An entry pinned after a project's first session also never reaches that project. `touchSession` runs before `contribute` (handle.ts line 67), so the test must also exclude the current session's own row, which the concept does not say. These limits should be stated as intended, with the exact query given: the earliest `started_at` or `id` for the project equals this session.
- F-14 · Major · What must be true before the first contribution · The hook reads part 1's index, but the concept does not say whether the hook calls `ensureFresh`. A stale fingerprint makes `ensureFresh` rebuild, which runs `git status` and takes leases, a process on the hook path that the brief forbids. The concept must say that hooks read the index as it is, never call `ensureFresh`, and stay silent when `moduleSchemaState` is not `current` or the tables are missing. Otherwise a too-new or missing schema throws on every hook and the composer logs it every time.
- F-15 · Major · Turning the module off · With knowledge removed from the setting, its tables, the FTS index, `knowledge_shown` rows and open proposals all stay (tables are created whatever the setting says, ADR 0020 K8). Nothing says whether `knowledge_shown` is pruned with sessions by retention or `compact`, or whether it grows without bound and keeps rows for deleted sessions. The off state, and the cleanup or its absence, should be stated.
- F-16 · Nit · Turning the module off and on again · Turning knowledge back on inside a live context relies on `knowledge_shown` keyed by session and context epoch, so entries shown before it was switched off are not shown again. The concept should say this is intended and that a compaction (a new epoch) of the first session shows the pinned entries again.
- F-17 · Nit · Rollback to 0.6.0 · 0.6.0's `mcp` reads flags only through `argv.includes("--global")`, so a new plugin file carrying `--agent` works with the old binary, and an explicit `memory,knowledge` setting is only logged once per process as an unknown module. The concept should still record that it relies on this tolerance, which no test pins today.
- F-18 · Nit · The tools, plugin and binary skew · The wrapper's `mcp)` branch never fetches, so a host started on an updated plugin can run the old binary's MCP server (no knowledge tools) until the host restarts the server after the session-start fetch. This first-session gap is worth one sentence.
