## Findings
- F-1 · Blocker · Design sketch, "Prompt" / "knowledge_search" · The design relies on "the FTS5 search", but part 1 deliberately builds no full-text index ("No full-text index and no search command: part 2 adds them"), and part 1's migration 6 drops `knowledge_fts` and `knowledge_shown` without creating them again. The concept names no knowledge migration 7: no FTS table over title, area, context, subject and body, no `knowledge_shown` table, no column for `pinned`, and nothing to keep the FTS rows in step with `rebuildRepo` and `writeEntry`. As written, the hook queries and the bm25 weights (title 4, area/context/subject 2, body 1) point at tables that do not exist.
- F-2 · Blocker · "Session start" / part 1 index schema · `pinned` is read on the hook path, but `knowledge_entries` has no `pinned` column. Part 1 keeps unknown keys only in the file text, so the hook would have to parse entry files, which breaks the 150 ms budget at scale. Part 1's `writeEntry` `change` shape also has no field to carry `pinned` (nor the `contradicts` of F-14), so `write --pinned` has no path into the store.
- F-3 · Major · Hook path freshness · Part 1 says "later parts call `ensureFresh` before a read", and its rebuild spawns `git status --porcelain` and parses up to 5,000 files per folder. The concept never says whether the session-start and prompt hooks call it. If they do, a hook spawns a process and can rebuild inline, against the brief's "no process in a hook" rule and the 80/150 ms budgets. If they don't, hand edits and an `adopt` by hand stay stale on the hook path with no refresh point named. ADR 0020 needed K5 (inline only up to 50 files, background drain otherwise); this concept has nothing in its place.
- F-4 · Major · Acceptance "The hook latency budgets of `tests/perf/budgets.test.ts` hold with knowledge on" · The perf corpus seeds 65,000 memories and no knowledge entries or repositories. With knowledge on and empty, the acceptance passes without exercising the new path. The concept names no fixture: entries across workspace, shared and project repositories, the part 1 caps (5,000 per folder, so up to about 15,000 visible entries), pinned entries at start. ADR 0020 measured only up to 500 entries in one folder.
- F-5 · Major · "Prompt" candidates "the FTS5 search's best 10 ... active, not yet shown" · The order of filter and limit is not stated. Filtering after LIMIT 10 returns nothing once the top 10 are drafts, archived or already shown. Filtering inside the query makes bm25 run over every match. src/retrieve/prompt.ts needed `POSTINGS_BUDGET`, common-term dropping and `PREFETCH` for exactly this reason, and the concept adopts neither its cost controls nor its exactness rule for three scopes of up to 5,000 entries each.
- F-6 · Major · "Session start, first session of a project" · `handleHook` calls `touchSession` before compose and returns early for `resume` and for hosts without `sessionInjection`. Several cases therefore never see the pinned entries, and nothing says so or retries: a project's first session that is a resume, one on a capture-only host, one whose hook timed out, or one created by the history import or another agent first. Every project that existed before the upgrade also already has a `sessions` row, so none of a user's current projects ever sees pinned knowledge. The mission's "a new project starts with the team's knowledge" then holds only for future projects whose first hook succeeds.
- F-7 · Major · "Session start" share of 840 characters, newest first · One line is `- <title> (<kind>, <area>; <scope>)` with titles up to 200 characters, so 840 characters fit roughly 4 to 10 pinned entries. Past that, the oldest (often the foundational personas and strategies) are dropped silently. The agent gets no "N more pinned; use knowledge_search" line, and no limit or warning on how many entries a person may pin.
- F-8 · Major · Composer F5′ and separators · compose.ts reserves `2*(speaking-1)` characters before any module speaks. With knowledge silent but defining `contribute`, memory would get 4,198, not 4,200, and the byte-for-byte snapshot claim could break whenever memory's brief is near its budget. "Plus the separators" does not say the reserve is charged only for contributions that were accepted (ADR 0020 F5′'s wording). The concept also does not say how knowledge is asked first while the output stays joined memory first.
- F-9 · Major · "Relevance" / `knowledge_search` rerank · One Noul per candidate over the top 20 puts all 20 entries in the request state. Bodies are capped only by part 1's 256 KiB file limit, so one search could send several hundred thousand input tokens. The concept has no clipping of state fields, no tokens-per-request ceiling, no per-session or per-day spend cap, and no attribution of `onUsage` to the tool path. An agent calls search many times per turn, and nothing bounds what that costs.
- F-10 · Major · "Duplicates and contradictions" via `Judge.consolidate` · The same unbounded-body problem applies: the draft plus 8 neighbours, each up to 256 KiB. An oversized request most likely comes back as 400 or 422, which client.ts maps to `invalid`. fallback.ts deliberately does not count `invalid` against the breaker, so every such proposal pays a full failed request and falls back silently, and the operator never sees a signal.
- F-11 · Major · Tool latency with TypeSafe down or slow · TypeSafeJudge allows 3,000 ms per attempt with retries after 250 and 1,000 ms, so up to about 10.25 s per judge call. One `knowledge_propose` makes two calls (catalogue and consolidate), up to about 20 s, plus 3 to 11 git calls of up to 15 s each through `Bun.spawnSync`. The concept states no deadline for a whole tool call, no shorter interactive timeout or no-retry policy for tool-path judging, and no check against hosts' MCP tool-call timeouts.
- F-12 · Major · MCP server concurrency · Part 1's git runner is `Bun.spawnSync`, which blocks the long-lived stdio MCP server's event loop. While a propose commits, every other tool on that server (memory_search, knowledge_search) stalls. Separately, several sessions each run their own MCP server against the same repositories, and a lease conflict is refused as `locked` ("try again") with no backoff. That invites agent retry loops, and the concept does not address either.
- F-13 · Major · Judge interface "the existing interface" · `ConsolidateInput` requires `draft.kind: MemoryKind`, `files: string[]` and neighbours with `id: number`. Knowledge entries have UUID ids, the kinds strategy, persona and pattern, and no files. The TypeSafe questions also speak of `new_memory`. The heuristic treats two empty file lists as `sameFiles`, so its `same` call rests on token Jaccard of 0.6 or more over whole bodies, which a reworded duplicate rarely reaches. "Existing interface" therefore needs a type change and new question text that the concept does not name.
- F-14 · Major · `contradicts: <entry id>` in the proposal frontmatter · The proposal is written by part 1's `writeEntry`, whose `change` has no such field. Part 1 keeps unknown keys only "when an entry is rewritten", and `knowledge_proposals` has no column for it. So nothing names how the contradiction reaches the file, the index or "the person at accept".
- F-15 · Major · New optional judge methods `catalogue?` and `relevant?` · fallback.ts wraps only `distill`, `consolidate` and `personal`. The concept does not say that `withFallback` gains the new methods. Without that, they either bypass the breaker or are missing from the composed judge. It also does not say which fallback applies when the primary is skipped, or whether the breaker's DB-backed state is re-read in a long-lived MCP server. Breaker loads its state once in the constructor and overwrites `breaker.typesafe` with its own view. Tool-path failures would also open the breaker shared with background distillation, and the reverse.
- F-16 · Major · Agent proposing in a loop · Quotas are 5 open proposals per target and 200 per repository. An agent varying titles can file 200 proposals, each with two TypeSafe requests and several git commits. That fills the repository quota and blocks every other agent and teammate from proposing to that scope (worst on the shared scope) until a person decides 200 items. Decided proposals then march toward the 5,000-file cap. The concept has no per-agent or per-session rate limit and no cost ceiling, and open proposals are not among the duplicate check's neighbours, so near-identical open proposals are not caught.
- F-17 · Major · Duplicate check scope "the FTS5's best 8 entries of the target scope" · A project-scope proposal that restates a workspace or shared entry (the common case: an agent rediscovering team knowledge) is never compared with it. The project is then shown both. Lexical top-8 also misses a duplicate that shares few words, and the concept offers no measured basis for the duplicate or contradiction thresholds on knowledge text.
- F-18 · Major · `knowledge_get { slugs }` and `knowledge_search { limit? }` · No maximum count of slugs, no `limit` ceiling and no size cap on the answer. One `knowledge_get` can return many 256 KiB bodies into the agent's context window, the token cost the hook budgets exist to prevent.
- F-19 · Major · `--global` for search, get and taxonomy · With no project, "visible scopes" is undefined. The concept does not say whether Claude Desktop's global server sees workspace and shared only, or every project's repository. The latter exposes all projects' knowledge to any global client, and the concept does not answer that disclosure question.
- F-20 · Major · Cataloguing heuristic "a lexicon per area in code" · The taxonomy is mutable (part 1's `area add legal`), so an added area has no lexicon, and without TypeSafe it is never chosen. The Choice runs "over the area ids", but workspace and shared each have their own taxonomy, and the concept does not say which root's areas a project proposal is catalogued against. Neither the 0.6 confidence threshold nor the lexicon's precision has any backing.
- F-21 · Major · Acceptance "with no entries every pinned hook snapshot ... unchanged" vs cost · The concept does not say what the empty module costs per hook. With no repository rows it should short-circuit before any FTS query, `buildQuery` or `knowledge_shown` lookup. It also does not say what happens when knowledge's module schema is `too-new` (part 1 throws `ModuleSchemaTooNewError`). On every prompt that becomes a contained exception through `onError`, unbounded log noise with no once-only latch like prompt.ts's `failOpen`.
- F-22 · Major · `knowledge_shown` growth · One row per entry per context, written on the hook path. ADR 0020 already listed "compact does not prune knowledge_shown" as deferred, and the concept names neither pruning nor an index for the per-prompt "not yet shown" lookup. The table and the lookup's cost grow with every session forever.
- F-23 · Major · Rerank value unproven · The claim that a Noul per query and candidate improves on bm25 for this corpus has no backing and no planned measure. ADR 0020's relevance probe (`tests/fixtures/knowledge-probe.ts`) exists and could measure it, and the concept spends per-search tokens on an unmeasured gain.
- F-24 · Nit · "first session" plus `/clear` · The acceptance says "each once per context" for session start, but the sketch says a later session gets nothing. Whether a `/clear` or `compact` inside the first session shows the pinned entries again (a new epoch) is not stated.
- F-25 · Nit · Agent id `mcp --agent <id>` · The id is a command-line flag any local configuration can set to any value. It tells "agent" from "person", which is all part 1's guarantee needs, but the concept should say the id is not authenticated, so a reader does not take `proposed_by` as proof of which host proposed.
- F-26 · Nit · `knowledge_taxonomy` counts "per area in the visible scopes" · Workspace and shared taxonomies can hold the same id with different labels, and the concept does not say whether counts merge by id or appear per root.
