## Findings
- F-1 · Major · Signatures, The tools: `areaEnum(store)` and "`knowledgeTools` calls it once, when the tools are listed" · `areaEnum` takes a `KnowledgeStore`, and a store needs a `db`, but the plan never says where that store comes from at listing time. Listing runs once per MCP server, and in `tool.ts` it also runs for the modules that are off. The open questions are whether `knowledgeTools` opens the database at `resolvePaths().storeDir` to list (with what busy timeout, and closed when), whether it builds a store with no database since `taxonomyFor` reads only `store.dataDir`, and what happens when that open fails. A competent reader would open the database inside `knowledgeTools`. Then a locked or too-new database, or any open failure, would throw out of `tools(mode)` and could break the server's whole `tools/list`, memory's tools included. The plan does not say whether a failure there falls back to `DEFAULT_AREAS` or stops the listing.
- F-2 · Nit · Signatures, The tools: "Each tool's `run` opens the database (`openDb` at `resolvePaths().storeDir`)" · `openDb` requires `busyTimeoutMs` and the plan gives none. Memory's tools use 2000 (`src/modules/memory/tools.ts:232`) and the knowledge CLI uses 5000 (`src/cli/commands/knowledge.ts:316`). The reader has to pick one.
- F-3 · Nit · Signatures, The judge: `src/judge/typesafe.ts` "reads the answers with `consolidateVerdict`" · Only `consolidateState` and `consolidateQuestions` are widened to `ConsolidateTexts`. `consolidateVerdict(input: ConsolidateInput, …)` (`src/judge/questions.ts:255`) still requires `kind` and `Redacted` bodies, so passing it the `ConsolidateTexts` that `relate` builds fails typecheck. The plan should say that `consolidateVerdict` takes `ConsolidateTexts` too.
- F-4 · Nit · Signatures, Status, doctor, compact: `src/store/compact.ts`, "A dry run counts the rows that match that condition, plus the rows whose session the run would remove" · Read literally, "plus" counts twice a row whose repository is gone and whose session the run would remove. The real run deletes that row once, so the dry run would report more than the real run. One count over the OR of the conditions is what the spec's "same number" needs.
- F-5 · Nit · Signatures, `src/retrieve/render.ts` (`withoutNotes`) and task 8 "Echoes" · No pattern is given for "lines shaped like the module's entry lines" (for example `^\s*(?:[-*>]\s*)*(?:workspace|project|shared)/[a-z0-9-]+ · `). The plan also does not say whether the two intro lines, the indented paragraph line or the count line are stripped as lines outside a block, the way memory's intro is in `NOTE_LINE`. The test names the count line but not the intros.
- F-6 · Nit · Task 16, "Propose, the refusals": "The 6th open proposal for one target answers `refused quota: there are already 5 open proposals for <slug>…`" · The judge (step 5) runs before part 1's quota check in `writeEntry`. If the five earlier proposals for a new slug share their text with the sixth, the heuristic refuses it as `duplicate` first. The plan does not say that the drafts differ, or that the target is an existing entry, whose own open proposals `without` drops from the neighbours. Whoever writes the test has to work this out from a failing run.
- F-7 · Nit · Task 14, `tests/unit/mcp-tools-list.test.ts`: "`listTools` also returns the `initialize` result" · The helper's new return shape is not given, yet the existing `toMatchSnapshot()` cases snapshot its return value and must stay byte for byte. Task 16's agent-id cases also need the helper to take the client's name (today it hard-codes `clientInfo: { name: "test" }`) and to send a `tools/call`. Neither change to the helper is described.
- F-8 · Nit · Task 4 (`tests/perf/budgets.test.ts`) and Signatures, `readRepoState(store, repo): RepoState` · "three visible knowledge repositories … of 2,000 entries each, 10 pinned" does not say whether that is 10 per repository or 10 in all. The fields of `RepoState` are listed only in prose (head, fingerprint, changed paths, parsed files), with no shape, and `overCap` and the dirty-check flag that `recordRepo` needs are left implicit.
- F-9 · Nit · Signatures, `src/doctor/checks.ts` (`knowledgeRepositories`) and `contribute` step 2 · Status passes `() => {}` as `enabledModules`' `onUnknown`, but doctor's call does not name one. With the default, an unknown id is written to the log from `doctor`. The text of the "logged once per process under `knowledge`" schema line is not given either, though the test counts that line.
