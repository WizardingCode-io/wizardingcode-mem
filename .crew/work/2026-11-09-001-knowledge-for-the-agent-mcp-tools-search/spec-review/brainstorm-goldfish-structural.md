## Findings
- F-1 · Major · The tools · Every tool answers in free prose ("Proposed <id> for <slug>; a person decides it", "already known as <slug>; use knowledge_update…", "one heading per entry" with no fields named), and agents and host skills will start parsing those strings. The concept should fix a stable answer shape now, the same in every tool: scope, slug, entry id, version, hash, plus a machine-readable refusal code that reuses part 1's `KnowledgeError` codes (`stale`, `exists`, `quota`, `invalid`, `dirty`, `locked`). Otherwise every later wording change breaks callers without anyone noticing.
- F-2 · Major · The tools / scope argument · `scope: "all" | "workspace" | "project" | "shared"` bakes in exactly one shared repository (part 1's single `knowledge/shared/`). The team server, the sharing policy and personas will want several shared repositories (one per team or client), and widening a closed zod enum that agents have learned is a breaking change. Define scope as a repository reference now (for example `shared:<name>`, with `shared` as an alias) and list the visible repositories in `knowledge_taxonomy`.
- F-3 · Major · knowledge_get / knowledge_update · Entries are addressed by slug, but part 1 makes the UUID the identity and says a later part may add renames. A slug is unique per repository, not across scopes, so `knowledge_get { slugs, scope? }` with no scope is ambiguous when workspace and shared share a slug, and a later rename breaks every slug an agent has stored. Have search return the entry id and have get and update accept it (or a qualified `scope/slug`), so a rename needs no change to the tool contract.
- F-4 · Major · knowledge_update · The stale check is `base_version`, which part 1 (D-8) defines as a local counter kept beside a content hash, and part 1 says `base_hash` is recorded for the sync (part 6). Once two machines sync, the same version number can mean different content, so an update based only on the counter would be accepted against the wrong text. The tool contract should carry the hash (or entry id plus hash) from day one, not only the counter.
- F-5 · Major · Duplicates and contradictions · The concept says it uses "the existing interface", but `ConsolidateInput` is memory-shaped. `draft.kind` is a `MemoryKind`, which has no strategy, persona or pattern; `neighbours[].id` and `perNeighbour[].id` are numbers while entry ids are UUIDs; and `files` means nothing for an entry. Taken literally this does not type-check, and an adapter would leak memory's types into knowledge. Each new module would then add more optional methods (`catalogue?`, `relevant?`, and later personas'), turning `Judge` into a grab-bag. Settle a module-scoped judge, or generic Choice/Noul/Score calls with each module's questions in its own folder, before the second module ships.
- F-6 · Major · The judgements · Memory records the judge's `version` so it can judge again when the judge improves, but a proposal records no judge source, version or confidence for its cataloguing, duplicate check or `contradicts`. In two years nobody can tell a TypeSafe area from a heuristic guess, or judge old proposals again. Add `judged_by`/`judge_version` (or put them in the commit message) now; the files never change afterwards.
- F-7 · Major · Cataloguing heuristic · "A lexicon per area in code" covers only the nine starting areas. The taxonomy is data: a person can add areas (`area add legal`), and workspace and shared keep separate taxonomies (D-9). Any added or shared-only area can never be catalogued without TypeSafe, and the stemmed lexicon is English for a team that writes Portuguese too. Keep the lexicon with the taxonomy (for example an optional word list per area in `taxonomy.md`), or derive it from the area's active entries.
- F-8 · Major · Duplicates and contradictions · Neighbours are "the FTS5's best 8 entries of the target scope" only. A project or workspace proposal that repeats a shared entry, or contradicts one, passes unseen, and with sync and a shared scope that is the common case. Neighbours should come from every visible scope, and the open proposals should be included too, so two agents proposing the same thing are not both filed under the quota.
- F-9 · Major · Contradictions · `contradicts: <entry id>` is a new key in part 1's frontmatter that this part never defines. It holds one value, while a proposal can contradict several neighbours, and it holds a bare id, while a cross-scope contradiction needs to name the repository. Define it as a list of qualified references in the entry format now; a sync peer on an older binary will carry the key as an unknown key forever.
- F-10 · Major · Session start / pinned · `pinned` is one global boolean, rendered newest first inside 840 characters. As the team pins more entries, older pins are dropped silently with no order and no warning. A pin in the shared repository reaches every team member's new projects once synced, which is a sharing-policy decision made by a frontmatter flag. The concept also never says whether an agent's proposal may set or clear `pinned` (unknown keys survive accept). Fix now: who may pin, an explicit order or priority, and a doctor or viewer warning when pinned entries exceed the share.
- F-11 · Major · Session start · The pinned line `- <title> (<kind>, <area>; <scope>)` has no slug or id, unlike the prompt line, so the agent cannot `knowledge_get` a pinned entry without searching for it first. It also shows the area id rather than the renamable label. Use one reference format on both paths, the same one F-3 asks the tools to accept.
- F-12 · Major · Session start / first session · "First session" depends on local state (no earlier `sessions` row). That one chance is lost to a crashed or cleared first session, to existing projects at upgrade, to whatever the history import already recorded, and on each new machine under sync it fires again. One-shot delivery tied to the store's session table will be hard to change once the acceptance test pins it. Record the delivery in its own table (project, entry, delivered at) so the later parts can redefine "new project" without moving data.
- F-13 · Major · Prompt / lexical floor · ADR 0020 measured the floor's three rules on title, tags and body. The concept moves rule 3 onto "the title or the area, context and subject", where the area is a single common word (`sales`, `code`, `design`) shared by every entry in that area. That reopens the back door ADR 0020 versions 1 and 2 failed on, and the 12/12 and 1/28 probe numbers no longer apply. The spec should require the probe to be run again and pin the floor's constants and field weights in one policy file.
- F-14 · Major · Prompt and session start / freshness · The concept never says whether the hook calls part 1's `ensureFresh`. If it does, a changed fingerprint triggers a rebuild that runs `git status`, spawning a process on the hook path against the brief's constraint; if it does not, the index is stale after every hand edit or sync until something else refreshes it. The cost also grows with each visible repository (three listings and three `stat`s each). Decide the hook's freshness rule now (the background drain, as in ADR 0020 K5); every new shared repository added by sync makes this worse.
- F-15 · Major · The index / FTS and shown tables · Neither the FTS table nor `knowledge_shown` is specified: no migration version (7), no columns, no content mode, no tokenizer, no maintenance (triggers or rebuild), no scope column for filtering, no pruning by `compact`. ADR 0020 had to choose a self-contained FTS because the composite key has no stable rowid, and `(repo_id, id)` here has the same problem. A tokenizer choice (diacritics, Portuguese, prefixes) means a rebuild on every store once shipped, and `knowledge_shown` keyed on the local `repo_id` integer lacks the moment and time the viewer's history will want.
- F-16 · Major · The module / visible scopes · "The project's visible scopes" is written out inline in three places (session start, prompt, search) as project, workspace and shared, leaving out memory's linked projects (ADR 0018). The sharing policy and the team server will need to redefine visibility. Fix one function (`visibleRepos(project, mode)`) that the hooks, the tools and the judge's neighbour search all call, so part 4 changes one place.
- F-17 · Major · Agent writer / --agent flag · The writer is `agent:<host>` and nothing else. Once the shared scope syncs, five team members' `agent:claude-code` proposals look the same, and the person the agent worked for is lost from a history that is never rewritten. Add the person's name beside the agent id in the proposal's frontmatter and commit (an `on_behalf_of` field, from part 1's `personAuthor`) now, before shared proposals exist.
- F-18 · Major · Agent writer / --agent flag · Writing `--agent <id>` into every host's plugin command spreads the identity across each host's packaging. Configurations installed before this release keep running `mcp` without the flag and stay `agent:mcp` until the plugins are reinstalled, and every new host needs its own plugin change. Consider taking the id from the MCP `initialize` handshake's `clientInfo`, with the flag as an override, and say what the default `mcp` id means in the viewer and in the sync.
- F-19 · Major · The tools · Agents can propose but cannot see what they proposed: there is no tool to list open proposals or their decisions, `knowledge_search` does not say whether it returns open proposals, and there is no way to propose archiving an entry or setting `supersedes`. Agents will propose again, hit the 5-per-target quota, and report dead entries in prose. Decide now whether these will be new tools or new optional arguments, so the tool list snapshot changes only once.
- F-20 · Major · Cost of a write · Part 1's NFR says "part 2's MCP server runs one write per tool call and measures this cost before accepting it". The concept drops that obligation, though a propose now adds an FTS search, possibly two TypeSafe calls (catalogue plus consolidate) and 3 to 11 git spawns inside one MCP call, under hosts' tool timeouts. Put the measurement and a time budget for a propose into this part's acceptance criteria.
- F-21 · Major · Decision record · ADR 0019's note (2026-10-13) says knowledge is a separate product, not a module, and the F5′ composer rule exists only in the withdrawn ADR 0020. The concept reverses the first and adopts the second without naming the ADR that will record either. The reasoning behind both choices will then live in a work folder; say which ADR (0024 or an amendment to 0019) records F5′, `pinned`, `contradicts` and the tool contract.
- F-22 · Nit · The composer · F5′ handles one declared module. Once personas declares a share too, the composer needs a rule for how declared shares add up and in what order they are asked, and the 0.2 is a constant in code with no setting. State the rule for several declared modules now, so the personas part does not rework the composer.
- F-23 · Nit · Personas · `kind: persona` entries can be pinned and shown through knowledge's share, while a later personas module will want to show personas itself. Without a rule such as "knowledge never shows `persona` once the personas module is on", the agent sees each persona twice.
- F-24 · Nit · knowledge_taxonomy / --global · The concept does not say how the workspace and shared taxonomies are merged when the same id has different labels, or what `scope: "project"` means under `--global`, where there is no project.
- F-25 · Nit · Wrapper · The intro "Knowledge the team keeps on purpose, versioned and reviewed" becomes part of the pinned snapshots once entries exist. It describes a team even for a solo workspace, and synced shared entries arrive without local review, so changing the wording later means updating the snapshots and changing what agents are told.
- F-26 · Nit · Entry format · `pinned` and `contradicts` join the format without a format version bump in `knowledge.json` and without a list of known keys. Peers on different binaries will exchange these keys through sync, so keep one registry of frontmatter keys, each with the part that defined it.
- F-27 · Nit · The module / default on · Turning knowledge on by changing `DEFAULTS.modules` reaches nobody whose `<data dir>/env` already holds `WIZARDINGCODE_MODULES=memory`, for example written by the settings API. Say whether existing explicit values are migrated or left alone.
- F-28 · Nit · Relevance in search · Twenty Noul questions per `knowledge_search` call, with no cache, is a recurring cost and a delay in every agent loop that searches. State a cap or a cache keyed by the query and the entry hash.
