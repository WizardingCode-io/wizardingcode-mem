## Findings
- F-1 · Major · Design › Migration 7 (`knowledge_fts`), Prompt, The tools › `knowledge_search` · The spec makes `repo_id` and `entry_id` searchable FTS5 columns. It then builds the content match without a column filter: `repo_id:(...) AND (<the query's quoted tokens>)`, and for search "each double-quoted, joined by OR". `searchTokens` (src/util/words.ts:57) keeps single digits and short tokens. So a query such as "step 3" or "v2 pricing" matches every row of repository 3 or 2 through the `repo_id` column, and a hex group in a prompt can match an `entry_id`. Memory, which the spec cites as its model, avoids this by qualifying its columns: `{title body terms} : (...)` (src/retrieve/prompt.ts:71, src/mcp/tools.ts:212). Built as written, `knowledge_search` returns padding rows that share no word with the query, `No knowledge matches.` stops being reliable, and the prompt path's top 10 candidates can be crowded out. The content tokens need a column filter such as `{title area context subject body}:`, and AC-17 or AC-15 should test for it.
- F-2 · Major · Design › The judgements, neighbours · A change proposal (`slug` + `base_version`) is judged against the FTS's best 8 entries, and the entry being changed is not excluded. A small edit to entry X will score "same" against X, and the agent gets `refused duplicate: already known as X; propose a change with its slug and base version`, which is what it just did. That is a refusal loop that also uses up the 20-per-hour window. A reversal of X will also always be flagged as contradicting X. The spec should say how a change treats its own base entry, and AC-10 or AC-16 should cover it.
- F-3 · Major · Design › The judgements, contradiction rule · The spec says it reuses "thresholds from `src/distill/policy.ts`", but it takes only `SUPERSEDE.minContradiction` (0.7). It drops `SUPERSEDE.minRelationScore` (0.8), which memory's rule also requires (src/distill/policy.ts:24, src/distill/consolidate.ts:80-81). With TypeSafe the Score and the Noul are separate questions, so a neighbour judged "different" can still come back with contra ≥ 0.7. Every such entry is recorded in `contradicts` and shown to the person. The reader builds a looser rule than memory's while believing it is the same one. Either keep the relation floor or give the reason for dropping it.
- F-4 · Major · Design › Prompt; F5′ · Each prompt entry shows "its first paragraph indented, inside the share". The prompt share is floor(0.2 × 2400) = 480 characters for up to two headings plus paragraphs, and no clip is stated for the paragraph. compose drops a contribution that says more than its share (src/engine/compose.ts:5-6). If the implementer does not clip or fall back to fewer entries, one long first paragraph makes knowledge silent on that prompt. CUJ 2 and AC-4 would then fail on ordinary entries. The spec should state the clip, or say that an entry is dropped when it does not fit.
- F-5 · Major · The tools › `knowledge_propose` area enum; NFR › The area enum · The enum is "the area ids of the workspace and the shared taxonomies at listing time". The spec does not say what the schema is when neither repository exists, which is the normal state with no entries (CUJ 6). `readTaxonomy` throws `missing` when there is no root (src/modules/knowledge/taxonomy.ts:27-29), so the enum would be empty, and an empty zod enum is not a valid schema. The tool list's shape also depends on files read when the server starts, which undercuts "loaded lazily". Separately, the list of refusal codes omits part 1's `missing` (src/modules/knowledge/errors.ts:5), which a propose to a nonexistent shared repository, or a change to a deleted slug, will raise. The spec calls the answer shape "fixed", yet an unlisted code can come back.
- F-6 · Major · Open Questions / Decisions D-9 / Alternatives rejected · The spec admits that D-9 is unresolved and that a general go-ahead was not an answer to it. Yet the Decisions table says "Answer taken", and Alternatives rejected lists "Pinned entries only at a project's first session" as **Rejected**. The validator ruled that this choice belongs to the person. A reader would treat it as settled and build and gate AC-3 on it. Until the person answers, the alternative should be marked as pending, not rejected.
- F-7 · Major · Design › What the agent is shown; NFR › Hook path · Recording `knowledge_shown` is a write on every session start and every prompt that shows an entry. The spec says the stale mark fails open but says nothing about this write: if the insert fails under `busy_timeout`, is the entry still shown (and then shown again on the next prompt, breaking "once per context") or dropped? The NFR's hook budget counts "one `knowledge_shown` lookup" and not this write. The drain's rebuild can hold the write lock for up to 2 s in one transaction (Migration 7), which is a stated source of contention against a 150 ms session-start budget, and it is not addressed.
- F-8 · Nit · Design › Migration 7 · "a rebuild of a 2,000-entry repository … completes under 2 s on the gate machine (measured)". The triggers do not exist yet, so this cannot have been measured. It reads as a result when it is a target (AC-15 gates it correctly).
- F-9 · Nit · The tools › Rate and cost · The per-agent-id counter in `meta` is a read-modify-write shared by separate processes (the MCP server and each `tool` bridge call). The spec does not say it runs inside the write transaction, so concurrent calls can go slightly past 20.
- F-10 · Nit · Design › The judgements, neighbours · The spec does not say how the neighbour FTS query is built from the draft (title tokens only? body tokens ORed, clipped?). A long body produces a match of hundreds of OR terms.
- F-11 · Nit · Design › The judgements, neighbours · Open proposals are checked only in the target repository, but entries are checked across every visible repository. The same draft proposed to the workspace while an identical one is open in the project is not caught. The asymmetry has no stated reason.
- F-12 · Nit · Problem (Heilmeier Q1, Q4) · The opening is heavy with internal terms (F5′, Noul, TypeSafe, D-numbers). It also does not say plainly who benefits and what changes for them beyond the test of success.
- F-13 · Nit · Acceptance criteria · The numbering runs AC-1..7, 8 (superseded), 16, 9..12, 14 (superseded), 17, 15, 13, which makes the list hard to follow. The superseded stubs add nothing to the spec.
- F-14 · Nit · Status, doctor, compact · "Entries shown in the last 24 hours" in `status` queries `knowledge_shown` by `at`, which has no index. The cost grows with the table, whose growth the ADR is only asked to describe.
