## Findings
- F-1 · Blocker · Scope "Modify, tests that pin a fact this part changes" and Phase B task 3 · Four existing tests stand for "tables a newer version wrote" by inserting `('knowledge', 7, 'x', 0)` into `module_migrations` by hand: tests/unit/knowledge-index.test.ts:364, tests/unit/knowledge-store.test.ts:491, tests/unit/doctor-knowledge.test.ts:158 and tests/integration/knowledge-cli.test.ts:436. `module_migrations` has `PRIMARY KEY (module, version)` (src/store/db.ts:245). Once migration 7 is recorded by `openDb`, each of these inserts hits a primary-key conflict, so all four tests fail. The plan moves only module-migrations.test.ts's hand row to 8. knowledge-index.test.ts and knowledge-cli.test.ts are not in Scope at all, and the plan's changes to doctor-knowledge.test.ts and knowledge-store.test.ts do not cover these lines. As written, the full suite at the gate fails.
- F-2 · Major · Signatures, The judge, `src/judge/typesafe.ts` and `questions.ts` · The plan widens `consolidateState` and `consolidateQuestions` to `ConsolidateTexts`, but TypeSafe's `relate` also "reads the answers with `consolidateVerdict`". That function is still typed `consolidateVerdict(input: ConsolidateInput, …)` (src/judge/questions.ts:255), and `ConsolidateInput` requires `draft.kind: MemoryKind` and `Redacted` bodies (src/judge/types.ts:47-51). A `ConsolidateTexts` value is not assignable to it, so `bun run typecheck` fails in task 13 unless the implementer invents a change to `consolidateVerdict`'s signature that the plan never names.
- F-3 · Major · Signatures, The tools, `areaEnum` and "`knowledgeTools` calls it once, when the tools are listed" · `areaEnum(store)` needs a `KnowledgeStore`, and `openStore` needs a `db` (src/modules/knowledge/store-open.ts:10-17). But `tools(mode)` gets only the mode (src/engine/module.ts:91), and the plan says the database is opened per call, inside `run`. The plan does not say whether listing the tools opens (and migrates) the database at `resolvePaths().storeDir`, builds a store with no database, or reads the two taxonomies some other way. It also does not say what happens when that step fails. `moduleTools` catches the throw and drops every knowledge tool (src/mcp/run.ts:21-26), so a reader can build a listing that writes a database, or one that silently offers no knowledge tools.
- F-4 · Major · Signatures, The tools, each tool's `run` ("resolves the project from `call.projectDir` (`resolveProject` …)") · `resolveProject` returns a `disabled` flag (src/core/project.ts:14, 157). The hook path stops on it before any module is asked (src/hooks/handle.ts:65), and memory's tools answer "Memory is turned off for this project." (src/modules/memory/tools.ts:279). The plan says nothing about a project that is turned off, so a reader will build knowledge tools that read, and propose into, the project repository of a project the person turned off.
- F-5 · Major · Signatures, `src/modules/knowledge/policy.ts`, the floor · The plan says "The rule is ADR 0020's", then says "two words with one stem count twice" (and task 6 pins `query`/`queries` as two). ADR 0020 says the floor counts "distinct words compared by stem" (docs/adr/0020-knowledge.md:110), and its rule 2 says "3 distinct non-generic words". The two statements disagree, and a reader cannot tell which one governs the `words` and `title` thresholds.
- F-6 · Major · Signatures, `src/store/compact.ts` (dry run) and task 18 · The dry run counts "the rows that match that condition, plus the rows whose session the run would remove". A `knowledge_shown` row whose repository is gone and whose session the run would remove matches both, so a literal sum counts it twice. The real run deletes it once. That breaks task 18's claim that the dry run "reports the same number". The plan should say the two conditions are OR'd in one count.
- F-7 · Nit · Signatures, `src/modules/knowledge/entry.ts`, `renderProposal` · "writes the new keys after `status`" is ambiguous. `decision`, `decided_by`, `decided_at` and `decided_version` also follow `status` (src/modules/knowledge/entry.ts:491-496), so the new keys could go right after `status` or after the `decided_*` lines.
- F-8 · Nit · Signatures, `index-store.ts`, `replaceRepoRows` · It is described as a transaction that "only replaces the repository's rows". The current transaction also runs `recordRepo` (head, fingerprint, over_cap, dirty_checked) (src/modules/knowledge/index-store.ts:522), and the bullet does not name it. The fields of `RepoState` are not named either.
- F-9 · Nit · Signatures, `judgeProposal` step 9 · `judgeVersion` is `judge.versions[source]`, which is typed `string | undefined` (src/judge/types.ts:84), but the plan types it `string | null` and does not say what an absent version becomes.
- F-10 · Nit · Signatures, `src/doctor/checks.ts`, the pinned-share warning · The plan does not say where the pinned entries come from: the index (`pinnedEntries`) or the files `doctor` already reads by hand (`readRepoFiles`). The check's own comment limits what it reads from the database to four things (src/doctor/checks.ts:606-611).
- F-11 · Nit · Signatures, The tools, each tool's `run` (`openDb` at `resolvePaths().storeDir`) · No busy timeout is given. Memory's tools use 2000 ms (src/modules/memory/tools.ts:232).
