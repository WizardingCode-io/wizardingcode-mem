## Findings
- F-1 · Blocker · Task 16 (`src/mcp/run.ts`) against task 17 · `GLOBAL_INSTRUCTIONS` is one constant, and `runMcpServer` sends it unchanged whenever `--global` is set (`src/mcp/run.ts:40`, `src/mcp/server.ts:36`). Task 16 changes it to name the knowledge tools. Task 17 then requires two things: with `WIZARDINGCODE_MODULES=memory` the `initialize` instructions must be "byte for byte the old text", and with the default setting they must name `knowledge_search` and `knowledge_get`. One constant cannot do both, so the plan as written fails its own test. The plan has to say how the instructions depend on the enabled modules: for example, a per-module instructions field on `EngineModule`, or `server.ts` appending a fixed sentence when knowledge is on. It also has to give the exact sentence.
- F-2 · Major · Signatures, `contribute(input: MomentInput)` and `visibleRepos(store, …)` · On the hook path the module only gets `MomentInput`, which has `db` and no `dataDir` or `env`. But `visibleRepos`, `pinnedEntries` and `searchEntries` take a `KnowledgeStore`, and the stale check needs absolute repository paths (`repoPath(store.dataDir, …)`, `headOf`, `fingerprintOf`). The plan never says where the hook gets its store. Options include `resolvePaths()` as memory's tools do, `db.filename`, or a new `MomentInput` field. It also does not say whether `openStore`'s `loadSettings` is acceptable on every hook. Task 7's tests ("each world a data directory") will pass or fail depending on this choice.
- F-3 · Major · What the agent is shown, "one count, cached for the process" · Task 7 runs many worlds (no repository, then repositories) in one test process. A process-wide "no repositories" cache would silence every later world. The plan does not say what is cached (only a non-zero count? keyed by `db`?) or how a test resets it. The same question applies to the "logged once per process" schema state.
- F-4 · Major · Session-start and prompt lines, `<area label>` · The label comes from `taxonomy.md`, a file read through `taxonomyFor`, and that function throws `invalid` on an unreadable taxonomy. The plan does not say whether the hook reads two taxonomy files on every session start and prompt, or caches them. It also does not say what is printed when the root's taxonomy is missing, unreadable, or lacks the entry's area (the id? nothing?). A builder could easily let one bad taxonomy throw and silence the whole contribution. The same gap applies to the search tool's line.
- F-5 · Major · Signatures, `src/retrieve/evidence.ts` `sharedStems(queryWords, text): Set<string>` · Memory's `hasEvidence` (prompt.ts:351-366) works on the matched query words. It counts `matched.length` and calls `isGeneric(word)` on each word. A function that returns the set of stems loses both the count and the original words. Calling `tellingOf` on stems can also give different answers from calling it on words. With these signatures, a builder either cannot keep memory's behaviour "unchanged" or has to redesign the primitive. The plan should give a return type that keeps the matched words, and say which form `tellingOf` receives.
- F-6 · Major · Prompt and search FTS match (`searchEntries`, `match: string`) · `repo_id` and `entry_id` are searchable columns. An unqualified term therefore also matches them: a search for `"2"`, or an identifier fragment, matches every entry of repository 2. bm25 weight 0 changes the rank, not the match. Memory confines its terms to columns (`FTS_MATCH = {title body terms} : (…)`). The plan does not say that the query's terms are restricted to `{title area context subject body}`, and it does not say who builds the final match string, the caller or `searchEntries`.
- F-7 · Major · Tools, `knowledge_propose` area enum · The plan does not cover these cases:
  - No workspace or shared taxonomy exists yet, which is the normal first run. `z.enum([])` is invalid, and the default-list snapshot in task 17 depends on the answer: `DEFAULT_AREAS`? the property left out?
  - The same id is in both taxonomies with different labels.
  - How each option carries its "`<label> (<root>)`" description. A zod enum has no per-option descriptions, so this needs a union of described literals or a single field description.
  The JSON Schema shape the model sees is left for the builder to choose.
- F-8 · Major · Tools, `src/install/opencode-plugin.ts` · The OpenCode plugin's tools are hand-written static schemas. The plan does not say:
  - which `area` schema the plugin uses, since the taxonomy enum is not available there;
  - what happens when knowledge is off (`memory` setting): the plugin still offers the three tools, and `tool.ts` answers `unknown tool`.
  It also leaves out `tests/unit/opencode-plugin.test.ts`. That test asserts the exact sorted tool keys (line 185) and breaks once the tools are added.
- F-9 · Major · Tools, refusal shapes against part 1 · Part 1's `checkArea` throws `area: legal is not in the taxonomy (code, …)`. The plan's test expects `refused invalid: area legal is not in the workspace taxonomy; its areas are code, …`. The plan does not say whether the tool checks the area itself, and if so where it sits in the order (counter, area, judge, write); or whether part 1's message changes. Part 1 also throws code `missing` (a change to a slug that does not exist), which is outside the spec's code list. The plan gives no answer line or test for it.
- F-10 · Major · Tools, `base_hash` · The spec says a given `base_hash` must equal the entry's current hash. The plan's signatures, steps and tests never mention it: `EntryChange` has no base hash, part 1's `propose` does not check one, and there is no refusal code or test case. A builder following the plan would leave it out.
- F-11 · Major · Judgements, `relateState(input)` redaction · AC-17 requires `relateState` to redact with the store's `env`. `RelateInput` has no `env`, and the other judge inputs arrive already `Redacted`. The plan has to choose: either add `env` to `RelateInput`, or redact in `judgeProposal` before `relate`. In the second case the heuristic also sees redacted text, and the test that seeds an AWS key behaves differently.
- F-12 · Major · Tools, `knowledge_get` answer and caps · D-11 promises fixed answer shapes, but the plan leaves these to the builder:
  - the heading line;
  - the field lines' layout (`id: …`?);
  - the wording of the clip note at 8,000 characters;
  - what happens at the 32,000 cap: later refs dropped or cut, and with what note.
  The global answer for `repo: "project"` is also not fixed. It could be a schema without `project`, which changes the global snapshot, or a run-time message with unstated wording.
- F-13 · Major · Task 17 "Red run for the new cases" · The behaviour these cases test was built in tasks 14 (handshake mapping, `--agent`) and 16 (tools, instructions). Written after the code, they cannot run red, so the test-first record for AC-6 and AC-9 cannot be produced as planned. They belong before tasks 14 and 16, or the plan should say they are recorded as already green.
- F-14 · Major · Task 19 against task 18 · Task 18 asserts that `rebuildAll` on a removed repository folder deletes its `knowledge_shown` rows. Task 19 modifies only `report.ts`, `checks.ts` and `compact.ts`, so the green run needs a `src/modules/knowledge/index-store.ts` change (`rebuildAll`) that no step names. The same applies to task 9's "folder gone … deletes its rows": the plan does not list which rows (`knowledge_repos`? shown rows?).
- F-15 · Major · Task 18/19, `compact --dry-run` count · The plan names no new field on `CompactReport` and no CLI output for the count. `src/cli/commands/compact.ts` is not in Scope. It also does not say whether the dry-run count includes rows of sessions that the same run would remove; in dry-run those sessions are not deleted, so a plain orphan query undercounts.
- F-16 · Major · Task 7, "a hook on a store … holding the write lock still answers" · `recordShown` writes as well, and under a held write lock it fails like the stale mark does. The plan does not say what "answers" means here: knowledge's text shown with the record skipped, or knowledge silent and memory alone. It also does not say whether the shown lookup and the record share one `withWrite`, as memory's file-read does, to stop two parallel prompts showing the same entry.
- F-17 · Nit · Signatures, `src/modules/knowledge/entry.ts` bullet · `KnowledgeEntry`, `KnowledgeProposal` and `EntryChange` are in `types.ts`, and `writeEntry` is in `store.ts`, not `entry.ts`. `AGENT_ID_PATTERN` "(part 1's)" is `AGENT_ID` in `entry.ts`; say whether to re-export it or rename it.
- F-18 · Nit · Signatures, `runMcpServer` · The `--agent` value has to reach the server, but the plan does not name the new `runMcpServer` option. `resolveAgentId` throws on a bad flag in every handler call, after the start-up check in `mcp.ts`.
- F-19 · Nit · `knowledgeStatus(db, now)` · `on` depends on the modules setting, which this signature cannot read. `shownToday` disagrees with the spec's "in the last 24 hours", and the plan does not say whether it counts distinct entries or rows.
- F-20 · Nit · Task 18, doctor "pinned entries exceed the session-start share" · Visible pins differ per project. The plan does not say which set doctor measures: workspace plus shared? each project?
- F-21 · Nit · Tasks 9/10, refresh · The plan does not say whether `refreshKnowledgeSafely` calls `ensureFresh` (the spec) or `rebuildRepo` (the plan's word "rebuilds"), or whether it takes the repository lease the way `rebuildAll` does with `withRepoLeases`.
- F-22 · Nit · Task 8 · The comments in `src/engine/modules.ts` (lines 33-34) and `src/hooks/handle.ts` (lines 38-40) still say "the default, memory alone"; the plan only names the settings comments.
- F-23 · Nit · Task 15 · The window-reset case ("the store's `now` advanced") and the stub-TypeSafe cases run "through the module's `tools(...)`", which build their own store, clock and judge. The plan does not name the seam: the `WIZARDINGCODE_MEM_TYPESAFE_URL` endpoint, or calling `proposeKnowledge` directly. The neighbour search's match string from a long draft (how many tokens) is also unstated.
- F-24 · Nit · Scope/task 7 · The plan never says that `contribute` returns null for `file-read` and `tool-failed`. Because of F5′ this matters, since memory then keeps the whole budget, and no test pins it.
