## Findings
- F-1 · Blocker · Task 16 (`src/mcp/run.ts`: "`GLOBAL_INSTRUCTIONS` names the knowledge tools") against Task 17 · `GLOBAL_INSTRUCTIONS` is one exported constant (src/mcp/run.ts:40), and src/mcp/server.ts:36 passes it to every `--global` server whatever modules are on. If the constant names `knowledge_search` and `knowledge_get`, then task 17's memory-alone case ("the `initialize` result's `instructions` for `--global` byte for byte the old text" with `WIZARDINGCODE_MODULES: "memory"`) cannot pass. Making the instructions depend on the enabled modules needs a change to server.ts, which the plan does not describe (server.ts is listed only for the agent id). As written, the plan cannot be built.
- F-2 · Major · Task 4 (migration 7) and the Scope list · tests/unit/module-migrations.test.ts pins the current schema: `KNOWLEDGE_SCHEMA_VERSION` is 6 (line 76), the migrations are `[[6, "knowledge_store"]]` (line 77), a fresh store records exactly 2 rows and `not.toContain("knowledge_fts")` (lines 84, 93), and version 7 counts as "behind" or "too-new" (lines 121-131). Migration 7 breaks all of these. The file is in no task and not in Scope's Modify list, so the builder meets red tests that no task accounts for. The file is also being edited right now by the sharing change.
- F-3 · Major · Task 3 (AC-15 rebuild of 2,000 entries "written directly") and Task 20 (perf corpus "written directly as files … indexed by `rebuildRepo`") · `rebuildRepo` asks git for changed paths (`statusOf`: `--untracked-files=all`, repo.ts:886). Every file that has not been committed comes back as changed and is indexed with `status: draft` plus the problem "changed outside the engine" (index-store.ts:493-503). Under the spec's trigger rule, those rows never reach `knowledge_fts` and are never shown as pinned. Files written directly therefore leave an empty FTS index: the 2 s rebuild and the hook budgets are measured over no searchable entries and pass without testing anything. The plan must say the files are committed, or say how the corpus avoids the dirty check.
- F-4 · Major · Signatures `contribute(input: MomentInput)`, `visibleRepos(store, …)` and Task 7 (the stale check on the hook) · `MomentInput` (src/engine/module.ts:12-31) carries `db` and `root`, but no data directory, `env` or settings. `KnowledgeStore` (types.ts:27) and the head/fingerprint comparison need `dataDir`, because `knowledge_repos.path` is relative to it. The data directory differs from the store directory (`resolvePaths`), and tests use their own `env`. The plan never says where `contribute` gets the data directory and env (a new MomentInput field, the process env, something else), so the builder has to make a design choice.
- F-5 · Major · Signatures `src/retrieve/evidence.ts` `sharedStems(queryWords, text): Set<string>` and `tellingOf(words)` · Memory's `hasEvidence` (prompt.ts:339-368) works on the matched query words, not their stems. Its weight uses `matched.length` and `telling.length`, and two words with one stem (for example "query" and "queries", both kept by `buildQuery`) count twice. `isGeneric` is applied to the word, not the stem. A `Set` of stems cannot reproduce either, so rebuilding memory's rule on this signature changes its behaviour, while the plan says "without a change of behaviour". The signature needs to return the matched words.
- F-6 · Major · Signatures `src/judge/types.ts` `RelateInput` (plain `string` fields), `relateState(input)` and AC-17 (redaction with the store's `env`) · Neither `relateState(input)`, `RelateInput` nor `TypeSafeJudgeOptions` (typesafe.ts:23) carries an `env`. The existing pattern (`ConsolidateInput`) takes text already redacted, typed `Redacted`. The plan does not say where redaction with the store's env happens: the caller in propose.ts, an env field on the input, or a judge option. A builder who calls `redact` inside `relateState` defaults to `process.env` and misses the store's env, which is exactly what AC-17 tests.
- F-7 · Major · Task 4 (the FTS triggers kept "by every writer") · `upsertEntry` deletes by slug and then runs `INSERT OR REPLACE` (index-store.ts:54-62). When an entry keeps its id under a new slug, the `(repo_id, id)` primary-key conflict is resolved by REPLACE. SQLite fires no DELETE trigger for a REPLACE deletion unless `recursive_triggers` is on, and the store never sets it. The old FTS row survives and the AFTER INSERT trigger adds a second one for the same `entry_id`. That gives duplicate hits and a false "FTS rows ≠ active entries" warning from doctor. The plan neither changes the upsert nor turns on `recursive_triggers`, and no test case covers it.
- F-8 · Major · Signatures `knowledge_propose` (`base_hash?`) and Task 4 (`store.ts` changes) · Part 1's agent `propose` (store.ts:415-519) never compares a base hash, and `EntryChange` (types.ts:109) has no hash field. The spec requires "the base hash, when given, must equal the entry's current hash", but no task wires it (store.ts is changed only for `pinned` and the proposal extras), and no case covers a wrong `base_hash`. The check, where it runs and the refusal code are all left to the builder.
- F-9 · Major · Task 15/16 (propose semantics and refusal codes) · Part 1 treats `slug` without `base_version` as a change at the current version (store.ts:447-452). It throws code `missing` for a change to an entry that does not exist, for "no repository yet" and for "has no taxonomy" (store.ts:190, 200, 460). The spec's refusal list (`invalid, stale, exists, dirty, locked, quota, git, too-new, duplicate`) has no `missing`. The plan does not say what the tool does with `slug` alone, `base_version` alone, or a `missing` error: a `refused missing:` answer, or an error thrown back to the agent.
- F-10 · Major · Task 15 (`refused invalid: area legal is not in the workspace taxonomy; its areas are code, …`, `refused exists`) · Part 1's `checkArea` says `area: legal is not in the taxonomy (code, …)` (store.ts:144-149), and it runs only inside `writeEntry`, under the leases, after the judge would already have run. The plan does not say whether propose.ts checks the area, `exists` and `stale` before the judge (with the spec's wording) or relies on part 1's message. It also does not say which refusal wins when an existing-slug draft is also a heuristic duplicate. The tests as written need one fixed order and one fixed message.
- F-11 · Major · Signatures `knowledgeTools(mode)` (the area enum) and Task 17 (default-list snapshot) · Knowledge is now on by default, and a fresh install has no workspace or shared taxonomy, so the `area` enum built "at listing time" has no members. The plan does not say what `knowledge_propose`'s schema is then (tool left out, open string, empty enum), or what the default snapshot in task 17 contains.
- F-12 · Major · Task 3/4 (`knowledge write --pinned` and `--unpin`) · The CLI parser (src/cli/commands/knowledge.ts:69-85) treats every option as taking a value ("`--pinned` needs a value"). The plan does not say whether these are value-less flags, or how the parser changes. It also does not say what a person's write without either flag does to an existing entry's `pinned`: keep it or reset it to false.
- F-13 · Major · Task 3 (`parseProposal` with `contradicts: [workspace/a, shared/b]`) · Part 1's frontmatter reader supports only block lists (`- item` lines after an empty key, entry.ts:144-160). A flow list `[a, b]` parses as one scalar string. The plan does not say whether `contradicts` is written as a block list or whether the parser gains flow syntax, so the round-trip test can be read either way.
- F-14 · Major · Signatures `knowledgeStatus(db, now)` and Task 18 ("with the setting `memory` gives `on: false`") · The signature takes no settings or env, so it cannot tell whether the module is on. The plan also gives no text for the `status` line, and does not say when the function returns `null`.
- F-15 · Major · Signatures `src/store/compact.ts` and Task 18/19 · `CompactReport` (compact.ts:18-25) has no field for pruned `knowledge_shown` rows. The CLI that prints the report, src/cli/commands/compact.ts:25-29, is not in Scope or any task. The plan does not name the field or the output text. It also does not say how `--dry-run` counts rows "whose session is gone" when the dry run deletes no sessions: does the count include rows of sessions that would be removed?
- F-16 · Major · Task 18 (`rebuildAll` deletes a gone repository's shown rows) and Task 19 · Task 19 modifies only status, doctor and compact, but the deletion lives in `src/modules/knowledge/index-store.ts` `rebuildAll` (lines 608-617). There is also a second path that drops a repository's rows: `saveRow` when a repository moves (resolve.ts:66-78). The plan says nothing about shown rows or the `knowledge.stale:<old path>` mark on that path.
- F-17 · Major · Signatures `refreshKnowledgeSafely` and the tools' `ensureFresh` · `ensureFresh` takes no lease (index-store.ts:623-632); the CLI wraps it in `withRepoLeases` and tolerates `locked` (knowledge.ts:278-283), and `rebuildAll` does the same. The plan does not say whether the drain and the tools take the repository lease, or what happens to a stale mark when the lease is held elsewhere (kept, cleared or logged). The drain's "folder gone" case also needs `rebuildAll`'s guard for an absent knowledge root (index-store.ts:597-604), which the plan does not mention.
- F-18 · Major · Task 7 (`knowledge_repos` queried once; spec: "one count, cached for the process") · The plan does not say what the cache is keyed by. One test process runs many worlds (different databases). A cache for the whole process keeps "no repository" from the first world and silences the module in every later one; per-database caching is a different design.
- F-19 · Major · Signatures `getKnowledge` and Task 15 · The answer is "the heading line, then `id`, `version`, `hash`, `author`, `updated`, `pinned`, then the body", but the line format of those fields (`key: value`, one per line, blank line before the body), the clip note's wording and the separator between refs are not given, though the plan calls the answer shapes fixed.

The plan also does not say what is recorded when the contradicted neighbour is an open proposal rather than an entry.
