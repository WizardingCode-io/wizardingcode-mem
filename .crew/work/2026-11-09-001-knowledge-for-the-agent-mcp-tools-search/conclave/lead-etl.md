## Returns
- R-1 · .crew/work/2026-11-09-001-knowledge-for-the-agent-mcp-tools-search/spec.md:89 · Name how the triggers find and delete an FTS row, and bound the cost. The spec says `(repo_id, id)` has no stable rowid, so `knowledge_fts` is self-contained and `repo_id` and `entry_id` are `UNINDEXED`. FTS5 can only delete by rowid or by MATCH, so a trigger's `DELETE … WHERE repo_id=? AND entry_id=?` scans the whole table, which holds every repository's entries. Part 1's `rebuildRepo` replaces a repository's rows in one `withWrite` (part 1 spec.md:251). A 2,000-entry rebuild therefore fires about 2,000 full scans of a 6,000-row table inside the write lock, and the drain runs it (spec.md:108). Neither the spec nor plan.md:40 says how the delete is keyed. Task 20 (plan.md:72) times only hook latency, never a rebuild or a trigger delete. Change: state the delete mechanism (for example, make `entry_id` and `repo_id` searchable columns and delete by `MATCH`, or keep an explicit rowid map), and add an AC-12 case that times `rebuildRepo` on the 3 × 2,000 corpus, with a budget, so the lock is shown to be short.
- R-2 · .crew/work/2026-11-09-001-knowledge-for-the-agent-mcp-tools-search/spec.md:106 and plan.md:72 · The prompt query must confine the search to the visible repositories inside the index, and the perf corpus must be able to show whether it does. As written, `repo_id` is `UNINDEXED` (spec.md:89), so `repo_id IN (visible)` filters only after FTS has matched and ranked the entries of every project's repository. Memory hit exactly this cost: `src/store/migrations/0002_fts_project.sql:1-4` made `project_id` a searchable column because the prompt hook "took over 100 ms" with other projects' memories. `src/retrieve/prompt.ts:127` now uses `project_id : (…)` inside MATCH. The perf corpus (spec.md:172, plan.md:72) is three repositories, all visible, so it cannot catch the regression. Change: either index `repo_id` and query it inside MATCH (this also helps R-1), or bound the prefetch as `prompt.ts` does. Add to the corpus non-visible project repositories, for example 30 other projects with 200 entries each, sharing common words with the measured prompts, and keep the 80 ms and 150 ms budgets with them present.
- R-3 · .crew/work/2026-11-09-001-knowledge-for-the-agent-mcp-tools-search/spec.md:108 and :188 · The stale mark is a write on the hook path, and the spec does not say so. The hook "sets `meta` `knowledge.stale:<path>`" whenever head or fingerprint differ, but the NFR on the hook path (spec.md:188) lists only reads. Migration 7 clears every `head` and `fingerprint` (spec.md:89), so every repository differs on the first hook after the upgrade and on every hook until the drain rebuilds. Change: state that the mark is read first and written only when absent (never one write per prompt), that the write is fail-open under `busy_timeout`, and that the write is counted in the AC-5 hook case and in the NFR. Say how the drain behaves with `WIZARDINGCODE_MEM_DISTILL=off` or no key, since pinned entries stay at `pinned = 0` until some rebuild runs (the tools' `ensureFresh` also covers this).
- R-4 · .crew/work/2026-11-09-001-knowledge-for-the-agent-mcp-tools-search/spec.md:89 and :142 (plan.md:27) · `knowledge_shown` has no foreign keys and `compact` prunes only "rows of the sessions it removes". That leaves a stale-key hazard. `sessions.id` is a plain `INTEGER PRIMARY KEY` with no AUTOINCREMENT (`src/store/migrations/0001_init.sql:20`), and `knowledge_repos.id` is the same kind of key (part 1 spec.md:245). SQLite can reuse the id of a deleted highest row. A new session or repository then inherits old `knowledge_shown` rows and silently suppresses entries as "already shown". An FK cascade (memory's `injections` has one) is rejected on purpose by the spec. Change: define the prune as orphan-based, run in the same `withWrite` after the session delete, as `DELETE FROM knowledge_shown WHERE session_id NOT IN (SELECT id FROM sessions) OR repo_id NOT IN (SELECT id FROM knowledge_repos)`. Have `rebuildAll` or the repository-row deletion also clear the shown rows of a repository it deletes. Make `--dry-run` count these rows without deleting them, and extend the plan.md:67 cases to cover id reuse and the dry-run.

## Notes
- Migration 7 is sound in its shape. It follows 6 in the same module namespace, uses `ALTER … ADD COLUMN` with defaults, and creates `knowledge_fts` and `knowledge_shown` only after migration 6 has dropped any withdrawn-module tables of those names (part 1 spec.md:243). The upgrade runner takes a backup first (part 1 spec.md:238), and DDL rolls back with the runner's transaction. The triggers sit on a module table, never on a core table, so core migrations that rebuild core tables do not touch them (spec.md:89, conclave.md:10).
- Rollback is stated and coherent. Parts 1 to 3 ship in one release, 0.6.0 ignores the tables, and `ModuleSchemaTooNewError` is the guard for a binary older than the recorded version.
- Triggers keep the index in step for every writer (spec.md:155). They fire on foreign-key cascade deletes as well, and `PRAGMA foreign_keys = ON` is set at `src/store/db.ts:170`. The AC-2 trigger transitions (insert, update to draft, delete, a `problem` row) are tested in plan.md:40.
- `UPDATE knowledge_repos SET head = NULL, fingerprint = NULL` correctly forces the next `ensureFresh` to parse every file and fill `pinned`. The re-fill goes through the same triggers, which makes the cost in R-1 real at that point.
- The `knowledge_shown` primary key (session, epoch, repo, entry) is covered by the anti-join in the prompt query, and the added `(repo_id, entry_id)` index serves the status and doctor counts. The module answers null with one cached count when `knowledge_repos` is empty (spec.md:93), so a store with no knowledge pays nothing.
- The old module's index ruling in `docs/adr/0020-knowledge.md:62` (self-contained FTS5, triggers, deletes "confined to its project") is the precedent for the approach. This spec drops the confinement, which is what R-1 and R-2 ask it to restore.
- `doctor`'s FTS-count versus active-entries check (spec.md:141) is a good trigger-gap detector, and its repair path (`knowledge rebuild`) is named.
