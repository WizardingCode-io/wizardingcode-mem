## Findings
- F-1 · defect · src/store/compact.ts:113 · `compact` counts and deletes `knowledge_shown` rows (the DELETE is at line 124). The only test it runs first is `hasShownTables` (line 50), whether the tables exist; it never checks the module's schema version. The base says (CLAUDE.md, knowledge paragraph) that `schema.ts` is "the leaf with `requireSchema`, which everything that reads or writes the tables calls". ADR 0024 part 1 adds that the store refuses to read or write when the version is too new (`ModuleSchemaTooNewError`), and `openDb` leaves such tables alone on purpose. So a binary at knowledge version 7, run against a store that a newer version left at 8, would delete rows from a table whose shape and meaning it does not know. The knowledge parts of `contribute` (`moduleSchemaState`), the tools (`requireSchema`) and `doctor` (its `too-new` branch) all follow the rule; `compact` is the one writer that does not. Rubric question 2 (data model) and question 1 (a boundary the base draws). Fix: skip the prune and report 0 when `moduleSchemaState(db, KNOWLEDGE_MODULE, KNOWLEDGE_SCHEMA_VERSION) !== "current"`, the same gate `contribute` uses; `compact` has no `KnowledgeStore`, so it cannot call `requireSchema` itself.
- F-2 · advisory · src/status/report.ts:192 · `knowledgeStatus` reads `knowledge_entries.pinned` and `knowledge_shown` after checking only that the tables exist (line 186), never the module's version, so a too-new knowledge schema could make `status` throw or misread. It should be gated by `moduleSchemaState` like `doctor`'s branch; its SQL would also sit better beside `ftsCount` in `index-store.ts` than in the status layer.
- F-3 · advisory · src/modules/knowledge/contribute.ts:11 · The hook path gets its three read queries (`pinnedEntries`, `searchEntries`, `shownKey`) from `index-store.ts`, which statically imports `repo.ts` (the git runner and `openRepo`), `resolve.ts` and, through `author.ts`, more of the store. Since `engine/modules.ts` now imports `knowledge/index.ts` statically, every hook process loads the store's whole write side. Nothing runs at load time, so this breaks no stated rule, but it goes against the spirit of "the hook path reads the database and nothing else" and "no heavy import on the hook path". Moving the hook's read queries into a leaf with no dependency on `repo.ts` would keep the boundary visible.
- F-4 · advisory · src/mcp/agent-id.ts:4 · The MCP transport now imports a module's code by name (`AGENT_ID` from `modules/knowledge/entry.ts`), and `mcp --agent` is checked against knowledge's pattern even when knowledge is off. The Design names `AGENT_ID` as the check, so this does not depart from the spec. It does run against ADR 0019's rule that the server asks the modules and never one of them by name; an engine-level agent-id pattern that knowledge's `entry.ts` imports would keep the dependency pointing the base's way.
- F-5 · advisory · src/modules/knowledge/tools.ts:105 · `rootAreas` repeats part 1's `taxonomyFor` (`repo.ts:712`) line for line: `kindAt`, `readRegularFile`, `parseTaxonomy`. The only difference is that it needs no store, which the Design requires because listing opens no database. Two copies of the rule for reading a taxonomy can drift; a store-less `taxonomyAt(dataDir, root)` that both call would keep one copy.
- F-6 · advisory · src/retrieve/render.ts:99 · `KNOWLEDGE_LINE` copies the two intro sentences, the count line and the kind list as regex literals, independent of `INTRO`, `PROMPT_INTRO` and `pinnedCountLine` in `contribute.ts`. If that wording changes, `withoutNotes` silently stops stripping echoed knowledge lines. The direction is right (retrieve should not import module code), so the fix is a test that pins `contribute.ts`'s constants against `withoutNotes`.
- F-7 · advisory · src/modules/knowledge/tools.ts:63 · `KINDS` is declared again as a list, beside `entry.ts`'s `KINDS` regex. The OpenCode plugin and `render.ts` each carry a third copy. `entry.ts` is "the formats", so the list should come from there.

## Outside the change
- CLAUDE.md:12 · The knowledge paragraph says `doctor` "is the one reader that does not go through `openRepo`". Part 1's `taxonomyFor` already read taxonomy files directly, and this item's `rootAreas` and `propose`'s area check add more such readers. The sentence predates this diff and no longer describes the code. Debt: say which readers go around `openRepo` and why (reading a file runs no git).
