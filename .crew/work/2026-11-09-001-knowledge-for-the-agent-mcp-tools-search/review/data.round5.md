## Findings
- F-1 · advisory · src/modules/knowledge/contribute.ts:176 · On a prompt, `searchEntries` runs inside the hook's `withWrite` (BEGIN IMMEDIATE). Its `f.repo_id IN (…)` (index-store.ts:1050) filters on an UNINDEXED FTS column after the MATCH, so bm25 is scored over every repository's matching rows, the non-visible ones included. The time the write lock is held therefore grows with the whole knowledge corpus. It is measured inside the prompt budget (3×2,000 visible, 30×200 non-visible), so it is a cost to watch, not a loss (Q2, Q6). Unchanged since round four.
- F-2 · advisory · src/modules/knowledge/index-store.ts:963 · At every session start, inside the write transaction, `pinnedEntries` reads every entry row of the visible repositories through the primary key's `repo_id` prefix to find the few rows with `pinned = 1`. A partial index on `knowledge_entries(repo_id) WHERE pinned = 1` would read only the pins. Measured within budget at 3×2,000 entries with 10 pins each (Q2). Unchanged since round four.
- F-3 · advisory · src/modules/knowledge/propose.ts:47 · Nothing ever deletes the `meta` rows `knowledge.rate:<agent id>`, and any id that matches the pattern creates one, so their number has no fixed bound. Each row is small and holds no personal data (Q6, growth). Round four cited this at line 87; the write is `setMeta` at line 47 in this tree.
