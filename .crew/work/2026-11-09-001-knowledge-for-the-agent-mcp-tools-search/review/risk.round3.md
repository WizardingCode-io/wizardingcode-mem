# risk findings for 2026-11-09-001-knowledge-for-the-agent-mcp-tools-search
reviewer: review-risk
read: spec, plan, 14 files

## Findings
- F-1 · advisory · .crew/work/2026-11-09-001-knowledge-for-the-agent-mcp-tools-search/spec.md:379 · The spec's rollback line still says 0.6.0 "logs an unknown module id once per hook process", but probes/rollback-to-0-6-0.md measured that 0.6.0 ignores the module rows silently and writes no log line. ADR 0024:380 was corrected and the spec was not, so the item's own words about the rollback disagree with each other.
- F-2 · advisory · .crew/work/2026-11-09-001-knowledge-for-the-agent-mcp-tools-search/spec.md:387 · The Rollout paragraph names no release-day steps or order. The committed plugins/opencode/index.js already lists the three knowledge tools while plugins/opencode/binary.js still pins VERSION 0.6.0. If the OpenCode package is published before the version bump and `bun run plugins`, or before the release binary exists, a 0.6.0 binary answers `tool knowledge_*` as an unknown tool (exit 64). The plugin turns that into an empty answer with stderr ignored, so the failure is not seen. The steps are the version bump, `bun run plugins`, then the binary release before the npm publish, and nobody is named to take them.
- F-3 · advisory · src/judge/index.ts:68 · The tools' judge uses a 3 s deadline with no retries (line 59) and shares distillation's breaker, which is persisted in `meta`. Three slow TypeSafe answers in interactive `knowledge_propose` calls therefore open the breaker for 1 to 15 minutes, and the drain then distils with the heuristic judge. This is stated in ADR 0024:358, and `doctor` shows the breaker state, so it is visible and recovers on its own. It is still a new way for a slow service to lower distillation quality.
- F-4 · advisory · src/judge/index.ts:28 · The tools' TypeSafe cost is counted under `typesafe.tools.requests` and `typesafe.tools.input_tokens`, but no `status` line or viewer shows these counters (ADR 0024:358 says so). The cost is capped at 20 calls per agent id per hour, each at most 16 questions. Since agent ids are not authenticated and every host is its own id, the only place to see the tools' spend in the first hour is a raw `meta` read.
- F-5 · advisory · src/install/opencode-plugin.ts:31 · A `knowledge_propose` killed by the 15 s plugin timeout after part 1's write has committed returns "" to the agent (line 40), so the agent cannot tell a written proposal from a failed one. A retry is caught by the open-proposal duplicate check (heuristic, same text) and costs one hourly rate slot, so nothing is written twice. The agent gets no signal, though, and the plugin logs nothing.
- F-6 · advisory · src/modules/knowledge/tools.ts:79 · `knowledge_search` and `knowledge_get` are annotated `readOnlyHint: true, idempotentHint: true`. Each call can still run `openRepo` and `ensureFresh` under a lease, which runs git and rewrites a repository's index rows (line 194; ADR 0024:316 says a tool call can write the index). The writes are derived and rebuildable, but a host that approves read-only tools without asking will run git on them.
- F-7 · advisory · docs/adr/0024-knowledge-module.md:376 · A project folder emptied by hand, or whose `.git` was deleted, keeps its last-indexed rows. Hooks keep showing them, pinned ones included at every session start, and the tools keep returning them, because `openRepo` returns null and `refreshStale` passes the folder over (index-store.ts:813-814). The limit is stated, and a rebuild or a write clears it. The ADR names no `doctor` signal for this state.

## Outside the change
- src/install/opencode-plugin.ts:36 · The bridge's `spawn` ignores stderr and returns "" for any non-zero exit or timeout, for every tool. The plugin never shows a failure, and this item adds three tools that inherit it (debt).
- src/judge/breaker.ts:101 · The breaker's state is loaded when it is constructed and saved with a plain `setMeta`, with no transaction around the read and the write. Two processes can lose each other's failure counts. This item adds tool-call processes as a second kind of writer to this shared state (debt).
- src/modules/knowledge/migrations/0006_knowledge_store.sql:7 · Migration 6 drops the withdrawn module's tables (`promoted_memories` included) and three `meta` rows, with no backup and no down path. This is part 1's migration (item 2026-11-08-003, reviewed there); it is in this diff only because this item's base predates part 1.

## Not answerable
- Rollback (Q2) · probes/rollback-to-0-6-0.md records "(no output)" for the 0.6.0 `hook session-start` against a store with 3 active memories in the same project. It explains the silent prompt (no knowledge module in 0.6.0) but not whether memory's brief was expected at session start. It is therefore not shown that memory, the main feature, still reaches the agent after a rollback rather than failing open silently. The payload's `source`, and what 0.6.0's brief needs before it prints, are missing.
- Rollback (Q2) · The probe did not run the 0.6.0 drain or the 0.6.0 `compact` against the version-7 store (the probe says so). It is unshown whether 0.6.0's compact, which deletes sessions without pruning `knowledge_shown`, leaves rows that a re-upgrade reads under a reused session id before the new `compact` runs.
