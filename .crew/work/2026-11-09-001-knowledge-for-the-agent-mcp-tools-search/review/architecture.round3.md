## Findings
- F-1 · defect · src/modules/knowledge/index-store.ts:803 (diff 5464-5470, 5502) · The drain can forget repositories in states where a rebuild refuses and forgets nothing.
  - **What the change does:** `refreshStale`/`refreshOne` forget a repository's rows (`dropRepoRows` plus the `knowledge_repos` delete) whenever `kindAt(<repo path>)` is `"absent"`. The only guard before that is `kindAt(knowledge/) === "absent"`. It never calls `refuseLinkedRoots`.
  - **What the base says:** CLAUDE.md says `refuseLinkedRoots` guards `knowledge/` and `knowledge/projects/` themselves, and that "only a name with nothing at it is gone". The spec's Design and ADR 0024 part 2 say the drain forgets a gone repository "by `rebuildAll`'s own rule". That rule runs behind `inEachRepo` → `listRepos` → `scanRepos` → `refuseLinkedRoots`, which throws before anything is forgotten.
  - **Consequence:**
    - If `knowledge/` is a file, `lstat` of every repository path fails with ENOTDIR. `unseen` reads that as "not there", so the unattended drain forgets every repository's rows.
    - If `knowledge/` or `knowledge/projects/` is a link, the drain decides presence through the link, which the store must never follow.
    - In both states `knowledge rebuild` refuses and forgets nothing.
  - **Rubric:** Q1, a rule the base keeps in one guarded place, built a second time without its guard. Q5, the Design says "by `rebuildAll`'s own rule".
  - **Fix:** in `refreshStale`, call `refuseLinkedRoots(store.dataDir)` before the loop and treat its refusal as "forget nothing, log, return 0". Better, move the forget step into one helper that both `rebuildAll` and `refreshOne` call behind that guard. Add a refresh test with `knowledge/` as a file and with `knowledge/projects` as a link. `tests/unit/knowledge-refresh.test.ts` has neither case.
- F-2 · advisory · src/modules/knowledge/tools.ts:9 · The knowledge module imports `UNKNOWN_AGENT` from the MCP transport (`src/mcp/agent-id.ts`). `agent-id.ts` in turn imports `AGENT_ID` from `modules/knowledge/entry.ts`, so a module and the transport now depend on each other. The base has the MCP server ask the modules, not the other way round, and the fallback `agent:mcp` is part of the engine's `ToolCall.agentId` contract (`module.ts`). Fix: keep the fallback id in the contract or in the module (e.g. `author.ts`) and let `src/mcp` import it.
- F-3 · advisory · src/modules/knowledge/tools.ts:107 · `rootAreas` is a second reader of a root's taxonomy file beside part 1's `taxonomyFor` (`repo.ts:712`). Only its fallback differs: defaults where `taxonomyFor` throws. Like `taxonomyFor`, it reads through a linked `knowledge/` without `refuseLinkedRoots`. A thin wrapper around `taxonomyFor` (catch → `DEFAULT_AREAS`) would keep one reader.
- F-4 · advisory · src/retrieve/render.ts:99 · `KNOWLEDGE_LINE` repeats knowledge's two intros and count line as regex literals instead of building them from `INTRO`, `PROMPT_INTRO` and `pinnedCountLine` in `contribute.ts`. If an intro changes, echoes stop being stripped and get distilled with no error. Building the pattern from the exported constants keeps one source.
- F-5 · advisory · docs/adr/0019-one-engine.md:20 · ADR 0019's contract paragraph still describes `ToolCall` as `projectDir` alone and has no `globalInstructions`. The reversal note this diff adds (line 141) names F5′ but not the two contract additions. ADR 0024 part 2 (line 228) records them. Pointing to it from the reversal note would keep the contract's own ADR complete.
