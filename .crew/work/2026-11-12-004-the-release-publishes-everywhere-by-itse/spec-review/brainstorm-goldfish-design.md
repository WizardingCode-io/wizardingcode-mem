## Findings
Lens: cost, quotas and token economics, failure modes, permissions, secret scope, races.

- F-1 · Blocker · §1 workflow_dispatch / build path · A dispatch runs on the branch it was dispatched from, so `actions/checkout`, `GITHUB_REF_NAME`, the package.json check at release.yml:25 and `docker/metadata-action`'s `type=semver` all see a branch and not the input tag. The concept lets `build/sign/docker/publish` run on a dispatch when the release does not exist yet. That is the exact repair case after a run that failed before `gh release create`. In that case the job would build the branch HEAD and publish it under the tag, or produce no semver image tag at all. Every job needs to check out `refs/tags/<tag>` and use the resolved tag, never `GITHUB_REF_NAME`, and the concept does not say so.
- F-2 · Major · §1 dispatch trigger / secret scope · npm trusted publishing checks the workflow file name, not the ref, and a dispatch runs the `release.yml` from whatever branch was picked. Anyone with write access can therefore push a branch with an edited `release.yml`, dispatch it with a real tag, and get an npm OIDC publish plus `MARKETPLACE_TOKEN`. That token writes to the tap and to the shared marketplace repo, which holds every WizardingCode plugin's `ref`. A leak lets someone repoint every plugin to any commit, so it is a supply-chain risk for all plugins, not only this one. Nothing in the concept limits this: no GitHub environment with a tags-only deployment rule bound to the npm trusted publisher, no check that the dispatch ref is the default branch, and no rule that the secret appears only in the `tap`/`marketplace` steps.
- F-3 · Major · §1 dispatch input · The `tag` input is free text. If it is put into `run:` shell as `${{ inputs.tag }}`, that is script injection. The concept gives no format check (`^v\d+\.\d+\.\d+(-[0-9A-Za-z.]+)?$`) in `plan`, and no rule that later jobs use only `plan`'s output, passed through `env:`.
- F-4 · Major · §1 `tap` · The marketplace job has a forward-only guard ("a manifest that names a newer version … is left alone"). The tap has none: "identical content is success", and anything else is written. Dispatching an old tag, or an older run finishing after a newer one, rewrites `Formula/wizardingcode-mem.rb` to the older version, and every `brew upgrade` stays on it. The tap needs the same version comparison as the marketplace job.
- F-5 · Major · §1 `npm` · `npm publish` without `--tag` moves the `latest` dist-tag to whatever version it publishes, even a lower one. Dispatching an old plain tag that was never published (npm is at 0.4.4, so backfilling 0.5.x–0.7.x is plausible) moves npm `latest` backwards for every `npx wizardingcode-mem`. "latest only ever names a plain release" is not the same as "latest never goes down", and the concept has no rule for the second.
- F-6 · Major · §1 `npm` idempotency check · `npm view <name>@<version>` for a version that does not exist usually prints nothing and exits 0. It returns E404 only when the package itself is missing. If "answering" is read as the exit code, the job reports "already published" and never publishes. The check has to be a non-empty `version` field in the output, and a unit test should hold that.
- F-7 · Major · §1 no `concurrency` group · A tag push and a dispatch, or two tags pushed close together, run in parallel, and the concept names no `concurrency:` group. Three things race. Contents-API writes to the same file fail with 409 on a stale `sha`, or win in the wrong order (see F-4). The `latest` job does read-label-then-retag, so two runs can both read 0.8.0 and the older one can retag last. Two runs can also both see "release does not exist" and both build, and the second `gh release create` fails after its image push has already overwritten the version tag with different, non-reproducible binaries. Fix: one `concurrency: release-${tag}` group without cancel, plus a global group for `tap`/`marketplace`/`latest`, or a check right before each write.
- F-8 · Major · §1 `plan` "release exists" gate · `gh release create … dist/*` creates the release and then uploads the assets. If an upload fails partway, a release exists with assets missing, possibly without `checksums.txt`. On repeat, `plan` sees "exists" and skips `build/sign/docker/publish`. The distribution jobs then fail forever on `gh release download -p checksums.txt`, and both repair paths stay stuck. The gate should be "release exists with all six assets", or the concept should name a manual repair. A draft release left behind has the same problem.
- F-9 · Major · §1 `needs` on skipped jobs · By default, GitHub skips every job that `needs` a skipped job. On a repeat, `publish` is skipped, so `npm`, `tap`, `marketplace` and `latest` would all skip silently and the run would show green. The concept's "(or its skip)" needs an explicit `if: ${{ !failure() && !cancelled() && … }}` on each job, and the shape test in `deploy-files.test.ts` should assert it.
- F-10 · Major · §1 `latest` client-first rule (D-10) · The gate tests a rise in `CONTRACT`. But the server already accepts the previous contract (`ACCEPTED_CONTRACTS = [1, 2]`, src/team/contract.ts:55), and the client handles an older server (`spokenAfterMe`), so a `CONTRACT` bump alone strands nobody. The real danger is a release where `min(ACCEPTED_CONTRACTS)` rises and the server refuses clients that have not upgraded. The gate does not test that, and it would let such a release go to `latest`. The rule is also measured against the previous plain release, not against the image `latest` holds. A hotfix one day after a contract bump therefore moves `latest` before any client could have updated, which defeats the stated purpose.
- F-11 · Major · §1 `plan` reading `CONTRACT` · `git show <tag>:src/team/contract.ts` needs full history and tags in `plan` (`fetch-depth: 0`), and the concept does not say how "the previous plain release" is found. Older tags have no `src/team/contract.ts`, so the read fails, and that blocks dispatching an old tag. The rule for a missing file or an unparseable constant (0? fail?) is not stated.
- F-12 · Major · §2 forward-only, no way back · Once a bad release is staged, nothing moves `<data dir>/bin` back. The shim, the plugins, OpenCode and `install` all refuse to downgrade, and the concept offers no `--force` or documented recovery. A broken 0.9.0 can only be escaped by publishing 0.9.1 or deleting the file by hand. That operating burden is unnamed, and there is no runbook line for it.
- F-13 · Major · §1 coupling of `latest` to npm/tap/marketplace · Until the author registers the npm trusted publishers, or while the token has expired, the server image's `latest` never moves. That holds even though the image has nothing to do with npm. A failure in one channel holds back an unrelated one with no time limit, and "the run says so" is the only signal. Operators following `latest` silently fall behind.
- F-14 · Nit · §1 `latest` permissions · The `latest` job needs `packages: write` and `npm` needs `id-token: write`, while the workflow's top-level permission is `contents: write`. Only `npm`'s permission is named. `latest` and the `MARKETPLACE_TOKEN` jobs should state their least-privilege permissions per job.
- F-15 · Nit · §1 `latest` label read · Reading `org.opencontainers.image.version` from a multi-arch index takes a per-platform config lookup. The concept does not say what happens when `latest` does not exist or has no label, which applies to images pushed before metadata-action set it.
- F-16 · Nit · §1 `token` expiry header · `github-authentication-token-expiration` is missing for a token with no expiry, and for some token types. Its absence should be defined as "no warning", not a failure. Also, an org can require approval for a fine-grained PAT, which turns it into a silent 404 or 403 on the contents API. The failure message should name that case.
- F-17 · Nit · §2 `older()` copied into the shim · The shared `older()` (plugin/wizardingcode-mem.sh:30, scripts/plugins.ts:99) orders pre-releases by plain string comparison, so `-rc.10` sorts before `-rc.9`. Copying it into a fourth place means the same bug, and the same drift risk, in four copies. A shared test vector should hold all four.
- F-18 · Nit · §2 `stageBinary` probe · The check that a staged file "does not answer `--version`" runs an unknown binary at install time. The concept gives no timeout; the shim uses 10 s. A hung or foreign binary would stall `install`.
