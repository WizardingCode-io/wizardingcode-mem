## Findings

**What this proposes.** Pushing a `v<version>` tag should publish to every channel with no hand steps. `release.yml` gets a `plan` job that decides what to run. Build, sign, Docker and the GitHub release run only if the release does not exist yet. After that, four repeatable jobs run: publish both npm packages through trusted publishing (pre-releases under `next`), render and push the Homebrew formula to the tap, bump the plugin's entry in the two marketplace manifests, and check the token. A final `latest` job moves the Docker `latest` tag, but not when the team contract went up. A partial failure is fixed by re-running the failed jobs or by a `workflow_dispatch` with the tag. Separately, the binary at `<data dir>/bin` should never move to an older version: the npm shim and `install` (the Homebrew path) leave a newer staged binary alone, as the plugin scripts already do.

**How the existing system works, per this document.** Today the workflow builds, signs, pushes the image (version tag and `latest`) and creates the GitHub release. The formula, the tap, both marketplace manifests and the release notes are then done by hand, and npm is not published at all (it is at 0.4.4, the repo at 0.8.0). Every channel stages the binary at the same path, but with different rules. The plugin script and OpenCode's `binary.js` replace it only with a newer version. The npm shim replaces it whenever the versions differ (I confirmed `npm/bin/wizardingcode-mem.js:65`). `install` always copies (I confirmed `stageBinary` has no version check). So one machine's binary can be moved back to an older version.

- F-1 · Major · §1 `npm` ("the package's version must equal the tag (else the job fails)") · This check runs only after `publish` has already created the GitHub release. If the author forgot to bump `npm/package.json` or to run `bun run plugins` for `plugins/opencode/`, the failure cannot be repaired. "Re-run failed jobs" and `workflow_dispatch` both read the same tagged commit, so they fail the same way, and the only fix is a new version. Nothing says the check should also run in `plan`, before anything is published, or what the author has to bump before tagging. The author reads "can be repeated" and expects a failed target to be fixable by repeating it, but here it is not.
- F-2 · Major · §1 `plan` / "run only when the GitHub release does not exist yet" · `gh release create … dist/*` creates the release first and then uploads the files. If the upload fails partway, a release exists without all its files or `checksums.txt`. On a repeat, `plan` sees the release, skips `publish`, and the distribution jobs fail on `gh release download`. Neither path can repair it. The document does not say what "exists" means (complete? holding `checksums.txt`?) or what the author sees and does in that case.
- F-3 · Major · §1 trigger `workflow_dispatch` with a `tag` input · Under dispatch, `GITHUB_REF_NAME` and the default checkout point at the branch, not the tag. Today's jobs use both (`publish` uses `GITHUB_REF_NAME` for the notes, the prerelease flag and the title). The document never says that every job checks out and names the tag from `plan`'s output, or that the tags are fetched so `git show <tag>:…` and the Changes list work. Someone building this would leave a dispatch that builds `main` or labels the release with the branch name.
- F-4 · Major · §1 `latest` / client-first rule · When the contract goes up, `latest` is held "until the next plain release with the same contract". A `workflow_dispatch` of the same tag compares the same two values, so it never moves `latest` either. Once clients have updated, the author has no way to move `latest` except cutting another release. The document gives no override and does not say whether that is intended. Team-server operators who pull `latest` stay behind with no signal of why.
- F-5 · Major · §1 `latest` "the run says so"; `token` "`::warning::` annotation" · The document does not say where the author sees these messages: a job summary, an annotation, the release notes, a failure. A run with a warning annotation still shows green in the Actions list and the release notification, and a green run with `latest` held looks like one that moved it. The author will miss both the token expiry and the held `latest` unless the document names the surface and the exact wording.
- F-6 · Major · §2 forward-only, Homebrew user · Agents run `<data dir>/bin`, but a person typing `wizardingcode-mem …` runs Homebrew's binary in the Cellar. A Homebrew user whose plugin staged 0.9.0 while brew still holds 0.8.0 will have `install` report "a newer version is already staged". After that, `wizardingcode-mem status` or `doctor` in their shell still runs 0.8.0 against a store the newer binary may have migrated, which gives the `SchemaTooNewError` the concept sets out to avoid. The document does not say what this user sees, or whether the `install` line tells them their PATH binary is older. The reverse is also unstated: after `brew upgrade`, agents keep running the old staged binary until the person runs `wizardingcode-mem install` again, and the formula's caveats mention `install` only for first setup.
- F-7 · Major · §2 forward-only, no way back · All channels now refuse to go back, so a person or the author can no longer return to an earlier version after a bad release, short of deleting `<data dir>/bin/wizardingcode-mem` by hand. The document neither names an escape (a flag, an environment variable, a documented `rm`) nor says that none is intended. A support case for a broken 0.9.0 then has no documented answer.
- F-8 · Nit · §2 npm shim · With a newer binary staged, `npx wizardingcode-mem@0.7.0 --version` silently prints the newer version. `install` gets a one-line notice, but the shim gets none. A person who pinned a version is not told why they got another one.
- F-9 · Nit · §1 `latest` "the previous plain release's" `CONTRACT` · "Previous" is not defined: the previous tag by semver, `git describe` from the tag, or the release that `latest` currently names. For a dispatch of an old tag, each reading gives a different answer.
- F-10 · Nit · Where this comes from / §1 / What the author does once · D-8, D-9 and D-10, "the six lenses" and "the brief's goals 1 and 2" are cited but not explained in the document. A reader without `.crew/decisions.json` cannot tell what was decided. "Plain release" is defined only in passing (no hyphen in the tag).
- F-11 · Nit · §1 `tap` · `packaging/homebrew/wizardingcode-mem.rb.template` does not exist yet; the repository has only the rendered `.rb`. The document should say the template is new and derived from the current file. Also unstated: what the author loses by deleting the in-repo copy, which is the only place a formula change is reviewed in a PR today.
- F-12 · Nit · What the author does once · The setup names "the two repositories" without naming them (the tap and `wizardingcode-plugins`). It does not say how the author finds out setup is missing on the first release. Distribution jobs fail red while the GitHub release succeeds, and the message for a missing npm trusted publisher is npm's own and is not described.
