Lens: contrarian and code minimisation. The problem is real and needed now: npm sits at 0.4.4 while the repository is at 0.8.0, and the shim's `!==` check moves the binary back. The claims about the code hold up. `npm/bin/wizardingcode-mem.js:65` replaces the binary whenever the versions differ. `stageBinary` copies with no version check. `older()` exists in the plugin template and in `scripts/templates/wizardingcode-mem.sh`. The findings below are about where the concept builds more than it needs, or misses something.

## Findings
- F-1 · Major · Hypothesis 1, `latest` job and the client-first rule (D-10) · Nothing in the repository reads the `latest` image tag. `compose.yml:6` requires `${WIZARDINGCODE_MEM_VERSION:?…}`, `.env.example` pins `0.8.0`, and the runbook tells the operator to set the tag. The `latest` job adds a lot for a tag nobody pulls: a retag that waits on npm, tap and marketplace, a never-lower check through the OCI version label, and a CONTRACT comparison read with `git show <tag>:src/team/contract.ts`. Also, `ACCEPTED_CONTRACTS = [1, 2]` ("the current one and the one before it", contract.ts:55) already lets a server one contract ahead serve the clients that lag. The only consumer this design serves is piece 3 (the server upgrading itself), which is out of bounds. Simpler for piece 1: either keep metadata-action's existing `latest` rule as it is, or stop pushing `latest` at all. Design the gate in piece 3, where its consumer and its real compatibility need can be seen.
- F-2 · Major · Hypothesis 1, single file with a `plan` job gating everything · The concept says the graph must live in one file because of npm trusted publishing. That forces gating inside the file: build, sign, docker and publish are skipped when the release exists, and the four distribution jobs "need `publish` (or its skip)". In GitHub Actions, a job whose `needs` was skipped is itself skipped unless every one of them carries `if: ${{ !cancelled() && (needs.publish.result == 'success' || needs.publish.result == 'skipped') }}`. That is a known footgun, and the concept does not name it, so a builder will wire it naively and the repeat path will silently do nothing. A smaller shape meets the same constraint. Put npm, tap, marketplace and token in one `distribute.yml` with only a `workflow_dispatch: tag` trigger, and register that file as the trusted publisher. Leave `release.yml` as it is, ending with `gh workflow run distribute.yml -f tag=…` (needs `actions: write`; a release created by GITHUB_TOKEN would not fire a `release:` trigger). This drops the "release exists" probe and the skip propagation, and a repeat becomes one dispatch.
- F-3 · Major · Hypothesis 2, `<data dir>/bin` only moves forward · The concept lists the writers to `<data dir>/bin` as plugin script, OpenCode, npm shim and `install`. It misses `scripts/install.sh`, which runs `mv -f "$tmp" "$bin/wizardingcode-mem"` unconditionally (line 64). It fetches `latest` or a pinned `WIZARDINGCODE_MEM_VERSION`, and `--download-only` stops there. A curl install with a pinned older version, or `latest` over a staged pre-release, still moves the binary back, so the "only moves forward" goal is not met. Either add install.sh to the rule (it already runs `--version` on the new file and could do so on the old one) or state why it is exempt.
- F-4 · Major · Hypothesis 2, "`older()`, the same rule… copied into the shim" and `stageBinary` · The code already has a version-order rule: `Bun.semver.order` in `src/store/meta.ts:158` (the sync lease's newer-version takeover). `stageBinary` and the TS compare in `scripts/release/` should reuse it rather than add a third or fourth hand-written compare. The two rules also disagree. `older()` compares pre-releases as plain strings (`have < wanted`), so it orders `0.9.0-rc.10` before `0.9.0-rc.9`, while semver orders rc.9 first. Two writers judging "newer" differently can hand the binary back and forth between them. Pick one rule: the JS and shell copies should match semver's pre-release order, or the concept should state that pre-releases are never staged by two channels at once.
- F-5 · Nit · Hypothesis 1, `token` step and its expiry warning (D-9) · A GitHub App installation token (`actions/create-github-app-token`) covering the two repositories never expires. It would remove the expiry-header read, the 30-day warning and the yearly rotation. D-9 chose to keep the PAT, so this is noted only as the ready-made option that removes this step entirely.
- F-6 · Nit · Hypothesis 1, `tap` and `marketplace` through the contents API · Checking out the other repository with `actions/checkout` (`repository:`, `token:`) and running `git commit`/`git push` only when `git diff --quiet` fails is the ecosystem's standard pattern. It gives "identical content is success with no commit" for free. The contents API path has to handle the blob SHA, base64 and the no-change comparison by hand. Ready-made formula bumpers (mislav/bump-homebrew-formula-action, dawidd6/action-homebrew-bump-formula) do not fit a formula with four `on_*` url/sha256 blocks well, so rendering a template is reasonable.
- F-7 · Nit · Hypothesis 1, `scripts/release/` as tested pure functions · Rendering four checksums into a template and setting two JSON keys are each a few lines. A module per concern with unit tests, plus a "never move the marketplace back" guard, is more structure than the job needs. The newer-than-tag guard is only reachable through a manual dispatch of an old tag. Refusing a dispatch for any tag that is not the highest plain release would cover that guard and the `latest` never-lower check (F-1) in one place.
