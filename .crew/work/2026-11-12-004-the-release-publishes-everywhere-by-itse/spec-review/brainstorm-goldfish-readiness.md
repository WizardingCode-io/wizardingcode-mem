# readiness findings for 2026-11-12-004-the-release-publishes-everywhere-by-itse
reviewer: goldfish-readiness
read: .crew/work/2026-11-12-004-the-release-publishes-everywhere-by-itse/probes/concept.md (whole); .github/workflows/release.yml; npm/bin/wizardingcode-mem.js; npm/package.json; src/install/binary.ts; src/team/contract.ts; plugins/opencode/binary.js; plugin/wizardingcode-mem.sh (the version lines); packaging/homebrew/wizardingcode-mem.rb; tests/integration/plugin-script.test.ts (lines 140-170); grep of tests/, scripts/, docs/runbooks/, docs/adr/ for release, latest and homebrew references
lens: migration and backward compatibility (migration and rollback)

## Findings
- F-1 · Major · §1 `npm` job, repeat path · Only the marketplace and `latest` get a "never move back" rule. `npm publish` without `--tag` sets npm's `latest` dist-tag to whatever version it publishes. npm holds only 0.4.4, so `npm view` for any older tag finds nothing. Repeating an old tag (for example a v0.8.0 backfill after v0.9.0 is out) therefore publishes it and moves npm `latest` back. The concept needs a rule for this: compare with the current dist-tag and use `--tag` or skip.
- F-2 · Major · §1 `tap` · The tap has no forward-only check either. Repeating an older plain tag renders the older formula, and "identical content is success" does not cover a different, lower version, so the job commits it and moves Homebrew users back.
- F-3 · Major · §1 repeat via `workflow_dispatch` · A dispatch runs `release.yml` from the branch it is started on, not from the tag. The concept never says which tree each job checks out. `scripts/release/*.ts` exists only on new refs. The npm package contents and the "version must equal the tag" check must come from the tag's tree. `git show <tag>:…` needs the tag fetched. The engineer has to choose a checkout ref for each job.
- F-4 · Major · First npm publish / migration from the hand procedure · Repeating v0.8.0 (or any tag cut before §2 lands) publishes the old shim from that tag's tree. That shim replaces the staged binary whenever the versions differ (`npm/bin/wizardingcode-mem.js:65`), so the backfill spreads the downgrade bug this item fixes. The concept should name the first version allowed onto npm and forbid backfilling older ones.
- F-5 · Major · §2 forward-only, existing installs · The forward-only rule only covers shims published after this item. Machines that already have the 0.4.4 shim (installed globally or in the npx cache) keep moving `<data dir>/bin` back, down to a binary older than the store's schema. The concept presents the problem as solved. It should say this residual risk remains and what, if anything, mitigates it (for example a `doctor` warning).
- F-6 · Major · Rollback of a bad release · No rollback path is defined, and three rules block the obvious one. `<data dir>/bin` never moves back, the marketplace never moves back, and `latest` never moves lower. npm versions cannot be reused, and unpublish works only within 72 h. A broken 0.9.0 that still answers `--version` stays on every machine. The concept must state that a bad release is fixed by rolling forward (0.9.1), and how a person or operator downgrades by hand: deleting the staged binary, a manual `imagetools` retag, a manual manifest or tap revert.
- F-7 · Major · §2 `stageBinary`, deliberate downgrade · `brew install` of an older formula followed by `wizardingcode-mem install` now leaves the newer staged binary in place, and nothing lets a person override that. Whether to add an override (a `--force` flag, an environment variable) is left to the engineer.
- F-8 · Major · §2 `stageBinary`, equal versions and how versions are read · The concept does not say what happens when the source and the staged binary have the same version. That case covers a local `bun run build` at the version in package.json, which today always replaces the staged binary. It also does not say how `stageBinary` learns either version: the source's own constant or spawning `--version`, with what timeout for a staged file that hangs, and on Windows. Each of these is a design choice left to the engineer.
- F-9 · Major · §1 `plan`, a release that exists but is partial · `gh release create` creates the release and then uploads the assets. If the upload fails partway, the release exists without every binary or without `checksums.txt`. A repeat then skips `build`/`publish`, and the distribution jobs fail on every attempt. The concept gives no way out, such as an asset completeness check in `plan` or an instruction to delete the release and re-tag.
- F-10 · Major · §1 `plan`, the contract rule on old tags · The concept does not define "the previous plain release": the semver predecessor among tags, or `git describe` ancestry? The two differ when an old tag is repeated. It also does not say what happens when `src/team/contract.ts` is missing at that tag (releases before the team server). `plan` also needs the full history fetched, which the concept says only for `publish`.
- F-11 · Major · §1 `latest`, a hold with no way to release it · When the contract rule holds `latest`, only a later plain release with the same contract moves it. Repeating the held tag gives the same comparison, so it stays held. If no further release comes, operators who pull `latest` stay on the old server indefinitely, and the concept offers no manual release of the hold.
- F-12 · Major · docs/runbooks/team-server.md line 9, tests/unit/deploy-files.test.ts line 166 · The runbook says `latest` moves with every plain release, and the test pins `type=raw,value=latest,enable=…` in `docker`. Both change with this item: `latest` now moves last, after npm, the tap and the marketplace, and may be held. The concept does not list the runbook update, so operators would not know `latest` can lag.
- F-13 · Major · §1 concurrency · No `concurrency:` group is specified. Two runs for one tag (a push and a dispatch, or "re-run failed jobs" alongside a dispatch) or two quick tags race on the contents-API writes (a stale `sha` gives 409) and on the `latest` retag's read-compare-write. The engineer has to pick a grouping key and decide whether to cancel or queue.
- F-14 · Major · §1 `marketplace` · The concept says both manifests get `version` and `ref`, but the problem statement says `.agents/plugins/marketplace.json` carries only `source.ref`. The engineer must decide whether to add a `version` key to Codex's manifest, which risks its schema, and what "a manifest that names a newer version" means for a manifest that has no version: comparing refs as tags?
- F-15 · Major · What cannot be tested before a real tag · npm trusted publishing over OIDC, contents-API writes with `MARKETPLACE_TOKEN`, the `github-authentication-token-expiration` header, and the `imagetools create` retag are first exercised by a real plain release on the production channels. No rehearsal is planned: a pre-release tag skips tap, marketplace and `latest`, and the npm `next` publish it does make is permanent. The concept should name a rehearsal, for example a dry-run input or a scratch tap and marketplace.
- F-16 · Major · §1 `tap`, deleting `packaging/homebrew/wizardingcode-mem.rb` · Once the tap holds the only rendered formula, any hand edit made in the tap (a `livecheck`, a fix) is silently overwritten by the next render. The first render from the new template also has to match what the tap holds now, or repeating 0.8.0 produces a commit. The concept should say whether drift in the tap is detected or reported.
- F-17 · Nit · §1 `docker`, a repeat before the release exists · If `publish` fails after `docker` has pushed, a repeat rebuilds and pushes the same version tag again, possibly with a different digest. The version tag is mutable in that window. Worth stating.
- F-18 · Nit · §1 `latest`, the first run · The concept does not say what happens when `latest` is missing or its image has no `org.opencontainers.image.version` label (an image pushed by hand).
- F-19 · Nit · §1 `token` · The expiry warning appears only on release runs. A token that expires during a quiet month gives no warning until a release fails. Acceptable under D-9, but worth stating.
- F-20 · Nit · Undoing a bad target write · After a hand revert of a manifest or the tap, "re-run failed jobs" on the bad tag's old run re-applies the write, because the forward-only check sees the reverted version as older. The rollback note should say not to re-run.

## Not answerable
- The current contents of the tap's `Formula/wizardingcode-mem.rb` and of the two marketplace manifests · they live in other repositories outside the allowed path, so F-14 and F-16 rest on the concept's description of them.
- npm's trusted-publisher constraints (whether a registration is bound to the triggering ref or event) and whether `npm publish` of a pre-release fails without `--tag` on npm ≥ 11.5.1 · these are external registry behaviours I could not check from the repository.
