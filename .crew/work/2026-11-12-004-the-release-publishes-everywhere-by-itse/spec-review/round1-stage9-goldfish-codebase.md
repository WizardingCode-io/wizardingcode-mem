## Findings
- F-1 · Blocker · Phase 1, steps 4 and 6 · Step 4 makes `OLDER_JS` start with its doc comment line, but step 6's test compares `OLDER_JS` with "the text of `function older(` up to its closing `}`" in `npm/bin/wizardingcode-mem.js`. That cut leaves out the comment, so the two can never be equal byte for byte. Step 6's test and AC-18 cannot pass as written. The cut needs to include the comment line, or `OLDER_JS` needs to drop it.
- F-2 · Blocker · Phase 5, step 31, jobs `tap` and `marketplace` · The `token.ts` step is listed with no `env:`, and only the `push.ts` step gets `MARKETPLACE_TOKEN: ${{ secrets.MARKETPLACE_TOKEN }}`. Step 26 has `token.ts` read `MARKETPLACE_TOKEN` from the environment, and step 22 maps a missing token to an error. Built as written, both jobs fail on every real run with "the secret MARKETPLACE_TOKEN is not set". Step 30's test does not catch this, because it only limits where the secret may appear.
- F-3 · Major · Phase 1, step 2 · The test is told to import `older` from `plugins/opencode/binary.js`. tsconfig.json has `strict: true` and no `allowJs`, and includes `tests`. A static import of an untyped `.js` file is a TS7016 implicit-any error, so `bun run typecheck` fails. The existing tests (tests/unit/opencode-plugin.test.ts:60, tests/integration/plugins-packaging.test.ts:60) load that package by dynamic `import(path)` with a cast. The plan should say to do the same.
- F-4 · Major · Phase 1, step 2 (`shellOlderBlock`) · The plan says the block is cut "between the line `# True when version $1 is missing or older than $2.`". That exact line never exists: today it continues with ` A pre-release is older than its release,` (scripts/templates/wizardingcode-mem.sh:21), and step 5 changes the rest of the line again. Neither "between" (start included or not) nor "the line" (exact match or prefix) is defined. An exact-match helper finds nothing. Step 7 needs the comment lines inside the block, so the helper must match by prefix and include that line.
- F-5 · Major · Phase 1, step 4 (`OLDER_JS`) · Behaviour for a `have` that is not a version is not defined. stageBinary checks `isVersion`, but the npm shim (`installedVersion()` returns any trimmed stdout, npm/bin/wizardingcode-mem.js:31-38) and the shell `installed()` do not. With the rules as written, a staged binary that prints junk gives NaN comparisons and falls through to "not older". The shim then never downloads, and it prints "running <junk> already in …". The plan must state what a non-version `have` gives (older, i.e. replace, to match AC-20).
- F-6 · Major · Phase 1, steps 4 and 7 · `npm/bin/` is under `biome check` (biome.json excludes `plugins` and `tests/fixtures`, not `npm`), and the shim must hold `OLDER_JS` byte for byte. The plan does not require `OLDER_JS` to be biome-formatted as written (line width 100, 2 spaces). If it is not, either the lint gate fails or `biome --write` breaks the byte equality of AC-18.
- F-7 · Major · Phase 2, step 11 (`stageBinary`) · The plan does not say to catch a throw from `Bun.spawnSync([target, "--version"])`. A staged file that cannot be executed (mode 644, the wrong architecture giving ENOEXEC, a broken file) makes `Bun.spawnSync` throw, not return a non-zero exit. `install` then fails with an error instead of replacing the file as AC-20 requires. Both existing readers wrap the same call in try/catch (npm/bin/wizardingcode-mem.js:32-37, scripts/plugins.ts:89-96).
- F-8 · Major · Phase 3, step 23 (`commitAndPush`) · Two gaps. (1) Only the clone is said to run "with `gitEnv`". `git push`, the `git pull --rebase` and the second push to `remote` also need the auth header, which lives only in the environment, so a builder may leave it off them. (2) The bot identity is passed with `-c` on `commit` only, but `git pull --rebase` replays commits and needs a committer identity. On ubuntu-latest, and in the tests with `GIT_CONFIG_GLOBAL=/dev/null`, the retry fails with "Committer identity unknown". The plan must say every git call to `remote` gets `gitEnv`, and that the identity reaches the rebase too.
- F-9 · Major · Phase 4, steps 24 and 27 (`readEnvironment`) · The mapping from the API answers to `PlanFacts.environment` is not given: which fields of `GET …/environments/release` become `policy` (`deployment_branch_policy`, which is null for "all branches") and which become `branches` (`branch_policies[].name` and `.type` of the second call). How "404" is detected through `gh api` (it exits 1 for every HTTP error) is not given either. And there is no rule for any other failure (403, network): does it refuse, exit 1 with which sentence, or count as `exists: false`? The same gap applies to `gh release view` failing for a reason other than "not found", and to how `assets` objects become `string[]`.
- F-10 · Major · Phase 5, step 32 (`token.yml`) · Only "Create `.github/workflows/token.yml` to match" the test is given. The test does not pin the steps the spec needs: checkout and setup-bun in `door`, `bun scripts/release/door.ts` with `GH_TOKEN`/`GITHUB_REPOSITORY` in `env:`, the job output `ready` mapped from the step, and `MARKETPLACE_TOKEN: ${{ secrets.MARKETPLACE_TOKEN }}` on `check`'s `token.ts` steps. Without the last one, `check` always fails with "not set". A builder has to design these.
- F-11 · Major · Phase 6, steps 34 and 35 · The plan says `tests/unit/team-runbook.test.ts` may "pin" the `latest` sentence of team-server.md line 9, and step 35 records that it holds that sentence. The test pins no sentence: it checks cited commands, `WIZARDINGCODE_*` variables, file paths that exist, log events and back-links. The observed reason for AC-32 would state a coverage that does not exist. What the test will check is that `docs/runbooks/release.md`, if cited in backticks, exists, and that `wizardingcode-mem install --force` names a known command.
- F-12 · Nit · Phase 3, step 23 · The `commitAndPush` options signature has no `runner`, yet the test "reads the commands through an injected `runner` option defaulting to `run`". The signature and the test disagree.
- F-13 · Nit · Phase 4, step 27 · "`door.ts` … Exports `environmentReady`" contradicts "this one function in `lib.ts`". Say which file exports it.
- F-14 · Nit · Phase 2, step 13 · "`run()` calls it once after the agent checks" does not say whether staging happens before or after `detectAgents`/`found.length === 0` in the no-agent branch, or where the "A newer …" line falls relative to the Gemini lines. Staging before detection stages a binary on a machine where install then exits 1.
- F-15 · Nit · Phase 1, step 2 · `sh -c '<block>; older "$1" "$2"'` does not say to pass a `$0` placeholder before the pair. Passed as `[have, wanted]`, `have` becomes `$0` and the test calls `older wanted ""`.
- F-16 · Nit · Phase 2, step 15 · Under `set -eu`, `new="$("$tmp" --version)"` aborts the script if the download's `--version` fails. The plan does not say whether that is intended or what the person sees.
- F-17 · Nit · Phase 5, step 31 · The `env:` sources are not named: `VERSION`/`PRERELEASE`/`DRY_RUN`/`SHA`/`BY_HAND` (presumably `needs.plan.outputs.*` and `inputs.dry_run`) and `CHECKSUMS` (presumably `${{ runner.temp }}/checksums.txt`). `summary.ts` has no stated precedence when both `DRY_RUN` and `BY_HAND` are true. Where `push.ts` reads `packaging/homebrew/wizardingcode-mem.rb.template` from (main's checkout, not the tag's tree) is also unsaid.
- F-18 · Nit · Phase 4, step 24 vs spec "plan: what may be distributed" · The spec's `plan` outputs include `hold_reason`, and the plan writes `by_hand` and no `hold_reason`. The spec and the plan disagree on the output set.
