## Findings
- F-1 · Major · The door, second bullet / J-8 / refusal 4 · The ancestor check is called the second barrier, but it only stops tags on branch commits. Without the `v*` ruleset (J-8's premise), anyone with write access can put `v99.0.0` on any old commit of `main` that carries `distribute.yml`. Refusals 4 and 5 then pass. Contents write lets them create the GitHub release by hand with six assets of their choosing, so refusals 7 and 8 pass too. They then dispatch `distribute.yml` from `main`. `npm` stops at the version check, but `tap` and `marketplace` need only `plan`, so they run in parallel and write anyway. The tap gets a formula whose URLs and checksums point at the attacker's binaries. The `v99.0.0` tag also blocks every later real release through refusal 6, so J-8's "a later real v0.9.0 is still distributed" is false in this case. `plan` never checks that the tag's version equals `package.json` at the tag's commit, and never checks that the release was created by `release.yml` and not by a person. A builder would treat the ancestor check as a real second barrier when it is not.
- F-2 · Major · The writers of `<data dir>/bin`, `wizardingcode-mem install` / AC-43 · When a newer binary is kept, `install` still goes on in the older running binary. That binary opens the store: `src/install/takeover.ts:48`, `history-offer.ts:97` and `semantic-offer.ts:87` all call `openDb`. If the newer binary has already migrated the schema, the older one throws `SchemaTooNewError` part way through `install`, after the hooks have been pointed at the staged binary. The spec says nothing about this case. It does not say whether `install` should hand off to the kept binary (as `install.sh` does), skip the store steps, or stop. A builder would ship an `install` that fails half-way in exactly the mixed-version situation this item is meant to fix.
- F-3 · Major · Risks, "The first real run is the first exercise of four external calls" / The first release · The stated mitigation is a `dry_run: true` dispatch before any write, but that dispatch runs none of the four untested calls. `npm publish --dry-run` does not use trusted publishing (OIDC). `push.ts` on a dry run does not push. The retag step is skipped by its `if:`. `token.ts` checks only a GET. A green dry run therefore says nothing about whether the real run will publish. The first real dispatch is the real test, and a partial failure there is what leaves channels on different versions. The author would trust a check that cannot catch these failures.
- F-4 · Major · `token.ts` / Goal 6 · The spec takes "status 200 whose `permissions.push` is not true" as proof that the token cannot push, but gives no source. For a fine-grained personal token, nothing shown says that `permissions` on `GET /repos/{owner}/{repo}` reflects the token's own grant and not its owner's role. If it reflects the owner's role, a token granted contents read only passes the check, and the failure appears later at `git push`. That later failure does not match any `token.ts` sentence, so Goal 6 ("names a token … without access") is not met. Either cite a source or test the push right another way, for example with a dry-run push.
- F-5 · Major · `plan` refusal 6 · The rule counts tags, not tags that have a usable release. Suppose `v0.9.1` is pushed and its `release.yml` fails (a check fails, or signing fails), so it never gets a release. Every repeat of `v0.9.0` is now refused as not the highest, and `v0.9.1` is refused by refusal 7. Nothing can be distributed until an admin deletes the tag. Neither the Risks section nor the runbook contents in AC-56 name this failure or its repair. The author would miss that one broken tag blocks every repair of the previous release.
- F-6 · Major · The summary / Goal 4 / J-1 · The summary table has no outcome for a failed target. When `npm`, `tap` or `marketplace` fails, that job's reason goes to standard error only. `latest` is then implicitly skipped (implicit `success()`), and nobody writes a line for it, because `plan` writes lines only for skips and holds it caused itself. When `plan` refuses, there are no lines at all. J-1 promises one line per target, and Goal 4 promises "what each target did and why". A builder following the table would deliver summaries with missing targets on exactly the runs the author most needs to read.
- F-7 · Major · `tap` and `marketplace` · The spec never says which tree the tap job reads `packaging/homebrew/wizardingcode-mem.rb.template` from, or which tree `scripts/release/` comes from in the `tap` and `marketplace` jobs. For `npm` it is explicit: `plan`'s `sha` goes in `release/`, with `main` beside it. If the template comes from `main`, repeating an older tag renders that tag with a newer template that may not fit its binaries. The rendered formula then depends on when the job ran, not on the release. Builders will choose differently.
- F-8 · Nit · `npm`, "a publish refused because the version exists" · npm also refuses with "cannot publish over" for a version that was published and then unpublished. In that case the job reports "already published" for a version that is not on the registry.
- F-9 · Nit · Goals, 6 vs `token.ts` · Goal 6 promises a warning within 30 days of expiry. The design admits the expiry header may be absent for fine-grained tokens and then passes with "expiry unknown". The goal should be worded as conditional, as the design is.
- F-10 · Nit · Risks · The runbook (AC-56) names one limit that the Risks section omits: a third dispatch silently replaces a pending run in the `distribute` concurrency group. That can drop a tag's automatic run while a repeat is running.
- F-11 · Nit · Risks / `token.ts` · The token is a personal fine-grained token. If its owner loses access to the organisation, or the organisation revokes approval, it stops working, which makes that person a single point of failure for tap and marketplace releases. This is not named as a risk, only implied by D-9.
- F-12 · Nit · Cost and duration (Heilmeier Q7) · The phases and the setup steps are listed, but there is no estimate of how long the build will take, so Q7 is not answered.
