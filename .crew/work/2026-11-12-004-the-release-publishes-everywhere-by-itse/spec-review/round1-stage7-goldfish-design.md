## Findings
- F-1 · Major · `plan`, refusal 6 (with J-8) · The "highest version" rule is computed over all of the repository's `v*` tags, not only tags whose commit is on `main`. So the J-8 attacker's `v99.0.0` (refused by refusal 4) stays in the tag list, and from then on refusal 6 refuses every real release (`v0.9.0` is not the highest plain tag) until someone notices and deletes the tag. The same unfiltered list picks the "previous plain release" for the hold. Anyone who can push a branch can stop distribution with one tag push. A builder following the text will filter the wrong list. The spec also does not say how a `v*` tag that fails the refusal-2 regex is ordered or skipped.
- F-2 · Major · `latest` / "Never lower" / J-7 / Security NFR · "Nothing else in the repository moves `latest` once `docker` stops pushing it" is false. A tag pushed on any commit runs that commit's own `release.yml`, whose token has `packages: write`. An older commit, or a branch commit, can still carry the `docker` job that tags `latest`. Separately, a branch's own `distribute.yml` dispatched from that branch can have a job with no environment and `packages: write` that retags `latest` to any image. The environment rule guards only the marketplace token and npm. Goal 3 and J-7 leave `latest` out, but piece 3 makes servers follow `latest`, so whoever controls `latest` gets code on team hosts. The Risks section does not name this. The ruleset on `v*` tags is left optional in the runbook.
- F-3 · Major · "The door" ("the content published is then content that passed a pull request") / `tap` · The ancestor check pins the commit but not the release assets. Anyone with `contents: write` can replace assets and `checksums.txt` on an existing release (`gh release upload --clobber`) between `release.yml` and `distribute.yml`, or before a repeat. `tap` then writes the replacement checksums into the formula, and the npm shim and plugins download the replaced binaries. The claim holds for the npm package source, not for the binaries every channel actually runs. Neither immutable releases nor any check of the assets against the build is named.
- F-4 · Major · "The writers of `<data dir>/bin`" / Risks · The forward-only rule makes a bad high version permanent. A binary that answers a very high version, such as the J-8 attacker's `v99.0.0`, which becomes GitHub's "latest" release that `scripts/install.sh` downloads from `releases/latest/download`, is kept by every channel from then on, and only a person who knows to run `install --force` gets rid of it. This limit appears only as an ADR item in AC-32. It is not in Risks and has no detection: there is no doctor line, because provenance is deferred to piece 2.
- F-5 · Major · "The hold (D-2)" · The rule compares the tag's lowest accepted contract only with the contract of the immediately previous plain release. Members still on any older release are refused without a hold. Example: 0.8.0 speaks 2, 0.9.0 speaks 3 and accepts [2,3], 0.10.0 accepts [3,4]; members on 0.8.0 are refused and `latest` moves. Clients do not update themselves until piece 2, so lagging members are the normal case. J-4 and the Problem present the hold as protecting "members who have not updated" without stating this one-release limit.
- F-6 · Major · `tap` and `marketplace` / `push.ts` · The design assumes that `WizardingCode-io/homebrew-wizardingcode` and `WizardingCode-io/wizardingcode-plugins` accept a direct push, with a fine-grained PAT, to a branch the spec never names (default branch? `main`?). Nothing backs this. If either repository has a ruleset that requires pull requests or status checks, every write fails. The runbook's one-time setup does not check it, and `token.ts` probes only `GET /repos/...` (read), so it cannot detect a missing push right before the job fails.
- F-7 · Major · Goal 6 / `token.ts` / `token.yml` · Goal 6 ("cannot expire unannounced") is not met by the design. The spec itself says the expiry header may be absent, and in that case both the release run and the weekly check pass with a warning, which leaves only a note the human was asked to keep. The weekly schedule can also be disabled by GitHub after 60 days without repository activity. That is mentioned only as a runbook line, with no detection. "A failed scheduled run notifies the author" is asserted without a basis: GitHub notifies the user who last edited the cron, subject to their notification settings.
- F-8 · Major · `npm`, the repeat (J-3, Goal 2) · `npm view <name>@<version>` can briefly answer empty for a version that was just published, because of registry or CDN caching. A repeat soon after a partial failure then publishes again and gets `E403` ("cannot publish over the previously published versions"). The design maps that to the trusted-publisher hint, sending the author to the wrong repair, and the job fails, so `latest` does not move. The "already published" detection needs either a fallback that reads the publish failure itself or a stated limit.
- F-9 · Major · Heilmeier questions 6 and 7 · The spec states no cost in effort or people and no duration. It adds three workflows, about six scripts, changes to three binary writers in three languages, a template, an ADR and a runbook, and its first real run is admitted to be untested (Risks: "expected to need the runbook's repairs once"). Without a size or schedule nobody can judge whether to split this piece further. Midway checks exist only as the first release's dry run.
- F-10 · Nit · J-1 / `publish` · `git describe --tags --abbrev=0 "$tag^"` returns the nearest tag of any kind. When `v0.9.0-rc.1` exists, the Changes list for `v0.9.0` starts at the rc, not at `v0.8.0` as J-1 says.
- F-11 · Nit · Design / ACs · No job has `timeout-minutes`, so a hung `npm view`, `git` or `gh` call holds the single `distribute` concurrency group for GitHub's 6-hour default and blocks every later dispatch.
- F-12 · Nit · `marketplace` · The rule "an entry already at a higher version is left alone" is stated per entry. It does not say what happens when the two manifests disagree, for example `.claude-plugin` higher and `.agents` lower: whether one file is written, both are, or the job fails. It also does not say whether `.agents`' "version" is read from its `ref` tag.
- F-13 · Nit · npm dist-tags · After a plain release supersedes it, `next` stays on the last pre-release, which is below `latest`, and `npx wizardingcode-mem@next` then installs an older version. This is not stated.
- F-14 · Nit · J-5 / J-7 / J-8 / AC numbering · J-5 is titled "an old shim" but describes a shim that carries this item. J-8 comes before J-7. The ACs run 17 to 38 with 25, 30 and 34 missing and 36 to 38 out of order.
- F-15 · Nit · "The door" ("the workflows therefore never create the environment") · Before runbook step 2, a branch's own workflow that names `release` creates the environment with no rule. The runbook should say to check for and clear a pre-existing `release` environment, not only to create one.
