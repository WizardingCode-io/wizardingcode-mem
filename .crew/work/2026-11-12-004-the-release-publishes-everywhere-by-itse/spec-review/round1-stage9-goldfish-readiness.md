## Findings
- F-1 · Blocker · Steps 4, 6 and 7 (OLDER_JS and the shim) · Step 4 says `OLDER_JS` has "its doc comment as the first line of the string", and step 7 pastes `OLDER_JS` into the shim. Step 6 then compares the shim's text from `function older(` to its closing `}` with `OLDER_JS` byte for byte. That extract never includes the doc comment, so the test can never pass as written. The plan must say whether the extract starts at the comment or whether `OLDER_JS` leaves the comment out. That choice also decides what `export ${OLDER_JS}` produces in binary.js: `export /** … */ function older`.
- F-2 · Major · Step 23, `commitAndPush` · Only the clone is said to run "with `gitEnv`". The token reaches git only through the child's environment (nothing is kept in the clone), so a reader who follows the text runs `git push` and `git pull --rebase` without the header. Both then fail authentication against GitHub. The local bare-repository tests in `release-push.test.ts` would not catch this. The plan must say which git calls get `gitEnv` (clone, pull, push) and which do not (ls-remote).
- F-3 · Major · Step 23, retry after a refused push · The identity is given only to `git commit` (`-c user.name=… -c user.email=…`). `git pull --rebase` re-creates the commit, so it also needs a committer identity. With `GIT_CONFIG_GLOBAL=/dev/null` in the tests, and on an Actions runner with no git identity, git can fail with "unable to auto-detect email address", so the "second clone pushes first" case fails on CI. The plan also does not say what happens when `pull --rebase` itself fails (a conflict): throw `ReleaseError` with which sentence, or count it as the second refusal.
- F-4 · Major · Step 23, the marketplace `left-alone` path · `edit` has the type `(dir: string) => void`, and `commitAndPush` returns `already-at` on a clean tree. Nothing says how "either manifest is `left-alone`" reaches the outcome, or where `higher` comes from: a closure flag the command checks, a different `edit` return type, or an override after the call. Phase 4 also gives every command file a test in `release-commands.test.ts` but leaves out `push.ts`'s `import.meta.main` part, so the target and environment parsing, the tap's checksums read and this left-alone path have no test.
- F-5 · Major · Steps 30-31, `MARKETPLACE_TOKEN` in `tap` and `marketplace` · The `token.ts` step in each job is listed with no `env:`, and only the `push.ts` step gets `MARKETPLACE_TOKEN`. Built as written, `token.ts` always fails with "the secret MARKETPLACE_TOKEN is not set". Step 30 also asserts by "counting the raw occurrences" without giving the expected count (4 in distribute.yml if both steps carry it, 2 in token.yml?), so the engineer picks the number the test pins.
- F-6 · Major · Steps 24, 27 and 32, `readEnvironment` / `door.ts` / `token.yml` · The plan does not say how a 404 is detected from `gh api` (exit code plus stderr `HTTP 404`?). It also does not say what any other failure of either call does (a 403, no `GH_TOKEN`, a network error): refusal 9, a different sentence, or a throw. `door.ts` "always exits 0", so a door job that cannot read the API reports `ready=false` and the weekly check stays green for good. Step 32 builds `token.yml` "to match" without listing the steps or env of `door` (checkout, setup-bun, `GH_TOKEN: ${{ github.token }}`, the step id for `ready`) or of `check` (permissions, `MARKETPLACE_TOKEN` env).
- F-7 · Nit · Step 27, `environmentReady` · It is first "exported" by `door.ts` and then said to live "in this one function in `lib.ts`" that `decidePlan` calls. The plan should name one file. It should also say how rule 9 still tells its two sentences apart when the shared function returns a boolean.
- F-8 · Nit · Steps 24 and 31, outputs and env wiring · The spec's `plan` outputs include `hold_reason`; the plan writes `by_hand` instead and does not note the change. Several values are left unwired: the `env:` sources for `summary.ts`'s `VERSION`, `DRY_RUN` and `BY_HAND`; `TAG` for the `gh release download "$TAG"` step; and the value of `CHECKSUMS` (presumably `${{ runner.temp }}/checksums.txt`).
- F-9 · Nit · Step 31, `scripts/release/summary.ts` · It is created inside the workflow step. It is missing from the conventions' list of command files and has no test, unlike the other callers in phase 4.
- F-10 · Nit · Step 2, `shellOlderBlock` · The start marker is quoted as the line `# True when version $1 is missing or older than $2.`, but the template's line continues past it, both today and after step 5. The plan should say "the line starting with" and whether the comment lines are part of the block. Step 7's "comment lines included" suggests they are.
- F-11 · Nit · Step 4 · The text of `OLDER_JS`'s doc comment is not given, though steps 6 and 7 pin it byte for byte across three files.
- F-12 · Nit · Step 16, `planSummary(decision)` · The parameter's type is not defined: the `decidePlan` result, the `decideHold` result, or both. Nor is it said whether a pre-release that would also be held writes the held line.
- F-13 · Nit · Step 13, `run()` · "after the agent checks" does not say whether staging comes before or after the "No supported agent found" refusal in the no-agent branch. That decides whether a machine with no agent gets its binary staged.
- F-14 · Nit · Steps 19, 22 and the conventions · `release.assets` is `string[]`, but `gh release view --json assets` gives objects, and the mapping to names is not stated. `decideToken`'s `status: number | null` has no meaning given for null, and as written it would print "answered null". `run`'s `options?: { env?, cwd? }` has no types.
- F-15 · Nit · Step 15, `scripts/install.sh` · Unlike `stageBinary`, the staged output is not checked as a version before `older "$new" "$staged"`. Under `set -e`, a download that cannot run aborts at `new="$("$tmp" --version)"` with no message.
- F-16 · Nit · Step 31, the `npm` job's version gate · "the version through `env:`" cannot carry a command's output in a step's `env:`. The plan should say whether it means a previous step's output or a shell variable in the same `run`.
- F-17 · Nit · Step 24, contract read at the previous tag · Every failure of `git show <prev>:src/team/contract.ts` becomes `atPrevious: null` ("missing, not held"). The spec's fail-closed rule wants an unreadable-but-present file to hold `latest`. The plan should say how "missing" is told apart, for example `git cat-file -e` first.
