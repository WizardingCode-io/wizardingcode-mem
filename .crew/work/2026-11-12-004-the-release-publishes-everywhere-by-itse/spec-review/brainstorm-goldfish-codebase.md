## Findings
- F-1 · Major · §1 repeat path (`workflow_dispatch` with `tag`) · Every job today reads the tag from `GITHUB_REF_NAME`: build's tag check (release.yml:25), publish's `git describe` and `gh release create` (:129, :140), and docker's `metadata-action` `type=semver` (:87). Every `actions/checkout@v7` checks out the triggering ref. On a dispatch, that ref is a branch. The concept says only that `plan` resolves the tag. Unless every job checks out `ref: <plan.tag>` and takes the version from `plan`, a dispatch builds the default branch's HEAD under the tag's name, metadata-action produces no semver tag, and the npm job compares the tag with the branch's package.json. Whoever debugs that run sees a branch name in every log, not the tag. A `run-name` that shows the tag is also needed so the Actions list says which release a dispatch was repeating.
- F-2 · Major · §1 `plan`: "whether the GitHub release already exists" · `gh release create` (release.yml:140) creates the release and then uploads the assets. If the upload fails partway, a release exists with some binaries or no `checksums.txt`. Under the concept's rule, every repeat then skips build/sign/docker/publish. The distribution jobs then fail on `gh release download … checksums.txt` or on a missing name, and no repeat can repair it. `plan` needs to check that the expected assets are complete (the five binaries and `checksums.txt`) and print which ones are missing, not just whether the release exists.
- F-3 · Major · §1 "each needing `publish` (or its skip when the release exists)" · In GitHub Actions, when a needed job is skipped, the dependent job is skipped too unless its `if:` uses a status function (`!failure() && !cancelled()`). The concept states the intent but not the mechanism. If someone writes a plain `needs: publish`, the repeat path skips npm, tap, marketplace and latest, and the run still shows green. That is the hardest failure to notice, because nothing turns red. deploy-files.test.ts should hold these `if:` expressions as it holds `needs`.
- F-4 · Major · §1 "the run says so" (held `latest`, newer manifest "reported") · The concept never says where these outcomes show up. Every idempotent target ends green whether it published, found the version already there, skipped, or held `latest`, so a green run tells the operator nothing. It needs a per-target line in `$GITHUB_STEP_SUMMARY` (published / already there / skipped: pre-release / held: contract N>M / left: manifest names X) plus a `::notice::`. Otherwise a `latest` held by D-10 can stay held with no one aware of it.
- F-5 · Major · §1 `latest`, D-10 · "The next plain release with the same contract moves it" sets no deadline and does nothing on its own. Nothing in the repository or on the image records that `latest` is being held, or why. Also, docs/runbooks/team-server.md:9 says the release pushes "`latest` for a plain release". That stops being true, and the concept does not list the runbook (or tests/unit/team-runbook.test.ts) among the things that change. Operators reading the runbook would expect `latest` to be current.
- F-6 · Major · §1 `plan` reads `git show <tag>:src/team/contract.ts` · This needs the tags and history in `plan`'s checkout. The concept asks for full history only in `publish`, and today's checkouts are shallow with no tags. The concept also does not say what happens when the previous plain release's file is missing or `CONTRACT` cannot be parsed: fail, hold, or move. Whoever debugs a held or moved `latest` needs to see both values and both tags printed.
- F-7 · Major · §1 `npm` idempotency · "`npm view` answering means already published" does not separate a registry or network error from E404. If `npm view` treats an error as "not published", the job goes on to `npm publish`. That publish then fails with npm's own message: E403 for an existing version, or E404/ENEEDAUTH when the trusted publisher is not registered (the one-time setup in "What the author does once"). Those messages do not name the cause. The concept writes a named message for a missing `MARKETPLACE_TOKEN` but none for an unregistered trusted publisher, which is the most likely failure on the first run.
- F-8 · Major · §1 `tap` / `marketplace` contents API · Nothing prevents a re-run of failed jobs and a `workflow_dispatch` of the same tag from running at the same time. Both then PUT with a stale `sha` and one gets a 409. The concept has no `concurrency:` group per tag and no retry on 409, and the error a person would see is the raw API response. The job should print the repository, path, sha and HTTP status of each contents call.
- F-9 · Major · §1 `token` · The expiry warning only appears in a release run, as an annotation on a run that is otherwise green. If releases are more than 30 days apart, the first sign of expiry is a failed tap/marketplace job. The concept also does not say what happens when `github-authentication-token-expiration` is missing (a token with no expiry, or a different token type). A run should say "expiry unknown" rather than stay silent.
- F-10 · Major · §2 forward-only, `older()` copied into the shim · `older()` (plugins/opencode/binary.js:39, scripts/templates/wizardingcode-mem.sh:23) compares two pre-releases of one version as strings (`have < wanted`). It therefore ranks `0.9.0-rc.10` below `0.9.0-rc.9`, and a shim of rc.9 would replace a staged rc.10. Copying `older()` into the shim and `stageBinary` brings that backward move into the rule the concept calls forward-only. Numeric pre-release identifiers need their own rule and test.
- F-11 · Major · §2 debugging a wrong staged binary · Nothing records which channel staged `<data dir>/bin/wizardingcode-mem`, from which version, or when. The plugin script throws away every fetch failure (`fetch > /dev/null 2>&1 || true`, wizardingcode-mem.sh:66), and OpenCode's `ensureBinary` returns silently on any failure (binary.js:57-68). Under forward-only, the shim also stays silent when it defers to a newer binary. So `npx wizardingcode-mem@0.7.0 --version` prints 0.8.0 with no explanation. The concept should add a one-line stderr note when the shim defers, and a provenance record next to the binary (or a `doctor` line naming the staged version and its source). Otherwise, finding out why a machine runs a given version means guessing.
- F-12 · Major · §2 `stageBinary` asks the staged file `--version` · `stageBinary(source, dataDir)` knows neither the source's version nor how to call the staged file. The concept gives no timeout: the shim uses 10 s (npm/bin/wizardingcode-mem.js:33), and a corrupt or wrong-architecture file can hang or crash instead of failing cleanly. It also does not say whose version is compared. When the source is not the running binary (`--binary` skips staging, install.ts:232), the caller has to supply it.
- F-13 · Nit · §2 "`install` then says in one line" · `install` with no agent calls `installOne`, and therefore `stageBinary`, once for each agent it finds (install.ts:181). As described, the "newer version already staged" line would print once per agent.
- F-14 · Nit · §1 `tap` · `packaging/homebrew/wizardingcode-mem.rb.template` and `scripts/release/` do not exist today. Only the rendered `packaging/homebrew/wizardingcode-mem.rb` exists, and its header (lines 1-2) calls itself "the source it is updated from". The concept does not mark which files are to be created, modified or deleted, so a reader cannot tell the planned files from claims about the repository as it is.
- F-15 · Nit · §1 `docker` · tests/unit/deploy-files.test.ts:166 asserts the `type=raw,value=latest` line and :171 asserts `publish.needs == ["sign","docker"]`. The concept says the test "holds the workflow's shape" but does not say these assertions are changed or removed, which a reader of the test would trip over.
- F-16 · Nit · §1 `marketplace` "a manifest that names a newer version" · `.agents/plugins/marketplace.json` has only `source.ref`, with no `version`. The comparison for that file has to parse a tag out of `ref`, and the concept does not say what happens when `ref` is not a `v<semver>` tag.
