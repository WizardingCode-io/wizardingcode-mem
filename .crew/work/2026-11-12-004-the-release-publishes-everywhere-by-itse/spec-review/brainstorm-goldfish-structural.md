# structural findings for 2026-11-12-004-the-release-publishes-everywhere-by-itse
reviewer: goldfish-structural
read: .crew/work/2026-11-12-004-the-release-publishes-everywhere-by-itse/probes/concept.md (whole); checked against .github/workflows/release.yml (job list), tests/unit/deploy-files.test.ts (how it reads release.yml), scripts/plugins.ts, plugin/wizardingcode-mem.sh, plugins/opencode/binary.js, src/install/binary.ts, packaging/homebrew/ (Glob only)
lens: long-term debt and maintenance

## Findings
- F-1 · Major · §2 forward-only rule, §1 `latest` · "Is this version newer?" would be answered in at least six places in four languages. Today it exists in two: `older()` in shell (`plugin/wizardingcode-mem.sh:23`) and in JS (`scripts/plugins.ts:99`, which generates `plugins/opencode/binary.js:39`). The concept adds a hand copy in the npm shim, a TS rule in `stageBinary`, a compare in `scripts/release/`, and a compare against the image label in `latest`, which is probably shell inside the YAML. The rules already have subtle cases ("a pre-release is older than its release; of two, the one that sorts first"). If one copy drifts, that channel moves `<data dir>/bin` backwards, which is the bug this item exists to fix. Nothing proposed holds the copies equal. The risk a reader would miss is that the shim copy will not be regenerated by `bun run plugins` unless the concept says so.
- F-2 · Major · §1 job graph · `release.yml` grows from 4 jobs (build, sign, docker, publish) to about 10. Every one of them has a "skipped because the release exists" path. In GitHub Actions a job that `needs` a skipped job is itself skipped unless it uses `if: always() && …`/`!cancelled()` with explicit result checks, so each distribution job carries a compound condition. `deploy-files.test.ts` parses the YAML and checks shape (names, `needs`, conditions as strings). It cannot tell whether a skipped `publish` lets `npm` run. In two years the file is mostly conditions, and the test changes on every edit without catching a wrong one.
- F-3 · Major · §1 idempotency branches · The branches that make a repeat safe only run during a real release: "already on npm", "identical formula", "manifest names a newer version", "contract raised, `latest` held", "token under 30 days". The pure functions get unit tests, but the glue that picks the branch (`npm view` exit codes, contents-API 404/409/sha handling, the label read) has no rehearsal path, such as a dry-run input to `workflow_dispatch` or a fake tap. Untested glue in a yearly-touched file rots quietly, and the first anyone hears of it is a half-published release.
- F-4 · Major · §1 `token` · The 30-day warning appears only on a release run. If there is no release in the month before the token expires, no warning is ever shown, and the first notice is a failed `tap`/`marketplace` on the next release. That is exactly the drift D-9 meant to prevent. A one-year token is certain to hit this. A scheduled check (a `schedule:` trigger, or the existing `traffic.yml` cadence) is what would make the warning real.
- F-5 · Major · §1 `marketplace`, `tap` (a second product) · Everything is wired for one product: the `wizardingcode-mem` entry name, `Formula/wizardingcode-mem.rb`, a `MARKETPLACE_TOKEN` scoped to this repository's needs, and `scripts/release/marketplace.ts` living in this repository. A second WizardingCode product in the same marketplace and tap would copy the scripts, the template-render pattern, the token check and the version compare into its own repository. That second copy multiplies F-1, and both repositories hold write tokens to the shared marketplace and tap. The shape that scales would make the marketplace and tap repositories own their edit, for example a reusable workflow, or a `repository_dispatch` that carries name, version and checksums. The concept should at least say which way it will grow.
- F-6 · Major · §1 contents-API writes · No `concurrency:` group is named. A tag push and a `workflow_dispatch` repeat, or two products releasing (F-5), can both read a manifest's sha and commit. One then gets a 409, or with a stale read overwrites the other product's entry. "Touching no other plugin's entry" only holds if the read-modify-write is serialized or retried on a sha conflict.
- F-7 · Major · §1 contract rule (D-10) · `plan` reads `CONTRACT` by `git show <tag>:src/team/contract.ts` and parses source text. This ties the release pipeline to the file's path and to the constant's literal form. Moving the constant, deriving it, or renaming the file makes the parse fail, or worse, return a default that silently lets `latest` move. The concept should name the failure mode (fail closed: `latest` held) and the test that pins the parse to the real file.
- F-8 · Major · §1 contract rule, repeat path · A release whose contract is raised can never move `latest`, even when repeated by `workflow_dispatch`, because "previous plain release" relative to that tag never changes. `latest` waits for an unspecified future release. There is no override input for the operator who has checked the clients are ready. Over two years `latest` can sit a contract behind for months, and the only lever is cutting a release to move it.
- F-9 · Major · §2 forward-only, no way back · With every channel forward-only, a bad release (no schema bump) cannot be rolled back by publishing a fix at a lower version or by npm deprecate. Every machine that staged it keeps it until a higher version ships. The concept names no escape hatch: no `install --force`, no environment variable, no documented "delete `<data dir>/bin`" step. Without one, the first bad release turns into support work.
- F-10 · Nit · §1 `npm`, trusted publishing · npmjs.com registers the workflow file name. Splitting or renaming `release.yml` later, which is the natural fix for F-2, silently breaks publishing until it is registered again on npmjs.com for both packages. That constraint is recorded only in this concept. It belongs in a comment at the top of `release.yml` and in the test, or the next refactor will break it.
- F-11 · Nit · §1 `tap`, template · The template names exactly four checksums, and the release ships five binaries. Adding or renaming a platform touches the build matrix, `checksums.txt` parsing, the template, its test and the tap formula, with nothing tying them together. Also, a hand fix made in the tap (a `brew audit` tweak) is overwritten silently by the next render. The concept should say the tap is not edited by hand.
- F-12 · Nit · §1 `latest`, OCI label · Comparing against the `org.opencontainers.image.version` label of the current `latest` assumes every image already pushed carries that label. An image from before this change, or a label format change in the metadata action, needs a defined answer: is "no label" treated as lower, or does `latest` refuse to move?

## Not answerable
- Whether `npm/bin/wizardingcode-mem.js` is generated by `scripts/plugins.ts` or maintained by hand · not read. This decides whether the shim's `older()` copy in F-1 can be generated or must be held equal by a shared test table.
- The current `docker` job's labels and its `latest` push · release.yml was read only for its job list, so F-12 is stated as a risk, not a confirmed gap.
