## Findings
- F-1 · Nit · Plan step 19 `REQUIRED_ASSETS`, spec refusal 8 · `scripts/build.ts` already exports `TARGETS`, and its `file` fields are exactly the five binary names refusal 8 lists. The plan writes them out by hand again as a sixth list. If a build target is added or renamed later, `plan` would still accept a release that lacks the new binary, and the tap template would not notice either. Simpler: build `REQUIRED_ASSETS` from `TARGETS.map((t) => t.file)` plus `checksums.txt`. `scripts/build.ts` only uses built-ins, so importing it keeps the "Bun and Node built-ins only" rule.
- F-2 · Nit · Plan step 26 `token.ts`, spec "`token.ts`: the token's state" · This is the only release command that calls the GitHub API through raw `fetch`. It needs a new test-only base-URL variable in the product namespace (`WIZARDINGCODE_MEM_GITHUB_API`) and a `Bun.serve` stand-in. `plan.ts` reads the same API with `gh api`, and phase 4 already tests that with a stub `gh`. `GH_TOKEN="$MARKETPLACE_TOKEN" gh api -i repos/<repo>` returns the status, the `permissions.push` body and the expiration header, so `token.ts` could share `run` and the stub-`gh` harness. That removes the override variable and the second test style.
- F-3 · Nit · Plan step 23, the command part of `push.ts` (`PUSH_REMOTE`, `PUSH_ORIGIN` "used by tests only") · `commitAndPush` already takes `remote` and `origin` as parameters, and `tests/integration/release-push.test.ts` calls it directly. No test in phase 4 runs `push.ts` as a command, so these two override variables are environment hooks that no test uses, sitting in the script that holds the marketplace token. Either drop them, or add the phase 4 command test that needs them.
