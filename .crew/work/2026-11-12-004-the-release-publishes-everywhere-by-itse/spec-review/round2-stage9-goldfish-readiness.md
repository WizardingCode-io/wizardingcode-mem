## Findings
- F-1 · Major · Step 30 (distribute.yml) · The step lists the trigger, the inputs, each job and the pins, but it never mentions top-level `permissions: {}`, `run-name: distribute ${{ inputs.tag }}`, or `concurrency: { group: distribute, cancel-in-progress: false }`. AC-52 and the spec's design both require them. An engineer who builds the file from step 30 would leave all three out: the workflow would inherit the default token permissions and two dispatches could run at once. Step 29 does not pin them either, because it says only "asserting every clause of AC-52" and does not list the assertions (the group name, `cancel-in-progress` false, `permissions` equal to `{}`). So nothing forces the omission to be caught.
- F-2 · Nit · Step 29 · Apart from AC-53 and the last clause of AC-52, the step names no assertions. A builder has to turn each clause of AC-52 into a check themselves: which jobs have `environment`, the exact `if:` strings of `tap`, `marketplace` and `latest` and of the retag step, `needs` as a list, and `id-token` and `packages` appearing only where allowed.
- F-3 · Nit · Step 12 · `codexContext("", env).hooksPath` does not exist. `src/install/codex.ts:50-63` returns `settingsPath` (`<configDir>/hooks.json`). The fallback clause ("if that field has another name") hedges where the plan could simply name `settingsPath`.
- F-4 · Nit · Step 15 · The `case` glob `[0-9]*.[0-9]*.[0-9]*` is looser than the order's version rule: `*` matches anything, including a second line. So a staged file whose `--version` prints `1.2.3 junk`, or two lines, counts as a version and goes into the awk `older` as `$2`, and step 5 does not validate `$2`. The spec says "answers `--version` with a version". The test with `hello` would not catch this.
- F-5 · Nit · Step 25 · The step says "the `already-published` line", "the `published` line" and "`would-publish`" but does not say they go through `summary(summaryLine("npm", …))`. Phase 4's intro says the tests assert the `GITHUB_STEP_SUMMARY` file, but step 25's tests do not check it. Steps 23 and 26 do name `summary`.
- F-6 · Nit · Step 18 · The return shape of `editManifests(claude, agents, version)` is not given (for example `{ claude: string; agents: string; outcome; higher? }`). Step 23's marketplace edit depends on it. The step also gives no rule for the outcome when one manifest is `written` and the other `already-at`.
- F-7 · Nit · Step 18 · "copied byte for byte … as read with `gh api repos/…/contents/<path>`": that endpoint answers with JSON holding base64 content, not the file. The step should name the decoding or the raw media type (`-H "Accept: application/vnd.github.raw"`) so the fixture really is byte for byte.
- F-8 · Nit · Step 23 tests · The rebase case does not say that the second clone's concurrent commit must touch a file other than `a.txt`. If it edits `a.txt`, `git pull --rebase` conflicts and the case fails for the wrong reason.
- F-9 · Nit · Step 23 · On a dry run, `git diff` does not show untracked files. A first write that creates a new file (for example `Formula/wizardingcode-mem.rb` in an empty tap) would print an empty diff while still returning `would-write`. `git diff` after `git add -N`, or `git status`, would show it.
- F-10 · Nit · Step 24 · The step gathers every fact before `decidePlan`, so a failed `gh` read (which throws) comes before an earlier refusal. For example, a run on a branch ref with a `gh api` 403 reports "could not read the environment release" instead of refusal 1. The step also does not say what `git merge-base`, `git cat-file` and `readRelease` are given when `tagSha` is null, or what `held` holds for a pre-release (whether `decideHold` runs at all for one).
