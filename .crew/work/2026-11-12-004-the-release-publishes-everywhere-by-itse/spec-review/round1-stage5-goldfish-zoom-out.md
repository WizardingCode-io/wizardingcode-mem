## Findings
- F-1 · Major · Design "The hold (D-2)", J-4, AC-26, the `release_hold` input, the two "held" summary rows · The spec says twice that nothing reads `latest` until piece 3 (Non-Goals; Risks "`latest` may lag"), and the code agrees: `compose.yml:6` pins `${WIZARDINGCODE_MEM_VERSION}` and no file uses `:latest`. So the contract hold protects no reader in this piece, yet it adds a source-text parser of `src/team/contract.ts` that fails closed, `previousPlain`, `decideHold`, a third dispatch input, two summary outcomes, a manual-release path and a runbook section. A builder would ship and test a gate for a consumer that does not exist yet, and would freeze its rule before piece 3 has decided how a host follows `latest`. The simpler shape: this piece moves `latest` last and does nothing more; the hold is built in piece 3 next to its reader. D-2 is the author's decision, so the session should confirm it was made knowing that nothing reads `latest` today.
- F-2 · Major · Design "`token.ts`: the token's state" and `token.yml` (Goal 6, AC-28, AC-31, plan steps 22, 26, 27, 32) · GitHub already emails a personal access token's owner, fine-grained tokens included, before the token expires. The spec also admits that the header the check reads may be absent ("expiry unknown … passes"). That leaves the weekly workflow, `door.ts`, the second environment check and `--fail-under` largely repeating a notice the platform already sends, on a signal that may not exist. A builder would maintain a second scheduled workflow, which GitHub also disables after 60 days without activity (the runbook's own limit), for little gain over the platform's email plus the warning on the release run. The simpler shape: keep `token.ts` as the first step of `tap` and `marketplace`, which gives a named failure and the under-30-days warning; drop `token.yml` and `door.ts`, or state why the platform's email does not satisfy Goal 6.
- F-3 · Nit · "One version order" and plan steps 4–5 · Three hand-written implementations of full semver precedence, one of them in awk, cover cases this project never produces: `0.9.0-aaa`, `0.9.0-1` against `0.9.0-rc`, and alphanumeric order by code unit. Refusal 2's tag pattern could narrow pre-releases to `-rc.<n>`. Then the JS and shell `older()` need only compare the core and an integer rc number, and `Bun.semver.order` stays the one full implementation on the TypeScript side.
- F-4 · Nit · Design "`tap` and `marketplace`", `editManifest`, plan step 18 · The edit is a bespoke text scanner that matches braces outside strings so that every other byte stays the same. A shorter path gives the same guarantee: refuse a file where `JSON.stringify(JSON.parse(text), null, 2) + "\n"` does not equal the text, otherwise parse, set the two fields and stringify again. The fixtures copied from the marketplace already show whether the files round-trip.
- F-5 · Nit · Design "The summary", "One version order", "`npm`" · The spec's Design names helper functions and their file locations (`summaryLine(target, outcome)` in `lib.ts`, `olderThan(have, wanted)`, `OLDER_JS`) and dated npm facts ("what npm 11.19.0 answered … on 2026-11-12"). That is plan-level detail. The spec needs the fixed texts table and the contract "a registry error is never read as not published"; the plan already carries the names.
- F-6 · Nit · Plan step 31, `latest` job, `scripts/release/summary.ts` · A fourth command file, with a checkout and a Bun setup, exists only to print one summary line. `plan` already writes the lines of the targets it skips. It could also emit the `latest` line as an output for the job to echo through `env:`, or `latest` could run an existing command with a flag, so no new file is needed.
