# design findings for 2026-11-11-005-share-a-project-without-a-git-remote
reviewer: goldfish-design
read: probes/concept.md; src/sharing/levels.ts, src/sharing/store.ts (setLevel, aliasToBind, reconcileLevels), src/core/project.ts (resolveProject), src/team/contract.ts, feed.ts, validate.ts, push.ts, store.ts (feedSql), routes.ts (/v1/health), migrations/0001_team_init.sql, server.ts (limits), src/sync/naming.ts, inbound.ts, outbound.ts, src/modules/knowledge/resolve.ts

## Findings
- F-1 · Blocker · §5 "An older server" · The plan depends on a premise that is false. `/v1/health` returns `{ ok: true }` and no version (routes.ts:205-211). With no contract bump, `/v1/me` reports `contract: 1` on both versions, so a 0.8 client has no way to recognise a 0.7.0 server. What the person sees: `feedSql` sends all the aliases in one main-set pull, so a single `team:` alias in `projects=` gets a 400 `projects` for the whole pull (feed.ts:57). That stops the sync for their remote-named projects as well. On the push side, every `team:` item is refused `shape` and `writeRefusal` records it once per hash (outbound.ts:695). After the server is upgraded it stays refused until its content changes. The design needs a real signal (a version in health or `me`, or a capability flag), and that is a contract change.
- F-2 · Major · §1, §6, Q1 · Collisions are the normal case, not a rare one. The field is prefilled with the slug of the project's name, so two members with unrelated `docs`, `website` or `app` projects bind the same alias without typing anything. On the server, project-scope entries take writes from any member, and only `workspace` is owner-checked (push.ts:214). Each side's entries land in the other's `knowledge/received/.../projects/docs-<hex>/`, and memories become `imported` rows of the wrong project (§9). The other side's sessions then read them as their own project's context. Showing the list with counts does not help on the first bind, because the list is empty or the name looks free. What the person sees is unrelated knowledge appearing in their sessions, with nothing reporting an error. My answer to Q1: refuse a name whose first sender is another member unless it was picked from the list. Better still, have the server issue team names (create or join), so it holds a registry instead of names emerging from slugs.
- F-3 · Major · §3, project.ts:94-102 · A path-only project with a team name that later gains a git remote (`git init` plus `remote add`) keeps its project id. `resolveProject` then adds `remote:` beside `team:`. §3 says host-led remotes are tried first and that `as` on a remote project is refused. If a later level change goes through `aliasToBind`'s new order, the binding quietly moves to `remote:`. Today's `aliasToBind` keeps the existing binding (store.ts:345), and the concept does not say which rule wins. In the moving case, entries re-push under the new alias as moves (push.ts:252), and every member bound to `team:<name>` gets tombstones with `movedTo` an alias they do not pull. The project then vanishes for the team.
- F-4 · Major · downgrade, levels.ts:155, store.ts:453 · The reverse version case. If a store written by 0.8 is opened by a 0.7.x binary (a rollback, or a second install sharing the data dir), `effectiveLevel` reads every `team:`-bound row as `unbound-alias`. `reconcileLevels` then deletes those rows as `system`, and the outbound D-10 sweep withdraws everything sent under them. Every member loses the team's copy, and the level does not return after re-upgrading. The concept does not mention this.
- F-5 · Major · §10, resolve.ts:29 · Making `team:` a strong alias treats it as a permanent identity. But a team name can be released: a rename deletes the old row, after which another local project may take the name. A manifest that still lists `team:docs` can then tie the old folder to the new owner on a rebuild. Either keep `team:` weak, or never let a name released on this machine be reused.
- F-6 · Major · §6 `GET /v1/projects` · (a) It has no pagination and no size cap. One row per alias that has ever been current, so 10k aliases is roughly 1–2 MB per combobox open. (b) `changes_scope` is (scope, remote_alias, current, seq). The member count and the op filter (to exclude tombstone and purge) need `member_id` and `op`, which are not in the index. So every request reads every current project change row: O(current rows) per call, and any member can call it with no rate bucket named. (c) It lets any member list every `remote:` repository name on the server, including private repo paths. D-11's "any member may name any alias" covers guessing a name, not listing them all. That is a new disclosure and needs a decision.
- F-7 · Major · §2 `name-taken` · Setting Nothing keeps the alias row, and the only way to clear it is renaming that project. A name held by an abandoned or `imported:` project therefore blocks every other local project from using it. The person sees `name-taken` and no verb that frees the name. The design needs "forget name", or `name-taken` should name the holder and give the way out.
- F-8 · Major · Q2 · Binding a folder to a `remote:` alias picked from the list is dangerous. `resolveProject` writes the remote alias with `INSERT OR IGNORE` ("a remote names one project for good", project.ts:133). If the person later clones the real repository, its sessions resolve to the unrelated folder project, and that cannot be undone. Keep it out of this item, or bind under a `team:` name only.
- F-9 · Nit · alias cap · With 158 projects and "tudo é partilhado", more than 100 bound aliases push the rest into the extras rotation: one alias every 60 s (inbound.ts:640-654). Project 101 of 150 is refreshed only about every 50 minutes, and the status display does not show this. Server cost is small: up to 102 `UNION ALL` index ranges per pull, re-run every 5 s while held.
- F-10 · Nit · §1 slug · A name made only of non-Latin characters or emoji (`日本語`) slugs to the empty string under NFKD and mark stripping, which leaves no default and no refusal sentence. Truncating at 63 characters can make two long names collide.
- F-11 · Nit · Q3 · The premise is partly wrong. The server already treats an alias change of the same uuid as a move: it continues the revision and writes a tombstone with `movedTo` (push.ts:252, 353). It does not create a new entry. Moving a name is therefore N pushes, against 2N for "Nothing first" plus a full re-download through `noteUnbound`. For the members bound under the old name, both have the same result. The rule (Nothing first) holds, but the reason the concept gives is wrong.
- F-12 · Nit · Q4 · Under D-19, sharing wizardingcode at "Knowledge and memories" sends little, because most of its memories are `imported`. If that stays out of scope, the item ships without meeting the author's requirement. Record it as a decision of this item, even if the work is done in a second one.
