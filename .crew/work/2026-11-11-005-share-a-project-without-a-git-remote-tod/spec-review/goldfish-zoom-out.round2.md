## Findings
- F-1 · Major · spec D-4, "The server: schema 2" and Alternatives "Keep the column names and the store version" · The only reason given for renaming the four server `remote_alias` columns to `project_alias` is to make a 0.7.0 image refuse the database. The `names` table and `TEAM_LATEST` 2 already do that, because `openTeamExisting` with `latest` 1 throws `SchemaTooNewError` on any schema 2 file whatever the migration holds. So the rename adds no loudness. It does rewrite every statement and row type in `src/team/store.ts`, mirror.ts, push.ts, feed.ts and status.ts and the raw SQL in the team tests. It also creates the "two vocabularies of `remote_alias`" that the ADR then has to explain, because the client's columns and the wire key `remoteAlias` keep the old name. A builder following the spec will take on that churn and risk for the wrong reason. The simpler design keeps the columns and lets the registry table carry the schema bump. If the rename is wanted for clarity, it can be its own decision with its own reason.
- F-2 · Major · spec "The name of a project" (`dryRun` "inside a read of the store") vs plan task 6 ("`dryRun` runs the chain inside `withWrite`") · The two documents disagree. `withWrite` is `db.transaction(fn).immediate()` (src/store/db.ts:433), which takes the write lock. The preview route calls the dry run "as the person types", so the plan as written takes BEGIN IMMEDIATE on every keystroke in the dock, and each one competes with hook writes under `busy_timeout`. The builder would follow the plan and miss that risk. The dry run needs a deferred read, and the real write already re-checks every refusal inside its own transaction. Make the documents agree on a read transaction.
- F-3 · Nit · spec "The identity leaf", `ALIAS_KINDS` `permanent` property · `resolve.ts` is explicitly unchanged, and no other reader in the spec or plan consults `permanent`. The property exists only for a future reader, and the Alternatives say as much: "makes a third identity a row". AC-14 still tests it. Drop it until a reader exists.
- F-4 · Nit · spec "The identity leaf" `isSharedName` and "The name of a project" `sharedNameOf` · The slug grammar would then live in three places: `isSlug` in entry.ts, the regex repeated in the leaf, and a contract test kept only to check that the two agree. The "no letter or digit survives" rule would also be written twice, because `sharedNameOf` re-implements the check of the private `slugOf` in src/team/contract.ts:165. Reuse would be simpler. Move the slug grammar into the leaf and have entry.ts import it, and export the letters check from one place for both `slugOf` and `sharedNameOf`.
- F-5 · Nit · spec "The contract spoken" (the `/v1/me` refresh at sync start, the 409 retry with downgrade, the bare-404 detection that sets the row to 1) · The spec builds three separate ways to discover the same fact, that the server speaks 1. Each needs its own tests: AC-17, AC-22, AC-23 and the plan's edge cases. The 409 path alone covers both the rollback and the old server for sync requests. A reader should be told why each of the other two is needed. Otherwise the downgrade logic ends up spread across client.ts, inbound.ts, outbound.ts, run.ts, binding.ts, servers-api.ts and share.ts.
- F-6 · Nit · spec "Sizing" and the `GET /v1/names` paging (50 a page, at most 200, `after` cursor and its own 400) · The spec's own sizing is "tens of projects, not thousands". Both consumers reassemble the whole list anyway: the viewer route follows every page up to 1,000, and `share names` prints all of them. The paging protocol, the `after` validation and the 60- and 120-name seeding tests buy nothing at this scale. It is defensible only as consistency with the feed, and the spec should say that if it is the reason.
- F-7 · Nit · spec "The two-phase write and its race", plan tasks 19 and 20 (`hooks.afterServer`, `sharingHooks` on `src/ui/server.ts`'s start options) · A test-only hook is threaded through the production viewer server's options to drive a race that lasts one round trip. Testing `bindName` directly, as task 22 already does, covers the outcome. The viewer route then only needs to map `named: true` to a status, which can be tested without new plumbing in production.
- F-8 · Nit · spec "Proposed architecture" (whole) · This is architecture-level text holding code-level detail: regexes and the reserved-name list, the full SQL repeated in the plan, every UI sentence word for word, every HTTP status per route, and the refusal order with message text. The plan and the ACs repeat the same detail, so the spec reads as a third copy. Keep the interfaces, data flow and rules in the spec, and leave the strings, SQL and statuses to the plan and the copy test.
- F-9 · Nit · spec line 3 and "Acceptance criteria" preamble (line 266); plan task 10 · Process history sits in the reader's path: the revision counts and AC renumbering history, and in the plan the thinking-aloud "(the row types keep their field name `remote_alias`? No: rename the row fields…)". It belongs in `conclave.md`, and the plan should state only its decision.
