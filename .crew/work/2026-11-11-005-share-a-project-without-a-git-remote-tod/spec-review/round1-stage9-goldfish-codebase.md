## Findings
- F-1 · Blocker · Task 3 and task 9 (the upgrade copies) · Task 3 expects a `backups/*-v8-*.db` copy after upgrading a version 7 store, and task 9 expects a `team-<ms>-v2-<pid>.db` copy after migrating schema 1 to 2. The code names the copy after the version it is upgrading from. `migrateFile`'s `backupVersion` returns `userVersion(lock)` before the upgrade (src/store/db.ts:204-208), so the copies are `-v7-` and `team-…-v1-…`. tests/unit/team-db.test.ts:79 already pins `team-\d+-v1-\d+\.db` for a 1→2 upgrade. Both new assertions fail as written.
- F-2 · Blocker · Task 9 (`serve purge name` test) · The test asserts that the alias string "still appears in `purged.key`, in `changes.key`". The code never puts it there. `eraseEntry` and `eraseMemory` (src/team/mirror.ts:565-618) call `markPurged`/`insertPurged` (src/team/store.ts:896-909) with `key` = the entry's uuid or `<device id>:<uid>`, and neither key embeds the alias. The alias survives only in `changes.uid` and the `remote_alias`/`project_alias` column. The spec's "the key … embeds the alias" (spec.md:158) has the same error.
- F-3 · Blocker · Task 1 (isSharedName vs isSlug) · Task 1 says "every refused one fails `isSlug`", but the refused `name:x-` (and the edge case `name:x--y`) have slugs that pass `isSlug`. `SLUG = /^[a-z0-9][a-z0-9-]*$/` accepts a trailing hyphen and a double hyphen (src/modules/knowledge/entry.ts:11, 90-92). The test cannot pass.
- F-4 · Major · Task 2 `SHARED_NAME` vs the AC-14 edge cases · The pinned regex `[a-z0-9](?:[a-z0-9-]{0,78}[a-z0-9])?` accepts `name:x--y`, yet the edge-case list says `isSharedName("name:x--y")` is false. A builder who copies the regex gets a failing test; one who follows the test must change the grammar the plan pins.
- F-5 · Major · Task 25 / AC-13 ("the named cases are the only changes to existing tests") · That claim is false. These existing tests and helpers break and no task names them:
  - tests/unit/team-db.test.ts:238-246 writes `user_version = 2` as "newer" and expects `SchemaTooNewError`; that becomes the current schema.
  - tests/unit/team-db.test.ts:174 pins the `-v7-` module copy name, which becomes `-v8-`.
  - tests/integration/team-process.test.ts:304-313 expects exit 3 from a schema-2 team.db.
  - tests/unit/sync-schema.test.ts:114 and 279 pin `userVersion` 7.
  - tests/integration/sync-client.test.ts:222 expects `accepted: [1]`.
  - tests/integration/team-auth.test.ts:91 expects `contract` 1, and :227-238 expects header 2 → 409 `[1]`.
  - tests/helpers/team.ts:418 (`seedFeed`) inserts into `changes (… remote_alias …)`.
  - tests/integration/team-push.test.ts:66-125, 351-368, 798-839 select and match `remote_alias` on `entries` and `memories`.
- F-6 · Major · Task 10 ("`grep -n remote_alias src/team` ends empty") · This check can never pass. src/team/migrations/0001_team_init.sql holds five occurrences, and migrations are never edited (src/store/db.ts:19). A builder chasing the check would edit a released migration.
- F-7 · Major · Task 9 (the schema-too-new tests) · Two of the seams the tests use do not exist as described:
  - `openTeamExisting(dir)` takes no `latest` option (src/team/db.ts:97), so "openTeamExisting with latest 1" has no seam.
  - For the serve CLI case, `startTeamServer` calls `openTeamForWrite(options.dataDir, now())` with no options (src/team/server.ts:95), so there is no way to force `TEAM_LATEST` to 1. The fallback ("run the binary with a database written at 2 and assert exit 3") exits 0 once `TEAM_LATEST` is 2. The existing exit-3 test (team-process.test.ts:304) has to move to `user_version` 3.
- F-8 · Major · Task 23 (`createName` in client.ts) · `failureOf` turns every 409 into `{ kind: "contract", accepted }` and drops the rest of the body (src/sync/client.ts:115-120). `POST /v1/names` answering 409 `exists` would therefore arrive as a contract failure with `accepted: []`, which task 14's rule turns into `stop("contract")`, and the `name` item is lost. The plan never says the names calls must tell `exists` from `contract` or keep the body.
- F-9 · Major · Task 14 (the header spoken) · The plan never says that pulls and sweeps send the stored contract. `pullOnce`, `sweep` and `withdrawAll` build `new SyncClient(ctx, { url, token })` without `contract: row.contract` (src/sync/inbound.ts:459, src/sync/outbound.ts:307, 904). Built as written, every request to a contract-1 server first gets a 409 and then the retry, on every tick. Only `refreshContracts` is told to pass `row.contract`.
- F-10 · Major · Tasks 14 and 16 (a downgrade inside one run) · Two places keep the old contract after it changes:
  - `runSync` reads `confirmedServers` before `startSteps` and hands those rows to `runOnce` (src/sync/run.ts:152, 161, 170), so in `sync --once` the value `refreshContracts` just wrote is not seen.
  - `sweep` builds its candidates before `pushBatch` (src/sync/outbound.ts:341-454). After a same-tick 409, `setContract` to 1 and the retry, items of a name-bound project are still in the batch. The contract-1 server refuses them `shape` and `sharing_refusals` rows are written, which contradicts AC-8's "writes no `sharing_refusals` row".
- F-11 · Major · Task 20 (`setProjectSharing` calls `bindName`) · `setProjectSharing` is synchronous and has no `SyncContext` (src/ui/api.ts:1055-1086); src/ui/server.ts:512 calls it without `await`. `bindName(ctx, …)` is async and needs the context that `syncContext()` builds (server.ts:224). The plan never gives the new signature or the call site. Also, the viewer's options are `UiOptions` (server.ts:102), not "start options".
- F-12 · Major · Task 20 (`listProjects` `boundTo` "from the level row's `bound_alias`") · src/ui/api.ts is on the quiet list of tests/unit/sync-boundary.test.ts:175-187 and may not name `sharing_levels`. Reading the row by SQL fails that suite. The plan should say the value comes from `policy.levels.get(levelKey(…)).boundAlias`, which outbound.ts:432 already uses.
- F-13 · Blocker · AC-22 edge cases ("a pending server → 404 `no such server` as the other server routes") · This is not how the other server routes answer. They answer 404 `unknown-server` (src/ui/servers-api.ts:209, 218, 277, 288). `findServer` finds pending rows too, so they do not 404 a pending server. "no such server" is the sharing-destination refusal (src/ui/api.ts:1038).
- F-14 · Nit · Task 10 (server.ts and tests/helpers/team.ts) · `StartOptions` does not exist; the type is `ServerOptions` (src/team/server.ts:51). `startTestServer` already spreads `overrides` into `startTeamServer` (tests/helpers/team.ts:54-86), so adding `contract` to `ServerOptions` needs no helper change. `checkContract(request)` takes no `ctx` today (src/team/auth.ts:43).
- F-15 · Major · Task 21 (the captures) · It cites "the earlier `seed-sharing-capture.ts`" and "`scratchpad/capture`" as existing. Neither is in the repository (scripts/ has no such file). A fresh session has no seed script or capture script to start from.
- F-16 · Major · Phase E, task 20 · Task 20's green run is deferred until after task 22 in Phase F. Phase E therefore ends red, against the plan's own "every phase leaves `bun run check` green" and the readiness rubric.
- F-17 · Major · Tasks 13 and 15 (`world()`) · `world(level = "knowledge")` takes one positional argument and starts its server with `startTestServer({}, …)` (tests/helpers/sync-world.ts:39-42). Task 15 adds an options bag `{ named?: true }`, and task 13 needs a world whose server starts at `{ current: 1, accepted: [1] }`. Neither the new signature nor how the server options reach `startTestServer` is given, so the builder has to design the helper's API.
- F-18 · Major · Task 9 ("no query ran for the last two") · The plan leaves the method open: "a spy on `store.ts`'s `nameByAlias`, or the SQL trace of `bun:sqlite`". That is a decision the plan should make. Bun's ESM exports are live bindings that a test cannot reassign, and I found no SQL-trace hook used anywhere in the repo.
- F-19 · Major · Task 11 ("the replay shortcut under a name purged since → `name`") · This case cannot be built. `serve purge name` refuses while `currentItemsUnder` is non-zero, but the idempotent shortcut needs a current row with `withdrawn_at === null` (src/team/push.ts:202-211). A purged item's uuid answers `purged` first (push.ts:200).
- F-20 · Major · Task 15 (the forgotten-name-then-remote move) · `sentRowByUuid` reads only rows with `withdrawn_at IS NULL` (src/sync/ledger.ts:108-117). Setting Nothing withdraws the sent rows on the next full sweep (the plan's own case). The entry goes out as a move only if no full sweep ran between Nothing and the rebind; otherwise it is sent on base 0 and the server answers `stale`. The test does not fix that order.
- F-21 · Nit · src/sync/join.ts:86 · The contract failure message hard-codes "this client speaks 1", which becomes false at `CONTRACT` 2. No task touches it.
- F-22 · Nit · Line 41 and task 9 (409 `exists` shape) · A 409 goes through `IDS_ON` (src/team/routes.ts:37, 525), so the body also carries `serverId` and `instance`. An exact-match test against `{ error, name }` fails.
- F-23 · Nit · Task 11 ("both pass `PROJECT_FOLDER`") · `PROJECT_FOLDER` is private to src/sync/naming.ts:15. The test has to use `isComponent("project-folder", …)`.
- F-24 · Nit · Task 12 (`refused(uid, "name", NAME_RULE)`) · `refused` in src/team/push.ts:45 takes two arguments: the uid and a `Refusal` or `PushReason`. A rule text needs a `Refusal` object (`{ result, reason, rule }`).
- F-25 · Nit · Tasks 6 and 23 (`folderRemote`) · The existing field is `SetLevelInput.remoteAlias` (src/sharing/store.ts:254), and share.ts:211 passes it. The plan writes `folderRemote` in `aliasToBind` and in `BindInput` without saying whether the field is renamed.
- F-26 · Nit · Task 20 (`imported` count) · The SQL given filters on `origin = 'imported'` only, while the spec counts active imported memories (spec.md:191). The `status = 'active'` filter is missing.
