## Findings
- F-1 · Blocker · Task 5 and task 6 (sharedNameOf) · The plan expects `sharedNameOf("CON")` to answer `no-name` with `word: "con"`, and `""` and `"!!!"` to answer `no-name`, and it builds the name from `slugify`. But `slugify` in src/modules/knowledge/entry.ts:72-87 returns `"entry"` for empty or symbol-only text and appends `-entry` to a reserved slug, so `slugify("CON")` is `con-entry`. That passes `SHARED_SLUG` and is not reserved, so the rule as written yields `name:con-entry` and the test cannot go green. Fix: say exactly how the reserved word is detected (the slug before the `-entry` suffix, or a slug function without the fallbacks) and where it lives.
- F-2 · Blocker · Tasks 5, 6, 22 and the AC-33 edge cases (`formatChange`) · `formatChange` is described as an existing function "the one `share status` and the Sharing page use", but it does not exist anywhere in src or ui/src. src/cli/commands/share.ts:311 formats the last change inline. ui/src/components/settings/Sharing.vue:93-111 formats it inside the component with its own `^project:(\d+)$` regex, and a Vue component cannot import src/sharing/store.ts. Fix: mark it `Create`, say which module it lives in and its signature, and say how Sharing.vue gets the rendered line (a server-side field, or its own `name:` branch).
- F-3 · Blocker · Task 10 (`src/team/auth.ts`) · The plan says `checkContract`'s one call site is "inside `authenticate`" and passes `ctx.contract.accepted`. In fact it is called from `withCaller` in src/team/routes.ts:174. `authenticate(db, request, now)` at auth.ts:20 takes no `ctx`. Fix: name `withCaller` in routes.ts as the call site that passes `ctx.contract.accepted`.
- F-4 · Blocker · Task 23 (`ui/src/api.ts`) · "`ApiError` exposes `reason`": there is no `ApiError`. The class is `RouteError` (ui/src/api.ts:274), and `call` already copies the whole refusal body into it (line 301), so `reason` is on `body.reason` today. Fix: name `RouteError` and say whether anything changes.
- F-5 · Major · Task 10 (`src/team/store.ts` names functions) · `nameItemOf` and `listNames` are typed to return `NameItemShape` from src/team/contract.ts. tests/unit/team-store-boundary.test.ts:27-28 lets store.ts import only `./db.ts` and `./errors.ts`, and its header says it returns plain rows. A builder who imports the type from `./contract.ts` breaks a test the plan says "passes unchanged". Fix: store.ts returns plain rows, and the shape is built in routes.ts or another non-store module (name it).
- F-6 · Major · Tasks 3, 9, 13 and 26 (the existing tests changed, "no other") · Several existing tests break and are not named. tests/unit/sync-schema.test.ts:97 (`SHARING_SCHEMA_VERSION` 2), :99-102 (the sharing list), :115 (`moduleVersion` sharing 2) and :218-225 (`sharing_levels` columns without `name_id`). tests/unit/team-db.test.ts:298-317: it appends `{ version: 2 }` to `TEAM_MIGRATIONS`, which now already holds a version 2, so no upgrade and no copy happen. tests/integration/team-auth.test.ts:171 (`/v1/me` `contract: 1`). tests/integration/sync-join.test.ts:108 (the row's `contract: 1`, which becomes 2). tests/unit/module-migrations.test.ts:88 and :114 (length 5) and the lists at :123-129, :146-153 and :212-224. Fix: list each edit in its task and correct task 26's claim.
- F-7 · Major · Task 3 (team-db.test.ts line 174) · The text leaves the pin undecided ("`-v8-`? No: ... the test's fixture decides"). The fixture is decided: a fresh `openDb`, then a module-only bump, whose copy is named after `userVersion(lock)` (src/store/db.ts:329-333). After migration 8 that is 8, so the pin must become `-v8-`. Fix: state `-v8-` and remove the hedge.
- F-8 · Blocker · Task 14 (sync-contract.test.ts fixture) · `world("knowledge", { named: true, server: { contract: { current: 1, accepted: [1] } } })` cannot be built. The named world creates the name with `POST /v1/names`, which the plan makes a 404 below contract 2. `joinServer` then stores `min(CONTRACT, 1) = 1`, so there is no `nameId` to bind with. Separately, starting a server with `accepted: []` contradicts "keeps answering 409 with `[1]` to header 1": with `[]` the client rule finds no value to drop to and stops at once, with no repeat. Fix: say how the name and its id are seeded on a contract-1 server (for example `insertName` on the server database), and pick one fixture for the "409 again after the retry" case.
- F-9 · Major · Plan intro (the widened `world`) and Phase D · The change to the shared helper tests/helpers/sync-world.ts (the new signature, the `NAME` export, the second project, the create, `as`, `nameId` and `confirm`) is described only in prose. It appears in no task and is not marked `Modify`, yet tasks 14 and 16 depend on it. The current `world(level)` at sync-world.ts:39 takes no options. Fix: give it a task marked `Modify` before task 14, with how the name is created and how its id is read back.
- F-10 · Major · Task 6 (`policy.ts` reads `name_id`) · The loader takes its rows from `levelRows` (src/sharing/store.ts:172-180), which selects named columns. The plan neither marks `levelRows`/`StoredLevel` nor `src/sharing/types.ts` `LevelRow.nameId` for change. `readStore` refuses only a `too-new` sharing schema (policy.ts:213), so `status` and `doctor`, which open the store without migrating it, will select `name_id` on a store whose sharing namespace is still at 2 and fail with "no such column". Fix: name these edits and say how a sharing-v2 store is read (a guard on the column, or `nameId` null).
- F-11 · Major · Wire section (the viewer's refusal body) · The `reason` codes skip existing refusals of the sharing routes in src/ui/api.ts: 400 `{ error: "server" }` (several servers and none named, lines 1040-1042), 404 "no such server" (line 1038), and 400 "body must be an object" and the other preview body errors (lines 977-1003). The new `server` reason (502) also reuses the word that today's 400 `error: "server"` means "name a server". The dock switches on `reason`, so a builder would either leave these refusals without a code or send them down the 502 path. Fix: give each existing refusal its code and pick a distinct one for the 502.
- F-12 · Major · Task 10 (`POST /v1/names` and `serve purge name`) · Every route that writes an audit row calls `ctx.onWrite({ feed: false })` (for example routes.ts:232 and :253), and every CLI write calls `writeHighWater` (serve.ts:255 and :508). That keeps the audit mark in feed.seq, which `checkRestore` compares (src/team/instance.ts:74-90). The plan's create route and `purgeName` mention neither, so the file falls behind the database. Fix: state the `onWrite` call in the handler, and say that `purgeName` goes through `write(shell, …)` or calls `writeHighWater`.
- F-13 · Nit · Wire section (sync client kinds) · "a 404 whose body says `unknown-name` is `{ kind: "refused", status: 404, body }` as today": today `refused` carries `error`, not `body` (src/sync/client.ts:59 and :125). Also, the new kinds `conflict` and `oldServer` need cases in src/sync/join.ts `failureMessage`, an exhaustive switch over `ClientFailure` (lines 70-101), which no task names.
- F-14 · Nit · Task 10 (`Meta` gains `lookup`) · `Meta` is `Partial<Pick<RequestLine, …>>` (src/team/types.ts:49), so `lookup` has to be added to `RequestLine` in src/team/log.ts, which is not listed. Also, the request log's `route` field is the literal path (routes.ts:501), not a `GET /v1/names/…` pattern, so the test should match the encoded path.
- F-15 · Nit · Task 15 (`src/sync/join.ts`) · The join stores `min(CONTRACT, answer.contract)`, but the `me()` call right after it (join.ts:177) still builds its client with the default header 2. Against a 0.7.0 server (accepted `[1]`) that call answers 409, and the join reports `limits: null`. Fix: say whether that client speaks the answered contract.
- F-16 · Nit · Task 9 (team-db.test.ts) · "the existing pin at line 79 holds" for the 1-to-2 copy: line 79 belongs to the generic `openFile` test over the fixture lists `ONE` and `TWO`, not the team migration list. The new copy assertion needs its own line.
- F-17 · Nit · Task 22 (ui-servers.test.ts, seeding 1,050 names) · The devices bucket allows 600 requests per minute (src/team/server.ts:29) on a fake clock, so seeding 1,050 names through `POST /v1/names` gets 429 from the 601st. The plan does not say how they are seeded (for example `insertName` on the server database, or clock advances).
- F-18 · Nit · Task 9 (team-process.test.ts lines 304-313) · The existing case starts the binary through its local `serve(dir, home)` helper, not `spawnCli`, and its fixture is a hand-made file with only `meta` rather than "a schema 2 file". The text describes a different mechanism without saying why it changes.
- F-19 · Nit · Task 15 (`boundAliases(ctx, server)`) · The current signature is `boundAliases(ctx, serverId: string)` (src/sync/inbound.ts:75). The plan writes it with `server` but does not state the signature change or its callers.
