## Findings
- F-1 · Blocker · Acceptance criteria, AC-29 (and journey 6, "the entries' keys") · AC-29 asserts that after `serve purge name` "the `purged` keys of its purged entries ... still carry the string", but the architecture itself says the `purged` table's keys are the entry's uuid or the device's memory key and hold no alias, and the code agrees (src/team/store.ts:908 inserts the bare key, src/team/mirror.ts purgeItem passes the uuid, migration 1 has `purged (key, at)`). A test written to AC-29 fails, or someone writes a test that proves something false. Journey 6 and ADR 0028's limit say the string stays in "the entries' keys", which is also wrong, because a purged entry's row is deleted and an entry's key is its uuid. Fix: in AC-29, journey 6 and the Known limits, list where the string really stays: `changes.uid` and `changes.project_alias`, the withdrawn rows' `project_alias`, `entry_revisions.project_alias` of withdrawn entries, and the audit rows (`name created`, `name purged`, and each per-item `purged` row whose target is the full uid).
- F-2 · Major · The server, the feed's `nameId`; A name re-created; the operator's erasure · The spec says every feed item under a shared name carries "the id the registry holds now", and the client skips any item whose `nameId` differs from the stored `name_id`. It never says what `nameId` is when the registry holds no row for the alias (after `serve purge name`, or after a restore older than the name). It also never says whether the skip covers `tombstone` and `purge` rows. The runbook order is to purge the items, then purge the name. Feed rows stay current, so any client that pulls after the second step gets the `purge` rows (src/team/store.ts:900 turns them into op `purge` under the same alias) with no matching id. A builder following the rule as written skips them, so the purge never reaches teammates' copies, a sender's ledger is never marked purged (src/sync/inbound.ts:190-195), and the binding is flagged with the false sentence "re-created on the server by <member>". The spec also does not say whether skipped items count as seen in `compareSnapshot`, so one builder will wipe a flagged name's received copies on the next snapshot and another will keep them. Fix: define `nameId` for an alias the registry does not hold, exempt `tombstone` and `purge` rows from the id check (or apply them always), and state how a flagged name's skipped items affect the snapshot comparison.
- F-3 · Major · The `name` refusal on the client; `nameState`; `doctor sync` · The `missing` state is kept in the server row's `lastError`. That is one field per server, and `recordAnswer` (src/sync/state.ts:222-231) sets it to null on every successful pull or push, and a pull runs in every loop. So the dock's `missing` sentence, `nameState: "missing"`, `share status (missing on the server)` and the Servers page flicker off within seconds. With two missing names on one server only one can be recorded, so the promise that `doctor sync` warns "once per missing name" cannot be met. The spec also does not say whether writing this error counts as a failure that sets `retry_at` and backs off the whole server, which would hold back every other project on it. Fix: store the missing state per alias (a meta key such as `names.missing:<serverId>:<alias>`, like the re-created flag), clear it when a push under the name is applied, and say it never counts toward the backoff.
- F-4 · Major · The operator's erasure; journey 6; Risks, "A sensitive or wrong name on the server" · The erasure does not hold against the members still bound to the name. After `serve purge name`, their next push is refused `name`, and the dock, `status` and `doctor` tell them "the server does not hold `<slug>`; set the level again to create or join it". The first one who follows that advice re-creates the typo or the person's name the operator just removed. The client cannot tell an operator's purge from a lost restore. Members still at Knowledge or Knowledge and memories also keep pushing new items under the name between the item purges and the name purge, so `serve purge name` stays refused ("still holds n entries") until the operator gets every member to stop. None of this is in the risks or the runbook section. Fix: give a purged name a distinct reason (a purged-alias record in the registry, a refusal such as `name-purged` that is not offered as "create it", and unbinding on the client), or state the limit and the coordination the operator needs in ADR 0028 and the runbook.
- F-5 · Major · Risks, "Registry growth"; Non-goals ("the devices bucket bounds the rate"); Sizing · "Bounded by the devices bucket" is unbacked at this design's scale. The bucket is 600 requests a minute per device (src/team/server.ts:29, src/team/limits.ts:59), so one buggy or hostile device can create about 36,000 names an hour. The list then truncates at 1,000, and the preview route asks the server nothing, so a typed held name past the first 1,000 shows `New` (only the 409 `exists` catches it). The only cleanup is the operator running `serve purge name` once per name. Fix: a per-member creation limit or a dedicated `names` bucket, or a measured statement of what the bucket allows and why that is acceptable.
- F-6 · Major · Risks and mitigations (missing); Terms, "Carried" · A project with no remote and no git directory is known on this machine only by its `path:` alias (src/core/project.ts:80-142). If the person moves or renames the folder, the next session creates a new project, and the shared name stays on the old one. To move the name, the person must set the old project to Nothing, which withdraws everything it sent from the server and from every teammate's copy, then forget the name and re-share from the new project. That is a silent stop of sharing followed by a full withdraw and resend for the case this item exists for (non-git folders such as `~/Projects/wizardingcode`). Fix: state the limit and its recovery, or add a local move of the name and its level row from one project to another with no withdrawal.
- F-7 · Major · Rollout and rollback, "The server"; journey 9; Risks, "A name the server lost" · After a restore older than a name, the spec has the person re-create the name by setting the level again. That mints a new registry id, so every other member bound to the name is then flagged `name-recreated` and stops sending and receiving under it until each one re-confirms the join. The rollback section, journey 9 and the runbook items do not name this burden, which falls on every member for every name after any restore. Fix: state it in the rollback and the runbook, or let a client that detects a renewed instance re-create the name with the `name_id` it holds, so teammates' ids still match.
- F-8 · Nit · The `name` refusal on the client; A name re-created; AC-32 · `bindName` is used as a function ("`bindName`, the create state", "cleared by `bindName`", "a `bindName` join") but the architecture defines only `prepareBinding` and `commitBinding`. Fix: name the real function, or define `bindName`.
- F-9 · Nit · setLevel refusal 7, `needs-confirm` · The rule "the stored level, if any, not bound to that alias with that id" cannot be judged in the dry run, which runs before the server answers and so has no id for a join. Fix: say what the dry run compares (the alias, plus the stored `name_id` against a flag) and what the write re-checks.
- F-10 · Nit · Sizing, Effort · Heilmeier question 7 (how long) is answered only with "built in this session, the size of part 6's item", with no duration or measure a newcomer can check. Fix: give the duration part 6's item took, or an estimate.
