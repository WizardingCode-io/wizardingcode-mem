## Findings
- F-1 · Major · spec "The `name` refusal on the client", `nameState` in "The viewer" routes, "Status, doctor and the read-outs per name"; plan task 17 (`recordAnswer` with the error text) · The `missing` state is kept in the server row's `lastError`, and the dock, `status`, `share status`, `doctor sync` and `nameState` all read it from there. That field belongs to the breaker. `recordAnswer` (src/sync/state.ts:217) does two things that break this. A failed answer raises `failures` and sets `retry_at` by backoff for the whole server, so one missing name slows every project on that server. Any later successful answer, such as the next pull a few seconds on, sets `lastError` back to null, so the state disappears. The field also holds only one text per server: two missing names cannot both show, and a network error overwrites the name's text. A builder following plan task 17 would connect five read-outs to a value that cannot hold them, and would push the server into backoff. Simpler: keep a flag per name beside the existing `names.recreated:<serverId>:<alias>` meta key, for example `names.missing:<serverId>:<alias>`. Set it on the refusal and clear it when a push is applied or the person binds again. Keep `recordAnswer` and the breaker out of this.
- F-2 · Major · journey 9, "Rollout and rollback" (the server), Risks "A name purged or lost in a restore and re-created for another project" · After `team.db` is restored to a copy older than a name, the spec's fix is that the creator sets the level again, which creates the name again with a new id. Every teammate bound to that name then pulls items whose `nameId` differs from the one they stored, and is flagged `name-recreated`. One restore therefore makes each member join each name again by hand. The id mechanism treats this legitimate re-creation exactly like the unrelated re-creation it was built to catch. Neither the journey, the risk nor the runbook text says so, so an operator who restores will not warn the members. One fix is to state this cost in journey 9, the risk and the runbook's restore section. Another is to let the create carry the id the creator's client stored (`POST /v1/names { alias, id }`, accepted only when the alias is not held), so a restore followed by re-creation keeps the id that teammates joined.
