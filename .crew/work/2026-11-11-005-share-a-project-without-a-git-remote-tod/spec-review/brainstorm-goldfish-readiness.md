## Findings
- F-1 · Blocker · concept §5 / §4 "no contract bump" · The older-server gate rests on something that does not exist. `/v1/health` returns `{ ok: true }` and nothing else (routes.ts, the `GET /v1/health` route), and `/v1/me` gives `contract` but no version. Without a signal, a 0.8 client against a 0.7.0 server gets a 400 `projects` on any pull that names a team alias. That 400 fails the whole pull, shared and workspace scopes included. On push it gets `shape`, and `writeRefusal` records that refusal per hash (ledger.ts; `refusalFor` in outbound.ts:397). So the items stay refused after the server upgrades, until they are edited. D-18 already gives the mechanism: set `CONTRACT = 2` with the server's `ACCEPTED_CONTRACTS = [1, 2]`. The client then knows a server takes team names when it accepts 2. §6 forces the bump in any case, because a new answer shape the client reads (`GET /v1/projects`) belongs in `RESULT_SHAPES`, and changing it changes `CONTRACT_FINGERPRINT`. Keeping the pull's 400 off the main cursor is not enough, because the per-hash refusal is a lasting loss.
- F-2 · Major · client rollback (levels.ts `effectiveLevel` line 155; store.ts `reconcileLevels`) · A 0.7.0 client reads a level bound to `team:x` as `unbound-alias`, and `reconcileLevels` deletes the row on the next load through in-force.ts. It logs the removal as `system` and calls no `noteUnbound`. The person sees nothing. After that, the 0.7.0 withdrawal sweep (`withdrawals`, outbound.ts) finds every sent item of that project ruled `withdraw`. The removal was not logged as `cli` or `viewer`, so `explainedBy` returns false and the withdrawals count as unexplained. A downgrade therefore either withdraws the member's team copy or trips the unexplained-withdrawal hold. When they go back to 0.8, the level is gone and only the alias row is left. A shipped version cannot be changed, so this cannot be fixed in 0.7.0. The new ADR and the release notes must state it: "downgrading drops team-name levels and withdraws what they sent; set them again after upgrading."
- F-3 · Major · release order · F-1 and F-2 together force server first. A 0.7.0 client against a 0.8 server is safe: it never names a team alias (D-11), and the feed and validate paths stay a superset. Client first is safe only with the F-1 gate. The runbook's Upgrade section needs a line saying the server is upgraded before members set team names.
- F-4 · Major · server rollback (ADR 0026 "Rollback"; runbook "Rollback") · The concept adds no `team.db` migration: the `remote_alias` columns have no CHECK and `changes_scope` indexes any text. So a previous image does not exit 3, the documented restore is not triggered, and the 0.7.0 server runs on with `team:` rows. On that server, `parseEntryUid` returns null for those uids. 0.8 clients' withdrawals are then refused `shape`, and so is any admin act that goes through push.ts:401. Worse, the 0.7.0 mirror's `repoFolder` strips only `remote:`, so it writes `projects/team-wizardingcode-<hex>` beside 0.8's `wizardingcode-<hex>`. The runbook needs a rollback paragraph for a release without a schema bump: run `serve mirror --rebuild` after going back or forward, and accept that team-named items stay frozen and unwithdrawable until the server is upgraded again.
- F-5 · Major · §1 "eight places" is incomplete · More readers filter with `LIKE 'remote:%'` and would silently ignore team names. The worst is `projectAliases` in inbound.ts:664, which names a received memory's project, so §9's "received memories become imported rows of that project" fails as written. The others are ui/api.ts:92, links/suggest.ts:42, sync/conflicts.ts:44 and sync/ledger.ts:567 (these three I saw only in grep output and did not read). The plan needs the full list, each with a ruling.
- F-6 · Nit · what needs a migration · On the client, nothing does. `project_aliases.alias` is a TEXT primary key with no CHECK (store 0001_init.sql), it already holds `imported:` rows written outside `resolveProject` (import/claude-mem.ts:112), and `sharing_levels.bound_alias` is plain TEXT. On the server, nothing does either (0001_team_init.sql). The `changes_scope` index (`scope, remote_alias, current, seq`) already serves §6's query. Only the grammar widens: `ENTRY_UID`, `isTeamAlias`, `repoFolder`'s strip, `PROJECT_FOLDER` (the slug already fits), and `strong` in resolve.ts. A 0.7.0 resolve reads a manifest's `team:` alias as weak (`aliasRank` 3), so a rollback there degrades without harm.
- F-7 · Major · §3 lifecycle · A project bound by its team name that later gains a host-led remote keeps its stored `team:` binding: `aliasToBind` prefers the stored alias and it stays in aliases. The project now has two possible identities, against §3's "never two", with no ruling on whether to rebind (which changes every uid, as in §10's rename question) or to keep the name.
- F-8 · Nit · received tree on client rollback · Folders under `received/<server>/projects/<name>-<hex>/` stay orphaned under 0.7.0, because `receivedFolder` throws for that alias and `compareSnapshot` only covers the cursor's own aliases. Harmless, but it should be named.

On the concept's four questions, through this lens:
- Q1 (two members pick one name): this lens has no migration answer. Note that once both have sent, a rename means withdrawing everything (Q3), so the cost of a collision grows with time.
- Q2 (binding to a `remote:` picked from the list): `resolveProject` writes `remote:` with `INSERT OR IGNORE`, so a hand-bound `remote:` row stops a later real clone from getting that alias. That alias is project-identity state written outside the disk, which a rollback cannot undo. Keep it out of this item.
- Q3 (the rename rule): Nothing-first is the only rename that rolls back cleanly. A server-side move rewrites uids, which a 0.7.0 server cannot parse (F-4).
- Q4 (imported memories): a separate decision with no migration impact here.
