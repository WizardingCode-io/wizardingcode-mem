# zoom-out findings for 2026-11-11-005-share-a-project-without-a-git-remote-tod
reviewer: goldfish-zoom-out
read: probes/concept.md (whole); rubrics/spec-zoom-out.md; ADR 0025 (D-16, D-19, "The meaning of `all`", "What leaves", "Identity of an item", known limits), ADR 0024 (manifest section, limits at l.183 and l.187); src/sharing/store.ts (`aliasToBind`, `setLevel`), src/sharing/levels.ts (`isHostLedAlias`, `effectiveLevel`), src/core/project.ts (`identify`, `resolveProject`), src/modules/knowledge/resolve.ts (`strong`, `matchProject`), src/team/contract.ts (`parseEntryUid`, `slugOf`, `repoFolder`), src/team/routes.ts (`/v1/health`), src/import/claude-mem.ts, plus a search of src for slug helpers

## Findings
- F-1 · Major · The problem, second fact; question 4 · The case for this item rests on "149 of 158 without a remote", but most of those are `imported:<name>` projects. ADR 0025 "The meaning of `all`" and D-19 keep every imported memory on the machine whatever the level, so a team name on those projects sends only their knowledge entries, and those projects probably have few. "tudo é partilhado" is blocked mainly by D-19, not by identity. If most of wizardingcode's 61 memories are imported, this item ships a client, server and sync change that sends almost nothing the author asked for. Question 4 is a decision of this item, and it must come first: settle D-19 for imported memories (or measure the wizardingcode split) before scoping the identity work. Otherwise a reader builds the plumbing and the author finds the project still shares nothing.
- F-2 · Major · Hypothesis 1–4, "does something already solve this" · A zero-code path exists. `identify` (`src/core/project.ts`) reads `originUrl` and nothing else: no push and no reachable host are needed. So `git init && git remote add origin https://github.com/<org>/wizardingcode` in the folder gives a host-led `remote:` alias, `isHostLedAlias` accepts it, and every existing path works today. The concept should rule on this, either as the answer or as the rejected option with its reason (a `.git` folder in a non-repository; nothing for `imported:` projects that have no folder). Without that ruling a reader cannot tell whether eight call sites, a server grammar change and a new ADR are needed at all.
- F-3 · Major · Hypothesis 3 against `resolveProject` · No rule covers a team-named project that later gains a remote (`git init` plus origin, or a clone). `resolveProject` adds `remote:` to the same project, and `has-remote` then forbids `as`. With the hypothesis's candidate order (remotes first, then the team name), the next level change rebinds to the remote. Every entry uid then changes (`project:<alias>:<uuid>`), and the items sent under the team name are orphaned on the server, not withdrawn. Today's `aliasToBind` keeps a bound alias only if it is in `remotes`, so carried over as written this case breaks. Decide it: keep the bound team name, or require Nothing first.
- F-4 · Major · Hypothesis 5, the older-server rule · False premise: `/v1/health` returns `{ ok: true }` only (`src/team/routes.ts`) and has no `version`. The rule also guards a population nobody named: the only 0.7.0 server is the one just released for this team. Simpler: release server and client together, and show the existing 400 `projects` and `shape` refusals as a plain "the server does not know team names" sentence. Adding a version to health and a gate in outbound, inbound, status, doctor and the Servers page is speculative.
- F-5 · Major · Hypothesis 6, `GET /v1/projects` · This is the most costly piece: a server read, a route, a viewer proxy, a combobox and a CLI command. Its only stated purpose is guarding against collisions (question 1). For a team of a handful of members, a typed name plus the received counts after the first pull are enough warning. Defer it until a collision is actually seen. If it is kept, it is the answer to question 1, and the concept should say that instead of offering it as a convenience.
- F-6 · Major · Hypothesis 10, the knowledge manifest · Wrong gain. The `team:` alias lives only in `project_aliases`. The ADR 0024 limit (l.183) is about losing those rows, and losing them loses the team name too, so nothing ties the manifest. Also, a project manifest is written only into a folder with no commit (ADR 0024 l.187), and later aliases reach it only through `adopt`. A reader would mark the ADR 0024 and 0025 limit as closed when it is not. Drop it from this item.
- F-7 · Nit · Hypothesis 1, the slug · `slugify` already exists (`src/modules/knowledge/entry.ts`, NFKD plus mark removal), and `slugOf` in `contract.ts` wraps it. Reuse it and add only the length cap. Do not define a third NFKD rule.
- F-8 · Nit · Hypothesis 2, rename · "Nothing first" is right and reuses what exists: `noteUnbound` / `sharing_unbound` already withdraw under the old alias. A server-side move turns every uid into a new entry plus a tombstone (ADR 0025 "Identity of an item"). That is speculative; reject it (question 3).
- F-9 · Nit · Question 2 (binding a folder to a `remote:` picked from the list) · This is a different feature, and a dangerous one. `resolveProject` writes `remote:` with `INSERT OR IGNORE` ("a remote names one project for good"), so a hand-bound remote alias would capture the real clone when it later appears on that machine, and its memories would merge into the stand-in folder's project. Keep it out of this item.
- F-10 · Nit · Altitude · The concept names call sites and function changes (eight `isHostLedAlias` sites, column names). That is acceptable for a probe, but the spec should keep the rule at the level of "one predicate for a team-matchable alias" and leave the list of sites to the plan.

## Not answerable
