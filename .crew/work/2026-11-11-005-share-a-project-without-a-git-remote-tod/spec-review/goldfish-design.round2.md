## Findings
- F-1 · Blocker · Proposed architecture, "The identity leaf" (`isSharedName`) and AC-14 · The spec says the leaf's grammar is "`isSlug`'s repeated", but `SLUG` in src/modules/knowledge/entry.ts:11 is `/^[a-z0-9][a-z0-9-]*$/`. That accepts a trailing hyphen and double hyphens, so `isSlug("abc-")` is true while `isSharedName("name:abc-")` is false. AC-14 requires both that the leaf refuses a trailing hyphen and that every string it refuses fails `isSlug`. Both cannot hold, so the contract test as written cannot pass. Either the grammars differ, and the spec must say so and drop the both-ways test, or one of them changes.
- F-2 · Blocker · Non-goals (last bullet), and AC-24's "two vocabularies of `remote_alias`" · This states something false. `sharing_received_memories` has no `remote_alias` column (src/sharing/migrations/0002_sharing_servers.sql:57-60: memory_id, server_id, remote_uid, member_id, member_name, revision, hash, remote_kind, remote_importance, remote_status). Only `knowledge_received` has one. ADR 0028 would record a column that does not exist.
- F-3 · Major · "The contract: 2, with 1 accepted", and journey 4 · The contract spoken only goes up at the join, or at `startSteps`, which runs once per sync process (src/sync/run.ts:161). `sync --auto` lives until 15 minutes pass with no hook run (`IDLE_MS`), so for anyone working all day it may not restart for hours or days. A header of 1 to an upgraded server is accepted, so no 409 ever corrects it. After the runbook's "server first", names stay held for an unbounded time, and the dock and CLI keep refusing from the stored row with "the server speaks contract 1; needs its upgrade", which is now false. The spec gives no refresh on the viewer or CLI path, and no bound on how long the hold lasts. A builder would ship journey 4's "the next sync start releases them" as if it came promptly.
- F-4 · Major · "The contract spoken" (409 handling), and AC-17 · "The request repeated once" with the lower contract is not safe unless the request is rebuilt under the names-held rule. A 0.7.0 server's `parsePullQuery` throws 400 `projects` for any alias that is not host-led (src/team/feed.ts:56-58), so the whole pull fails. Its `checkMemoryPayload` and `parseEntryUid` refuse `shape` for a `name:` alias (validate.ts:155, contract.ts:47). Refusals are recorded per hash and never re-sent (0002_sharing_servers.sql:40), which breaks the spec's "a `sharing_refusals` row is never written for them". AC-17 tests the retry only with no name-bound project, so this case goes untested.
- F-5 · Major · Push reason `name`, and NFR Rollback ("re-send what the copy lacks") · The spec never says what the client does with the new `name` refusal: whether it is stored per hash, retried, shown in `status` or the dock, or stops the binding. Under today's rule it would be stored and never re-sent. After a `team.db` restore that loses names created since the copy, or after an operator purge, or after the create race, every item under the name is refused for good, even once the name is created again. Meanwhile the dock goes on saying "Shared as `x`". The Rollback claim that clients "re-send what the copy lacks" is false for any project bound to a name created after the copy.
- F-6 · Major · "The operator's erasure", and Risks ("two unrelated projects … never merge in silence") · `serve purge name` checks only for current items under the alias. Members bound at Receive only, or bound with nothing sent, keep their binding and keep naming the alias in every pull. If the name is purged, or lost in a restore, and anyone later creates the same slug for an unrelated project, those stale bindings receive it with no confirmation: the silent merge the registry exists to prevent. Nothing on the server (such as a creation id or generation) lets a client tell a re-created name from the one it joined, and the spec names this case nowhere.
- F-7 · Major · D-6, the dock's and CLI's "`<k>` imported memories stay", and AC-4 · Journey 2 says memories received from the team "land as `imported` rows … with the judge `team:<serverId>`", and AC-4 defines the count as "the active imported memories of the project". A builder would count teammates' received copies together with the claude-mem imports. A teammate who joined `wizardingcode` and later widens would then read "60 imported memories stay on this machine" about the team's own copies, which defeats Goal 6. The spec must say which imported rows the count includes.
- F-8 · Major · Heilmeier questions 6-8 (cost, time, midway checks) · There is no estimate of effort or duration, and no midway check. The item spans a client store bump, a team schema bump with a column rename, a contract bump, about 30 source files, the viewer, the CLI and four documents, all landing as one unit. The acceptance criteria are final checks only, so a planner has no staged checkpoint, for example "leaf plus server schema 2 green before any client work".
- F-9 · Nit · "The operator's erasure" ("the key, which embeds the alias") · A memory's server key is `remote:<deviceAlias>:<uid>` (src/team/push.ts:143), which holds the device alias, not the project alias. Only entry keys and the `changes.remote_alias` column keep the name, so the sentence overstates what remains.
- F-10 · Nit · Sizing and NFR Performance ("index seeks") · The per-name counts and the last change time over `entries_project` and `memories_project` are range scans whose cost grows with the rows under each alias, not seeks. That is fine at the stated sizing, but the wording is wrong.
- F-11 · Nit · Terms ("Shared name"), and `sharedNameOf` · `slugify` turns a reserved word into `<word>-entry`, so typing "CON" gives `name:con-entry`, which the person never typed. The spec does not say so, and no journey shows it.
- F-12 · Nit · Viewer route `GET /api/servers/<id>/names` (1,000-name cap), and CLI `share names` · Names past 1,000 drop silently, so the dock says "New" for a name the server holds (the 409 `exists` then recovers). The spec never says whether `share names` follows every page.
- F-13 · Nit · Non-goals (`resolve.ts` "needs no change") · `resolveRepo` writes every project alias into the knowledge manifest and commits the aliases a project gains. A `name:` alias, including one later forgotten, is therefore written into the project repository's manifest and its git history. This does no harm, since `name:` is not a strong alias, but the spec does not say it.
- F-14 · Nit · Routes `POST /v1/names` · No member-side limit on how many names one device may create, beyond the devices bucket. A misbehaving or compromised device can fill the registry that every member sees, and the only way out is one operator `serve purge name` per name. The spec raises neither the risk nor a limit.
- F-15 · Nit · AC-2 · Part of the criterion depends on a 0.7.0 binary at the user's own install path, "when present", so CI cannot prove that half. Only the `openExistingFile` case is a deterministic check.
- F-16 · Nit · "The contract spoken" (one `/v1/me` per server in `startSteps`) · The calls run in turn before any sweep or pull, so a server that is down delays the start of every server's loop by the client's timeout. The spec gives no timeout or parallelism.
