## Findings
- F-1 · Blocker · Task 1 (AC-14), "every accepted slug passes isSlug and every refused one fails it" · This is false against the code. `isSlug` (src/modules/knowledge/entry.ts:90) is `/^[a-z0-9][a-z0-9-]*$/` plus length and reserved names, so it accepts `x-` and `x--y`, which the plan's `SHARED_NAME` refuses. The refused list includes `name:x-`, so the test cannot pass. It also gives no rule for what to pass to `isSlug` for `remote:x` or `x`. The spec's "the grammar is isSlug's repeated" is false too. Decide which grammar wins and restate the cross-check.
- F-2 · Blocker · Task 3 (`backups/*-v8-*.db`) and task 9 (`team-<ms>-v2-<pid>.db`) · The runner names the copy after the version it upgrades from, not the version it reaches: `backupVersion` returns the current `user_version` (src/store/db.ts:204-207). A 7→8 upgrade writes `-v7-` and a team 1→2 upgrade writes `team-…-v1-…`, so both asserted file names fail.
- F-3 · Major · Task 10, "`grep -n remote_alias src/team` ends empty" · `src/team/migrations/0001_team_init.sql` holds `remote_alias` five times, and migrations are forward-only ("never edited once released", db.ts:19). As written, the reader either edits a released migration or fails the check. The check must exclude the migrations folder.
- F-4 · Major · Task 10 file list · Existing test SQL that uses the old column is not named: `tests/helpers/team.ts` `seedFeed` (`INSERT INTO changes (… remote_alias …)`) and `tests/integration/team-push.test.ts` (the row types and the `SELECT … remote_alias …` at lines 66-125, plus `toMatchObject({ remote_alias })`). Task 10 only changes the helper's `contract`, so the green run breaks on files the plan says nothing about. AC-13 lists these renames as allowed.
- F-5 · Major · Task 2, `src/ui/api.ts` `listProjects`: "the SQL `WHERE ${TEAM_ALIAS_SQL}` and `isTeamAlias` in code" · Today that loop fills `remote` (api.ts:88-96). Switching it to `isTeamAlias` makes `remote: true` for a project that has only a name. The spec says `remote` keeps its meaning, and the dock (`sharingLocked` = `p.remote || p.name`, the remote-too sentence, the "host-led remote and no name" branch) depends on that. The plan needs to say that `remote` keeps `isHostLedAlias` and that `name` is a separate read.
- F-6 · Major · Phase E, task 20 ("calls `bindName` (phase F's module, built first in task 22; this task's green run follows task 22's)") · Phase E imports a module that only exists after phase F, so phase E does not typecheck on its own. That breaks the plan's own rule that every phase leaves `bun run check` green. Put phase F before phase E.
- F-7 · Major · Task 20, `setProjectSharing` "gains `as`, `create` and calls `bindName`" · Today the function is synchronous over `(db, dataDir, env, …)` and returns an `Answer`. `bindName(ctx: SyncContext, …)` is async and needs a `SyncContext` (src/ui/server.ts:224 builds one). The plan gives no new signature, no async return type, and no word on how `server.ts` passes the context and `sharingHooks`.
- F-8 · Major · "The wire and the shapes", viewer refusals (`409 has-remote|name-taken|…`, `400 no-name`) · Today `refused(status, why)` puts the sentence from `setLevelMessage` in `error`, not the reason code (api.ts:1082-1083). The new server-side ones are codes (`{ error: "contract" }`, `{ error: "exists", name }`). The plan does not say whether the `setLevel` refusals answer the code or the sentence, or where `other` goes in `name-taken`'s body. The tests in task 19 cannot be written without this.
- F-9 · Major · Task 23 / task 22 (CLI) · `bindName` takes `confirm` as an input and runs dry run → server → write in one call. The CLI must ask its question after the local refusals and before any request, and the join question names the creator and the counts, which only the server knows. The plan gives no API for this: no preview phase of `bindName`, no `hooks.ask`, no separate lookup. The reader must invent the flow, and the "server saw no request" assertion depends on it.
- F-10 · Major · Tasks 20 and 23, client methods · Only `createName` and `nameByAlias` are added to `src/sync/client.ts`. `share names` and `serverNamesView` page through `GET /v1/names?after=&limit=`, but no client method, signature or failure mapping is named for the list (including the bare-404 → `contract` rule).
- F-11 · Major · Task 14 (contract spoken) · The spec says "the header sent is the stored value". `inbound.ts:459`, `outbound.ts:307` and `outbound.ts:904` build `new SyncClient(ctx, { url, token })` with no `contract`, so they always send `CONTRACT` (2). The plan only passes `contract: row.contract` in `refreshContracts`. As written, every pull and push to a downgraded server first gets a 409 and then retries.
- F-12 · Major · Task 14, the 409 retry ("repeat the request once") in `outbound.ts` · The repeated push sends the same batch, which can hold name-bound items picked while the row read 2. A real 0.7.0 server refuses `project:name:…` uids with `shape`, and `outbound.ts:695` then writes `sharing_refusals` rows. The spec forbids those rows. The plan must say that after `speak()` the batch is filtered (or rebuilt) by `heldByContract`. The in-process server at `{ current: 1 }` still accepts name uids, so the tests would not catch this.
- F-13 · Major · AC-17 edge case "refreshContracts runs before the first sweep so a held name is never sent in the same start" · In `sync --once`, `runSync` reads `confirmedServers` before `startSteps` (run.ts:152-170) and hands those stale rows to `runOnce`. The sweep then sees `contract` 2 after `refreshContracts` has stored 1. The plan must say the rows are re-read after `startSteps`. It must also say that a thrown `me()` inside `startSteps` is caught, since a throw there today becomes EXIT_START_FAILED.
- F-14 · Major · Task 13, `tests/integration/sync-contract.test.ts` "`world()` with a server started at `{ current: 1, accepted: [1] }`" · `world(level)` starts its own server with `startTestServer({}, …)` and takes no server options (sync-world.ts:39-42). After task 14, its join stores `min(CONTRACT, 1)` = 1, so the first pull never gets a 409. The plan does not say how `world` takes the server's contract, or that the test forces the row to 2 before the first pull.
- F-15 · Major · Task 9, "`openTeamExisting` with `latest` 1" and "`serve` … (the existing seam of `openTeamForWrite`'s options, or a test that runs the binary … asserts exit 3)" · `openTeamExisting(dir)` takes no `latest` (src/team/db.ts:97), so that call cannot be written. The exit-3 test is left as an either/or. Neither option says how a binary that is now at `TEAM_LATEST` 2 is made to see a too-new file (for example, a file at `user_version` 3).
- F-16 · Major · Task 9, "assert through a spy on `store.ts`'s `nameByAlias`, or through the SQL trace of `bun:sqlite`" · This leaves a choice of mechanism, and `bun:sqlite` has no SQL-trace API to choose. Name one mechanism, for example a module spy or an injected counter.
- F-17 · Major · Task 6, `forgetName(db, projectId, now, source)` · No return type is given. The plan also does not say what happens for a project with no name (the viewer's `DELETE` answers 200 `{ forgotten: true }`; the CLI prints "forgot the shared name <slug>"), or whether `forgetName` and the name replacement at Nothing bump the change counter. `setLevel` documents "counted once", and the counter feeds the policy epoch.

Neither is in the repository (no file matches `seed-sharing-capture*`). A reader without the session cannot run the task. Name the script's location, or say what to build.
