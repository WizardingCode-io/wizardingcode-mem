## Findings
- F-1 · Blocker · The wire and the shapes, Viewer routes (GET /api/projects rows gain name), and tasks 2, 22, 23 · `ProjectSummary` in src/ui/api.ts already has `name: string` (the project's own name, line 55, filled by `SELECT p.name`, used by the dock). The plan adds `name: string | null` for the shared name to the same rows, fills it in phase A from `isSharedName`, and the dock logic (`sharingLocked` as `p.remote || p.name || typedName`, the field's `v-if` on `!p.remote || p.name`) reads it. As written, the project's name and the shared name overwrite each other, and `p.name` is always truthy. Fix: give the shared name its own field (for example `sharedName`) everywhere it appears: the route, the ui/src/api.ts type, ProjectsView.vue, and the task 22 assertions.
- F-2 · Blocker · Tasks 5, 6, 22, 23 (`formatChange`) · No `formatChange` exists anywhere in src or ui/src. `share status` prints the last change through `formatShareStatus` in src/cli/commands/share.ts, and Sharing.vue renders `lastChange.what old → new` inline at line 250. The plan treats it as an existing function to "learn the name: prefix" and to be shared by the CLI and the Vue page. It does not say which module creates it, its signature, or how the Vue bundle imports it. src/sharing/store.ts imports the Db, so the page cannot use a function placed there. Fix: Create `formatChange` with a stated home in a pure module that ui/src may import (as ui/src/api.ts already imports src/sharing/types.ts), give its signature, and name the call sites to change in share.ts and Sharing.vue.
- F-3 · Major · Task 6 (`sharedNameOf`) against task 5's case `sharedNameOf("CON")` · `slugify` in src/modules/knowledge/entry.ts appends `-entry` to a reserved slug (line 86) and returns `entry` for an empty one. The design as stated (hasLetterOrDigit, then slugify, then SHARED_SLUG) returns `name:con-entry` for "CON", not `no-name` with `word: "con"`, so the task 5 test fails against the task 6 build. Fix: state the step that finds the reserved word before slugify's fallback, for example slug the text without the fallback and test `RESERVED` on it, and say whether that step lives in names.ts or in a new export of entry.ts.
- F-4 · Major · Task 13 (the client's new kinds `conflict` and `oldServer` added in phase C) · `failureMessage` in src/sync/join.ts is an exhaustive `switch (failure.kind)` with return type string and no default. Adding two kinds to `ClientFailure` breaks typecheck at the end of phase C. Task 15 edits join.ts only at line 86, and no task gives the join's sentence for these kinds or the mapping of a join that now answers `conflict` (a 409 with no `accepted`). Fix: in task 13, add the two cases to `failureMessage` with their sentences, and say how `joinFailure` in src/ui/servers-api.ts maps them.
- F-5 · Major · Task 3 (tests/unit/team-db.test.ts line 174) · The step argues with itself ("`-v8-`? No: ... the test's fixture decides, and the pin follows the fixture") and leaves the choice to the implementer. In that test both `openDb` calls build the core store at `LATEST_VERSION`, which this plan makes 8, so the module upgrade's copy is named `-v8-`, not `-v7-`. Fix: state the pin as `-v8-` and delete the deliberation.
- F-6 · Major · Task 9 (tests/unit/team-db.test.ts) · The test "the way back across a bump" (lines 298-317) builds `two = [...TEAM_MIGRATIONS, { version: 2, name: "later" }]`. Task 9 does not name this case, and task 26 says no other existing test changes. Fix: list it in task 9 (version 3, `userVersion` 3, copy `-v2-`) or say how it is kept.

- F-9 · Major · Task 14 (tests/integration/sync-contract.test.ts setup) · Three cases cannot be built as described. (1) "a server that keeps answering 409 with [1] to header 1 ... start it with accepted: []": a server at `[]` answers `accepted: []` to the first request, so under task 15's rule there is no value to retry with and the client stops at once; the described retry-then-stop never happens. (3) "two servers, one whose fetch stalls past 5 s": the world uses one real `fetch` for the context, and no per-origin stalling fetch is described. Fix: say how each server and fetch is built.
- F-10 · Major · The viewer's refusal body ("one shape for every refusal of the sharing routes") and task 22 ("every refusal body of the route carries reason") · `destinationFor` in src/ui/api.ts refuses with `400 { error: "server" }` and `404 { error: "no such server" }`, and `sharingPreview` has its own refusals ("body must be an object", the roots and areas sentences). Fix: give each existing refusal its `reason` code and status, and rename one of the two `server` codes.
- F-11 · Major · Viewer routes, `GET /api/servers/<id>/names` (task 23 `serverNamesView`) · src/ui/servers-api.ts answers refusals as `{ error: <code>, detail? }`, while the sharing routes now use `{ error: <sentence>, reason: <code> }`.
