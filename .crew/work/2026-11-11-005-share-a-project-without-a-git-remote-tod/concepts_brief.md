# Concept brief: share a project without a git remote

## Overview

A team server (ADR 0026) and its sync (ADR 0027) carry a project's knowledge entries and memories between the members' machines, and two machines land on the same project by one name: the project's git remote on a host, as the alias `remote:<host>/<path>` (ADR 0025 D-16, ADR 0026 "The alias", ADR 0027 D-9). A project with no such remote cannot be set above Nothing: `setLevel` refuses `no-remote`, the dock disables the levels and says "This project has no git remote", and ADR 0025 lists the case as a known limit "until part 5 has another identity for it". The author's machine, read on 2026-11-11: 158 projects, 149 without a `remote:` alias; the one the author named, `wizardingcode` at `~/Projects/wizardingcode` (a `path:` alias only, not a git repository), holds the Claude Desktop and Cowork work (skills, strategies, brand systems) in 61 active memories, none imported, one stale: under "Knowledge and memories" 60 would leave. The author's requirement, in their words: "não é preciso um remote host, tem que deixar partilhar mesmo sem remote host … tudo é partilhado".

The hypothesis put to the six lenses (`probes/concept.md`): a project is shared under a name the person gives, stored as an alias beside the remotes, accepted by the server wherever a remote alias is, and bound to by a teammate who types or picks the same name. The lenses kept the shape and found three false premises, one conflict inside the hypothesis, and one gap that decides whether the feature meets the requirement at all.

## Analysis

What the six lenses found, one account, duplicates merged. Each claim below was read in the code by the lens that made it, and the three the brief rests on were read again for this brief.

**The older-server rule rested on nothing (all six).** `/v1/health` answers `{ ok: true }` and no version (`src/team/routes.ts`); the sync never calls it. Without a signal, a client that names a `name:` alias to a 0.7.0 server gets 400 `projects` for the whole pull (`parsePullQuery` refuses the query when any alias is bad), which stops the shared and workspace scopes too, and every push of a named item is refused `shape` and recorded per hash in `sharing_refusals`, where it stays after the server upgrades until the text changes. The signal exists already: `/v1/me` answers the server's `contract` (`CONTRACT`, 1 today), and the client has `me()`. Adding a new answer the client reads (the list of names, below) changes `RESULT_SHAPES` and the fingerprint, so the contract moves to 2 in any case, with the server accepting 1 and 2 (ADR 0026 D-18). The rule becomes: a client holds names out of its pulls and pushes while the server's contract is 1, says so in `status` and on the Servers page, and the server is upgraded before members give names (the runbook). This item's order is server first; the client-first rule of item 2026-11-11-004 (its D-10, open) is about a server that stops old clients, which a server at contract 2 accepting 1 does not.

**Collisions are the normal case, not the rare one (design, comprehension, structural, codebase).** The field is prefilled with the slug of the project's name, so two members with unrelated `docs`, `website` or `app` projects bind the same alias without typing; project-scope entries take writes from any member (`push.ts`); each side's items land in the other's received folder and received memories become `imported` rows of the wrong project, which that member's sessions then read as their own context, with no error anywhere. A list with counts is seen once, when the field opens, and is empty for the first of the two. Three lenses converge on the same answer: split create from join. The server holds a registry of names (a `names` table: the name, the member who created it, when); a name is created once, by one member, and joined by the others from the list; a push under a name the server does not hold is refused; the dock shows two states, "new name, you create it" and "joins `docs`, created by Ana, 14 entries, 3 memories", and reaching an existing one takes a pick. The zoom-out lens would defer the list and let a typed name plus the received counts warn; the brief keeps the registry because the merge is silent and feeds unrelated knowledge into sessions, and the registry is the seed of a server-minted project id later (structural).

**A named project that gains a remote (five lenses).** `~/Projects/wizardingcode` may get `git init` and an origin one day; `resolveProject` then adds `remote:` to the same project. The hypothesis forbade two identities only at the moment the name is given. Today's `aliasToBind` keeps the alias the level is already bound to while the project has it, so the binding stays on the name; the concept's "remotes first" would have moved it on the next level change, re-pushing every entry as a move (the server treats an alias change of a uuid as a move with a tombstone, `push.ts`) to an alias the teammates do not pull: the project vanishes for the team. The rule, stated once: the bound alias wins while the project carries it; a project with a host-led remote and no bound name binds by the remote, and `--as` is refused there (`has-remote`); a named project that gains a remote keeps the name, and the dock says so, with the one way to match by the remote instead (leave the name, set the level again).

**A rename is not a rename (comprehension, design, zoom-out, codebase).** Setting Nothing withdraws this machine's items (`noteUnbound`, `sharing_unbound`); teammates stay bound to the old name. The hypothesis's reason for "Nothing first" was wrong (a server move is N pushes, not new entries plus tombstones), but the rule holds: a move rewrites uids that `compareSnapshot` would show as a delete and a new entry with no log line, and the members bound under the old name end in the same place either way. The words change: "leave this name", never "rename". The README sentence "Lowering a level recalls nothing already sent" contradicts ADR 0027's withdrawals and is corrected.

**The knowledge manifest change was a wrong gain and a conflict (zoom-out, structural).** A `name:` alias lives in `project_aliases` only; losing those rows loses the name too, so nothing ties the manifest; a project manifest is written only into a folder with no commit (ADR 0024), and a strong alias has to name one project for good, which a name a person can leave does not. Dropped from this item; ADR 0024's and 0025's limit stays open.

**The predicate swap misses the SQL prefilters (structural, readiness, codebase).** Five readers filter by `LIKE 'remote:%'` before any predicate runs: `src/ui/api.ts:92` (the dock's `remote` flag), `src/sharing/report.ts:183`, `src/core/project.ts:87` (`hasRemote`), `src/links/suggest.ts:42`, `src/sync/inbound.ts:664` (`projectAliases`, which feeds `compareSnapshot`: a received memory under a name would never be reconciled by a snapshot, so one withdrawn on the server would stay). `ENTRY_UID` holds the literal `remote:`; `repoFolder` strips only `remote:`; `resolve.ts` ranks aliases by prefix. The structural lens's answer: one leaf, `src/core/identity.ts`, with no imports, holding a table of alias kinds (`remote`, `name`, `gitdir`, `path`, `imported`) and their three properties (travels to a team, ties a manifest, names one project for good), `aliasKind(alias)`, and one function that returns the alias that leaves for a project; the server's `contract.ts` imports it instead of a client policy module; a prefilter becomes one SQL fragment the leaf exports, or a filter in code. A third identity form later is a row, not a pass over twenty files.

**Rollback on the client loses the team's copy silently (readiness, design).** A 0.7.0 binary opening a store with a level bound to `name:` reads it as `unbound-alias`, `reconcileLevels` deletes the row as `system`, and the withdrawal sweep then withdraws everything the project sent, or trips the unexplained-withdrawal hold. A shipped version cannot be changed. The second older install item 004 found (a Homebrew CLI left on PATH beside the staged binary) makes this plausible, not only a downgrade. ADR 0018's answer to the same shape: a store version an older binary refuses (`SchemaTooNewError`), so the failure is loud. Migration 8 can carry the one constraint the design needs (one name per project).

**Rollback on the server runs on in the dark (readiness).** No `team.db` migration means a 0.7.0 image starts against rows it cannot parse: named items freeze, their withdrawals are refused `shape`, and the 0.7.0 mirror writes `projects/name-wizardingcode-<hex>` beside the 0.8 folder. The structural lens's rename of the `remote_alias` columns to `project_alias` (one statement per table) is team schema 2, and a schema bump is what makes a previous image exit 3 and the runbook's restore apply. The two findings have one answer.

**The imported memories (all six, split on where).** ADR 0025 D-19 keeps imported memories on the machine whatever the level ("Imported memories stay"). Of the machine's 71,935 active memories, 67,295 are imported, and most of the 149 remote-less projects are `imported:<name>` projects with few or no knowledge entries: named and set to "Knowledge and memories", they would send almost nothing, and nothing in the dock says why. The author's named project is not affected (0 imported of 61). The lenses agree it is a decision of this item and split on whether the work is: the brief puts the decision to the author and, whatever the answer, has the dock and the preview show the count that stays.

**What the CLI cannot reach (comprehension, codebase).** `share project` acts on the project of the current folder; an `imported:` project has no folder, so only the viewer can name it. `share projects` (the list) and `share project` (the level) would differ by one letter: the list is `share names`. `name-taken` means another project on this machine holds the name, so the sentence names it and the way out (that project forgets its name at Nothing); `has-remote` says no action is needed and that a teammate adds the same remote; a local-path or `file://` remote counts as no remote, and the dock says that where it offers the field.

**Observability (codebase).** Nowhere today says why a teammate's project never arrives: `status` shows a server's cursor and backlog and no alias, the sync logs errors only, `doctor` has no alias check. Per bound name, `status` and the Servers page show the entries and memories received, the members seen among them (the lasting answer to "who sends under this name"), and the last item's time; the held names, while the server's contract is 1, are one line.

**Smaller corrections.** The slug is `slugify`'s (`src/modules/knowledge/entry.ts`: NFKD, marks removed, 80 characters), not a third rule; a text that leaves no letter or digit is refused, never `entry`. `/v1/me` already carries the contract. `share explain` shows no alias today; `share status` does. The `unbound-alias` texts say "git remote" and would be wrong for a lost name. The pull's alias cap (100) puts a member with more bound projects into the extras rotation, one alias a minute, which `status` does not show (a nit kept for the plan). Binding a folder to a `remote:` alias picked from a list (the concept's second question) is a different and dangerous feature: a remote alias is written once and names one project for good, so a hand-bound one would capture the real clone when it appears. Out.

## Goals vs. Non-Goals

Goals:

1. **A project with no host-led remote is shared under a name the person gives**, bound to the server under the alias `name:<slug>`, with the levels, the roots, the areas and the confirmation unchanged.
2. **The server knows the names**: a registry (create once, join from the list), the alias accepted beside `remote:` in the uid grammar, the push, the pull, the feed and the mirror; the list of names any member reads; contract 2, with 1 accepted.
3. **A teammate binds a project of theirs to a name** from the list or by typing it, and receives the team's copy as for a remote-named project.
4. **The identity rule lives in one leaf** (`src/core/identity.ts`), applied by every reader, SQL prefilters included; the bound alias wins while the project carries it.
5. **Failure is loud, not silent**: store version 8 on the client, team schema 2 on the server, names held while the server's contract is 1, the per-name read-outs in `status` and the viewer.
6. **The person understands what they did**: the dock's two states (create, join), "Shared as `wizardingcode`", the sentences for `name-taken`, `has-remote` and `no-name`, the count of what stays, "leave this name" instead of a rename, the README and the runbook.

Non-goals of this item: binding a local folder to a `remote:` alias without a clone; a server move as a rename; a project with no folder created from the viewer (a decision below, out by default); the knowledge manifest's strong aliases; a server-minted project id (the registry is its seed); a change to what imported memories do (a decision below); an admin's deletion of a name from the registry.

## Alternatives Weighed

- **`git init` plus a remote URL in the folder, no code.** `identify` reads `originUrl` and nothing else, so a URL on a host that is never pushed gives a host-led alias today. Rejected as the answer: a `.git` folder in a folder that is not a repository, nothing for the `imported:` projects that have no folder, and the author asked for sharing without a remote. Kept as the workaround the README names until the release ships.
- **Names that emerge from slugs, the list as a warning (the hypothesis).** Rejected: the merge of two unrelated projects is silent and the warning is seen once; the registry makes joining explicit at a small cost (one table, two routes, one refusal).
- **The server mints a project id; names are labels.** Rejected for this item: a server round trip inside `setLevel`, a mapping for remote-named projects, a larger contract change. The registry keeps the door open.
- **A version in `/v1/health`.** Rejected: `/v1/me` carries the contract already, and the list of names moves the contract anyway.
- **Keep the column names and the store version; document the rollbacks.** Rejected: the client rollback withdraws the team's copy with no word to the person, and the server rollback runs on with frozen items; the two schema moves are small and make both failures loud. The person may still choose this (decisions D-4 and D-5).
- **A rename as a server move.** Rejected: uids rewritten, a delete and a new entry on every machine with no log line, the same outcome for the teammates as leaving the name.
- **`name:` in the knowledge manifest's strong aliases.** Rejected: a mutable name cannot be a permanent tie, and the manifest is not written where the limit bites.
- **Binding a folder to a `remote:` from the list.** Rejected as a separate and dangerous feature.
- **The list shows remote-named projects too.** Rejected: it would disclose every private repository path on the server to any member, a new disclosure ADR 0026 D-11 does not cover; the list shows names only.

## Key Decisions

Taken by the lenses' agreement and by this brief, as assumptions the author can refuse:

- The alias prefix is `name:` (not `team:`, which the received memories' judge `team:<serverId>` already uses); the viewer says "shared name" and "Shared as `x`".
- A rename is "leave this name" (Nothing, which withdraws) and a new name; Nothing keeps the name; a project at Nothing can forget its name (the dock, and `share name forget` in its folder).
- The bound alias wins while the project carries it; a project with a host-led remote and no bound name binds by the remote, `--as` refused there; a local-path or `file://` remote is no remote.
- CLI: `share project <level> [--as <name>] [--server] [--yes]`, `share names [--server]`, `share name forget`; the viewer: the dock's field and states, `GET /api/servers/<id>/names`, `as` on `PUT /api/projects/<id>/sharing`.
- The slug is `slugify`'s; no letter or digit refuses; the received folder stays `projects/<slug>-<8 hex of the alias>`.
- Contract 2 with 1 accepted; names held while the server answers contract 1; server first in the runbook.
- The list of names: names only, paged, under the pull's rate bucket; entries and memories counted by two indexes schema 2 adds; the members seen are counted on the client from the received rows.

Decisions only the author can take, recorded as D-1 to D-7 with their defaults:

- D-1 The identity: a shared name beside the remote, which changes ADR 0025 D-16 ("a level above local needs the project's remote alias").
- D-2 The collision rule: the server's registry (create or join), or names from slugs with the list as the warning.
- D-3 The contract and the order: contract 2 accepting 1, names held until the server is at 2, the server upgraded first.
- D-4 The server's columns: `remote_alias` renamed `project_alias` in team schema 2 (a 0.7.0 image then refuses the database, the runbook's rollback), or kept.
- D-5 The client's store: version 8, so a 0.7.0 binary refuses the store instead of dropping name-bound levels and withdrawing what they sent.
- D-6 The imported memories: D-19 kept, with the count that stays shown in the dock and the preview, and a later item for a per-project opt-in; or D-19 changed now.
- D-7 A project with no folder, for a teammate who only receives or for Claude Desktop's chat: out of this item, or "new project from a name" in the viewer.
