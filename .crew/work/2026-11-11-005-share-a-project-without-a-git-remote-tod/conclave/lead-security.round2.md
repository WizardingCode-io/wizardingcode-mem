# security lead's validation of 2026-11-11-005-share-a-project-without-a-git-remote-tod: spec
verdict: returned
## Returns
- R-1 · .crew/work/2026-11-11-005-share-a-project-without-a-git-remote-tod/spec.md:147-148 · `GET /v1/names/:alias` says only "the item, or 404". Add that the path parameter is decoded and checked with `isSharedName` before any SQL, and that a malformed alias, a `remote:` alias and an unheld name all answer the same 404 `unknown-name`. The same check applies to `after=` on the list, which must be a string of bounded length. Otherwise the route can be used to probe whether a remote alias exists. AC-5 (spec.md:257) should name this case: a `remote:` alias on the by-alias route gets the same body as an unknown name. The code today validates through `ENTRY_UID` and `parsePullQuery` (src/team/validate.ts, src/team/feed.ts:47). A new route has no such guard unless the spec requires one.
- R-2 · .crew/work/2026-11-11-005-share-a-project-without-a-git-remote-tod/spec.md:66,174,177 · The name is disclosed to every member at creation and cannot be removed afterwards. The dock's field is prefilled from the project's folder name, and "levels enabled once the field holds a name" means a single click on a level creates the name. The widening confirmation at line 66 and line 177 is worded as "N entries and M memories would leave for <server>". It does not name the slug or say whether it creates or joins. Change two things. (a) The widening confirmation in the dock must name the slug and say "creates `x` on <server>, visible to every member" or "joins `x`, created by <member>", as the CLI's question does (line 197). (b) A join of a name the server already holds must require an explicit confirmation at every level, Receive only included. As written (journey 2, line 67) Receive only binds without one, so a prefilled `docs` joins another team's unrelated `docs` and pulls its content on one click. Add both to AC-9 and the copy test.
- R-3 · .crew/work/2026-11-11-005-share-a-project-without-a-git-remote-tod/spec.md:34,269 and docs/runbooks/team-server.md · The registry has no erasure path. Names are never renamed or deleted, and the admin's `serve name delete` is out of scope (line 269). A name is personal or confidential text (for example a project called after a client or a person). Every member can read it, with its creator and counts, from `GET /v1/names`. `serve purge` replays erasure per item key (src/team/store.ts:895-913) and does not touch a `names` row. Do one of two things. Either state in the spec and AC-12 that the runbook documents the operator's erasure of a name (the exact `names` row to delete and the audit entry to write, with the order against `serve purge` of its items). Or take `serve purge --name <alias>` into the item. The ADR must say plainly that until then a typo or a sensitive name stays on the server.
## Notes
- Authentication, rate and tokens: the three routes sit behind `authenticate` and the devices bucket (src/team/routes.ts:164-190). A disabled member gets 403 (src/team/auth.ts:30), so creation by a disabled member is already refused. Create is member-level, list and read are any member, and nothing is admin-only. This matches ADR 0026 D-12. The brief's wording "under the pull's rate bucket" and the spec's "devices bucket" (spec.md:144) agree in effect, since the code has one devices bucket.
- Disclosure: the list shows names only (spec.md:147, 221), and the creator's id and name are already on feed items. The alternative that would have exposed remote paths is rejected at line 221. I found no leak of `remote:` or `path:` aliases through the list. R-1 closes the one remaining probe, the by-alias route.
- Path safety: the grammar (spec.md:84) has no `/`, `.` or `:`, is capped at 80 characters and refuses reserved Windows names. The received folder is `projects/<slug>-<8 hex>` (spec.md:150), checked by `PROJECT_FOLDER` in src/sync/naming.ts:15,42. src/team/contract.ts:180-193 builds the folder from slug and hash only. The hash covers the full alias, so `name:x` and `remote:…/x` cannot share a folder. Stripping both prefixes before `slugOf` is sound.
- Push refusal: `name` is a new refusal reason, and `shape` still covers a malformed alias (AC-6, spec.md:258). A pull under an unheld name answers nothing and is not refused. A pull needs no join, because any member may pull any alias. That is the existing minimisation-not-permission rule (ADR 0026 D-11). The spec's non-goal at line 39 keeps it, and the by-name guessability is a consequence worth one sentence in ADR 0028.
- Migration safety: src/team/migrations/0001_team_init.sql references `remote_alias` only in table columns and in the index `changes_scope` (line 64), which `RENAME COLUMN` follows. There are no triggers or views, so schema 2 is safe. Rollback is loud on both sides: store 8 gives `SchemaTooNewError` (D-5), and team schema 2 makes a 0.7.0 image exit 3 (D-4). Both are backed by the upgrade copy. The wire key `remoteAlias` stays, so 0.7.0 clients still work.
- What leaves: `path:` and `gitdir:` still never leave (spec.md:242, ADR 0025 D-19). A name leaves only by the person's choice and only once the server confirms it (AC-9). The viewer asks the server before it writes (spec.md:185) and a failure writes nothing. The identity leaf's `TEAM_ALIAS_SQL` is only a prefilter, and each row is judged in code again (spec.md:86), which is the right shape.
- Registry growth is bounded only by the devices bucket (advisory O-3 in conclave.md:35). This is acceptable for a closed team. Pages are capped at 200 and the viewer's follow-all is capped at 1,000.
