## Findings
- F-1 · advisory · src/sync/ledger.ts:830 · `clearServerLedger` (the `share server remove` path, src/sync/join.ts:351) deletes the hold and authorised keys but not the new `names.<state>:<serverId>:<alias>` meta flags this change introduces, so a removed server's missing, recreated and purged flags stay in `meta` with no level left to read them, and they come back if the same server id is added again (rubric Q1/Q6: data left behind by a cleanup path).
- F-2 · advisory · src/sharing/report.ts:681 · `importedStayCounts` filters `memories` on `status = 'active' AND origin = 'imported'` with no index on `origin` (only `memories_rank(project_id, status, …)` exists), so every `wouldLeave` (each dock preview, `share project`, `status`) adds one full pass over the growing memories table; the result is right, it is just slower (rubric Q2).
- F-3 · advisory · src/team/routes.ts:73 · `nameItemOf` runs `nameCountsOf` (two queries) and `memberById` for each row, so `GET /v1/names` makes up to 3×200 queries per page; each query uses an index (`entries_project`/`memories_project`, the PK) and SQLite runs in the same process, so the cost is small, but one grouped read per page would do the same job (rubric Q2, per-row loading in a list path).
- F-4 · advisory · src/sync/ledger.ts:625 · `receivedNameCounts` filters `knowledge_received` by `remote_alias` while only the `(server_id, uid)` primary-key prefix is indexed, and it reads the same rows twice (count, then DISTINCT member_id). That means each bound name walks all of that server's received entries twice on every `status`/`doctor`/Servers read (rubric Q2).
- F-5 · advisory · src/team/migrations/0002_team_names.sql:11 · the `names` row holds the creating member and device (`created_by_member`, `created_by_device`), and `serve purge name` only sets `purged_at`, so they are kept forever. ADR 0028 ("The erasure of a name, and its limit") says the alias string survives in "the marked `names` row", but it never names the creator columns or how long they are kept. It is not called a defect because members and devices are already kept indefinitely under ADR 0026, but one sentence would close the gap (rubric Q5).

Checked and found sound: team migration 2's four `RENAME COLUMN`s carry `changes_scope` with them, and no data is copied or dropped. It is forward-only, and the reason is stated with the upgrade copy and the rollback in ADR 0026 "Rollback" and ADR 0028 "The schemas and the rollbacks". The two partial indexes match the predicates of `nameCountsOf` exactly. Client migration 8's partial unique index cannot fail on existing data, because no earlier code writes a `name:` alias. Sharing 3 is a nullable `ADD COLUMN`, and `nameIdColumn` reads `NULL` on an older namespace. The registry check in push runs inside each item's transaction. The `POST /v1/names` create and `serve purge name` each run in one transaction, with no network call inside. `setLevel`'s `dryRun` is a deferred read transaction and every write in it is guarded. `foreign_keys` is ON for the `names` references, and no code path deletes members or devices.
