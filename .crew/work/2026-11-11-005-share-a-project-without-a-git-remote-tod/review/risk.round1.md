# risk findings for 2026-11-11-005-share-a-project-without-a-git-remote-tod
reviewer: review-risk
read: spec, plan, 14 files

## Findings
- F-1 · advisory · src/sync/outbound.ts:632 · When a name is `missing` (a push answered `name`, for example after the server is restored to a copy older than the name), the sweep re-sends the project's items on every sweep with no backoff: up to one 200-item batch every few seconds while the store changes, and every 60 s otherwise, until the person sets the level again. It writes no refusal row and does not touch the breaker, so the only signal is the `missing` flag in `status`, `doctor` and the dock. Nothing limits this repeated traffic to the server.
- F-2 · advisory · src/cli/commands/serve.ts:510 · `serve purge name <alias> --yes` has no dry run and no undo. A mistyped alias retires a live team name for good: a create of that alias is refused `purged` from then on, and every bound member's pushes are refused `name-purged`. Neither the spec nor the runbook gives a way back other than restoring `team.db`, which loses everything written since. A dry run that prints the counts before marking would make this safer.
- F-3 · advisory · docs/runbooks/team-server.md:74 · The runbook's Rollback section is unchanged. ADR 0026 and ADR 0028 now say that a rollback loses the names created since, and that the projects bound to them read `missing` until each creator sets the level again. The runbook does not say this, so the operator doing the rollback is not told which members must act or in what order.
- F-4 · advisory · src/sync/inbound.ts:789 · After a restore to a schema-2 copy older than a name, the instance is renewed and a snapshot runs. A Receive-only teammate's received copies under that name are then dropped, because only the `recreated` flag keeps a name out of `compareSnapshot`. The teammate never pushes, so `missing` is never set on their side, and nothing they can see explains why the copies went. The copies come back only if the creator sets the level again, which is a step on someone else's machine. spec.md:296 says "the teammates stay bound" but not that their copies are dropped in between.
- F-5 · advisory · .crew/work/2026-11-11-005-share-a-project-without-a-git-remote-tod/spec.md:295 · The client rollback (restore the upgrade copy from `backups/`, losing what was written since) is promised to "the ADR and the release notes". ADR 0028 says it, but no task in the plan writes the release notes and README does not mention the version 8 store. A person downgrading through Homebrew would get a store that refuses to open, with no sentence telling them what to do. The release item has to carry that sentence.

## Outside the change
- src/team/server.ts:99 · The server's start refuses to migrate while `serve.lease` is fresh. This is the first team schema bump, so if the old container is killed without releasing its lease, `restart: unless-stopped` restarts the new image repeatedly until the lease expires. The cause shows only as the "another serve holds" line in the container log.
- src/store/db.ts:1 · An older binary still on PATH (Homebrew, or a pinned agent package) refuses the version 8 store, and its hooks fail open with exit 0 and empty output. That agent then silently stops capturing and injecting; only `doctor` would show it. Every store bump has carried this risk; this item is one more bump.

## Not answerable
- Third parties: cost of the first run · The only outside party is the team's own server. No request count was measured for a first full sweep of a named project against a server that lacks the name (the F-1 retry loop).
