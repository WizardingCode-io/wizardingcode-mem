# risk findings for 2026-11-11-005-share-a-project-without-a-git-remote-tod
reviewer: review-risk
read: spec, plan, 15 files

## Findings
- F-1 · advisory · src/sync/outbound.ts:632 · Carried from round 1 and unchanged. When a push is answered `name` (the server lost the name), the sweep sets `missing` and tries again at every later sweep, with no backoff and no breaker. Until the person sets the level again, the server gets this repeated, refused traffic, and the only sign is the `missing` flag in `status`, `doctor` and the dock.
- F-2 · advisory · src/cli/commands/serve.ts:515 · Carried from round 1 and unchanged. `serve purge name <alias> --yes` marks the row purged at once, with no dry run and no undo. A mistyped alias retires a live name for good: every bound member's push is refused `name-purged`, and a new create of that alias is refused `purged`. The only way back is restoring `team.db`, which loses everything written since.
- F-3 · advisory · docs/runbooks/team-server.md:81 · The amended Rollback paragraph (round 1's F-3) now names the lost names. But it says a member bound to a lost name "reads `missing`" and should "set its level again". Against the rolled-back 0.7.0 image, the client speaks contract 1, so the member reads `names held`, and setting the level again is refused `contract`. `missing` appears only after the server is upgraded again, and only for a project that has something to push. docs/adr/0028-shared-names.md:57 makes the same claim; spec.md:296 states it correctly ("fall back to contract 1 and hold names"). An operator following the runbook would send members to a step that fails until the next upgrade. The failure is visible and harmless, but the order of steps is wrong.
- F-4 · advisory · docs/runbooks/team-server.md:81 · The runbook tells the operator to "tell them which names the copy predates", but gives no way to find those names. The `cp` two lines above overwrites the newer `team.db` without keeping it, `serve` has no subcommand that lists names (`serve status` prints only a count), and the image has no SQL shell. Running `share names` from a member's machine, or keeping the newer file, before the `cp` would give the list. Without the list, the creators who must act are found by guesswork.
- F-5 · advisory · src/sync/inbound.ts:791 · Carried from round 1 and unchanged. After a restore older than a name and the instance renewal, a teammate at Receive only never pushes, so `missing` is never set on their side. Their received copies under the name are dropped by the snapshot, because only `recreated` keeps a name out of `compareSnapshot`. The same holds for a creator bound at a level with nothing to send. Nothing on those machines explains the loss. The runbook's line 81 promise that "a member … reads `missing`" does not hold for them.
- F-6 · advisory · .crew/work/2026-11-11-005-share-a-project-without-a-git-remote-tod/spec.md:295 · Carried from round 1. The client rollback (restore the upgrade copy from `backups/`) is promised to "the release notes". README.md still has no sentence about the version 8 store or `SchemaTooNewError`, so the release item still owes that sentence.

## Outside the change
- src/team/server.ts:99 · Debt from round 1. A stale `serve.lease` after a kill makes the new image restart repeatedly until the lease expires. Runbook line 99 now documents it.
- src/store/db.ts:1 · Debt from round 1. An older binary still on PATH refuses the version 8 store, and its hooks fail open, so that agent silently stops capturing and injecting. Only `doctor` shows it. Every store bump has carried this risk.
