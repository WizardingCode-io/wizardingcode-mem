## Findings
- F-1 · Major · §5 "Kept", step 3 (`insert` with `source_ordinal = 1`) · `insertMemory` (src/store/memories.ts:43-90) handles an `ON CONFLICT (source_turn_id, source_ordinal)` by looking up the memory at `source_ordinal = 0`, the old memory, and overwriting its title, body, files and vector in place. `--undo` archives the replacement but does not delete it, so a second run after an undo hits the conflict at ordinal 1. That second run then silently rewrites the old memory the undo had just brought back, and calls `supersede(old, old)`. The spec gives `NewMemory` a `sourceOrdinal` but does not say that the conflict path, which is hard-coded to ordinal 0, has to change, or what a rerun after an undo should do. A competent implementer would reuse `insertMemory` as written and break reversibility, which is the guarantee the design leans on.
- F-2 · Major · §5 Reversibility / `--undo` · Undo puts back only the rows in `memory_reviews` (the old memory and its replacement). Several side effects of the run are not recorded. Consolidation's `action.supersedes` can supersede other active memories, and nothing records them. A `duplicate` calls `reinforce`, which adds a `memory_sources` row and bumps `evidence_count` on the target (memories.ts:105-116). Undo reverses neither. The claim "Reversible … nothing deleted", and the rehearsal check "counts by status match", would both pass while neighbours stay superseded and evidence stays inflated. Counts that match are not the same as the original rows coming back.
- F-3 · Major · §5 "What it does" (oldest first + consolidation) · The pass consolidates each new v2 draft against neighbours that are still v1 memories. Take a v1 record that a v2 draft supersedes. It stops being active, so the run never selects it, never judges it and never writes a review row for it. Its knowledge leaves circulation without a verdict, and undo cannot see it. The reverse also happens: a v2 draft judged a `duplicate` of a v1 record reinforces that record and archives the old memory, then the record is archived later in the same run, and the knowledge is lost both ways. The spec never says whether neighbours during the pass should be limited to memories already reviewed, or to v2 memories.
- F-4 · Major · §5 `--concurrency <n>` · The existing `rejudge` judges in parallel and writes once per batch of 200 (rejudge.ts:137-165). For `rejudge distilled` the spec does not say whether consolidation (`findNeighbours`, then supersede or duplicate) runs per memory, in order, after the earlier writes. If it follows the batch pattern, two near-duplicate drafts in one batch both get inserted, because neither sees the other. The live path avoids this by working one turn at a time under the drain lease.
- F-5 · Major · §5 "Only one run at a time (the drain lease is taken for the run…)" · The drain lease lasts 120 s and the queue renews it per turn (queue.ts:13, 109-119). The spec does not say how the rejudge renews it, what happens when a live drain already holds it (wait or refuse), or how long live distillation is blocked. By the spec's own numbers (2,513 requests, about 2,000 tokens each) a full run could take tens of minutes at the default concurrency. `--limit` has no stated default, and the existing `rejudge` default is "all", so live distillation would stall for the whole run. Whether `--dry-run` takes the lease is also unstated.
- F-6 · Major · §5 The dry run · The dry run "makes every request", and the real run makes them all again. TypeSafe is a model, so the real run's verdicts can differ from the report the author reviewed. Nothing ties the applied outcome to the reviewed one: no replay of the dry run's verdicts, and no diff. The safety gate the design relies on (dry run first, then apply) does not cover what actually gets applied. It also doubles the cost.
- F-7 · Major · §6 "runs the version 2 pipeline on the 400 source turns, in process (`distillTurn` on the copy…)" · Running `distillTurn` on a turn that already has a memory overwrites that memory in place through the ordinal-0 path. It does not update `judge`/`judge_version`. When v2 skips the turn, the v1 memory stays. `distillTurn` also consolidates against the copy's other v1 memories, so a v2 knowledge draft can come back as a `duplicate` of a v1 record, and the proof would wrongly count that as a "`keep` lost". The spec does not define how "stored memories" after v2 are measured: from the return value, the draft, or the store. So the headline metrics can be computed several different ways and get different results.
- F-8 · Major · Why / §1 "Only patterns with 97–100% precision" · The precision figures come from a hand-labelled sample whose labels were lost (line 24), so nobody can check them again. `status-label` (4 hits) and `template-label` (2 hits) report 1.00 on samples too small to support any claim of 97–100% precision. `protocol-tag` (0.88) and `verdict` (0.80) break the spec's own entry rule (line 65). They are let in on an argument ("at sentence level the tagged sentence is the record") that nothing measured. These filters drop sentences before the judge sees them and cannot be undone for live turns. The removal rule in §1 ("a pattern that drops a `keep` sentence is removed") depends entirely on the proof's new labels.
- F-9 · Major · §6 Samples and labels · The baseline (9%, 62%) was "labelled by hand" (line 7). The new labels come from "a labelling agent", with the author spot-checking only 20 of 200. Before and after use different labellers, and no agreement rate between them is set or reported. The "before" figure for "title is knowledge" is also the share labelled Knowledge (9%). It is not the share whose title was the knowledge sentence, so the baseline measures a different thing from the target.
- F-10 · Major · §6 Metrics / Heilmeier Q8 · Targets are set (≥ 60%, 0 lost, ≤ 15%), but nothing says what happens when one is missed. There is no go/no-go rule for shipping judge v2 to the live path, and none for running the cleanup. The "0 `keep` lost" target, with a model doing the judging and a model doing the labelling, is likely to be missed by a few. The reader cannot tell whether that blocks the release, blocks only the cleanup, or is just noted in the ADR.
- F-11 · Major · Decisions "Nothing else moves" / §2 Versions / §5 "Not in this change" · The spec says imported memories are "a separate decision". Yet the existing `rejudge` of imported memories asks the same questions (rejudge.ts:77-106), so it switches to the v2 wording and stamps `judge_version = '2'` from this release on (line 131). That is a change to imported memories, made in this change, and it contradicts both statements.
- F-12 · Major · Risks / rollout (spec-feature "rollout and rollback") · Judge v2 and the noise filter take over the live path at release. Live turns that v2 or the filter drop are marked `skipped`, and the spec gives no way to distill them again. `--undo` only covers `rejudge distilled` runs. There is no flag to go back to v1 questions on the live path. If v2 turns out to lose knowledge in daily use, those turns cannot be recovered.
- F-13 · Major · §5, interactions not named · Superseding or archiving distilled memories affects stores the spec does not mention. One is `rule_proposals` (0007_links.sql): proposals hold sets of `memory_ids`, and the unique index on those sets is what keeps the same rule from being proposed twice, so replacement ids can bring an already rejected rule back as a new proposal. Another is `history_replacements` (0004_history.sql): claude-mem imports were archived because distilled history replaced them, so archiving that distilled history leaves both copies gone. A third is evidence counts: the replacement starts at `evidence_count = 1` and keeps only the origin source, so the other turns' `memory_sources` reinforcement on the old memory is lost from ranking. None of these is addressed.
- F-14 · Major · Alternatives considered (spec-feature) · The only alternative mentioned is generative rewriting, set aside under the founding rule. Other workable designs are not weighed: thresholds per kind, keeping v1 memories and down-ranking records at retrieval, a separate classification pass, and running the cleanup as a review queue rather than a batch supersede. The rubric fails a spec that offers one path with no rejected alternatives.
- F-15 · Major · §1 `stripHost`, `summary` and `hand-back` · `<details>`/`<summary>` is ordinary assistant markdown, not only host framing, so the pattern breaks the spec's own rule "the host's text, never a user's or an assistant's words". The `hand-back` rule strips lines "up to the report" with no stated boundary. If the host changes its frame wording, either the frame leaks through or the report's opening knowledge is stripped. Calling the pattern "structural" is a claim about an outside system's format, and the spec gives no source or version for it.
- F-16 · Nit · §5 The dry run, "about $0.21 at the published price" · There is no source for the price (which model, which tier) and no output-token cost. 2,000 input tokens per memory is an assumption that sits beside the "≈ 1,200–1,450 … will cost more" of §6. The dry run, the real run and every rerun after an undo are not added together.
- F-17 · Nit · Heilmeier Q7 · The spec says nothing about how long the build will take, or how long the cleanup will take to run.
- F-18 · Nit · spec-feature sections · There are no Open questions, no Critical user journeys (given/when/then for the live turn, `rejudge distilled`, `--undo`), and no separate Risks and mitigations section. The risks are scattered through the text, or missing (F-1 to F-13).
- F-19 · Nit · §4 Durability penalties · The heuristic penalises commit hashes and status verbs by −0.25. The spec itself says these signals must stay with the judge because "Decisão aplicada (commit 5808e41)" was knowledge. With a 0.5 threshold, installations without a key will drop such sentences. The golden floors measure precision and recall overall, not that case. The hex regex (7–40 characters with a digit and a letter) also matches ordinary identifiers.
- F-20 · Nit · §2 headings "`worth` (noul)", "`knowledge_<i>` (noul…)" · "noul" is never defined. §5's `outcome = 'kept'` is only implied for turn-less memories, and the outcome recorded for a `duplicate` (archived?) is not stated. "The last run" for `--undo` is not defined in terms of `run_id`.
- F-21 · Nit · §6, "a fresh data directory under the work directory" · The location of the work directory is not given. A full copy of the private store, and `full.md` with its titles, could end up inside the repository tree. The spec only says the labels file is refused there.
