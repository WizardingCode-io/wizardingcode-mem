## Findings
- F-1 · Major · §2 "Versions" and D-2 (lines 48, 174) · The spec says the import rejudge "keeps the version 1 wording" and "stamps judge_version = '1', as today", and that "the pipeline's types do not change". The code does not support that. `rejudge` calls the same `judge.distill(...)` entry point as the drain (src/judge/rejudge.ts:106), through the same `withFallback` judge. It stamps the version it reads from `options.judge.versions.typesafe` (rejudge.ts:122), which this change sets to "2". Nothing in the spec says how a v1 question set is chosen for one caller: a new Judge method, a parameter, or a second judge instance. Nothing says where a hard-coded '1' comes from either. A builder who follows "as today" will ship a rejudge that asks the v2 questions, or stamps '2', or both. The test in §8 would catch it, but the design gives no shape to build towards. The `Judge` interface has to change, and the spec says types do not change.
- F-2 · Major · §6 "Samples and labels", line 216 (`prepareTurn`, `draftTurn`) · The spec calls these "the same code as the drain", but neither function exists in src. Today `distillTurn` (pipeline.ts:159) does everything in one function: it reads detail and writes `turns`, it judges, it calls `consolidate` (which can make its own consolidation request to the judge), and it inserts. The spec never says where the split falls. In particular it does not say whether the proof's "memory stored" is measured before or after consolidation. On the read-only copy the v1 memory made from the same turn still exists, so a v2 draft that goes through `consolidate` can come back as a `duplicate` of its own v1 memory, or supersede it. The metrics "memories stored" and "title-only" are undefined until the spec says where the cut is, whether consolidation runs, and whether consolidation requests count toward cost.
- F-3 · Major · §6 "Metrics", title-is-knowledge and "lost" rows (lines 224-225) · The labels describe the v1 stored memory: one title plus at most 5 facts. Version 2 reads the whole turn, up to 40 candidates (segment.ts DEFAULT_MAX_CANDIDATES). Each `knowledge`/`mixed` label quotes a single sentence. So if v2 picks a different and equally valid knowledge sentence, especially one v1 never stored, the metric counts it as a miss. For `knowledge` memories, the rule "a `knowledge` memory's sentence" does not say whether the `Context:` line or any body line counts. A reader would build a metric biased against v2. A miss on the ≥60% target would block the merge (line 234) on a measurement artefact, while a pass could hide titles taken from the narrative of a `knowledge` memory.
- F-4 · Major · Why, finding 2 (line 28) vs §6 Metrics · The second problem the spec names is importance saturation: 79% of memories sit at importance 4. No metric measures the importance distribution under v2. The new level 4 ("a rule of the project … or a correction the author gave") describes much of what v2 is meant to keep, so saturation may simply move. A reader would ship v2 believing that problem is answered, with no evidence either way.
- F-5 · Major · §2 `knowledge_<i>` and §6 "Input tokens per judged turn" (line 229), Risks (line 249) · The cost of the change is reported, but nothing limits it or blocks the merge on it. The per-candidate question repeats its instructions and criteria for every candidate (questions.ts:71-78). The v2 criteria are about twice as long, and there can be up to 40 candidates. Multiplying out gives several thousand extra input tokens per turn, set against the ≈1,200–1,450 baseline. That is an estimate from the code, not a measured figure. The spec sets no budget, no ceiling and no merge condition on tokens, latency or TypeSafe quota. It also does not consider sharing the criteria once (for example in the state) instead of repeating them per candidate. Heilmeier Q6 (cost) is left open: what the drain costs in TypeSafe tokens per turn, and what the proof costs (400 TypeSafe requests, two labelling passes of 200, any relabelling).
- F-6 · Major · Goals (line 37) vs §4 and §6 (lines 196, 230) · The goals cover "memories distilled from now on", but the only real-data merge gate applies to TypeSafe verdicts. Installs without a key are the default (src/judge/index.ts:36), and a TypeSafe outage falls back to the heuristic in the live drain (fallback.ts). On those paths the heuristic v2 decides, with real-data shares "reported, no target". Its only gate is the golden set: 8 hand-written turns plus floors. The heuristic v2 changes (report penalties, worth discount) could lose knowledge for every keyless user without failing anything that blocks the merge. Risks names only the commit-hash case.
- F-7 · Major · §3 policy, "The title must be knowledge" (line 182) vs §2 `title` `none` option (line 140) · The spec does not say what happens when the judge answers `none` for the title while some candidate reaches `KNOWLEDGE_THRESHOLD`. Read literally, the policy falls back to the highest-knowledge candidate and ignores `none`. That may be the intent, but the `none` option was added only to say "no candidate states knowledge", and the spec never says whether it vetoes the turn. Two builders would build two behaviours, and they store different amounts.
- F-8 · Major · §7 Risks, first row (line 244) · The mitigation reads "Skipped turns keep their text in `turns` until `compact`, so the separate cleanup item can distil them again". The window it depends on goes unstated. `compact` deletes finished turns with no memory after 90 days (src/store/compact.ts:12, 62-64). The user runs it from the CLI or the UI at any time. Knowledge v2 drops in daily use can be recovered only for 90 days, and only if the cleanup item (D-1, not yet designed) ships first. A reader would assume losses can be recovered indefinitely.
- F-9 · Major · §6 "Samples and labels" (line 215), Risks · There is no privacy statement for the labelling. The spec guards where files go (outside the repo and the live directories) but not where the text goes. A "labelling agent" receives 400 memories and their source turns from the author's store, which spans 59 projects. That text is sent to a model, and the spec names neither the model nor the provider, nor any limit on which projects may be sampled. The rubric asks for security consequences. Redaction at capture handles secrets, not confidential project content.
- F-10 · Nit · §1 "The notes the session had been shown" (line 108) · `turns.ended_at` can be NULL (QueuedTurn.endedAt is `number | null`, and the column is nullable in 0001_init.sql). Under the `injections.at <= turns.ended_at` bound, a NULL silently removes no notes at all, and the spec states no behaviour for that case.
- F-11 · Nit · §6 Samples (line 214) · "Active distilled memories with `judge_version = '1'`" includes memories made by heuristic v1 as well as TypeSafe v1 (3,941 active distilled vs 3,733 judged by TypeSafe, line 28/31), but the v1 column is meant as the TypeSafe baseline. The spec does not say whether the sample is filtered on `judge = 'typesafe'`.
- F-12 · Nit · §6 Metrics, records row (line 226) · The denominator is not stated. "≤ 15%" could be a share of the memories v2 stored, or a share of the record/fragment turns in the sample. The v1 figure (62%) only makes sense as the first.
- F-13 · Nit · §7 Risks (line 244) · The mitigation cites "the `keep lost` metric", but no metric has that name. The table calls it "`knowledge` or `mixed` turns lost".
- F-14 · Nit · Whole document (Heilmeier Q7) · Nothing says how long the work, the labelling or the proof will take, and nothing gives a midway checkpoint between the golden-set floors and the final proof.
- F-15 · Nit · Header (line 3) · The status says "approved by the author on 2026-10-14". The 2026-11-06 revision changes scope (D-1 to D-3) and does not say whether it was approved again.
