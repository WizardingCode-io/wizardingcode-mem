## Findings
- F-1 · Major · Spec §6 "Samples and labels" and Metrics, "Memories stored from turns labelled record or fragment ≤ 15%"; plan Task 7 `ELIGIBLE` (`m.judge_version = '1'` joined to its source turn) · Both samples are drawn only from turns version 1 already stored as a memory. Turns version 1 skipped are never sampled. Version 2 uses different `worth`, `kind` and `knowledge_<i>` criteria, so it can store records from turns version 1 skipped, and the proof cannot see that. A reader will take "≤ 15% from records" as version 2's noise rate on the live stream, but it only measures the turns version 1 kept. That leaves the second goal ("A turn that is only a record stores nothing") half measured. The simpler fix is to add a sample of skipped turns (`turns.state = 'skipped'`, text still present) to the draw, or to state the limit in §6 and in the ADR's "What the proof leaves open".
- F-2 · Nit · Plan Task 3 Step 5(b), `const WORD = /\p{L}[\p{L}\p{N}_'-]*/gu;` added to `src/distill/pipeline.ts` · `src/distill/segment.ts:18` already defines this exact regex and uses it for the `MIN_WORDS` count. Exporting a word count from `segment.ts` (or exporting `WORD`) and using it would keep one definition of "a word" in the distill layer. As planned, `CONTEXT_MIN_WORDS` and `MIN_WORDS` could drift apart.
- F-3 · Nit · Plan Task 5 / Task 6 Step 3, `DistillInput.wording?: 1 | 2` and the version 1 branches of `distillState`, `distillQuestions` and `distillVerdict` · The only caller of wording 1 is `rejudge`, and `rejudge.ts:77–86` always sends `candidates: []`. So the version 1 `durable_<i>` and `title` paths, and the `durable_<i>` branch in `distillVerdict`, have no caller. They are still kept and unit-tested in `questions.test.ts` ("the verdict reads durable_<i>"). The version 1 code could be cut down to the `worth`, `kind` and `importance` that D-2 names. The plan also adds a field to the shared judge input that the heuristic judge ignores. Keeping the version 1 questions is decision D-2 and is not questioned here. The point is that the version 1 branch carries more than D-2 needs.
- F-4 · Nit · Spec "Decisions", D-2 · D-2 says the import rejudge keeps the version 1 questions but never says why. Without the reason, a reader cannot tell whether the version 1 branch in `questions.ts` is permanent or temporary. The Open questions section ("whether the imported memories ever move to version 2") suggests it is temporary. One clause of reasoning would settle it.
- F-5 · Nit · Spec §3 and §2 "Versions": `DistillVerdict` keeps the field name `durable` for what is now a knowledge probability · This avoids touching the types, but it leaves a misleading name at the centre of the policy. The plan needs comments in `buildDraft` and in `distillVerdict` to explain it. Renaming the field is a small, local change, and a reader of `policy.ts` would otherwise reason about "durability" when the threshold is `KNOWLEDGE_THRESHOLD`.
- F-6 · Nit · Plan Task 7 Step 4, `scripts/proof/quality.sh` · This is the third copy of the live-store resolution, the work-dir refusal and the `.backup` block (`scripts/proof/links.sh:56–86` and `scripts/proof/semantic.sh:60–96` hold the same code). Following the existing proofs' pattern is reasonable. If a fourth proof is expected, a shared sourced helper would remove the duplication, but nothing here requires it. Noted only so the duplication is a deliberate choice.
- F-7 · Nit · Spec §1 `status-label` row ("case as written; `state:` in a code sentence passes") and §4 (0.25, 0.2, 60%) · These are tuning constants and regex case rules sitting in the design text. They are small and do no harm, but they belong to the code and its tests, which the spec already names as the place for "everything that turns a probability into an action". §4 could state the rule ("report signals lower a sentence's knowledge and a mostly-report answer's worth") and leave the numbers to `heuristic.ts`.
