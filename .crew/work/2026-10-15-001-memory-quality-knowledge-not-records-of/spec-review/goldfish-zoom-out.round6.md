## Findings
- F-1 · Major · Spec §9 "The heuristic judge, version 2"; D-6; plan Task 4 · The heuristic version 2 has no target for a gain. Its only acceptance condition is D-6, "loses no more than version 1". So the proof can pass while the report penalties and the worth discount do nothing useful. They can also do harm: §9's "Known limit" already admits they lower real knowledge ("Decisão aplicada (commit 5808e41)"). The heuristic judged only 208 of 3,941 memories (about 5%), and the noise filter and the new rule that the title must be knowledge already apply to it. What a competent reader would build wrong: a second set of regexes, a production export `heuristicJudgeV1`, and a fourth column in the proof, all for a change whose benefit nobody measures. Simpler: ship the filter and the policy for the heuristic and leave its scoring at version 1. Or, if it stays, give it a target (for example records stored from B and S, heuristic v2 below v1).
- F-2 · Major · Spec §7 "Versions" says the proof asks both wordings "to measure version 1's tokens and verdicts"; plan Task 7 "Version 1" says the wording-1 draft "is not used" and version 1's reading is the memory already stored · The spec and the plan disagree on what the version-1 request is for. In the plan it yields only a token count. Because of that one number, `questions.ts` keeps the full version-1 builder with candidates (`durable_<i>`, `title`) in production code that no live path reaches: `rejudge` sends no candidates. It also doubles the paid requests, and a failed version-1 request removes the turn from every share, including the version-2 shares. A reader of the spec would expect version-1 verdicts from the re-ask, and would keep that code path forever, believing it measures something. Simpler: correct §7 to "tokens only". Then either compute the version-1 request size without retaining the builder, or keep only the no-candidate version-1 wording `rejudge` needs. If the re-ask stays, its failure should not exclude version 2's reading.
- F-3 · Nit · Spec §3 "Stricter questions, same shape"; §8 · The design now has three gates that ask nearly the same question: `worth` ≥ `SAVE_THRESHOLD`, `kind ≠ none`, and a title whose `knowledge` passes `KNOWLEDGE_THRESHOLD`. The new title rule makes `worth` close to redundant. Calibration lever 2 shows it: `worth` can only lose turns. The spec keeps it to preserve the shape, which is a reasonable choice. Still, the proof could report how often `worth` alone vetoed a turn whose title passed. That is the evidence the next change needs to remove a question and its tokens (D-5).
- F-4 · Nit · Spec §5 "The notes the session had been shown"; §2 Goals · The bound on `toldInSession` (the turn's end, and never the turn's own memory) is presented as a pipeline detail, but the proof depends on it. Samples A and B are turns whose memories were often shown later in the same session. Without the bound, `prepareTurn` would strip their own sentences and the proof would measure damaged turns. Say so in §5, so that nobody treats it as an optional extra and drops it.
- F-5 · Nit · Plan Task 7 Step 4, `scripts/proof/quality.sh` · This is the third copy of the same shell logic: resolving the live store (including a moved store), the realpath refusal, the read-only `.backup`, and turning the environment off. The other two copies are `scripts/proof/links.sh:56-86` and `scripts/proof/semantic.sh:60-96`. The plan does extract `random.ts` from `moments.ts` for the same reason. A shared sourced helper, or at least a note that this is a deliberate copy, would keep the three guards from drifting apart. (The seeded generator is also duplicated in `tests/helpers/links-fixture.ts:23`, `tests/perf/large-project.test.ts:31` and `tests/perf/budgets.test.ts:58`; leaving those copies is fine.)
- F-6 · Nit · Spec §11 "Where it runs" · The section goes down to implementation level (real-path comparison, which environment variables count as live, the refusal list) that the plan and `live-guard.ts` already hold. At this level the spec only needs: a read-only copy, never the live store, nothing written to the repository.
- F-7 · Nit · Spec §8, body bullet, against plan Task 3 `buildDraft` and `draft.test.ts` · "The five strongest knowledge sentences … without the title" can be read as five facts plus the title. The code takes the top five and then removes the title, so the body holds four facts when the title is among them. The test expects four. Pick one reading and word §8 to match it.

Reuse checked, nothing missed: `stripHost` has no earlier equivalent. `src/core/host-prompt.ts` only detects a host notification at the start of a prompt, and `src/store/migrations/0003_host_context.ts` is a one-off migration. `wordCount` reuses the segmenter's own `WORD` pattern. `random.ts` reuses `moments.ts`. Token usage is recorded only as lifetime totals (`USAGE_KEYS`, `src/judge/index.ts:20`), with no per-turn figure. Pinning the import rejudge with one constant, `IMPORT_WORDING`, is the simplest correct form of D-2.
