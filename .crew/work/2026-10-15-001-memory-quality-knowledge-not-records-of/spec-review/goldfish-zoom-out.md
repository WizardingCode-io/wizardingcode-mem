## Findings
- F-1 · Major · Spec §7 "Versions" ("The version 1 builder in `questions.ts` stays whole (`durable_<i>` and `title` included)") / Plan Task 6 intro and Task 7 "Version 1" · Production code keeps a complete second question set, `durable_<i>` and `title` included, and the proof sends a second paid TypeSafe request for every turn (about 500). Both exist only to measure version 1's input tokens for D-5, and the plan throws away that request's draft. The import rejudge needs only the version 1 `worth`, `kind` and `importance`. Version 1's tokens per turn already exist: `scripts/record-typesafe.ts:30` stores `inputTokens` for each golden turn in `tests/golden/typesafe-answers.json`, and Task 6 Step 7 records version 2's tokens on the same 40 turns. Version 2's tokens from the proof could also be compared with the request size of the stored version 1 rows. The risk a reader would miss: `questions.ts` keeps a dead question set to maintain alongside the live one, and the proof's cost doubles, to get a number the golden recordings already give. The simpler design keeps only the three questions D-2 needs and takes the D-5 ratio from the golden recordings, or from version 2's real requests against that baseline. If version 1's verdicts on the same turns are wanted, that is F-2 of the first pass, and the design should say so as its reason.
- F-2 · Nit · Spec §9 bullet 3 / Plan Task 4 (`heuristicJudgeV1`) against Task 5 (`DistillInput.wording`) · The design switches "version 1 or 2" in two different ways. TypeSafe gets a `wording` field on the judge's input. The heuristic gets a second exported judge object in `src/judge/heuristic.ts` that "the drain never uses", so the production module exports something only the proof calls. Using the same `wording` field for the heuristic (report signals off when `wording: 1`) would give one switch for both judges, add no extra export to `src/`, and let the proof build the heuristic version 1 just as it builds `typesafeV1`.
- F-3 · Nit · Spec §6 `status-label` and `template-label` (evidence: 4 and 2 matches) · Once the title has to be knowledge (§8) and version 2's criteria name statuses and plans as records (§7), the judge already rejects these sentences. That leaves the two patterns one job: saving a request on a turn they empty, which the 2026-10-13 sample shows as rare. They are built and cheap, so this is no blocker. Still, D-3's own principle (drop a sentence unseen only when the evidence is strong) fits six matches poorly. The proof's per-pattern report should decide whether they stay. The text should not treat them as settled.
- F-4 · Nit · Spec §7 "Versions", second paragraph · This paragraph sits at code level in a design section. It names the `DistillVerdict.durable` field and why it keeps that name, says `rejudge` stamps its version "from the same constant it sends as the wording", and says the heuristic "ignores the field". The design-level points are that the import rejudge keeps version 1 and stamps `'1'`, and that the proof can ask both wordings. The constant and the field name belong in the plan, which already holds them in Task 5 and Task 6 Step 3. (This is separate from F-6 of the first pass, which is about §11.)
