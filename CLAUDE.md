# wizardingcode-mem

Persistent memory across sessions for coding agents, by **WizardingCode**. One binary, no daemon, no generative LLM, local by default.

Brand conventions: products, plugins and skills are called `wizardingcode-<thing>`; variables `WIZARDINGCODE_<THING>_*`; data in `~/.wizardingcode/<thing>` (honouring `WIZARDINGCODE_HOME`). Until 0.3.0 this was `shibaox-mem`. The shibaox brand is retired, and installs of it are taken over automatically (`src/util/legacy.ts`, `src/install/legacy-plugins.ts`). Never reintroduce the old names outside that compatibility code. See `docs/adr/0011-wizardingcode-brand.md`.

## The non-negotiable rule

**This project is written from scratch. It is not a fork of claude-mem.** Never copy code, schema, prompts, text or names from claude-mem, and never open its source to implement a feature. See `CLEAN-ROOM.md`.

## Where things are

- Design and decisions: `docs/design/2026-10-05-shibaox-mem-design.md` (written under the old name)
- Measured decisions and departures from the design: `docs/adr/` (read the latest before touching the schema or retrieval)
- One engine with modules (ADR 0019): `src/engine/` is the contract (`module.ts`), the composer and budgets (`compose.ts`, `budget.ts`) and the enabled set (`modules.ts`); `src/modules/memory/` and `src/modules/knowledge/` are the two modules shipped (`BUILT_IN`, memory first). Hooks, the MCP server and the viewer's rail ask the modules, never memory by name. The composer asks the modules with a declared share first and gives memory, the remainder, the budget less what they actually wrote (ADR 0024's F5′), so a silent module costs memory nothing. `WIZARDINGCODE_MODULES` (comma list, default `memory,knowledge`): memory is always on (the API refuses a list without it), `WIZARDINGCODE_MODULES=memory` turns knowledge off (`doctor` warns `knowledge is off`), and stopping memory for a project stays the per-project "memory off". `src/core/project.ts` and the links store are the engine's: every module uses the same project ids.
- The team server (ADR 0026, a draft: part 5 of the journey; the sync client, part 6, and the runbook, part 7, are not built): `wizardingcode-mem serve [--data <dir>] [--host] [--port] [--trust-proxy]` is a long-running process over its own SQLite `team.db` in `WIZARDINGCODE_MEM_TEAM_DATA` (default `<data dir>/team`), one process per directory by the lease `serve.lease`; it never opens a client's store and no hook imports `src/team/`. Every SQL statement lives in `src/team/store.ts` (`transaction` wraps `withWrite`; `db.ts` is the schema, the three opens and the statements an open runs before the store can be asked, the version read, the schema check, `secure_delete` and migration 1's identity write; `types.ts` is the leaf with `Limits`, `Context` and `Meta`; the `team-store-boundary` test fails on SQL anywhere else); the change signal, the leases, the rate buckets, the held-pull counts and the high-water file `feed.seq` assume that one process. Every request but `health` and `join` is authenticated by a device token (`wcm1_`, stored as a digest); invitations (`wci1_`) are admin-only; the alias filter of a pull is minimisation, not a permission (any member may read any item). Push applies items one by one in the spec's order (`push.ts`, `validate.ts`); pull reads the feed by a cursor and may `wait` up to 25 s (`feed.ts`); the mirror under `repos/` is an export written by `serve mirror` (`mirror.ts`, a child process the server runs hourly and a quiet minute after a push); erasure is the operator's `serve purge … --yes` (the replay it owes the repositories is noted in `meta` until whole, and the next run finishes it). Subcommands: `invite`, `invitations`, `invitation revoke`, `members`, `revoke`, `disable`, `enable`, `role`, `withdraw`, `reinstate`, `status`, `audit`, `mirror`, `purge`, `instance renew`, `health` (`src/cli/commands/serve.ts`; the log on standard error, their own output on standard output). Deployment: `Dockerfile` (a `pick` stage, user 10001, `/data`), `compose.yml` (hardened server behind Caddy), `Caddyfile`, `.env.example`; the release pushes the image to `ghcr.io/wizardingcode-io/wizardingcode-mem`. `src/core/redact.ts` names `team-token` and `team-invitation`. Tests: `tests/helpers/team.ts` (a server with an injected clock and timers), `tests/integration/team-*.test.ts`, `tests/unit/team-*.test.ts`, `tests/unit/deploy-files.test.ts`.
- `ui.json` (the running viewer's state) lives at the brand level, `~/.wizardingcode/ui.json` (honouring `WIZARDINGCODE_HOME`); the old file in the data directory is migrated once. A new module's rail icons must be listed in `ui/vite.config.ts`, since icons are bundled at build time.
- The knowledge module (ADR 0024, a draft: part 1 the store, part 2 knowledge for the agent; no view yet): `src/modules/knowledge/`. The module (`index.ts`, share 0.2) reads the database and nothing else on a hook (`contribute.ts`): the pinned entries at every session start, once per context, within `SESSION_START_SHARE` (840 characters; D-9 (part 2), confirmed by the person on 2026-11-09), and on a prompt at most two entries that pass the lexical floor (`knowledgeEvidence` in `policy.ts`, `MIN_SHARED` 3), as information, not instructions; each shown entry is a `knowledge_shown` row. `visible.ts` (`visibleRepos`) is the one place that says which repositories a project sees. The probe `tests/fixtures/knowledge-probe.ts` (18 entries): 12 of 12 relevant prompts bring their entry first, 1 of 28 unrelated injects (the known "User roles" leak). The tools (`tools.ts`): `knowledge_search`, `knowledge_get` (both also with `--global`, over workspace and shared only) and `knowledge_propose`; a call opens the database, runs `openRepo` and `ensureFresh` under the lease (so it can write index rows; listing writes nothing); a propose runs the hourly rate (20 per agent id, `meta` `knowledge.rate:<id>`), the area, the target, the judge (`propose.ts`: `Judge.relate`, memory's `consolidate` logic and thresholds over at most 8 lexical neighbours, redacted, open proposals by the heuristic only; `makeJudge({ toolPath: true })`, `TOOL_JUDGE_TIMEOUT_MS` 3 s, no retries, usage under `typesafe.tools.*`, the breaker shared with distillation), then the store's write; a refusal is `refused <code>: …`. The agent id is the handshake's client name mapped by `agentIdFromClient` (`src/mcp/agent-id.ts`), `mcp --agent <id>` overrides, `mcp` otherwise, the OpenCode bridge `opencode`; a proposal is `proposed_by: agent:<id>` with `on_behalf_of` the person. The module's version is 7 (`0007_knowledge_agent.sql`: `pinned`, `fts_rowid`, the proposal's `contradicts`/`on_behalf_of`/`judged_by`/`judge_version`, `knowledge_fts` kept by the index writer, never by triggers, and `knowledge_shown`). The drain runs `refreshStale` (at most `REFRESH_PER_DRAIN`, 3, repositories that differ from the disk; whatever the modules setting). `status` has a `knowledge` line; `doctor`'s knowledge check warns when the module is off, when the search table's rows differ from the active entries, and when the pins exceed the session-start share; `compact` removes the `knowledge_shown` rows of gone sessions and repositories. The store: the truth is Markdown files with frontmatter in one git repository per scope under the data directory (`<data dir>/knowledge/workspace`, `shared`, `projects/<folder>`; `entry.ts` is the formats, `repo.ts` the repositories and the one git runner `runGit`, `resolve.ts` the mapping of a project to its repository through its manifest, `store.ts` the writes, proposals and `adopt`, `taxonomy.ts` the areas, `index-store.ts` the index rebuilt from the files, `schema.ts` the leaf with `requireSchema`, which everything that reads or writes the tables calls). Every git call goes through `runGit`, never on a hook path, and never with the person's git configuration; `openRepo` is the one way to a repository, and before git runs it refuses a folder the store did not make (`refuseForeign`: one whose `.git` holds anything but regular files and folders included; `refuseLinkedRoots` for `knowledge/` and `knowledge/projects/` themselves) and a `.git/config` that holds anything but the settings `git init` writes (`checkRepoConfig`, an allow list: add to `ALLOWED_SETTINGS` only what the store itself writes); `statusOf` never looks into a nested repository. The store keeps no file of its own under `knowledge/` beside the repositories: git gets `/dev/null` as its global configuration, the repository's own `.git/config` (a file) as its hooks path, and no template. `doctor` is the one reader that does not go through `openRepo`, which writes: it reads by hand under the same guards (`refuseLinkedRoots`, `refuseForeign`, `checkRepoConfig`), each of which it must be given when `openRepo` gains one. Only a name with nothing at it is gone: the places that decide whether a repository is there, or which entry and proposal files it holds (the two roots, a repository's name, its `entries/` and `proposals/` folders and the names in them), ask the disk with `lookAt`, `kindAt` and `namesIn` (`repo.ts`), for which anything that cannot be looked at is a refusal, never "not there"; `doctor` lists the folders with the same three. The older `isDirectory` and `existsOnDisk` read any failure to look as "no" and are used only inside a repository, behind one of those refusals: never decide a repository's presence with them. A link or a file where a repository's folder was is refused by name and its index rows stay, and a project's row names its folder while anything is at that name (`matchProject` in `resolve.ts`), so no state of the disk gives a project a second folder. The index belongs to one data directory: `rebuild` refuses, forgetting nothing, where there is no `knowledge/` folder and the index holds repositories. An interrupted operation is put back by its intent record, path by path, only where a file is still as the engine left it; a record is read only when every path in it is the store's own (`ownPath`), and a path is followed only through real folders (`reachedByFolders`). Three rules live in one place each: the write of the engine's own text, with its record and its undo, in `commitChange` (`repo.ts`; `adopt` keeps its own frame in `store.ts`, since it gives a person's bytes back instead of restoring from HEAD); a step of `openRepo` under the repository's lease in `underOwnLease` (`repo.ts`); a command over several repositories, where one the store refuses is set aside, in `inEachRepo` (`index-store.ts`, with `isRefusal` in `errors.ts`). An agent's write is a proposal until a person accepts it; the entry point passes the writer, never the caller. A module's tables are versioned apart from the core schema in `module_migrations`: `src/store/migration.ts` is the `Migration` type, `src/engine/module-schemas.ts` the one list `openDb` reads (it imports migration lists, never module code), and `user_version` stays 7. Knowledge starts at module version 6 (1 to 5 were the withdrawn module's) and is at 7; a development store that ran 6 alone runs `knowledge rebuild` once. `wizardingcode-mem knowledge write | accept | reject | area | rebuild | adopt | list` is the store from a shell; `doctor` has a `knowledge` line. `wizardingcode-mem backup` does not copy the repositories. In tests, `tests/helpers/knowledge.ts` gives a data directory, a throwaway home and stores whose environment the test controls, and `tests/helpers/stub-git.ts` a git that fails or stalls on demand.
- The sharing policy (ADR 0025, a draft: what may leave for a team server; the server exists since ADR 0026, the sync client does not, so nothing is sent yet): `src/sharing/`. `types.ts` is the leaf (levels `local | knowledge | all`, shown as Nothing, Knowledge, Knowledge and memories; the roots; `REASONS`; the item and payload types and their pinned key lists), `levels.ts` the rule both readers apply (`effectiveLevel`, `levelOf`, the derived `epochOf`), `policy.ts` the loader (`loadPolicy`, never throws, fails closed) and `decide`, the one predicate parts 5 and 6 call (`send | withdraw | keep` with a reason and the epoch), `in-force.ts` the policy a change is made under (`policyInForce`, `sharingRefusal`, shared by the CLI and the viewer), `store.ts` the writes (`setLevel`, `applySettingsPatch`, the two reconciles, `resetLevels` for a restore), `report.ts` the counts and previews (`wouldLeave`, `withChange`), `edge.ts` `redactForSend`, `patch.ts` the viewer's settings patch, `hash.ts` `memoryHash` over `MEMORY_HASH_FIELDS`, `migrations.ts` the namespace's migration list (`SHARING_MODULE`) and the store's generation key (`GENERATION_KEY`, `sharing.generation`). The tables are the `sharing` namespace in `src/engine/module-schemas.ts` (`sharing_levels`, `sharing_ledger`, `sharing_changes`; `user_version` stays 7); the counter, the baseline and the store's generation are `meta` keys. The roots and the areas are the env file's `WIZARDINGCODE_MEM_SHARE_ROOTS` and `WIZARDINGCODE_MEM_SHARE_AREAS`: the environment only narrows them, an invalid token empties the list. A widening needs `confirm` in the store itself. `wizardingcode-mem share project | roots | areas | status | explain`; its terminal question and `install`'s are `askYesNo` in `src/cli/prompt.ts`. The viewer: the Settings → Sharing page, the Sharing section of a project's dock in Across projects, and `GET /api/sharing`, `POST /api/sharing/preview`, `PUT /api/projects/<id>/sharing` (a sharing key in `PUT /api/settings` goes through `applySettingsPatch`). `status` has a `sharing` line, `doctor` a `sharing` check; a restore resets every level to Nothing. No hook reads the policy.

## Commands

- `bun run check` — typecheck, lint and tests
- `bun run build` — compiles the five binaries into `dist/`
- `bun run format` — formats and fixes lint
- `bun run plugins` — rewrites what each agent installs (manifests, hooks, `wizardingcode-mem.sh`, the OpenCode package) from `scripts/plugins.ts`; run it after changing the version or the events
- `wizardingcode-mem install [claude-code|claude-desktop|codex|cursor|opencode|qwen|droid|copilot|antigravity]` installs for one agent (Claude Desktop: its chat gets the MCP server with `--global`, across every project; Cowork gets the plugin; ADR 0012); with no agent, for every one it finds. In Claude Code it imports claude-mem's memories and retires it (with confirmation); `wizardingcode-mem import claude-mem` only imports. claude-mem's database is only read, never changed. Qwen Code, Droid, Copilot and Antigravity install directly (hooks file and MCP server, no plugin; ADR 0016). Gemini CLI is no longer supported: `install gemini` points to Antigravity, `uninstall gemini` removes an old install (`src/install/gemini-leftover.ts`; never touches Antigravity's `~/.gemini/config`).
- Adapters in `src/adapters/<agent>/`; installers in `src/install/`. The design per agent, and what was or was not confirmed in real sessions, is in ADR 0006 (Claude Code, Codex, Cursor, OpenCode) and ADR 0016 (Qwen Code, Droid, Copilot, Antigravity).
- Installation is native in each agent (plugin, extension, npm package): ADR 0009. The files in `.claude-plugin/`, `hooks/`, `plugin/` and `plugins/` are generated; do not edit them by hand.
- `wizardingcode-mem rejudge [--limit n] [--concurrency n]` asks TypeSafe for the kind and importance of imported memories; what is not worth keeping becomes `archived` (never deleted). Resumable; needs a key. It asks the version 1 questions and stamps judge_version 1, whatever the distillation questions' version (ADR 0023).
- Distillation quality (ADR 0023): `src/distill/noise.ts` removes the host's own blocks from a turn (`stripHost`) and drops the sentences that are never knowledge, by named pattern (`host-frame`, anchored to the host's fixed lines; `status-label`; `template-label`), before either judge, and takes the dropped sentences out of the texts the judge reads and the `Context:` line quotes; a turn left with no sentence is skipped without a request. A skipped turn keeps its reason in `turns.last_error` (`skip:saved`, `skip:empty`, `skip:not-worth`, `skip:no-title`; `skipMark` in `src/distill/pipeline.ts`, no migration); `distill` and `status` print the counts by reason, and a skipped turn with no reason (skipped before reasons were kept) counts as `unknown`. The notes a session was shown are removed from a turn only when shown before it ended, and never the turn's own memory. The judges are version 2: one `knowledge_<i>` question per sentence against a named `reader`, contrastive kinds; the title must be a knowledge sentence (`KNOWLEDGE_THRESHOLD`) and the `Context:` line needs `CONTEXT_MIN_WORDS` in the prompt. The heuristic judge penalises report sentences (hashes, "PR #", status verbs, verdicts, test counts); `heuristicJudgeV1` keeps its version 1 for the proof. Proof: `scripts/proof/quality.sh <work dir> sample|measure`, on a read-only copy at `<work dir>/home/mem`; it sends nothing to a model but TypeSafe, labels name candidate ids (`scripts/proof/quality-brief.md`), and the samples, the labels, `verdicts.json` and `full.md` never enter the repository.
- `wizardingcode-mem history import [--days n] [--agent claude-code|codex] [--max-seconds n]` distils the agents' own transcripts from the last days (`historyDays`, default 180) into memories dated when they happened, live turns first; resumable, never archives. `wizardingcode-mem history replace-imports` then archives the claude-mem imports inside each finished project's history span, sparing those history confirmed; `wizardingcode-mem history restore-imports` undoes it. `wizardingcode-mem history index [--agent] [--max-seconds n]` keeps a separate, redacted, searchable index of every past turn in `history.db` (store dir, rebuildable, not in backups; session end updates it once the file exists); `history search <words> [--project] [--limit]` reads it (also the MCP `history_search`), `history forget` deletes it; never injected. One run at a time (meta lease `history.lease`); `install` offers it once (`--import-history` / `--no-import-history`), the viewer has a banner offer, a Settings History card (progress via `/api/history/progress`) and a History view that searches `history.db`. ADR 0013.
- `wizardingcode-mem embed download [--backfill] | status | delete | backfill [--limit n]` manages the optional search model (`<data dir>/models/potion-multilingual-128M.wcpack`; fixed `MODEL_URL`, sha256 and size pinned in `src/embed/download.ts`; the feature's only network access). Vectors: `memory_vectors` in the main database (they travel in backups), `turn_vectors` in `history.db` (filled by `history index`). Used only by on-demand search (`memory_search`, `history_search`, the viewer's palette and History view), never by the hooks or injection (ADR 0014). `WIZARDINGCODE_MEM_SEMANTIC=off` turns it off; `install --semantic` / `--no-semantic` answers its offer; the viewer's Settings → Search card drives it through `/api/semantic` (GET) and `/api/semantic/download|backfill|on|off|delete` (POST); `doctor` has a `semantic search` line. Leases `embed.download.lease` (handed over to) `embed.lease`; both block move, restore and compact. Memories that lack a vector heal by themselves: each background drain and `history import` ends with a bounded backfill (`healVectors`, never on the hook path). Floor 0.32, proof `scripts/proof/semantic.sh`: ADR 0017.
- `wizardingcode-mem ui [--port n] [--no-open] [--auto]` opens the viewer (loopback, token in the URL, stops when idle and no tab is open; `--auto` is what the session-start hook runs: show the viewer already running, or become it). `wizardingcode-mem compact [--dry-run]` prunes old records; never deletes memories. `wizardingcode-mem backup [--list | --restore <name>]` copies the database to the configured folder or bucket.
- Linked projects and your rules (ADR 0018). Migration 7 adds `project_links`, `rule_proposals` and `user_memories`; a user rule is an active memory with a `user_memories` row (Ruling P1), never a `scope` value. 0.5.0 binaries refuse a v7 database (`SchemaTooNewError`, and `doctor` fails its database check). After the drain, `distill` runs, each in its own guard and never on a hook path: the vector heal, `suggestLinksSafely` (`src/links/suggest.ts`: same remote owner plus a shared name stem outside the generic list in `src/links/signals.ts`, a manifest dependency, one workspace) and `proposeRulesSafely` (`src/links/rules.ts`: a 5 s budget, a meta cursor `rules.cursor` (new rows by id, changed rows by `(updated_at, id)`) so a quiet drain costs two index reads, the `rules.lease` lease, 60% of the budget for the scan when the judge has `personal` and a bounded `rules.pending` list for groups it had no time for; "said always" is `saidAlways`: typed text only, a rule phrase and two of the title's words in one short sentence, one per turn, a sure `personal` verdict with a judge). Linking by hand is only the MCP tool `project_links` (`list`, `link`, `unlink`, `confirm`, `reject`; also on OpenCode's internal `tool` bridge) and the viewer: no `link`/`unlink` commands. Viewer routes: `GET/POST /api/links`, `POST /api/links/<id>/confirm|reject|unlink`, `GET /api/links/offer`, `POST /api/links/offer/dismiss`, `GET /api/rules`, `POST /api/rules/<id>/accept|reject|undo` (undo takes the rule's memory id). Retrieval reads `visibleProjects` (`src/store/links.ts`; links never chain, `uses` is one way, disabled projects are never visible; deciding one row of a pair rejects the pair's other suggestions in the same transaction); user rules from disabled projects are never read; the shares are in `src/retrieve/brief.ts`; with no confirmed link and no user rule, brief and prompt notes are byte for byte as before (pinned snapshots). Proof: `scripts/proof/links.sh`.
- Settings live in `<data dir>/env` (dotenv, 0600; `src/settings/`), edited from the viewer's Settings tab; keys are named like the environment variables and the environment wins, except for `WIZARDINGCODE_MEM_SHARE_ROOTS` and `WIZARDINGCODE_MEM_SHARE_AREAS`, which the environment can only narrow (ADR 0025). The data directory (`defaultDataDir`) holds the binary, the settings and the logs (`ui.json` is at the brand level); the database may live elsewhere (`resolvePaths().storeDir`, `WIZARDINGCODE_MEM_STORE_DIR`): open it with `openDb()` and its default, never from `dataDir` directly. ADR 0010.

The `bun` the scripts use is the one pinned in `devDependencies`, not the global one; run tests as `bun run test` (or `./node_modules/.bin/bun test <files>`).

## Conventions

- TDD: the test is written and seen failing before the code.
- Hooks never exit with code 2 (in the agents, 2 blocks the action). They fail open: code 0 and empty stdout. In tests, `WIZARDINGCODE_MEM_DISTILL=off` and `WIZARDINGCODE_MEM_UI_AUTO_OPEN=off` keep hooks from starting background work, `WIZARDINGCODE_MEM_MIGRATE=off` keeps them away from a real `~/.shibaox`; `WIZARDINGCODE_MEM_UI_BROWSER=none` keeps the browser closed. Claude Code also gets notes on `file-read` (`PostToolUse`, matcher `Read`): at most two, once per context, no background work. `tool-failed` (`PostToolUseFailure`) is built but held, not installed, until a narrower version passes ADR 0015's bar.
- No heavy SDKs on the hook path; use `await import()` per command.
- Semantic judgements go through the `Judge` interface (TypeSafe opt-in, heuristics as the fallback). Exact rules and calculations stay in code.
- Imports with an explicit `.ts` extension.
- The viewer is a Vue 3 + Tailwind 4 + Nuxt UI app in `ui/`, built by Vite into a single `src/ui/dist/index.html` (not in git; `bun run ui:build`, included in `test`, `build` and `check`) that the binary embeds. The viewer follows WizardingCode's app pattern (the Sales OS mockups in the rebrand repository, `09-sales-os/SHELL.md` and `DENSITY.md`): dark frame (40px top bar, 56px rail, 216px sidebar), three-row page header, grouped lists with 32px rows, a 320px detail dock, the compact type scale. The tokens live in `ui/src/app.css` and feed Nuxt UI's `--ui-*` variables (`--ui-radius` sets every radius); its component sizes are set in `ui/vite.config.ts`; icons are bundled at build time; the fonts in `src/ui/assets/` travel in the binary. Nothing leaves for the network from the viewer. `bun run ui:dev` to develop against a running `wizardingcode-mem ui`.
- Repository documents (README, design, ADRs, this file) are written in English.
