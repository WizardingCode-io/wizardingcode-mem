# ADR 0028 — Shared names: a project without a git remote, shared under a name

Date: 2026-11-11 · Status: **draft**. Work item 2026-11-11-005 of the knowledge and team journey (2026-11-08-001), after the runbook (part 7). [ADR 0025](0025-sharing-policy.md) gave a project one identity for a team, its host-led git remote; [ADR 0026](0026-team-server.md) named a project on the server by that alias; [ADR 0027](0027-sync-client.md) pulled by it. This record adds a second identity, the shared name, and amends the three. The seven rulings were taken with the author on 2026-11-11 (the item's `brief.md`); the operator's erasure of a name came from the security lead's return, under ADR 0026's rule that erasure is the operator's. Where this record and the item's specification differ, this record is the later one.

## Context

A project that is not a git repository on a host could not be shared: `setLevel` refused `no-remote`, the dock said a team can only match projects by their remote, and ADR 0025 listed the case as a known limit. On the author's machine 149 of 158 projects have no `remote:` alias, among them the one that holds the work done in Claude Desktop and Cowork. The requirement, in the author's words: a remote host must not be needed, sharing must work without one, everything is shared. Three things had to hold with it: two unrelated projects with the same name must never merge in silence; an older binary or an older image must refuse the newer schema instead of losing the team's copy; and `status`, `doctor` and the viewer must say what is held and why.

## Decision

A person gives a project a **shared name**, the alias `name:<slug>`, a second alias a level can bind to beside the host-led remote. The server holds a **registry** of names: one member creates a name, the others join it from the list, and a push under a name the registry does not hold is refused. Creating or joining is confirmed by name at every level, Receive only included, and every local refusal is decided before the server is asked. The contract moves to 2 with 1 accepted, the team schema to 2, the client store to version 8 and the sharing namespace to 3. While the contract a client speaks to a server is 1, shared names are **held**: left out of the pulls and the pushes to that server, and said in `status`, in `doctor` and on the Servers page. A name re-created on the server after a purge or a restore is told from the one a client joined by its id. The operator erases a name with `serve purge name`.

Taken from the brainstorm as assumptions the author confirmed: the prefix `name:` (not `team:`, which is the received memories' judge), the words "shared name", `Shared as` and "leave this name", a project at Nothing may forget its name, the slug is `slugify`'s and a text with no letter or digit gives no name, the received folder stays `projects/<slug>-<8 hex of the alias>`, the list shows names only.

## The identity leaf

`src/core/identity.ts` is a module with no imports that holds the one rule of what a team may know a project by: the alias kinds (`ALIAS_KINDS`: `remote` when host-led, `name`; `gitdir`, `path` and `imported` never), `aliasKind`, the slug grammars (`SLUG`, which the knowledge store imports from here, `SLUG_MAX` 80, `RESERVED`, and `SHARED_SLUG`, a slug with no leading, trailing or double hyphen), `hasLetterOrDigit`, the predicates every reader applies (`isHostLedAlias`, moved here from the sharing module and re-exported by it; `isSharedName`; `isTeamAlias`), the prefixes and `stripTeamPrefix` (the folder slug), and `TEAM_ALIAS_SQL`, the one fragment the three prefilters narrow by before judging every row in code (the viewer's project list, the report's entry aliases, the sync's project aliases). A third identity is one entry in the table. The contract module imports the leaf, never the sharing module.

## The name of a project

`src/sharing/names.ts` (it imports the knowledge store's `slugCore`, the slug rule without its `entry` fallbacks, exported for it): `sharedNameOf(text)` makes `name:<slug>` of a text, or `no-name` with the reserved word when that is the reason (nothing is appended behind the person's back); `nameOf(aliases)` is the one name a project carries; `noNameMessage` is the sentence the CLI and the viewer give. `setLevel` takes `as` (the alias to create or join), `nameId` (the registry id, stored in `sharing_levels.name_id`, sharing migration 3), `dryRun` (the whole chain in a deferred read transaction, nothing written) and `recreated`. Its refusals, after `invalid` and `no-project`: `disabled`; `has-remote` (`as` on a project with a host-led remote and no name); `renamed` (`as` different from the name carried while a level above Nothing is stored); `name-taken` (`as` is another local project's name); `no-name` (nothing to bind to: no `as`, no bound alias still carried, no name carried, no host-led remote; it replaces `no-remote`); `one-server`; `needs-confirm` (a widening, or a binding that creates or joins a name, at every level). The alias bound (`aliasToBind`): the one the row is bound to while the project still carries it, else `as`, else the name carried, else the folder's host-led remote, else the project's first host-led remote by alias bytes; `defaultTeamAlias` is the same order with no row, for previews. The sharing store is the one writer of a `name:` row in the engine's `project_aliases` table: `setLevel` inserts the alias inside its own write transaction, before the level row, and replaces a name the project carried at Nothing; `local` removes the row and keeps the name; `forgetName` removes the name at Nothing (`name-bound` while bound) and logs `name:<project id>`; `formatChange` renders that row as `shared name of <project>: <old or none> → <new or none>` for `share status` and the Sharing page.

## The two-phase bind

`src/sync/binding.ts` (a sync module, since it calls the server; it names no sharing table): `prepareBinding` runs the dry run, so every local refusal is answered before any request; for a shared name on a server it reads the contract (`spokenContract`, below) and makes one lookup, `GET /v1/names/<alias>`, answering `create` (the server holds no live name) or `join` (with the name's item: its creator and counts); a level change on a name already bound needs no server step, unless the name is flagged missing or re-created. `commitBinding` creates the name when asked (`POST /v1/names`, with the id the creator's own row held when it re-creates one it was bound to, so the teammates stay bound), answers `unknown-name` for a create not asked for, `exists` with the item for a create against a live name, `purged` for a name the operator removed, then writes the level with the name's id. A write refused after a create answers `named: true` and one sentence (the name is on the server; set the level again, or the operator purges it): the one-round-trip race between the dry run and the write, left open on purpose. The CLI asks its question between the two functions, so nothing is created before the yes and the join question names the creator; the viewer's `PUT` runs both, the question having been asked from the field's sentence. `bindMessage` is the one sentence per refusal, read by both; `listServerNames` is the one read of every page of the list (at most 1,000), for `share names` and the dock's field.

## The registry and its ids

`team.db`'s `names` table: the alias (primary key), an id of 16 hex characters minted at creation or given by a creator that re-creates its own name, the creating member and device, the time, and `purged_at`. Every feed item under a shared name carries `nameId`, the live row's id at the time of the page (`null` when the registry holds no live row); an item under a remote, a tombstone and a purge carry `null`. The client stores the id it created or joined with the level row and compares it on every pulled upsert: a differing id means the name was re-created for something else, the item is skipped and the binding flagged. Routes, every one behind the device token and the devices bucket: `POST /v1/names` (201 with the item; 400 `alias`; 409 `exists` with the item; 409 `purged`; 429 past `namesPerHour`, 10 creates per member per hour, a bucket of its own); `GET /v1/names?after&limit` (50 a page, at most 200; names only, never a remote, never a purged one); `GET /v1/names/<alias>` (one 404 `unknown-name` for a malformed alias, a remote, a purged and an unheld name, so the route cannot probe for a remote). Below contract 2 the three answer the route table's own 404, as a 0.7.0 server does (`Context.contract`, the seam a test server is started at 1 with). The push checks the registry inside each item's transaction, after the pure checks and `purged` and before the replay shortcut: `name` for a send under a name never held, `name-purged` under one removed since. `serve status` prints the live count; `serve purge name <alias> --yes` marks the row, audits `name purged` and prints what is still under it.

## The contract spoken, and names held

`sharing_servers.contract` holds the contract a client speaks to one server: the lower of `CONTRACT` and the server's, set at the join and read again from `/v1/me` at every sync start and, while below `CONTRACT`, at every full sweep (60 s, five seconds each, in parallel, a failure keeping the stored value), from a 409's accepted list (the live path down: the row set to the highest acceptable value, the request rebuilt under the held rule and repeated once), and from a bare 404 on a names route (a 0.7.0 server reached with a row at 2: the row is set to 1). The header sent is the stored value (`SyncClient.speak`). The dock and the CLI read `/v1/me` once before refusing on a row below 2, since they may act before the sync has run since an upgrade or a rollback. While the contract spoken is 1 the pull names remotes alone, the sweep sends and withdraws nothing of a name-bound project, no refusal row is written for them, the dock's field is disabled, and `status` ends the server line `names held (server at contract 1)` (with `contract 1` shown only below `CONTRACT`), `doctor sync` warns, the Servers page says it under the server. The sync's `me` read at every full sweep is what ends the hold without a person's step.

## The three flags of a name

Three `meta` keys per server and alias, written by the sync, read by one function (`nameStateOf`: `purged` wins over `recreated` over `missing`) that `status`, `doctor`, `share status` and the viewer call:

- `missing`: a push answered `name` (the server lost the name: a restore to an older copy). Never stored in `sharing_refusals`, never counted by the breaker; the sweep stops sending that project's items for the sweep and retries at the next; the flag is cleared when a push under the name is applied or when the person binds again. Setting the level again is the create, with the id the row holds.
- `recreated`: a pulled upsert under the name carried another id (a purge, or a restore, then a new creation for something else). The item is skipped; the project's items are left out of the sweep's candidates and withdrawals and out of the snapshot's comparison; the alias stays in the pull so the flag is refreshed. Setting the level again is the join (confirmed again, the new creator named); `rejoinName` clears the flag and reads the name from the start.
- `purged`: a push answered `name-purged` (the operator removed the name). Nothing is sent under the name again; nothing is withdrawn by the client on its own (D-10's spirit); Nothing clears the flag with the level.

## The schemas and the rollbacks

The client store: migration 8 (`project_aliases_one_name`, a partial unique index); the sharing namespace 3 (`sharing_levels.name_id`); the knowledge module unchanged. A 0.7.0 binary refuses the version 8 file through `openDb`'s check, `doctor` fails its database check, hooks fail open: no level is deleted and nothing withdrawn; going back is the upgrade copy under `backups/`. The server: team schema 2 (D-4); a 0.7.0 image exits 3; the runbook's rollback restores the upgrade's copy, the names created since are lost with it, the clients detect the renewed instance and re-send under remote aliases what the copy lacks, and a project bound to a lost name is `missing` until its person sets the level again, which re-creates the name with the id the row holds. The contract: `CONTRACT` 2, `ACCEPTED_CONTRACTS` `[1, 2]`, `PUSH_REASONS` plus `name` and `name-purged`, `RESULT_SHAPES` plus `nameItem`, `namesPage`, `contractRefusal` (the 409 on the header, with its `accepted` list, which ADR 0027 owed) and `nameConflict` (the 409 `exists` with the name's item, which the client reads to re-open the join), `feedItem` plus `nameId`, `RefusalShape` without the `retryAfterSec` that never reached a body, the fingerprint repinned once; a 0.7.0 client speaks 1, names no shared name and sees at most a tombstone it already knows how to read.

## The viewer and the CLI

The dock's Sharing section, for a project with no host-led remote or one that carries a name: a "Shared name" field (`UInputMenu` with `create-item`, the server's names read once per server from `GET /api/servers/<id>/names`, prefilled with the project's slug) and one sentence under it, asked from `POST /api/projects/<id>/sharing/preview` when the field settles, never per keystroke: `New: you create …`, `Joins … · created by … · <n> entries, <m> memories`, or `This name is …'s on this machine`; a text that makes no name and a local collision are decided in the page without a request. Choosing a level under a name the project is not yet bound by opens a confirmation whose body is the question (`Create … on <server>, visible to every member, <level phrase>?` or `Join …, created by … (…), <level phrase>?`) followed by the would-leave line and, when above 0, the imported line; the action reads `Create and share` or `Join and share`; a 409 `exists` re-opens the join confirmation with the answered item (two members typed the same name between the list and the yes). Once bound: `` Shared as `<slug>` ``, `Set Nothing to leave this name.`, the sentence of the flag when one stands, the remote-too sentence when the project gained a remote; at Nothing with a name: the field with the name and `Forget name` (`DELETE /api/projects/<id>/name`); with names held: the field disabled and `The server speaks contract 1; shared names need its upgrade.`; under the levels, `<k> imported memories stay on this machine.` when so. Every refusal of the sharing routes is one shape, `{ error: <sentence>, reason: <code>, …extra }`, the dock switching on `reason`. The overview's rows carry `sharedName`, `boundTo`, `imported` and `nameState`; the Servers page lists each bound name's received counts and state, and the held sentence. The CLI: `share project <level> [--as <name>] [--create] [--yes]` (the question with the counts before any `POST`; `--create` creates; the answer line adds `, shared as <slug>` and `<n> imported memories stay`), `share names` (every page, the bound ones marked `*`), `share name forget`, and `share status` with `shared as <slug>` and the flag's words. The UI evidence is `.crew/work/2026-11-11-005-share-a-project-without-a-git-remote-tod/review/ui/`: fourteen dock states and two Servers states, at 360, 768 and 1280, light and dark, taken by `probes/capture-005.ts` over Chrome's DevTools protocol against the real routes.

## The erasure of a name, and its limit

`serve purge name <alias> --yes` needs no coordination with the members: from that moment the name is out of every member's list, a push under it is refused `name-purged` (never offered as "create it"), a create of the same alias is refused `purged`, and the members' docks and `status` say the operator removed it. The operator then purges its items one by one (`serve purge entry`, `serve purge memory`), in any order. What it does not erase: the string stays where the server's own records keep it, in the marked `names` row (with the creating member and device, kept as every member row is, ADR 0026 D-19), in the `changes` rows (their `uid` and `project_alias`), in the withdrawn rows' and revisions' `project_alias`, and in the audit rows, until `team.db` is restored or rebuilt; and in the mirror under `repos/`, where the name's repository (`repos/projects/<slug>-<8 hex>`, its `knowledge.json` naming the alias, its init commit) stays after its items are purged and a restore of `team.db` does not reach, until `serve mirror --rebuild`, the erasure's third step. Until the operator acts, a name stays readable by every member, with its creator and its counts.

## The boundary

The identity rule is the leaf's, applied in code by every reader; the SQL fragment only narrows. The server's SQL stays in `src/team/store.ts`; the client's bind calls live in `src/sync/binding.ts`, which names no sharing table (the boundary test's quiet list) and reaches them through `setLevel` and `servers.ts`; the viewer's project list reads the bound alias from the loaded policy, never from the levels table. The alias filter of a pull stays minimisation, not a permission (ADR 0026 D-11): any member may pull any alias, a held name included. A shared name is a slug (no path character) and reaches a folder only as `<slug>-<8 hex>`; the list discloses names only; creating or joining is the person's confirmed act.

## What building changed from the plan

The name id is 16 hex characters (the specification's grammar; the plan said 32). The dock decides a text that makes no name and a local collision without a request, before the preview, so the console holds no refused request for an expected state; the preview still answers `name-taken` for the race. The create and join confirmations put the question in the dialog's body under a short title (`Create a shared name?`, `Join a shared name?`): the dialog's header is one line. The field also takes a typed text when it is left without a pick (`blur`). `formatChange` keeps a level row as before (`project:<id> <old> → <new>`) and the Sharing page reads the project of such a row through `projectOfChange`, a leaf export, instead of a regex of its own. `bindMessage`, `nameCounts`, `spokenContract` and `listServerNames` moved from the CLI into the sync client, so the CLI and the viewer read one sentence and make one read; the rule for the contract after a `/v1/me` read is one function, `spokenAfterMe` in `servers.ts`, with one deadline (`CONTRACT_READ_MS`), applied by the sync's start and full sweep, the dock and the CLI, and a non-integer contract in an answer keeps the stored one. The identity leaf's predicates and its SQL fragment are built from `ALIAS_KINDS`. The names list is assembled in the routes from plain rows (`listLiveNames`, `nameCountsOf`, `memberById`), two or three indexed queries per name, the SQL still in `store.ts`.

## Known limits

- A project known by its folder alone becomes a new project when the folder is moved or renamed, and the shared name stays on the old one; the recovery is Nothing on the old project, forget its name, share the new one under the same name (which re-sends). A local move of a name and its level between projects is a later item.
- `knowledge_received.remote_alias` keeps its name on the client though it holds shared names too; only the server's four columns were renamed.
- The list of names is capped at 1,000; a held name past the cap shows as `New` until the server's 409 `exists` catches it at the write.
- Any member may pull a held name (the alias filter is minimisation); a name stays readable by every member until the operator purges it, and the string stays in the server's own records and in the mirror after that (the erasure section above, with its three steps).
- No member-facing route renames, deletes or purges a name; an admin's route is a later item.
- The imported memories never leave (D-6); a per-project opt-in is a later item.
