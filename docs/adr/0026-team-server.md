# ADR 0026 — The team server: `wizardingcode-mem serve`

Date: 2026-11-10 · Status: **draft**. This is part 5 of the knowledge and team journey (2026-11-08-001): the server a team runs on its own host, built and tested in-process, with its image and compose file. The sync client (part 6) and the runbook (part 7) are not built: no client calls this server yet, and nothing on a person's machine sends anything. The twenty-six rulings below were taken with the author on 2026-11-10 (SQLite; several servers per person, a project bound to one; the fastest sync; no token expiry; purge as the operator's; the first slice; the mirror as an export) or recorded as the specification's stated choices; where this record and the specification differ, this record is the later one.

## Context

Parts 1 to 4 built the knowledge store ([ADR 0024](0024-knowledge-module.md)) and the sharing policy ([ADR 0025](0025-sharing-policy.md)): what may leave a person's machine is decided, and nothing leaves. The author asked for the other end: one Docker image on the team's VPS where members' agents share knowledge entries and the memories a project's level allows, in near real time, with the repositories on the volume readable by a person. The author also asked for several servers per person (one for the WizardingCode projects, another for a client's), bound per project, and for the sync to be as fast as it can so the team's work becomes collaborative.

## Decision

`wizardingcode-mem serve` is a long-running process over its own SQLite database, `team.db`, in a data directory of its own, one process per directory. Members join with single-use invitation codes and hold one device token per machine. A device pushes items one by one (`POST /v1/push`) and pulls the feed by a cursor (`GET /v1/pull`), holding the pull open for up to 25 seconds so a change made on one machine reaches another within a second. Every item is kept with every revision; a withdraw is a tombstone; erasure is the operator's `serve purge`. The repositories under `repos/` are an export of the entries, written from the database by `serve mirror`, which the server runs as a child process and the operator runs by hand. The image runs as user 10001 behind Caddy, which terminates TLS. The whole of the server's SQL is one module.

## One process, one store boundary

Every SQL statement is in `src/team/store.ts`, one exported function per statement, and `transaction` wraps the core `withWrite`; `db.ts` holds the schema, the migration list and the three ways to open the file; every other module of `src/team/` calls those functions and holds no SQL (the `team-store-boundary` test reads the folder and fails on an import from `src/store/`, on `bun:sqlite`, or on `.query(`, `.run(`, `.prepare(` and `withWrite(`). Another engine would be a second `store.ts` behind the same signatures. Four other things bind the design to one server process per data directory, and the boundary does not undo them: the change signal a held pull waits on lives in the process; the leases (`serve.lease`, `mirror.lease`) are rows in `meta` renewed by timers of the process; the rate buckets are in memory; the high-water file is written by the process that writes the rows. A second process is refused by the lease; a server whose renewal finds another owner answers its held pulls and exits 1.

## The data model

`team.db` (team schema 1): `meta` (the ids, the leases, `mirror.last`), `members`, `devices` (the token's digest, the alias a feed names a device by), `invitations` (the code's digest), `entries` (keyed by the UUID; `scope`, `remote_alias` and `slug` as attributes of the current revision; `created_by_member`; the current `revision`, `hash`, `size`, writer, `withdrawn_at`, `locked_by_admin`, `mirror_revision`), `entry_revisions` (every revision's bytes, keyed `(uuid, revision)`, with the feed's `seq`), `memories` (one row per device and uid, the payload as JSON), `changes` (the feed: `seq` by `AUTOINCREMENT`, the key, the op `upsert | tombstone | purge`, the scope and alias, a `current` flag and the indexes `(key, seq)` and `(scope, remote_alias, current, seq)`), `purged` (the keys erased for good) and `audit`. An entry's identity is its UUID (ADR 0024, D-8); where it lives is the current row's scope and alias. A memory's key is `<device id>:<uid>`, where the uid is part 4's `<generation>:<row id>`; the feed shows it as `remote:<device alias>:<uid>`, so no member learns another's device id.

## The API

Every route but `/v1/health` and `/v1/join` is authenticated by a bearer token; every 401, 403, 409 and 410 body carries `serverId` and `instance`; every answer carries `X-Request-Id`, the client's own when it is 1 to 64 safe characters. The routes: join; me; rotate; push; pull; the admin's invitations, members, devices, revoke, disable, enable, role, withdraw, reinstate and audit (the plan's route table gives each answer).

**Push.** Items are applied one by one, each in its own transaction, and answered in order as `applied`, `stale` (with `current`), `refused` (with a reason) or `withdrawn`. For an entry send the rules run in this order: the shape (part 4's key list and types, the uid's grammar, the scope and alias agreeing with it), the slug, the size, the hash recomputed over the bytes received, the entry read by part 1's parser (its `id` the uid's UUID, its `area` by the area rule), the secret check, the purged keys, idempotency, ownership against the stored row, the admin's lock, the base (with `appliedAs` when the same device's earlier revision has the payload), the bytes bucket, the storage floor, then the write. Idempotency is over the hash, the scope, the alias and the slug: a retry of an applied item always succeeds, whatever its base, the lock, the bucket or the disk; a move or a rename with the same bytes is a new revision, and a move leaves a `tombstone` with `movedTo` in the range the item left. A memory send runs the same way without a base: a later `updatedAt` replaces, an older one is `stale`. The reason codes are a fixed list of eleven: `shape, size, hash, slug, secret, purged, not-owner, withdrawn-by-admin, unknown, rate, storage`.

**Withdraw.** On the current base, by the entry's creator's member or an admin, by a memory's device, another device of its member or an admin; one retry rule for both kinds: the tombstone's own actor, with the revision just before it, is answered `withdrawn` with nothing changed; any other base is `stale`.

**The alias.** A project is named by part 4's `remote:<host>/<path>` alias, and only a host-led one; the uid grammar is `workspace:<uuid>`, `shared:<uuid>`, `project:<alias>:<uuid>`. The alias filter of a pull keeps a machine small. It is not a permission: any member may name any alias and read any item of the server. The Sharing page already says a shared item reaches the team.

## The feed, snapshots, cursors and the wait

A pull reads the `current = 1` rows after `since` as one indexed range per scope and alias, merged by `seq`, so a key with three rows is served once by its newest; a page stops at 500 items or before the item that would cross 2 MiB. `since` 0 opens a snapshot (`snapshot: true` on that page), paged with `since` set to `next` until `more` is false; "absent from the snapshot is gone" applies to that set and those scopes. A cursor above the sequence is 410 `fullPull: true`. With `wait`, an empty answer waits on the change signal, re-reading every 5 seconds so a write from another process (a CLI tombstone) is seen, and answers the empty page when the wait ends; `stop()` answers every held pull first. A member's view carries the writer's member and no device; an admin's adds the device; a CLI write's row carries `{ id: "operator", name: "operator" }`.

## The server id, the instance and restores

`server.id` is minted once and never renewed: the client keys its ledger and policy by it. `server.instance` changes when the server detects a restored copy: after every write of a feed or audit row the writer rewrites `<data>/feed.seq` with both `AUTOINCREMENT` high-waters, and at start a file ahead of the database on either mark means the database is an older copy; the server renews the instance, advances the feed's sequence by 1,000,000 above the greater mark (so rows written from now on never reuse a number a client passed), rewrites the file, audits `restore detected` and carries on; a database ahead of the file rewrites the file. `serve instance renew` does the same by hand, with the server stopped: the step after a restore of the whole volume, when the file came back with the copy. That is the one undetected case: a client that pulls between such a restore and the renewal reads rows under reused numbers and misses what the restore lost until the renewal makes it pull from zero.

## The mirror

An export (D-26) to `repos/shared/`, `repos/projects/<slug of the alias>-<8 hex of its hash>/` and `repos/members/<member id>-<slug of the name>/`, each with a `knowledge.json` naming it; folders come from ids, hashes and slugs, never the raw name or alias. One commit per revision in `seq` order, the file `entries/<slug>--<8 hex of the UUID>.md` with the bytes verbatim, the message `team: send|withdraw|move <uid>` with the trailers `Revision`, `Uid` and `Hash`, the member as author (`<name> <<member id>@members.wizardingcode.invalid>`) and the server as committer; a withdraw removes the file; a move removes it in the old repository in a commit there and writes it in the new one. A run holds `mirror.lease` (120 s, renewed before every git call through the runner's host; a lost renewal ends the run), goes on past a failing repository and records the error in `meta.mirror.last` for `serve status`; a stale `index.lock` is removed under the lease. Git runs through part 1's runner with the mirror's `repos/` as the ceiling, no user configuration, no hooks, no signing, `--template=` on init and `safe.directory=*` for a volume owned by another user, synchronously in the child process, never on a request. `--rebuild` removes every repository and replays `entry_revisions`, beside the running server; at the pilot's size (20,000 revisions, a git spawn per commit) about 35 minutes. History keeps withdrawn text unless purged.

## Purge

A purge takes the mirror lease first, so a run in progress refuses it ("a mirror run is in progress") before anything is erased, and a run that started after it never writes the purged revisions. Under the lease, one transaction removes the item's row and an entry's revisions, turns its feed rows (the move tombstones included) into `purge` rows with no hash, writes one more `purge` row the devices pull, records the key in `purged`, so a re-send is `refused purged` for good, and writes the audit row; then the repositories the entry's revisions touched are removed and replayed without it, one revision at a time, and a repository that held nothing else keeps its init commit. A replay that fails is recorded in `meta.mirror.last` and in the command's output. The connection runs with `secure_delete` on, so the erased rows are overwritten in the file and the WAL. What a purge does not reach: the upgrade copies under `backups/` (`team-<ms>-v<n>-<pid>.db`, pruned to the newest few of their prefix) hold what the live database held when they were taken, a copy taken before the purge has no `purged` row, and clones of the volume are the operator's; the runbook names removing or purging those copies as the operator's step after an erasure.

## Limits and logs

The limits of D-15 are constants published in `/v1/me`. Three more bound what a request can cost: requests with a missing or wrong token count against their source address (60 a minute, then 429), so a token cannot be guessed at line speed; a device may hold at most 8 pulls open at once, a ninth answering the empty page at once; a pull names at most 100 aliases, de-duplicated. The join and auth buckets are keyed by the address behind the proxy's last hop. A body over 1 MiB is 413 by its header or as its bytes arrive, the rest drained so the answer reaches a client still sending; `Bun.serve`'s own cap is 2 MiB, above the handler's, so Bun's own 413 without a request id happens only past that, and Caddy's `max_size 1MiB` refuses first behind the proxy. The log is JSON lines on standard output: `request` lines with the id, the device, the route, the status, the time, the address, a held pull's time, the pull's cursor and counts, the push's counts and the refused uids with their reasons; `error` lines with the id; every `logError` of the process is routed into it. The bootstrap line is the only secret the log ever carries. A thrown error answers `{ error: "internal error", requestId }`.

## The image and the compose file

The `Dockerfile` builds from the release's `dist/`: a `pick` stage on the build platform maps `TARGETARCH` to the binary's file name and copies it executable into a digest-pinned `debian:bookworm-slim` with git and ca-certificates; user 10001 owns `/data`; the environment sets the data directory, the host `0.0.0.0`, the brand home under `/data` and the migration off; the health check runs `serve health` every 60 seconds. `compose.yml` runs `server` with `init: true`, trust-proxy in its environment, a 30-second grace, a read-only root with `/tmp` on tmpfs, no capabilities, no new privileges and no published port, and `caddy` (digest-pinned) with the domain from `.env`, ports 80 and 443 and the `Caddyfile`: `request_body { max_size 1MiB }`, `header Strict-Transport-Security "max-age=31536000"` (Caddy does not send it on its own), `reverse_proxy server:8787`. The release workflow's `docker` job builds the image for `linux/amd64` and `linux/arm64` from the signed binaries and pushes it to `ghcr.io/wizardingcode-io/wizardingcode-mem` tagged with the version and, for a plain release, `latest`; `publish` waits for it. CI builds the image on the runner, runs it hardened, waits for health, checks the user and the exit code.

## The contract and skew

The contract is the key lists `OUTGOING_ENTRY_KEYS` and `OUTGOING_MEMORY_KEYS`, the result shapes and the reason codes; `CONTRACT_FINGERPRINT` pins their SHA-256 beside `CONTRACT = 1`, and the `team-contract` test fails when they change without the contract. A newer client against an older server speaks the older contract, read from `/v1/me` or the 409; from the first bump the server accepts the previous contract for one release, so a member who has not updated keeps working. The redaction rules are not part of the contract: a server with a rule a client lacks refuses that client's entry with `secret` and the rule's name; the client's upgrade is the remedy, and a new rule ships in the client release first.

## The boundary

What the server holds: members' shared and workspace entries and the memories a project's level allows, stored verbatim with the client's redaction as the only text-level protection and the server's secret check as defence in depth; any member may read any item. Where it lives: the named volume (`team.db`, `feed.seq`, `repos/`, `backups/`), the container's log (the bootstrap code, request lines, no payload), the host (the operator with a shell may read the volume and run `serve purge`). The binary listens on loopback by default and warns once (`plain-http`) on a public host without trust-proxy; behind the proxy every request but health needs `X-Forwarded-Proto: https`, join included, since its answer carries the token. `join` is rate-limited per source address and a refused code is audited with the address, never the code. The audit table holds that address for every join and refused join, with the member's and device's ids for every admin act; its retention is the life of the database: nothing prunes or purges the audit in this part (an `audit` pruning is a follow-up of D-25, below), and a person who asks for their address to be gone is served by the operator with a shell, like a purge.

## Rollback

The server is new code behind a new command; a client without part 6 never calls it. Across a schema bump a previous image exits 3 against the newer `team.db` and `restart: unless-stopped` would loop. The procedure: `docker compose stop server`; then `docker compose run --rm --entrypoint sh server -c 'cp /data/backups/team-<ms>-v<n>-<pid>.db /data/team.db && rm -f /data/team.db-wal /data/team.db-shm'` (the WAL and SHM files go with the replaced file, or a stale write-ahead log replays frames of the newer schema over the older copy); then `WIZARDINGCODE_MEM_VERSION` set to the previous tag in `.env` and `docker compose up -d server`. `feed.seq` stays ahead of the copy, so the restore detection renews the instance and every client pulls from zero and re-pushes what the copy lacks. A writer subcommand of a newer binary refuses to migrate a database a running older server holds.

## The one-time step: the package is public

A package on the GitHub container registry starts private: until the operator makes `ghcr.io/wizardingcode-io/wizardingcode-mem` public once in the organisation's package settings, `docker compose pull` on the VPS needs `docker login ghcr.io` with a token that reads packages. The runbook (part 7) carries both.

## The lease's 30-second window

After a kill the old `serve.lease` stays fresh for up to 30 seconds: under `restart: unless-stopped` the restarted server exits 1 naming the lease, repeatedly, until it expires, and `serve instance renew` refuses for as long. A clean stop releases the lease at once.

## What parts 6 and 7 must do

Part 6, the sync client: hold a list of servers with their `https://` URL, `serverId`, device token and contract; bind a project to one server at most; choose roots and areas per server; key the ledger and the policy by `serverId`, migrating part 4's `sharing_ledger` (`destination` from the one value `team` to a `serverId`); speak the highest contract the server accepts; fill `frontmatter` and `body` by splitting the file's text at the end of the frontmatter block, redact both and recompute `hash` over the redacted bytes; record the local hash beside the server's; treat `applied` with an unchanged revision as success, `stale` with `appliedAs` as an earlier success, `refused` as final for that content (`secret` names the rule; `purged` means drop the copy and never re-send), `rate` and `storage` as "try later"; keep one pull open per server with `wait` while a session or the viewer is active and push right after each local change the policy allows, never on a hook path; open a snapshot at the first pull, after a new `instance`, after a 410, and for one alias when a machine takes up a project; drop the copy of an item whose tombstone says `movedTo` a range it does not read; use the feed's memory uid as it stands and dedupe copied stores by content; re-join with a device invitation on a 401 whose `instance` it does not know. Part 7, the runbook: DNS and ports 80 and 443, never 8787; the three files from the release; `docker login ghcr.io` until the package is public; rotate the first admin's token after joining and rotate Docker's logs; `serve instance renew` after a volume restore and `serve mirror --rebuild` after a database restore without the mirror; the rollback above; the volume at 50 GiB and `serve status`'s free-disk figure; `serve revoke` as the remedy for a looping device.

## Follow-ups

Named by D-25 and not built here: stored daily and per-member quotas; pruning of superseded feed rows and a cursor horizon; pruning of the audit table (its source addresses included); two-phase token rotation; reinstating an entry to a chosen revision; `serve backup`. Known limits of the release path: the release's `docker` job pushes the version tag (and `latest`) before `publish` runs, so a `publish` that fails leaves an image with no release, undone by deleting that package version or re-running the job; the two-platform image is pushed without being run, and the arm64 image runs for the first time on a host (CI runs the amd64 image and the arm64 binary); the apt packages (git, ca-certificates) are not pinned by version, only the base image is. Known limits of the code: a copied client store sends its memories twice until part 6 dedupes by content; join spam from many addresses grows the audit table and the address buckets, with the proxy's own limits as the remedy; memories are ordered by the client's `updatedAt` for a device's own replaces only; the mirror runs on macOS and Linux and is not run on Windows (the runner's isolation holds as ADR 0024 states).
