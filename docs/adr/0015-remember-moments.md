# ADR 0015 — Remember at two more moments: a file read, a failed command

Date: 2026-10-11 · Status: accepted for `file-read` in Claude Code; `tool-failed` is built but held (not installed) after the replay below showed it noisy on real history. The payloads are still the documented ones (not captured in a real session). Roadmap item A4.

## Context

Notes reach the agent at two moments: a brief at session start and a lookup on each prompt (ADR 0002). Two other moments carry more specific evidence. When the agent reads a file, the file itself is the query, and `memory_files` already links memories to project-relative paths. When a command fails, its error is often what a fix or a gotcha was about. The design (`docs/superpowers/specs/2026-10-11-semantic-recall-design.md`, component 6) proposed both; ADR 0014 removed the semantic channel, so both are lexical.

## Decisions

- **Two events, Claude Code only.** `file-read` is `PostToolUse` with matcher `Read` (`hooks/hooks.json`, generated by `scripts/plugins.ts`); `tool-failed` would be `PostToolUseFailure` with matcher `Bash`, and is held (see Decision). Claude Code injects a `PostToolUse` hook's `additionalContext` next to the tool result, which is where a note about that file or that error belongs.
- **Why a read, not an edit.** A `PreToolUse` context on `Edit` arrives next to the tool result too, which is after the edit ran: too late to change it. Reading comes before editing, so the read is the moment to warn.
- **`file-read`** (`src/retrieve/file.ts`): memories linked to the file's project-relative path (resolved first, so a path with `..` is judged by where it points; a path outside the project gives nothing), of kind gotcha, fix, convention or decision, `changed` links before `read` links, then by the usual prior. At most 2 notes within 1,200 characters (about 350 tokens): a read is frequent, so each gets little room.
- **`tool-failed`** (`src/retrieve/failure.ts`): the error is redacted first, the `Exit code N` line, the timeout line and the host's truncation markers are dropped, and the first 2,000 characters go through the prompt lookup (`retrieveForPrompt`) restricted to fix and gotcha memories, with the same evidence rule and the session-files channel. At most 2 notes within 1,200 characters. An interrupted command (`is_interrupt`) and an error with nothing left to search inject nothing.
- **Once per context, across every event.** Both record what they injected in `injections` with their own event name (migration 5 widens the CHECK). A note given on a prompt, a read or a failure is not given again in that context by any of them; a session brief that only named a note does not count, unless the title is all there is to it.
- **Quiet.** Neither event opens a turn, queues work or starts the distiller, the viewer or a backup: they fire per tool call. Subagent events are ignored, as for every event. The output is gated on the adapter's prompt injection, like the prompt's.
- **Why not the other agents.** Codex's `PostToolUse` does not honour `additionalContext` (only a block, which would interrupt the agent). Cursor's `postToolUseFailure` cannot inject context. Gemini's `AfterTool` is not confirmed in a real session. None of them is wired; their specs are unchanged. OpenCode has no comparable hook today.

## Budgets

`tests/perf/budgets.test.ts`, the compiled binary measured from outside, 30 runs after one unmeasured, against a project of 5,000 memories in a store of 65,000. `file-read` reads a file that 3 of the 65,000 memories are linked to; `tool-failed` gets a twenty-word error that shares one identifier with a fix. Each run is a new session, so every run looks the notes up rather than finding them already shown. Budget p95 ≤ 50 ms each (Windows 150 ms); on CI the median is held to the budget × 2.5 and the tail only reported, as for the other events. Apple M4 Max, macOS 26.6.2, the pinned Bun 1.4.2:

## Measured: a replay of the last 30 days

### Method

`scripts/proof/moments.ts <copy.db> <transcripts root>` on a copy of the author's database (taken with `sqlite3 -readonly … ".backup"`; the real one untouched), TypeSafe off, reading the Claude Code transcripts under `~/.claude/projects` changed in the last 30 days (top-level session files only: subagent transcripts are left out, as the hook ignores subagent events; sidechain lines likewise). For every successful `Read` and every `Bash` result marked as an error, it calls `notesForFile` / `notesForFailure` exactly as the hook does (same path normalisation, same gating on `failureQuery`), and records the injections, so "once per context" holds. Its default output is anonymous (projects as letters, files as extensions, no titles); `--full` shows paths, error lines and titles locally and is never to be committed.

- **Sessions.** One fresh session per transcript; the context epoch advances at each recorded compaction (with a new session brief, as the hook does on `compact`). Prompts are replayed through `retrieveForPrompt` and session briefs through `sessionBrief`, because a note they give is not repeated on a read or a failure.
- **Session files.** At the end of each turn, the files it read and changed (project-relative) are stored on a turn row, as the distiller stores them, so the failure lookup's session-files channel sees what it would live.
- **Projects.** A transcript's working directory is mapped with `findProject`, which never creates one; events in directories the database does not know are counted and skipped.
- **Which memories.** All events from all transcripts are replayed in time order. With `--memories then` (the main run) a memory is visible only from its creation time on, so a memory distilled from a session cannot answer that session's earlier reads. `--memories now` uses today's memories throughout: what a session would meet now.
- **Not failures.** A `Bash` error result that never ran is left out: refused or interrupted by the user, denied by a permission rule or by auto mode's classifier, or cancelled because a sibling call failed (the hook is told `is_interrupt` or is not called for these; to be confirmed when the payload is captured).
- **For the overlap concern** (Task 3's review: the session-files overlap plus one telling word lets a fix surface on a loosely related failure), each failure is also looked up with the session's turn rows removed (inside a savepoint, rolled back); a note present only with them came through the overlap.

The copy held 67,800 active memories (67,426 imported from claude-mem, 374 distilled) in 89 projects. A run takes about 4.5 minutes.

### What it means

- **Reads are sparse and on the file.** One read in six injects, never more than one note, and every note is about the file being read by construction. Whether it is worth the interruption varies: six of the ten examples bear on the file (1, 3, 5, 8, 9, 10), four are records of work done on it (2, 4, 6, 7), which the kinds filter does not exclude because the imported memories call them decisions or fixes.
- **The budget, not the evidence, limits reads.** 546 looked-up reads had an eligible linked note, but only 282 injected (264 got nothing), and never two: an imported claude-mem memory averages about 780 characters, so with the intro one note usually fills the 1,200 characters, and when the two best candidates are both too long, nothing is shown even if a shorter third exists. The limit of two is not reached on this database.
- **Failures are noisy.** Five in six failures inject, and of the ten failure examples above none is clearly related by eye: eight are unrelated, two share only the kind of mistake. Most "failures" in these sessions are not errors at all but the output of a command that exited non-zero: a `grep` that found nothing, a script printing sections, a directory listing, a traceback from a one-off check. That output is long and full of identifiers and file names, and the evidence rule accepts any memory that shares one identifier. One example (11) is another plugin's `PreToolUse` hook refusing the command, which may not reach `PostToolUseFailure` at all.
- **The overlap channel.** It brought 63 notes on 62 failures, about one injecting failure in five, and in every one of them the overlap was the only reason the note came.
- **Then and now agree.** With today's memories, slightly more reads inject (20.3% against 17.0%) and failures barely change: the noise is not an artefact of hiding the future.

The retrieval rules were not changed to improve these numbers. Whether `tool-failed` ships as is, is narrowed (for example a stricter evidence rule for failures, the error's first lines only, or no session-files channel), or is held back is for the author to decide.

## Decision

By the author's decision after the replay: **`file-read` ships; `tool-failed` is held.**

- **Held, not removed.** The `PostToolUseFailure` entry is taken out of `CLAUDE_CODE.events` (`src/install/claude-code.ts`), so neither `install` nor the generated `hooks/hooks.json` hooks it, and `doctor` does not ask for it. The event type, the payload parsing, the handler, `notesForFailure`, the golden cases and their tests stay, so the work is not lost and stays tested. `uninstall` still removes a `PostToolUseFailure` hook of ours left by a development install, because it removes our entries under any event. `tests/perf/budgets.test.ts` keeps measuring `tool-failed`: the handler still runs if called, and the budget must hold the day it returns.
- **What a return requires.** A narrowed version: only test-like and build-like commands (a test runner, a build, a typecheck, a linter, a package install), not exploratory ones (`grep`, `ls`, `cat`, one-off scripts); stronger evidence (no note on a shared identifier alone, and no session-files channel for failures); measured again with `scripts/proof/moments.ts` on the same replay (last 30 days, memories as of then) with **at most 20% of failures injecting** and the sampled failure examples judged relevant by eye. Until then it is not installed.

## Not confirmed yet

- **Payloads.** The `PostToolUse` (Read) and `PostToolUseFailure` (Bash) fixtures in `tests/fixtures/claude-code/payloads/` follow Claude Code's documentation; neither has been captured from a real session, nor has it been seen that the notes reach the agent's context next to the tool result. That needs installing this build into a real Claude Code, which waits for the author.
- **What fires `PostToolUseFailure`.** Whether commands denied by a permission rule or by auto mode, cancelled siblings, or a `PreToolUse` hook's refusal reach it; the replay assumes not for the first three and counts the last as a failure.
- **Parallel reads.** Claude Code runs parallel tool calls' hooks concurrently; the unique index and `INSERT OR IGNORE` keep a note from being recorded twice, but two processes could each inject the same note once before either records it. Not observed; not measured.
