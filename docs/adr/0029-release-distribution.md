# ADR 0029 — The release distributes itself, and the staged binary only moves forward

Date: 2026-11-12 · Status: **draft**. Work item 2026-11-12-004, piece 1 of 3 of 2026-11-11-004 ("updated everywhere on release"). Its piece 2 is narrowed by [ADR 0030](0030-release-notice.md): the client is told of a release and does not follow by itself. It supersedes the Homebrew row of [ADR 0008](0008-m5-distribution.md) (the source copy of the formula under `packaging/homebrew/`), amends its npm and curl rows (the npm package and the curl script now replace only an older binary) and carries out that ADR's follow-up to automate the rest of a release. It amends [ADR 0026](0026-team-server.md)'s paragraph on the image: the release's `docker` job no longer tags `latest`; the distribution does, last, and may hold it. [ADR 0009](0009-native-installation.md) is unchanged: the files each agent installs are still generated by `scripts/plugins.ts`. The author's procedure is `docs/runbooks/release.md`.

## Context

A tag `v<version>` built the release and stopped there. The Homebrew formula, the plugin's entry in the marketplace's two manifests and the release notes were written by hand for 0.7.0 and 0.8.0, and npm was not published at all: both packages stood at 0.4.4 while the repository was at 0.8.0. A forgotten step left the channels on different versions.

Every channel stages the binary the agents run at `<data dir>/bin/wizardingcode-mem`. Three of its five writers moved it back to an older version: the npm package's shim on any version difference, `wizardingcode-mem install` always, the curl script always. The two that compared versions ordered pre-releases as strings, so `0.9.0-rc.10` was older than `0.9.0-rc.9`. An older binary put over a newer one then refuses a store the newer one migrated.

## Decision

**Two workflows.** `release.yml` keeps building and publishing the GitHub release; it no longer tags the image `latest`, and it ends by starting `distribute.yml` from `main` with the tag. `distribute.yml` is dispatch-only and has five jobs: `plan` decides whether the tag may be distributed; `npm` publishes both packages by trusted publishing; `tap` writes the formula, rendered from a template with the release's checksums; `marketplace` writes the plugin's entry in the two manifests; `latest` retags the image last. The decisions are pure functions in `scripts/release/lib.ts`, which also carries what the commands share (the one runner of other programs, the summary and output writers); the workflow's shape is held by `tests/unit/deploy-files.test.ts`.

**What the token and the publish right rest on.** They sit behind the GitHub environment `release`, whose rule allows the branch `main` alone, and the npm trusted publishers name that environment and the file `distribute.yml`. `plan` reads the environment through the API and refuses to go on when it is missing or its rule is anything else, because a job that names a missing environment makes GitHub create it with no rule. `plan` also refuses a run that is not on `main`, a tag whose commit is not on `main`, and a tag whose version is not its commit's `package.json` version; `npm` checks out the commit `plan` judged, never the tag by name; the writer to the other repositories refuses when the tag no longer names that commit. That writer (`scripts/release/push.ts`) hands git the token as a basic authorization header in the child's environment, and redacts the encoded credential by exact match from every text git answers before a failure's sentence or a dry run's line is built from it, so what it prints and appends to the run's summary never carries it. The match is exact: a text that splits or re-encodes the value is not covered, and a change that builds another form of the credential must add its own redaction. No `::add-mask::` line is printed for the encoded form: the runner registers the base64 of every secret at three byte alignments (`ValueEncoders.cs` in `actions/runner`, read on 2026-11-12; not tested here), which covers the token inside the header in the log, and such a line would itself print the whole credential to standard output.

**Never lower.** Only the highest release is distributed: a plain tag must be the highest plain tag merged into `main`, a pre-release the highest of all. Repeating is therefore safe: each target first looks at what is there.

**One version order.** Semantic versioning's precedence, in three implementations held equal by one table (`tests/fixtures/version-order.ts`): `src/util/version.ts`, the JavaScript `older()` (`OLDER_JS` in `scripts/plugins.ts`, in the OpenCode package and the npm shim) and the shell `older()` (the plugins' script and `scripts/install.sh`). A version that is missing or malformed is older.

**The staged binary only moves forward.** Each of the five writers replaces only an older or equal version. `install` stages once per run and, when a newer binary is in place, says so and hands the install over to it. `install --force`, and `--force` passed to the curl script, is a person's way back.

## Rulings

Taken by the author (2026-11-11 on the parent item, 2026-11-12 on this one):

- A server follows the image tag `latest`, moved last, after every other target succeeded (D-1 of the parent).
- The writes to the tap and the marketplace use a fine-grained token, `MARKETPLACE_TOKEN`, not a GitHub App (D-3, D-9 of the parent).
- npm is published by trusted publishing, with no token in the repository (D-4 of the parent).
- The work is three items: this one, then the client that learns of a release and follows it, then the server that upgrades itself (D-8 of the parent).
- D-1: `distribute.yml` is a separate, dispatch-only file under the environment `release`, not a second trigger of `release.yml`.
- D-2: the contract rule lives in this piece, corrected: `latest` is held when the release's lowest accepted contract is above the contract the previous plain release speaks, and a dispatch input releases the hold. The author kept it here knowing that nothing reads `latest` until piece 3.
- D-3: no scheduled check of the token between releases. The release run names a token that is missing, expired, without access or within thirty days of an expiry GitHub returns.
- D-4: a ruleset that reserves `v*` tags to admins is a mandatory step of the setup.
- D-5: `main`'s ruleset requires a pull request and its checks but no approval. That limit is written down, not changed: the distribution trusts what is on `main`, and one approval is to be required once a second person has write access.

## Alternatives

- **One `release.yml` with a second trigger.** A job that needs a skipped job is skipped too while the run still reports success, and a dispatch builds the branch it was started on.
- **`distribute.yml` on the `release` event.** A release created with the workflow's own token starts no other workflow; a dispatch does.
- **The contents API for the other repositories.** Each write needs the file's sha, a base64 body and a hand-made no-change comparison; a clone and a push give the same result under git's own conflict rule.
- **Editing the manifests by parsing and re-serialising.** The agents' manifest holds one-line inline objects, so a re-serialisation rewrites bytes that are not this plugin's. The edit is on the text, inside the plugin's entry only.
- **A hand copy of `older()` per writer, each with its own tests.** Nothing would hold them equal, and the two that existed already disagreed with semver. The copies stay, with one table and two byte-for-byte tests over them.
- **Pre-releases narrowed to `-rc.<n>`.** Binaries already staged may carry any pre-release.
- **A weekly check of the token.** The expiry header is documented only in a 2021 changelog that predates fine-grained tokens, GitHub disables a scheduled workflow after 60 days without activity, and GitHub emails the owner anyway.
- **The contract rule on any rise of `CONTRACT`.** It holds where nobody is refused: the server accepts the contract before its own.
- **The environment's rule, or the tag ruleset, left to the runbook alone.** Neither is a file a test can read. The environment's rule is checked by `plan` on every run; the tie between a tag and `main` is the ancestor check, with the ruleset as the second barrier.

## Limits

- The first real run is the first exercise of the four writes to the outside (the npm publish, the two pushes, the image's retag). A dry run proves the checks, the renders and the edits, and none of those four.
- The barrier is a pull request with green checks. It stops access from a branch or a tag, not a person who can merge to `main`; a repository admin can change the environment and the rulesets.
- A release's binaries and `checksums.txt` are not tied to the commit `plan` judged: someone with write access can replace them between the release and its distribution. Signatures are not part of this item.
- `latest` can be moved outside `distribute.yml`: a tag on an older commit runs that commit's `release.yml`, and a branch's workflow can ask for `packages: write`. Nothing reads `latest` until piece 3, which must take this up.
- A tag on `main` whose release failed blocks the repeat of the release before it, until that release is completed or the tag deleted.
- The hold looks one release back, as the server's accepted contracts do.
- `install --force` is a way back for one binary, not for a machine: a plugin still at the newer version stages the newer binary again at its next session start, and an older binary refuses a store the newer one migrated.
- `release.yml` is green once the distribution is started; whether the distribution succeeded shows on its own run.
- A staged file that answers a very high version is kept by every channel and replaced only by `--force`. Only someone who can already write to the data directory, or cut a release, can put one there.
- npm packages published before this item (0.4.4) keep the old rule on the machines that hold them.
- The first publish takes every unpinned npm user (`npx wizardingcode-mem`, the OpenCode package) from 0.4.4 to the current version in one step, across every store migration since; a 0.4.4 shim still on such a machine then meets a store it refuses. The way back is the current package, or a backup. The runbook has the first release go out as a pre-release under `next` first.
- The dist-tag `next` stays on the last pre-release after a plain release supersedes it; a version published and later unpublished is reported as already published.
- The formula's template and the scripts are read from `main`, not from the commit `plan` judged; only the highest tag is distributed, so `main` is never behind it, but a template changed on `main` after the tag is the one used.
- The tap has no check of its own against a lower version: the highest-tag rule is what keeps it from moving back.
- `plan` checks the environment's rule on every run but not the ruleset on `v*` tags, which stays a step of the setup.
- The command of `push.ts` takes no destination from its environment: the two repositories come from its code and `GITHUB_REPOSITORY`, and writes are tested through `commitAndPush` against local repositories. This removes a named knob, not the reach of whoever controls the step's environment, who holds the token and can still configure git through `GIT_CONFIG_GLOBAL` or a home `.gitconfig`; the token's git is not isolated from global and system configuration, and its calls have no time limit of their own beyond the job's.
- The token is one person's.
