# ADR 0027 — The sync client: `wizardingcode-mem sync`

Date: 2026-11-11 · Status: **draft**. This is part 6 of the knowledge and team journey (2026-11-08-001): the process on a person's machine that sends what the sharing policy allows to the team servers the person joined, and brings the team's entries and memories back. Parts 4 ([ADR 0025](0025-sharing-policy.md)) and 5 ([ADR 0026](0026-team-server.md)) built the policy and the server; nothing left a machine until this part. The ten rulings below were taken with the author on 2026-11-10 (D-9 by the author's word, the rest as the specification's stated choices, confirmed at the spec review); where this record and the specification differ, this record is the later one. The runbook (part 7) is not written.

## Context

The policy says, per project and per root and area, what may leave; the server keeps every revision a device sends and feeds a device what its projects need. Between them a machine needed: a list of servers with a device token each, a process that runs while sessions do and never on a hook path, a sweep that sends the allowed items and withdraws what the policy no longer allows, a pull that applies the team's items to a received store the agent can read but never edits, a rule for a revision of the person's own entry that arrives from a teammate, and the hold that keeps a restore or a surprise from withdrawing a team's items by mistake. Every one of those had to survive a laptop's sleep, a restore on either side, a revoked device and a server rebuilt from an old copy.

## Decision

`wizardingcode-mem sync --auto` is a detached process, one per data directory by a lease in `meta`, started by the session-start and prompt hooks and by the viewer, which leave within a millisecond of asking. It ticks every two seconds on SQLite's `data_version`, sweeps what changed at most every five seconds and everything every minute, holds one pull open per server, and exits after fifteen idle minutes. A project binds to one server at most; a device token lives in `<data dir>/servers.json`, outside the database and its backups; the ledger, the server list, the cursors and the state live in the database. Received items live under `knowledge/received/<serverId>/`, read-only, marked, never pinned, erased with the server. A teammate's revision of the person's own entry is applied to the file and the person's text becomes a proposal and a conflicts row. A withdrawal the person did not ask for is held until `share server resume`.

## Rulings

| Ruling | Decision | Why | Cost if wrong |
| :- | :- | :- | :- |
| D-1 | The sync is its own detached process, `sync --auto`, started by the session-start and prompt hooks and by the viewer, one per data directory by the lease `sync.lease` (60 s, renewed every 20 s), never on a hook path. | A hook has 100 ms and must never open the network; a process that is already running costs the hook one statement and one `kill(pid, 0)`. | A machine with several data directories runs several syncs ([The process](#the-process)). |
| D-2 | On a stale push of an own entry, the server's revision is applied to the file; the local text is kept as a proposal and in a conflicts row, never lost, never sent until the person accepts it. | The server's copy is the team's; the person's words are never discarded by a machine. | A person who edits while offline finds a proposal, not the edit, in the file. |
| D-3 | The CLI and the viewer's Servers card both ship: `share server add | rejoin | remove | mute | unmute | resume | list`, the Servers card, the Sharing card's server selector, the project dock's selector and the listed routes. | The viewer is where levels are set; the CLI is what a runbook can script. | Two surfaces to keep in step ([The viewer](#the-viewer)). |
| D-4 | The first run after a server is added sends everything the policy allows, batched under the server's limits (200 items, 900 KiB of serialized body), resumable, shown by `status`. | A team that joins late gets the history, not a trickle. | A large store's first run takes minutes; `status` shows the backlog. |
| D-5 | The team's project items arrive whenever there are changes, with no step beyond binding the project to the server; a level above `receive` is needed only to send. | Reading the team costs nothing; sending is the choice. | Revised by D-9 for what a pull names. |
| D-6 | Received items live apart under `knowledge/received/<serverId>/`, read-only, erasable, marked, never pinned; `knowledge take` copies one to edit; received memories carry provenance, take at most a third of a brief's slots, and a server or a member can be muted. | The agent must tell a teammate's word from the person's; the person must be able to erase a server's trace in one move. | A pin a teammate sets is not honoured here. |
| D-7 | The device token lives in `<data dir>/servers.json` (0600) beside the env file, outside the database file and the backup; the server list, the cursors and the state live in the database. | A backup copied to another machine must not carry a credential; a restore must not revive a revoked one. | A restored machine re-joins with a code (`share server rejoin`). |
| D-8 | A conflict is a proposal by `sync:<serverId>` on behalf of the person, outside the quota, plus a `sharing_conflicts` row; the server's revision and instance, with the sent-hash history, tell a rollback from a conflict. | A rollback on the server must re-send, not propose; a conflict must survive a full proposal queue. | The sent-hash history is eight hashes per uid ([Conflicts and rollbacks](#conflicts-and-rollbacks)). |
| D-9 | What a pull names to a server: only the projects bound to that server (any stored level but Nothing, `receive` included), so no server learns the names of projects the person did not bind to it. | The author's choice on 2026-11-10 over naming every local project not bound to another server. | A project is received only once the person binds it. |
| D-10 | A withdrawal the person did not ask for is held: after a restore, and when one sweep would withdraw, for reasons no action of the person explains, more than 20 items or more than half of a server's sent rows. A withdrawal that follows the person's own narrowing is never held. `share server resume` shows what would be taken back, per project, and releases the hold on the yes, which authorises that set for the next sweep. | A restore resets every level to Nothing; without the hold the next sweep would withdraw the team's copy of everything this device sent. | A person who never resumes keeps a server's stale copies ([Known limits](#known-limits)). |

## The process

`src/sync/run.ts` is the loop; `src/cli/commands/sync.ts` the command (`--auto`, `--once`, `stop`); `src/sync/spawn.ts` what the hooks and the viewer call. The context (`src/sync/context.ts`) carries the connection, the data and store directories, the environment, `fetch`, a clock and timers (tests inject fakes, `tests/helpers/clock.ts`), the pid, the binary's version and a log function; the loop sets `ctx.lease` to its owner, and every write of the sync runs through `guarded`, one transaction that first checks the lease is still the context's and throws `LeaseLost` when it is not.

- **The lease.** `sync.lease` in `meta`, owner `sync-<pid>-<version>`, 60 s, renewed every 20 s; a dead owner's lease is taken; a newer version takes over an older holder's, which writes nothing after losing it and exits 1 after its page. `anyLeaseActive` counts it, so a move, a compact or a restore knows the sync is there.
- **The stop flag.** `sync.stop` (who, when). `sync stop`, `backup --restore`, a store move, `compact` and `share server remove` set it, wait up to 30 s for the lease's release (`stopSync`, the three store operations through their own clock and timers) and clear it at their end; the loop reads it every 5 s on its own interval and leaves within that; the hooks and the viewer spawn nothing while it is set; a flag older than ten minutes is stale and cleared by the next spawn.
- **The ticks.** `PRAGMA data_version` every 2 s; a change from a quiet state is swept at the next tick, a burst coalesced into one sweep per 5 s; a full sweep every 60 s whatever changed; its own writes move no `data_version`. A quiet tick sweep on the fixture (1,000 entries, 10,000 memories) issues one indexed query over the memories and none over the entries or the ledger, and reads no row: the entries are read only when a repository's HEAD moved since the last look, the memories through the window `updated_at >= last read's start OR id > the highest id seen`, through the index `sharing_memories_updated` on `memories(updated_at, id)` (owned by the sharing namespace, created by migration `0002_sharing_servers`, `INDEXED BY` for the first half and the rowid for the second), and the ledger only against candidates. A tick runs no `git status`; the full sweep refreshes at most three repositories in rotation and asks the working trees.
- **Idle and exit.** It exits within a minute once fifteen minutes pass with no hook run, no live viewer and no backlog, and not while a viewer is live or a backlog remains. Exit codes: 0 done or a second `--auto`, 1 the lease lost or a stopped server, 2 `--once` refused while `--auto` holds the lease, 3 a start that failed, after writing `sync.last_failed_start` (time, reason, failures): the next spawn skips while the mark is younger than five minutes, then ten, then an hour; a start that reaches the loop clears it. `WIZARDINGCODE_MEM_SYNC=off` makes `--auto` exit 0 at once and the spawn a no-op.
- **The hooks' spawn.** On `session-start` (any source) and `prompt`, `handleHook`'s `spawnSync` dep (optional, as `spawnViewer` is; the hook command wires it to `startSync`) runs one statement over `sharing_servers` and `meta` (the schema's presence asked of `sqlite_master` once per connection), one `kill(pid, 0)` for the lease's pid, and spawns `sync --auto` detached when there is a confirmed, not stopped server, no live lease, no flag and no young mark; any failure fails open. The viewer calls the same function at its start and `POST /api/sync/run` spawns `sync --once`, which skips the failed-start backoff (a person's own run). The hook snapshots are unchanged with no server listed.
- **The start's steps**, before any sweep or pull: `deleteServerReceived` for every server id with received rows or a folder under `knowledge/received/` but no `sharing_servers` row; `reindexReceived` over the listed servers' folders (the folder is the truth; a server whose id the store writes no path for is skipped with a log line); the close of conflicts rows whose proposal is no longer open. A confirmed server with no token fails the start (`token missing … share server rejoin`).
- **The log.** `logError` writes one line per distinct error per server and operation with its count; no token, code or payload reaches the log or `last_error`.

## The servers and the tokens

`src/sync/servers.ts` owns `sharing_servers` and `sharing_muted_members` and the token file; `src/sync/join.ts` the join, the confirmation, the rejoin, the removal, the mutes and the resume; `src/sync/client.ts` the HTTP client (`join`, `me`, `push`, `pull`, a deadline on the injected timers, the loopback allowed over http, never a redirect) with typed failures. `share server add <url> --code <code>` (or the code typed on the terminal with no echo) checks the URL, joins, writes the token to the file first and the row pending, reads `me` for the limits, prints the counts of what would leave and confirms on the yes; a server whose id is not sixteen hex is refused (`server-id`) before anything is written, since the received store writes no path for it. `rejoin` replaces the device of a listed server with a new code; `remove` stops the sync through the flag, refuses with open conflicts unless `--yes`, withdraws every sent item first with `--withdraw` (a `stale` retried once on `current`; a second failure refuses naming the count, the server still listed), then deletes in one transaction the server's received files, rows and memories, its levels, ledger rows, refusals, conflicts, sent hashes, mutes, pending rows, unbound rows, hold key, authorised list and its row, logs the change and forgets the token; the device stays on the server until an admin revokes it. A reference that names two servers is refused with their ids.

A server's state: `pending` (added, not confirmed), `token missing`, `stopped` (`contract`, `unauthorized`, `rejoin` after a 410 the cursor could not survive, `disabled`) with its remedy, or `ok`. A 401 or 403 stops the server; a 409 on the contract stops it; a 410 sets a snapshot due; a new `instance` in an answer sets a snapshot due and drops the pending rows.

## The policy per server

The destination of a level is a server id; `team` remains the default while no server is confirmed, and once one is, `reconcileLevels` removes a `team` row with a logged `system` change. `loadPolicy(db, dataDir, env, serverId)` intersects the server's lists (`sharing_servers.roots` and `areas`, edited by `share roots | areas --server <s>` and the viewer's selector) with the env file's and the environment's; the env file's lists stay the ceiling. The level `receive` binds a project without sending (`decide` answers `keep` with `level-receive`); Nothing to `receive` needs no confirmation, `receive` to Knowledge does. `setLevel` refuses a level other than Nothing for a project bound to another server (`one-server`), and the partial index `sharing_levels_one_server` refuses it in SQL; the index leaves out the destination `team`, so part 4's two-destination test keeps passing. Every reader (the viewer's project list and sharing routes, `status`, `doctor`, `share project`) reads the level of the project's bound server, else Nothing, never `team`.

## The outbound side

`src/sync/outbound.ts` is the sweep. Candidates: own entries whose index hash differs from the ledger's `local_hash` or that have no record, read from committed files only (an uncommitted edit is skipped and counted as dirty, `sync.dirty:<serverId>` in `meta`, until it is committed); memories from `memoryItems` in the tick's window or every memory on a full sweep, after an epoch or a generation change, or at the first run. The payload splits the file at the end of its frontmatter block, drops the `pinned` line, redacts both halves (`redactForSend`) and hashes the redacted bytes as the server does (`entryBytes` of `src/team/contract.ts`); a memory's payload and hash are ADR 0025's. Batches of 200 items and 900 KiB of serialized body, the live change first; a 413 splits the batch; an item over the per-item limit `me` publishes is refused locally as `too-large`. Answers: `applied` writes the `sent` row (the server's revision, its hash, `local_hash`, `instance`, `policy_epoch`, `reason`) and the sent-hash row; `stale` on a memory is recorded as sent with the local `memoryHash` as `local_hash` (the server holds a later copy); `stale` on an entry is a rollback when the server's revision is below the ledger's or its instance differs, and the item is re-sent once on `current`, else a teammate's revision the pull brings; `refused` is kept with its rule and never re-sent for that hash, `purged` for good; `rate` and `storage` schedule the next sweep. A move sends the new uid on the old row's base and retires the old row with reason `moved`.

Withdrawals (D-10) run on the full sweep: the not-withdrawn sent rows whose item is gone from a present, readable repository or no longer decides `send`. A withdrawal a `cli` or `viewer` change after the sent row explains (a narrowing of a level, the roots or the areas) is never held; the rest are held when more than 20 or more than half of the server's sent rows, under `bulk`, or whenever a `restore` hold stands. The hold key `sharing.restore_hold:<serverId>` carries its reason, its time and the count the last sweep held; `share server resume` (and the viewer) previews the set per project, refreshing every opened repository first so the preview tells the truth after a restore, and the yes writes the set as authorised (`sharing.resume_authorised:<serverId>`), which the next sweeps withdraw and consume, holding nothing for it; a sweep interrupted by `rate` keeps the rest authorised.

## The inbound side

`src/sync/inbound.ts` is the pull; `src/sync/received.ts` the received store; `src/sync/naming.ts` the grammar of every path component the server supplies (sixteen-hex server ids, twelve-base32 member ids, the contract's project folder and file name, a UUID). One main pull per server with `scope=all` and a sticky set of at most 100 bound aliases (`planAliases`), the aliases past it pulled with `scope=project` in rotation at 60 s; a one-alias snapshot when a project is bound; `reconcileReceived` before the first page (an alias the person unbound loses its copies unless an enabled project is bound under it again); pages applied in chunks of 50; a row whose target is dirty or locked stops the cursor and is set aside in `sharing_pending_rows` after ten tries, a row that fails for any other reason is set aside at once with the failure named, and the pending rows are re-applied hourly, oldest first, a row that applies dropping itself and every older row of its uid (an older row that still fails must never come back over the later revision) while a newer row that still fails stays; a move's tombstone leaves the copy for the upsert that follows only when this machine reads the new range, else deletes it. A snapshot's comparison runs after a cursor's last page over everything every page of it showed, entries and memories alike: a received entry or memory the server no longer has is deleted with its copy and its provenance, a sent one cleared and re-sent on base 0; a cursor whose snapshot completed is not pulled from zero again when a cut snapshot restarts. A teammate's revision of an own entry is a conflict when the file's own hash differs from the sent row's `local_hash`, whatever the index holds.

A received entry is written verbatim under `knowledge/received/<serverId>/{shared,members/<member id>,projects/<slug>-<8 hex>}/entries/<slug>--<8 hex>.md` (the project folder carries `knowledge.json` with the alias; the slug is derived from the title, since the feed carries none, so a name may differ from the server mirror's), then its `knowledge_received` row, its search row (`knowledge_fts` with `repo_id` 0 and `entry_id` `<serverId>|<uid>`) and its `received` ledger row in one transaction. A received memory is an `imported` row with `judge team:<serverId>` and a provenance row (`sharing_received_memories`), deduped by the SHA-256 of title and body; `history replace-imports` spares them and `rejudge` never selects them. The knowledge reads (`index-store.ts`) show received entries to a project bound to the server, for listed, confirmed, unmuted servers and unmuted members, with `from <member> via <server>` and, for the person's own entry a teammate revised, `revised by` and the held pin; the floor shows at most one received entry per prompt; `knowledge_get` takes `<server>:<slug>--<8 hex>` (a server whose name holds a colon, by its id). Retrieval (`src/retrieve/received.ts`, `brief.ts`, `prompt.ts`) gives received memories at most a third of a brief and of a prompt's notes, after the person's own, marked `(team: <server>)`.

## Conflicts and rollbacks

`src/sync/conflicts.ts`: a teammate's revision of an entry this device sent is applied to the file by the sync writer (author the member, committer `wizardingcode-mem sync <sync@<serverId>.wizardingcode.invalid>`, message `sync: apply <uid> revision <n> from <server name>`), the ledger's `applied` row holding the server's revision and the member's name in `reason`; when a local edit was in flight, the person's text becomes a proposal by `sync:<serverId>` on behalf of the person, outside the quota, and a `sharing_conflicts` row with the local text, version and hash and the server's revision and hash; accepting or rejecting the proposal closes the row; the start closes orphan rows. A rollback on the server (`stale` with a revision below the ledger's, or another instance) re-sends the own text instead.

## Restore, move and compact

`backup --restore` carries eight tables from the live store into the copy before the one commit point, the rename: `sharing_servers`, `sharing_muted_members`, `sharing_ledger`, `sharing_sent_hashes`, `sharing_refusals`, `sharing_conflicts`, `sharing_pending_rows` and `sharing_unbound`, server by server, so a listed server's ledger is the live one (no refused hash is re-sent, no conflict's text is lost, the old generation's memory uids can be withdrawn) and an unlisted server's rows are gone; the copy is first brought to this binary's schema through `openStoreFile` with `upgradeBackup: false` (the core and the module upgrade make no copy of the copy); then `resetLevels`, the copy's hold keys, authorised lists and `sync.*` marks cleared, a hold with reason `restore` on every listed server, `snapshot_due` on each, `PRAGMA journal_mode = DELETE` and the close; a `-wal` or `-shm` file beside the unpacked copy refuses before the open, and a `-wal` still beside it after the carry refuses the rename (a leftover `-shm`, which holds no row, is removed). The copy is inspected read-write, since a copy whose header says WAL cannot be opened read-only. The report names the carried servers and the dropped ones whose received copies the sync's next start deletes (`sync --once` with no server listed runs the start's steps and exits 0). The restore, a store move and `compact` stop the sync through the flag instead of refusing on its lease, and refuse with their own busy error when it has not left within 30 s; `compact` is async for it; the move removes the flag from the moved copy.

## Status, doctor and explain

`status` prints the sync's state (`not running …`, `running (pid), idle since …`, `stopping …`, `stopped by …`, `start failed: …; next try …`, or a lease held by a pid that is gone) once a server is listed or something of the sync stands, and one `server` line per server: name, host, member and role, the state with its remedy, cursor, last push and pull (attempt and success), backlog, dirty paths, pending rows, open conflicts and a held withdrawal with its reason and count; `status --json` carries `sync`, `servers` and `now`, never a token. `doctor sync` warns for the token file's mode, an orphan token, a confirmed row with no token, a non-https URL (loopback http allowed), a stopped server with its remedy, a lease whose process is gone, a stale stop flag, a failed start with its reason, a server with no successful push or pull in 24 h while sessions ran, open conflicts, pending rows and a held withdrawal, and asks the network nothing; on a store at sharing v1 neither prints a server line nor warns of the sync. `share explain … --server <s>` prints the ruling and the item's ledger history, the `applied` rows included. `src/sync/report.ts` is what the three readers and the viewer read, through `state.ts` and `ledger.ts`, with no SQL of their own; the viewer's server routes also read `servers.ts` (the list and one server) and the ledger's open-conflict count, and `doctor` checks a URL with the client's `checkServerUrl`, a pure function that makes no request.

## The viewer

A `Servers` card under Settings, above Sharing: the list (name, host, member and role, state, last sync), Add (URL, code, label, name; the counts and a Confirm before the yes; a pending row with its Confirm), Rejoin, Remove (naming what is deleted, with the withdrawal as a choice), Mute, Resume while a hold stands, Run now, and the sync's line. The Sharing card names the listed server and, with several, a selector picks whose roots and areas the switches edit (`GET /api/sharing?server=<id>`, `PUT /api/settings` with `server`), the file's lists stated as the ceiling; the project dock names the bound server, offers Receive only and, with several servers, a picker for an unbound project (`PUT /api/projects/<id>/sharing` with `server`; `400 { error: "server" }` when several are confirmed, the project is bound to none and no server is named). Routes: `GET /api/servers`, `GET /api/sync`, `POST /api/sync/run`, `POST /api/servers` (with `code`; with `yes` for the pending row of that URL), `POST /api/servers/<id>/rejoin|mute|unmute|resume`, `DELETE /api/servers/<id>` (`withdraw`, `yes`; 409 `conflicts` with the count, 409 `withdraw` with what is left, 503 `sync` when it does not stop); no answer carries a token. The UI evidence is `.crew/work/<item>/review/ui/`: every declared state at 360, 768 and 1280, light and dark, taken by the Bun script over Chrome's DevTools protocol against the real routes.

## The boundary

`tests/unit/sync-boundary.test.ts` holds it: `src/cli/commands/hook.ts` reaches `src/sync/spawn.ts` and nothing else of `src/sync/`, `src/hooks/handle.ts` nothing of it, and `spawn.ts` imports nothing else of the folder; `src/sync/` imports nothing of `src/team/` but `contract.ts` (which exports the shapes and the hashing both sides share), and `src/team/` nothing of `src/sync/`; the knowledge module and retrieval import nothing of `src/sync/` or `src/sharing/`; `src/sync/` and `src/backup/` never import each other. The ledger's seven tables are named in SQL only in `src/sync/ledger.ts`, `src/sharing/`, `src/backup/backup.ts`, `src/store/memories.ts` and the three readers (`index-store.ts`, `contribute.ts`, `src/retrieve/received.ts`); `sharing_servers` and `sharing_muted_members` also in `servers.ts`, `state.ts` and `spawn.ts`; `sharing_levels` and `sharing_changes` only in `src/sharing/`, `backup.ts` and, for the levels, the two readers; `status`, `doctor`, the viewer's server, `join.ts` and the knowledge tools name none.

## What building changed from the plan

- `tests/helpers/clock.ts` (one fake clock and timers for the server and the client tests), `SyncContext.lease`, `applyRevision`'s `uid` and `revision` options, the member's name in the `applied` row's `reason`, and `sync.dirty:<serverId>` as a `meta` key, defined in `src/store/meta.ts`.
- The feed carries no slug, so a received file is named from the entry's title and may differ from the server mirror's name; changing the contract was out of this part's scope.
- The one-server index excludes `team`; a server whose name holds a colon is referred to by its id in `knowledge_get`; `sync --auto` exits 3 with no mark when `openDb` itself fails (nowhere to write it); the retrieval's SQL lives in `src/retrieve/received.ts` rather than in `brief.ts` and `notes.ts`.
- The index `sharing_memories_updated` on the core table `memories`, created by the sharing namespace's migration 2 for the tick's window; the migration is unreleased, so no store outside this branch ran it without the index, and a development store that did needs the index created by hand.
- `openRepos` takes how many repositories to refresh (none on a tick, three on a full sweep, all for a resume preview); the hold carries a `count`; the join refuses a server id the received store cannot name; the re-index skips such a row.
- `openStoreFile` and `upgradeBackup`; the copy inspected read-write; the `-shm` removed and the `-wal` refused after the carry; `RestoreOutcome.servers` and `pendingDeletion`; `compact` async; `clock` and `timers` on the restore, the move, the compact and the viewer.
- `status` prints the sync line only once a server is listed or something of the sync stands, so a store with no server prints what it printed before; `syncState` tells a lease held by a process that is gone (`dead-holder`); `doctor` warns on a restore hold too, so "doctor raises nothing after an ordinary restore" was tested on a restore with no server listed; `startSync` takes the mode, `--once` from the viewer's button skipping the failed-start backoff.
- `GET /api/sharing?server=`, `ProjectSummary.server`, and the viewer's `RouteError` with the route's one-word error for the page's sentences.
- Tests this part changed beyond AC-85's list: the MCP tools-list snapshot (knowledge_get's reference now names a teammate's `<server>:<slug>--<8 hex>`), the backup test's bare-copy case (the restored copy now gains the sharing tables), and the lease test's wake owner (`process.ppid`, a live process, since a lease counts only while its owner is alive).

## Known limits

Three write-lock holds are unmeasured on a large store: `share server remove` (every received memory, ledger row and copy of the server in one transaction), a first full sweep over many entries, and `backup --restore` (the live store under `BEGIN IMMEDIATE` while the copy is upgraded and the eight tables carried); `scripts/proof/upgrade-copy.ts` measures the first open alone and the 50 ms bar one pull chunk. While one runs, a hook that waits past its busy timeout fails open, so the cost is a session's lost context, never data; run `remove` and `--restore` outside a session. The contract pins no `accepted` in `RESULT_SHAPES.refusal` though the server sends it and the client reads it, and `RefusalShape.retryAfterSec` never reaches a body (the server moves it to `Retry-After`): the next contract bump pins the one and drops the other. The mute and the binding hide a teammate's copies from the knowledge reads, the brief and the prompt alone: a received memory is an ordinary `memories` row, which `memory_search` and the viewer read with no mute or binding check, and which the distillation's consolidation can send to the person's TypeSafe provider as a neighbour; a received memory is filed under any enabled project that holds its alias, with no check that the project is bound to the sending server (the entry path makes that check); the pull's answer is read as sent, with no shape check on its items and no size cap on its body, so a hostile or compromised server can exhaust the sync process's memory; `--code` on the command line puts the invitation code in the shell's history and in `ps`, where the no-echo prompt does not. A person who never resumes keeps a server's stale copies (D-10). An own entry the owner withdrew on the server from another device is sent again by the next sweep while the file stays and the policy allows it; only an admin's lock on the server stops that, as a refusal recorded for its hash. A rollback to a binary before this part leaves `sync --auto` running under the old inode until `wizardingcode-mem sync stop` or a kill, and reads knowledge's module version 8 as too new, so the knowledge module stays silent until the upgrade is put back; nothing is lost either way. `knowledge take` and the `write --pinned` refusal of a received reference are covered by the store's tests, not through the CLI. The dirty count is refreshed by full sweeps and by ticks that could send an entry; an uncommitted edit made while nothing else changes is counted within a minute. A slower one-time copy of the sharing v1 to v2 upgrade is a known limit noted at the delivery with its remedy (open the store once from a shell before the session). The viewer's add and the CLI's both use the real clock for the join; only the store's stops of the sync take the injected one.
