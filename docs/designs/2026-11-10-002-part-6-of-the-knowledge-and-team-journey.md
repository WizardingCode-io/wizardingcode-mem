# The sync client: servers, the policy per server, push and pull in the background (part 6)

Work item 2026-11-10-002. Predecessor: `concepts_brief.md` (the brainstorm's six reviews under `spec-review/`). The design records this builds on: ADR 0024 (the knowledge store), ADR 0025 (the sharing policy and the contract), ADR 0026 (the team server). This part's record is `docs/adr/0027-sync-client.md`. Revision 16; the history of the validation rounds and of the review rounds is in `conclave.md`.

## Terms

- **Server**: a team server of part 5, named on this machine by its `serverId` (minted by the server) and shown by its name (the server's, else the URL's host).
- **Listed server**: a server with a `sharing_servers` row on this machine, pending or confirmed.
- **Device**: this machine's identity on one server: a device id, an alias and a token the server minted at the join.
- **Destination**: ADR 0025's word for where an item may leave for. While no server is confirmed, the one destination is `team`, as in part 4; from the first confirmed server on, every destination is a `serverId`.
- **The policy of a server**: ADR 0025's `SharingPolicy` loaded for one server: the levels of this machine's projects for that server, and the effective roots and areas (the server's own lists, narrowed by the env file's lists and by the environment).
- **Bound**: a project is bound to a server when its stored level for that server is anything but Nothing (`receive` included; D-9).
- **Received item**: an entry or a memory that came from a server. A received entry is a byte-for-byte copy of the server's current revision, kept under `knowledge/received/<serverId>/` outside the person's repositories, with no version history; a received memory is an `imported` row with a provenance row. Items of this same member pushed from another device are received items too.
- **Own item**: an entry in one of the person's repositories or a memory of this store, whatever its origin otherwise. An own entry a teammate revised is still an own item; the revision is applied to the person's file.
- **The ledger**: ADR 0025's `sharing_ledger`, keyed by destination, item and direction, with this part's columns.
- **Sweep**: one pass of the outbound side over the items that changed since the last pass, for one server.
- **Snapshot**: a pull with `since=0` that lists the server's current items for the scopes and aliases this machine reads (ADR 0026).
- **The brief** and **the prompt floor**: what the engine puts into an agent's context, as ADR 0024 defines them: the brief is the session-start block, with its shares per module and the pinned entries; the prompt floor is the two entries at most that a prompt may bring in when they pass the lexical floor.
- **The sync process**: `wizardingcode-mem sync --auto`, one per data directory.
- **Loopback**: the literal host `localhost`, an address in `127.0.0.0/8`, or `::1`; nothing else.

## Problem

A person who joined a team server has their knowledge on their machine and the team's on the server, and nothing moves between them. Parts 4 and 5 built the policy that says what may leave and the server that holds what the team shares, but no client speaks the server's API: no item reaches a server and none arrives. Once this part works, a person's allowed entries and memories reach their team's server within seconds of a change, the team's reach them the same way, and the agents on every machine of the team read the same knowledge, each item marked with who wrote it and where it came from. The client must do this without a hook ever waiting on the network, without a byte leaving that the policy did not allow, without a teammate's text becoming this person's own work or steering their agents unmarked, and with every state of the sync readable from `status`, the viewer and the log (the list of states is in "Status, doctor and the log").

## Goals

- Join a server with an invitation code from the CLI and the viewer; keep several servers; see each server's state; re-join a server that stopped.
- Key the policy and the ledger by server; bind a project to one server at most; receive for the projects bound to a server, with a level that sends nothing (D-9).
- Send what the policy allows within 5 s of a committed change made through the store, the hooks or the tools while the sync runs (an edit made outside the store leaves once the person commits it, at the next sweep, within 60 s), and receive the team's changes within 5 s of theirs under the server's signal wake, within 10 s under its poll (the non-functional requirements state the bounds and what is measured).
- Keep received items under `knowledge/received/<serverId>/`, outside the person's repositories, read-only, erasable by a server's purge, marked for the agents, never pinned, capped in the brief and on the prompt floor; let the person take one into their own repository.
- Never lose text on a conflict; tell a server rollback from a conflict; never let a teammate's revision pin an entry or un-pin it.
- Survive restores on either side, contract skew, revoked devices and disabled members, rate limits, long offline periods and a laptop's sleep, with a stated state and remedy for each.
- Keep hooks off the network: the sync is its own process, started by the hooks and the viewer and left alone by them; the store's own operations (restore, move, compact) can stop it.

## Non-goals

- A Team view in the viewer, a conflict editor, or editing a received entry in place.
- A taxonomy sync (received entries are not parsed against the local taxonomy), a second contract version, certificate pinning, a review gate before received items are shown (the marker, the pin rule, the cap and the mute stand in for it; a gate stays possible since received items are kept apart).
- Changes to the server (`CONTRACT` 1 and its code), beyond its contract module exporting the answer shapes, the two header names, the request-id grammar, `entryBytes`, `isLoopback` and the two folder-naming functions.
- A per-server area editor in the viewer beyond the two lists; MCP tools beyond provenance in their results; the OpenCode bridge's tools beyond the same fields (they share the module's functions).
- Detecting a data directory copied whole to a second machine (a known limit, below).
- Part 7, the runbook: the admin's steps on a `rejoin`, `unauthorized` or `disabled` stop; revoking the device a removed machine left, or the device of a join whose answer was lost; `serve forget`; the token file's place in a machine's backup strategy and the copied-directory limit; the retention of received items and the fact that a machine's own backups keep received memories a later purge never reaches; the erasure of a member's name on the clients.

## Decisions

| Id | Decision |
| :- | :- |
| D-1 | The sync is its own detached process, `wizardingcode-mem sync --auto`, started by the session-start and prompt hooks and by the viewer, one per data directory by a lease, never on a hook path. |
| D-2 | On a stale push of an own entry, the server's revision is applied to the file; the local text is kept as a proposal and in a conflicts row, never lost, never sent until the person accepts it. |
| D-3 | The CLI and the viewer's Servers card both ship; the viewer's part is the scope stated under "The viewer": one Servers card, the Sharing card's server selector, the project dock's selector, and the listed routes. |
| D-4 | The first run after a server is added sends everything the policy allows, batched under the server's limits, resumable, shown by status. |
| D-5 | The team's project items arrive whenever there are changes, with no step beyond binding the project to the server; a level above `receive` is needed only to send. (Revised by D-9 for what a pull names.) |
| D-6 | Received items live apart under `knowledge/received/<serverId>/`, read-only, erasable, marked, never pinned; take to edit; received memories carry provenance, take at most a third of a brief's slots, and a server or a member can be muted. |
| D-7 | The device token lives in `<data dir>/servers.json` (0600) beside the env file, outside the database file and the backup; the server list, cursor and state live in the database. |
| D-8 | A conflict is a proposal by `sync:<serverId>` on behalf of the person, outside the quota, plus a `sharing_conflicts` row; the server's revision and instance, with the sent-hash history, tell a rollback from a conflict. |
| D-9 | What a pull names to a server: only the projects bound to that server (any stored level but Nothing, `receive` included), so no server learns the names of projects the person did not bind to it. The person chose this option on 2026-11-10 over the alternative (every local project not bound to another server), which is stated under Alternatives. |
| D-10 | A withdrawal the person did not ask for is held: after a restore (every level reset to Nothing), and when one sweep would withdraw, for reasons no action of the person explains (an entry gone from a present repository, a `system` removal of a level or an alias), more than 20 items or more than half of a server's sent rows. A withdrawal that follows the person's own narrowing (`setLevel`, `share roots`, `share areas`, the viewer), which showed its preview, is never held. `share server resume` shows what would be taken back, per project, and releases the hold on the person's yes, which authorises that set for the next sweep; nothing else releases it. A choice of this spec, stated as such in ADR 0027. |

## Critical user journeys

1. **Join.** Given a server's URL and an admin's invitation code, when the person runs `share server add https://team.example.com --code wci1_…` (or fills the viewer's Servers card), then the client joins, stores the device as pending, prints the server's name, the member's name and role, and the counts of what would leave under the levels already set, asks for a yes (or takes `--yes`), confirms the server and moves the `team` rows to it when it is the first, and starts the sync; nothing leaves before the yes, whatever the hooks start meanwhile.
2. **A change leaves.** Given a project at Knowledge bound to the server, when the person (or their agent, once accepted) writes an entry, then within 5 s the sync sends it, the server answers `applied`, the ledger records the sent row, and `share explain --server` shows why it left.
3. **A change arrives.** Given a teammate's entry applied on the server, when this machine's sync holds its pull, then within 5 s the entry is written under `knowledge/received/<serverId>/`, indexed, and the next `knowledge_search` returns it marked `from <member> via <server>`; it is never pinned.
4. **A conflict.** Given the person edited an entry a teammate also changed, when the push answers `stale`, then the file takes the server's revision in a commit naming the member and the revision, the person's text becomes a proposal by `sync:<server>` on their behalf (and a conflicts row), and `status`, the viewer and the next session start say so; accepting the proposal sends their text over the teammate's.
5. **A second server.** Given a second server for another client's projects, when the person adds it, then it starts with every level Nothing and its own roots and areas; a project bound to the first server cannot be bound to the second; `share status` and the viewer show both; the second server never learns the first client's project names.
6. **Trouble.** Given a revoked device, a disabled member, a server restored from an old copy, a server upgraded to a contract this client does not speak, or a week offline, when the sync next runs, then it stops or recovers as the rules below say, and `status` names the state and the remedy; a stopped server is re-joined with a new code without losing the ledger.
7. **Leaving.** Given a server the person no longer uses, when they run `share server remove`, then the sync is stopped first, the server's received files, rows and memories are deleted, its levels and ledger rows go, the token is forgotten, and, with `--withdraw` while online, what this machine sent is withdrawn first.
8. **A restore.** Given a store restored from a backup while the sync runs, when `backup --restore` runs, then it stops the sync, carries the server list and the ledger into the copy before putting it in place, holds the withdrawals, and the sync's next start re-indexes the received folder; once the person has set their levels again, `share server resume` shows what the withdrawal sweep would take back and releases the hold on their yes (D-10).
9. **A second machine.** Given the same member joined from another machine, when their first machine's workspace entries reach the server, then the second machine receives them as read-only copies marked `from <their name> (another device) via <server>`, never as own items; `knowledge take` makes one their own on the second machine too; the projects they want to receive on the second machine are bound once there (D-9).

### The server list and the token (D-7)

`sharing_servers` (sharing v2): `server_id` (primary key), `url` (origin only, `https://` required unless the host is loopback), `name`, `device_id`, `device_alias`, `member_id`, `member_name`, `role`, `contract`, `instance`, `confirmed_at` (null while pending: the sweep, the pull and the spawn skip the row), `cursors` (JSON: `main`, the cursor of the main pull, and `extra`, one cursor per alias past the hundredth), `roots`, `areas` (the server's own lists, comma-joined, validated as ADR 0025 validates the env lists), `muted`, `stopped` (null, `contract`, `unauthorized`, `rejoin`, `disabled`), `snapshot_due`, `last_sweep_at`, `last_sweep_max_id`, `last_sweep_epoch`, `last_sweep_generation`, `added_at`, `last_push_at`, `last_push_ok_at`, `last_pull_at`, `last_pull_ok_at`, `backlog`, `retry_at`, `failures`, `last_error`, `last_error_at`, `last_request_id`. `sharing_muted_members(server_id, member_id)`. `sharing_pending_rows(server_id, seq, uid, kind, payload, reason, tries, at)`: the rows set aside after ten failed applies, with the feed row's JSON so a retry needs no server. `sharing_unbound(server_id, alias, at)`: the aliases the person unbound, waiting for the reconcile. `sharing_received_memories` keeps, beside the member and the hash, the remote kind, importance and status as the server sent them.

`<data dir>/servers.json`, mode 0600 from its creation (`writeFileAtomic`: a 0600 temporary file, then a rename), `{ "version": 1, "tokens": { "<serverId>": "wcm1_…" } }`; read by the sync process, the CLI and the viewer's process, and written only by `add`, `rejoin` and `remove` from the CLI and the viewer, each reading, changing and writing it inside `withWrite` (the store's write lock, which spans processes), so two writers never interleave; never logged (`team-token` redaction holds); never returned by any route (`GET /api/servers`, `GET /api/sync`, the answers of `POST /api/servers`) or any output (`share server list`, `status --json`); not inside the database file, so `backup` never copies it. It sits in the data directory beside the env file (`dataDir`, while the database may live in `storeDir`, ADR 0010: the client keeps both), so a data directory copied whole to a second machine carries the token: a known limit (ADR 0027), since ADR 0025 already names a copied store as one; the remedy is `share server rejoin` on one of the two machines, which gives it a new device.

### Joining, re-joining, leaving and resuming

`share server add <url> [--code <code>] [--label <label>] [--name <person's name>] [--yes] [--no-sync]`: the URL is checked (`https://` or loopback as the Terms define it, origin only, no path, no credentials); the code is prompted for on a terminal when absent (`askSecret`, never echoed), refused when absent elsewhere; `POST /v1/join` with the label (the hostname by default) and, for a bootstrap code, the person's name from the settings; a `serverId` already listed and confirmed is refused ("already joined; `share server rejoin` to replace the device"); the token goes to the file first, then the row with `confirmed_at` null, in that order (a crash leaves a token for a pending row, which `doctor` reports and a re-run of `add` replaces). A join whose answer is lost (a network error after the server minted the device) leaves a device on the server and no token here: invitation codes are single-use (ADR 0026 D-4), so the remedy is a new code from an admin and `add` again; the orphan device is the admin's to revoke (part 7). Then `GET /v1/me` reads the limits and the server's name. Then the would-leave counts for this server are computed (`wouldLeave` with this server's policy over the `team` rows when it is the first server, else over its own) and printed; on a terminal the person is asked (`askYesNo`), elsewhere `--yes` is required. The yes is one transaction, `confirmServer(db, dataDir, env, serverId, now)`, which writes: `confirmed_at`; a `sharing_changes` row `server:<id>` with `old` `''` and `new` the host; when this is the first confirmed server, every `sharing_levels` and `sharing_ledger` row of destination `team` moved to this `serverId`, the env file's roots and areas copied into the server's lists, and the baseline (`sharing.settings_seen`) re-set so the move is not read as a hand edit (ADR 0025 D-13 holds: the env file stays the ceiling); `sharing_changes` rows are not moved (the history stays as written; from this part the `what` of a per-server change is `project:<id>@<serverId>`, `roots@<serverId>` or `areas@<serverId>`). A no leaves the row pending: `status` says `not confirmed: share server add again`, nothing is swept or pulled for it. The command ends by starting the sync (`spawn.ts`), unless `--no-sync`. A sync running between the join and the yes sends nothing for the pending server: it reads only confirmed rows, and the `team` rows are not its destination once a server is confirmed.

`share server rejoin <server> [--code <code>] [--yes]`: for a listed server (stopped or not), `POST /v1/join` with a new code; the token and the device columns are replaced, `stopped` cleared, `snapshot_due` set; the ledger, the levels and the received items stay (ADR 0026 lets another device of the member withdraw its items, and the server scopes memory uids by device: the old device's memory uids are withdrawn by the next sweep, from the ledger, and re-sent under the new device). `share server add` of a listed, stopped server does the same as `rejoin`.

A server is named to a command by id, name or host (`findServer`); a reference that matches more than one server (two servers with one name or host, or a name equal to another's host) is refused with the ids listed ("name two servers; use the id"). `share server list`: one line per server (name, host, member and role, contract, the cursors' sum, the state line of "Status, doctor and the log"). `share server remove <server> [--withdraw] [--yes]`: the removal stops the sync through the one stop flag (`stopSync`: the flag set, the lease waited for up to 30 s, else the refusal "the sync is running; run `sync stop` first"), does its work, clears the flag, and the next spawn restarts the sync; with `--withdraw` it first pushes a `withdraw` for every not-withdrawn sent row, a `stale` withdraw retried once on the server's `current` base (the person's intent is explicit), and a second failure refuses the removal naming the count left (the token is still valid, since removal happens before the forget); then, in one transaction, deletes the received rows and memories of that server (`deleteServerReceived`, below), its levels (`removeServerLevels`), ledger rows, refusals, conflicts (open conflicts are printed first and refuse without `--yes`), sent hashes, mutes, pending rows, unbound rows, its hold key, its authorised list and its row, and writes the `sharing_changes` row `server:<id>` with `new` `''` (`logServerChange`); then deletes `knowledge/received/<serverId>/` and the token (a crash between the transaction and the folder's deletion leaves a folder with no row, which the sync's start deletes). The output says that the device stays listed on the server until an admin revokes it. `share server mute|unmute <server> [--member <id>]` writes `sharing_changes` rows `server:<id>` with `mute`/`unmute` through `logServerChange`.

`share server resume [<server>] [--yes]` (D-10): releases a server's withdrawal hold, or every server's with one argument less; it prints, per project, the sent items the withdrawal sweep would take back from the server under the levels now set (every not-withdrawn `sent` row whose item no longer decides `send`), asks for a yes (`--yes` elsewhere), clears the hold (`meta` `sharing.restore_hold:<serverId>`, whatever set it: a restore or a bulk withdrawal), records the uids it showed as authorised (`meta` `sharing.resume_authorised:<serverId>`) and starts the sync; the withdrawal sweeps that follow withdraw those uids with the guard suspended for them, each uid removed from the list as its withdrawal is answered (so a sweep interrupted by `rate`, a failure or a lost lease keeps the rest authorised), and the key is deleted when the list is empty; the hold does not return for the set the person saw, and later sweeps are guarded again. Nothing else clears a hold; `share server remove` deletes the server's authorised list with its hold key, and the restore clears every `sharing.resume_authorised:*` key of the copy with the hold keys.

### The policy per server

`loadPolicy(db, dataDir, env, serverId?)`:

- Its `destinations` are the confirmed servers' ids (`destinationsOf`), or `{ team }` (the kept default `DESTINATIONS`) while none is confirmed, so part 4's suites pass unchanged and `policyWith` keeps its default.
- With a server, the effective roots and areas are the intersection of the server's lists, the env file's lists (the person's ceiling, hand-editable as today) and the environment's (narrow-only, as ADR 0025 D-13); the epoch is `counter × 2^20 + hash20(effective roots | effective areas)` of that server.
- The counter is global: a change to one server's lists moves every server's epoch, which stops their sweeps, and the next sweep of every server then re-checks every memory (bounded by the batch limits) and re-sends no entry whose hash is unchanged.
- Without a `serverId` while servers are confirmed, it returns the policy of the first confirmed server by name; it takes no project, so every caller that reads a project's level (`src/ui/api.ts`, `status`, `doctor`, `previewLevel`) passes the project's bound server (`boundServerOf`). Every new destination or server parameter of `report.ts`, `in-force.ts` and `policy.ts` is optional and defaults to the project's bound server, else `team`, so the preserved suites keep their calls.
- `decide` does not change: the `decide` cases of `tests/unit/sharing-policy.test.ts` and the `DECISION_KEYS` block of `tests/unit/sharing-contract.test.ts` stay as they are.
- `ledgerRecords` hands `decide`, `wouldLeave` and `explain` the `local_hash` as the record's `hash` for an entry row (the index hash of the file as it was when sent or applied; an empty `local_hash` falls back to `hash`, so the preserved tests keep their records), so a redacted entry reads `already-sent`, and the server's hash of the redacted bytes is the ledger's `hash` column for the push's base; for a memory row it hands a non-empty `local_hash` the same way (the memory `stale` rule, below). The three new `LedgerRecord` fields are optional and left out of a record when empty.
- The `direction` union of `LedgerRecord` gains `applied` (the row of a teammate's revision applied to an own item): `ledgerRecords` selects an `applied` row only for its own destination (its `OR direction = 'received'` clause does not widen to it), `decide` never reads it, and the row is cleared with the `sent` row (the snapshot's clearing, `purged`, `remove`).
- `policyInForce`, `wouldLeave`, `entryItems`, `memoryItems`, `ledgerRecords`, `withChange` and `explain` take the destination.

The level `receive` (D-9):

- A stored level between `local` and `knowledge` (`LEVELS` is `local, receive, knowledge, all`; `LEVEL_LABELS` gains "Receive only"): it binds the project to the server (the partial index below counts it) and sends nothing.
- `decide` and `levelRefusal` do not change: `effectiveLevel` returns `{ level: "local", reason: "level-receive" }` for a row at `receive` that is otherwise in force (the project known and enabled, the bound alias still the project's), so the policy's `levels` map never holds `receive`, `levelOf` returns what `effectiveLevel` gave, and `levelRefusal` returns the new reason through its existing last line; `REASONS` gains `level-receive` (`REASON_TEXT`: "The project receives from this server and sends nothing."), which changes the REASONS block of `tests/unit/sharing-contract.test.ts` and nothing of its `DECISION_KEYS` block or of `decide`'s cases.
- `widens` ranks by what leaves (`local` and `receive` rank 0, `knowledge` 1, `all` 2), so Nothing to `receive` is not a widening and needs no `confirm`, and `receive` to Knowledge is one.
- `setLevel` that sets a project bound to a server to Nothing writes, in its transaction, a `sharing_unbound` row (server, alias, at), unless another enabled project is still bound to that server under the same alias (two clones of one repository share an alias, and a pull names aliases); one that binds a project removes that row; a restore's `resetLevels` writes none, and neither does a `system` removal by `reconcileLevels` (memory off, a lost alias), whose received copies stay on disk, hidden from every read (below), until the server is removed, which ADR 0027 states. `setLevel` clears no hold (D-10).
- `setLevel` reads the stored row for its idempotence and its change log (a stored `receive` row set to `receive` again changes nothing; `receive` to Nothing removes the row and logs `receive` to `local`), since `effectiveLevel` reads the row as `local` for `decide`.
- `setLevel` refuses a level other than `local` when another server binds the project (`one-server`, after `unknown-destination` and before `needs-confirm` in its order of refusals; `SET_LEVEL_MESSAGES` gains "this project is bound to <server>; set it to Nothing there first"), and a unique partial index `sharing_levels_one_server ON sharing_levels(project_id) WHERE level != 'local' AND destination != 'team'` (the pre-server `team` row is not a server, and may stand beside an unknown destination's row until `reconcileLevels` removes it) holds it in the schema (an older binary's `setLevel` for such a project fails on the index with SQLite's constraint error, a known limit of the downgrade); its "not configured" check reads `destinationsOf` (confirmed servers only).
- `share project | roots | areas | explain | status` take `--server <server>`, which defaults to the only confirmed server and is required with several (a pending server is never the default and is refused as `not confirmed` when named); `share roots | areas` without a server edit the env file's lists (the ceiling) as today; `share project <p> receive --server <s>` binds without sending.
- `reconcileLevels` keeps `team` rows while no server is confirmed; once one is, a `team` row (written by an older binary) is removed with a logged `system` change, and so is a row of a destination that is not a confirmed server (this reverses ADR 0025's "may be a newer version's" rule; the amendment records it).

### The sync process (D-1)

`sync --auto` claims `sync.lease` in the client store's `meta` (owner `sync-<pid>-<version>`, 60 s, renewed every 20 s, including while a pull is held, through the client's own timer); `anyLeaseActive` includes it. The lease's rules:

1. `ownerAlive` learns the `sync-<pid>-<version>` pattern and reads its pid, so a crashed owner's lease is taken over. Across a laptop's sleep the 60 s lease expires while the pid stays alive; a spawn on wake may then take the lease, and the old holder sees its lease lost at its next renewal and exits after the current page or batch without another write (rule 3): the expected and safe path, so no two holders ever both write.
2. A newer binary takes over a live lease whose owner carries a lower version (`takeOverLease` in `meta.ts`: the `<version>` parts compared by `Bun.semver.order`, the running version the one `package.json` gives the CLI); the holder sees its lease lost at its next renewal and exits 1 after the current page or batch.
3. Every write of a cursor, a state row, a ledger row or a received file by the loop runs in a transaction that first checks the lease is still its own (`leaseOwned`, a compare on the owner); a process that lost the lease writes nothing more and exits; a cursor never moves backwards (a save keeps the larger of the stored and the new value).
4. A second `--auto` while the lease is live exits 0 at once.

The process runs one loop per confirmed server concurrently (a failure in one never stops another), plus a tick every two seconds that reads `PRAGMA data_version`, which moves only when another connection commits, so the sync's own writes never start a sweep: a change by another connection runs a sweep for every server at the next tick, provided five seconds passed since the previous tick sweep ended, over the rows that changed (the outbound side): from a quiet state a change leaves at the next tick, within 5 s, and a burst of changes is coalesced into one sweep every five seconds, so a change made during a burst leaves within 10 s; a full sweep runs at least every sixty seconds. It exits after fifteen minutes with no hook run (`hook_runs.at`), no live viewer (`readUiState` and `probeUi`) and no backlog; on SIGTERM or SIGINT after the current page or batch; and within five seconds of the stop flag. Exit codes: 0 on the idle exit, on a signal and on `--once` with every server ok; 1 on `--once` with a stopped server or a failed batch; 2 on `--once` refused while `--auto` holds the lease; 3 on a failed start.

The stop flag: `meta` `sync.stop` (a value naming who set it and when). `sync stop` sets it, waits for the lease's release (at most 30 s) and clears it; `backup --restore`, a store move, `compact` and `share server remove` set it themselves, wait the same way, run, and clear it at their end (the three store operations used to refuse with `busy` on any lease; for the sync lease they stop it instead, and refuse with their own busy error when it does not stop within 30 s); the hooks and the viewer do not spawn the sync while the flag is set; a flag older than ten minutes is stale and cleared by the next spawn. `sync --once` runs the start's steps (below), even with no server listed, then one sweep and one pull per server (no `wait`) and exits as stated; it refuses while `--auto` holds the lease (`sync is running`). `WIZARDINGCODE_MEM_SYNC=off` makes `--auto` exit 0 at once and the spawn a no-op (the tests' switch, beside `DISTILL` and `UI_AUTO_OPEN`).

The start's steps, in order, before any sweep or pull: `deleteServerReceived` for every server id that has received rows, or a `knowledge/received/<serverId>/` folder, but no `sharing_servers` row (the folder looked at through `lookAt`, `kindAt` and `namesIn`, so a link or an unreadable folder is a refusal, never a deletion); `reindexReceived` over the listed servers' folders (the folder is the truth for received entries); the close of conflicts rows whose proposal is no longer open.

The hooks: on `session-start` (any source) and on `prompt`, `spawn.ts`'s `startSync` runs one statement over `sharing_servers` and `meta` (the count of confirmed, not stopped servers, the lease, the stop flag and the failed-start mark in one `SELECT`; skipped, with no spawn, on a store without the sharing schema, which `sqlite_master` tells once), one `process.kill(pid, 0)` for the lease's pid, and spawns `sync --auto` detached when there is a server, no live lease, no flag and no young failed-start mark; a failure of any step fails open (no spawn, exit 0); none of the viewer's guards (CI, SSH, display) apply; the snapshots of the hook outputs do not change. A start that fails before the loop (`openDb` refused, a token missing for a confirmed row) writes `meta` `sync.last_failed_start` (time, reason) and exits 3; the spawn skips while the mark is younger than five minutes, then ten, then an hour (the backoff doubles per failure, capped), a start that reaches the loop clears it, and `status` and `doctor` show the reason. The viewer calls the same function at its start and on `POST /api/sync/run` (which spawns `sync --once` when `--auto` is not running).

### The outbound side (the sweep)

For a confirmed server that is not stopped: re-read the policy (`policyInForce`, which reconciles), and stop the sweep at the first batch whose epoch differs from the one it started with. The sweep reads committed text only: the store, the hooks and the tools commit what they write; an edit made outside the store (an editor, a git operation) leaves once the person commits it, or adopts it with `knowledge adopt`, and a dirty path is skipped and counted (`status` shows the count as `dirty`). At the sixty-second mark the sweep first runs `ensureFresh` over the repositories bound to the server, at most three per sweep as `refreshStale` of `src/modules/knowledge/index-store.ts` bounds the drain, so a committed edit made outside the store is seen within a minute; the tick's sweep (at most once per five seconds) reads only the rows that changed: entries whose index row changed since the previous read's start, and memories by the rule below; the withdrawal sweep and the full comparison of entries run only at the sixty-second mark.

Candidates: own entries from `entryItems` whose index hash differs from the ledger's `local_hash` or that have no record; memories from `memoryItems` with `updated_at` at or after the previous read's start (`last_sweep_at` is the time a read started, not ended) or with an id above the highest id the previous read saw (`last_sweep_max_id`, so a row inserted with a past `updated_at` is seen once), or every memory when `last_sweep_epoch` or `last_sweep_generation` differs from the policy's epoch or the store's generation (a widening or a restore); every not-withdrawn `sent` row whose item is gone or no longer decides `send` under its uid (the withdrawal sweep, from the ledger's uids, ADR 0025), with two guards: an entry whose repository is missing, refused or unindexed is never withdrawn (only a deletion inside a present, readable repository withdraws), and, among the withdrawals no action of the person explains (an entry gone from a present repository, a project whose level or alias a `system` change removed; a withdrawal that follows the person's own narrowing, logged in `sharing_changes` with the source `cli` or `viewer` after the sent row, is never held), a sweep that would withdraw more than 20 items or more than half of a server's sent rows holds them under D-10 (the hold key set with the reason `bulk`, `status` naming the count and the remedy `share server resume`); the uids a `resume` authorised are withdrawn by the next sweep with the guard suspended for them; while a hold is set, that server's withdrawal sweep withdraws only what the person's own narrowing explains. Items with a refusal row for their (uid, hash), or a purged row for their uid, are skipped. `decide(policy, serverId, item, records)` rules each; the sweep records `last_sweep_at`, `last_sweep_max_id`, `last_sweep_epoch` and `last_sweep_generation` at its end.

A `send`: an entry's text is read after `ensureFresh` and a clean `git status` for its path; the payload is an `OutgoingEntry` with `frontmatter` and `body` split at the end of the frontmatter block, the `pinned` line removed from the frontmatter (pins never leave), both through `redactForSend`, `hash` recomputed over the redacted bytes as the server does (`entryBytes` of `src/team/contract.ts`), and `localHash` the index's; a memory's payload is an `OutgoingMemory` through `redactForSend` and `memoryHash`. The base: the ledger's `sent` revision (the `version` column) and hash for the uid, the newest revision this machine knows for that server, since an apply of a teammate's revision to an own file moves the `sent` row to the server's revision and hash (the inbound side, below), so the person's next edit never pushes on a stale base; a move (an own entry whose uuid has a sent row under another uid for this server) sends the new uid with that row's base, and on `applied` the old row is retired (`withdrawn_at` set, `reason` `moved`, no withdraw sent). A withdraw is a push item of kind `withdraw` (the client has no other route for it). Batches: at most 200 items and 900 KiB measured on the serialized request body (under the server's 1 MiB cap, ADR 0026 D-15); a 413 all the same splits the batch in two and retries; a single item whose serialized size is over the per-item limit `/v1/me` publishes (256 KiB, D-15), measured as the server measures it, is refused locally (`too-large`, recorded as a refusal row and never retried for that hash); live changes (changed since the last sweep) before the backlog (the first run and anything older); the backlog figure is the count left.

Answers: `applied` writes the `sent` row (destination, uid, direction, the server's revision in `version`, its hash, `local_hash`, `instance`, `policy_epoch`, `reason`) and a `sharing_sent_hashes` row (the last eight per uid kept); `stale` with `appliedAs` is recorded as sent at that revision; `stale` on an entry is a rollback or a conflict by the server's revision and instance: a `current` whose revision is below the ledger's sent revision, or whose instance differs from the row's, is a server rollback, and the item is re-sent on `current` in the next batch; a `current` with a higher revision is a teammate's revision, applied or made a conflict as the inbound side says, even when its hash is in the sent history (a teammate's revert to a text this machine once sent is their revision, not a rollback); `stale` on a memory means the server holds a later `updatedAt` for the uid (another generation of this device after a restore, or clock skew): the server's copy is recorded as sent (the `sent` row takes the server's revision and hash, and its `local_hash` the local `memoryHash` at the time of the `stale`), and the sweep skips the uid while the memory's current `memoryHash` equals that `local_hash`, so the next sweep sends nothing and a later local change (a new `memoryHash`) is sent; `refused` writes a refusal row (reason, rule) and is never re-sent for that hash; `purged` also sets a purged row for the uid and clears its ledger rows; `rate` ends the batch and schedules the next after `max(5 s, bytes / (64 MiB per hour, the server's applied-payload limit of D-15, as bytes per second))`; `storage` schedules the next sweep in ten minutes; `withdrawn` sets `withdrawn_at`. Every answer updates the server's state row.

### The inbound side (the pull)

What a pull names (D-9), as the server answers it (`scope=all` with up to 100 aliases returns the shared scope, every member's workspace and those projects; `scope=project` returns one alias; ADR 0026):

1. The main pull: `scope=all` with the `remote:` aliases of this machine's enabled projects bound to that server, up to 100 of them, the main set, stored with its cursor (`cursors.main`, `cursors.mainAliases`); held with `wait=25`. One held pull per server, which stays under the server's cap of 8 held pulls per device. Membership is sticky: `mainAliases` holds only aliases the pull names (an enabled project's, bound to the server), and an alias in the main set stays there whatever its level becomes, until it stops being named: unbound by the person, its project disabled, its alias lost, or its level removed by `reconcileLevels`, at which point the next pull removes it from `mainAliases` (the main cursor stands); an alias named anew (a new bind, a re-enabled project, a regained alias) follows the new-alias path below: the first free slot, else an extra alias, then a one-alias snapshot, so no row written meanwhile is skipped.
2. An extra alias is pulled with `scope=project`, one alias and one cursor each (`cursors.extra`), without `wait`, in rotation at the sixty-second mark, so a person may bind more than 100 projects to one server at that cost (an extra alias's changes arrive within a minute, not within 5 s). The extras are ordered by their alias bytes, which is also the tie-break when a free slot is filled from them.
3. A newly bound alias joins the main set first (so the main pull catches its new rows from then on) and then gets a one-alias snapshot (`scope=project`, `since=0`, every page until `more` is false) for its older rows; a row of the alias written during that snapshot arrives through the main pull too, and the apply is idempotent. The main cursor stands.
4. An unbound alias leaves the main set; the main cursor stands; the first extra alias by its bytes is promoted into the free slot and gets the same one-alias snapshot. No alias is ever demoted from the main set, so no rows are skipped.

What runs before a pull's first page, the reconcile of unbound aliases (`reconcileReceived`):

1. For each alias `sharing_unbound` lists for the server, the row is re-checked: when an enabled project is bound to that server under the alias again, the row is dropped and nothing is deleted (a re-bind before the reconcile keeps the copies, which the alias's snapshot refreshes).
2. Otherwise, per alias, the files are deleted first, then, in one transaction, the `knowledge_received` rows, their search rows, the received memories (`deleteReceivedMemory`, with the `superseded_by` rule below), their provenance rows and the `sharing_unbound` row.
3. A crash between the two steps leaves rows without files, which the sync's start drops (`reindexReceived` drops a row whose file is gone), and received memories without files, which the next reconcile removes, since the `sharing_unbound` row waits until the transaction completes; an unbind made while the sync was stopped waits the same way.
4. A reconcile that fails (a refused folder, a locked row) holds that pull's first page and is retried at the next pull. Until the reconcile, the rows of an unbound alias are hidden from every read (the received section), not deleted.
5. A restore unbinds nothing (`resetLevels` writes no `sharing_unbound` row), so the received project copies survive it, hidden until the project is bound again, when the pull names them again.

The request: with `snapshot_due`, a snapshot per cursor, the main cursor and each extra alias in turn (`since=0`, every page until `more` is false, each compared after its last page over its own request's scopes and aliases only); the flag clears only after every cursor's snapshot completed, and a cut one restarts from the first uncompleted cursor with the flag still set; else `since=<cursor>&wait=25` on the main cursor (and `since=<cursor>` with no wait on an extra alias), with a client deadline of 35 s, `redirect: "error"` on every request (a 3xx is a failure), a request id of the server's grammar (`REQUEST_ID_RE` of `contract.ts`) sent in `x-request-id` and recorded. The page is applied in chunks of at most 50 rows, each in one transaction held for at most 50 ms (file writes, and the vectors of received memories, happen outside the transaction: a file before its row, a vector after its row through `healVectors`' path; the dedupe below looks up an in-memory map of the project's memory hashes, built once per page outside the transaction and updated as the page inserts, so no hashing runs inside a chunk), the cursor saved after the page; a page is idempotent (a row already applied by hash is skipped), so a crash re-applies the page. For each row:

- entry `upsert` for a uid this machine sent and still holds as its own: the server's hash equal to the ledger's is an echo and is skipped; another hash is a teammate's revision of this person's entry: applied to the own file verbatim (the server's `frontmatter + body`, with the local file's `pinned` line kept as it was, so a teammate can neither pin nor un-pin) by the sync writer through the store's `applyRevision` (`commitChange` under `withRepoLeases`, which throws `locked`; never `writeEntry`), the ledger row of direction `applied` written with the server's hash and `local_hash` the new file's hash, the `sent` row's revision, hash and `local_hash` moved to the same (so the person's next edit is pushed on the teammate's revision, never on a stale base that would read as a false conflict), and, when the file's hash before the apply differed from the ledger's `local_hash` (a local edit in flight), the conflict path. Until the person edits the entry again, the agents' results carry `revised by <member> via <server>` for it (a derived state, not a stored one: an `applied` ledger row whose `local_hash` equals the entry's current index hash, read by the knowledge module's own SQL, so a `knowledge rebuild` loses nothing); when the entry was pinned, its pin is held by the same rule: the entry leaves the brief's pinned block and shows on the floor marked `revised by <member> via <server> (pin held)` until the person edits it or pins it again, so a teammate's text never enters the brief under the person's pin. Every other entry `upsert`, items of this same member from another device included: written under `knowledge/received/<serverId>/<folder>/entries/<slug>--<8 hex of the uuid>.md` with `frontmatter + body` verbatim (so `hashOf` equals the server's), where `<folder>` is `shared`, `members/<member id>` (the client's own naming, by id alone, so a renamed or erased member moves no folder) or `projects/<slug of the alias>-<8 hex of its hash>` (`repoFolder` of `src/team/contract.ts`, the server's own function; `fileNameFor` names the file), then its `knowledge_received` row and search row, and the `received` ledger row, in one transaction (the file first). A server purge of a member's items reaches the received copies, and their name in received files is deleted with the copies.
- entry `tombstone`: applied to the (scope, alias) of its uid: when the uid is a received copy, the copy and its rows are deleted (a withdraw) or, with `movedTo` naming a range this machine reads, left for the `upsert` that follows in the same page; for an own entry whose sent row exists, the row gets `withdrawn_at` with reason `withdrawn-by-admin` (the server withdrew its copy; the file stays). entry `purge`: a received copy is deleted with its rows; an own entry gets a purged row and stays.
- memory `upsert` from another device: a row whose `(title, body)` hash equals an existing memory's of the project (the in-memory map) is not inserted (the dedupe of copied stores, ADR 0026), its `received` ledger row written all the same; a later revision of a deduped uid is matched by that ledger row and deduped again when its content still equals a memory of the project, else inserted; else a new `imported` row (`judge` `team:<serverId>`, `judge_version` `1`, the kind mapped to the client's set (an unknown kind to `discovery`), the importance rounded to the nearest integer and clamped to 1 to 5, a status outside `active`, `superseded` and `archived` mapped to `active`, the remote values kept in the provenance row; the project the enabled project with the alias and the lowest id when two share it; `insertMemory` without the model inside the transaction, the vector healed after) with a `sharing_received_memories` row (server, remote uid, member, revision, hash, the remote kind, importance and status) and the `received` ledger row whose `item_uid` is the feed's uid as the server shows it, `remote:<device alias>:<uid>`; a known remote uid updates the row. From this device: an echo, skipped. memory `tombstone` and `purge`: the received row is deleted through `deleteReceivedMemory` (`src/store/memories.ts`), which clears every table keyed by memory id (`sharing_received_memories`, the ledger row; `memory_vectors` through its cascade) after every memory whose `superseded_by` pointed at it is set back to `superseded_by` null and status `active`, so a row id SQLite reuses inherits nothing: a received memory is a copy, the one exception to "memories are never deleted", stated in ADR 0027.
- A row whose target is dirty or locked is retried on the next pull: the cursor stops at the row's `seq`; after ten tries the row is written to `sharing_pending_rows` with its payload, shown in status, and the cursor goes on; a pending row is re-applied from its payload once an hour and dropped by a later row of the same uid.

Instance and errors: a page whose `instance` differs from the row's sets `snapshot_due` and deletes the server's pending rows (their `seq` values belong to the old instance; the snapshot re-derives them); a snapshot's comparison runs after its last page over the scopes and aliases it named: every `received` row absent from it is dropped with its copy (only received ones); every `sent` row absent from it is cleared, with its `applied` row, so the item is re-sent on base 0; present with a hash in the sent history is left; present with another hash is a teammate's revision, applied as above (a conflict only when the file's hash differs from `local_hash`); present as a tombstone sets the sent row's `withdrawn_at` with reason `withdrawn-by-admin`. 410 sets `snapshot_due`. 401 with the row's instance stops the server (`unauthorized`: "this device was revoked; ask an admin for a code, then `share server rejoin`"); 401 with another instance stops it (`rejoin`: "the server was rebuilt; ask an admin for a code, then `share server rejoin`"); 403 `member disabled` stops it (`disabled`: "the member was disabled; ask an admin"); 409 stops it (`contract`: "this client speaks 1, the server accepts <list>; upgrade wizardingcode-mem"). 429 waits `Retry-After`; 5xx and network errors back off with jitter, the interval doubling from 2 s up to 10 min; an empty page that came back in under a second with `wait` set means the server already holds its cap of held pulls for this device, or closed the held pull because its instance changed, and backs off the same way; three consecutive failures open a breaker that keeps the interval at its current value and doubles it on each further failure, up to the cap, until a success resets it to 2 s (the state on the server's row: `failures`, `retry_at`).

### Received items for the agents (D-6)

`knowledge_received` (knowledge v8) holds one row per received entry (server, uid, scope, alias, project, member id and name, the parsed fields, body, hash, revision, received at, the search row id). Received rows are searchable through `knowledge_fts` with `repo_id` 0 (`RECEIVED_REPO_ID`, stated once in `index-store.ts`) and `entry_id` `<serverId>|<uid>`, which is also a received hit's `id`, so `knowledge_shown` rows and the already-shown filter key on it; `rebuildAll` keeps the search rows `knowledge_received.fts_rowid` points at, and `compact` keeps the `knowledge_shown` rows of `repo_id` 0 whose entry id names a received row. What the reads return, by the module's own SQL over the sharing tables named under "Where things live":

- `searchEntries`, `browseEntries`, the prompt floor and `knowledge_get` read received rows beside the local rows for the project (the callers pass the project; the index reads its binding): the project items under the alias the project's level binds it with, and every listed server's shared and workspace items; only for listed servers (a `sharing_servers` row), only under the alias bound to that server (a `sharing_levels` row above Nothing whose `bound_alias` is the item's alias and still one of the project's, so the copies of any other alias, which no pull refreshes, never reach an agent), and never for a muted server or member; `received: { server, member }` on each hit. A project with no repository of its own still gets received hits (`contribute` returns null only when nothing at all is visible).
- The prompt floor shows at most one received entry among its two per prompt, and the brief's pinned block shows none (received entries are never pinned); `knowledge_shown` rows are written for them as for any shown entry.
- `knowledge_get` reads one by `<server>:<slug>--<8 hex>` (the file's name), where `<server>` is the server's name, else its id (resolved by `serverByName` in `index-store.ts`, never in `tools.ts`); a name two servers share, or one that holds a colon, is refused with the ids listed.
- Every result carries the provenance, which the tools render as `from <member name> via <server name>`, or `from <member name> (another device) via <server name>` for this member's own items from another device; every rendering of a member's or a server's name for an agent (this one, `revised by <member> via <server>` and `(team: <server name>)`) goes through `agentName`.
- `pinnedEntries` never reads them and leaves out an own entry whose pin is held (the `applied`-row rule, read in `index-store.ts`), so the brief's pinned block needs no read of its own; `knowledge write --pinned` on a received reference is refused (there is no separate pin command); `doctor`'s search-table check counts them in `active`.
- The session-start line of the knowledge module counts the open conflicts (the module's own SQL over `sharing_conflicts`) and is rendered even when no pin is shown.

The received tree is under the store's own guards: `knowledge/received/` and each `knowledge/received/<serverId>/` are refused when linked (`refuseLinkedRootsAt`), every path is followed through real folders only (`reachedByFolders`), presence is decided with `lookAt`, `kindAt` and `namesIn` (a look that fails is a refusal, never "not there", so `reindexReceived` drops no row for a folder it cannot read and `remove` follows no link), and every path component the server supplies is checked before it is used: the `serverId` and the member id against the server's hex id grammar, the slug against the entry module's slug rule, the alias folder against `<slug>-<8 hex>`. `deleteServerReceived` (`src/sync/received.ts`) is the one owner of a server's received deletion (files, rows, search rows, received memories through `deleteReceivedMemory`), called by `remove` and by the sync's start.

`knowledge take <server>:<slug>--<8 hex>` copies a received shared or project entry into the matching own repository under the same uuid as the person's write; it does not call the store's `adopt`, which keeps its one meaning (giving a person's bytes back into the repository); from then on the own entry is what the results show for that uuid, and the received copy is kept but hidden until the next received revision replaces it.

Received memories take part in retrieval like imported ones, marked `(team: <server name>)` in the note's origin, and take at most a third of a brief's budget and of a prompt's notes (`RECEIVED_SHARE`), after the person's own; the rows of a muted server or member (the member read through `sharing_received_memories`), of an alias not bound to the server (through `sharing_levels`) and of a server with no `sharing_servers` row are left out. `history replace-imports` narrows to `imported` rows whose `judge` is not `team:…` (ADR 0025's own rule); `rejudge` stays `claude-mem`-only.

### Conflicts (D-2, D-8)

The sync writer is a third `Writer` kind, `{ kind: "sync"; serverId; serverName; member: { id; name } }`, handled by its own store functions and never by `writeEntry` (which throws on it; every `writer.kind` switch names `sync` explicitly, `author.ts`'s `identityOf` and `authorOf` included): a commit of an applied revision has the author `<member name> <<member id>@members.wizardingcode.invalid>` and the committer `wizardingcode-mem sync <sync@<serverId>.wizardingcode.invalid>`, and the message `sync: apply <uid> revision <n> from <server name>`; its intent record carries the operation `apply`; `applyRevision` returns the new version and hash. On a conflict the file takes the server's revision (verbatim but for the local `pinned` line); the local text becomes a proposal through `proposeConflict` (the exported wrapper over the store's private `propose`, for the sync writer only: the local text parsed into the proposal's fields with the `pinned` line dropped, redacted as every proposal is, both quotas skipped, `base_version` the file's new version and `base_hash` its hash, `proposed_by: sync:<serverId>`, `on_behalf_of` the person's name), whose file is committed under the person's own identity with the sync as committer, since it holds the person's text; and a `sharing_conflicts` row keyed by (server, uid, at) keeps the local text, version and hash, the server's revision and hash and the proposal id, whatever happens to the proposal and however many conflicts the entry has. Accepting the proposal (`knowledge accept`, the viewer later) writes the person's text as a new version, which the next sweep sends on the server's current base; rejecting keeps the server's. A conflicts row is open while its `resolved_at` is null: `knowledge accept` and `knowledge reject` (the CLI, after the store's write, through `closeConflict` of `src/sync/conflicts.ts`; the viewer has no accept or reject route for knowledge proposals in this part) close the row by its `proposal_id`, and the sync at its start closes every row whose proposal is not in state `open`, or is gone, so a crash between the store's write and the close leaves no row open for ever; `status`, `doctor`, `share server remove`, the viewer and the session-start line of the knowledge module count the open rows.

### Restore of the client store

Why the restore carries the sharing tables: a restored copy is older than the live store, and the server cannot give the ledger back. An own item the server holds that the restored ledger does not know would read, at the snapshot, as a teammate's revision (the own file overwritten by the server's revision, or a false conflict); the withdrawal of the old generation's memories needs the `sent` rows; a refusal not carried re-sends a refused hash; a conflicts row holds the server revision and hash the rollback test needs. So the carry copies eight tables, server by server, into the raw copy before the rename, which is the restore's one commit point: a failure before it changes nothing, and nothing is owed afterwards. `backup --restore` runs these steps:

1. Sets the stop flag and waits for the sync's lease (at most 30 s; a refusal says `sync stop` first).
2. Freezes the live store and reads from it, for every server the live list holds: `sharing_servers`, `sharing_muted_members`, the ledger's `sent` and `applied` rows whole (withdrawn included), `sharing_sent_hashes`, `sharing_refusals`, `sharing_conflicts`, `sharing_pending_rows` and `sharing_unbound`. A failure here fails the restore with nothing changed.
3. Refuses, with nothing changed, a `-wal` or `-shm` file beside the unpacked copy (`.restore-<time>.db` in the work folder); then opens that file through `openStoreFile` (a wrapper of `src/store/db.ts` over `openFile`, which takes a file, unlike `openDb`, which opens the store's fixed name, followed by the module migrations) with the module list and the upgrade's own backup copy disabled (`{ upgradeBackup: false }`, a restore-only option, reaching the core and the module upgrade alike), so a copy at sharing 1 or knowledge 7 gains sharing v2 and knowledge v8 before anything is written into it.
4. In one transaction on the copy (`carryIntoCopy`, with `resetSharingInCopy`, both in `src/backup/backup.ts`): replaces the copy's rows of the eight tables, server by server, with the live ones (so no refused hash is re-sent and no conflict's text record is lost); deletes the copy's sharing rows of any server the live list did not hold, table by table (ledger rows, sent hashes, refusals, conflicts, pending rows, unbound rows, mutes); resets every level to Nothing (`resetLevels`, ADR 0025); clears every `sharing.restore_hold:*` and `sharing.resume_authorised:*` key and every stale `sync.*` mark the copy carried, and sets the hold key of every listed server (D-10, reason `restore`); sets `snapshot_due` on every server; then sets `journal_mode = DELETE` on the copy (so no side file holds a carried row) and closes it, and refuses the rename if a `-wal` file is still beside the copy. A failure here fails the restore with nothing changed, the copy discarded.
5. Renames the live file to `<db>.replaced-<time>` (kept, as today) and puts the copy in its place; the token file is outside the backup and is kept.
6. Reports the counts and names the pending deletion of the unlisted servers' received copies (`knowledge_received` rows, their search rows, files, received memories), which `deleteServerReceived` performs at the sync's next start, before the re-index (`sync --once` runs the start's steps even with no server listed; the report says to run it when the live list is empty); until that start the reads return none of that server's items, since they read listed servers only.
7. Afterwards: while a server's hold is set, its withdrawal sweep does not run; `status` says `withdrawals held since the restore: set the levels, then share server resume`, and only `share server resume` clears it. The old generation's `sent` memory rows are withdrawn by the first sweep after the hold clears; the sync's start re-indexes `knowledge/received/` (a restore unbinds nothing, so the received project copies survive it, hidden until their projects are bound again), and the snapshot brings back received memories the copy lacked. A copied-whole data directory is the known limit above.

### Status, doctor and the log

`status` prints the sync's state (`sync: running (pid), idle since …`, `stopped by <who> …`, `start failed <reason>; next try at …`, or `not running; starts with the next session or sync --once`) and one line per server: name, host, member, the state (`pending`, `ok`, a stop with its remedy, `token missing: rejoin`), cursor, last push and pull (attempt and success), backlog, dirty paths, pending rows, open conflicts, and a held withdrawal with its reason and the count (`restore`, `bulk`). `doctor` adds `sync`: the token file's mode and its orphans (a token for no row, a confirmed row for no token), a non-https URL, a stopped server with its remedy, a dead lease holder, a stale stop flag, a failed-start mark with its reason, a server with no successful run in 24 hours while a session ran, open conflicts, pending rows, a held withdrawal; it touches no network. `share explain --server` prints an item's ledger history (sent at, revision, refused with reason and rule, purged, received, applied, withdrawn and why). The sync logs errors only, through `logError(ctx, serverId, operation, error)` (`src/sync/log.ts`) under `sync.<serverId>.<operation>`: one line per distinct message per server and operation, with a count kept in memory until the message changes, never a token, a code or a payload; `last_error` is stored through `redact`.

### The viewer (D-3)

A `Servers` card under Settings, above Sharing: the list (name, host, member and role, state, last sync), Add (URL, code, label; the would-leave counts and a confirmation before the yes; a pending row shown as such with a Confirm button), Rejoin (a code), Remove (a confirmation naming what is deleted), Mute, and Resume (the withdrawals the sweep would take back, per project, and a confirmation) while a hold is set. The Sharing card's texts name the server; with several servers, a selector picks which server's roots and areas the switches edit (the env file's lists stay the ceiling, said on the card); the two sentences that said nothing is sent until a server is configured (one in the Sharing card, one in the project dock) change to name the listed server, and the copy test changes with them. The project dock's selector gains "Receive only", names the bound server and, with several, lets the person pick one. Routes (their request and answer shapes are in the plan): `GET /api/servers` (no token), `POST /api/servers` (url, code, label; answers the counts and `confirm: true` with the pending row until a second call with `yes`), `POST /api/servers/<id>/rejoin`, `DELETE /api/servers/<id>` (`withdraw`, `yes`), `POST /api/servers/<id>/mute|unmute`, `POST /api/servers/<id>/resume` (`yes`), `GET /api/sync` (no token), `POST /api/sync/run`; the dock and the Sharing card send the chosen server's id with a level or a list when several are listed. Pages (AC-90, which superseded AC-24 after the first review round): `/settings#servers` (states: empty, listed, adding, confirming, pending, error, stopped, rejoining, removing, resuming, token-missing, held, muted, unavailable), `/settings#sharing` (states: one, several), `/projects` dock (bound, choosing, receive, sent, widening); viewports 360, 768, 1280; schemes light and dark; motion: none. Design: the viewer follows WizardingCode's app pattern as CLAUDE.md states it (the dark frame, the grouped lists, the 320px dock, the compact type scale), with no `DESIGN.md` of its own, and the Sharing card's conventions of ADR 0025 D-18. The UI evidence is the session's captures under `review/ui/` with their manifest, taken with the Bun script over the Chrome DevTools protocol the earlier parts used (the project has no e2e suite: the standing skip in `policy.json`).

## Alternatives considered

- Received entries in the person's own repositories: rejected (a purge cannot erase git history; unmarked text in the pins and the floor; teammates' workspace entries colliding with the person's and refused `not-owner` after a local edit).
- A review gate before received items are shown: rejected for this part by D-5; the marker, the pin rule, the cap and the mute stand in; the apart storage keeps a gate possible.
- The token in the database: rejected (backups, buckets and store copies would carry a credential; two machines would share one device).
- A file watcher or a signal from every writer: rejected (polling `PRAGMA data_version` is one read every two seconds, and no writer need know the sync).
- The sync inside the viewer or the MCP server: rejected by D-1 (neither runs in every session; the viewer is not started over SSH or in CI).
- Env keys per server: rejected (opaque ids in a hand-edited file, and per-server keys in the env file would read as hand edits); the env file stays the ceiling and per-server lists live in the database.
- A proposal kind "sync conflict": rejected (`kind` is the entry's kind); `proposed_by: sync:<serverId>` and a conflicts row carry it.
- "Absent from the snapshot is gone" for every local item: rejected (it would delete the person's own entries after a server restore); only received copies are dropped.
- A received `knowledge_repos` row per server: rejected (the table's scope check and unique key would need the table rebuilt under foreign keys); a separate `knowledge_received` table joins the search by the reserved repo id 0.
- A pull naming every local project not bound to another server (D-9's alternative): it would need no step per project on a second machine, but each server would learn the names of every project the person did not bind to it, in a query string that proxies log; rejected by the person on 2026-11-10 (D-9).
- Alias groups of 100 with a cursor per group keyed by their sorted aliases: rejected; the server answers `scope=all` with up to 100 aliases (always with the shared scope and the workspaces) or `scope=project` with one alias, so a group pull would re-read the shared corpus per group and the comparison would have to disown rows; the main pull plus one cursor per extra alias is what the server supports.
- A refusal at the 101st bound project: rejected; the extra aliases cost a plain pull each at the sixty-second mark and keep the cap out of the product's limits.
- Withdrawing everything after a restore (the levels reset to Nothing), or clearing the hold at the first `setLevel`: rejected; one `setLevel` would release the withdrawal of every other project's items unseen; the hold is released per server by `share server resume` after a preview and a yes (D-10), and the same hold covers a bulk withdrawal a sweep would make on its own.
- Refusing restore, move and compact while the sync runs (the base's `busy`): rejected; they stop the sync through the flag and wait for its lease.
- A restore carry of the server rows and the mutes only, letting the snapshot rebuild the ledger, or of those and the `sent` rows: rejected; the snapshot tells an own item from a teammate's by the ledger, so a restored ledger that lacks an own item has the server's revision overwrite the own file, and without the refusals and the conflicts a refused hash is re-sent and the rollback test loses its record.
- The carry after the rename, with owed and done marks, a carry retried at the sync's start and a `doctor` check for replaced files: rejected; the raw copy can be upgraded and written before the rename while the live store is frozen, which makes the rename the one commit point and removes the recovery machinery.
- A `removing` state per server with a busy mark the loop checks before every page, for `share server remove`: rejected; the one stop flag stops the sync for the removal and the next spawn restarts it.
- A breaker shared with the judge's (`src/judge/breaker.ts`): rejected; the sync's breaker state lives on the server's row, and the judge's is keyed on one `meta` key and its own error kinds.

## Risks and mitigations

- Risk: a loop against the server (re-sends, hot pulls) using up the device's rate limits (ADR 0026 D-15). Mitigation: stored refusals and purged keys, the memory `stale` rule with its stored marker, the empty-page rule, the breaker, `Retry-After`, the `local_hash` fed to `decide`, the tick that moves only on other connections' commits; the server's `serve revoke` remains the operator's stop.
- Risk: a received text steering the agents (any member may push to any bound alias, ADR 0026, and the floor's false-injection rate was measured on 18 entries, ADR 0024; a team's corpus is larger), or a teammate's revision of a pinned own entry entering the brief under the person's pin. Mitigation: received items kept under `knowledge/received/`, marked, never pinned (pins never leave or arrive), at most one received entry on the floor per prompt and none in the brief's pinned block, a third of a brief, can be muted per server or member; a revised pinned entry has its pin held until the person edits or re-pins it; the person's own items first.
- Risk: the copies of a project no longer pulled going stale or missing a purge. Mitigation: the reads return project items only for aliases bound to the server, so a copy no pull refreshes never reaches an agent; a re-bind's snapshot refreshes them.
- Risk: a withdrawal the person did not mean (a repository unmounted or renamed, a branch without the knowledge files, a restore). Mitigation: no withdrawal for a missing, refused or unindexed repository; a bulk withdrawal and a restore hold under D-10 until `share server resume`.
- Risk: the first run's cost (the server's applied-payload limit of 64 MiB an hour per device, ADR 0026 D-15). Mitigation: live changes first, batches by bytes, the backlog in status, retries from the limit's refill.
- Risk: git work in a long-lived process. Mitigation: received entries have no git; own-file applies are under the repository lease and verbatim; no apply holds the lease across the network.
- Risk: the hooks' busy timeouts against the sync's writes. Mitigation: chunks of 50 rows held under 50 ms, files, vectors and the dedupe map outside the transaction; measured on wall time by AC-75's test on its fixture. `share server remove` and the restore's carry write or delete a whole server's rows in one transaction, which can take longer than 50 ms: they are CLI operations, and a hook that meets the lock skips its write and exits 0 (it fails open, as ADR 0027 states).
- Risk: a sync that fails at every start spawned on every prompt. Mitigation: the failed-start mark and its backoff; `status` and `doctor` name the reason.
- Risk: the sweep's cost on a busy session (the hooks commit on every prompt). Mitigation: the tick's sweep runs at most once per five seconds over the rows that changed, with the withdrawal sweep and the full comparison at the sixty-second mark only; AC-76 measures a quiet tick sweep on the fixture.

## Non-functional requirements

- Latency: a change made from a quiet state reaches a connected machine in under 5 s when the server wakes the held pull on its in-process signal (ADR 0026), and in under 10 s when it falls back to its 5 s poll or when the change is made during a burst of writes (the tick's sweep is coalesced to one every five seconds); the path is the sync's 2 s tick, the push, the server's wake, the pull and the apply; proven in-process under the test's clock; on a real network the round trips are added and are not measured by this part.
- Hook cost: one statement and one `process.kill(pid, 0)` per spawn decision, nothing on a store without the sharing schema; no network; the snapshots and the perf budgets unchanged, the one-time upgrade copy aside (AC-56).
- The sync's memory and time: a page at a time (500 items, 2 MiB) and a batch at a time; the tick's sweep reads only changed rows (at most once per five seconds), the full sweep at the sixty-second mark; memory hashes only for rows that changed, or for every row after a widening or a restore.
- Security: the token in a 0600 file, never in the database, logs, URLs, routes, outputs or backups; `https://` outside loopback; no redirect followed (`redirect: "error"` on every request of the client: join, `me`, push, withdraw and pull); redaction of every text that leaves; the contract header on every request; request ids recorded; every server-supplied path component checked; the received tree under the store's guards; nothing of a server this machine no longer lists, or of an alias no longer bound, reaches an agent.

### Rollback

- A binary downgrade to 0.6.0 or the 0.7.0 of part 5: sharing v2 and knowledge v8 are add-only with defaults; an older binary reads no `team` row (every level reads Nothing until it writes one), its `setLevel` for a project bound to a server fails on the unique index with a constraint error, and the `team` rows it writes are removed by the next upgrade's `reconcileLevels` with a logged change. No released binary older than this part spares `team:…` rows in `history replace-imports` (the narrowing is this part's), so running that command on a downgraded binary deletes received memories: ADR 0027 states it as the downgrade rule. The token file is read by nobody older; `user_version` stays 7, so the 0.5.0 refusal and the 0.6.0 and 0.7.0 opens are unchanged. The sync lease carries the binary's version and a newer binary takes over an older holder.
- On the server: nothing changes but the contract module's exports.

## Acceptance criteria

Ids superseded during the validation and review rounds live in the engine's record (`crew status`); each criterion names the one it supersedes.

- AC-15 (behavior): `share server add <url> --code <code>` against the in-process test server joins, writes the token to `<data dir>/servers.json` (mode 0600; the token in no table, in no route's answer and in no command's output) and the `sharing_servers` row as pending, prints the server's name and the member's name and role, prints the would-leave counts and, without a terminal, refuses to confirm without `--yes`; while the row is pending a sync spawned by a prompt hook sends nothing; the yes confirms the row in one transaction with the `sharing_changes` row `server:<id>` and, for the first server, moves every `team` row of `sharing_levels` and `sharing_ledger` to its `serverId` and copies the env lists into the server's lists, after which `status` reads nothing as a hand edit; a non-https URL outside loopback and `http://localhost.example.com` are refused; a redirect answered by the server is a failure that never follows; a confirmed `serverId` already listed is refused and `share server rejoin` replaces the device and the token keeping the ledger.
