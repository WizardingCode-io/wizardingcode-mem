# Shared names: a project without a git remote shared under a name the person gives

Work item 2026-11-11-005, revision 6. Predecessor: `concepts_brief.md` (the brainstorm's six reviews under `spec-review/`), with D-1 to D-7 answered by the person on 2026-11-11 (`brief.md`, Assumptions). The design records this builds on: ADR 0025 (the sharing policy: a project's identity for a team), ADR 0026 (the team server: the alias, the contract, the schema), ADR 0027 (the sync client: what a pull names, the received store). This item's record is `docs/adr/0028-shared-names.md`. The history of the validation and review rounds is in `conclave.md`.

## Terms

- **Levels**: what a project shares, as the viewer and the CLI name them: Nothing (stored and typed `local`), Receive only (`receive`), Knowledge (`knowledge`), Knowledge and memories (`all`). `local` is the stored form of Nothing.
- **Host-led remote**: a `remote:<host>/<path>` alias whose first segment is a host name (`isHostLedAlias`); a remote that is a local path or a `file://` origin is none. Today the one identity a level binds to.
- **Shared name**: the alias `name:<slug>` a person gives a project so a team can know it by that name. The slug is `slugify`'s text (`src/modules/knowledge/entry.ts`: NFKD, marks removed, lower case, hyphens, 80 characters) held to the stricter grammar `SHARED_SLUG` (no leading, trailing or double hyphen, no reserved file name); a text that leaves no letter or digit, or whose slug is a reserved file name, gives no name.
- **Team alias**: an alias a team may know a project by: a host-led remote or a shared name. `isTeamAlias` in the identity leaf.
- **The identity leaf**: `src/core/identity.ts`, a module with no imports that holds the alias kinds (`ALIAS_KINDS`, `aliasKind`), the slug grammars (`SLUG`, `SHARED_SLUG`, `hasLetterOrDigit`), the three predicates every reader applies (`isHostLedAlias`, `isSharedName`, `isTeamAlias`) and the one SQL fragment a prefilter uses (`TEAM_ALIAS_SQL`).
- **Bound alias**: the team alias a stored level names (`sharing_levels.bound_alias`): the project's identity on that server while the project carries it.
- **Carried**: a project carries an alias while `project_aliases` holds the row for it. A project carries at most one shared name (migration 8's index).
- **The registry**: the server's `names` table: one row per shared name the team holds, with an id minted at creation, the member who created it and when. A push under a name the registry does not hold is refused.
- **Name id**: the registry row's id (16 hex characters). The client stores the id it created or joined (`sharing_levels.name_id`), and every feed item under a shared name carries the id the registry holds now, so a client can tell a name re-created after a purge or a restore from the one it joined.
- **Create** and **join**: the two ways a person binds a project to a name. Creating writes the name into the registry; joining binds to a name the registry holds. The dock and the CLI tell the two apart before anything is written, and each needs the person's explicit yes.
- **Leave a name**: set the project to Nothing (which withdraws what it sent, ADR 0027). The project keeps the name; at Nothing it can **forget** it (the alias row removed) or take another.
- **The contract spoken**: `sharing_servers.contract`, the contract this client speaks to one server: the lower of this binary's `CONTRACT` and the server's, read from the join, from `/v1/me` (at each sync start, at each full sweep while it is below `CONTRACT`, and once before the dock or the CLI refuses on it), from a 409's accepted list, and from a bare 404 on a names route (a 0.7.0 server).
- **Names held**: the state of a server whose contract spoken is 1: the client keeps shared names out of its pulls and pushes to it, refuses to create or join a name against it, and says so in `status`, in `doctor` and on the Servers page.
- **The contract seam**: the server's `Context.contract` (`{ current, accepted }`), the constants by default; a test server started with `current` 1 behaves as a 0.7.0 server (accepts `[1]`, answers 1 on `/v1/me` and the join, has no names routes).
- **No request** (in the criteria and the journeys): no `POST` reaches the server; the one read-only lookup `prepareBinding` makes before a question is allowed.
- **Judge** of a received memory: its `judge` column, `team:<serverId>`, the provenance ADR 0027 gives a memory a teammate sent.

## Problem

A project that is not a git repository on a host cannot be shared with a team today. This item lets a person give such a project a name, share it under that name as they would share any other, and lets teammates join it by the same name.

A team server and its sync carry a project's knowledge and memories between members, and two machines match a project by the same alias: the project's git remote on a host (ADR 0025 D-16, ADR 0026 "The alias", ADR 0027 D-9). A project with no such remote cannot be set above Nothing: `setLevel` refuses `no-remote`, the dock disables the levels and says "This project has no git remote. A team can only match projects by their remote", and ADR 0025 lists the case as a known limit. On the author's machine, read on 2026-11-11, 149 of 158 projects have no `remote:` alias; the one they named, `wizardingcode` at `~/Projects/wizardingcode` (a `path:` alias only), holds the work done in Claude Desktop and Cowork (skills, strategies, brand systems) in 61 active memories, none imported and one stale; the stale one stays by ADR 0025's status rule, so 60 would leave under Knowledge and memories. The requirement, in the author's words: "não é preciso um remote host, tem que deixar partilhar mesmo sem remote host … tudo é partilhado" (a remote host must not be needed; sharing must work without one; everything is shared). Once this item works, a person names such a project once, sets its level as for any other, the team's server holds the name, a teammate binds a project of theirs to it, and what the policy allows moves both ways; two unrelated projects with the same name never merge in silence; an older binary or an older image refuses the newer schema instead of losing the team's copy; and `status`, `doctor` and the viewer say what is held and why.

## Goals

1. A project with no host-led remote is shared under a name the person gives, bound to the server under `name:<slug>`, with the levels, the roots, the areas, the confirmation and the ledger unchanged.
2. The server knows the names: a registry (create once, join from the list), the alias accepted beside `remote:` in the uid grammar, the push, the pull, the feed and the mirror; a list of names any member reads; contract 2 with 1 accepted; the operator's erasure of a name.
3. A teammate binds a project of theirs to a name from the list or by typing it, after an explicit yes, and receives the team's copy as for a remote-named project.
4. The identity rule lives in one leaf, applied by every reader, the SQL prefilters included; the bound alias wins while the project carries it.
5. An older binary refuses the newer store and an older image the newer database (store version 8, team schema 2); names are held while the contract spoken is 1 and released at the next full sweep while the sync runs, or at the next dock or CLI action; every local refusal is decided before the server is asked; a name re-created on the server is told from the one a client joined; `status`, `doctor` and the viewer read out each bound name.
6. The dock and the CLI show create and join as two states, confirm each by name, say `` Shared as `<slug>` ``, name the refusals (`has-remote`, `name-taken`, `renamed`, `no-name`), count the imported memories that stay, say "leave this name" instead of "rename", and the README and the runbook say the same.

## Non-goals

- Binding a local folder to a `remote:` alias picked from a list without a clone: a remote alias is written once and names one project for good (`resolveProject`), so a hand-bound alias would capture the real clone when it appears.
- A rename as a server move (uids rewritten, a delete and a new entry on every machine); a member-facing or admin API route that renames or deletes a name (the operator's `serve purge name` is the erasure path of this item; an admin's route is a later item).
- A project with no folder created from the viewer, for a teammate who only receives or for Claude Desktop's chat (D-7): a teammate binds an existing project of theirs; the README says so.
- A change to what imported memories do (D-6): ADR 0025 D-19 stays; the count that stays is shown. A per-project opt-in is a later item.
- `name:` among the knowledge manifest's strong aliases (`src/modules/knowledge/resolve.ts`): a name a person can leave is no permanent tie; ADR 0024's and ADR 0025's limit stays open. `resolve.ts` ranks `name:` as a weak alias already and needs no change; `resolveRepo` writes every alias of a project into the project repository's manifest and commits the ones it gains, a `name:<slug>` included (one later forgotten too), as a weak alias that ties nothing.
- A server-minted project id (the registry's id is its seed), a per-name access rule (the alias filter stays minimisation, ADR 0026 D-11: any member may pull any alias, a held name included, which ADR 0028 says in one sentence), a search over names, an admin's route that purges a name (the operator's command is this item's; the conclave's O-3), a local move of a name and its level from one project to another (the folder-moved limit below).
- The semantics of the two prefilters that ask about git remotes and not about a team's identity: `resolveProject`'s `hasRemote` (`src/core/project.ts`, a folder reused by another repository) and the link suggestions' remotes (`src/links/suggest.ts`, the same remote owner). Both stay `remote:` by meaning. On the client, `knowledge_received.remote_alias` keeps its name (it holds team aliases of both kinds); only the team's four columns are renamed (D-4), and ADR 0028 says so.
- A Team view in the viewer; editing a received entry.

## Sizing

The author's store: 158 projects, 149 without a `remote:` alias; the named project 61 active memories, 60 would leave at Knowledge and memories; machine-wide 67,295 of 71,935 active memories are imported and never leave (D-19). An assumption with that one machine as its measure: a team of a few members names tens of projects, not thousands. The list of names is paged at 50 and capped at 200 a page because the endpoint checklist refuses a list with no limit and the feed's paging is the shape the client already reads; the two consumers, the viewer's names route and `share names`, reassemble it at this scale. The creates have a bucket of their own (`namesPerHour`, 10 per member per hour), since the devices bucket (600 requests a minute per device) would let one device fill the registry in an hour. The per-name counts on the server are range scans over the rows under each alias (the two indexes of schema 2), bounded by that project's items; on the client, the per-name read-outs are two queries per server (one over `knowledge_received`, one over `sharing_received_memories`).

Effort: the plan has seven phases and twenty-seven tasks; it creates 13 files (the leaf, three migrations, `names.ts`, `binding.ts`, the ADR and seven test files) and copies one capture probe, and it modifies about 45 (the sharing store and levels, the server's store, routes, auth, push, feed, validate, contract, mirror and status, the sync's client, servers, join, run, inbound, outbound, naming, ledger, state and report, the viewer's api, servers-api and server, three Vue components and the viewer's client, the share and serve commands, status and doctor, three ADRs, the README, the runbook, CLAUDE.md, and about twenty test files). The time box is one journey session: part 6's item (2026-11-10-002, the sync client, nine phases) ran from 2026-11-10 to 2026-11-11 in one session, and this item is sized the same. The cost's reason is the three bumps it carries: the client store, the team schema and the contract.

## Critical user journeys

1. **Name a project (the author's case).** Given `wizardingcode` (a `path:` alias only, 61 active memories, a server confirmed at contract 2), when the person opens its dock, then the Sharing section shows a "Shared name" field prefilled `wizardingcode` with the sentence ``New: you create `wizardingcode` on <server>`` and the levels enabled; when they choose Knowledge and memories, then a confirmation says ``Create `wizardingcode` on <server>, visible to every member, and share knowledge and memories of wizardingcode as it?`` followed by `0 knowledge entries and 60 memories would leave.` (no line about imported memories, since none stay); on the yes the viewer decides every local refusal first (a dry run of `setLevel`), creates the name on the server, binds the level to `name:wizardingcode` with the name's id, the dock says `` Shared as `wizardingcode` ``, and the next sweep sends the 60 memories, each keyed under the name.
2. **A teammate joins.** Given the name on the server, when a teammate opens the dock of a project of theirs with no host-led remote and picks `wizardingcode` from the field's list (``Joins `wizardingcode` · created by André · 0 entries, 60 memories``) and chooses Receive only, then a confirmation says ``Join `wizardingcode`, created by André (0 entries, 60 memories), and receive it into <project>?`` followed by `Nothing of <project> leaves.`; on the yes the binding is written with the name's id, the next pull names `name:wizardingcode`, the memories land as `imported` rows of their project with the judge `team:<serverId>`, entries (when any) land under `knowledge/received/<serverId>/projects/wizardingcode-<8 hex>/`, and their sessions in that project read them as any received item. No level joins or creates a name without that yes, Receive only included.
3. **A collision avoided.** Given a name `docs` on the server created by Ana, when Bruno types `docs` for an unrelated project, then the field says ``Joins `docs` · created by Ana · 14 entries, 3 memories`` before anything is written, and the confirmation would name the join; Bruno types `docs-mobile` instead, sees `New`, and creates it. Had Bruno confirmed `docs` as new while Ana created it between the list and the confirm, the server answers `exists`, nothing is written, and the dock shows the join state for a second confirmation.
4. **The server is still 0.7.0.** Given a client at this version joined to a 0.7.0 server (the contract spoken is 1), when the person opens the dock of a project with no remote, then the field is disabled with `The server speaks contract 1; shared names need its upgrade.`, and a `PUT` with `as` asks `/v1/me` once and, the answer still 1, is refused 409 `contract`. For a name bound before the server was rolled back, the pull omits the name's alias, the sweep skips the project's items, `status` prints `names held (server at contract 1)` on the server's line, `doctor sync` warns, and the Servers page says it; the sync asks `/v1/me` again at every full sweep (every 60 s) while the row speaks 1, so within a minute of the server's upgrade the row reads 2 and the next pull names the alias again.
5. **A named project gains a remote.** Given `wizardingcode` shared as a name, when the person runs `git init` and adds an origin there, then the next session records the `remote:` alias on the same project, the level stays bound to the name (the bound alias wins), nothing is re-sent as a move, and the dock says ``Shared as `wizardingcode`. This project now has a git remote; to match by the remote instead, set Nothing, forget the name, then set the level again.``
6. **Leave a name; erase a name.** Given a project shared as `x`, when the person sets Nothing, then this machine's items under `x` are withdrawn (ADR 0027), the project keeps the name, the dock shows the field with `x` and a "Forget name" action; forgetting removes the alias row and logs it; the teammates bound under `x` keep their binding and their copies. Given a name that must go from the server (a typo, a client's or a person's name), when the operator runs `serve purge name <alias> --yes`, then the name leaves every member's list at once, a push under it is refused `name-purged` and the members' docks say the operator removed it; the operator then purges its items one by one; until the first step the name stays visible to every member, and after both the string still sits in the marked `names` row, the `changes` rows (their `uid` and `project_alias`), the withdrawn rows' `project_alias` and the audit rows until `team.db` is restored or rebuilt.
7. **A name re-created.** Given a teammate bound at Receive only to `docs`, when the operator purges `docs` and a member later creates `docs` for an unrelated project, then the teammate's next pull brings items whose name id differs from the one they joined: the items are skipped, the binding is flagged `name-recreated`, nothing is sent under it, and the dock and `status` say ``The shared name `docs` was re-created on the server by <member>; join it again, or set Nothing to leave it.`` Joining again (the level set again with the name, confirmed) stores the new id and the next pull applies the items.
8. **The CLI.** Given a folder whose project has no host-led remote, when the person runs `share project all --as "Estratégia de marca" --create`, then the local refusals are decided first, the question ``Create `estrategia-de-marca` on <server>, visible to every member, and share knowledge and memories of <project> as it?`` is asked with the counts (`--yes` answers), the slug is created on the server, the level is bound, and the answer prints `sharing: <project> → Knowledge and memories, shared as estrategia-de-marca`; without `--create` against a name the server does not hold, the refusal names `share names` and `--create`; `share names` lists every page of the server's names with their counts and marks the ones this machine is bound under; `share name forget` in the folder forgets the name at Nothing.
9. **A rollback.** Given a store at version 8, when a 0.7.0 binary opens it (a Homebrew install left on PATH, or a downgrade), then it refuses with `SchemaTooNewError`, `doctor` fails its database check, hooks fail open, and no level is deleted and nothing is withdrawn; given `team.db` at schema 2, when a 0.7.0 image starts, then it exits 3 and the runbook's rollback (the upgrade's copy) applies; given a `team.db` restored to a copy older than a name, when the clients detect the renewed instance, then they re-send the items under remote aliases that the copy lacks, and a project bound to the lost name is refused `name` until the person sets its level again, which re-creates the name with the id their level row holds, so the teammates stay bound (a re-creation from a machine that never held the id mints a new one, and the teammates join again).

## Proposed architecture

### The identity leaf (`src/core/identity.ts`)

A module with no imports. It holds:

- `ALIAS_KINDS`: the five kinds an alias in `project_aliases` can be, each with whether it may name the project to a team (`team`): `remote` (team when host-led), `name` (team), `gitdir`, `path`, `imported` (not). A new kind is one entry.
- `aliasKind(alias)`: the kind by prefix, `null` for an alias of no kind.
- `SLUG` (`entry.ts`'s pattern, `^[a-z0-9][a-z0-9-]*$`, which `entry.ts` imports from here so the two files hold one pattern), `SLUG_MAX` (80), `RESERVED` (`con`, `prn`, `aux`, `nul`, `com1`-`com9`, `lpt1`-`lpt9`), and `SHARED_SLUG`: `SLUG` without a trailing or a double hyphen (`^[a-z0-9](?:-?[a-z0-9])*$`), at most `SLUG_MAX`, not `RESERVED`. Every shared slug is a slug; not every slug is a shared slug (`abc-` and `a--b` are slugs and no shared slug).
- `hasLetterOrDigit(text)`: whether a letter or a digit survives NFKD, the marks removed and the case folded; the check `src/team/contract.ts`'s `slugOf` makes before `slugify`'s `entry` fallback, now imported by it and by `sharedNameOf`.
- `isHostLedAlias(alias)`: moved here from `src/sharing/levels.ts` byte for byte (the `HOST` pattern included); `levels.ts` re-exports it, so its importers do not change.
- `isSharedName(alias)`: `name:` followed by a shared slug.
- `isTeamAlias(alias)`: a host-led remote or a shared name.
- `TEAM_ALIAS_SQL`: the fragment `(substr(alias, 1, 7) = 'remote:' OR substr(alias, 1, 5) = 'name:')`, for the three prefilters that read the alias table before the predicate runs (`src/ui/api.ts` `listProjects`, `src/sharing/report.ts` `entryAliases`, `src/sync/inbound.ts` `projectAliases`); each still judges every row with `isTeamAlias` in code.
- `NAME_PREFIX` and `REMOTE_PREFIX`; `stripTeamPrefix(alias)`: the alias without its prefix, for the folder slug (`repoFolder`).

`src/team/contract.ts` imports the leaf instead of `src/sharing/levels.ts`; `src/team/feed.ts`, `src/team/validate.ts` and `src/sync/naming.ts` import `isTeamAlias` from it; `src/modules/knowledge/entry.ts` imports `SLUG`, `SLUG_MAX` and `RESERVED` from it. The boundary tests (`tests/unit/sync-boundary.test.ts`, `tests/unit/team-store-boundary.test.ts`) constrain neither `src/core/` nor its importers, so they need no change; `src/modules/knowledge/resolve.ts` is unchanged.

### The name of a project (`src/sharing/names.ts`, `src/sharing/store.ts`)

`src/sharing/names.ts` (imports `slugify` from `entry.ts` and the leaf): `sharedNameOf(text)` returns `{ ok: true, alias: "name:<slug>" }` when `hasLetterOrDigit(text)` and `slugify(text)` passes `SHARED_SLUG`, else `{ ok: false, reason: "no-name", word?: string }` (the word when the slug is a reserved file name: nothing is appended behind the person's back); `nameOf(aliases)`: the one `name:` alias a project carries, or null.

`setLevel` (`src/sharing/store.ts`) gains three inputs: `as?: string | null`, a shared name alias (already slugged by the caller through `sharedNameOf`); `nameId?: string | null`, the registry id of the name created or joined, stored in `sharing_levels.name_id`; and `dryRun?: boolean`, which runs the whole chain below inside a deferred read transaction (`db.transaction(fn)()`, never `withWrite`'s `BEGIN IMMEDIATE`), writes nothing, and answers what the write would answer. Its refusals, in this order, after `invalid` and `no-project`, with `local` still removing the row and nothing else (the name is kept):

1. `disabled` (memory off).
2. `has-remote`: `as` given and the project carries a host-led remote and no name (`this project is matched by its git remote; a teammate adds the same remote to join it`).
3. `renamed`: `as` given, different from the name the project carries, while a level above Nothing is stored for any destination (``this project is shared as `<name>`; set it to Nothing first to leave that name``).
4. `name-taken`: `as` is another local project's alias (``` `<name>` is the shared name of `<other project>`; that project forgets its name at Nothing ```). Read inside the transaction; the alias table's primary key refuses the insert either way.
5. `no-name` (replaces `no-remote`): no `as`, no bound alias still carried, no name carried, no host-led remote (`this project has no git remote; give it a shared name`). `no-remote` goes from `SET_LEVEL_MESSAGES` and from `REFUSAL_STATUS`; its tests change to `no-name`.
6. `one-server`, as today.
7. `needs-confirm`: a widening without `confirm`, as today; and, new, a binding that creates or joins a shared name without `confirm`, at every level, Receive only included. The dry run judges it from what the store holds: `as` given and no stored row bound to that alias, or a stored row bound to it whose name carries the re-created flag; a stored row bound to the same alias with no flag is a no-op. The id is compared and stored at the write, with the item the server answered.

The alias a level binds to (`aliasToBind`, widened): the alias the level is bound to already, while the project still carries it and it is a team alias; else `as`; else the name the project carries; else the host-led remote the caller names (the folder's); else the project's first host-led remote by alias bytes, ascending. The name comes before the remotes, so a named project that gains a remote keeps the name (journey 5). With `as` and no stored level above Nothing, a name the project carries that differs from `as` is replaced: the old alias row deleted, the new inserted, one change row `name:<project id>` from the old alias to the new. The insert of a new name alias happens inside `setLevel`'s write transaction, before the level row; `name_id` is written with the row and replaced when the person joins a re-created name.

`forgetName(db, projectId, now, source)`: refused `name-bound` while a level above Nothing is stored for the project on any destination, `no-name` for a project with no name, `no-project` for an id the store does not know; else deletes the project's `name:` row, logs `name:<project id>` from the alias to `""` and bumps the counter once.

`effectiveLevel` (`levels.ts`): a row bound to an alias the project lost, or to an alias that is not a team alias, reads `unbound-alias`; the texts (`REASON_TEXT`, `LEVEL_PROBLEMS`) say "git remote or shared name". `reconcileLevels` is unchanged in logic: a lost name's row is removed as the system's. `boundAliasesOf` is unchanged: it joins `project_aliases` on the bound alias, so a name is a pull scope once bound. `src/sharing/levels.ts` gains `defaultTeamAlias(aliases, folderRemote)`: the candidate order above without a stored row, for `entryAliases` (a preview of a level on a project with no row) and the dock's prefill.

The sharing namespace moves to version 3 (`src/sharing/migrations/0003_sharing_names.sql`, add-only: `ALTER TABLE sharing_levels ADD COLUMN name_id TEXT`), which `module_migrations` records and `tests/unit/module-migrations.test.ts` pins; `user_version` is moved by migration 8 alone.

**The two-phase write and its race.** The viewer route and the CLI run `setLevel` with `dryRun` first, so every refusal that does not depend on the server (`invalid`, `no-project`, `disabled`, `has-remote`, `renamed`, `name-taken`, `no-name`, `one-server`, `needs-confirm`) is decided before the server is asked; then the server is asked (create or join); then `setLevel` writes, with the name's id. Between the dry run and the write another process may change the project (memory turned off, a binding to another server from a second viewer): the write then refuses, and a name created a moment before stays on the server with nothing under it. The answer says so (`named: true` beside the refusal, and the one sentence ``the name `<slug>` was created on the server; set the level again to use it, or the operator purges it``); the dock shows the join state next time, since the registry holds it. The window is the one HTTP round trip; the risk is recorded below.

**`prepareBinding` and `commitBinding`.** The two-phase flow is two functions in `src/sync/binding.ts`, beside `join.ts`, which already does "dry run, ask the server, write" for `share server add`: `prepareBinding` (the dry run, the contract read, one `GET /v1/names/<alias>` lookup, answering whether the name would be created or joined and, for a join, the name's item with its creator and counts) and `commitBinding` (the create when so, with the id the creator's level row holds when it re-creates a name it was bound to; the write with the name's id). The CLI asks its question between the two, so the join question can name the creator and the counts and nothing is created before the yes; the viewer's `PUT` runs both, the question having been asked from the preview and the list. They are server calls, so they live in the sync client (ADR 0027's boundary) and never under `src/sharing/`, which the sync imports and which must not know the client. The registry's store functions (`store.ts`, the only SQL): `insertName` (with the id given or minted), `nameByAlias` (the row, purged or not), `liveNameByAlias` (`purged_at IS NULL`), `listNames(after, limit)` (the live rows by alias, with the counts: current entries and memories by the two indexes, the last `updated_at` of either, the creator), `nameItemOf(alias)` (a live row's item), `nameIdsOf(aliases)` (for the feed: the ids of the live names a page's items are under, one query per page), `currentItemsUnder(alias)` (the not-withdrawn and not-purged entries and memories under an alias, for the purge's print-out), `purgeName(alias, at)`, `countNames` (the live rows).

**The contract seam.** `Context` (`src/team/types.ts`) gains `contract: { current: number; accepted: readonly number[] }`; `startServer` takes it as an option and `serve` passes `CONTRACT` and `ACCEPTED_CONTRACTS`; `src/team/auth.ts` judges the header against `ctx.contract.accepted` and answers 409 with that list; the join and `/v1/me` answer `ctx.contract.current`; the three names routes answer the route table's own 404 `not found` while `ctx.contract.current` is below 2, so a test server started at 1 is a 0.7.0 server for every case below. `tests/helpers/team.ts`'s `startTestServer` takes `contract`.

Routes (`routes.ts`), each authenticated by a device token and taken from the devices bucket like every other (`withCaller`), each refusing in the server's problem shape:

- `POST /v1/names` `{ alias, id? }`: `isSharedName` or 400 `{ error: "alias" }` (an `id` that is not 16 hex characters too); a live row already → 409 `{ error: "exists", name: <item> }`; a purged row → 409 `{ error: "purged" }`; past the names bucket (`namesPerHour`, 10 creates per member per hour, a bucket of its own beside the devices bucket) → 429; else the row with the id given (when unused) or a minted one (`newHexId`), an audit row `name created` (target the alias), 201 with the item. Any member.
- `GET /v1/names?after=<alias>&limit=<n>`: `after`, when given, must pass `isSharedName` (else 400 `{ error: "after" }`); `limit` 1 to 200 clamped, 50 by default, a value that is not an integer 400 `{ error: "limit" }`; the page `{ items, more, next }` of the live names ordered by alias; an item is `{ alias, id, createdAt, createdBy: { id, name }, entries, memories, lastChangeAt }`. Names only: a `remote:` alias never appears, whatever the server holds under it; a purged name never appears.
- `GET /v1/names/<alias>`: the parameter is URL-decoded and judged by `parseNameParam` (a pure guard, `isSharedName` or null) before any SQL; a malformed alias, a `remote:` alias, a purged name and an unheld name answer the same 404 `{ error: "unknown-name" }`, so the route cannot be used to probe for a remote; a live name answers the item. A parameter whose escapes do not decode never reaches the handler: the router's `match` answers its own 404 `not found` on the `decodeURIComponent` throw, which reveals nothing.

The grammar and the checks: `ENTRY_UID` accepts `project:(remote:…|name:…):<uuid>`, `parseEntryUid` judges the alias with `isTeamAlias`; `checkEntryPayload` and `checkMemoryPayload` (`validate.ts`, pure, no SQL) refuse `shape` for an alias that is not a team alias as today and learn only the new reason `name` and its rule text; the registry check lives in `push.ts`, inside each item's transaction, after the pure checks and `purged` and before the idempotent replay shortcut and the apply (the per-item order: the pure checks, `purged`, the registry for a shared name, the replay shortcut, the ownership rules, the base, the rate and the disk): a send under a shared name the registry never held is refused `name` (`the name is not on this server; create it or pick one from the list`), a send under a purged name is refused `name-purged` (`the operator removed the name from this server`), and a replay under a name purged since is refused `name-purged` too. A move between a remote and a name (an alias change of a uuid, which the server records as a tombstone under the old alias with `movedTo`) needs the new alias live when it is a name; the tombstone under the old alias needs nothing of the registry. `parsePullQuery` accepts team aliases; an alias the registry does not hold answers nothing and is not refused, as an unknown remote is today. Every `upsert` feed item under a shared name carries `nameId`, the live registry row's id for that alias at the time of the page (`nameIdsOf`), or `null` when the registry holds no live row for it; an item under a remote, a `tombstone` and a `purge` carry `nameId: null`. `repoFolder` strips either prefix (`stripTeamPrefix`): `name:wizardingcode` lands in `projects/wizardingcode-<8 hex of the alias>`, a different folder from any remote's. The mirror, the feed's paging and the ownership rules are unchanged in logic.

**The operator's erasure.** `serve purge name <alias> --yes` (beside `purge entry` and `purge memory`) marks the registry row purged (`names.purged_at`), writes the audit row `name purged` and prints the counts of the items still under the alias; exit 1 `no such name` for an alias the registry never held, exit 0 and `already purged` for one marked already. From that moment the name is out of every member's list (`GET /v1/names` and the by-alias route answer as for an unheld name), a push under it is refused with the reason `name-purged` (never offered as "create it"), and a create of the same alias is refused 409 `purged`; the members bound to it need no coordination before the operator acts, and the operator then purges the items under it one by one at leisure (`serve purge entry`, `serve purge memory`), in whatever order. What it erases, and what it does not: the name goes from the list and from the pushes; the string itself stays where the server's own records keep it: in the `names` row (kept, marked), in the `changes` rows (their `uid`, `project:name:<slug>:<uuid>`, and their `project_alias`; the per-item purge turns them into `purge` rows and keeps both; the `purged` table's keys are the entry's uuid or the device's memory key and hold no alias), in the withdrawn entry and memory rows and the `entry_revisions` rows of withdrawn entries that carry it as `project_alias`, and in the audit rows (`name created`, `name purged`, and each per-item `purged` row whose target is the full uid); an operator who needs the string gone restores or rebuilds `team.db`. The runbook's erasure section gives the order (the name first, then the items), says that until the operator does it a name, with its creator and counts, stays readable by every member, and states the limit above; ADR 0028 states both. `serve status` gains `names <n>` on its first line (the live registry's count).

**A purged name on the client.** A push answered `name-purged` is never stored in `sharing_refusals` and never counts toward the breaker: the sweep stops sending the project's items, writes the flag `names.purged:<serverId>:<alias>` (a `meta` key with the time), and sends nothing under the name again; `status`, `doctor`, `share status` and the dock say ``the operator removed `<slug>` from the server; set Nothing to leave it``; nothing is withdrawn by the client on its own (D-10's spirit: no withdrawal the person did not ask for), and Nothing clears the flag with the level.

### The contract: 2, with 1 accepted

`CONTRACT` 2; `ACCEPTED_CONTRACTS` `[1, 2]`; `RESULT_SHAPES` gains `nameItem: ["alias", "createdAt", "createdBy", "entries", "id", "lastChangeAt", "memories"]` and `namesPage: ["items", "more", "next"]`, and `feedItem` gains `nameId`; `PUSH_REASONS` gains `name` and `name-purged`; `CONTRACT_FINGERPRINT` is repinned once; `tests/unit/team-contract.test.ts` pins the new value. A 0.7.0 client speaks 1: it names no shared name in a pull and sends no item under one, so it never receives a name's items (project items arrive only for the aliases a pull names, ADR 0026 D-11) and sees at most a tombstone with a `movedTo` it does not read, which deletes its copy as a move away does today; the added key `nameId` on a feed item it does read is one it ignores (the client reads the keys it knows).

**The contract spoken, and how it is read.** `sharing_servers.contract` (the column the server row has) holds the contract this client speaks to one server: the lower of `CONTRACT` and the server's. It is set at the join to the lower of `CONTRACT` and the join's `contract`. The 409 `contract` with an accepted list is the sync's live path down: when the list holds a value at or below `CONTRACT`, the row is set to the highest such value, the request is rebuilt under the names-held rule below (the pull re-planned without name aliases, the batch filtered of items under names, none recorded as a refusal) and repeated once with the new header; a 409 with no acceptable value stops the server with `contract` and the remedy `upgrade wizardingcode-mem`, as today. A server at 2 never answers 409 to a client speaking 1, so the only way back up is an active read: the sync reads `/v1/me` for every confirmed, unstopped server at its start and, for a server whose row speaks below `CONTRACT`, at every full sweep (60 s), the reads running in parallel with a 5 s deadline each and a failure keeping the stored value; so a hold ends within a minute of the server's upgrade while the sync runs. The dock and the CLI, which may act before the sync has run since an upgrade or a rollback, read `/v1/me` once before refusing on a row below `CONTRACT`, and treat a bare 404 on a names route (a 0.7.0 server reached with a row at 2) as the server speaking 1: the row is set to 1 and the refusal given. The header sent is the stored value (`SyncClient`'s `contract`, made mutable: `speak(contract)`). The contract spoken is shown in `status` (`contract 1`) only when it is below `CONTRACT`.

**Names held.** While the contract spoken to a server is 1: `boundAliasesOf` is unchanged, and the sync's `boundAliases` (inbound) and the sweep's candidate filter (outbound) drop the aliases that are shared names, so the pull names remotes only and no entry or memory of a name-bound project is sent or withdrawn; a `sharing_refusals` row is never written for them; `status`'s server line ends `names held (server at contract 1)`, `doctor sync` warns `names held: the server <name> speaks contract 1; upgrade it (the runbook)`, and the Servers page says it under the server. The viewer route and the CLI refuse to create or join a name against such a server (`contract`), after the one `/v1/me` read above, and nothing is written. The runbook's order: the server first, then the members name projects.

**The `name` refusal on the client.** A push answer `refused` with reason `name` is never stored in `sharing_refusals` (it is a state of the server, not of the item) and never counts as a failed answer (the breaker, `recordAnswer`, is untouched): the sweep stops sending that project's items for this sweep, writes the flag `names.missing:<serverId>:<alias>` (a `meta` key with the time), and retries at the next sweep; the flag is cleared when a push under the name is applied or when the person binds again; `status`, `doctor` and the dock (beside `Shared as`) read it and say ``the server does not hold `<slug>`; set the level again to create or join it``. A project bound to a name the server lost (a restore to a copy older than the name, an operator's purge) is thus re-created by the person setting its level again (`prepareBinding` answers the create state, `commitBinding` creates), never by the sync on its own (D-2). When the creator's own level row still holds the name's id, `commitBinding` sends it (`POST /v1/names { alias, id }`), so the re-created name keeps the id the teammates joined and no teammate has to join again; a re-creation from a machine that never held the id mints a new one.

**A name re-created.** When a pulled `upsert` under a shared name carries a `nameId` that is not null and differs from the `name_id` the level row holds, the item is skipped and the binding is flagged `name-recreated` (a `meta` key `names.recreated:<serverId>:<alias>` holding the new id, the creator and the time, written by the sync, cleared by `commitBinding` when the person joins again or by Nothing); an `upsert` with `nameId` null (the registry holds no live row) is applied as today, and so is every `tombstone` and `purge`, so an operator's purge reaches the teammates' copies and a sender's ledger as it does for a remote; a flagged name is left out of the sweep's candidates and withdrawals (nothing of the project leaves or is withdrawn until the person decides), left out of `compareSnapshot`'s scopes (its received rows are neither counted as seen nor dropped by a snapshot while the flag stands), stays in the pull (so the flag is refreshed), and is read out by `status` (``name `<slug>` re-created on the server by <member>; join it again or set Nothing``), by `doctor sync` (a warning) and by the dock (the sentence of journey 7). Joining again is `prepareBinding` with the carried name (the dry run passes, the lookup reads the item and answers `join`) and `commitBinding`, whose `setLevel` stores the new `name_id`; the next pull applies the items.

## Alternatives considered

- **`git init` plus a remote URL in the folder, no code.** `identify` reads `originUrl` alone, so a URL on a host never pushed to gives a host-led alias today. Rejected: a `.git` folder in a folder that is no repository, nothing for the `imported:` projects that have no folder, and the author asked for sharing without a remote.
- **Names that emerge from slugs, the list as the only warning.** Rejected: two unrelated `docs` projects merge in silence, each member's sessions read the other's knowledge as their own, and the warning is seen once; the registry makes joining explicit at the cost of one table, three routes and one refusal.
- **The server mints a project id; names are labels.** Rejected for this item: a round trip inside `setLevel`, a mapping for remote-named projects, a larger contract change. The registry's id is its seed.
- **A version in `/v1/health`.** Rejected: `/v1/me` carries the contract already, and the list of names moves the contract anyway.
- **Keep the column names.** Rejected (D-4): the four columns now hold names too, and the server's statements and row types would say `remote_alias` of a value that is none; the schema bump that makes a 0.7.0 image refuse comes from the registry table either way.
- **Keep the store version.** Rejected (D-5): a client rollback would withdraw the team's copy with no word to the person.
- **A rename as a server move.** Rejected: uids rewritten, a delete and a new entry on every machine with no log line, the same outcome for the teammates as leaving the name.
- **`name:` among the manifest's strong aliases.** Rejected: a mutable name is no permanent tie, and the manifest is not written where the limit bites.
- **Binding a folder to a `remote:` alias from the list.** Rejected: a hand-bound remote alias would capture the real clone when it appears (the non-goal).
- **The list shows remote-named projects too.** Rejected: every private repository path on the server disclosed to any member, a disclosure ADR 0026 D-11 does not cover; the list shows names only.
- **Create a name lazily at the first push.** Rejected: creation would be invisible, so a second member's "create" of an existing name would join in silence; the create and join states must be shown at the moment the person types the name.
- **Create the name on the server, then decide the local refusals.** Rejected (the architects' return): a refusal after the create leaves a name on the server with nothing under it, and names are not deleted by members; the dry run decides everything local first, and only the one-round-trip race can orphan a name, which the answer then says.
- **Receive only joins without a confirmation (as a level today).** Rejected (the security lead's return): a prefilled `docs` would join another team's unrelated `docs` and pull its content on one click; creating or joining a name is confirmed by name at every level.
- **No erasure of a name (documentation only).** Rejected (the security lead's return): the image has no SQL shell and `serve purge` erases per item key only, so a typo or a person's name would stay on the server with no path out; `serve purge name` is the operator's erasure, under ADR 0026's rule.
- **No name id; the alias alone.** Rejected (the design review): a binding kept at Receive only outlives a purge or a restore, and a name re-created for an unrelated project would feed it with no confirmation, the merge the registry exists to prevent; one id per registry row and one key on the feed item let the client tell the two apart with no extra request.
- **The contract spoken read from the 409 alone.** Rejected (the design review): a server at 2 never answers 409 to a client speaking 1, so a hold would never end while the sync runs; the `/v1/me` read at start and at each full sweep while held, and once on the dock's or the CLI's path, end the hold at the next full sweep while the sync runs, or at the next dock or CLI action.
- **The identity rule as a predicate swap in each file.** Rejected: the three team prefilters and the literal prefixes in `contract.ts`, `repoFolder` and `levels.ts` are easy to miss in a pass over twenty files; one leaf with a table and a fragment makes a third identity one entry.

## Risks and mitigations

- **Two members create the same name between the list and the confirm.** The create answers 409 `exists`; nothing is written; the dock shows the join state and asks again, by name.
- **A name typed by two members for two unrelated projects.** The join state names the creator and the counts before the write, and the confirmation repeats them at every level; the registry refuses a push under an unheld name; the received copies are read-only and marked with their provenance line (`from <member> via <server>`), and a member who joined by mistake leaves the name (Nothing) and forgets it; what they sent is withdrawn by the same step.
- **A name created and then not bound (the race).** The dry run decides every local refusal before the server is asked, so only a change made by another process during the one round trip can refuse the write; the answer says the name was created and how to use or purge it; the registry shows it as a name with nothing under it.
- **A name purged or lost in a restore and re-created for another project.** The feed item's `nameId` differs from the stored one: the items are skipped, the binding flagged, nothing sent; the person joins again or leaves; no silent merge.
- **A name the server lost while a project stays bound to it.** The `name` refusal is never stored in `sharing_refusals` (which keys a refusal by the item's hash); the sweep retries, the dock and `status` say the server does not hold it, and setting the level again re-creates it with the id the row holds.
- **A named project gains a remote and the binding moves.** The bound alias wins while carried; the candidate order puts the name before the remotes; proven by the store test and the sweep test (no move sent).
- **A lost name reads as unbound and the reconcile deletes the level.** A name is lost only by `forgetName`, refused while bound; `reconcileLevels` stays for the disabled and lost-alias cases; the sentence names "git remote or shared name".
- **A client at 2 against a 0.7.0 server.** The 409's accepted list sets the contract spoken to 1, the request is rebuilt under the held rule and repeated once; names held; the dock and the CLI refuse a new name after one `/v1/me` read, and on a bare 404 set the row to 1; the runbook says the server goes first.
- **A hold that outlives the server's upgrade.** The `/v1/me` read at every full sweep while the row speaks below `CONTRACT`, and the one read on the dock's and the CLI's path, end it at the next full sweep while the sync runs, or at the next dock or CLI action.
- **A 0.7.0 client against this server.** Accepted at 1; it never names a shared name, so it receives none; a tombstone with a `movedTo` it does not read deletes its copy, as a move away does today.
- **The column rename under a live server.** `openTeamForWrite` refuses to migrate while the server's lease (`serve.lease`) is not yet expired (`SchemaBehindError`); the image's start migrates before it listens; the copy precedes the rename.
- **The names list and the by-alias route as a disclosure or a probe.** Names only, never a remote; the by-alias route answers one 404 for a malformed alias, a remote and an unheld name; `after` is judged by the grammar; the creator's name is already on every feed item; every route is under the devices bucket and the list is paged.
- **A sensitive or wrong name on the server.** Readable by every member until the operator marks it purged (`serve purge name`, which needs no coordination with the members: their pushes are refused `name-purged` and their docks say so) and then purges its items; after that the string stays in the marked `names` row, the `changes` rows (their `uid` and `project_alias`), the withdrawn rows' and revisions' `project_alias` and the audit rows, and only a restore or a rebuild of `team.db` removes it; the ADR and the runbook say both.
- **A project known by its folder alone whose folder moves.** A `path:`-only project becomes a new project when its folder is moved or renamed (`resolveProject` writes a new row for a path it has not seen), and the shared name stays on the old one. The recovery is stated in the README and the runbook: Nothing on the old project (which withdraws what it sent), forget its name, then share the new project under the same name (which re-sends); a local move of a name and its level from one project to another is a later item.
- **Registry growth.** The devices bucket allows 600 requests a minute per device, so it alone would let one device create tens of thousands of names an hour; the creates have their own bucket, `namesPerHour` (10 per member per hour, 429 past it); the operator's purge is the way out of a filled registry; the list's cap of 1,000 leaves a held name past it shown as `New` until the server's 409 `exists` catches it at the write.
- **The per-name read-outs as a cost on a large store.** Two queries per server, by the indexes `knowledge_received_project` and `sharing_received_memories_uid` plus the alias join; `status` and the Servers page read them, no hook does.
- **A name that is a reserved file name or carries path characters.** `SHARED_SLUG` refuses it on both sides (a reserved word is refused with its name, nothing appended); the folder is `<slug>-<8 hex>` checked by `PROJECT_FOLDER` before any path.
- **Imported memories never leave and the person wonders why.** The count that stays is shown in the dock, the confirmation and `share project` (D-6), counting the claude-mem imports and never a teammate's copy; the README says it.

## Non-functional requirements

- Hook cost: nothing new on a hook path; `resolveProject` is unchanged; migration 8 adds one index and sharing migration 3 one column, each run once per store on the first open by this version (the upgrade copy as for every version).
- Security and privacy: a shared name is a shared slug (no path characters), carried to a folder only as `<slug>-<8 hex>`; the list discloses names only and the by-alias route cannot be used to probe for a remote; the registry's rows name a member id and name already on every feed item; every new route is behind the device token and the devices bucket; creating or joining a name is confirmed by the person by name; `path:` and `gitdir:` aliases still never leave (ADR 0025 D-19); a name leaves only by the person's choice and only once the server confirmed it.
- Performance: the names list is paged (50, at most 200) and its counts are range scans bounded by each project's items; the per-name read-outs are two queries per server; the `/v1/me` reads run in parallel with a 5 s deadline.

- Rollout: the server first (schema 2, contract 2 accepting 1), then the clients (store version 8, sharing namespace 3); the midway check is the end of the plan's phase C: the leaf, migration 8 and the server at schema 2 and contract 2 green against a 0.7.0 client (AC-41's header-1 case) before any client phase; a client that meets a server at 1 holds names and says so; a 0.7.0 client keeps working against the new server.
- Rollback, the client: a 0.7.0 binary refuses a version 8 store (`SchemaTooNewError`; `doctor` fails its database check; hooks fail open), so nothing is deleted or withdrawn; to go back to 0.7.0 the person restores the upgrade's copy from `backups/` (what was written since is lost, as for any version) and the ADR and the release notes say so.
- Rollback, the server: a 0.7.0 image exits 3 against schema 2; the runbook's rollback restores the upgrade's copy; the names created since are lost with it; the clients detect the restored instance and re-send the items under remote aliases that the copy lacks; a project bound to a lost name is refused `name` until the person sets its level again, which re-creates the name with the id the creator's level row holds, so the teammates stay bound (a re-creation from a machine that never held the id mints a new one and the teammates join again); against the 0.7.0 server they fall back to contract 1 and hold names.
